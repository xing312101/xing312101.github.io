GitLab CI/CD 通用核心

一套與語言/框架無關的 GitLab CI/CD 實作基礎：pipeline 觀念與樣式、機密管理、自架 runner，以及部署到自己的主機（deploy repo、用 tag 上正式）。 任何專案（web、後端、mobile…）都能套用；各語言/框架只要在自己的章節補上「build / 測試 / 發佈」的具體指令即可。

note

本系列為通用範例，所有網址、帳號、路徑皆為佔位符，請替換成你自己的值。通用核心只講 GitLab； 各語言的實作範例見該語言章節（例如 Flutter Mobile CI/CD，GitLab 與 GitHub Actions 並列）。 例外是最後一組「發佈給使用者安裝」：GitHub Releases、自己簽章、Homebrew，用的是 GitHub Actions。

推薦架構：混合式（雲端 + 自架）​

三大原則（跨語言通用）

  1. 能用免費雲端的就丟雲端 — 快檢每個 MR 都要跑，放在 always-on 的雲端 runner，不被你的電腦有沒有開機拖累。 額度不夠、把快檢搬到自架時，就是刻意放棄這條：要留一行就能切回雲端的開關（見同一台 Mac 的兩種 runner）。
  2. 只有「沒有免費雲端替代品」的工作才自架 — 例如需要特定 OS（iOS 需 macOS）、特殊硬體、或機器上的特定授權軟體。
  3. 發佈永遠要有手動關卡 — push 不該自動把成品推給正式用戶；正式釋出一定要有人按一下。

心智模型：控制面 vs 執行者​

  • GitLab = 控制面：依 .gitlab-ci.yml 的規則決定「什麼時候該跑哪個 job」。
  • Runner = 執行者：實際執行 job 的機器。雲端 hosted runner 由 GitLab 提供；自架 runner 是你自己機器上跑著的常駐 agent。
  • 觸發是 GitLab 端的事；自不自架，只影響「這個 job 由哪台機器執行」。

章節一覽​

側邊欄分成四組，每組照建議的閱讀順序排。第一次讀，把「基礎」照順序讀完就能寫出能用的 pipeline；後面三組遇到需要時再讀。

1. 基礎（每個專案都用得到）

篇內容
CI 基本觀念pipeline / job / 觸發、exit code（含 pipe 與 pipefail）、allow_failure、resource_group（含死結）、失敗時才跑的 job、compute minutes、常用內建變數
Merge gate 與 MRPipelines must succeed、保護主分支、fast-forward＋squash、主分支上不重跑測試、為什麼只讓雲端快檢當閘門、push options（開 MR、自動 merge、ci.variable）
Pipeline 樣式通用骨架、快檢要點、省分鐘三招、排程的 pipeline、只檢查這次的改動、services: 資料庫、本機模擬 CI、SDK 版本一致
套件漏洞檢查pip-audit／npm audit、緊急出口、升級只升有漏洞的、每天在主分支上排程跑一次
機密管理CI/CD Variables、二進位檔與 File 型變數、部署用的 SSH 私鑰與主機指紋、用 environment 範圍把私鑰收窄到部署的 job、多個 App 共用憑證
本機綠、CI 紅時區、機器剛開機、skip 藏問題、全新環境 vs 升級上來的環境、升級框架後安靜地全綠

2. 自架 Runner（雲端額度不夠，或需要特定 OS／硬體時）

篇內容
安裝與註冊只出不進（不用改防火牆）、建立 runner 與 tags、executor、常駐 service、別睡著、公司網路、省 compute minutes
macOS shell runner 的雷git credential helper、臨時 keychain、LaunchAgent 與 QoS、Spotlight 讓 git clean 失敗、排隊堆積
並發與跨專案共用concurrent vs limit、request_concurrency、全域狀態衝突與分道、多專案共用一台、並發要開多少、會掛著等的 job
同一台 Mac 的兩種 runnershell 道與 Docker 道對照、跑 Mac／雲端的兩種切換寫法、merge gate 的代價、拿私鑰的 job 要不要也跑這台、看 job 容器的結束碼
Windows（WSL2）當 runner專用的 WSL 系統、跟 Windows 隔開、讓它一直開著、時鐘／DNS／記憶體三個坑、每週清理
兩台 runner 互為備援GitLab 沒有優先順序、拆出獨立的 runner 程序、切換程式、切過去的順序、runner 跑到一半不見時 GitLab 怎麼判、retry 要列哪些

3. 部署到自己的主機（前後端各一個 repo，部署到自己管的 Linux 主機）

篇內容
用 deploy repo 部署multi-project trigger、GitLab 端必設的、部署帳號最小權限、切換在主機上自己跑、失敗收拾與回滾
部署時使用者看到什麼重啟不回 502（Caddy／nginx）、維護模式（含 CORS）、舊分頁提示有新版、前後端誰先上
用 tag 上正式打 tag 那條要不要重跑測試、部署前的檢查、配對端對端測試、沒人在用的閘門、補號碼（deploy key）
兩邊一起上正式在哪裡等（resource_group 死結）、進度寫在主機上、失敗時通知另一邊（when: on_failure）、等多久

4. 發佈給使用者安裝的程式（命令列工具這類，發給別人下載、裝在他們的電腦上；用 GitHub Actions，跟前面的 GitLab 各篇無關，可以單獨讀）

篇內容
總覽三個 repo（原始碼、releases、Homebrew tap）、整條流程與鐵則
CI：打包、驗證、建草稿推 tag 時打包、每個平台照使用者的步驟裝一次、建草稿；重跑時不覆蓋已發佈的檔；已經發佈的版本不能改寫；釘住第三方 action
在自己的電腦上簽章為什麼不在 CI 簽、在自己的電腦上用 minisign 簽、附註綁住版本和檔名、使用者怎麼驗、金鑰遺失或外洩
Homebrew tapformula 的寫法、tap 自己的 workflow 驗過簽章才更新、brew trust、怎麼測

前置需求（通用）​

項目說明
GitLab 專案gitlab.com（SaaS，內建免費 Linux runner）或自架 GitLab
Runner雲端 hosted（SaaS 現成）或自架一台（見自架 Runner：安裝與註冊）
版本鎖定用你語言的版本管理工具鎖 SDK 版本，讓 CI 與本機一致

語言/框架專屬的前置（SDK、build 工具、簽章…）屬於各語言章節，不在通用核心。
