GitLab CI 基本觀念

在寫任何 .gitlab-ci.yml 之前，先弄懂這幾個判斷邏輯，後面所有設定才不會像黑魔法。這些觀念與語言無關。

1. Pipeline / Stage / Job​

  • Job：最小執行單位，就是一段 script。
  • Stage：一組同時跑的 job；stage 之間依序執行（前一個 stage 全綠才進下一個）。
  • Pipeline：一次觸發所產生的所有 stage/job 的集合。
stages: [check, build, deploy]   # 依序執行

lint:
  stage: check
  script: [ "<你的 lint 指令>" ]

build:
  stage: build                   # check 全過才會跑
  script: [ "<你的 build 指令>" ]

2. 觸發：pipeline 什麼時候會跑​

觸發來源說明
push推 commit 到任何分支
merge request開/更新 MR（merge_request_event）
tag推一個 git tag（常用於發版本，如 v1.2.0）
scheduleGitLab 內建 cron（例如 nightly 跑重測試）
manualpipeline 裡的 job 設 when: manual，變成手動按鈕
API / trigger token從外部系統呼叫觸發

用 rules 控制「某個 job 在什麼情況出現」：

fast_check:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"   # 只在 MR 跑

release_job:
  rules:
    - if: $CI_COMMIT_TAG =~ /^v/                          # 只在推 v* tag 跑

3. 判斷：一個 job 過不過 → 看 exit code​

GitLab 只認一件事：job 的 script 最後 exit code 是不是 0。0 = 綠、非 0 = 紅。

所以指令必須「失敗時真的回非 0」。常見陷阱：

  • 測試 / 靜態分析工具通常失敗會回非 0 ✅
  • 某些格式化工具（formatter）預設「只重排、不回非 0」——要加對應的「檢查模式」旗標（如 --check / --set-exit-if-changed 之類），否則格式沒過它也回 0，等於沒把關。
warning

最常見的假把關：以為「有跑 = 有擋」，但指令根本沒回非 0，紅的東西也放行。導入任何檢查後，故意製造一個失敗案例，確認 pipeline 真的變紅。

4. Pipeline 過不過 → 看有沒有「必過 job」掛掉​

  • 任一必過 job（非 allow_failure）紅 → 整條 pipeline 紅。
  • manual job 設 allow_failure: true 時是「選配」，不會擋 pipeline 變綠（你按不按都不影響綠燈）。
  • 設 allow_failure: false 時，manual job 變「阻塞式」→ pipeline 卡在 blocked，直到有人手動執行。
allow_failure 的預設值取決於 when: manual 寫在哪裡

官方定義是三段式，不是一句「manual 預設 true」：

寫法allow_failure 預設
job 直接寫 when: manual（不在 rules 裡）true
when: manual 寫在 rules: 裡面false ← 會擋
其他所有情況false

也就是說，只要你用 rules: 控制觸發條件（現代寫法幾乎都是），when: manual 的預設就翻成 false＝阻塞式。發佈類的 manual job 若沒有明寫 allow_failure: true，普通 MR 就會卡在 blocked 等人按。

rules:
  - if: $CI_COMMIT_TAG =~ /^v/
    when: manual
    allow_failure: true      # ← 在 rules 裡面時，這行是必要的，不是可省的美化

4.5 互斥：resource_group（只在單一專案內有效）​

同一時間只想讓某類 job 跑一條（例如會動到共用測試資料庫、或搶同一個模擬器），用 resource_group：

e2e:
  resource_group: shared-sandbox    # 同名的 job 會排隊，不會並行
resource_group 的作用域是「單一專案」

它讓同一個專案內同名 resource group 的 job 排隊。跨專案沒有效果——兩個專案各自宣告 resource_group: shared-sandbox，那是兩個互不相干的群組，照樣會同時跑。

如果你的衝突來源是「同一台機器上的全域狀態」（鑰匙圈、固定檔名、模擬器…），resource_group 擋不住，要改用 runner 的 limit，見並發與跨專案共用。

5. 真正的閘門：Merge gate​

pipeline 綠不綠是一回事，「不綠就不准 merge」要另外開：

  1. Settings → Merge requests → 勾「Pipelines must succeed」 → MR 的 merge 按鈕在 pipeline 沒綠之前是鎖住的。
  2. Settings → Repository → Protected branches → 保護主分支，禁止直接 push，強迫所有變更走 MR + 過 CI。

關鍵設計：只讓「always-on 的雲端快檢」進入 merge gate。 不要讓跑在自架機器上的 build 成為 MR 的必過 job —— 否則機器沒開機時 MR 會卡死。發佈類 job 一律用 tag + manual，排除在 merge 判斷之外。

6. Compute minutes（雲端額度）​

  • GitLab.com 免費層通常提供 每月 400 compute minutes（實際以你帳號 Settings → Usage → Usage quotas 顯示為準）。
  • 只有雲端 hosted runner 吃這個額度；自架 runner 不計分鐘、完全免費。
  • 額度不夠時的逃生門：把快檢也搬到自架 runner（例如一台 Linux VM / WSL2），就變無上限、0 分鐘。

省分鐘三招（詳見 pipeline-patterns）：只在 MR 跑、開 interruptible、快取依賴。

常用內建變數​

變數意義
$CI_PIPELINE_SOURCE觸發來源（push / merge_request_event / schedule / web …）
$CI_COMMIT_TAG若由 tag 觸發，為 tag 名稱；否則空
$CI_COMMIT_BRANCH分支名稱
$CI_DEFAULT_BRANCH專案預設分支（通常 main）
$CI_COMMIT_SHORT_SHA短 commit hash（可當 build 標記）
$CI_PIPELINE_IID專案內遞增的 pipeline 序號（可當 build number）
