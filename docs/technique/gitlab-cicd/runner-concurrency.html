並發與跨專案共用一台 Runner

自架 runner 一旦要服務「多條 pipeline」或「多個專案」，就會遇到兩個問題：要開多少並發，以及哪些 job 不能同時跑。本篇是與語言無關的通用設計；shell executor（無法容器化的 build，如 iOS）遇到的狀況最多，所以例子以它為主。

前置：自架 Runner 的安裝與註冊。

concurrent 與 limit：兩個不同層級的上限​

config.toml 裡有兩個容易搞混的設定：

# 頂層：這台機器同時最多跑幾個 job
# —— 跨所有 [[runners]]、所有專案、所有 pipeline。預設值是 1。
concurrent = 3

[[runners]]
  name = "light"
  limit = 2          # 這個 runner 自己最多同時跑 2 個
  # ...

[[runners]]
  name = "heavy"
  limit = 1          # 這個 runner 一次只跑 1 個
  # ...
設定作用域預設
concurrent（頂層）整台機器：所有 runner、所有專案、所有 pipeline 的總和1
limit（每個 [[runners]]）該 runner 自己無上限（實際受 concurrent 封頂）

兩個常見誤解：

  • ❌「concurrent = 1 是每個專案一個」→ 不是，是整台機器一個。兩個專案會互相排隊。
  • ❌「多註冊一個 runner 就能平行」→ 不會，concurrent 仍然封頂。要同時調 concurrent 才有用。
concurrent 太小時，limit 會「看起來壞掉」

這是分道之後最容易誤判的一件事。假設 concurrent = 2、輕量道 limit = 2、專用道 limit = 1：

專用道跑 1 個（例如簽章）  →  佔掉 1 格
輕量道                     →  只剩 1 格可用
──────────────────────────────────────────
合計 2 = concurrent 上限

於是你會看到「輕量道明明 limit = 2，卻只有一個 job 在跑，其他全部 pending」——很像 limit 沒生效， 其實是全域預算被吃掉了。limit 的語意是「這個 runner 最多能跑幾個」，不是「保證有幾格」。

規則：concurrent 至少要等於你希望「同時存在」的各道 job 數總和。 上例若想要「2 輕量 + 1 專用」 同時跑，concurrent 就得是 3。

反過來說，concurrent 仍是最終的安全閥：把它設成小於各道 limit 之和，就等於刻意讓各道互相競爭 ——有時候正是你要的（機器不夠力時，寧可讓簽章 job 排到輕量 job 後面，也不要三個編譯同時搶核心）。 這是取捨，不是 bug，但你得知道自己選了哪一邊。

改 concurrent 不需要重啟：runner 會偵測 config.toml 變更並自己重讀，程序 PID 不變、正在跑的 job 也不受影響。調大的話幾秒內就會多撈 job。

反而要小心「為了確定生效」去重啟——brew services restart / gitlab-runner restart 會殺掉正在跑的 job。真的想重啟就先確認沒有 job 在執行（runner 程序底下沒有 shell 子程序）。

驗證方式：看 runner 程序的 PID 有沒有變（沒變＝熱重載，job 安全），再數它的子程序數量是否跟著上升。

已經自動隔離的：工作目錄​

shell executor 的工作目錄長這樣：

<working-dir>/builds/<runner-token-前綴>/<CI_CONCURRENT_ID>/<namespace>/<專案>

CI_CONCURRENT_ID 是並發槽位編號，而且每個 runner 有自己的 token 前綴目錄。所以：

  • 同一專案的兩個 job 並行 → 落在不同槽位編號 → 不同目錄
  • 不同專案 → namespace/專案名不同 → 不同目錄

結論：檔案系統層面的 workspace 衝突不需要你手動處理。 也因此，真正要擔心的只剩下「不在 workspace 裡」的那些狀態。

這也意味著把 concurrent 調大之後，第一條 pipeline 會變慢：新槽位是全新目錄，要完整 clone、重新灌相依快取。

不會被隔離的：使用者／機器全域狀態​

以下都在 workspace 之外，並發時會互相破壞。這份清單就是決定「哪些 job 必須序列化」的依據：

類型例子並發時的後果
固定名稱的鑰匙圈security create-keychain … build.keychain另一個 job 的 after_script 執行 delete-keychain build.keychain，把你正在用的刪掉
使用者全域清單security list-keychains -d user -s …兩邊互相覆寫，其中一邊默默地找不到憑證 → codesign 失敗
固定檔名的憑證／描述檔~/Library/MobileDevice/Provisioning Profiles/dist.mobileprovision互相覆蓋 → 用錯的描述檔簽章（不一定會失敗，可能簽出錯的東西）
/tmp 固定路徑/tmp/cert.p12、/tmp/ExportOptions.plist、暫存報告檔互相覆蓋。匯出設定檔裡通常帶 team ID／bundle ID／描述檔名稱，覆蓋後果同上
全機器範圍的 killpkill -f GradleDaemon殺掉別的 job 還在用的 daemon
全機器範圍的裝置操作xcrun simctl shutdown all關掉別的 job 正在跑測試的模擬器
全域工具快取版本管理工具（如各語言的 SDK 版本切換器）的全域安裝目錄兩個 job 同時安裝不同版本時的併發寫入
特別注意「同一份 CI 模板複製到多個專案」

上面這些名稱通常是寫死的。當你把一份能用的 .gitlab-ci.yml 複製到第二個專案，兩邊就會用完全相同的固定名稱——衝突於是變成跨專案的，而且兩邊各自看起來都沒問題。

兩種解法：唯一化，或分道​

解法 A：把名稱唯一化​

用 $CI_CONCURRENT_ID（或 $CI_JOB_ID）讓每個槽位有自己的名稱：

script:
  - |
    KEYCHAIN="build-$CI_CONCURRENT_ID.keychain"
    security create-keychain -p "$PW" "$KEYCHAIN"

代價：/tmp 檔案、描述檔檔名、暫存報告都要一併處理，而且「改寫使用者全域清單」這一項沒辦法靠改名解決——得改成不碰全域清單的做法（例如把鑰匙圈路徑直接傳給簽章指令）。等於要動到「目前已經能正常運作」的簽章邏輯。

解法 B：分出一條 limit = 1 的專用道 ← 多數情況更划算​

註冊第二個 runner，給它不同的 tag 和 limit = 1，然後把所有「會動全域狀態」的 job 用 tag 指名過去：

concurrent = 2        # 全域封頂

[[runners]]
  name = "light"      # tag: light —— lint / 測試 / 一般 build
  limit = 2

[[runners]]
  name = "exclusive"  # tag: exclusive —— 簽章 / 上架 / 需要裝置的測試
  limit = 1
# 預設走輕量道
.defaults: &defaults
  tags: [ light ]
  before_script: [ "<環境準備>" ]

lint:
  <<: *defaults          # → light

signed_build:
  <<: *defaults
  tags: [ exclusive ]    # ← job 層明寫的 key 會蓋掉 << 合併進來的值

為什麼這樣就夠：limit 是機器範圍的，所以它連「不同專案的 job」也一起序列化。上表那些固定名稱一行都不用改。

上面 concurrent = 2 + 2 / 1 的組合，同時最多只會是「2 輕量」或「1 輕量 + 1 專用」，永遠不會出現兩個專用道 job。

resource_group 還是 runner limit？​

兩個都是「讓 job 排隊」的工具，作用域完全不同：

resource_grouprunner 的 limit
作用域單一專案內整台機器（跨專案）
設定位置.gitlab-ci.ymlrunner 的 config.toml
適合擋專案自己的共用資源（測試資料庫、部署環境）機器上的全域狀態（鑰匙圈、固定檔名、裝置）

選擇規則：衝突來源在專案內 → resource_group；在機器上 → runner limit。兩個專案各寫 resource_group: 同一個名字不會互斥，那是兩個獨立的群組。

一台機器服務多個專案​

一個 project runner 可以被「開放給其他專案」使用（GitLab 上該 runner 的設定頁），這是一台機器服務多個專案最直接的做法——即使那些專案在不同的 namespace 底下（group runner 只能覆蓋同一個 group）。

新註冊的 runner 一定要記得開放

新 runner 只屬於建立它的那個專案。忘記開放給第二個專案的症狀是：那個專案裡帶此 tag 的 job 永遠 pending——不是失敗，所以不會有紅字通知你。

concurrent 該開多少​

先看清楚機器的核心組成。Apple silicon 是大小核架構，sysctl 分開報：

sysctl -n hw.perflevel0.logicalcpu   # P-core（效能核心）
sysctl -n hw.perflevel1.logicalcpu   # E-core（效率核心）

基本款常見是 4 P + 6 E = 10 個邏輯核心，但**「10 核」不代表可以開 5 個並發**：編譯類負載（compiler、linker）只在 P-core 上跑得快，一顆 E-core 大約只有 P-core 的 1/4～1/3。所以有效的編譯吞吐量遠低於核心總數。

判斷方式：

  • 平行度超過「P-core 數 ÷ 2」之後，每個 job 分到的 P-core 就不足 2 顆，單一 job 的 wall-clock 會明顯拉長，而總吞吐量幾乎沒增加——等於把「排隊等待」換成「每個都變慢」，對 MR 回饋速度而言是退步。
  • 記憶體通常不是第一個瓶頸。判斷有沒有真的在 thrash 要看 sysctl -n vm.swapusage 搭配 pageout／pagein 的比例：pageout 遠小於 pagein 表示只是讀取壓力，不是寫入 thrash。
  • 調大 concurrent 的真正價值是消除 head-of-line blocking（一個慢 job 擋住其他 pipeline），以及填滿 I/O／網路等待（抓相依、上下傳快取、git fetch、上傳產物）。不是為了讓 CPU 更忙。

實務建議：

  1. 先決定各道的 limit（依「哪些 job 不能同時跑」而定，見上面的地雷清單），
  2. 再把 concurrent 設成各道 limit 之和——否則專用道一佔格，輕量道就達不到自己的 limit （見上方 concurrent 太小的警告）。
  3. 之後才依機器實力決定要不要故意壓低 concurrent 讓各道互相競爭。

換句話說：limit 表達「正確性」（什麼不能同時跑），concurrent 表達「這台機器吃得下多少」。 先滿足正確性，再談吞吐量。

調整後先量再加：看 lint／測試類 job 的 duration 中位數有沒有變差，而不是憑感覺。

macOS 不能把工作釘在 P-core 上

沒有 thread affinity API（taskpolicy 只能往下降級）。排程器依 QoS 與當下負載決定，P-core 滿了就溢出到 E-core。正因為無法控制配置，才更該讓需求不要超過供給。

唯一相關的槓桿是 service 的 QoS：LaunchAgent plist 的 ProcessType 若是 Background，所有 CI job 都會被排到 E-core（見自架 Runner）。

config.toml 生命週期​

gitlab-runner list      # 驗證 TOML 語法、列出設定裡的 runner
gitlab-runner verify    # 逐一驗證每個 token 對伺服器是否仍有效
register / unregister 會重寫 config.toml，並刪掉所有註解

這兩個指令是用「讀進結構 → 整份寫回」的方式改檔案，所以你手寫的註解、排版全部消失。

如果你把「為什麼 concurrent 是這個數字」「為什麼這條道 limit = 1 不能改大」寫在 config.toml 裡當說明——下一次動 runner 就會失去它。那些理由應該寫在版控裡的文件或 .gitlab-ci.yml 的註解中，config.toml 只留一行指標。

unregister --name <名稱> 除了移除設定區塊，也會在 GitLab 伺服器端刪掉該 runner。

診斷：這個 token 屬於哪個專案？​

glrt- token 內嵌一段 base64url 的路由資訊，解碼後可以看到專案識別碼：

python3 - <<'PY'
import base64
tok = "glrt-<貼上 token>"
body = tok[len("glrt-"):].split(".01.")[0]
for i in range(len(body)):
    s = body[i:]; s += "=" * (-len(s) % 4)
    try: d = base64.urlsafe_b64decode(s).decode()
    except Exception: continue
    if d.startswith(("p:", "o:")): print(repr(d)); break
PY
# → 'p:<專案碼>\nt:<型別>\nu:<使用者>'

用途：確認兩個 runner 是不是屬於同一個專案。在網頁上開錯專案建立 runner 是很容易發生的事，而 tag 又存在伺服器端看不到，這個解碼是少數能在本機判斷的線索。

驗證並發真的生效​

最直接的證據是工作目錄：concurrent = 1 時只會存在槽位 0；真的有兩個 job 並行過，就會出現槽位 1。

find <working-dir>/builds -maxdepth 2 -mindepth 2 -type d

若調大了 concurrent 卻始終只有槽位 0，可能是（a）job 其實沒有重疊（各自太快或提早失敗），或（b）設定沒生效（service 沒重啟、或誤開了兩套 service）。
