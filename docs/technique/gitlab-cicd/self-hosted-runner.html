自架 GitLab Runner

當某些 job 需要特定 OS、特殊硬體、或機器上的特定授權軟體（雲端免費 runner 給不了）時，就自架一台 runner。本篇是與語言無關的通用設定；框架專屬的 build 工具前置，屬於各語言章節。

核心觀念：只出不進（outbound-only），不用改防火牆​

GitLab Runner 是裝在你機器上的常駐 agent，它主動往 GitLab 連出去（HTTPS / 443）問「有沒有我的 job」。GitLab 從不反向連進你的機器。因此：

  • 不需要開任何 inbound port、不需要固定 IP、不需要改防火牆。
  • 判斷能不能用最簡單的方法：這台機器現在能不能正常開 GitLab 網頁 / git pull？ 能 → runner 就連得上（走同一條 outbound 443）。
  • GitLab 不會「啟動」你的 runner：runner 是你保持常駐跑著的 service，它自己撈 job。機器關機/睡著、或 service 沒開 → job 就 pending 等它上線（GitLab 無法遠端喚醒你的機器）。

安裝與註冊​

1) 安裝 gitlab-runner​

依平台安裝（macOS brew install gitlab-runner、Linux 套件庫、Windows 二進位），詳見 GitLab 官方文件。

2) 在 GitLab 建立 runner（tags 在這一步就決定）​

到 GitLab：專案 → Settings → CI/CD → Runners → New project runner（或 group 層級）。這個畫面就是設定 tags、描述、以及「Run untagged jobs」的地方；填完才會拿到 runner authentication token（glrt- 開頭）。

新版流程：tags 存在伺服器端，config.toml 裡沒有副本

GitLab 16 起改用 runner authentication token。在這個流程下，tags、描述、「是否接受沒有 tag 的 job」全部存在 GitLab 伺服器端，由上面那個建立畫面決定。

因此 register 的 --tag-list 與 --description 會被接受但不生效——那兩個旗標是留給舊的 registration token 流程的，指令不會報錯、也不會有警告，只是什麼都沒發生。

打錯 tag 的症狀特別難查：帶該 tag 的 job 永遠 pending——不是失敗、沒有錯誤訊息，而且 config.toml 裡沒有 tag 可以對照。要改 tag 就回 GitLab 上該 runner 的設定頁改。

3) 選 executor​

Executor何時用
docker大多數情況：每個 job 在乾淨容器裡跑，環境隔離、好維護。適合 Linux 上的 lint/測試/build。
shelljob 需要原生工具鏈、無法容器化時（典型：iOS build 需要原生 Xcode）。直接在機器 shell 執行，環境要自己備好。
gitlab-runner register --non-interactive \
  --url "https://gitlab.com" \
  --token "glrt-<YOUR_RUNNER_TOKEN>" \
  --executor "shell" \
  --name "my-selfhosted-runner"        # 只是 config.toml 裡的區塊名稱，與 GitLab 上的 tag 無關

--registration-token 已棄用，用 --token。註冊完可以用 gitlab-runner list（驗證 config.toml 語法）與 gitlab-runner verify（逐一驗證 token 對伺服器是否有效）自我檢查。

tags 是關鍵：在 .gitlab-ci.yml 用 tags: [<你的標籤>] 就能把特定 job 精準指名給這台機器。這裡填的字串必須跟上一步在 GitLab 網頁上設定的 tag 完全一致（見上方警告）。job 要有 runner 的全部 tag 才會被撿走。

4) 跑成常駐 service（開機自啟）​

gitlab-runner install     # ⚠️ 注意：--working-directory 預設是「執行這行時的 cwd」
gitlab-runner start
gitlab-runner status

install 的 --working-directory 決定 builds/ 落在哪，而它預設取當下的 cwd——在專案目錄裡執行這行，build 目錄就會長在專案裡。要指定就明寫 --working-directory "$HOME"。

install 與 brew services 是互斥的兩套 service，不要都開

macOS 上有兩條路：gitlab-runner install（自己註冊的 service）與 brew services start gitlab-runner（Homebrew 的 LaunchAgent，label homebrew.mxcl.gitlab-runner）。兩者讀同一份 config.toml，但是兩個獨立的 service。

同時開起來的後果是：機器上有兩個 gitlab-runner run 程序，各自套用一整份 concurrent（設 2 就變成實際 4），而且各自的 CI_CONCURRENT_ID 都從 0 開始編號——於是兩邊會寫進同一個 build 目錄，剛好是 runner 的目錄配置本來能避免的唯一衝突。

macOS 上選一條就好（brew 比較省事，它的 plist 已經把 WorkingDirectory 設在家目錄）。

到 GitLab Settings → CI/CD → Runners 應該看到這台 runner 顯示為 online（綠點）。

讓機器在跑 job 時別睡著​

自架的唯一代價就是「機器要在線」。若這台平常會睡眠，跑 build 時要避免：

  • macOS：caffeinate -dimsu &，或系統設定關閉閒置睡眠。
  • Linux：systemd-inhibit / 電源設定。
  • 長期當 runner 的機器，建議設成接電源時不自動睡眠。

macOS shell runner 的常見雷​

自架在 macOS 上、用 shell executor（iOS build 的典型情境）時，特別容易踩到：

1) 停用 git credential helper（否則跳鑰匙圈密碼框 / -60006）​

macOS 的 git（Xcode 附的）系統設定預設開了 credential.helper=osxkeychain。runner 拉 code 時 git 會想把 CI job token 存進鑰匙圈——一旦鑰匙圈狀態不對（例如某個 job 動過預設鑰匙圈），就會 failed to store: -60006、跳出鑰匙圈密碼框卡住 job。CI 的 job token 是臨時的、根本不該存。

在 runner 的 config.toml 對應的 [[runners]] 停用它（只影響 runner，不動你自己的 git）：

[[runners]]
  executor = "shell"
  environment = ["GIT_CONFIG_COUNT=1", "GIT_CONFIG_KEY_0=credential.helper", "GIT_CONFIG_VALUE_0="]

2) 臨時 keychain 不要動「預設鑰匙圈」​

簽章用的臨時 keychain，只加進搜尋清單（security list-keychains -s <臨時> <login>）即可讓 codesign 找到憑證；不要 security default-keychain -s <臨時>。若改了預設又在 after_script 把它 刪掉，預設鑰匙圈就指向一個「已刪除的東西」，連帶讓上面第 1 點的 git 存 token 失敗、跳密碼框。 清理時把搜尋清單還原成 login-only 再刪臨時 keychain。

這招只在「一次一個 job」時安全

list-keychains -d user -s 改寫的是使用者全域的鑰匙圈搜尋清單，臨時 keychain 的名稱也是固定的。 一旦同一台機器同時跑兩個簽章 job，兩邊都在改同一份清單、用同一個名字，結果是其中一邊默默地 找不到自己的憑證（codesign 失敗），而另一邊的 after_script 還會把對方的 keychain 一起刪掉。 並發大於 1 時要怎麼處理，見並發與跨專案共用。

3) runner 是 GUI session 的 LaunchAgent​

brew services start gitlab-runner 裝的是 user LaunchAgent：登入後才會起（不是開機畫面就起）， 且 iOS simulator 需要登入的 GUI session 才開得動。要「開機自動待命」就搭配自動登入 + 接電源不睡眠。

順手確認 plist 裡的 ProcessType（~/Library/LaunchAgents/homebrew.mxcl.gitlab-runner.plist）：

<key>ProcessType</key><string>Interactive</string>

這個鍵決定 service 及其子程序繼承的 QoS。在 Apple silicon 上，Background 會讓所有 CI job 被排到 E-core（效率核心）去跑，編譯速度掉一大截，而且不會有任何錯誤訊息——只是變慢。 Homebrew 產生的 plist 用的是 Interactive（正確值），所以這是「確認一下，通常不用改」的檢查項。

4) Spotlight 索引害 git clean 以「Directory not empty」失敗​

shell executor 會重用 workspace；每個 job 開跑前 runner 會 git clean 掉上一輪的未追蹤檔 （build 產物）。但 macOS 的 Spotlight（mds）在背景索引那堆原始碼時會「間歇持有」目錄，剛好撞上 git clean 要刪就 warning: failed to remove …: Directory not empty → git clean 回非 0 → 整個 job 在「取原始碼」階段就紅（還沒跑到你的 script）。特別容易發生在 iOS 的 SPM SourcePackages/checkouts （一堆巢狀 git repo）和大型 build 目錄。徵兆：同一個 commit 重跑時好時壞（競態）。

三道一起上（單一招常常不夠，這個雷特別頑固）：

  1. 根治——把 CI 的 builds 目錄加進「Spotlight 隱私清單」（一次性、GUI）： 系統設定 → Spotlight → Spotlight 隱私權 → + → 加入 builds 的母目錄（預設是 ~/builds）。 這是最可靠的硬排除。

    要加母目錄而不是底下某一層具體路徑。實際的工作目錄是 ~/builds/<runner-token-前綴>/<CI_CONCURRENT_ID>/<namespace>/<專案>——每個 runner 有自己的 token 前綴目錄，每個並發槽位又各有一層編號。只加了當下那條具體路徑的話，之後多註冊一個 runner、或把 concurrent 調大，新目錄就不在清單上，這個雷會安靜地回來。

    加完要驗證（隱私清單的 UI 不會告訴你有沒有生效）：

    # 加之前先量一個基準；加完應該變成 0
    mdfind -onlyin ~/builds "<專案裡一定有的字，例如某個檔名>" | wc -l

    # 或直接看單一檔案還有沒有索引來的 metadata
    mdls <builds 裡的某個檔> | grep -c kMDItem

    排除生效後 mdfind 應回 0；mdls 的屬性數會大幅減少（剩下的是 mdls 從檔案本身推導的靜態 屬性，不是索引來的，所以不會歸零）。

    touch <builds>/.metadata_never_index 或 mdutil 看似方便，但擋不住「已排隊」的索引（實測 放了 .metadata_never_index，mds/mdbulkimport 照樣在跑、還是撞上）——所以要用隱私清單。

  2. 最有效的防禦——build 一結束就在該 job 自己的 after_script 清掉重產物（那當下沒程序鎖著， rm 一定成功），別留給「下一條 pipeline 的 git clean」：

    ios_build:
      after_script:
        - rm -rf build/ios/SourcePackages 2>/dev/null || true   # SPM 那堆巢狀 git repo

  3. 開跑前的保險——pre_get_sources_script 先清一次（rm 重試幾次以防仍在索引）：

    default:
      hooks:
        pre_get_sources_script:
          - |
            D="$CI_PROJECT_DIR"                  # 一定要絕對路徑，見下方
            for i in 1 2 3 4 5; do
              rm -rf "$D/build" && break
              echo "清理失敗，重試（$i/5）"; sleep 5
            done
            if [ -e "$D/build" ]; then           # 驗證：別把「什麼都沒做」當成成功
              echo "build/ 仍存在 —— git clean 會以 Directory not empty 失敗"
              ls -la "$D/build"; exit 1          # 這個 exit 1 是刻意的：讓 job 當場紅
            fi
    這個 hook 有三種寫法會壞，而且壞得很不明顯

    ① 用相對路徑 → 靜默 no-op。 pre_get_sources_script 在 clone 之前執行，實測 cwd 是 / （不是專案目錄，專案目錄那時可能還不存在）。所以 rm -rf build 是對著 /build 執行，而 -f 讓 「路徑不存在」靜默回傳 0 —— hook 看起來成功、實際什麼都沒清。要確認自己這台是什麼情況， 在 hook 裡加一行 pwd，log 會直接告訴你。

    ② 把錯誤吞掉 → 永遠不會浮現。 rm -rf build 2>/dev/null … ; true 連結束碼都丟了。

    ③ 用 cd 或 exit 0 → 會把 clone 整個跳掉。 這段 script 是內嵌進 runner 產生的同一支 bash 腳本，後面才接 clone 的邏輯。所以：

    • cd "$CI_PROJECT_DIR" || exit 0 看起來像「目錄不存在就跳過清理」，實際是終止整支腳本， clone 根本不執行。症狀：get_sources 只花不到一秒、沒有 Fetching changes，接著 restore_cache 以 cd: /builds/…: No such file or directory 失敗。

    • cd 本身也會改掉後續 clone 邏輯的 cwd。

    結論：只用絕對路徑、不動 cwd、不要提早 exit 0。 專案目錄還不存在時（雲端容器每次全新）， rm 對不存在的絕對路徑就是 no-op、[ -e ] 也是 false，自然往下走去 clone，不必特別處理。 結尾的 exit 1 則要保留——那是「清不掉就當場紅」的刻意行為。

    ①②的共同症狀是騙人的成功：hook 那段 log 乾乾淨淨，job 卻在幾秒後的 git clean 以 Directory not empty 失敗，看起來像 git 的問題而不是 hook 的問題。

同一類「重用 workspace 又鎖檔」的還有 Gradle daemon：若 gradle.user.home 落在 workspace 內， 常駐的 daemon 會鎖住快取讓下個 job 的 git clean 失敗。除了在 CI 關掉 daemon，after_script 收尾時 用 ./gradlew --stop（daemon registry 就放在該 gradle.user.home 底下，所以只會停到自己的）。 不要用 pkill -f GradleDaemon——那是全機器範圍，並發時會殺掉別的 job 還在用的 daemon，而且 沒辦法改成「只比對自己專案路徑」，因為 daemon 的命令列帶的是 launcher jar 的 classpath，不是 GRADLE_USER_HOME。詳見 Android CD。

5) 單一 runner + 頻繁 push → pipeline 排隊堆積​

config.toml 的 concurrent 預設值就是 1（一次一個 job），iOS build 又慢。連續 push 幾個 commit 就會 讓多條 pipeline 排隊等這一台。

針對「同一分支的舊 pipeline 白跑」：job 設 interruptible: true + 專案開 Settings → CI/CD → Auto-cancel redundant pipelines，新 push 一來就自動取消同分支還在跑的舊 pipeline。

針對「不同分支／不同專案互相堵住」：那是 concurrent 太低，interruptible 幫不上忙（那些 pipeline 都還有效，不該被取消）。要調 concurrent、並用每個 runner 的 limit 分道—— 見並發與跨專案共用。

公司網路（proxy / TLS 檢查 / 白名單）​

即使不改防火牆規則，企業網路常有 outbound 限制，要在 runner 這端配合：

  1. 強制 proxy → 設環境變數，runner 支援走 proxy：

    export https_proxy="http://proxy.corp.example:8080"
    export http_proxy="http://proxy.corp.example:8080"
    export no_proxy="localhost,127.0.0.1"

  2. TLS 中間人檢查（MITM） → 讓機器信任公司的 CA 根憑證，否則連 GitLab 會憑證錯誤。

  3. 白名單型 egress（只准連特定網域） → 除了 GitLab 本身，build 過程通常還要連：套件庫（你語言的 package registry）、相依下載來源、以及發佈目標的伺服器。這些若被白名單擋掉，build 會失敗——但依然不用開 inbound，頂多請 IT 把這幾個網域加進 outbound 白名單。

驗證​

推一個測試分支或手動觸發一個帶你 runner tag 的 job，觀察：

  • GitLab pipeline 頁面該 job 是否被這台 runner 撿走並執行。
  • 機器上 gitlab-runner status 為 running。
  • job log 裡工具鏈版本是否正確。

自架 Linux runner 省 compute minutes​

若雲端免費額度不夠，把快檢也搬到自架 Linux runner（實體、VM，或 Windows 的 WSL2），executor 選 docker，給 tag 後在 job 加 tags: [...] → 0 分鐘、無上限。雲端與自架差別只在「誰執行」，.gitlab-ci.yml 幾乎不用改。
