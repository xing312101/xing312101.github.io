CI/CD 機密管理

簽章金鑰、API token、service account 這類機密絕不 commit 進 git。GitLab 提供 CI/CD Variables 來注入，本篇是通用通則；各語言的具體變數清單見該語言章節。

GitLab CI/CD Variables​

Settings → CI/CD → Variables，每個變數可設：

選項意義
Masked在 job log 裡把值遮成 [MASKED]，避免外洩（值需符合遮罩規則，如夠長、無特殊字元）
Protected只有 protected 分支/tag 的 pipeline 才拿得到——發佈用的機密建議勾，避免任意分支偷用
File 型別值會寫進一個暫存檔，變數內容是「檔案路徑」——適合整份 JSON / 憑證 / .p8 這種檔案
Expanded / Raw是否展開 $ 參照；含 $ 的密碼建議設 Raw 避免被誤解析

常見手法​

二進位檔（keystore、憑證）→ base64​

變數不能直接放二進位，先在本機編碼、放進變數，job 裡還原：

# 本機：編碼
base64 -i my-keystore.jks | pbcopy      # 貼進 CI/CD Variable

# job 裡：還原
echo "$MY_KEYSTORE_BASE64" | base64 --decode > /path/to/keystore.jks

整份 JSON / 金鑰檔 → File 型變數​

把 service account JSON、API 金鑰 .p8 設成 File 型別，job 裡直接用它給的路徑：

gcloud auth activate-service-account --key-file="$GCLOUD_SA_JSON"

鐵則​

  • .gitignore 掉所有本機機密檔（keystore、key.properties、*.p8、*.json 金鑰…）。
  • 機密只走 CI/CD Variables，勾 Masked +（發佈用）Protected。
  • 搭配 Protected branches：讓發佈機密只在受保護的 tag/分支 pipeline 可用，一般 feature 分支拿不到。
  • 定期輪替：金鑰外洩或成員異動時能撤換。
  • 最小權限：service account / API key 只給必要範圍的權限。

與 merge gate 的關係​

發佈類 job 用 tags + when: manual + tag 觸發（見 pipeline-patterns），並把發佈機密設為 Protected：

  • 一般 MR 的快檢拿不到也不需要發佈機密；
  • 只有推 release tag、手動觸發的發佈 job 才取用 —— 縮小機密暴露面。
Protected 變數在 MR pipeline 讀不到

MR 的 pipeline 跑在「來源 feature 分支」的情境，而 feature 分支通常不是 protected → Protected 變數在 MR 一律讀不到。所以如果你想「在 MR 就驗證某個需要機密的步驟」 （例如 iOS 在 MR 就跑簽章 build），那組機密不能只設 Protected，否則 MR 會因缺變數而失敗。

取捨：把「MR 也要用」的那組設非 Protected（任何分支的 pipeline 都讀得到，含惡意改設定檔的 MR——私有 repo + 可信團隊可接受），只把「純發佈才用」的（如上傳金鑰）留 Protected。要更嚴， 就 MR 用低權限素材（如開發憑證）、release 才用正式的。

多個 App 共用憑證（跨專案 CI/CD）​

團隊有第二、第三個 App 要接 CI 時，先分清楚哪些機密是「帳號/團隊層級」（一份到處用）、 哪些是「App 專屬」（每個各自準備）。以行動 App 簽章為例：

機密可跨 App 共用？原因
iOS Distribution 憑證（.p12）+ 密碼✅ 可憑證綁團隊、不綁 App，同團隊一張可簽多個 App
App Store Connect API key（.p8 + Key/Issuer ID）✅ 可帳號層級，一把可上傳同帳號多個 App
Play service account JSON✅ 可一個 service account 可被授權到多個 App（在 Play Console 逐一授權）
臨時 keychain 密碼✅ 可只是隨意字串
自架 runner✅ 可一台可服務多專案（見下方；另注意並發衝突）
iOS provisioning profile + 名稱❌ 專屬profile 綁 bundle id，每個 App 各建一個
Android keystore + 別名 + 密碼❌ 專屬每個 App 一把上架 key（已上架就用它原本那把）

省事做法：把「可共用」的設成群組層級變數。 若這些 App 都在同一個 GitLab 群組下，把共用機密設在 Group → Settings → CI/CD → Variables， 底下所有專案自動繼承——只設一次；各專案只需再補自己的 provisioning profile / keystore。 Runner 同理：註冊成群組 runner，一台服務整個群組。

若這些專案不在同一個群組（不同 namespace），群組 runner 就覆蓋不到，改用 project runner + 「開放給其他專案」：在 GitLab 上該 runner 的設定頁把它加給第二個專案。注意新註冊的 runner 只屬於建立它的專案，忘記開放的症狀是那邊的 job 永遠 pending（不是失敗，沒有紅字）。

多個專案共用一台機器還有另一類問題——同名的臨時鑰匙圈、固定檔名的描述檔、全機器範圍的 pkill 會跨專案互相破壞。見並發與跨專案共用。
