llama-server 實戰指南 — 參數、記憶體帳、速度物理與加速原理

對象：在自己的機器上用 llama-server（llama.cpp）跑本地大模型的人。 內容與具體專案無關；範例以「Apple Silicon 64GB 統一記憶體 + 27B Q8_0 模型」 為工作例，因為它的數字剛好落在每個坑的邊緣上，換算到你的硬體只需改常數。 所有實測數字標明量測條件；公式優先於數字——數字會過時，公式不會。

安裝、各量化版本的一鍵啟動指令與 alias 自動化見 llama-cpp.md； 量化命名（Q4_K_M / Q6_K / Q8_0）見 quantization.md； 把 Windows 桌機（小 VRAM＋CUDA）變成區網推論伺服器給 coding agent 用，見 offline-llm-server-for-coding-agents.md。

旗標語意以 llama.cpp master（2026-09）的原始碼與 server README 查證；版本間的差異集中在第 8 節。

1. 快速開始：單人本地推理的建議指令​

llama-server -hf <repo>/<model>-GGUF:Q8_0 \
  --ctx-size 65536 --parallel 1 \
  -fa on -ctk q8_0 -ctv q8_0 \
  -ngl 99 --host 0.0.0.0 --port 8080

單人用、追求穩定長 context 的基準配置。每個旗標為什麼這樣選，見下節； 記憶體算不算得過，見第 3 節——先算再跑，配置錯誤的代價不是慢一點， 是 swap 之後慢一個數量級。

2. 逐參數詳解​

參數作用要點
-hf <repo>:<quant>從 Hugging Face 拉模型名字會成為 API 回報的 model 名（要固定對外名稱用 --alias）。⚠ llama-server 不驗證 client 請求裡的 model 名——送錯名字不會報錯，照樣用當前載入的模型回答。client 端若拿 model 名做快取鍵，名實不符會靜默污染快取。
--ctx-size (-c)context 預算（token 數）⚠ 它決定的是 KV cache 的總量，不是每個請求保證拿到的量：明示 --parallel N 時每個 slot 分到 c ÷ N；--parallel 留自動（新版預設）時所有 slot 共用同一池、單一請求可用到整池。哪一種，以啟動 log 為準（第 3、8 節）。
--parallel (-np)同時服務的請求道（slot）數這不是 CPU 執行緒（那是 --threads）。單人串行使用一律明示 1：多 slot 要嘛把 context 切碎（每 slot 只剩 c ÷ N，長 prompt 直接塞不下），要嘛依版本多配幾份 KV 燒記憶體，兩種都換不到任何吞吐。
-fa onflash attention省記憶體、常見提速；同時是 KV 量化（尤其 -ctv）的前置需求。新版預設 auto，寫死 on 讓行為跨版本可預期。⚠ 旗標格式陷阱見第 8 節。
-ctk q8_0 -ctv q8_0KV cache 量化K/V 各從 f16 降到 q8_0 ≈ KV 減半、近無損。長 context 場景收益最大。例外：沒有 tensor core 的 NVIDIA 卡（GTX 16／Pascal）量化 KV 會把 attention 踢回 CPU，見 Windows 篇 §6-2。
-ngl 99全部層 offload 到 GPU/Metal純 CPU 跑則無效果、無害。
--host 0.0.0.0綁所有網路介面預設 127.0.0.1 只服務本機——container 內的 client 連 host 時必須 0.0.0.0（配 host.docker.internal）。
--port埠OpenAI 相容 API 掛在 /v1（client 的 endpoint 結尾要 /v1）；Anthropic Messages API 掛在 /v1/messages。

選配（吞吐與行為調校）：

  • --threads N / --threads-batch N：生成／prefill 的 CPU 核數。GPU 全 offload 時影響小，CPU fallback 時關鍵。
  • -b / -ub（logical / physical batch）：prefill 批量，長 prompt 的「讀入時間」直接受此影響。
  • --kv-unified（-kvu）：所有 slot 共用一池 KV。--parallel 自動時預設開；--parallel 1 時開不開無差。
  • --fit on（新版預設）：沒明示的參數（含 ctx）會自動縮到裝得進裝置記憶體；你明示了 -c 它就不會替你縮——先算再跑的責任還是你的。
  • --alias NAME：固定 API 對外的 model 名，client 設定與快取鍵都認這個。
  • --mlock：鎖權重防 swap——RAM 足夠才開，不夠反而擠壓其他程序更糟。
  • --no-mmap：一次載入取代 mmap 分頁（冷啟慢、熱路徑穩）。

3. 記憶體帳（先算再跑）​

權重 ≈ 參數量 × bytes/param     （Q8_0 ≈ 1.06、Q6_K ≈ 0.82、Q4_K_M ≈ 0.60）
KV bytes/token ≈ 2(K+V) × n_layer × n_kv_head × head_dim × bytes/elem
                 （f16 = 2；q8_0 ≈ 1.07）
總 KV ≈ KV bytes/token × n_ctx      ← n_ctx 取「啟動 log 印出來的那個數」，不是你以為的 -c
  • 精確值別用公式猜——server 啟動 log 會印 n_ctx、n_ctx_seq（每 slot）、n_seq_max、kv_unified 與 KV self size = … MiB，以它們為準；公式用來事前估量級。
  • 量級感（32B 級架構、64 層、8 KV head、head_dim 128 作參照）：f16 KV ≈ 256 KB/token → 65536 ctx ≈ 16 GB；q8 量化後 ≈ 8-9 GB。
工作例（真實事故）

64GB 機器跑 27B Q8_0（權重 ~29GB），開了 --parallel 4 × --ctx-size 65536——當時觀察到系統配置了 4 份 65536 的 KV（≈36GB），29+36 = 65GB > 64GB → 恆常 swap → 生成從 ~4.75 掉到 1.5-4 tok/s 且抖動。 改 --parallel 1 + q8 KV 後總占用 ~38GB，速度回穩。

要注意的是：本文查證當下的 master 原始碼語意是「-c 為總量、明示 --parallel N 時每 slot 得 c ÷ N」， 照這個語意同樣的旗標不會多吃記憶體、但每個 slot 只剩 16K——同一組旗標在不同版本可能差 4 倍記憶體， 或差 4 倍 context。結論不變：單人一律 --parallel 1，而且別背規則，看 log。 --parallel 省下的不是「快一點」，是免於掉下懸崖。

  • 記憶體壓力簽名：tok/s 掉到低個位數且不穩、系統狂 swap、prefill 異常慢。看到這組合先查記憶體，別急著調別的參數。
  • macOS 檢查法：sysctl vm.swapusage（swap 用量開始長 = 超編）、vm_stat；兩套 runtime 通用的檢查見 README。

4. 生成速度的物理：為什麼「就是這麼慢」​

自回歸生成的本質：每吐 1 個 token，都要把整套權重從記憶體搬進運算單元一次。 所以單流生成幾乎永遠是記憶體頻寬瓶頸，不是算力瓶頸：

理論 tok/s 上限 ≈ 記憶體頻寬 ÷ (權重 bytes + KV 讀取 bytes/token)

工作例：400 GB/s 頻寬（M1 Max）、27B Q8 權重 28.7GB、40K ctx q8 KV 每 token 讀 ~5.5GB → 上限 ≈ 400 ÷ 34.2 ≈ 11.7 tok/s；實測 4.75 tok/s ≈ 理論的 40% （損耗來源：第一代 Metal 的長 context attention 效率、同機其他負載分食頻寬、GPU 工作集上限約 RAM 的 75%）。

三個推論：

  1. 實測落在理論 35-60% 都算正常——遠低於此才值得調參，貼近此值就別折騰了，剩下的是物理。
  2. prefill（讀 prompt）與生成（寫 token）是兩種速度：prefill 可以批次平行（實測同機 ~112 tok/s），生成不行。長 prompt 的等待大頭在 prefill 一次性付清，之後靠 prompt cache 秒級重用（單 slot 時同前綴請求免重算）。
  3. 降量化（Q8→Q6_K）≈ 權重變小 ≈ 等比例提速，但輸出品質微降、且模型名改變（見第 2 節快取鍵警告）。無損的提速只有一條路——下一節。

同一條公式在 MoE 模型上要改成「每 token 實際啟用的參數量」——這就是為什麼 35B-A3B 比 27B dense 快將近十倍， 詳見 Windows 篇 §1。

5. Speculative decoding：無損加速的原理與代價​

本質​

第 4 節說了：慢的根源是「每 token 搬一次全部權重」。Speculative decoding 的把戲：

  1. 一個小 draft 模型（快）先猜 K 個 token；
  2. 大模型一次前向同時驗證這 K 個猜測——猜對的整批收下，猜錯的從錯誤點丟棄重來；
  3. 於是權重搬運費從「每 token 付一次」變成「每批攤一次」。

關鍵性質：貪婪解碼（temperature 0）下輸出與不開完全逐 token 相同——這是驗證演算法的數學保證，不是近似。你得到的是純粹的延遲改善，不犧牲任何輸出品質。

為什麼它不是預設——五個真實代價​

  1. 賭注會輸：猜錯的 token 全部作廢，draft 的算力白燒。接受率取決於 draft 與大模型「有多像」＋內容有多可預測——程式碼、固定格式輸出接受率高（常見 1.5-2.5×）；創意文本、多語混雜低，低到一定程度反而變慢。伺服器不知道你要跑什麼，不敢替你賭。
  2. 要多載一顆模型：多吃 2-4GB 記憶體。對貼著記憶體上限跑的機器（第 3 節工作例），預設打開會把一部分使用者從「慢」直接推進「swap 深淵」。
  3. 沒有萬用 draft：draft 必須與主模型同 tokenizer 家族（理想上同訓練譜系），伺服器無法替任意 GGUF 組合自動選對搭子——所以它是手動旗標。
  4. 吞吐 vs 延遲的立場：大型 API 服務的瓶頸是總吞吐——batch 塞滿時權重搬運費本來就被幾十個請求攤掉了，speculative 反而佔用能服務別人的算力。它只在「單使用者、batch=1、記憶體頻寬瓶頸」時是純賺——恰好就是本地單人跑大模型的形狀。
  5. 工程成熟度：draft 深度、接受策略等參數仍在演化，不同版本行為有差；保守的專案不把演化中的路徑設為預設。

什麼時候該開（自查清單）​

全部滿足就是甜區：☐ 單人使用（batch=1）☐ 生成內容公式化（程式碼／結構化輸出） ☐ 有同家族小模型可當 draft ☐ RAM 還有 3-5GB 餘裕 ☐ 生成速度顯著低於需求。

啟動方式​

llama-server -hf <repo>/<大模型>-GGUF:Q8_0 -hfd <repo>/<同家族小模型>-GGUF:Q8_0 \
  --ctx-size 65536 --parallel 1 -fa on -ctk q8_0 -ctv q8_0 -ngl 99 --host 0.0.0.0 --port 8080

旗標對照（現行版本）：Hugging Face 拉 draft 用 -hfd／--hf-repo-draft，本地 GGUF 用 -md／--model-draft； draft 自己的 KV 量化是 -ctkd／-ctvd。旗標名版本間有異動，報錯就 llama-server -h 對現版。 開了之後量 30 分鐘實際接受率與 tok/s，不賺就關——切換對輸出零影響（temp 0 等價），可以放心 A/B。

6. Thinking 模型的 token 預算陷阱​

會「思考」的模型（如 Qwen3 系）走 OpenAI 相容 API 時：思考進 reasoning_content 欄位、答案進 content 欄位。三個必踩的坑：

  1. 多數 client 只讀 content——思考若吃光 max_tokens，content 會是空字串且不報任何錯。症狀：API 回 200、finish_reason=length、內容空白。
  2. 預算公式：max_tokens ≥ 思考（實測常 ~3K tokens，複雜任務更多）＋ 答案，且 prompt + max_tokens ≤ 每 slot 的 ctx。 伺服器端也能封頂：--reasoning-budget N（-1 不限、0 立即結束思考、N 為 token 上限）。
  3. 不需要思考的場景（格式化輸出、程式碼生成）直接關掉：請求帶 chat_template_kwargs: {"enable_thinking": false} 或 reasoning_effort: "none"（prompt 裡寫 /no_think 不一定生效）。關了更快、更省、content 不會被餓死。 這兩招都靠 jinja 模板引擎——新版預設開，舊版要加 --jinja。

7. 監控與量測​

curl -s http://localhost:8080/health      # {"status":"ok"}
curl -s http://localhost:8080/v1/models   # 確認實際載入的模型（對照 client 設定，防名實不符）
curl -s http://localhost:8080/props       # server 配置快照（含 total_slots、chat_template）
curl -s http://localhost:8080/slots       # 各 slot 即時狀態 ← 最有用也最會騙人，見下

/slots 讀法陷阱：n_prompt_tokens 是 slot 目前手上的全部 token 數（prompt＋已生成，即 n_past）， 會隨生成緩慢成長；n_prompt_tokens_processed 才是本輪真正 prefill 的量（prefill 完成後凍住）， n_prompt_tokens_cache 是命中 prompt cache、不用重算的量。判讀規則：

  • 「processed 凍住＋n_prompt_tokens 每秒 +1~5」＝正常生成中，不是卡死；
  • 兩個數字都凍住＋/health 或小請求也異常＝才是真卡死；
  • 生成速率 ≈ 兩次採樣的 n_prompt_tokens 差 ÷ 間隔秒數（你的版本若有 n_decoded，用它更直接）：
a=$(curl -s http://localhost:8080/slots | jq '[.[]|select(.is_processing)|.n_prompt_tokens]|add // 0'); \
sleep 30; \
b=$(curl -s http://localhost:8080/slots | jq '[.[]|select(.is_processing)|.n_prompt_tokens]|add // 0'); \
echo "$(( (b-a) / 30 )) tok/s"

不干擾大請求的活性探測（單 slot 時會排隊，多 slot 時走空 slot）：

curl -s http://localhost:8080/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"whatever","messages":[{"role":"user","content":"say OK"}],"max_tokens":5}'

server log 的 timing 行是最權威的速度來源： prompt processing … 112.25 tokens per second ＝ prefill 速度； n_decoded = 618, tg = 4.75 t/s ＝ 生成速度（tg = token generation）。兩者是不同的量，別互相比較。 走 API 的話，回應裡的 timings.prompt_per_second / timings.predicted_per_second 就是同一組數字。

8. 版本陷阱​

旗標語法隨版本演化是常態——照抄任何教學（包括本檔）報錯或行為不對時，第一動作是 llama-server -h 對現版。 已知會咬人的幾條：

  • -fa 從布林旗標改為吃值 [on|off|auto]：老教學寫裸 -fa，新版會把下一個參數吃成它的值（error: unknown value for --flash-attn: '-ctk'）。一律寫 -fa on。
  • --parallel 預設從 1 變成 auto（＝4 個 slot ＋ unified KV 共用一池）。單人用還是明示 --parallel 1，別靠預設。
  • --ctx-size 與 slot 的關係在版本間反覆：總量切 N 份、或每 slot 各一份。以啟動 log 的 n_ctx／n_ctx_seq／kv_unified／KV self size 為準，不要靠記憶（第 3 節工作例）。
  • --jinja 從要手動開變成預設開（--no-jinja 關）。tool calling、chat_template_kwargs、reasoning_effort 都靠它；舊版忘了加的症狀是「模型不會呼叫工具」。
  • --fit 新版預設開：沒明示的 ctx 會被自動縮小到裝得下——別誤判成模型變笨，看 log 裡實際的 n_ctx。
  • -hfd／--hf-repo-draft、-md／--model-draft 等 speculative 旗標名有過異動（第 5 節）。

9. 排查速查表​
