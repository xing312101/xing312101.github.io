自架離線 LLM Server 給 Coding Agent 用：完整教學

公開教學。把一台閒置的 Windows 桌機變成區域網路裡的 LLM 推論伺服器，讓筆電上的 coding agent 在雲端額度用完時無縫切換到本地模型繼續寫 code。 從硬體評估、模型選型、資源調校到客戶端接線的完整流程。客戶端以 Claude Code 為主要範例（llama.cpp 原生支援 Anthropic Messages API，不需要任何轉換 proxy），Cline / Aider / OpenCode 等其他前端也適用，見第 10 章。 適用對象：手邊有一台顯卡不強但記憶體還行的 x86 桌機，想在不改變開發習慣的前提下，多一條離線的退路。

0. 先搞懂這套架構在解決什麼問題​

常見的誤解是「本地模型 = 在自己筆電上跑」。但筆電通常記憶體不夠，而且跑推論會發燙、掉電、拖慢你正在做的事。

比較實際的做法是把推論和開發拆到兩台機器：

┌─────────────────────┐         區域網路          ┌──────────────────────────┐
│  MacBook（開發機）   │  ───────────────────────▶ │  Windows 桌機（推論機）   │
│                     │   HTTP / Anthropic API    │                          │
│  Claude Code CLI    │                           │  llama-server            │
│  你的專案原始碼       │  ◀─────────────────────── │  GGUF 模型檔              │
└─────────────────────┘        串流回傳 token       └──────────────────────────┘

這樣拆的好處：

說明
開發環境不變程式碼、git、終端機、編輯器都還在筆電上，習慣完全不用改
筆電不發燙推論的重活在另一台機器，筆電只是收 token
記憶體不打架桌機當純伺服器，32GB 全部給模型用，不用跟 IDE 搶
隨時可切換雲端額度還在就用雲端，用完了換一個指令切本地
為什麼可以直接接上 Claude Code

llama.cpp 的 llama-server 已經原生實作 Anthropic Messages API（/v1/messages 與 /v1/messages/count_tokens），包含串流、tool use、vision。

這代表不需要任何轉換 proxy。以前要靠 claude-code-router 或 LiteLLM 把 Anthropic 格式翻譯成 OpenAI 格式，現在設一個環境變數就好。

1. 最重要的觀念：決定速度的是「啟用參數」，不是「總參數」​

這是整份教學的地基。搞錯這件事，你會挑到一個檔案更小、跑起來卻慢十倍的模型。

CPU 推論的速度可以用一條很粗但很準的公式估算：

生成速度 (token/s) ≈ 記憶體頻寬 (GB/s) ÷ 每個 token 需要讀取的參數量 (GB)

每生成一個 token，CPU 必須把「這次用得到的權重」從記憶體讀進來一次。所以：

  • Dense（稠密）模型：每個 token 都要讀全部權重
  • MoE（混合專家）模型：每個 token 只啟用一小部分專家，只讀那一小部分

拿兩個真實模型對比，假設記憶體頻寬 40 GB/s（雙通道 DDR4-3200 的實測值）：

模型型態Q4 檔案大小每 token 讀取估計速度
27B 稠密模型Dense18 GB18 GB（全部）約 2 token/s
35B-A3BMoE，3B 啟用23 GB約 1.7 GB約 12–18 token/s
反直覺但關鍵

檔案比較小的那個，慢了將近十倍。

27B 稠密模型在紙面上的 benchmark 分數甚至更高，但它生成 2000 字的回覆要等十幾分鐘 —— agent 跑一輪就廢了。分數高 3 個百分點完全補不回這個差距。

在 CPU 推論的場景，MoE 幾乎是唯一可行的選擇。

順帶一提，這也解釋了為什麼「加記憶體不會讓模型變快」：加容量不等於加頻寬。插滿四條 DIMM 反而常常會被主機板強制降頻，讓速度變差。

2. 算出你的機器能跑什麼​

動手裝之前先算，免得下載完 20GB 才發現跑不動。

2-1. 三個要量的數字​

# Windows PowerShell

# 1) 可用記憶體
(Get-CimInstance Win32_OperatingSystem).FreePhysicalMemory / 1MB

# 2) 記憶體速度與通道配置（要確認是雙通道）
Get-CimInstance Win32_PhysicalMemory |
  Select-Object DeviceLocator, @{n='GB';e={$_.Capacity/1GB}}, Speed

# 3) 顯示卡可用 VRAM
nvidia-smi --query-gpu=memory.used,memory.total --format=csv

2-2. 記憶體夠不夠​

需要的 RAM ≈ 模型檔案大小 − 放進 VRAM 的部分 + 2GB（推論緩衝）

再留 4–5GB 給作業系統。以一台 32GB、可用 26GB 的機器為例：

量化檔案放 GPU佔 RAM剩餘判斷
Q3_K_XL17 GB2.5 GB約 16.5 GB9.7 GB舒服
Q4_K_XL23 GB2.5 GB約 22.5 GB3.7 GB可行但緊
Q630 GB2.5 GB約 29.5 GB不足跑不動
千萬不要讓它 swap

一旦記憶體不夠開始換頁到硬碟，速度會從十幾 token/s 掉到零點幾，而且整台機器會卡死。寧可降一級量化，也不要壓線。

2-3. VRAM 怎麼用才對​

只有 4GB VRAM 的顯卡塞不下整個模型，但不代表它沒用。正確的分工是：

  • MoE 的專家層 → 留在 CPU（參數量最大，但每次只用到一小部分）
  • 注意力層、embedding、KV cache → 放進 GPU（參數量小，但每個 token 都要算）

這樣做最大的收益在生成速度。實測（GTX 1650 4GB + 35B-A3B Q4）：

設定prefill生成
純 CPU70–74 tok/s12–13 tok/s
注意力層放 GPU74–77 tok/s27.7 tok/s
這裡違反直覺

GPU 讓生成速度翻倍，但對 prefill 幾乎沒有幫助（+5～9%）。

很容易誤以為「GPU 擅長平行運算，所以能加速批次處理提示詞」。但 prefill 的成本大頭在 MoE 專家層的矩陣運算，而那些依設計就留在 CPU —— GPU 碰不到，自然幫不上忙。

所以在小 VRAM 機器上，GPU 的價值在生成階段，不在 prefill。

3. 挑模型​

3-1. 篩選條件​

以「桌機 32GB RAM、顯卡 4–8GB」這種常見配置為例，條件是：

  1. MoE 架構，啟用參數約 3B —— 速度的硬性要求
  2. Q4 量化後 20GB 上下 —— 記憶體的硬性要求
  3. 原生支援 tool calling —— agent 要能呼叫工具，不然只是聊天機器人
  4. 長 context —— agent 每輪動輒塞進上萬 token

3-2. 候選比較​

模型架構SWE-bench VerifiedQ4 大小Context授權
Qwen3.6-35B-A3BMoE 35B / 3B 啟用73.4%23 GB262KApache 2.0
Qwen3.6-27BDense 27B77.2%18 GB262KApache 2.0
GLM-4.7-FlashMoE 30B / 3B 啟用59.2%約 18 GB128KMIT
Qwen3-Coder-NextMoE 80B / 3B 啟用70.6%約 45 GB256KApache 2.0
gpt-oss-20bMoE 21B / 3.6B 啟用約 34%12 GB128KApache 2.0

逐一淘汰：

  • Qwen3.6-27B：分數最高，但是稠密的，約 2 token/s。淘汰。
  • Qwen3-Coder-Next：架構完美（80B 只啟用 3B），但 Q4 要 45GB，32GB 機器放不下。如果你有 64GB 記憶體，這個值得試。
  • gpt-oss-20b：檔案最小跑最快，但 34% 的 SWE-bench 做不了多步驟 agent 任務。適合當補全模型，不適合當 agent。
  • GLM-4.7-Flash：能舒服跑 Q4，MIT 授權更寬鬆。但比 Qwen3.6 少 14 個百分點，差距不小。

結論：Qwen3.6-35B-A3B。它是目前 32GB 等級機器上綜合能力最強的選擇。

3-3. 量化選哪個​

品質優先的話，順序是這樣：

Q4_K_XL  >  Q3_K_XL  >>  Q4 但會 swap
用 Unsloth 的 Dynamic Quant

一般的 Q3 量化掉品質很兇，但 Unsloth 的 UD-Q3_K_XL / UD-Q4_K_XL 動態量化會針對不同層採用不同精度，同樣檔案大小下品質保留得好很多。

檔名裡有 UD- 前綴的就是。

如果記憶體壓線跑不了 Q4，兩個選擇：

  1. 降到 UD-Q3_K_XL —— 免費，品質小幅下降
  2. 記憶體升級到 64GB —— 可以舒服跑 Q4，還有空間開大 context

升級記憶體時建議換成兩條 32GB，而不是補成四條 16GB。消費級主機板插滿四條經常會被迫降頻（3200 掉到 2666），而頻寬直接決定速度 —— 為了容量犧牲頻寬並不划算。

4. Windows 端：先把資源清出來​

在裝任何東西之前，先做這四件事。順序不重要，但每一件都有實際效益。

4-1. 把螢幕改接主機板內顯​

如果你的 CPU 有內顯（Intel 非 F 版、AMD 帶 G 的型號），把螢幕線從獨立顯卡改插到主機板的 HDMI/DP。

Windows 桌面本身會佔用顯示卡的 VRAM。實測上，桌面環境會吃掉 280–400MB —— 在只有 4GB 的卡上，這是 7–10%。改用內顯之後獨顯就變成純運算卡：

改之前：|  280MiB / 4096MiB  |  Disp.A: On
改之後：|    0MiB / 4096MiB  |  Disp.A: Off

多數主機板預設就開著多顯示器輸出，插上去就能用。如果沒畫面，進 BIOS 找 IGD Multi-Monitor 或 Integrated Graphics 設成 Enabled。

驗證：

nvidia-smi
# Memory-Usage 應該接近 0MiB，Processes 應該是空的

4-2. 模型放 SSD，不要放機械硬碟​

這點很容易忽略：很多人把大容量的機械硬碟當資料碟，順手就把 20GB 的模型丟上去。

機械硬碟循序讀取約 150MB/s，載入 20GB 的模型要兩分鐘以上。更糟的是 llama.cpp 預設用 mmap 載入，作業系統回收記憶體時會把頁面丟掉，之後要用又得從硬碟重讀 —— 在機械碟上這會讓推論嚴重卡頓。

# 確認哪個磁碟是 SSD
Get-PhysicalDisk | Select-Object DeviceId, FriendlyName, MediaType, BusType

# 對照磁碟機代號屬於哪顆實體磁碟
Get-Partition | Where-Object DriveLetter | Select-Object DriveLetter, DiskNumber

把模型放在 MediaType 是 SSD 的那顆上。

4-3. 把模型目錄加入防毒排除清單​

即時掃描會在每次讀取 GGUF 時介入。20GB 的檔案被逐塊掃描，載入時間可能翻倍。

# 需要系統管理員權限
New-Item -ItemType Directory -Force -Path 'D:\ai\models'
Add-MpPreference -ExclusionPath 'D:\ai'
Add-MpPreference -ExclusionProcess 'llama-server.exe'

# 確認
(Get-MpPreference).ExclusionPath
warning

排除的是「你自己放模型的目錄」，不是關掉防毒。不要因為要跑模型就把整台機器的防護關掉。

4-4. 關掉開機自啟的重量級程式​

推論機不需要 Docker Desktop、通訊軟體、雲端同步。特別是 Docker Desktop 的 WSL2 後端，常態就吃掉 2–4GB。

# 看有哪些開機自啟項目
Get-CimInstance Win32_StartupCommand | Select-Object Name, Command | Format-List

# 動手之前先備份，方便還原
reg export "HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run" backup.reg /y

# 移除特定項目
$run = 'HKCU:\SOFTWARE\Microsoft\Windows\CurrentVersion\Run'
Remove-ItemProperty -Path $run -Name 'Docker Desktop' -Force

# 用不到的服務改成手動啟動（以 MongoDB 為例）
Set-Service -Name MongoDB -StartupType Manual
Stop-Service -Name MongoDB -Force

5. Windows 端：安裝 llama.cpp 與下載模型​

5-1. 取得 llama.cpp​

不用自己編譯，官方每次 commit 都有預編好的 Windows 執行檔。到 GitHub 的 ggml-org/llama.cpp releases 頁面，下載檔名像這樣的壓縮檔：

llama-<版本號>-bin-win-cuda-x64.zip

挑 CUDA 版本（不是 cpu 或 vulkan 版）。解壓到例如 D:\ai\llama.cpp。

CUDA 版本地雷

已知 CUDA 13.2 會產生亂碼輸出。用 nvidia-smi 確認你的驅動帶的 CUDA 版本，避開 13.2。如果剛好是，降回 13.1 或升到更新的修正版。

驗證能跑：

cd D:\ai\llama.cpp
llama-server.exe --version

5-2. 下載 GGUF 模型​

用 HuggingFace 官方 CLI：

pip install -U "huggingface_hub[cli]"

hf download unsloth/Qwen3.6-35B-A3B-GGUF ^
  --local-dir D:\ai\models\Qwen3.6-35B-A3B ^
  --include "*UD-Q4_K_XL*"
關於多模態

Qwen3.6 支援圖像輸入，對應的檔案是 mmproj-F16.gguf。純寫 code 的話不用下載 —— 省下來的記憶體拿去放 KV cache 更划算。要用再加 --include "*mmproj-F16*"。

模型很大，下載要一段時間。可以先往下看設定。

6. Windows 端：啟動 llama-server​

6-1. 完整啟動指令​

不要用批次檔包裝

最直覺的做法是寫一個 .bat，但 Windows 批次檔有兩個坑會讓你查很久：^ 續行符號需要 CRLF 行尾（在 Mac/Linux 上編輯的檔案會是 LF），而 rem 註解行裡的 | 字元仍會被當成管道解析。

失敗時的症狀很誤導：程序啟動後立刻結束，連輸出重導向的檔案都沒建立。

直接用完整命令列生成程序最可靠，日誌交給 llama.cpp 自己的 --log-file。

在 Windows 上建 D:\ai\launch.ps1：

param([int]$Ctx = 65536, [int]$Threads = 12)

$exe   = 'D:\ai\llama.cpp\llama-server.exe'
$model = 'D:\ai\models\Qwen3.6-35B-A3B\Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf'
$log   = 'D:\ai\server.log'

Get-Process llama-server -ErrorAction SilentlyContinue | Stop-Process -Force
Start-Sleep -Seconds 3

$cmd = @(
    "`"$exe`""
    "--model `"$model`""
    '--alias qwen3.6-35b-a3b'
    '--host 0.0.0.0'
    '--port 8080'
    '--api-key CHANGE_ME_TO_A_RANDOM_STRING'
    "--ctx-size $Ctx"
    "--threads $Threads"
    '--n-gpu-layers 99'
    '--cpu-moe'
    '--flash-attn on'
    '--kv-unified'
    '--cache-reuse 256'
    '--jinja'
    '--reasoning-preserve'
    '--temp 0.6'
    '--top-p 0.95'
    '--top-k 20'
    '--min-p 0.0'
    '--parallel 1'
    "--log-file `"$log`""
) -join ' '

# CIM 生成的程序不屬於 SSH 的 job object，斷線不會被殺
$r = Invoke-CimMethod -ClassName Win32_Process -MethodName Create -Arguments @{ CommandLine = $cmd }
Write-Output "rc=$($r.ReturnValue) pid=$($r.ProcessId)"
為什麼要用 CIM 生成程序

Windows OpenSSH 在 session 結束時會終止整個子行程樹。用 ssh win "llama-server.exe ..." 直接啟動的伺服器，斷線就會死。

Win32_Process.Create 生成的程序不屬於 SSH 的 job object，可以存活。

排程工作（schtasks）也能脫離 session，但不適用於需要 GPU 的程序 —— 以 SYSTEM 身分執行時位於 session 0，無法透過 WDDM 存取顯示卡，CUDA 初始化會失敗並回傳 LastTaskResult: 255。

6-2. 每個參數在做什麼​

參數作用為什麼這樣設
--host 0.0.0.0監聽所有網路介面必要。預設只聽 127.0.0.1，那樣筆電連不進來
--api-key簡易存取驗證開放到區網就該設，隨便一組長字串即可
--aliasAPI 對外的模型名稱之後 Claude Code 要用完全一樣的字串
--threads推論用的執行緒數實測影響很小，見 6-3
--n-gpu-layers 99盡量把層放進 GPU搭配下一行，實際上只有非專家層會進 GPU。用數字不要用 all，all 會被解析成 -2 而中止自動配置
--cpu-moeMoE 專家層留在 CPU小 VRAM 機器的關鍵。專家層佔了絕大多數參數
--flash-attn on啟用 Flash Attention省 VRAM
--kv-unified統一的 KV cache 配置單使用者情境下較單純
--cache-reuse 256前綴快取的進階模式見 6-5，某些架構會自動停用但無害
--jinja啟用 Jinja 模板引擎tool calling 的必要條件，少了它 agent 不能用
--reasoning-preserve保留多輪推理脈絡支援 thinking 的模型才有意義
--parallel 1只開一個推論槽單人使用時全部資源給一個請求，最快
不要量化 KV cache（除非你的顯卡有 tensor core）

--cache-type-k q8_0 --cache-type-v q8_0 看起來是穩賺的優化：KV cache 記憶體砍半，品質幾乎無損。

但在沒有 tensor core 的顯卡上（GTX 16 系列、Pascal 等），量化 KV cache 搭配 flash attention 的 CUDA kernel 不受支援，注意力運算會整個退回 CPU。

實測後果：生成速度從 24 tok/s 掉到 11 tok/s，GPU 使用率變成 0%。而諷刺的是 —— 它省下來的記憶體根本不需要省，f16 的 KV cache 在 65536 context 下也只佔 4GB 中的 3.9GB。

判斷方式：啟動後跑一次生成，同時看 nvidia-smi。GPU 使用率應該有明顯負載；如果是 0% 而 CPU 也沒跑滿，就是掉進這個坑了。

也不要用 --no-mmap

llama.cpp 會提示「tensor overrides to CPU 搭配 mmap 效能較差，考慮用 --no-mmap」。

實測結果相反：加上之後模型載入從 10 秒變 30 秒、可用記憶體從 21GB 掉到 6.8GB，而速度沒有變快。警告訊息不等於建議。

6-3. 混合架構 CPU：執行緒不是開越多越快​

Intel 從第 12 代開始採用混合架構，同一顆 CPU 上有兩種核心：

  • P-core（效能核心） —— 快，有超執行緒
  • E-core（效率核心） —— 慢，沒有超執行緒

以 i7-12700 為例，規格寫 12 核 20 執行緒，實際組成是 8 個 P-core + 4 個 E-core。

常見的推論是：llama.cpp 每一層算完要在同步點會合，只要有執行緒跑在慢的 E-core 上，其他 P-core 就得等它，所以應該只用 P-core 數（--threads 8）。

但實測結果是差異很小：

threadsprefill生成
873.5 tok/s27.76 tok/s
1277.0 tok/s27.71 tok/s

生成幾乎相同，prefill 反而是用滿 12 個實體核心略勝。E-core 拖累同步點的效應，在這個工作負載下沒有明顯到值得特別設定。

結論

先用實體核心數，再實測比較。 不要因為「聽起來合理」就直接設成 P-core 數。

--threads 12    # 實體核心數，起手值
--threads 8     # 只用 P-core，值得比較

查你的 CPU 組成：

Get-CimInstance Win32_Processor |
  Select-Object Name, NumberOfCores, NumberOfLogicalProcessors

若「邏輯處理器數」不等於「核心數 × 2」就是混合架構。以 12 核 20 執行緒為例：P + E = 12、2P + E = 20，解得 P = 8、E = 4。

用 llama-bench 一次比較多組設定，比手動重啟伺服器快得多：

llama-bench -m 模型.gguf -p 512 -n 128 -t 8,12 -ngl 0,99 -ncmoe 99 -fa on -r 2 -o md

注意 llama-bench 的參數名稱和 llama-server 不同（是 -ncmoe 不是 --cpu-moe）。

6-4. 調校 --cpu-moe：把 VRAM 榨乾​

--cpu-moe 是把全部專家層留在 CPU。如果 VRAM 還有空間，可以搬一部分專家到 GPU 換取速度。

用 --n-cpu-moe N 做微調 —— 它的意思是「前 N 層的專家留在 CPU」，所以 N 越小，放進 GPU 的專家越多。

調校流程：

  1. 先用 --cpu-moe 啟動，另開一個視窗跑 nvidia-smi 看 VRAM 用了多少
  2. 假設模型有 64 層，改成 --n-cpu-moe 64（等同全留 CPU），再逐步往下調
  3. 每次降 4：60 → 56 → 52…
  4. 直到啟動時出現 CUDA out of memory，退回上一個能跑的值
# 監看 VRAM（另開一個終端機）
nvidia-smi --query-gpu=memory.used,memory.total --format=csv -l 2

目標是讓 VRAM 用到 90% 左右，留一點餘裕給 context 增長。

6-5. 前綴快取：整套方案可不可行的關鍵​

Agent 場景有個特性：每一輪送出的提示詞，開頭都跟上一輪一模一樣（系統提示詞、工具定義、已讀過的檔案），只有結尾多了新內容。

如果每輪都要重算整段前綴，以實測的 50 tok/s prefill 計算，光「讀題目」就要好幾分鐘 —— 本地 agent 會直接不可用。

實測前綴快取的效果：

第 1 次（冷啟動）: 7,720 token → 135,160 ms
第 2 次（同前綴）: 7,720 token →     107 ms   ← 快 1,263 倍

前綴完全相同時，已算好的 KV 直接沿用，成本幾乎歸零。這是整套方案成立的前提。

cache_reuse 被停用不等於沒有快取

啟動日誌可能出現：

W srv load_model: cache_reuse is not supported by this context, it will be disabled

這在採用線性注意力／混合架構的模型上很常見（例如 Gated DeltaNet），因為那類層的遞迴狀態無法做 KV shifting。

但 --cache-reuse 只負責「有缺口的重用」（中間刪掉一段後把後面接上）。完全前綴匹配的快取是另一套機制，不受影響，上面那個 1,263 倍就是在這個警告出現的情況下量到的。

實務上的意義：

  • 一個任務留在同一個 session 做完 —— 大檔案的 prefill 只付一次
  • 避免會改寫前面內容的操作（context 壓縮、編輯歷史訊息），那會打斷前綴
  • 開新對話等於重新付全額

6-6. 開放防火牆​

# 系統管理員權限執行
New-NetFirewallRule -DisplayName "llama-server" `
  -Direction Inbound -Protocol TCP -LocalPort 8080 `
  -Action Allow -Profile Private
warning

-Profile Private 限定只在私人網路生效。不要設成 Public，也不要把這個埠轉發到公網 —— llama.cpp 的 API key 只是很基本的防護。

6-7. 驗證​

在 Windows 本機先測：

curl http://127.0.0.1:8080/v1/models -H "Authorization: Bearer CHANGE_ME_TO_A_RANDOM_STRING"

再從 Mac 測（換成你的桌機 IP）：

curl http://192.168.11.182:8080/v1/models -H "Authorization: Bearer CHANGE_ME_TO_A_RANDOM_STRING"

回傳的 JSON 裡應該看得到 qwen3.6-35b-a3b，跟 --alias 設的一致。

7. 客戶端：把 coding agent 指過去（以 Claude Code 為例）​

7-1. 需要哪些環境變數​

變數值說明
ANTHROPIC_BASE_URLhttp://<桌機IP>:8080指向你的 llama-server
ANTHROPIC_AUTH_TOKEN你設的 api-key對應 --api-key
ANTHROPIC_DEFAULT_SONNET_MODELqwen3.6-35b-a3b對應 --alias
ANTHROPIC_DEFAULT_HAIKU_MODELqwen3.6-35b-a3b不能漏，見下方說明
ANTHROPIC_DEFAULT_OPUS_MODELqwen3.6-35b-a3b同上
CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS1關掉本地伺服器不認得的實驗性標頭
三個模型層級都要設

Claude Code 內部會依任務類型呼叫不同層級的模型 —— 主要工作用 Sonnet 層、產生標題和摘要之類的雜務用 Haiku 層。

只設 Sonnet 的話，那些雜務請求會因為找不到模型而失敗，症狀通常是對話標題一直是空的、或是某些操作莫名卡住。三個都指到同一個本地模型就對了。

7-2. 做成可切換的指令（推薦）​

因為使用情境是「雲端額度用完才切本地」，不要直接改 ~/.claude/settings.json —— 那會讓你連雲端都回不去。做成另一個指令比較好用。

在 ~/.zshrc 加：

# 本地模型伺服器
export LOCAL_LLM_HOST="192.168.11.182:8080"
export LOCAL_LLM_KEY="CHANGE_ME_TO_A_RANDOM_STRING"
export LOCAL_LLM_MODEL="qwen3.6-35b-a3b"

claude-local() {
  ANTHROPIC_BASE_URL="http://${LOCAL_LLM_HOST}" \
  ANTHROPIC_AUTH_TOKEN="${LOCAL_LLM_KEY}" \
  ANTHROPIC_DEFAULT_SONNET_MODEL="${LOCAL_LLM_MODEL}" \
  ANTHROPIC_DEFAULT_HAIKU_MODEL="${LOCAL_LLM_MODEL}" \
  ANTHROPIC_DEFAULT_OPUS_MODEL="${LOCAL_LLM_MODEL}" \
  CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS="1" \
  claude "$@"
}

重新載入之後就有兩個指令：

claude          # 走雲端，額度還在時用這個
claude-local    # 走桌機上的本地模型

7-3. 確認真的切過去了​

進到 claude-local 之後隨便問一句，同時在 Windows 那邊看 llama-server 的終端機輸出 —— 應該會即時跑出處理日誌。沒動靜就表示請求根本沒送到。

8. 你該預期什麼​

這節很重要。期待錯了，你會覺得整套東西沒用。

8-1. 速度​

以下都是 i7-12700 / 32GB DDR4-3200 / GTX 1650 4GB 跑 35B-A3B Q4 的實測值：

指標實測對照 Claude 雲端
生成速度24–25 token/s慢數倍
Prefill（冷啟動）50–57 token/s幾乎感覺不到
Prefill（前綴命中）7,720 token → 107 ms差距幾乎消失
27,219 token 的檔案冷啟動9 分鐘數秒
模型載入3–10 秒—
Prefill 遠比想像中慢，而且會越來越慢

最容易誤判的就是 prefill。直覺會覺得「批次處理提示詞應該很快」，但實測只有 50 tok/s 上下，而且隨 context 加深持續下降：

n_tokens =  6144   60.5 tok/s
n_tokens =  8192   59.6 tok/s
n_tokens = 10240   58.5 tok/s
n_tokens = 12288   57.3 tok/s

因為注意力成本隨序列長度增加。所以大檔案的代價是超線性的，不能用「行數 × 固定速率」線性估算。

第一輪一定很慢，之後靠前綴快取會快到幾乎無感 —— 前提是不要開新對話、不要壓縮 context（見 6-5）。

8-2. 能力​

SWE-bench Verified 73.4% 這個數字聽起來很高，但實際使用時的體感大概是雲端旗艦模型的五到七成。具體來說：

做得到做不好
單一檔案的明確修改跨多檔案的大規模重構
寫測試、補型別、加註解模糊需求的架構設計
解釋既有程式碼需要長時間推理的疑難 debug
照範例產生樣板程式需要大量上下文的整合工作

8-3. 先估算你的專案跑不跑得動​

同樣的硬體，在不同專案上的體感可能天差地遠 —— 關鍵不是專案總行數，是你單一檔案的大小。

程式碼大約每行 10–12 個 token。加上 Claude Code 本身的系統提示詞和工具定義（約 13,000 token），一輪任務的 context 需求是：

需要的 context ≈ 13,000 + (要讀的檔案行數 × 11)

換算成首輪等待時間（依本文硬體的實測 prefill 速率，且已計入隨長度遞減的效應）：

要改的檔案約需 context首輪 prefill
200 行15,000約 4 分鐘
600 行20,000約 6 分鐘
1,200 行26,000約 8 分鐘
2,400 行39,000約 13 分鐘

2,408 行的檔案實測是 27,219 token、9 分鐘（不含系統提示詞）。

再加上 thinking 模式的開銷：開啟推理時，每輪會先生成數百個推理 token 才開始回答，以 24 tok/s 計算大約是每輪多 20–30 秒。多輪任務要乘上輪數。

這些數字只有首輪要付

前綴快取命中後幾乎歸零。所以真正的成本是「每個 session 開場一次」，不是「每輪」。

這也決定了正確的用法：不要為了小事開新對話。

先用這個指令看看你的專案落在哪個區間：

# 統計原始碼行數分佈（依你的專案調整副檔名與排除路徑）
find . -type f \( -name "*.py" -o -name "*.js" -o -name "*.vue" \) \
  -not -path "*/node_modules/*" -not -path "*/.venv/*" -print0 \
| xargs -0 wc -l | sort -rn | head -20

判讀方式：

多數檔案的大小本地模型體感（開場成本）
300 行以下順暢，開場約 4 分鐘，之後每輪數十秒
300–1,000 行可用，開場 5–7 分鐘
1,000 行以上開場 8–13 分鐘，建議留給雲端處理
大檔案的實務分工

如果專案裡有一批特別大的檔案，最有效的策略是依檔案大小分流：雲端額度還在的時候優先處理大檔案，把本地模型留給中小檔案。

這比「先用雲端直到額度歸零，再全部轉本地」有效率得多。

8-4. 一次真實任務的完整實測​

前面都是合成基準。實際用 claude -p 問一個純讀取的問題（「某支 API 有沒有權限問題？」，需要跨兩個檔案追查授權掛載方式）：

項目結果
總耗時18.9 分鐘
Tool calling穩定，多輪 Read/Grep 正常完成
答案結論正確，但兩點論證裡有一點誤讀了程式碼註解的語意

同一個問題，雲端旗艦模型約 30 秒。

這是最差情況，但也別過度樂觀

-p 非互動模式每次從零開始，光系統提示詞（約 13,000 token）就要 4–5 分鐘。互動式 session 的第二題之後會命中前綴快取，估計降到 3–5 分鐘。

即使如此，對互動式開發仍然太慢。比較務實的定位是「額度用完時的緊急備援」或「掛著慢慢跑的批次任務」，而不是日常工具。

副作用：claude.ai connector 會被停用

設定 ANTHROPIC_AUTH_TOKEN 之後會看到：

claude.ai connectors are disabled because ANTHROPIC_API_KEY or another
auth source is set and takes precedence over your claude.ai login

只影響指向本地模型的那個 session，雲端 session 不受影響。

8-5. 用法要跟著調整​

  • 把任務切小。 不要說「幫我重構這個模組」，改成「把這個函式的錯誤處理改成 Result 型別」
  • 每個 diff 都自己看過。 本地模型更容易改錯地方
  • 善用前綴快取。 同一個任務盡量在同一個 session 裡做完，開新對話等於重新 prefill
  • 心態上當它是「額度用完時的備援」，不是雲端的替代品

9. 疑難排解​

症狀原因解法

10. 延伸：不用 Claude Code 的其他前端​

如果你不想綁在 Claude Code，llama-server 同時也提供標準的 OpenAI 相容 API（/v1/chat/completions），可以接：

工具型態特點
ClineVS Code 擴充agent 迴圈完整，每個 diff 可逐一核准
Aider終端機 + git對能力較弱的模型容忍度最高，架構最不依賴 tool calling
OpenCode終端機 TUI操作感接近 Claude Code
Continue.devVS Code 擴充偏向補全和對話，agent 能力較弱

其中 Aider 特別值得一提：它不靠模型的 tool calling 能力，而是要求模型輸出特定格式的 diff，再由 Aider 自己套用。這讓它在本地小模型上的成功率明顯高於其他工具。
