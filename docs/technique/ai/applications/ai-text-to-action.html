用 AI 把自然語言回報轉成系統動作

團隊成員習慣在聊天群組打一句話回報進度。以維運團隊為例：

web-1~4 cert 更新完成
db-2 備份 失敗，磁碟滿了

希望系統自動找出「是哪幾筆任務」，然後更新狀態。聽起來是「丟給 LLM 解析一下」就好， 實際做起來，難的幾乎都不在模型。

本文先看常見做法哪裡出問題，再說明比較穩的架構、解析方式怎麼選、領域知識怎麼放進系統， 什麼時候才需要訓練模型，最後用一個可執行的範例把整套串起來。

1. 常見做法與它的問題​

最直覺的做法是兩步：

  1. 用 regex 或 LLM 把文字解析成欄位（主機、作業類型、結果）。
  2. 拿這些欄位去資料庫 LIKE 查詢，查到的任務直接改狀態。

這樣做會遇到的問題：

問題現象原因
對到太多說的是 web-1，結果 web-10、web-11 也被改到用 LIKE 'web-1%' 前綴比對
對不到使用者打「cert」，資料裡的作業名稱是「憑證更新」解析結果存的是使用者原字，比對時要求名稱包含它
全有或全無一則訊息有三段，一段對不到，整則都失敗沒有逐段處理結果
越權任何人都能改任何任務查詢範圍是整個專案，沒限定回報人
詞彙寫死新服務、新作業類型要改程式才認得別名表、名稱清單寫在程式碼裡
狀態被往回改「做一半」把已經待驗證的任務退回進行中意圖直接對應到狀態，沒有狀態機
規則兩套聊天和網頁後台改狀態的行為不一致、通知沒發聊天這邊直接寫資料庫，沒走既有的 service
對話狀態遺失服務重啟或多 worker 時，等附件、等確認的狀態不見對話狀態存在程式記憶體
按鈕失效長訊息的確認按鈕按了沒反應把原文和 id 清單塞進按鈕資料，超過平台長度上限（LINE postback data 上限 300 字）
解析器兩套同一句話，LLM 和規則解析的結果不同LLM 失敗時降級到另一套規則解析
無法量測改了 prompt 不知道變好還是變壞沒有評測集，只靠手動試幾句話

這些問題的共同原因是：把模型的輸出直接當成要執行的動作，而該放在系統層的東西 （權限、狀態機、確認、紀錄）被寫進了聊天機器人的處理程式裡。

2. 核心原則：AI 提案，系統決定​

模型永遠不直接改資料。它的輸出是一份提案，要經過程式解析、規則檢查、 必要時人工確認，才交給既有的業務邏輯執行。

輸入（LINE / Slack / Email / 表單 / 語音）
 → ① 取得情境：這是誰、他能動哪些東西（候選範圍）
 → ② 理解：模型把輸入轉成「提案」（只能從已知詞彙和動作裡選）
 → ③ 解析：程式把提案裡的條件展開成實際資料（entity linking）
 → ④ 檢查：權限、狀態機、前置條件、信心分數 → 自動執行／請人確認／轉人工
 → ⑤ 確認：用人看得懂的方式呈現會改什麼，可以逐項接受或退回
 → ⑥ 執行：走既有的 domain service，冪等、留稽核紀錄、可以撤銷
 → ⑦ 回饋：人工的修正寫回別名、範例和評測集

2.1 先限縮範圍，再讓模型理解​

權限和範圍在把資料交給模型之前就要限縮好。例如候選任務只取「指派給這個人、還沒完成的」。 模型看不到的東西就不可能動到，這比在 prompt 裡寫「不要動別人的資料」可靠得多。

範圍限縮之後，很多難題會自己消失：

  • 專案幾乎不用猜：候選任務只屬於一個專案就直接用；屬於多個時，只在這幾個裡面挑，挑不出來就請使用者選。
  • 文字提到的專案不在候選裡時，可以明確回覆「你在這個專案沒有被指派的任務」。

2.2 模型只輸出中間格式​

先定義提案的格式，例如：

{
  "segments": [
    {
      "action": "mark_done",
      "selectors": { "hosts": ["web-1", "web-2", "web-4"], "job": "憑證更新" },
      "source_text": "web-1~4 cert 更新完成",
      "confidence": 0.92
    }
  ]
}
  • action 只能從動作清單裡選。
  • selector 的值用 JSON schema 的 enum 限制在已知詞彙內（這次候選範圍裡實際存在的主機、作業類型）。
  • 模型輸出的是條件，不是 task id。展開成實際任務交給程式處理，結果可以重現，也方便測試。
  • 意圖放在每一段上，不要整則訊息共用一個。同一則訊息常常同時有「A 完成」和「B 失敗」。

2.3 解析和理解分開​

「辨識出提到 cert」跟「cert 是哪幾筆任務」是兩個問題。後者用程式處理，依序比對：

  1. 完全相同
  2. 別名表
  3. 模糊比對（處理錯字）
  4. embedding 相似度

對到多個可能時，回頭問使用者，不要自己猜。

資料端也要先正規化，比對只做精確比對：

  • 主機名稱統一成「前綴＋數字」（Web-02、web 2、WEB2 都變成 web-2）。區間只展開實際存在、而且數字完全落在區間內的主機，web-1~4 就不會碰到 web-10。
  • 文字提到、但不在候選範圍裡的對象（例如候選裡沒有的主機）要記下來，這一段轉人工，不要默默忽略。
  • 沒有指定對象時不要預設成「全部」。「cert 更新完成」沒說是哪幾台，對到不只一筆就請使用者選，不要把這個人所有的憑證任務一起改掉。
  • 同一則訊息裡對同一筆資料說了互相矛盾的話（「web-1~4 完成，web-1 失敗」），兩段都轉人工，不要讓後面的覆蓋前面的。
  • 作業類型用資料庫裡的清單，加上一張別名表（cert、SSL 都指「憑證更新」），不要寫死在程式裡。

2.4 用動作清單管風險​

每個動作宣告：參數、前置條件、可不可以撤銷、風險等級。依照這些屬性決定能多自動：

風險處理方式
可撤銷、低風險可以自動執行
中風險要使用者確認
高風險或無法撤銷只產生建議，由人執行
tip

自動化程度要靠數據逐步放寬：一開始全部都要確認；某一類動作量測下來 precision 夠高，才放寬成自動執行。

狀態轉換要有「不能往回改」的規則：

  • 「完成」只把進行中或驗證失敗的任務改成待驗證，已經是待驗證以上的跳過，並在確認畫面列出。
  • 「做一半」「還在跑」只寫備註，不改狀態。
  • 「失敗」「受阻」改成受阻，並記錄原因。

2.5 確認畫面是產品的核心​

  • 用 diff 的方式呈現：「哪 12 筆會從進行中改成待驗證」。
  • 逐段給結果，不要全有或全無：對到的段落可以直接確認，對不到的段落單獨轉人工。
  • 可以逐項勾選或取消，執行後留一段時間可以撤銷。
  • 選項多時，聊天卡片不好操作，改開一個網頁（例如 LINE 的 LIFF、Slack 的 modal）讓使用者勾選。
  • 使用者的確認和修正，本身就是最好的標註資料。

2.6 執行不要另外寫一套​

共用網頁後台的同一個 service：同一套狀態機、同樣的通知、同樣的稽核紀錄。 AI 只是另一個入口，不是另一套系統。

2.7 對話狀態和每一步都存下來​

  • 建一張草稿表，存原文、解析結果、每段對到的 id、附件和狀態。按鈕只帶草稿 id。 這樣同時解決狀態遺失、按鈕資料長度上限、重複按兩次的問題（同一份草稿只能確認一次）。
  • 每一步都記錄：輸入、模型和 prompt 版本、提案、解析結果、檢查結果、使用者最後的決定。 呼叫 LLM 的話，也記下實際回應的模型和 token 用量 —— 有設備援模型時，回答的不一定是你指定的那一個。 這些紀錄會直接變成評測集、few-shot 範例、別名表的來源和除錯軌跡。

3. 解析方式：不是只能靠 prompt​

prompt 只是其中一小塊，而且是最不可靠的一塊。可以分成幾層看：

3.1 從輸入下手：不讓使用者打自由文字​

最可靠的做法是根本不解析文字。在聊天軟體裡開一個網頁，列出這個人自己的任務， 依主機、作業類型分組，勾選後按「完成」或「受阻」，可以順便附截圖或 log。 自由文字留給備註用，不拿來推斷要改哪些任務。

缺點是大家習慣打一行字。要不要改變使用習慣，是產品決定，不是技術問題。

3.2 不用 LLM：規則解析，但詞彙從資料庫來​

這類回報其實相當固定，大多是「對象＋作業＋結果」。規則解析常見的問題不在「用了規則」，而在：

  • 詞彙寫死在程式裡
  • 比對用 LIKE

改成從候選範圍動態產生詞典（這個人實際有的主機、作業類型和別名）， 再對文字做斷詞、字典比對、展開區間，就能涵蓋大部分訊息。結果可以重現、可以寫單元測試， 沒有 API 費用和延遲。錯字和俗稱用字元層級的模糊比對加別名表處理。

3.3 用 LLM，但靠 API 機制約束​

機制做法取捨
Structured output用 JSON schema 強制輸出格式，欄位值用 enum 限定只設「回傳 JSON」不夠，要給 schema 才是強制
Function calling讓模型呼叫 list_hosts()、find_jobs("cert") 查完再回答比較準，但要多幾輪呼叫，比較慢
動態範例從已人工確認的歷史回報裡找最相似的幾筆當範例範例隨資料累積變好，不用改程式
Fine-tune／小模型用標註資料訓練需要大量標註資料，見第 6 節

3.4 不管用哪一種，正確性都靠解析之外的機制​

  • 候選範圍：解析錯了也改不到別人的資料。
  • 程式展開：模型只給條件，程式算出實際資料。
  • 狀態機：不合法的轉換直接拒絕。
  • 使用者確認：最後一道人工檢查。
  • 評測集：用真實訊息量測，不憑感覺調 prompt。

prompt 寫得好不好，影響的是「能自動對到多少」（recall）；上面這幾項保證的是「不會改錯」（precision）。

3.5 建議順序​

  1. 收集 100–200 則真實輸入，標註「應該對到哪些資料」。
  2. 先做「資料庫詞典＋規則」，量測命中率。
  3. 剩下規則處理不了的部分，看量和樣子再決定要不要加 LLM。如果加，用 structured output 只處理這些訊息， 兩者共用同一套「條件展開成資料」的程式，不要變成兩套各自比對的系統。
  4. 勾選網頁不管有沒有 LLM 都值得做：對不到或有歧義時就導過去。
warning

不要維持兩套平行的解析器（例如 LLM 失敗就降級到另一套規則）。兩套的行為會不一致，bug 也會變兩倍。 LLM 失敗時應該轉人工或導去勾選頁，而不是換另一套邏輯猜。

4. 這只是 bot 嗎？​

不是。bot 是介面，回答的是「使用者怎麼跟系統互動」；上面的架構回答的是 「一句話怎麼安全地變成資料異動」。

指令式 botAgentAI 工作流程系統
誰決定要做什麼寫死的規則模型自己模型提案，程式和人決定
模型的角色沒有，或只做分類規劃加執行只負責理解，輸出提案
業務規則放在哪散在 handler 裡prompt 裡動作清單和狀態機
可預測性高，但很死板低高，又有彈性
規模變大時每多一種輸入就多寫一段越大越難控制新增領域插件就好

為什麼不只是 bot：

  • 入口可以換：LINE、Slack、Email、表單、語音、掃描文件、監控告警都接得進來，後面走同一條流程。
  • 觸發不一定來自人：排程或事件也能觸發，例如「發現 3 天沒回報的任務，就產生催辦提案」。
  • 核心價值不在對話：動作清單、自動化分級、稽核紀錄、評測集、回饋資料才是資產，對話介面隨時可以替換。

這類系統通常叫 AI workflow automation 或 human-in-the-loop decision system，分三層：

  1. 入口層：bot 是其中一種，負責收輸入、回結果、提供確認畫面。
  2. 決策層：提案、解析、檢查、自動化分級，這是平台本體。
  3. 執行層：既有的業務系統和 service，AI 不另寫一套。

核心不綁特定業務。每個業務領域提供一個插件：實體 schema、詞彙來源、動作清單、狀態機、確認畫面的呈現方式。 進度回報、費用報銷、排班、客服單都是同一套核心，換插件就好。

5. 把領域知識變成 AI 系統的資料​

一個公司或領域的「知識」不是同一種東西。要先拆成幾類，每一類放進系統的方式不一樣。 最常見的錯誤，是把所有東西都塞進 prompt，或全部丟進向量資料庫。

5.1 六類知識​

類型例子放在哪怎麼給模型
主資料專案、主機、服務、人員、客戶原本的業務系統（唯一資料來源）執行時依範圍查詢，當成候選清單或 enum 注入
詞彙／本體標準概念、別名、上下位關係（cert、SSL 都指 憑證更新；web-* 屬於 前台服務）詞彙表，分層管理依情境挑出相關子集注入；不認得的詞由解析層比對
規則／流程狀態機、權限、動作前置條件程式碼或設定檔（DSL／YAML）不交給模型，由檢查層執行
解讀慣例「✅ 代表完成」「還在跑 代表做一半」已確認的歷史案例動態挑出最相似的幾則當範例
非結構文件SOP、runbook、規格書、合約文件索引（向量＋metadata）RAG，依租戶／專案篩選後再取
歷史結果提案加上人工最後的決定決策紀錄變成評測集、範例、別名來源，最後才考慮 fine-tune

5.2 三種把知識給模型的方式​

方式適合
執行時注入（prompt、RAG、schema enum）會變的事實：任務清單、人員、狀態
工具查詢（function calling）資料量太大塞不進 context
寫進權重（fine-tune）穩定的語言模式：行業術語的語感、輸出格式
tip

會變的放在資料，不放進權重；規則放在程式裡，不放進 prompt。 prompt 裡的規則模型可能不遵守，程式裡的規則一定會執行。

5.3 導入一個新領域或新公司​

  1. 盤點資料來源：資料庫 schema、文件、聊天紀錄、表單、試算表，以及資深人員腦中的知識。
  2. 建領域模型：跟領域專家一起定義實體、關係、動作和狀態。這一步決定系統的上限，最不能省。
  3. 整理詞彙：從歷史訊息挖高頻詞（n-gram 統計，或讓 LLM 提取候選詞），由專家審核後歸到標準概念下。
  4. 標註評測集：抽樣真實輸入，請專家標出正確結果。
  5. 串接即時資料：透過唯讀 view、資料同步或 CDC，不複製一份資料到 AI 系統去維護。
  6. 冷啟動：先用 shadow 模式（只記錄、不執行）收集提案和人工決定。

5.4 分層與隔離​

  • 知識分三層繼承：行業層（跨公司共用的術語、通用分類）→ 公司層（內部用語、流程差異）→ 專案層（特有名稱和例外）。下層可以覆蓋上層。
  • 租戶隔離做在查詢層：其他公司的資料在查詢時就篩掉，不能靠 prompt 寫「不要用其他公司的資料」。向量索引按租戶分開，或強制加 metadata filter。
  • 知識要有版本和生效時間：別名會改、專案會結束、服務會改名。要能回溯「這個提案當時是用哪一版詞彙判斷的」。

5.5 組裝情境（context builder）​

執行時要有一個專門的元件，針對每個輸入，在 token 預算內組出這次需要的資料：

  1. 這個人的候選實體（已限縮範圍）
  2. 跟輸入相關的詞彙子集
  3. 最相似的 k 個歷史確認案例
  4. 這次可以用的動作清單和 schema

這個元件決定了模型「這次看到什麼」，重要性比 prompt 的措辭高得多。

5.6 治理​

  • 每一類知識都要有負責人。例如別名表由營運或領域負責人透過後台維護，不是工程師改程式碼。
  • 自動學到的知識要審核：從人工修正學到的別名，達到一定次數或由人核准才生效。
  • 偵測衝突：同一個別名在不同專案指向不同東西時，自動降到專案層。
  • 隱私：送到外部模型前遮罩個資，確認合約寫明「不用於訓練」，注意資料存放地區的規定。

6. 需要重新訓練模型嗎？​

上面的做法大部分都不用重新訓練模型。「教」模型有兩種完全不同的意思：

  1. 不動模型，每次把資料放進輸入（主流做法）：像給一位通才顧問一份這次的資料夾。 顧問不用重新上學，資料夾換掉，知識就更新了，模型也可以隨時換成別家的。第 5 節的做法全部屬於這一類。
  2. 改動模型權重（fine-tune）：拿你的資料再訓練一次，讓模型把某些模式內化。

6.1 四條路​

方式怎麼做適合情境
供應商的 fine-tune API上傳訓練資料，由供應商訓練，拿到私有模型 ID最省事；不是每家、每個模型都開放
開源模型自己訓練下載開放權重模型（Llama、Qwen、Gemma 等），用 LoRA 在自己的 GPU 上訓練並部署資料不能離開公司，或要完全掌控
訓練小型專用模型不用大型語言模型，訓練文字分類或實體辨識（NER）小模型任務很窄、量大、要求低延遲
從頭預訓練自己從零訓練一般公司不會做，運算成本動輒數百萬美元以上

6.2 Fine-tune 的步驟​

  1. 準備資料：成對的「輸入 → 理想輸出」，格式通常是 JSONL。決策紀錄就是現成來源：原始輸入，加上人工確認過的正確提案。通常要幾百到幾千筆，品質比數量重要。
  2. 切出測試集：留一部分不拿去訓練。
  3. 訓練：現在多用 LoRA——原模型權重凍結，只訓練一組很小的附加參數（adapter），成本比整個重新訓練低好幾個數量級。
  4. 比較：跟「原模型＋RAG＋範例」在同一份測試集上比，沒有明顯比較好就不要用。
  5. 部署和監控：持續收集修正資料，定期重新訓練。

訓練資料的樣子（以對話格式為例）：

{"messages": [
  {"role": "system", "content": "把維運回報轉成提案 JSON，只能使用提供的詞彙。"},
  {"role": "user", "content": "web-1~4 cert 更新完成"},
  {"role": "assistant", "content": "{\"segments\":[{\"action\":\"mark_done\",\"hosts\":[\"web-1\",\"web-2\",\"web-4\"],\"job\":\"憑證更新\"}]}"}
]}

6.3 學得會與學不會的​

適合學的：

  • 行業術語和口語的語感
  • 輸出格式的穩定度
  • 讓 prompt 變短，成本和延遲下降
  • 蒸餾：用大模型加人工修正做出標註資料，再訓練一個小模型，在狹窄任務上接近大模型的品質，又便宜又快

不適合學的：

  • 會變的事實：任務清單、人員、狀態，訓練完就開始過期。
  • 規則：放進權重就無法保證一定遵守，也很難修改。
warning

fine-tune 的代價：供應商下架舊模型時要重新訓練；每次重新訓練都要重跑評測； 自己架開源模型還要有 GPU 和維運能力。

6.4 什麼時候才值得做​

同時符合下面幾點才考慮：

  • 「原模型＋RAG＋動態範例」的準確度已經調不上去。
  • 已經累積足夠的人工確認資料。
  • 呼叫量大到成本或延遲成為問題，或資料規定不能送到外部服務。

順序是：先把知識放進資料和輸入，用 shadow 模式和人工確認累積標註資料；等真的需要時，這份資料本來就有。 訓練是最後的優化，不是起點。

7. 評測與上線​

  • 按階段量測：理解的正確率、解析的 precision／recall、整體動作是否正確、自動執行比例、使用者修正比例。
  • 每次換 prompt 或模型都在 CI 裡跑評測集，像跑單元測試一樣防止退步。
  • 上線分四段：
階段做什麼
Shadow只記錄提案，使用者看不到
Suggest給建議，由人自己操作
Confirm一鍵確認後執行
Auto只開放已證明夠準的低風險動作

安全方面：輸入一律當資料處理，模型沒有自由呼叫工具的權限（用 function calling 時，工具也只限唯讀查詢、而且只能查候選範圍內的資料），所以 prompt injection 頂多產生一份錯誤提案， 會被檢查擋下來，或在確認時被人發現。執行要冪等、要限流，所有動作都可以稽核。

danger

precision 比 recall 重要：改錯資料的代價遠高於轉人工。不確定時寧可轉人工或請使用者選。

8. 實作範例​

下面用一個可以直接執行的 Python 範例，把第 2 節的七個步驟串起來。範例只用標準函式庫， 資料放在記憶體裡（實務上是資料庫的表）；parse_with_llm() 另外需要 Anthropic SDK，見 8.4。

情境是維運團隊回報主機的維護進度。資料是虛構的：兩位使用者 alice、bob，七筆維護任務。 刻意放了幾個陷阱來驗證設計：

陷阱要驗證的事
T5 是 web-10說 web-1~4 時不能被改到（第 1 節的前綴比對問題）
T3 指派給 bobalice 的回報不能改到別人的任務
T4 已經是待驗證不能被「完成」再改一次，要列在跳過清單
主機名稱存成 web-1、Web-02、web 4 混用正規化後才比對
「cert」「SSL」「kernel」是俗稱透過別名表對到標準作業名稱
回報提到候選裡沒有的 mail-1這一段轉人工，不默默忽略
「cert 更新完成」沒指定主機對到不只一筆時請使用者選，不能全部改掉
「web-1~4 完成，web-1 失敗」同一筆任務結果矛盾，兩段都轉人工
「升級到 v2」版本號不能被當成主機名稱

8.1 完整程式​

report_to_action.py
"""文字回報 → 提案 → 解析 → 檢查 → 確認 → 執行，最小可執行範例。

情境：維運團隊在聊天群組回報主機的維護進度，例如「web-1~4 cert 更新完成」。
只用標準函式庫；parse_with_llm() 另外需要 `pip install anthropic` 與 API key。
資料放在記憶體裡，實務上 TASKS、ALIASES、DRAFTS、AUDIT_LOG 都是資料庫的表。
"""
from __future__ import annotations

import json
import re
import uuid
from dataclasses import dataclass, field
from typing import Dict, List, Optional, Set, Tuple

# ── 業務資料（實務上來自資料庫）──────────────────────────────


@dataclass
class Task:
    id: str
    host: str  # 原始值，格式不一：'web-1'、'Web-02'、'web 4'
    job: str  # 作業類型的標準名稱
    status: str
    assignee: str
    notes: List[str] = field(default_factory=list)


TASKS: Dict[str, Task] = {
    t.id: t
    for t in [
        Task("T1", "web-1", "憑證更新", "進行中", "alice"),
        Task("T2", "Web-02", "憑證更新", "進行中", "alice"),
        Task("T3", "web-3", "憑證更新", "進行中", "bob"),
        Task("T4", "web 4", "憑證更新", "待驗證", "alice"),
        Task("T5", "web-10", "憑證更新", "進行中", "alice"),
        Task("T6", "db-2", "備份驗證", "進行中", "alice"),
        Task("T7", "cache-1", "核心升級", "進行中", "alice"),
    ]
}

# 別名表：俗稱 → 標準作業名稱。由後台維護，也從人工修正學習（見 learn_alias）
ALIASES: Dict[str, str] = {
    "cert": "憑證更新",
    "ssl": "憑證更新",
    "憑證": "憑證更新",
    "kernel": "核心升級",
    "備份": "備份驗證",
}

DONE_STATUSES = {"已完成"}

# ── ① 候選範圍 ─────────────────────────────────────────────


def candidates_for(user: str) -> List[Task]:
    """只取指派給這個人、還沒完成的任務。後面所有步驟都只在這個範圍內工作。"""
    return [t for t in TASKS.values() if t.assignee == user and t.status not in DONE_STATUSES]


# ── 正規化與詞彙 ───────────────────────────────────────────

# 主機前綴至少兩個英文字母，避免把「v2」「T1」這類版本號、編號當成主機
RE_HOST = re.compile(r"(?<![A-Za-z0-9])([A-Za-z]{2,})[-_ ]?0*(\d+)(?![0-9])")


def norm_host(raw: str) -> str:
    """'Web-02'、'web 2'、'WEB2' → 'web-2'。"""
    m = RE_HOST.fullmatch(raw.strip())
    if not m:
        return raw.strip().lower()
    return f"{m.group(1).lower()}-{int(m.group(2))}"


def host_key(host: str) -> Tuple[str, int]:
    prefix, _, num = host.rpartition("-")
    return prefix, int(num) if num.isdigit() else 0


@dataclass
class Vocab:
    hosts: Set[str]
    jobs: Set[str]
    aliases: Dict[str, str]  # 只留下指向候選範圍內作業的別名


def build_vocab(cands: List[Task]) -> Vocab:
    """詞彙從候選範圍動態產生，不寫死在程式裡。"""
    jobs = {t.job for t in cands}
    return Vocab(
        hosts={norm_host(t.host) for t in cands},
        jobs=jobs,
        aliases={a: j for a, j in ALIASES.items() if j in jobs},
    )


# ── ② 理解：把文字轉成提案 ─────────────────────────────────

ACTIONS = ("mark_done", "mark_blocked", "add_note", "unknown")


@dataclass
class Segment:
    action: str
    hosts: List[str]
    job: Optional[str]
    note: str
    source_text: str
    unknown_hosts: List[str] = field(default_factory=list)  # 有提到、但不在候選範圍裡的主機


RE_HOST_RANGE = re.compile(
    r"(?<![A-Za-z0-9])([A-Za-z]{2,})[-_ ]?0*(\d+)\s*[~～到至]\s*(?:[A-Za-z]+[-_ ]?)?0*(\d+)(?![0-9])"
)
RE_BLOCKED = re.compile(r"失敗|無法|卡住|受阻")
RE_PARTIAL = re.compile(r"一半|部分|還在跑")
RE_DONE = re.compile(r"完成|好了|搞定|✅")


def expand_host_range(prefix: str, start: int, end: int, known: Set[str]) -> List[str]:
    """只展開實際存在的主機，而且數字要完全落在區間內，所以 web-1~4 不會碰到 web-10。"""
    lo, hi = sorted((start, end))
    p = prefix.lower()
    return sorted((h for h in known if host_key(h)[0] == p and lo <= host_key(h)[1] <= hi), key=host_key)


def split_segments(text: str) -> List[str]:
    """依換行、句號、分號切段；逗號後面又提到主機時（「A 完成，B 失敗」）也切開。
    逗號後面沒提到主機的（「失敗，磁碟滿了」）是同一段的補充說明，併回前一段。"""
    segments = []
    for line in re.split(r"[\n；;。]+", text):
        current = ""
        for piece in re.split(r"[，,]", line):
            piece = piece.strip()
            if not piece:
                continue
            if current and RE_HOST.search(piece):
                segments.append(current)
                current = piece
            else:
                current = f"{current}，{piece}" if current else piece
        if current:
            segments.append(current)
    return segments


def parse_with_rules(text: str, vocab: Vocab) -> List[Segment]:
    """規則解析，但詞彙全部來自 vocab。"""
    segments = []
    prev_job: Optional[str] = None
    for part in split_segments(text):

        m = RE_HOST_RANGE.search(part)
        if m:
            hosts = expand_host_range(m.group(1), int(m.group(2)), int(m.group(3)), vocab.hosts)
            unknown = [] if hosts else [m.group(0)]
        else:
            mentioned = {f"{p.lower()}-{int(n)}" for p, n in RE_HOST.findall(part)}
            hosts = sorted(mentioned & vocab.hosts, key=host_key)
            unknown = sorted(mentioned - vocab.hosts)

        lower = part.lower()
        job = next((j for j in sorted(vocab.jobs, key=len, reverse=True) if j in part), None)
        if job is None:
            alias = next((a for a in sorted(vocab.aliases, key=len, reverse=True) if a in lower), None)
            job = vocab.aliases.get(alias) if alias else None
        if job is None and hosts:
            job = prev_job  # 同一則訊息裡沒寫作業的段落，沿用前一段的（「web-1~4 cert 完成，web-3 失敗」）
        prev_job = job or prev_job

        if RE_BLOCKED.search(part):
            action = "mark_blocked"
        elif RE_PARTIAL.search(part):
            action = "add_note"
        elif RE_DONE.search(part):
            action = "mark_done"
        else:
            action = "unknown"

        segments.append(Segment(action, hosts, job, note=part, source_text=part, unknown_hosts=unknown))
    return segments


def _nullable_enum(values: Set[str]) -> dict:
    if not values:
        return {"type": "null"}
    return {"anyOf": [{"type": "string", "enum": sorted(values)}, {"type": "null"}]}


LLM_LOG: List[dict] = []


def parse_with_llm(text: str, vocab: Vocab) -> Optional[List[Segment]]:
    """用 Claude 的 structured output 解析。欄位值只能從 vocab 裡選。

    失敗（拒答、輸出被截斷）時回傳 None，由呼叫端轉人工，不降級成另一套解析器。
    """
    import anthropic  # pip install anthropic

    host_values = sorted(vocab.hosts, key=host_key)
    schema = {
        "type": "object",
        "properties": {
            "segments": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "action": {"type": "string", "enum": list(ACTIONS)},
                        "hosts": {
                            "type": "array",
                            "items": {"type": "string", "enum": host_values} if host_values else {"type": "string"},
                        },
                        "job": _nullable_enum(vocab.jobs),
                        "note": {"type": "string"},
                        "source_text": {"type": "string"},
                        "unknown_hosts": {"type": "array", "items": {"type": "string"}},
                    },
                    "required": ["action", "hosts", "job", "note", "source_text", "unknown_hosts"],
                    "additionalProperties": False,
                },
            }
        },
        "required": ["segments"],
        "additionalProperties": False,
    }
    system = (
        "你把維運人員的進度回報轉成結構化提案。\n"
        "- 一則訊息可能有多段，每段一個 segment，各自判斷 action。\n"
        "- action：完成 → mark_done；失敗、受阻 → mark_blocked；做一半、只是說明 → add_note；看不出來 → unknown。\n"
        "- 主機區間（例如 web-1~4）展開成清單裡落在區間內的主機。\n"
        "- 提到但不在清單裡的主機放進 unknown_hosts。作業對不到清單就填 null，不要猜。\n"
        f"作業別名：{json.dumps(vocab.aliases, ensure_ascii=False)}"
    )

    client = anthropic.Anthropic()
    response = client.beta.messages.create(
        model="claude-opus-5-5",
        max_tokens=16000,
        # 模型拒答時由伺服器自動改用建議的備援模型
        betas=["server-side-fallback-2026-07-01"],
        fallbacks="default",
        output_config={"effort": "low", "format": {"type": "json_schema", "schema": schema}},
        system=system,
        messages=[{"role": "user", "content": text}],
    )
    # 實際回應的模型與用量也要進決策紀錄：用了備援模型時，response.model 會是備援的那一個
    LLM_LOG.append({"model": response.model, "stop_reason": response.stop_reason,
                    "input_tokens": response.usage.input_tokens, "output_tokens": response.usage.output_tokens})
    if response.stop_reason in ("refusal", "max_tokens"):
        return None

    # 中途改由備援模型回答時，content 裡會有 fallback 區塊；之前的文字是被拒答那一次的殘留，
    # 所以只取最後一個 fallback 區塊之後的文字
    blocks = list(response.content)
    last_fb = max((i for i, b in enumerate(blocks) if b.type == "fallback"), default=-1)
    raw = "".join(b.text for b in blocks[last_fb + 1:] if b.type == "text")
    data = json.loads(raw)
    return [Segment(**s) for s in data["segments"]]


# ── ③ 解析 ＋ ④ 檢查：把條件展開成任務，套用狀態機 ─────────────

# 每個動作允許的狀態轉換；不在表裡的就跳過，所以不會往回改
TRANSITIONS: Dict[str, Dict[str, str]] = {
    "mark_done": {"進行中": "待驗證", "驗證失敗": "待驗證"},
    "mark_blocked": {"進行中": "受阻"},
    "add_note": {},  # 只寫備註，不改狀態
}


@dataclass
class Change:
    task_id: str
    from_status: str
    to_status: Optional[str]  # None 代表只寫備註


@dataclass
class SegmentPlan:
    segment: Segment
    changes: List[Change]
    skipped: List[Tuple[str, str]]  # (task_id, 原因)
    problem: Optional[str]  # 有值代表這段要轉人工


def resolve(seg: Segment, cands: List[Task]) -> List[Task]:
    """精確比對：只在候選範圍內、只用正規化後的值、不用 LIKE。"""
    if not seg.hosts and seg.job is None:
        return []
    return [
        t
        for t in cands
        if (not seg.hosts or norm_host(t.host) in seg.hosts) and (seg.job is None or t.job == seg.job)
    ]


def plan_segment(seg: Segment, cands: List[Task]) -> SegmentPlan:
    if seg.action == "unknown":
        return SegmentPlan(seg, [], [], "看不出要做什麼")
    if seg.unknown_hosts:
        return SegmentPlan(seg, [], [], f"對不到主機：{'、'.join(seg.unknown_hosts)}")
    if seg.job is None:
        return SegmentPlan(seg, [], [], "對不到作業類型")
    tasks = resolve(seg, cands)
    if not tasks:
        return SegmentPlan(seg, [], [], "對不到任務")
    if not seg.hosts and len(tasks) > 1:  # 沒指定主機時不能預設成「全部」
        return SegmentPlan(seg, [], [], f"沒有指定主機，對到 {len(tasks)} 筆，請使用者選")

    allowed = TRANSITIONS[seg.action]
    changes, skipped = [], []
    for t in tasks:
        if seg.action == "add_note":
            changes.append(Change(t.id, t.status, None))
        elif t.status in allowed:
            changes.append(Change(t.id, t.status, allowed[t.status]))
        else:
            skipped.append((t.id, f"目前是「{t.status}」，不能再改"))
    return SegmentPlan(seg, changes, skipped, None)


# ── ⑤ 草稿與確認 ──────────────────────────────────────────


@dataclass
class Draft:
    id: str
    user: str
    text: str
    plans: List[SegmentPlan]
    status: str = "pending"  # pending → confirmed / cancelled


DRAFTS: Dict[str, Draft] = {}


def flag_conflicts(plans: List[SegmentPlan]) -> List[SegmentPlan]:
    """同一筆任務在同一則訊息裡被要求改成不同狀態時，相關的段落全部轉人工。"""
    owners: Dict[str, Set[int]] = {}
    for i, p in enumerate(plans):
        for c in p.changes:
            if c.to_status:
                owners.setdefault(c.task_id, set()).add(i)
    conflicted = {i for idx in owners.values() if len(idx) > 1 for i in idx}
    return [
        SegmentPlan(p.segment, [], [], "同一筆任務在這則訊息裡有不同的結果") if i in conflicted else p
        for i, p in enumerate(plans)
    ]


def propose(user: str, text: str, use_llm: bool = False) -> Draft:
    """整條流程的入口：產生草稿，還沒有改任何資料。"""
    cands = candidates_for(user)
    vocab = build_vocab(cands)
    segments = parse_with_llm(text, vocab) if use_llm else parse_with_rules(text, vocab)
    if segments is None:  # LLM 失敗：整則轉人工
        segments = [Segment("unknown", [], None, text, text)]
    plans = flag_conflicts([plan_segment(s, cands) for s in segments])
    draft = Draft(uuid.uuid4().hex[:8], user, text, plans)
    DRAFTS[draft.id] = draft
    return draft


def render(draft: Draft) -> str:
    """確認畫面：逐段列出會改什麼。按鈕只需要帶 draft.id 和段落編號。"""
    lines = [f"草稿 {draft.id}"]
    for i, p in enumerate(draft.plans):
        lines.append(f"[{i}] {p.segment.source_text}")
        if p.problem:
            lines.append(f"    ⚠️ {p.problem} → 轉人工")
            continue
        for c in p.changes:
            to = c.to_status or "（只寫備註）"
            lines.append(f"    ✅ {c.task_id} {TASKS[c.task_id].host}：{c.from_status} → {to}")
        for tid, why in p.skipped:
            lines.append(f"    ⏭  {tid} {TASKS[tid].host}：{why}")
    return "\n".join(lines)


# ── ⑥ 執行：走 service，冪等、留紀錄 ─────────────────────────

AUDIT_LOG: List[dict] = []

ALLOWED_TARGETS: Dict[str, Set[str]] = {}
for _rules in TRANSITIONS.values():
    for _frm, _to in _rules.items():
        ALLOWED_TARGETS.setdefault(_frm, set()).add(_to)


def update_task(task_id: str, to_status: Optional[str], note: str, actor: str, source: str) -> None:
    """網頁後台和聊天入口共用的 service。狀態機在這裡再檢查一次。"""
    t = TASKS[task_id]
    if to_status is not None:
        if to_status not in ALLOWED_TARGETS.get(t.status, set()):
            raise ValueError(f"{task_id} 不能從 {t.status} 改成 {to_status}")
        AUDIT_LOG.append({"task": task_id, "from": t.status, "to": to_status, "actor": actor, "source": source})
        t.status = to_status
    t.notes.append(f"[{actor}] {note}")
    # 實務上：同一個交易裡寫入異動紀錄，交易成功後發通知


def confirm(draft_id: str, user: str, accepted: List[int]) -> str:
    draft = DRAFTS.get(draft_id)
    if draft is None or draft.user != user:
        return "找不到這份草稿"
    if draft.status != "pending":  # 冪等：重複按不會重複寫入
        return "這份回報已經處理過了"

    applied = stale = 0
    for i in sorted(set(accepted)):
        if not 0 <= i < len(draft.plans):  # 按鈕資料不可信，段落編號要檢查
            continue
        plan = draft.plans[i]
        if plan.problem:
            continue
        for c in plan.changes:
            if TASKS[c.task_id].status != c.from_status:  # 草稿產生後資料被別人改過
                stale += 1
                continue
            update_task(c.task_id, c.to_status, plan.segment.note, actor=user, source=f"draft:{draft.id}")
            applied += 1
    draft.status = "confirmed"
    return f"已更新 {applied} 筆" + (f"，{stale} 筆在確認前已被其他人更新，略過" if stale else "")


# ── ⑦ 回饋：人工修正寫回別名表 ───────────────────────────────


def learn_alias(alias: str, job: str) -> None:
    """人工審核時把「tls」對到「憑證更新」，下次就能自動對到。
    實務上要達到一定次數或由人核准才生效。"""
    ALIASES[alias.lower()] = job


# ── 評測：用標註過的真實訊息量測 precision / recall ─────────────

GOLDEN = [
    # (回報人, 訊息, 正確結果：{(task_id, 新狀態)})
    ("alice", "web-1~4 cert 更新完成", {("T1", "待驗證"), ("T2", "待驗證")}),
    ("alice", "db-2 備份 失敗，磁碟滿了", {("T6", "受阻")}),
    ("alice", "cache-1 kernel 升級做一半", set()),
    ("alice", "web-10 SSL 換好了", {("T5", "待驗證")}),
    ("alice", "cert 更新完成", set()),  # 沒指定主機：請使用者選，不能全改
    ("alice", "web-1~4 cert 更新完成，web-1 失敗", set()),  # 同一筆任務結果矛盾：轉人工
    ("alice", "web-1 cert 換好了，升級到 v2", {("T1", "待驗證")}),  # v2 不是主機
]


def evaluate() -> Tuple[float, float]:
    tp = fp = fn = 0
    for user, text, expected in GOLDEN:
        draft = propose(user, text)  # 評測也會產生草稿；實務上評測要用另一個環境，不要寫進正式的草稿表
        predicted = {
            (c.task_id, c.to_status) for p in draft.plans if not p.problem for c in p.changes if c.to_status
        }
        tp += len(predicted & expected)
        fp += len(predicted - expected)
        fn += len(expected - predicted)
    precision = tp / (tp + fp) if tp + fp else 1.0
    recall = tp / (tp + fn) if tp + fn else 1.0
    return precision, recall


if __name__ == "__main__":
    print("== 評測 ==")
    p, r = evaluate()
    print(f"precision={p:.2f} recall={r:.2f}\n")

    text = "web-1~4 cert 更新完成\ndb-2 備份 失敗，磁碟滿了\nmail-1 DNS 設定完成"
    draft = propose("alice", text)
    print("== 確認畫面 ==")
    print(render(draft))

    print("\n== 使用者確認第 0、1 段 ==")
    print(confirm(draft.id, "alice", [0, 1]))
    print(confirm(draft.id, "alice", [0, 1]))  # 重複按

    print("\n== 結果 ==")
    for t in TASKS.values():
        print(t.id, t.host, t.job, t.status, t.assignee)
    print("\n== 稽核紀錄 ==")
    for row in AUDIT_LOG:
        print(row)

8.3 程式對應到架構​

步驟函式重點
① 候選範圍candidates_for()後面所有步驟只在這個範圍內工作
詞彙build_vocab()、norm_host()詞彙從候選資料動態產生，不寫死
切段split_segments()換行、句號、分號切段；逗號後面又提到主機才切開
② 理解parse_with_rules()／parse_with_llm()兩者輸出同一種 Segment，二選一，不互相降級
③ 解析resolve()精確比對，不用 LIKE
④ 檢查plan_segment()、TRANSITIONS、flag_conflicts()狀態機決定能不能改；不合法的列為跳過；對不到、沒指定對象卻對到多筆、同一筆結果矛盾的轉人工
⑤ 確認propose()、render()、Draft草稿先存起來，按鈕只帶草稿 id 和段落編號
⑥ 執行confirm()、update_task()走共用 service，再檢查一次狀態，寫稽核紀錄，冪等；段落編號來自按鈕，要檢查範圍
⑦ 回饋learn_alias()人工修正寫回別名表
評測GOLDEN、evaluate()改規則、換 prompt 或模型後都要跑

8.4 Anthropic SDK 與費用​

parse_with_llm() 用 Anthropic 官方的 Python SDK 呼叫 Claude：

pip install anthropic
export ANTHROPIC_API_KEY=...   # 在 Claude Console 建立
draft = propose("alice", "web-1~4 cert 更新完成", use_llm=True)

費用的部分要分清楚：

項目費用
安裝 SDK免費。SDK 是開源的 client 函式庫，本身不收費
呼叫 API依 input／output token 計費，需要 Claude Console 的 API key，從 Console 的帳戶扣款
Claude.ai 的訂閱方案（Pro、Max 等）不包含 API 用量。訂閱和 API 是兩套獨立的計費
Message Batches API非同步處理，費用約是一般呼叫的一半。適合 shadow 模式的大量回放和評測，不適合要即時回覆的對話
tip

沒有 API key 也能測大部分的東西：

  • 規則解析、比對、狀態機、確認流程，都不需要呼叫 API（use_llm=False）。
  • 想確認送出去的請求格式對不對，可以把 ANTHROPIC_BASE_URL 指到本機的假伺服器，攔下 SDK 送出的請求、回傳假的回應。請求不會離開本機，也不會計費。只是這樣測不到真實模型的判斷品質。

parse_with_llm() 裡幾個設定的用意：

  • output_config.format：用 JSON schema 強制輸出格式。主機和作業類型的 enum 是從候選範圍動態產生的，模型只能填這些值或 null。
  • effort: "low"：這是抽取型任務，不需要深度推理，用低 effort 省 token 和時間。
  • fallbacks: "default"：模型因安全分類拒答時，由伺服器改用建議的備援模型處理。
  • 檢查 stop_reason：拒答（refusal）或輸出被截斷（max_tokens）時回傳 None，整則轉人工，不改用規則解析。 設了備援模型之後，最終仍是 refusal 代表整串模型都拒答了。
  • 只取最後一個 fallback 區塊之後的文字：模型在輸出途中被換成備援模型時，content 前面可能留著被拒答那一次的部分文字， 直接取第一個文字區塊會拿到不完整的 JSON。
  • LLM_LOG：記下 response.model（實際回應的模型，用了備援時會不同）和 token 用量，接到第 2.7 節的決策紀錄。 用了備援時，每一次嘗試的用量在 response.usage.iterations，頂層的 usage 只算最後成功的那一次。
warning

schema 每次不同時，第一次請求會多一段編譯時間（相同的 schema 會快取 24 小時）。 enum 依使用者動態產生，代表 schema 經常變動。量大時可以改成：schema 固定（欄位只限型別）， 詞彙放在 prompt 裡，再由 resolve() 把不在詞彙裡的值當成對不到。正確性一樣由程式保證。

模型的選擇

範例用的是目前預設的 Opus 等級模型，並把 effort 設成 low。這是抽取型任務，量大時可以用同一份評測集比較 Sonnet 或 Haiku 等級的模型 —— 用 GOLDEN 跑 precision／recall，沒有變差才換。換模型時注意各型號支援的參數不同 （例如較舊或較小的型號不支援 effort、備援模型參數只支援部分型號），以官方文件為準。 另外，fallbacks 參數不能用在 Batches API，批次評測時要拿掉。

8.5 這個範例省略了什麼​

  • 資料庫與交易：TASKS、ALIASES、DRAFTS、AUDIT_LOG 實務上都是表，update_task() 要在同一個交易裡寫入狀態和稽核紀錄，交易成功後才發通知。
  • 歧義處理：範例遇到歧義（沒指定主機卻對到多筆、同一筆結果矛盾）只會轉人工；實務上應該直接列出候選讓使用者勾選，例如開第 2.5 節說的勾選網頁。
  • 切段規則：split_segments() 只認換行、句號、分號，以及「逗號後面又提到主機」。口語回報的變化很多，規則解析一定有漏網之魚，靠評測集逐步補。
  • 附件：附截圖或 log 的回報要先存檔，確認時再掛到對應的任務上。
  • 聊天平台介面：範例的 render() 輸出純文字；實際上要做成卡片或網頁，按鈕帶 draft.id 和段落編號呼叫 confirm()。
  • 自動執行分級：範例全部都要確認，沒有實作依風險自動執行。
  • 別名學習的審核：learn_alias() 直接生效；實務上要達到一定次數或由人核准。

9. 檢查清單​

  • 候選範圍在交給模型之前就限縮到「這個人能動的資料」
  • 模型輸出的是提案（動作＋條件），不是直接寫資料庫
  • 動作和詞彙用 schema enum 限定，不只是「請回傳 JSON」
  • 條件展開成實際資料由程式處理，用精確比對，不用 LIKE
  • 提到但對不到的對象會被偵測出來，該段轉人工
  • 詞彙、別名從資料庫來，不寫死在程式裡；有後台可以維護
  • 每段分開處理，對不到的段落單獨轉人工
  • 狀態轉換走既有 service 和狀態機，不能往回改
  • 對話狀態、草稿存在資料庫，按鈕只帶 id
  • 每一步都有紀錄，包含模型和 prompt 版本
  • 有真實語料做的評測集，改 prompt 或換模型都會跑
  • 自動執行只開放給量測過、低風險、可撤銷的動作
