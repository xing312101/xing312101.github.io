語音功能測試：讓電腦「說話」給手機聽

點擊和輸入都能用指令送進手機，聲音不行 —— 實機的麥克風只收得到空氣中的聲音。 所以要測「按住說話」這類功能，得讓電腦（或另一支手機）真的發出聲音，同時在正確的時機按住麥克風鍵。

這件事 AI 可以全自動做完，但有一個根本限制要先記住：AI 聽不到聲音。 指令回傳成功不代表喇叭真的有聲音，第一次一定要請旁邊的人確認一次（見第 4.2 節）。

1. 把聲音送進麥克風的幾種方式​

方式適用優點缺點
電腦喇叭 → 手機麥克風實機最接近真實使用情境，測到的是完整的辨識流程受環境噪音影響；需要人確認音量與距離
另一支手機播放 → 手機麥克風實機電腦沒喇叭或喇叭被佔用時的替代要多操作一支手機
虛擬音訊裝置（例如 BlackHole）→ 模擬器Android 模擬器、iOS 模擬器完全不經過空氣，安靜、穩定、可放進 CI測不到實機麥克風與降噪的行為
App 的除錯入口直接塞文字任何環境最快，適合測「聽懂之後」的邏輯跳過了語音辨識本身，不能代替上面幾種
請人對著手機說實機零設定不能重複、不能自動化

1.1 模擬器的虛擬麥克風​

  • Android 模擬器：Extended controls → Microphone → 開啟「Virtual microphone uses host audio input」，模擬器就會收電腦的輸入裝置。
  • iOS 模擬器：直接使用 Mac 目前的輸入裝置。
  • 再裝一個虛擬音訊裝置（macOS 上常用開源的 BlackHole），把播放的輸出設到它、錄音的輸入也設到它， 電腦播放的語音就會直接流進模擬器的麥克風，不經過喇叭。

2. 產生語音檔​

先把要說的句子做成音檔，之後每次播同一個檔案，結果才能重現。

工具平台指令範例備註
saymacOS 內建say -v Meijia -o ask.aiff "幫我查一下我的包裹"可用的聲音：say -v '?' | grep zh_TW（繁中有好幾個）
PiperLinux／macOS，離線echo "幫我查一下我的包裹" | piper -m zh_CN-xxx.onnx -f ask.wav神經網路語音，自然度好，有中文模型
espeak-ngLinux，離線espeak-ng -v cmn -w ask.wav "幫我查一下我的包裹"很機械，但辨識引擎通常聽得懂
雲端 TTS任何平台Google Cloud Text-to-Speech、Azure Speech、Amazon Polly、OpenAI TTS最自然、可選台灣腔；需要 API 金鑰

macOS 的 aiff 想轉成 wav 或 m4a：

afconvert -f WAVE -d LEI16@16000 ask.aiff ask.wav       # 16 kHz 單聲道，語音辨識最常用的格式
準備幾種說法

同一個意思準備幾個版本：不同的說法（「查包裹」「我有包裹嗎」）、不同語速、 需要的話加上台語或英文。語音助理最常壞在「換個說法就聽不懂」。

非官方的 TTS 網址

網路上流傳一些翻譯服務的朗讀網址可以直接下載語音檔。那不是公開的 API， 隨時可能失效、也可能違反服務條款 —— 臨時手動測試可以，不要寫進 CI 或交付的工具裡。

3. 播放與音量​

平台播放備註
macOSafplay -v 1 ask.wav-v 是這次播放的音量（0～1），不影響系統音量
Linux（PulseAudio／PipeWire）paplay ask.wav
Linux（ALSA）aplay ask.wav
任何平台ffplay -nodisp -autoexit ask.wav需要 ffmpeg

需要調整 macOS 系統音量時，先記下原本的值，用完還原（這會影響整台電腦）：

V=$(osascript -e 'output volume of (get volume settings)')
osascript -e 'set volume output volume 80'
afplay -v 1 ask.wav
osascript -e "set volume output volume $V"

3.1 用手機來播​

電腦不方便發聲時，讓另一支手機播放同一個音檔。最通用的做法是在電腦上開一個臨時的網頁伺服器，讓手機的瀏覽器打開音檔：

cd 放音檔的資料夾 && python3 -m http.server 8000 &

# Android：用 adb reverse 把手機的 localhost:8000 轉到電腦，不用管 IP 與防火牆
adb reverse tcp:8000 tcp:8000
adb shell am start -a android.intent.action.VIEW -d 'http://localhost:8000/ask.mp3'

iPhone 用 WebDriverAgent 的 POST /session/ID/url 打開 http://電腦的區網IP:8000/ask.mp3（手機和電腦要在同一個網路，見 iOS 篇第 4 節）。

note

不要用 file:///sdcard/... 讓播放器直接開手機上的檔案 —— 新版 Android 的儲存空間權限常常讓播放器讀不到，而且錯誤不會顯示在 adb 這邊。

4. 陷阱：指令成功了，但沒有聲音​

4.1 常見原因​

原因怎麼查處理
AI 的執行環境是沙盒，程序拿不到桌面的音訊say 回傳 0 卻沒聲音，afplay 播系統音效卻有聲音改成「先產生檔案、再用 afplay 播」；或把播放這一步放到沙盒外執行
輸出裝置不是喇叭（藍牙耳機、外接螢幕、虛擬音訊裝置）macOS：system_profiler SPAudioDataType 找 Default Output Device: Yes切回內建喇叭；say -a '?' 可以列出裝置、用 -a 指定
靜音或音量太小osascript -e 'get volume settings'見第 3 節
聲音有出來，但手機沒收到手機上的「聆聽中」有出現，辨識結果卻是空的縮短距離（10～30 公分）、提高音量、換成更清楚的語音

say 在某些 agent 沙盒裡會「成功地」什麼都不播，afplay 卻正常 —— 兩者走的系統服務不同。 最保險的組合是「say -o 產生檔案 → afplay 播放」，或乾脆用其他 TTS 產生的音檔。

4.2 第一次一定要請人確認​

AI 沒辦法聽，所以第一次設定時：

  1. 先播一個短的系統音效：afplay /System/Library/Sounds/Glass.aiff
  2. 問旁邊的人：「剛剛有聽到『叮』一聲嗎？」
  3. 有聽到，再播語音檔確認一次；沒聽到就照 4.1 的表排查。

確認過一次之後，後面就能全自動跑。

4.3 讓 AI 自己「聽」：用電腦的麥克風錄一段​

沒有人在旁邊時，可以讓電腦一邊播放、一邊用自己的麥克風錄音，再看錄到的音量，間接確認喇叭有出聲：

(sleep 0.5; afplay /System/Library/Sounds/Glass.aiff) &
ffmpeg -hide_banner -f avfoundation -i ':0' -t 2 -y check.wav 2>/dev/null     # macOS；Linux 改 -f pulse -i default
ffmpeg -i check.wav -af volumedetect -f null - 2>&1 | grep max_volume
# max_volume: -6.2 dB     → 有聲音
# max_volume: -60 dB 以下 → 幾乎是靜音

這需要終端機有麥克風權限（macOS 第一次會跳出詢問，要人按允許），而且在部分 AI 沙盒裡一樣會被擋。 它只能證明「有聲音」，不能證明手機聽得清楚 —— 那要看第 6 節。

5. 時機：按住說話​

「按住說話」要在按住期間把聲音播完。做法是：開始按住 → 等一下 → 開始播放 → 播完之後再放開。 播放放在背景執行，按住放在前景，兩者同時進行：

# Android：同一個座標「滑動」6 秒就是按住 6 秒
(sleep 1.5; afplay -v 1 ask.wav) & adb shell input swipe 540 2077 540 2077 6000; wait
# iOS（WebDriverAgent）：pointerDown → pause → pointerUp
actions = [{'type': 'pointer', 'id': 'f', 'parameters': {'pointerType': 'touch'}, 'actions': [
    {'type': 'pointerMove', 'duration': 0, 'x': 195, 'y': 780},
    {'type': 'pointerDown', 'button': 0},
    {'type': 'pause', 'duration': 6000},
    {'type': 'pointerUp', 'button': 0}]}]
# 送出前先在背景啟動：subprocess.Popen('sleep 1.5; afplay -v 1 ask.wav', shell=True)
參數建議
開始播放前等多久1～1.5 秒，讓 App 進入「聆聽中」狀態（太早播，開頭幾個字會被吃掉）
按住多久音檔長度 ＋ 2～3 秒
不是按住、而是「點一下開始、自動偵測結束」的點擊後等 1 秒再播放；播完後保持安靜，讓 App 自己判斷說完了

6. 確認手機真的聽懂了​

不要只看「沒有錯誤」。依序檢查：

  1. 聆聽中的畫面有出現 —— 播放期間截一張圖。

  2. 辨識出來的文字 —— 大多數語音助理會把聽到的句子顯示出來。Android 直接讀 UI 樹最準：

    adb shell uiautomator dump /sdcard/ui.xml >/dev/null
    adb shell cat /sdcard/ui.xml | grep -o 'text="[^"]*包裹[^"]*"'

  3. 回應與後續動作 —— 回答的內容、有沒有跳到對應的頁面。

回應通常要等雲端處理好幾秒，而「思考中」這類中間狀態一閃即逝。 放開按鈕後連續截幾張（例如每 3 秒一張、共 5 張），再拼成一張縮圖一起看，比猜要等多久可靠。

結果代表
「聆聽中」有出現，但對話紀錄是空的手機沒收到聲音 → 見第 4 節
有文字但不是你說的音質或語速問題 → 換語音、放慢、靠近一點
文字正確但回應錯了這才是 App 本身的問題，值得回報

7. 收尾​

  • 系統音量還原成原本的值。
  • 測試期間開著的播放器、瀏覽器分頁關掉。
  • 如果是在有人的辦公室裡，播放前先講一聲 —— 突然冒出的電腦語音很嚇人。
