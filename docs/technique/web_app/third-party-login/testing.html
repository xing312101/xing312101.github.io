第三方登入怎麼寫測試

「登入靠外部服務，所以沒辦法測」是很常見的誤解。 實際上這套功能有九成是可以在 CI 上全自動測的，而且它剛好是最值得測的那種程式碼： 平常一直走成功路徑、錯誤路徑上線一年可能都沒被執行過、出錯的後果是帳號被接管。

先讀：帳號串接（第 4 節的測試對象）與 Google 篇（第 3、5、6 節的測試對象）。 這一篇的範例都拿 Google 篇的程式碼當測試對象；LINE 與 Apple 的寫法相同，換掉 issuer 與 JWKS 網址即可。

1. 先分清楚：哪些測得到、哪些測不到​

部分測得到嗎怎麼測
state／nonce／PKCE 的產生與比對✅單元測試
ID token 的驗證（簽章、iss、aud、exp、nonce）✅自己簽測試 token，見第 3 節
帳號串接的四種情況（回訪、綁定、撞號、新註冊）✅ 最重要單元／整合測試，見第 4 節
callback 端點的完整行為✅整合測試 + 假 IdP，見第 5 節
錯誤路徑（使用者取消、state 不符、token 兌換失敗）✅整合測試，見第 6 節
Apple 的 client_secret 簽出來對不對✅單元測試：用測試用的 EC 金鑰簽、自己驗回來
Apple 的 form_post + SameSite 行為⚠️ 部分可以測「callback 收 POST」，但跨站 cookie 的實際行為只有真瀏覽器測得出來
供應商的登入頁本身❌有 CAPTCHA、二階段驗證、機器人偵測。不要在 CI 上自動化真的 Google 登入
Console 的設定有沒有填對❌這是設定，不是程式。只能靠部署前的人工檢查清單

不要在 CI 上用真的 Google／LINE／Apple 帳號跑登入。 會發生的事： 帳號被判定為異常活動而鎖定、遇到 CAPTCHA 而卡住、供應商改版導致選擇器失效、 以及最糟的 —— 正式環境的憑證要放進 CI。 需要「真的走一次」的驗證，用人工的部署前檢查處理。

2. 前提：端點與設定必須可注入​

這一整篇的技巧都建立在一件事上：你的程式不能把供應商的網址寫死成常數。

❌ const ISSUER = "https://accounts.google.com"   // 測試時沒辦法換掉
✅ 從設定／環境變數讀，測試時指向本機的假 IdP

這不是為了測試而扭曲設計 —— 正式環境本來就會有「測試站用不同的 client_id」這種需求， 把它做成設定是本來就該做的事。

3. 核心手法：自己當 IdP​

驗證 ID token 需要「一段被正確簽名的 JWT」。做法是測試時自己產一對金鑰， 自己簽 token，並把 JWKS 端點指向本機。

  • Go
  • Ruby on Rails
  • Python

Go 的 httptest 讓這件事特別乾淨 —— 起一個真的 HTTP server， 連 discovery document 都一起提供，go-oidc 就能像對真的 Google 一樣運作。 （這一篇的 Go 範例用到 t.Context()，需要 Go 1.24 以上；go-oidc 的新版本本身也要求較新的 Go，以它的 go.mod 為準。）

internal/authtest/fakeidp.go
package authtest

import (
	"crypto/rand"
	"crypto/rsa"
	"encoding/base64"
	"encoding/json"
	"math/big"
	"net/http"
	"net/http/httptest"
	"testing"
	"time"

	"github.com/golang-jwt/jwt/v5"
)

const testKID = "test-key-1"

type FakeIdP struct {
	*httptest.Server
	Issuer   string
	key      *rsa.PrivateKey
	TokenRes func() (int, string) // 讓測試可以模擬 token 端點失敗
}

func NewFakeIdP(t *testing.T) *FakeIdP {
	t.Helper()

	key, err := rsa.GenerateKey(rand.Reader, 2048)
	if err != nil {
		t.Fatalf("產生測試金鑰失敗：%v", err)
	}
	f := &FakeIdP{key: key}

	mux := http.NewServeMux()
	// discovery document：go-oidc 會先讀這一份
	mux.HandleFunc("/.well-known/openid-configuration",
		func(w http.ResponseWriter, _ *http.Request) {
			w.Header().Set("Content-Type", "application/json")
			_ = json.NewEncoder(w).Encode(map[string]any{
				"issuer":                                f.Issuer,
				"authorization_endpoint":                f.Issuer + "/authorize",
				"token_endpoint":                        f.Issuer + "/token",
				"jwks_uri":                              f.Issuer + "/keys",
				"id_token_signing_alg_values_supported": []string{"RS256"},
			})
		})

	mux.HandleFunc("/keys", func(w http.ResponseWriter, _ *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		_ = json.NewEncoder(w).Encode(map[string]any{"keys": []map[string]string{{
			"kty": "RSA", "use": "sig", "alg": "RS256", "kid": testKID,
			"n": base64.RawURLEncoding.EncodeToString(key.N.Bytes()),
			"e": base64.RawURLEncoding.EncodeToString(
				big.NewInt(int64(key.E)).Bytes()),
		}}})
	})

	mux.HandleFunc("/token", func(w http.ResponseWriter, r *http.Request) {
		status, body := 200, ""
		if f.TokenRes != nil {
			status, body = f.TokenRes()
		}
		w.Header().Set("Content-Type", "application/json")
		w.WriteHeader(status)
		_, _ = w.Write([]byte(body))
	})

	// 先啟動才知道 URL；handler 是在請求時才讀 f.Issuer，所以順序沒問題
	f.Server = httptest.NewServer(mux)
	f.Issuer = f.Server.URL
	t.Cleanup(f.Server.Close)
	return f
}

// Claims 是可以逐項覆寫的預設值，負面測試就靠它產出各種壞掉的 token
type Claims struct {
	Issuer   string
	Audience string
	Subject  string
	Nonce    string
	Email    string
	Expires  time.Time
	Alg      jwt.SigningMethod
	KID      string
}

func (f *FakeIdP) SignIDToken(t *testing.T, c Claims) string {
	t.Helper()

	if c.Issuer == "" {
		c.Issuer = f.Issuer
	}
	if c.Expires.IsZero() {
		c.Expires = time.Now().Add(time.Hour)
	}
	if c.Alg == nil {
		c.Alg = jwt.SigningMethodRS256
	}
	if c.KID == "" {
		c.KID = testKID
	}

	tok := jwt.NewWithClaims(c.Alg, jwt.MapClaims{
		"iss": c.Issuer, "aud": c.Audience, "sub": c.Subject,
		"nonce": c.Nonce, "email": c.Email, "email_verified": true,
		"iat": time.Now().Unix(), "exp": c.Expires.Unix(),
	})
	tok.Header["kid"] = c.KID

	s, err := tok.SignedString(f.key)
	if err != nil {
		t.Fatalf("簽測試 token 失敗：%v", err)
	}
	return s
}

Rails 這邊用 WebMock 把 JWKS 與 token 端點攔下來。

spec/support/fake_idp.rb
# spec/rails_helper.rb 裡要有：require "webmock/rspec"

module FakeIdP
  TEST_KID = "test-key-1".freeze

  def self.rsa_key
    # 2048 bit 的金鑰產生要花幾百毫秒，整個測試套件共用一把就好
    @rsa_key ||= OpenSSL::PKey::RSA.generate(2048)
  end

  def self.jwk
    @jwk ||= JWT::JWK.new(rsa_key, kid: TEST_KID)
  end

  def self.stub_jwks!(url)
    WebMock.stub_request(:get, url).to_return(
      status: 200,
      body: { keys: [jwk.export] }.to_json,
      headers: { "Content-Type" => "application/json" },
    )
  end

  def self.stub_token!(url, id_token:, status: 200)
    WebMock.stub_request(:post, url).to_return(
      status: status,
      body: { access_token: "at", id_token: id_token,
              token_type: "Bearer", expires_in: 3600 }.to_json,
      headers: { "Content-Type" => "application/json" },
    )
  end

  # 可以逐項覆寫的預設值，負面測試就靠它產出各種壞掉的 token
  def self.id_token(aud:, sub: "1234567890", nonce: nil,
                    iss: "https://accounts.google.com",
                    exp: 1.hour.from_now, alg: "RS256",
                    key: rsa_key, kid: TEST_KID, **extra)
    payload = {
      iss: iss, aud: aud, sub: sub, nonce: nonce,
      email: "alice@example.com", email_verified: true,
      iat: Time.now.to_i, exp: exp.to_i,
    }.merge(extra).compact

    JWT.encode(payload, key, alg, { kid: kid })
  end
end

記得在每個測試之間清掉 JWKS 快取。 三篇的 initializer 都用 @cached_jwks ||= 做快取， 它會跨測試殘留 —— 第二個測試就算 stub 了不同的 JWKS 也讀不到， 症狀是「單獨跑會過、整批跑會紅」。

# spec/rails_helper.rb
config.before do
  [GoogleOIDC, LineOIDC, AppleOIDC].each do |mod|
    mod.instance_variable_set(:@cached_jwks, nil)
    mod.instance_variable_set(:@jwks_fetched_at, nil)
  end
end

Python 這邊用 respx 攔 httpx 的 token 請求， JWKS 則因為 PyJWKClient 走的是 urllib，直接把 client 換掉最乾淨。

tests/conftest.py
import time

import pytest
from cryptography.hazmat.primitives.asymmetric import rsa
import jwt

TEST_KID = "test-key-1"


@pytest.fixture(scope="session")
def rsa_key():
    # 產生 2048 bit 金鑰要花幾百毫秒，整個測試套件共用一把
    return rsa.generate_private_key(public_exponent=65537, key_size=2048)


@pytest.fixture
def make_id_token(rsa_key):
    """可以逐項覆寫的預設值，負面測試就靠它產出各種壞掉的 token。"""
    def _make(
        aud: str,
        sub: str = "1234567890",
        nonce: str | None = None,
        iss: str = "https://accounts.google.com",
        exp: int | None = None,
        alg: str = "RS256",
        key=None,
        kid: str = TEST_KID,
        **extra,
    ) -> str:
        now = int(time.time())
        payload = {
            "iss": iss, "aud": aud, "sub": sub, "nonce": nonce,
            "email": "alice@example.com", "email_verified": True,
            "iat": now, "exp": exp if exp is not None else now + 3600,
            **extra,
        }
        return jwt.encode(
            {k: v for k, v in payload.items() if v is not None},
            key or rsa_key, algorithm=alg, headers={"kid": kid},
        )
    return _make


@pytest.fixture(autouse=True)
def stub_jwks(monkeypatch, rsa_key):
    """把 PyJWKClient 換掉，讓驗證用測試金鑰的公鑰。
    autouse=True 確保沒有任何測試會不小心打到真的 JWKS 端點。"""
    from app import auth_google

    class _StubKey:
        key = rsa_key.public_key()

    monkeypatch.setattr(
        auth_google.jwk_client, "get_signing_key_from_jwt",
        lambda token: _StubKey(),
    )

4. 最值得測的是帳號串接邏輯​

如果時間只夠寫一種測試，寫這個。 帳號串接的四種情況全部是純函式邏輯， 不需要任何 HTTP，跑得又快。

  • Go
  • Ruby on Rails
  • Python
internal/accounts/signin_test.go
package accounts

import (
	"context"
	"errors"
	"sync"
	"testing"
)

// newTestDB、countUsers、countIdentities 是測試用的小工具：
// 開一個乾淨的測試資料庫（套用與正式相同的 migration，唯一索引才會在）、數資料列。

func TestSignIn(t *testing.T) {
	google := func(sub string) ProfileFromProvider {
		return ProfileFromProvider{
			Provider: "google", ProviderUserID: sub,
			Email: "alice@example.com", EmailVerified: true,
		}
	}

	t.Run("第一次登入會建立新使用者", func(t *testing.T) {
		db := newTestDB(t)
		u, err := SignIn(t.Context(), db, google("g-1"), 0)
		if err != nil {
			t.Fatalf("預期成功，卻得到 %v", err)
		}
		if u.ID == 0 {
			t.Fatal("沒有建立使用者")
		}
	})

	t.Run("同一個 sub 再登入會拿到同一個使用者", func(t *testing.T) {
		db := newTestDB(t)
		first, _ := SignIn(t.Context(), db, google("g-1"), 0)
		second, err := SignIn(t.Context(), db, google("g-1"), 0)
		if err != nil {
			t.Fatalf("預期成功，卻得到 %v", err)
		}
		if first.ID != second.ID {
			t.Fatalf("同一個人變成兩個帳號：%d vs %d", first.ID, second.ID)
		}
		if n := countUsers(t, db); n != 1 {
			t.Fatalf("預期 1 個使用者，實際 %d 個", n)
		}
	})

	t.Run("已登入時綁定第二個供應商，仍是同一個使用者", func(t *testing.T) {
		db := newTestDB(t)
		u, _ := SignIn(t.Context(), db, google("g-1"), 0)

		line := ProfileFromProvider{Provider: "line", ProviderUserID: "U-1"}
		same, err := SignIn(t.Context(), db, line, u.ID)
		if err != nil {
			t.Fatalf("預期成功，卻得到 %v", err)
		}
		if same.ID != u.ID {
			t.Fatal("綁定後變成另一個使用者")
		}
		if n := countIdentities(t, db, u.ID); n != 2 {
			t.Fatalf("預期 2 個身分，實際 %d 個", n)
		}
	})

	t.Run("別人的 Google 帳號不能綁到我身上", func(t *testing.T) {
		db := newTestDB(t)
		alice, _ := SignIn(t.Context(), db, google("g-1"), 0)
		bob, _ := SignIn(t.Context(), db, ProfileFromProvider{
			Provider: "line", ProviderUserID: "U-bob",
		}, 0)

		// bob 想把 alice 已經綁定的 Google 帳號綁到自己身上
		_, err := SignIn(t.Context(), db, google("g-1"), bob.ID)
		if !errors.Is(err, ErrIdentityTaken) {
			t.Fatalf("預期 ErrIdentityTaken，實際 %v", err)
		}
		_ = alice
	})

	t.Run("未驗證的 email 不會自動合併到既有帳號", func(t *testing.T) {
		db := newTestDB(t)
		_, _ = SignIn(t.Context(), db, google("g-1"), 0) // alice@example.com

		unverified := ProfileFromProvider{
			Provider: "apple", ProviderUserID: "a-1",
			Email: "alice@example.com", EmailVerified: false,
		}
		u, err := SignIn(t.Context(), db, unverified, 0)
		if err != nil {
			t.Fatalf("預期建立新帳號，卻得到 %v", err)
		}
		if n := countUsers(t, db); n != 2 {
			t.Fatalf("未驗證的 email 被合併了：使用者數 %d", n)
		}
		_ = u
	})

	t.Run("Apple 轉寄信箱不會被當成可比對的 email", func(t *testing.T) {
		db := newTestDB(t)
		relay := ProfileFromProvider{
			Provider: "apple", ProviderUserID: "a-2",
			Email:         "abc123@privaterelay.appleid.com",
			EmailVerified: true, EmailIsRelay: true,
		}
		u, err := SignIn(t.Context(), db, relay, 0)
		if err != nil {
			t.Fatalf("預期成功，卻得到 %v", err)
		}
		if u.Email != nil {
			t.Fatalf("轉寄信箱不該寫進 users.email，實際是 %q", *u.Email)
		}
	})
}

// 並行登入只能建立一個使用者 —— 這一條在沒有唯一索引時會紅
func TestSignInConcurrent(t *testing.T) {
	db := newTestDB(t)
	p := ProfileFromProvider{Provider: "google", ProviderUserID: "g-race"}

	var wg sync.WaitGroup
	for range 10 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			_, _ = SignIn(context.Background(), db, p, 0)
		}()
	}
	wg.Wait()

	if n := countUsers(t, db); n != 1 {
		t.Fatalf("並行登入建立了 %d 個使用者，唯一索引沒有生效", n)
	}
}

RSpec.describe Identity, type: :model do
  def google_profile(sub, **overrides)
    {
      provider: "google", provider_user_id: sub,
      email: "alice@example.com", email_verified: true,
      email_is_relay: false, display_name: "Alice",
    }.merge(overrides)
  end

  it "第一次登入會建立新使用者" do
    expect { described_class.sign_in!(google_profile("g-1")) }
      .to change(User, :count).by(1)
      .and change(described_class, :count).by(1)
  end

  it "同一個 sub 再登入會拿到同一個使用者" do
    first  = described_class.sign_in!(google_profile("g-1"))
    second = described_class.sign_in!(google_profile("g-1"))

    expect(second.id).to eq(first.id)
    expect(User.count).to eq(1)
  end

  it "已登入時綁定第二個供應商，仍是同一個使用者" do
    user = described_class.sign_in!(google_profile("g-1"))

    same = described_class.sign_in!(
      { provider: "line", provider_user_id: "U-1", email: nil,
        email_verified: false, email_is_relay: false },
      current_user: user,
    )

    expect(same.id).to eq(user.id)
    expect(user.identities.count).to eq(2)
  end

  it "別人的 Google 帳號不能綁到我身上" do
    described_class.sign_in!(google_profile("g-1"))         # alice
    bob = described_class.sign_in!(
      { provider: "line", provider_user_id: "U-bob", email: nil,
        email_verified: false, email_is_relay: false },
    )

    expect { described_class.sign_in!(google_profile("g-1"), current_user: bob) }
      .to raise_error(described_class::IdentityTaken)
  end

  it "未驗證的 email 不會自動合併到既有帳號" do
    described_class.sign_in!(google_profile("g-1"))

    expect {
      described_class.sign_in!(
        google_profile("a-1", provider: "apple", email_verified: false),
      )
    }.to change(User, :count).by(1)
  end

  it "Apple 轉寄信箱不會寫進 users.email" do
    user = described_class.sign_in!(
      google_profile("a-2", provider: "apple",
                     email: "abc123@privaterelay.appleid.com",
                     email_is_relay: true),
    )
    expect(user.email).to be_nil
  end

  it "不能解除最後一個登入方式" do
    user = described_class.sign_in!(google_profile("g-1"))

    expect { user.identities.sole.unlink! }
      .to raise_error(described_class::LastIdentity)
    expect(described_class.count).to eq(1)   # 身分沒有被刪掉
  end
end

5. callback 的整合測試​

import (
	"fmt"

	"net/http/httptest"
	"net/url"
	"testing"

	"example.com/app/internal/authtest"
)

// newTestApp 組出一個掛好路由的測試用 app（實作 http.Handler，並帶著測試資料庫 DB），
// 其中 issuer 換成假 IdP 的網址 —— 這就是第 2 節說的「端點要可注入」。

func TestCallback(t *testing.T) {
	idp := authtest.NewFakeIdP(t)
	app := newTestApp(t, idp.Issuer) // 把 issuer 指向假 IdP

	// ① 先打 /auth/google，拿到導向 URL 裡的 state 與 nonce
	rec := httptest.NewRecorder()
	app.ServeHTTP(rec, httptest.NewRequest("GET", "/auth/google", nil))
	if rec.Code != http.StatusFound {
		t.Fatalf("預期 302，實際 %d", rec.Code)
	}
	loc, _ := url.Parse(rec.Header().Get("Location"))
	state := loc.Query().Get("state")
	nonce := loc.Query().Get("nonce")
	cookies := rec.Result().Cookies()

	// ② 假 IdP 的 token 端點回一段用正確 nonce 簽的 id_token
	idToken := idp.SignIDToken(t, authtest.Claims{
		Audience: testClientID, Subject: "g-1", Nonce: nonce,
		Email: "alice@example.com",
	})
	idp.TokenRes = func() (int, string) {
		return 200, fmt.Sprintf(`{"access_token":"at","token_type":"Bearer",
			"expires_in":3600,"id_token":%q}`, idToken)
	}

	// ③ 帶著 cookie 打 callback
	req := httptest.NewRequest("GET", "/auth/google/callback?code=c&state="+state, nil)
	for _, c := range cookies {
		req.AddCookie(c)
	}
	rec2 := httptest.NewRecorder()
	app.ServeHTTP(rec2, req)

	if rec2.Code != http.StatusSeeOther {
		t.Fatalf("預期 303，實際 %d（body: %s）", rec2.Code, rec2.Body)
	}
	if got := countUsers(t, app.DB); got != 1 {
		t.Fatalf("預期建立 1 個使用者，實際 %d 個", got)
	}
}

func TestVerifyIDToken_負面案例(t *testing.T) {
	idp := authtest.NewFakeIdP(t)
	v := newVerifier(t, idp.Issuer)

	valid := authtest.Claims{Audience: testClientID, Subject: "g-1", Nonce: "n1"}

	cases := map[string]func(c authtest.Claims) authtest.Claims{
		"aud 是別人的":   func(c authtest.Claims) authtest.Claims { c.Audience = "other-client"; return c },
		"iss 是別人的":   func(c authtest.Claims) authtest.Claims { c.Issuer = "https://evil.example"; return c },
		"已經過期":       func(c authtest.Claims) authtest.Claims { c.Expires = time.Now().Add(-time.Hour); return c },
		"kid 不存在":    func(c authtest.Claims) authtest.Claims { c.KID = "unknown-kid"; return c },
	}

	for name, mutate := range cases {
		t.Run(name, func(t *testing.T) {
			raw := idp.SignIDToken(t, mutate(valid))
			if _, err := v.Verify(t.Context(), raw); err == nil {
				t.Fatal("預期驗證失敗，卻通過了")
			}
		})
	}

	t.Run("簽章被竄改", func(t *testing.T) {
		raw := idp.SignIDToken(t, valid)
		if _, err := v.Verify(t.Context(), raw[:len(raw)-4]+"AAAA"); err == nil {
			t.Fatal("預期驗證失敗，卻通過了")
		}
	})

	t.Run("alg 為 none", func(t *testing.T) {
		unsigned := jwt.NewWithClaims(jwt.SigningMethodNone, jwt.MapClaims{
			"iss": idp.Issuer, "aud": testClientID, "sub": "g-1", "nonce": "n1",
			"exp": time.Now().Add(time.Hour).Unix(),
		})
		raw, _ := unsigned.SignedString(jwt.UnsafeAllowNoneSignatureType)
		if _, err := v.Verify(t.Context(), raw); err == nil {
			t.Fatal("接受了沒有簽章的 token")
		}
	})
}

def test_拒絕拿公鑰當_hmac_密鑰簽的_token(rsa_key):
    """alg confusion：攻擊者拿公開的 RSA 公鑰當 HS256 的密鑰。

    PyJWT 2.x 在「簽」的時候就會拒絕拿 PEM 公鑰當 HMAC 密鑰（丟 InvalidKeyError），
    所以不能用 jwt.encode 產生這張 token —— 那樣測試會在建構階段就出錯，
    根本沒測到驗證函式。這裡照攻擊者的做法手動組出來。
    """
    import base64
    import hashlib
    import hmac
    import json

    from cryptography.hazmat.primitives import serialization

    def b64url(data: bytes) -> str:
        return base64.urlsafe_b64encode(data).rstrip(b"=").decode()

    public_pem = rsa_key.public_key().public_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PublicFormat.SubjectPublicKeyInfo,
    )
    header = {"alg": "HS256", "typ": "JWT", "kid": "test-key-1"}
    payload = {"iss": "https://accounts.google.com", "aud": CLIENT_ID, "sub": "g-1",
               "nonce": NONCE, "exp": int(time.time()) + 3600}
    signing_input = (b64url(json.dumps(header).encode()) + "."
                     + b64url(json.dumps(payload).encode()))
    signature = hmac.new(public_pem, signing_input.encode(), hashlib.sha256).digest()
    token = f"{signing_input}.{b64url(signature)}"

    with pytest.raises(jwt.PyJWTError):
        verify_id_token(token, NONCE)


def test_拒絕_nonce_不符的_token(make_id_token):
    token = make_id_token(aud=CLIENT_ID, nonce="another-nonce")
    with pytest.raises(jwt.InvalidTokenError, match="nonce"):
        verify_id_token(token, NONCE)
warning

寫完負面測試，要確認它真的會紅。

做法：把對應的防護拿掉（例如刪掉 audience 參數、刪掉比對 nonce 那一行）， 跑測試，確認它失敗，然後改回來。

永遠會過的測試比沒有測試更糟，因為它讓所有人以為那件事有被守著。 這件事在登入的程式碼上特別容易發生 —— 例如一條測試斷言「aud 錯了會被拒絕」， 但你的驗證函式其實在更早的地方就因為別的原因丟出例外， 測試一樣是綠的，而 aud 根本沒被檢查。

6.1 先證明基準那張會過，再斷言是被什麼擋下​

上面那個「因為別的原因被擋」，最常見的來源是基準那張 token 本身就是壞的。 每一條負面測試都是「拿一張正確的 token，只改一個地方」—— 如果那張「正確的」其實不正確， 所有負面測試都會被同一個原因擋下，全部綠燈，實際上只測到那一件事。

一個真實的例子：測 callback 的整合測試時，在呼叫 /auth/start 之前就把測試用的 ID token 簽好了。 但 nonce 是 /start 當下才產生的，簽 token 的時候還不知道 —— 於是每一張 token 的 nonce 都對不上。 「aud 錯」「iss 錯」「已過期」「簽章壞掉」七條測試全部被「nonce 不符」擋下，全部綠燈。 要到把 aud 檢查拿掉、測試還是綠的，才發現。

兩個做法，都要做：

  1. 基準 token 要有一條自己的正面測試，而且用跟負面測試完全相同的方式產生 （同一個 helper、同一個時間點 —— 例如都在拿到這次流程的 nonce 之後才簽）。 它失敗的時候，所有負面測試的結果都不能信
  2. 斷言拒絕的原因，不只斷言「被拒絕」。 用函式庫給的具體例外型別，或你自己的錯誤碼：

tip

寫錯誤原因的斷言時，先確認你比對的就是程式實際丟出來的那個東西。 例如 Google 篇的 verify_id_token 在 nonce 不符時丟的是 jwt.InvalidTokenError —— 它正是 InvalidAudienceError、InvalidIssuerError、ExpiredSignatureError 的父類別。 所以「aud 錯」那條測試如果寫成 pytest.raises(jwt.InvalidTokenError)，被 nonce 擋下也照樣綠； 要斷言 nonce 本身，就像第 6 節那樣再加 match="nonce"。

Dex真的 OIDC 實作，可以設定靜態帳密（staticPasswords），也有給測試用的 mock 連接器
Keycloak最完整，但啟動慢、設定多
docker-compose.test.yml
services:
  idp:
    # 固定一個版本，不要用 latest；大版本之間有不相容的變更，升級前先看 release notes
    image: ghcr.io/navikt/mock-oauth2-server:6.0.3
    ports: ["8080:8080"]
    environment:
      # interactiveLogin 在容器模式下預設是 true（會出現一個填表的登入頁），
      # 關掉之後，假 IdP 直接發一個固定身分的 token
      JSON_CONFIG: >
        {"interactiveLogin": false,
         "tokenCallbacks": [{"issuerId": "default",
           "tokenExpiry": 3600,
           "requestMappings": [{"requestParam": "code", "match": "*",
             "claims": {"sub": "e2e-user-1", "email": "e2e@example.com",
                        "email_verified": true}}]}]}
warning

requestMappings 比對的是 token 請求（POST /token）的 body，不是授權請求。 授權碼流程裡 scope 只出現在授權請求，換 token 時不會再送 —— 所以網路上常見的 {"requestParam": "scope", "match": "openid"} 在這個流程裡永遠不會命中， 假 IdP 會安靜地改發預設的 claims，而你的測試拿到的是一個不是你設定的身分。 另外 match 是整串比對（或整串的正規表示式），"openid" 不會命中 "openid email profile"。 授權碼流程要比對就用一定會出現的參數，例如上面的 code 配 "*"。

然後在測試環境把 issuer 指向 http://localhost:8080/default （授權請求裡帶的 nonce 會被照抄進它發的 ID token，所以 nonce 的比對也能一起測到）。 你的程式碼完全不用改 —— 這就是第 2 節「端點要可注入」的回報。

warning

「測試用的登入後門」要非常小心。 有些團隊會加一個 /test-only/login?user_id=1 端點讓 E2E 跳過整個流程。這樣做跑得快，但代價是：

  • 那個端點必須在正式環境完全不存在，不是「用 if 擋住」—— 用建置標籤／環境判斷 在編譯或載入階段就排除掉。
  • 你的 E2E 從此沒有測到登入流程本身。

折衷做法：大部分的 E2E 用後門快速登入，但保留至少一條走完整假 IdP 流程的測試。

8. 在 CI 上跑​

8.1 憑證怎麼處理​

東西CI 上要放嗎
真的 client_id / client_secret不要。測試用假值就好，反正沒有真的對外連線
真的 Apple .p8不要。測試自己產一把 EC 金鑰來簽、自己驗回來
session 加密金鑰用固定的測試值，方便重現
CI 上的環境變數（全部是假的）
GOOGLE_CLIENT_ID=test-client-id
GOOGLE_CLIENT_SECRET=test-client-secret
GOOGLE_REDIRECT_URI=http://localhost:3000/auth/google/callback
LINE_CHANNEL_ID=1234567890
LINE_CHANNEL_SECRET=test-channel-secret
LINE_REDIRECT_URI=http://localhost:3000/auth/line/callback
APPLE_TEAM_ID=TESTTEAM01
APPLE_KEY_ID=TESTKEY001
APPLE_SERVICES_ID=com.example.test.web
APPLE_REDIRECT_URI=https://app.example.com/auth/apple/callback
# APPLE_PRIVATE_KEY：在 CI 上當場產生一把測試金鑰，見下方
# APPLE_BUNDLE_ID=com.example.test   選用：後端也要收 iOS App 的 ID token 時才設（Apple 篇第 10 節）
SESSION_SECRET=test-session-secret-do-not-use-in-production
# FRONTEND_BASE_URL=http://localhost:5173   選用：用了後端驗證 5.3 的一次性交換碼才需要

這份清單要跟程式實際讀的變數一致。 範例的 Rails（ENV.fetch）與 Python（os.environ[...]） 在載入模組時就讀這些值，少一個整個測試套件會在收集階段就失敗，看起來像環境壞了而不是少設定。 新增一個環境變數時，記得同一個 commit 裡把這份清單也補上。

APPLE_PRIVATE_KEY 不能隨便填一個字串 —— 程式要把它當成 .p8（PKCS#8 格式的 P-256 私鑰）解析。 在 CI 上當場產生一把就好，格式與 .p8 相同：

openssl ecparam -name prime256v1 -genkey -noout | openssl pkcs8 -topk8 -nocrypt

真正的憑證只出現在部署階段的密鑰儲存，而且不要讓測試階段的 job 讀得到。

8.2 讓測試不 flaky 的四件事​

  1. 不要有任何對外連線。 最好在測試設定裡直接禁止： Ruby 的 WebMock.disable_net_connect!(allow_localhost: true)、 Python 的 respx 預設就是 assert_all_mocked=True（沒被 mock 的 httpx 請求直接失敗，不要把它關掉； 但它只攔 httpx，走 urllib 的 PyJWKClient 要像第 3 節那樣另外換掉）、 Go 則靠把 issuer 指向 httptest server。 有東西漏打到真的 Google，你會希望測試立刻失敗，而不是偶爾變慢。
  2. 不要用「現在時間 + 1 小時」以外的魔法時間。 token 的 exp 要嘛明確設在未來、 要嘛明確設在過去，不要依賴測試跑多久。需要測「剛好過期」的話用時間凍結工具。
  3. 清掉跨測試的快取。 JWKS 快取、discovery document 快取、 模組層級的 memoize 都會在測試之間殘留，症狀是「單獨跑會過、整批跑會紅」。
  4. 平行測試時每個 worker 要有自己的假 IdP 與資料庫。 httptest 本來就是隨機埠；docker 的假 IdP 則要注意埠衝突。

8.3 Pipeline 範例​

.github/workflows/test.yml
name: test
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      db:
        image: mysql:8
        env:
          MYSQL_ROOT_PASSWORD: test
          MYSQL_DATABASE: app_test
        ports: ["3306:3306"]
        options: >-
          --health-cmd="mysqladmin ping -h 127.0.0.1"
          --health-interval=5s --health-timeout=3s --health-retries=20
    env:
      # 全部是假值：測試不會對外連線。要跟 8.1 的清單一致
      GOOGLE_CLIENT_ID: test-client-id
      GOOGLE_CLIENT_SECRET: test-client-secret
      GOOGLE_REDIRECT_URI: http://localhost:3000/auth/google/callback
      LINE_CHANNEL_ID: "1234567890"
      LINE_CHANNEL_SECRET: test-channel-secret
      LINE_REDIRECT_URI: http://localhost:3000/auth/line/callback
      APPLE_TEAM_ID: TESTTEAM01
      APPLE_KEY_ID: TESTKEY001
      APPLE_SERVICES_ID: com.example.test.web
      APPLE_REDIRECT_URI: https://app.example.com/auth/apple/callback
      SESSION_SECRET: test-session-secret
      DATABASE_URL: mysql://root:test@127.0.0.1:3306/app_test
    steps:
      # action 的大版本更新得很快，照抄前先看各 action 的 README 確認目前的版本
      - uses: actions/checkout@v7

      # 真的 .p8 不進 CI：當場產生一把同格式的測試金鑰，寫進後續步驟的環境變數
      - name: 產生測試用的 Apple 私鑰
        run: |
          {
            echo "APPLE_PRIVATE_KEY<<EOF"
            openssl ecparam -name prime256v1 -genkey -noout | openssl pkcs8 -topk8 -nocrypt
            echo "EOF"
          } >> "$GITHUB_ENV"

      # ↓ 依你的語言擇一
      - uses: actions/setup-go@v7
        with: { go-version-file: go.mod }
      - run: go test ./... -race -count=1

      # - uses: ruby/setup-ruby@v1
      #   with: { bundler-cache: true }
      # - run: bundle exec rails db:schema:load && bundle exec rspec

      # - uses: actions/setup-python@v7
      #   with: { python-version-file: .python-version }
      # - run: pip install -r requirements-dev.txt && pytest -q
tip

go test 記得加 -race。它抓的是 Go 程式裡的資料競爭 —— 例如 JWKS 快取、 設定這類套件層級變數被多個 goroutine 同時讀寫 —— 第 4 節那條並行測試跑起來時， 這類問題才有機會被它看見。 至於「兩個請求同時建立使用者」是資料庫層級的重複，不是記憶體的資料競爭， race detector 看不到；抓它的是那條測試最後的 countUsers 斷言，加不加 -race 都一樣。

-count=1 則是關掉 Go 的測試結果快取 —— setup-go 預設會快取建置目錄， 不加的話 CI 上可能拿到上一次的綠燈。

8.4 部署前的自動檢查​

有些東西測試測不到，但可以在部署流程裡自動檢查，比人工清單可靠：

# ① 各家的 discovery document 還通嗎，端點有沒有搬家
for issuer in https://accounts.google.com https://appleid.apple.com https://access.line.me; do
  curl -fsS "$issuer/.well-known/openid-configuration" | jq -e '.jwks_uri' > /dev/null \
    || { echo "$issuer 的 discovery 讀不到"; exit 1; }
done

# ② 登入入口導向的 client_id 與 redirect_uri，是不是「這個環境」該用的那一組
#    （測試站的設定被複製到正式站、或反過來，是最常見的部署事故之一）
loc=$(curl -fsS -o /dev/null -w '%{redirect_url}' https://app.example.com/auth/google)
expected_redirect=$(jq -rn --arg u "https://app.example.com/auth/google/callback" '$u | @uri')
case "$loc" in
  *"client_id=${EXPECTED_GOOGLE_CLIENT_ID}"*) ;;
  *) echo "導向的 client_id 不是這個環境的：$loc"; exit 1 ;;
esac
case "$loc" in
  *"redirect_uri=${expected_redirect}"*) ;;
  *) echo "導向的 redirect_uri 不是這個環境的：$loc"; exit 1 ;;
esac

9. 那真的要人工測什麼​

上面所有的自動化測試，刻意用假的 IdP、假的憑證、本機的網址 —— 這正是它們能在 CI 上穩定跑的原因， 但也代表它們從設計上就不會檢查：console 的設定、這個環境真正的憑證、正式網域、 以及真實裝置上的瀏覽器。偏偏登入的事故大多出在這幾個地方： 正式網域的 redirect URI 沒登記、client ID 和 secret 取自不同的 client、 LINE 的 channel 還在 Developing……這些情況下測試會全綠，因為它們根本沒被測到。

所以每個環境部署之後，把下面這份清單在那個環境上實際走一次：

環境與設定

  • 在這個環境的正式網域上走，不是 localhost、不是預覽網址 —— redirect URI、cookie 的 Secure／Domain、Apple 的 Return URL 都只有在真網域上才會對
  • 確認這個環境用的是自己那一組 OAuth client，而且 client ID 與 secret 取自同一個 client （ID 對、secret 錯的話，授權頁一切正常，要到換 token 才失敗）。見 Google 篇 1.5
  • 用一個不是開發者、也不是測試人員的帳號登入一次 —— Google 的 Testing 狀態、LINE 的 Developing 狀態都只擋「別人」，開發者自己永遠測不出來

瀏覽器與裝置

  • 在桌機的真的瀏覽器上用真的帳號走完三家登入各一次
  • 在真的手機上走一次。桌機瀏覽器的裝置模擬只換了 User-Agent 和畫面尺寸， App 內建瀏覽器、跳到原生 App 再跳回來的行為都不會出現
  • 真的在 LINE app 裡開：從聊天室點連結進來，走一次 LINE 登入， 也走一次其他家的登入（Google 在 App 內建瀏覽器裡可能回 disallowed_useragent）， 順便看有沒有跳出「翻譯此網頁」的提示（見 LIFF 篇第 8 節）
  • Apple 在 Safari 上測一次，iPhone 和 Mac 各一次（form_post 的跨站 cookie 行為各家瀏覽器不同）

帳號狀態

  • 用一個全新的 Apple 帳號測一次，確認姓名有被存下來（只有第一次會給）
  • 用一個沒有 email 的 LINE 帳號測一次
  • 用同一個人的兩種登入方式登入，確認是同一個帳號
  • 解除綁定到只剩一個，確認擋得下來
  • 登出後再登入一次
  • 有用 LINE Messaging API 推播的話，用剛在這個環境登入的帳號實際推一則 —— 從別的環境複製過來的帳號資料可能推不出去，而且錯誤訊息不會告訴你原因 （見常見錯誤 6.3）
tip

「讀程式碼推論出它會動」跟「它真的會動」是兩件事。 畫面做完了、測試全綠了、build 也過了，仍然要在真的瀏覽器上點一次。 lint、型別檢查、單元測試，三個 gate 沒有一個擋得住「按鈕打的 API 其實回 500」。
