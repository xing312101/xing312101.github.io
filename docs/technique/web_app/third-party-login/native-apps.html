原生 App 與行動裝置上的第三方登入

原生 App 的 OAuth 流程跟網站是同一套，但有三個結構性的差異： 沒有地方藏 client_secret、沒有 cookie 可以放 state、 redirect 回來的不是網頁而是 App。這一篇講這三件事該怎麼處理。

先讀：OAuth 2.0 與 OIDC 基礎的第 5、6 節（nonce 與 PKCE）。 後端收 App 送來的 ID token 時，驗證方式跟網頁相同（後端驗證），差異在第 6 節。

規範上的依據是 RFC 8252（OAuth 2.0 for Native Apps）， 它的結論可以濃縮成一句話：用系統瀏覽器，不要用 WebView，而且一定要用 PKCE。 （RFC 8252 §8.12：原生 App 不得（MUST NOT） 用內嵌的 user-agent 發授權請求； RFC 9700 也要求公開用戶端必須用 PKCE。）

1. 原生 App 是公開用戶端​

「公開用戶端（public client）」的意思是：它沒辦法保守秘密。

任何打包進 App 的字串 —— 不管是寫在原始碼、放在設定檔、還是做了混淆 —— 只要有人把 APK／IPA 解開就看得到。所以：

danger

絕對不要把 client_secret 放進 App。 這包括：

  • Google 的 Web application client secret
  • LINE 的 Channel secret
  • Apple 的 .p8 私鑰

一旦外流，攻擊者就能冒充你的 App 去換 token。而且你沒辦法悄悄換掉它 —— 換了之後所有舊版本的 App 都會壞掉。

各家給原生 App 用的是沒有 secret 的 client：

供應商原生 App 該用什麼
GoogleConsole 裡 Application type 選 Android 或 iOS 的 client（沒有 secret，靠套件名稱 + 簽章指紋 / Bundle ID 驗證）。Android 上官方建議用 Credential Manager 的「使用 Google 帳戶登入」，不走瀏覽器流程
LINE可以用同一個 LINE Login channel，在 console 的 App types 啟用 Mobile app；用 LINE SDK，或授權碼 + PKCE（LINE 只支援 S256）
Apple原生用 Bundle ID 當 client_id，透過 ASAuthorizationAppleIDProvider，App 端不需要 secret（要拿 refresh token 時，由後端用 .p8 簽的 client_secret 去換，見 Apple 篇）

沒有 secret 就只能靠 PKCE 保護授權碼，所以 PKCE 在原生 App 上不是「建議」而是「必須」。

1.1 兩種架構：App 換 token，還是後端換 token​

App 自己換 tokenApp 把 code 交給後端換
誰持有 refresh tokenApp（存在 Keychain／Keystore）你的後端
需要 client_secret 嗎不需要（公開用戶端）可以用有 secret 的 client
你的後端怎麼認人App 把 ID token 傳給後端驗後端自己驗
適合只需要登入需要長期代表使用者呼叫供應商 API

多數 App 選左邊：App 走完流程，把 ID token 傳給你的後端，後端驗完發自己的 session token。 選右邊時要注意：後端兌換時要用發出這個 code 的那個 client_id，當初授權請求有帶 redirect_uri 的話也要送一模一樣的值 （例如 Apple 原生拿到的 authorizationCode，後端要用 Bundle ID 當 client_id 去換）。

2. 不要用 WebView​

這是原生 App 最重要的一條規則。

WebView（iOS 的 WKWebView、Android 的 android.webkit.WebView）是你的 App 可以完全控制的瀏覽器： 你可以注入 JavaScript、讀取 DOM、攔截每一個請求 —— 也就是說，你可以偷走使用者的 Google 密碼。

供應商知道這件事，所以 Google 會直接擋掉 WebView 裡的登入，回一個 Error 403: disallowed_useragent 錯誤頁 （2021 年 9 月 30 日起全面封鎖內嵌 WebView）。Facebook 從 2021 年 10 月 5 日起也不再支援 在 Android WebView 裡登入。RFC 8252 本身也明文允許授權端點偵測並封鎖內嵌的 user-agent。

這不是 bug，是刻意的政策，沒有繞過的正當方法（改 User-Agent 字串是在規避安全機制， 而且會隨時失效）。想確認自己的 App 會不會中招，可以在 Google 的授權網址加上 disallow_webview=true 測試。

「App 內建瀏覽器」也算 WebView。 使用者在 LINE、Facebook、Instagram 等 App 裡點開你的網站連結時， 開的是那個 App 的內建瀏覽器 —— 你的網站按下「用 Google 登入」一樣會拿到 disallowed_useragent。 這種情況只能提示使用者「用預設瀏覽器開啟」，或改用在該環境可用的登入方式（例如在 LINE 內建瀏覽器裡用 LINE Login／LIFF）。

WebView 的其他問題：

  • 拿不到使用者已登入的狀態。WebView 有自己的 cookie 儲存區， 使用者就算已經在手機上登入 Google，在你的 WebView 裡還是要重打一次帳密。
  • 密碼管理員、Passkey、生物辨識全都用不了。
  • 使用者無法確認網址列，所以無法判斷這是不是釣魚頁。

正確的做法是用系統提供的、你控制不到的瀏覽器元件：

  • iOS（Swift）
  • Android（Kotlin）

用 ASWebAuthenticationSession（AuthenticationServices 框架）。 它會共用 Safari 的 cookie，所以使用者通常按一下就完成。 導向 callbackURLScheme 的那一下是由這個 session 直接攔下來交給你的 App，不經過系統的 URL scheme 分派， 所以別的 App 註冊同一個 scheme 也搶不到。iOS 17.4 起還可以改用 https 網址當 callback （ASWebAuthenticationSession.Callback.https(host:path:)，網域要先設成 App 的 associated domain）。

import AuthenticationServices

final class LoginCoordinator: NSObject, ASWebAuthenticationPresentationContextProviding {
    private var session: ASWebAuthenticationSession?

    func start(authURL: URL, callbackScheme: String) {
        let session = ASWebAuthenticationSession(
            url: authURL,
            callbackURLScheme: callbackScheme   // 例如 "com.example.myapp"
        ) { callbackURL, error in
            if let error = error as? ASWebAuthenticationSessionError, error.code == .canceledLogin {
                // 使用者按了取消：不是錯誤，不要顯示紅色警示
                return
            }
            guard let callbackURL else {
                // 其他錯誤（例如 presentationContextProvider 沒設）才需要提示
                return
            }
            // 從 callbackURL 取出 code 與 state，比對 state 之後換 token
            self.handle(callbackURL)
        }
        // true 時不共用 Safari cookie，等於每次都要重新登入。
        // 除非你的 App 明確需要「切換帳號」，否則維持 false
        session.prefersEphemeralWebBrowserSession = false
        session.presentationContextProvider = self
        session.start()
        self.session = session
    }

    func presentationAnchor(for _: ASWebAuthenticationSession) -> ASPresentationAnchor {
        UIApplication.shared.connectedScenes
            .compactMap { ($0 as? UIWindowScene)?.keyWindow }
            .first ?? ASPresentationAnchor()
    }
}

用 Custom Tabs（androidx.browser）。它共用 Chrome 的 cookie 與密碼管理員， 但你的 App 讀不到裡面的內容。

import androidx.browser.customtabs.CustomTabsIntent

fun startLogin(context: Context, authUrl: Uri) {
    CustomTabsIntent.Builder()
        .setShowTitle(true)
        .build()
        .launchUrl(context, authUrl)
}

回來的 redirect 由 manifest 裡宣告的 intent filter 接住：

<activity android:name=".AuthRedirectActivity" android:exported="true">
    <intent-filter android:autoVerify="true">
        <action android:name="android.intent.action.VIEW" />
        <category android:name="android.intent.category.DEFAULT" />
        <category android:name="android.intent.category.BROWSABLE" />
        <!-- App Links：比 custom scheme 安全，需要 assetlinks.json -->
        <data android:scheme="https" android:host="app.example.com"
              android:path="/auth/callback" />
    </intent-filter>
</activity>
tip

不想自己處理這些細節的話，用 AppAuth （iOS／Android）。 它是 OpenID Foundation 維護的實作，PKCE、state、系統瀏覽器、redirect 處理全都做好了， 而且它的預設值就是 RFC 8252 的建議值。

3. redirect 回 App 的三種方式​

方式長什麼樣安全性說明
Custom schemecom.example.myapp:/callback低任何 App 都可以註冊同一個 scheme 來搶這個 redirect。靠 PKCE 才安全。RFC 8252 要求用反轉網域的形式（含 .），爭議時才能證明所有權
App Links（Android）／Universal Links（iOS）https://app.example.com/auth/callback高需要在網站上放驗證檔，系統會確認這個 App 真的屬於那個網域，別的 App 搶不走
Loopback（http://127.0.0.1:隨機埠）桌面程式用中行動裝置上不適用；Google 已對 Android、iOS 與 Chrome App 類型的 client 停用這個選項

Google 對 custom scheme 越收越緊。 2023 年 10 月起，新建的 Android client 預設不能用 custom scheme （要在 client 的「進階設定」手動打開，官方強烈建議改用 Google Identity Services／Credential Manager）， Chrome 擴充功能則完全不能用、要改用 Chrome Identity API；既有的 client 設定不受影響。 iOS client 目前仍用 Google 指定的反轉 client ID scheme（com.googleusercontent.apps.…）。 這些限制是 Google 的政策，LINE、Apple 沒有對應的規定 —— 但方向很清楚：能用 App Links／Universal Links 或官方 SDK 就不要用 custom scheme。

warning

Custom scheme 沒有任何所有權驗證。 手機上另一個惡意 App 只要在自己的 manifest 裡 也宣告 com.example.myapp，系統就可能把授權碼交給它（Android 會跳出「用哪個開啟」讓使用者選， iOS 則是官方文件明講「沒有機制決定交給哪一個」—— 用 ASWebAuthenticationSession 時例外，見上一節）。

這正是 PKCE 存在的原因 —— 就算 code 被搶走，沒有 code_verifier 也換不到 token。 所以 custom scheme + PKCE 是可接受的，custom scheme 沒有 PKCE 則是漏洞。

有能力的話用 App Links／Universal Links，它從根本上解決這個問題。

驗證檔的位置（這是給 App Links／Universal Links 用的；Sign in with Apple 的網頁登入現在不需要任何網域驗證檔，見 Apple 篇 2.3）：

Android： https://app.example.com/.well-known/assetlinks.json
iOS：     https://app.example.com/.well-known/apple-app-site-association

4. state 存哪裡​

網站把 state 放在 cookie 或 server session；原生 App 沒有這些東西。 做法是存在 App 自己的記憶體或安全儲存區，跟那次登入流程綁在一起：

  • 不要存進 UserDefaults / SharedPreferences 的明文（其他 App 在 root 裝置上讀得到）。
  • App 被系統回收後要能復原（使用者切到瀏覽器登入時，你的 App 可能被殺掉）， 所以要存在能跨行程存活的地方 —— iOS 的 Keychain；Android 用 Keystore 裡的金鑰加密後存進 DataStore （EncryptedSharedPreferences 所在的 androidx.security:security-crypto 已在 1.1.0 整個標為 deprecated）。 用 AppAuth 的話它會自己處理這件事。
  • 用完立刻刪除。

code_verifier 同理，而且它比 state 更敏感。

5. 各家的原生 SDK​

自己走 OAuth 流程 vs 用官方 SDK：

自己走（AppAuth 或手刻）官方 SDK
三家的程式碼幾乎一樣，只換設定每一家都不同
使用者體驗跳系統瀏覽器較順（Apple 是原生表單、LINE 會直接開 LINE App）
依賴一個三個，各自有版本與相容性問題

Apple 是例外：iOS 上請用 ASAuthorizationAppleIDProvider。它是 Apple 平台上的原生 API （系統層級的那張確認表單，可以用 Face ID／Touch ID），不需要 Services ID 與網頁 redirect， aud 直接就是 Bundle ID；網頁流程是給非 Apple 平台（網站、Android）用的。

import AuthenticationServices

let request = ASAuthorizationAppleIDProvider().createRequest()
request.requestedScopes = [.fullName, .email]
// nonce 要先自己產生，並把 SHA256 雜湊放進 request
request.nonce = sha256(rawNonce)

let controller = ASAuthorizationController(authorizationRequests: [request])
controller.delegate = self
controller.performRequests()

// 回呼裡拿到 credential.identityToken（ID token）與 credential.fullName
// ★ fullName 一樣只有第一次會有值，拿到就要立刻傳給後端存起來
warning

ASAuthorizationAppleIDProvider 的 request.nonce 要放的是 原始 nonce 的 SHA256 雜湊，而 ID token 裡回來的 nonce 也是那個雜湊值。 後端比對時要用同樣的雜湊，不是原始字串 —— 這裡弄錯的症狀是「nonce 永遠不符」。

6. 後端收原生端的 token 時要注意​

App 把 ID token 傳給你的後端，後端的驗證邏輯跟網頁幾乎一樣，但有兩個差異：

① aud 不同。 原生 client 的 aud 是原生 client 的 ID：

供應商網頁的 aud原生的 aud
GoogleWeb client IDAndroid／iOS client ID（不同字串）；Android 用 Credential Manager 並設 setServerClientId 時是 web client ID，見下
AppleServices IDBundle ID
LINEChannel IDChannel ID（相同）

所以後端驗證時 aud 要接受一個清單，而不是單一值 —— Apple 篇第 10 節有完整說明。

tip

Google 可以讓 aud 收斂成同一個。 Android 用 Credential Manager 的「使用 Google 帳戶登入」時， GetGoogleIdOption.Builder().setServerClientId(webClientId) 要填的就是你的 web client ID， 拿到的 ID token aud 是 web client ID、azp 是 Android client ID —— 後端可以只認一個 aud， 並檢查 azp 在你的 client 清單裡。（舊版 Google Sign-In for Android 的 requestIdToken(webClientId) 是同一個概念， 那套 API 已被 Credential Manager 取代。）

這跟「會不會變成兩個帳號」無關：Google 的 sub 是 Google 帳號層級的，所有 client 都一樣。 會讓同一個人在網站和 App 變成兩個帳號的是 LINE（兩個 channel 放在不同 Provider）與 Apple（不同 Team）， 見帳號串接 2.1。

② 沒有 state 可以驗。 前端直接把 ID token 送進來時， state 的 CSRF 防護不存在了，nonce 變成唯一的綁定機制 —— 所以這條路徑上的 nonce 絕對不能省。

而且 nonce 要由後端發：App 登入前先向後端要一個 nonce（後端存起來、設短期限）， 放進 Credential Manager 的 setNonce()、Apple 的 request.nonce（放雜湊，見上一節）或 LINE SDK 的請求裡； 後端驗 ID token 時比對、比完作廢。如果是 App 自己產生再連同 token 一起送給後端， 後端只是在比對「App 說的」跟「App 說的」，擋不住一段從別處偷來的 token 被重送。

7. token 存哪裡​

東西iOSAndroid
你的 session tokenKeychain用 Keystore 裡的金鑰加密後再存（EncryptedSharedPreferences 已 deprecated，舊專案可沿用但不要新採用）
refresh token同上同上
ID token驗完就丟，不要存
danger

不要存在 UserDefaults、SharedPreferences 明文、或 App 目錄下的檔案。 在 root／越獄的裝置上，以及某些備份情境下，這些都是可以被讀出來的。

8. 常見錯誤​

症狀原因
disallowed_useragent在 WebView 裡跑 Google 登入。改用 ASWebAuthenticationSession／Custom Tabs
授權完回不到 Appcustom scheme 沒在 Info.plist／manifest 裡宣告；或 App Links 的驗證檔沒放好
redirect_uri_mismatch原生 client 的 redirect 格式跟 Console 登記的不同（注意 Google 的 iOS client 用的是反轉的 client ID）
invalid_grant（只在原生發生）沒送 code_verifier，或送的是 challenge 而不是 verifier
Apple「nonce 永遠不符」原生端送的是 nonce 的 SHA256 雜湊，後端卻拿原始字串去比
同一個人在 App 和網站是兩個帳號LINE：App 與網站用的 channel 在不同 Provider 底下；Apple：App 與 Services ID 在不同 Team 底下（sub 不同）。Google 的 sub 不會因 client 而不同，要查的是後端是不是拿了 sub 以外的東西當鍵
後端驗 App 送來的 Google ID token 時 aud 不符後端只認 web client ID，但 App 沒有用 setServerClientId(webClientId)，aud 是 Android／iOS client ID
disallowed_useragent，但你的 App 沒有用 WebView使用者是從 LINE／Facebook 等 App 的內建瀏覽器打開你的網站
登入到一半 App 被殺掉，回來就失敗state／code_verifier 只存在記憶體裡。要存到能跨行程存活的地方
