常見錯誤訊息對照與排查流程

第三方登入的除錯困難之處在於：錯誤發生在三方之間（瀏覽器、你的伺服器、供應商）， 而且供應商給的訊息通常很短、有時還指錯方向。 這一篇提供一個固定的排查順序，以及錯誤訊息的對照表。 遇到問題時可以直接從這裡開始，不需要先讀別篇；表格裡的連結會帶你到各篇的完整說明。

1. 先確定壞在哪一段​

不要一看到錯誤就開始改程式。先判斷失敗發生在四段裡的哪一段：

① 導向供應商 ──► ② 供應商的登入／同意畫面 ──► ③ 導回你的 callback ──► ④ 換 token 與驗證
你看到的畫面壞在先查什麼
停在供應商的網域上，顯示錯誤頁① 或 ②設定問題：client_id、redirect_uri、scope、App 狀態
回到你的網站，但顯示「state 不符」③cookie／session 問題
回到你的網站，顯示 500 或「登入失敗」④token 兌換或驗證問題，看你的伺服器日誌
登入成功但變成新帳號④ 之後帳號串接邏輯，見帳號串接
tip

判斷 ① / ② 的最快方法：看網址列。 如果錯誤頁的網域是 accounts.google.com、access.line.me、appleid.apple.com， 那就還沒回到你的程式，問題百分之九十在 console 的設定，改程式沒有用。

這時把那串授權 URL 整個複製出來，一個參數一個參數跟 console 的設定比對。

2. 停在供應商的錯誤頁​

錯誤供應商意思與處理
Error 400: redirect_uri_mismatchGoogle送出的 redirect_uri 與這個 client 登記的不是完全相同的字串。檢查尾斜線、http／https、大小寫、port、localhost vs 127.0.0.1。也要確認你改的是同一個 client（見第 6.1 節）。console 上改完，官方說要等 5 分鐘到幾小時才會生效
invalid_request（頁面上寫 Invalid web redirect url 之類）AppleReturn URL 沒登記在這個 Services ID 底下；不是 https；是 IP 或 localhost；或帶了 # 片段。Apple 的技術文件把這類錯誤歸在 unauthorized_client，實際畫面上常見的則是 invalid_request
錯誤頁停在 LINE 上，沒有導回你的站LINEclient_id 或 redirect_uri 不合法（沒登記、不完全相同）時，LINE 不會把錯誤導回 callback，只會顯示在它自己的頁面上
INVALID_SCOPELINEscope 要用空白（%20）分隔，不是逗號；要 email 就一定要一起帶 openid，而且 profile、openid 至少要有一個。LINE 的錯誤碼是全大寫，程式裡比對時不要寫成小寫
access_denied／ACCESS_DENIED全部通常是使用者按了「取消」 —— 這是正常流程，要導回登入頁而不是顯示錯誤。Google 的 App 還在 Testing 狀態、且要了敏感 scope 時，非測試使用者會看到 Error 403: access_denied
Error 403: org_internalGoogleAudience 設成 Internal，非該 Workspace 組織的帳號不能登入
Error 401: invalid_client／deleted_client／disabled_clientGoogleclient_id 打錯或對不上登記資料；client 已被刪除（30 天內可以還原）；或被停用。長期沒用的 client 也會被自動刪除
invalid_scope全部scope 拼錯、或該 scope 需要審查而你還沒通過
Error 403: disallowed_useragentGoogle在 WebView 裡跑登入。見原生 App，沒有繞過的正當方法。部分 App 的內建瀏覽器也會被這樣擋（有 LINE 內建瀏覽器的回報，但官方文件沒有點名），能做的是引導使用者改用外部瀏覽器開啟
「Google 尚未驗證這個應用程式」警告頁Google要了敏感或受限的 scope、但還沒通過驗證時才會出現，使用者可以按「進階」繼續，但未驗證前最多只能有 100 個新使用者。只用 openid email profile 的登入不會出現這一頁
只有自己能登入，別人都失敗LINEChannel 還在 Developing，其他人不是 Admin／Tester。見第 6.2 節

3. 回到 callback 但 state 不符​

這一類最容易誤判成程式邏輯錯誤，實際上幾乎都是 cookie 沒被送出來。

症狀原因
只有 Apple 會發生form_post 是跨站 POST，SameSite=Lax 的 cookie 不會送出。見 Apple 第 4 節
本機正常、正式站失敗cookie 設了 Secure 但本機是 http（或反過來）；或 cookie 的 Domain／Path 設得太窄
前後端分開部署，每一次都失敗登入按鈕經過前端的代理（dev server 的 /api proxy、Next.js rewrites、Nginx 轉發）去打後端的 /auth/start，交易 cookie 就設在前端的網域；而供應商是導回後端的 redirect URI，cookie 不在那個網域上。按鈕要直接連後端的絕對網址。見後端驗證第 5.3 節
偶發，重試就好session 存在單機記憶體，但有多台伺服器且沒有黏性連線 —— 第二個請求打到另一台。要用共用的 session store
使用者按了「上一頁」再登入一次state 已經被第一次的流程消耗掉了。這是正確行為，但訊息要寫得讓人看得懂
使用者在登入頁停留很久session／cookie 過期了。把 OAuth 交易 cookie 的壽命設成 10 分鐘左右，並給一個「請重新登入」的友善訊息
全部使用者都失敗你的 session 加密金鑰換了（例如重新部署時重新產生），舊 cookie 全部解不開

4. 換 token 或驗證階段失敗​

這一段的錯誤只有你的伺服器日誌看得到，所以第一件事是把供應商回的 body 記下來 —— 各家的 error_description 通常直接說出原因。

錯誤意思與處理
invalid_grant最常見的四個原因：① code 已經用過了（重新整理 callback 頁、前端打了兩次）；② code 過期（Apple 只有 5 分鐘）；③ 兌換時的 redirect_uri 跟授權時不同；④ PKCE 的 code_verifier 對不上（送錯、或送成了 code_challenge）。用 refresh token 換時出現則是它被撤銷或過期了
invalid_clientApple：client_secret 過期了（見第 6 節）；iss 不是 Team ID、sub 不是跟 client_id 一模一樣的 Services ID（常見是填成 Team ID，大小寫也要一致）；aud 不是 https://appleid.apple.com；header 少了 kid。Apple 的 ErrorResponse 文件也把「redirect URI 不符或無效」列在這個錯誤的說明裡（TN3107 沒有提到這一點）。其他家：client_secret 打錯、被輪替過，或 client ID 與 secret 取自不同的 client（見第 6.1 節）
invalid_request（token 端點）少帶必要參數（例如沒送 code_verifier，有些供應商會回這個而不是 invalid_grant）
unsupported_grant_typegrant_type 拼錯，或用了 form 以外的 content type
簽章驗證失敗（LINE）網頁流程的 ID token 是 HS256 用 channel secret 簽的，拿 JWKS 公鑰驗當然過不了。LINE 的 discovery document 只列了 ES256，所以「照 discovery 自動設定」的通用 OIDC 函式庫也會拒絕網頁流程的 token。見 LINE 第 5 節
aud 不符原生 App 與網頁的 aud 不同（Apple 是 Bundle ID vs Services ID）。見 Apple 第 10 節
kid 找不到對應金鑰供應商輪替了金鑰而你的 JWKS 快取沒更新。確認函式庫會在 kid 找不到時重抓
exp 已過期，但 token 明明剛拿到伺服器時鐘不準。裝 NTP，並在驗證時允許 60 秒誤差
nonce 永遠不符（Apple 原生）原生端送給 Apple 的是 nonce 的 SHA256 雜湊，ID token 裡的 nonce 也就是那個雜湊；後端卻拿原始字串比。要讓 App 把原始 nonce 交給後端，後端做 SHA256 之後再比

5. 登入成功了，但行為不對​

症狀原因
拿不到 emailGoogle：scope 沒帶／email_verified 是 false。LINE：權限沒申請／使用者拒絕／帳號沒綁 email。Apple：使用者選了隱藏信箱
拿不到姓名Apple 只有第一次授權會給，而且沒有 API 可以補查。見 Apple 第 5 節
寄信給使用者一直被退Apple 的轉寄信箱需要先登記寄件網域
LINE 推播回 400 Failed to send messages那個 userId 不屬於這個 Messaging API channel 的 Provider。見第 6.3 節
同一個人變成兩個帳號少了 UNIQUE (provider, provider_user_id)，或用 email 當鍵。見帳號串接
App 和網站登入是兩個帳號看是哪一家：LINE 的 App 與網頁 channel 不在同一個 Provider 底下；Apple 的 App 與 Services ID 不在同一個 Team；或是你的程式把兩邊存成不同的 provider 字串（例如 google 與 google_ios）。Google 的 sub 對同一個帳號在所有 client 都一樣，不會是它。另見原生 App 第 6 節
換了環境之後老用戶都變新用戶LINE 的 user ID 綁 Provider、Apple 的 sub 綁 Team —— 測試環境若用不同的 Provider／Team，同一個人拿到的就是另一組 ID。正式站與測試站的使用者資料不能直接互搬（Google 的 sub 不受影響）
拿不到 refresh_tokenGoogle 要 access_type=offline，而且只有第一次授權會給（要重拿得加 prompt=consent）
Google 的 refresh token 過一週就失效App 還在 Testing 狀態、而且要了 openid email profile 以外的 scope 時，refresh token 7 天就過期。切到 In production 才會解除
上線半年後 Apple 登入全掛client_secret 到期。改成每次即時簽發
使用者登出後又自動登入正常 —— 你的登出只清掉自己的 session，供應商那邊還是登入狀態

6. 錯誤訊息不會告訴你的設定問題​

下面這幾種情況有一個共同點：錯誤訊息要嘛指向別的地方，要嘛根本沒有錯誤訊息。 而且自動化測試全部是綠的 —— 測試用的是假的 IdP 與假的憑證，本來就不會碰到這些設定 （見測試第 9 節）。

6.1 Google：client ID 與 secret 取自不同的 client​

正式、測試、本機各建一個 OAuth client 是正確的做法（理由與設定見 Google 篇 1.5）， 但它帶來一種特有的事故：ID 從 A 複製、secret 從 B 複製。授權頁完全正常（它只看 client_id）， 要到換 token 時才回 invalid_client，很容易誤判成 secret 過期或打錯字。 反過來，redirect URI 只登記在另一個 client 上時，第一步就是 redirect_uri_mismatch。

這兩種錯誤只要看到，先確認 ID、secret、redirect URI 三個值出自同一個 client， 而且你正在看的 console 頁面，就是這個環境實際用的那個 client。 新版 console 的 secret 只在建立當下顯示完整內容，建立時就把 ID 與 secret 成對存進同一個地方。

6.2 LINE：Channel 還在 Developing​

Developing 狀態的 LINE Login channel 只有在 channel 上有 Admin 或 Tester 角色的人能登入。 其他人會停在 LINE 的錯誤頁，訊息類似：

The authorization server denied the request.
This channel is now developing status. User need to have developer role.

（這段文字來自實際畫面與社群回報，官方文件沒有列出確切字樣，可能會改。） 開發者自己測永遠是好的，所以通常是上線後第一個「別人」回報才發現。 處理方式是在 console 把 channel 切到 Published —— 這個動作切了就不能切回來； 還沒準備好公開的話，就把要測的人加成 Tester。

6.3 LINE：推播回 400 Failed to send messages​

用 Messaging API 推播給某個 userId，回的是：

{"message": "Failed to send messages"}

這個訊息不會告訴你是 userId 的問題（LINE 文件列的原因之一就是 user ID 不存在）。 常見原因是那個 userId 是在另一個 Provider 底下取得的 —— LINE 的 userId 是「每個 Provider 各一組」，同一個人在不同 Provider 下的 userId 完全不同， 而 Messaging API channel 只認得自己 Provider 底下的 userId（三家 sub 範圍的比較見帳號串接 2.1）。

最常見的情境：把正式環境的帳號資料複製到測試環境（或反過來）， 而兩個環境的 LINE channel 分屬不同的 Provider。資料表裡的 userId 看起來完全正常， 程式也沒有改過，推播就是送不出去。multicast 更安靜：這種 userId 會回 200，但訊息根本沒送到。 預防的做法是複製帳號資料時不要帶 identities，讓每個人在該環境重新綁定（見帳號串接 2.1）。

反過來，使用者封鎖了官方帳號、還沒加好友、帳號已刪除時，推播 API 回的是 200，只是訊息不會送達 —— 所以訊息內容本身確定沒問題、卻回 400 的時候，第一個該懷疑的就是 userId 不屬於這個 channel 的 Provider。

6.4 在 LINE 內建瀏覽器裡跳出「翻譯此網頁」​

中文頁面在 LINE 內建瀏覽器裡開啟時跳出翻譯提示，推測多半是 SPA 的 HTML 殼寫了 <html lang="en"> （依據是 Chromium 的語言判斷邏輯，尚未在實機上逐一確認）。原因與處理見 LIFF 篇第 8 節。

7. 排查時好用的幾招​

① 先用瀏覽器直接貼授權網址。 把你程式組出來的那串 URL 印出來、貼進網址列。設定錯誤會在那一頁就顯示， 不用先把 callback 寫完。

② 把 JWT 貼進解碼器看 claims。 ID token 的前兩段是明碼，任何 JWT 解碼工具都能看。 aud 是不是你的 client_id？iss 對不對？exp 是什麼時候？nonce 在不在？

warning

線上的 JWT 解碼網站不要拿來貼正式環境的 token。 那等於把一張還沒過期的身分憑證 送給第三方。用本機的指令就好：

# 取出 payload 那一段，Base64URL 轉回一般 Base64，補足被省略的 = 再解開
payload=$(cut -d. -f2 <<< "$ID_TOKEN" | tr '_-' '/+')
while [ $(( ${#payload} % 4 )) -ne 0 ]; do payload="${payload}="; done
printf '%s' "$payload" | base64 -d | jq .

JWT 的每一段都是不補 = 的 Base64URL，直接丟給 base64 -d 會在最後幾個位元組截斷， 結果是一段少了結尾 } 的 JSON，jq 解析失敗 —— 看起來像 token 壞了，其實是指令少了補位。

③ 對照 discovery document。 curl https://供應商/.well-known/openid-configuration | jq . 端點有沒有搬家、支援哪些簽章演算法、支不支援 PKCE，都在這裡面。

④ 把供應商回的錯誤 body 完整記下來。 不要只記 HTTP 狀態碼。error_description 常常直接寫出原因， 而它只出現在回應的 body 裡。

⑤ 用無痕視窗測。 登入問題有一大半跟既有的 cookie 狀態有關。無痕視窗能排除「我這邊是好的」這種假象。

8. 錯的訊息比沒有訊息更貴​

最後一件事，是關於你自己丟出來的錯誤訊息。

排查登入問題的人（可能是半年後的你、可能是客服）會照著你寫的訊息去查。 訊息指錯方向的話，他會照著那個方向改，改完還是失敗，然後卡住 —— 這比直接顯示「登入失敗」還糟。

所以：

  • 不要把所有例外都翻成同一句話。 「這個帳號已被使用」如果同時涵蓋了 「身分已綁在別人身上」「你已經綁過一個 Google 帳號」「email 撞號」三種情況， 使用者永遠猜不到該做什麼。
  • 不要靜默走到預設分支。 找不到指定的設定時就回錯誤， 不要偷偷用另一組設定繼續跑 —— 那會讓人在完全錯誤的地方找上好幾個小時。
  • 把技術細節記在伺服器日誌，給使用者看的是下一步該做什麼。 「登入失敗（代碼 A7）」配上一份代碼對照，比一串堆疊有用得多。
