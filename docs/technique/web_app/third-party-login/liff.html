LIFF：在 LINE 裡開的網頁

LIFF（LINE Front-end Framework）是給「在 LINE 裡面開啟的網頁」用的 SDK。 在 LIFF 裡你不需要自己跑授權碼流程 —— liff.init() 就會完成登入， 你只要把 ID token 交給後端驗（架構（B），見總覽 3.1）。 麻煩的地方在前端：深層連結會讓頁面整頁重載、SPA 的路由要等 liff.init() 完成、 在 LINE 以外的瀏覽器打開時要自己處理登入。

先讀：LINE Login 的第 1、2 節（Provider、Channel，LIFF app 就掛在 LINE Login channel 上）， 以及第 5 節（後端驗 ES256 ID token 的函式，這一篇的後端直接呼叫它）。

note

LINE 官方在 2025 年宣布 LIFF 之後會併入 LINE MINI App，並建議新的 LIFF app 直接建成 LINE MINI App （日期未定）。LINE MINI App 用的也是 LIFF SDK，下面講的載入流程與驗證方式都一樣適用。

1. 建立 LIFF app​

到 LINE Login channel 的 LIFF 頁籤 → Add。

  • LIFF app 只能加在 LINE Login channel（或 LINE MINI App channel）上， 不能加在 Messaging API channel。一個 channel 最多 30 個 LIFF app。
  • 一個 LIFF app 只有一個 Endpoint URL（必須是 https，不能有 #fragment）。 所以正式站和測試站通常各建一個 LIFF app，各自有自己的 LIFF ID。
  • Scopes 要勾 openid，否則 liff.getIDToken() 拿不到東西。 要 email 還要勾 email（前提是 channel 已經申請過 email 權限，見 LINE 篇 2.1）。
  • Add friend option 等同 bot_prompt：On (normal)／On (aggressive)／Off。

建好之後會拿到 LIFF ID 和 LIFF URL（https://liff.line.me/{liffId}）。 使用者點的、你分享出去的，都是 LIFF URL，不是你的 Endpoint URL。

LIFF 拿到的 ID token，aud 是這個 LIFF app 所在的 LINE Login channel 的 Channel ID。 如果測試站的 LIFF app 放在另一個 channel，後端驗 aud 時要用那個 channel 的 ID； 如果放在另一個 Provider，連 sub 都會跟正式站不同（見 LINE 篇第 1 節）。

2. 開啟流程：深層連結會讓頁面整頁重載​

LIFF URL 後面可以接路徑與參數，當成深層連結分享出去，例如 https://liff.line.me/{liffId}/items/42?tab=detail。但 LINE 不會直接開這個路徑，而是分兩段：

使用者點  https://liff.line.me/{liffId}/items/42?tab=detail
                 │  LIFF 伺服器
                 ▼
① 第一次載入：Endpoint URL?liff.state=%2Fitems%2F42%3Ftab%3Ddetail
                 │  （你的頁面跑 liff.init()）
                 │  init 完成時，SDK 把網址整頁轉到「Endpoint URL + 附加的路徑」
                 ▼
② 第二次載入：Endpoint URL + /items/42?tab=detail
                    （你的頁面再跑一次 liff.init()，這次才真正顯示內容）

官方文件稱這兩段為 primary redirect 與 secondary redirect，並要求兩次載入都要執行 liff.init()。 第二段是整頁導向（實作上是 location.replace），不是前端路由切換，所以：

  • 一次點擊至少載入兩次；在外部瀏覽器又沒登入時，中間還會多跳一趟 LINE 登入頁，變成三次以上。 頁面啟動時的程式要能承受被重跑，不要在 liff.init() 之前就送統計、打有副作用的 API
  • 第一次載入的網址裡會帶使用者的 access token。官方提醒不要把第一次載入的網址送到外部的分析工具； LIFF SDK v2.11.0 以後，liff.init() 完成時會把這些憑證從網址上拿掉，所以統計放在 init 之後送
  • 要產生某一頁的分享連結，可以用 liff.permanentLink.createUrlBy(url)，它會把 「Endpoint URL 底下的某個網址」轉成對應的 LIFF URL

另外，liff.init() 只保證在 Endpoint URL 本身或它底下的路徑有效。 Endpoint 設成 https://app.example.com/liff/，那 https://app.example.com/other/ 就不保證能 init。

3. SPA：liff.init() 要在路由讀網址之前完成​

官方的規則是：所有會改網址的動作，都要等 liff.init() 回傳的 Promise resolve 之後才做 —— 包括改 location、history.pushState()／replaceState()，以及伺服器回 301／302。

SPA 的前端路由一掛載就會讀 location，常常還會順手 replaceState（例如把不認得的路徑導回首頁）。 如果這件事發生在 init 之前：路由看到的是第一次載入的 Endpoint 根路徑， liff.state 還沒被處理，深層連結就丟了 —— 使用者點的是某一筆資料，打開的卻是首頁。

所以進入點要寫成「先 init，再建立路由」：

src/main.js
import liff from '@line/liff'
import { startApp } from './app' // 你的 SPA：在這裡面才建立路由、掛載畫面

const LIFF_ID = 'YOUR_LIFF_ID'

async function boot() {
  try {
    // ★ 一定要在路由讀網址之前完成：init 會處理 liff.state、必要時整頁轉到真正的路徑
    await liff.init({ liffId: LIFF_ID })
  } catch (err) {
    // init 失敗仍然讓畫面起來，才有地方顯示錯誤；這裡不要改網址
    console.error('liff.init 失敗', err)
  }
  startApp()
}

boot()

如果同一個 SPA 同時給一般網頁和 LIFF 用，只在 Endpoint URL 底下的路徑才呼叫 liff.init()。

4. 前端：拿 ID token 交給後端​

不用打包工具時，直接用 <script src> 載入 SDK。注意 await 不能寫在一般 <script> 的最外層， 要包進 async 函式（或改用 <script type="module">）：

public/liff/index.html
<!doctype html>
<html lang="zh-TW">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <script charset="utf-8" src="https://static.line-scdn.net/liff/edge/2/sdk.js"></script>
</head>
<body>
  <p id="status">載入中…</p>
  <script>
    const LIFF_ID = 'YOUR_LIFF_ID'

    async function main() {
      await liff.init({ liffId: LIFF_ID })

      if (!liff.isLoggedIn()) {
        // LIFF 瀏覽器裡 init 會自動登入，會走到這裡的是外部瀏覽器或 LINE 的內建瀏覽器。
        // redirectUri 不帶的話，登入完會回到 Endpoint URL，深層連結的路徑就丟了
        liff.login({ redirectUri: location.href })
        return
      }

      // 原始的 ID token（JWT 字串）交給後端驗；LIFF app 的 Scopes 沒勾 openid 會拿到 null
      const idToken = liff.getIDToken()
      if (!idToken) throw new Error('拿不到 ID token')

      const res = await fetch('/auth/liff', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ idToken }),
      })
      if (!res.ok) throw new Error(`登入失敗：${res.status}`)
      // 從這裡開始用你自己的 session，不要每個 API 都再送一次 ID token
      document.getElementById('status').textContent = '已登入'
    }

    main().catch((err) => {
      console.error(err)
      document.getElementById('status').textContent = '登入失敗，請關閉後重新開啟'
    })
  </script>
</body>
</html>

用 npm 的話是 npm install @line/liff，然後 import liff from '@line/liff'，其餘相同。 想釘版本的話，CDN 也有 https://static.line-scdn.net/liff/edge/versions/{版本}/sdk.js 的寫法。

danger

liff.getDecodedIDToken()、liff.getProfile() 回傳的是前端自己解開、自己拿到的內容。 它們可以用來在畫面上顯示名字，但官方明講不要把這些資料送給伺服器當身分依據 —— 前端送來的 { userId: "..." } 誰都能偽造。 傳給後端的一定要是 liff.getIDToken() 的原始字串（或 liff.getAccessToken()，由後端去 LINE 驗）。

5. 在 LINE 以外的地方打開 LIFF URL​

LIFF URL 支援 iOS 的 universal link 與 Android 的 app link，所以在手機瀏覽器點下去通常會跳進 LINE App； 但官方明講不保證 —— 依作業系統、以及是從哪個 App 點的，也可能就在外部瀏覽器裡打開。

在外部瀏覽器裡：

  1. 一樣是 LIFF 伺服器 → 你的 Endpoint URL，你的頁面照常載入
  2. liff.init() 會成功，但 liff.isLoggedIn() 是 false
  3. 呼叫 liff.login() 會轉去 LINE 登入，登入完回到 redirectUri（預設是 Endpoint URL， 所以上面的範例帶了 location.href；redirectUri 必須以 Endpoint URL 開頭，否則登入失敗）
  4. 回來後再跑一次 liff.init()，這時才拿得到 ID token

也可以在 init 時帶 withLoginOnExternalBrowser: true，讓 SDK 在外部瀏覽器自動呼叫 liff.login()。

判斷環境用 liff.isInClient()（在 init 之前就能呼叫）：它只在 LIFF 瀏覽器裡回 true。 在外部瀏覽器，以及在 LINE 的內建瀏覽器（在聊天室裡點一般網址開的那個）都是 false。 另外，liff.login() 不能在 LIFF 瀏覽器裡呼叫（那裡的登入由 liff.init() 自動完成）。

6. 後端驗 LIFF 的 ID token​

後端收到的 ID token 用 VerifyLIFFIDToken／verify_liff_id_token 驗（ES256 + JWKS，定義見 LINE 篇第 5 節）， 或用 LINE 的 verify 端點 （client_id 帶 LIFF app 所在的 LINE Login channel 的 ID，不要帶 nonce）。

跟網頁 callback 的差別：

  • 沒有你能比的 nonce。授權請求是 SDK 自己發的，你沒有機會放 nonce 進去。 所以別拿網頁 callback 那支「一定要比 nonce」的函式來驗，會全部失敗
  • 也因此，一張 LIFF 的 ID token 在效期內可以被重送。守的方式是：只走 HTTPS、不要把 token 寫進 log、 收到就換成你自己的 session（下面的範例）、之後的 API 看 session 不看 token
  • 這支端點只收 application/json。跨站的表單送不出 JSON，這是在擋「把攻擊者自己的 token 送進受害者的瀏覽器、讓他登入成攻擊者帳號」的 login CSRF

效期只有一小時（官方 liff.getIDToken() 的說明）。官方文件沒有說明過期之後 SDK 會不會自動換新， 也有開發者回報重新開啟 LIFF app 時，SDK 交出來的仍是快取裡已經過期的 token（後端會看到 IdToken expired.）。 所以：

  1. 一拿到就換成自己的 session，之後不再依賴它 —— 這樣只有「剛打開頁面」那一刻會碰到效期
  2. 後端因為過期回 401 時，前端重新取得一次：外部瀏覽器裡常見的做法是 liff.logout() 之後 liff.login({ redirectUri: location.href })，並用 sessionStorage 記一個旗標避免無限重導； LIFF 瀏覽器裡不能呼叫 liff.login()，請使用者關掉重開 （這段是社群的做法，官方文件沒有寫，請自己在實機上驗證）

下面的程式碼接在 LINE 篇的檔案後面：lineProfile／line_profile 定義在 LINE 篇第 4 節， 驗證函式在第 5 節；session 與 SignIn 的錯誤型別見 Google 篇第 3 節開頭的對照表。 這支是前端用 fetch 打的 JSON 端點，所以 SignIn 的三種錯誤不導頁，而是回 409 加上錯誤代碼 （identity_taken、provider_already_linked、email_taken），由前端顯示對應的訊息。

  • Ruby on Rails
  • Python
internal/authline/liff.go（跟 LINE 篇第 4、5 節的檔案同一個套件）
package authline

import (
	"database/sql"
	"encoding/json"
	"errors"
	"log"
	"mime"
	"net/http"

	"example.com/app/internal/accounts"
	"example.com/app/internal/web"
)

// LIFFSignIn 處理 POST /auth/liff，body 是 {"idToken": "..."}
func LIFFSignIn(db *sql.DB) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		// 只收 JSON：跨站的表單送不出 application/json，擋 login CSRF
		if mt, _, _ := mime.ParseMediaType(r.Header.Get("Content-Type")); mt != "application/json" {
			http.Error(w, "只接受 application/json", http.StatusUnsupportedMediaType)
			return
		}
		var body struct {
			IDToken string `json:"idToken"`
		}
		if err := json.NewDecoder(http.MaxBytesReader(w, r.Body, 16<<10)).Decode(&body); err != nil || body.IDToken == "" {
			http.Error(w, "缺少 idToken", http.StatusBadRequest)
			return
		}

		claims, err := VerifyLIFFIDToken(body.IDToken)
		if err != nil {
			// 過期（LIFF 的 ID token 只有一小時）也會走到這裡；前端收到 401 要重新取得
			log.Printf("liff id_token 驗證失敗：%v", err)
			http.Error(w, "ID token 無效或已過期", http.StatusUnauthorized)
			return
		}

		user, err := accounts.SignIn(r.Context(), db, lineProfile(claims), web.CurrentUserID(r))
		var se *accounts.SignInError
		if errors.As(err, &se) {
			// 這支是 fetch 打的 JSON 端點，不導頁；把錯誤代碼交給前端顯示對應的訊息
			http.Error(w, se.Code, http.StatusConflict)
			return
		} else if err != nil {
			log.Printf("liff 登入失敗：%v", err)
			http.Error(w, "登入失敗", http.StatusInternalServerError)
			return
		}
		if err := web.StartSession(w, r, user.ID); err != nil {
			log.Printf("無法建立 session：%v", err)
			http.Error(w, "登入失敗", http.StatusInternalServerError)
			return
		}
		w.WriteHeader(http.StatusNoContent)
	}
}
app/controllers/auth/line_controller.rb（接續 LINE 篇第 4 節，放在 private 之前）
  # POST /auth/liff，body 是 {"idToken": "..."}
  def liff
    # 只收 JSON：跨站的表單送不出 application/json，擋 login CSRF
    return head(:unsupported_media_type) unless request.media_type == "application/json"

    claims = LineOIDC.verify_liff_id_token(params.require(:idToken))
    user = Identity.sign_in!(line_profile(claims), current_user: current_user)
    start_session(user)
    head :no_content
  rescue ActionController::ParameterMissing
    head :bad_request
  rescue JWT::DecodeError => e
    # 過期（LIFF 的 ID token 只有一小時）也會走到這裡；前端收到 401 要重新取得
    Rails.logger.info("liff id_token 驗證失敗：#{e.message}")
    head :unauthorized
  rescue Identity::SignInError => e
    # 這支是 fetch 打的 JSON 端點，不導頁；把錯誤代碼（identity_taken 等）交給前端顯示對應的訊息
    render json: { error: e.class.name.demodulize.underscore }, status: :conflict
  end
app/auth_line.py（接續 LINE 篇第 4、5 節）
from fastapi import Response
from pydantic import BaseModel


class LiffLogin(BaseModel):
    idToken: str


@router.post("/auth/liff", status_code=204)
async def liff_login(body: LiffLogin, request: Request, db: Session = Depends(get_db)):
    # 只收 JSON：跨站的表單送不出 application/json，擋 login CSRF
    content_type = request.headers.get("content-type", "").split(";")[0].strip()
    if content_type != "application/json":
        raise HTTPException(415, "只接受 application/json")

    try:
        claims = verify_liff_id_token(body.idToken)
    except jwt.PyJWTError as exc:
        # 過期（LIFF 的 ID token 只有一小時）也會走到這裡；前端收到 401 要重新取得
        log.info("liff id_token 驗證失敗：%s", exc)
        raise HTTPException(401, "ID token 無效或已過期") from exc

    try:
        user = sign_in(db, line_profile(claims),
                       current_user=get_current_user(request, db))
    except SignInError as exc:
        # 這支是 fetch 打的 JSON 端點，不導頁；把錯誤代碼交給前端顯示對應的訊息
        raise HTTPException(409, exc.code) from exc

    start_session(request, user)  # 換發 session，防 session fixation
    return Response(status_code=204)

7. 跟官方帳號共用同一個 user ID​

同一個 Provider 底下，LIFF 拿到的 ID token sub，跟官方帳號（Messaging API）webhook 事件裡 source.userId 是同一個值（官方文件：同一個 Provider 下，user ID 不因 channel 類型而不同；實測也一致）。

所以如果你已經有「在官方帳號聊天室裡綁定帳號」的流程，把 webhook 的 userId 存成 identities 裡 provider = 'line' 的 provider_user_id，那麼這些人從 LIFF 開網頁就會直接登入， 不用再綁一次。反過來，從 LIFF 或 LINE Login 綁過的人，你也能用那個 ID 推播給他。

前提有兩個：LIFF app 所在的 LINE Login channel 與官方帳號在同一個 Provider 底下； 以及聊天室裡的綁定流程本身要能證明「這個 userId 是這個帳號的主人」（例如讓他在聊天室輸入一次性綁定碼）， 不能只憑他在聊天室裡打的帳號名稱就綁。

8. LIFF 頁面一直跳出「翻譯此網頁」​

SPA 的殼 index.html 常常照範本寫成 <html lang="en">。依 Chromium 原始碼 （components/translate/core/language_detection/language_detection_util.cc、 chrome/renderer/chrome_render_frame_observer.cc）的邏輯，Chrome 在頁面載入完成時判斷一次語言： 如果這時 JavaScript 還沒把文字畫出來，頁面是空的、偵測不出內容語言，就直接採用 lang 屬性 —— 於是一個全中文的頁面被當成英文，對中文使用者跳出翻譯提示。 LIFF 頁面每次點擊都會整頁重載好幾次（第 2 節），碰到這個時機的機會也就多了好幾倍。

修法：

  • lang 設成內容實際的語言，例如 <html lang="zh-TW">。舊版 Chromium 只認 xx 或 xx-YY 這種格式， zh-Hant 會被當成沒設，所以用 zh-TW 比較保險
  • 整個網站都不想被翻譯的話，在 <head> 加 <meta name="google" content="notranslate">
note

這是從 Chromium 原始碼推出來的，還沒有在 LINE 的 LIFF 瀏覽器實機上確認過 （LIFF 瀏覽器是 iOS 的 WKWebView 與 Android 的 WebView，不是 Chrome 本身）。 在外部的 Chrome 打開 LIFF URL 時，這個機制是適用的。

9. 常見錯誤​

症狀原因
liff.getIDToken() 回 nullLIFF app 的 Scopes 沒勾 openid，或使用者沒同意
LIFF 拿到的 ID token 裡沒有 emailLIFF app 的 Scopes 沒勾 email；其他原因（沒申請權限、使用者不同意、帳號沒有 email）見 LINE 篇第 8 節
驗 LIFF 的 ID token 一直說 nonce 不符拿網頁 callback 的驗證函式去驗。LIFF 的 token 沒有你能指定的 nonce，要用不比 nonce 的那支（第 6 節）
verify 端點回 IdToken expired.LIFF 的 ID token 只有一小時。拿到就換成自己的 session，過期時重新取得（見第 6 節）
verify 端點回 Invalid IdToken Audience.client_id 帶錯。LIFF 的要帶 LIFF app 所在的 LINE Login channel 的 ID
分享的 LIFF 深層連結，打開都是首頁SPA 的路由在 liff.init() 完成之前就讀了網址或改了網址（見第 3 節）；或外部瀏覽器裡 liff.login() 沒帶 redirectUri，登入完回到 Endpoint URL（見第 5 節）
同一次點擊，頁面載入了兩三次正常。LIFF 的深層連結會整頁重導一次，外部瀏覽器沒登入時再多一趟 LINE 登入（見第 2 節）
全中文的 LIFF 頁面，Chrome 跳出「翻譯此網頁」SPA 殼的 <html lang> 寫成 en，頁面還空白時被拿來判斷語言（見第 8 節）
