LINE Login

LINE Login 走的是標準的 OAuth 2.0 授權碼流程 + OpenID Connect， 所以整體結構跟 Google 篇一樣。 麻煩的地方在組織結構（Provider／Channel）、email 要另外申請、 ID token 的簽章演算法會依來源不同。在 LINE 裡面開的網頁（LIFF）有自己一套載入流程， 另見 LIFF 篇。

先讀：Google 篇。這一篇的程式碼只寫跟 Google 不一樣的地方， 共用的函式（SignIn、session、錯誤處理）對照表在 Google 篇第 3 節開頭。

1. 先搞懂 Provider 與 Channel​

概念是什麼類比
Provider提供服務的個人、公司或組織一個「組織」
Channel一個具體的服務接點組織底下的一個「應用程式」

Channel 有好幾種類型，做登入要建的是 LINE Login channel：

Channel 類型用途
LINE Login讓使用者用 LINE 帳號登入你的服務；LIFF app 也掛在這裡 ← 這篇在講的
Messaging API官方帳號的聊天機器人（webhook、推播）
LINE MINI App在 LINE 裡面跑的小程式（LINE 建議新的 LIFF app 改用這種，見 LIFF 篇）
warning

Provider 的選擇很重要，而且事後不能搬。 Channel 建立之後不能移到別的 Provider。 LINE 的使用者 ID（ID token 裡的 sub、webhook 裡的 userId）是依 Provider 發的 —— 同一個 Provider 底下，不管是 LINE Login 還是 Messaging API channel，同一個人的 user ID 都相同； 換了 Provider 就是另一組完全不同的 ID。

這代表：

  1. 你的 LINE Login channel 和你的官方帳號（Messaging API channel） 必須放在同一個 Provider 底下，登入拿到的 ID 才能拿去推播訊息。
  2. 正式站和測試站如果放在不同 Provider，兩邊的 LINE user ID 對不起來， 帳號資料的 identities 不能跨環境複製（見帳號串接 2.1）。 複製過去的 ID 拿去推播，只會得到一句不提 Provider 的 Failed to send messages（見常見錯誤 6.3）。
  3. Provider 名稱會顯示在使用者的同意畫面上。LINE 建議用公司或組織的正式名稱， 不要用專案代號或內部品牌名。

2. 申請步驟​

  1. 到 LINE Developers Console 用你的 LINE 帳號或 Business ID 登入 （建議用組織的帳號，不要用個人帳號，之後交接會很痛苦）。
  2. Create a new provider → 填名稱。
  3. 在該 Provider 底下建立新 channel → 選 LINE Login。
  4. 填 channel 基本資料：
欄位必填說明
Region to provide the service✅服務提供的地區（日本、泰國、台灣、印尼擇一）。只能在建立時設定，要服務多個地區就每個地區各建一個 channel
Company or owner's country or region✅會顯示在同意畫面上
Channel name✅會顯示在同意畫面上。不能含有「LINE」或類似字樣
Channel description✅會顯示在同意畫面上
Channel icon會顯示在同意畫面上
App types✅Web app 或 Mobile app。網站登入與 LIFF 選 Web app
Email address✅收 LINE 通知用的信箱
Privacy policy URL視情況認證 Provider（certified provider）才必填；一般 Provider 可以不填，但填了會顯示在同意畫面上
Terms of use URL同上，選填
  1. 建好之後主要看這幾個頁籤：
頁籤要設什麼
Basic settingsChannel ID（就是 client_id）、Channel secret（就是 client_secret）；OpenID Connect 區塊申請 email 權限；Linked LINE Official Account（要用 bot_prompt 加好友時設定）

LIFF新增 LIFF app（見 LIFF 篇第 1 節）
Roles邀請 Tester（Developing 狀態下只有 Admin／Tester 能登入）
tip

同意畫面上顯示的是 Provider 名稱、channel 名稱、圖示與說明，使用者靠這些判斷是誰在要他的資料。 建立時就填正式的名稱，不要填 test。

2.1 申請 email 權限​

LINE 預設不給 email。要拿到的話：

  1. Basic settings 頁籤 → OpenID Connect 區塊 → 按 Apply。
  2. 同意條款，並上傳一張截圖 —— 內容要能說明「你會蒐集使用者 email」以及「用途是什麼」。 通常就是你的註冊頁或隱私權政策裡那一段的畫面。
  3. 申請通過後，Email address permission 底下會顯示 Applied，scope 才能帶 email。
warning

就算申請通過了，使用者仍然可以在同意畫面上不勾選提供 email， 這時 ID token 裡就沒有 email 這個 claim。而且 LINE 帳號不一定有登錄 email。

另外，LINE 的 ID token 沒有 email_verified。官方文件沒有說明這個 email 是否經過驗證， 所以本系列的範例把它當成未驗證，不拿它自動合併既有帳號 （規則見帳號串接）。

所以：你的註冊流程必須能處理「沒有 email」的使用者。這也是 資料表設計裡 users.email 允許 NULL 的原因。

tip

不申請 email 權限也做得出來。 用 sub 認人就夠了；對不到帳號的人， 讓他輸入管理員發的一次性綁定碼綁上去 —— 做法見帳號串接 5.1。 內部系統、只給特定客戶用的平台特別適合這樣做，連截圖審查都省了。

2.2 上線前要把 channel 發布​

Channel 剛建立時狀態是 Developing，這時只有這個 channel 的 Admin 與 Tester 能登入。 其他人按登入會停在 LINE 的錯誤頁，訊息類似「This channel is now developing status」， 不會導回你的 callback，所以你的伺服器 log 裡什麼都看不到。

  • 加 Tester：Roles 頁籤 → Invite by email，角色選 Tester。對方必須已經有 LINE Developers 帳號，而且那個帳號的 Business ID 要綁定他的 LINE 帳號，才能用 LINE 帳號測登入。
  • 發布：打開 channel，按頁面上方的 Developing 狀態切成 Published。 切成 Published 之後就不能再改回 Developing，只給內部測試用的 channel 可以一直留在 Developing。

Discovery document 裡的 id_token_signing_alg_values_supported 只列了 ES256， 但網頁登入拿到的 ID token 是 HS256（見第 5 節； 各家 discovery 列不完整的對照見基礎篇第 8 節）。 所以「讀 discovery 自動設定」的通用 OIDC 函式庫，拿到網頁登入的 ID token 通常會直接拒絕。

4. 授權請求與 callback​

流程與 Google 篇相同：產生 state／nonce／PKCE → 導向 LINE → 比對 state → 換 token → 驗 id_token → 呼叫帳號串接裡的 SignIn／sign_in!／sign_in → 換發 session。用到的共用函式也跟 Google 篇相同（對照表在 Google 篇第 3 節開頭）。 Channel ID、Channel secret、Callback URL 從環境變數讀（LINE_CHANNEL_ID、LINE_CHANNEL_SECRET、LINE_REDIRECT_URI）。 跟 Google 不一樣的地方標了 ★：

  • ★ LINE 的錯誤碼是大寫：使用者按取消時 callback 收到的是 error=ACCESS_DENIED
  • ★ 驗 ID token 用的是 LINE 專用的函式（第 5 節），不是通用的 OIDC verifier
  • ★ ID token 裡沒有 email_verified，一律當成未驗證
  • ★ 有帶 bot_prompt 的話，callback 的 query 會多一個 friendship_status_changed

  • Ruby on Rails

用 x/oauth2 處理授權網址與換 token， 驗 ID token 用 golang-jwt（見第 5 節）。 端點與 JWKS 網址跟 Google 一樣從 discovery document 讀，所以測試時也能把 issuer 指向假的 IdP； 只是讀 discovery 借用了 go-oidc，驗 ID token 卻不能交給它（它不支援網頁登入用的 HS256）。

internal/authline/line.go
package authline

import (
	"context"
	"database/sql"
	"log"
	"net/http"
	"os"

	"github.com/coreos/go-oidc/v3/oidc"
	"github.com/gorilla/sessions"
	"golang.org/x/oauth2"

	"example.com/app/internal/accounts"
	"example.com/app/internal/web"
)

var (
	channelID     = os.Getenv("LINE_CHANNEL_ID")
	channelSecret = os.Getenv("LINE_CHANNEL_SECRET")

	issuer    string // Init 設定；ID token 的 iss 必須等於它
	oauthConf *oauth2.Config
	// 只放 OAuth 交易用的短命資料（state、nonce、code_verifier），跟登入用的 session 分開
	txStore = sessions.NewCookieStore([]byte(os.Getenv("SESSION_SECRET")))
)

// Init 在程式啟動時呼叫一次，issuer 傳 "https://access.line.me"。
// 做成參數的理由跟 Google 篇相同：測試時能指向假的 IdP
func Init(ctx context.Context, issuerURL string) error {
	// 只拿 discovery 裡的端點；ID token 用第 5 節的函式驗
	provider, err := oidc.NewProvider(ctx, issuerURL)
	if err != nil {
		return err
	}
	var meta struct {
		JWKSURI string `json:"jwks_uri"`
	}
	if err := provider.Claims(&meta); err != nil {
		return err
	}

	endpoint := provider.Endpoint()
	endpoint.AuthStyle = oauth2.AuthStyleInParams // client_id／client_secret 放在 body
	oauthConf = &oauth2.Config{
		ClientID:     channelID,
		ClientSecret: channelSecret,
		RedirectURL:  os.Getenv("LINE_REDIRECT_URI"), // 必須跟 LINE Login 頁籤登記的 Callback URL 相同
		Endpoint:     endpoint,
		Scopes:       []string{"profile", "openid", "email"},
	}
	issuer = issuerURL
	return initJWKS(ctx, meta.JWKSURI) // 第 5 節
}

// ── 第一步：把使用者導去 LINE ────────────────────────────────
func Start(w http.ResponseWriter, r *http.Request) {
	state := web.RandomToken()
	nonce := web.RandomToken()
	codeVerifier := oauth2.GenerateVerifier()

	tx, _ := txStore.New(r, "line_tx")
	tx.Values["state"] = state
	tx.Values["nonce"] = nonce
	tx.Values["code_verifier"] = codeVerifier
	tx.Options = &sessions.Options{
		Path: "/", HttpOnly: true, Secure: true, MaxAge: 600,
		SameSite: http.SameSiteLaxMode,
	}
	if err := tx.Save(r, w); err != nil {
		http.Error(w, "無法建立登入工作階段", http.StatusInternalServerError)
		return
	}

	http.Redirect(w, r, oauthConf.AuthCodeURL(state,
		oauth2.SetAuthURLParam("nonce", nonce),
		oauth2.S256ChallengeOption(codeVerifier),
		// oauth2.SetAuthURLParam("bot_prompt", "normal"), // 想順便邀請加官方帳號好友才加
	), http.StatusFound)
}

// ── 第二步：LINE 導回來 ──────────────────────────────────────
func Callback(db *sql.DB) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		ctx := r.Context()
		q := r.URL.Query()

		tx, _ := txStore.Get(r, "line_tx")
		state, _ := tx.Values["state"].(string)
		nonce, _ := tx.Values["nonce"].(string)
		codeVerifier, _ := tx.Values["code_verifier"].(string)
		tx.Options.MaxAge = -1 // 不論成敗都作廢，避免重放
		_ = tx.Save(r, w)

		// ★ LINE 的錯誤碼是大寫：使用者按取消時是 error=ACCESS_DENIED
		if e := q.Get("error"); e != "" {
			log.Printf("line 授權失敗：%s %s", e, q.Get("error_description"))
			http.Redirect(w, r, "/login?error=cancelled", http.StatusSeeOther)
			return
		}
		if !web.SameToken(state, q.Get("state")) {
			http.Error(w, "state 不符", http.StatusBadRequest)
			return
		}

		tok, err := oauthConf.Exchange(ctx, q.Get("code"), oauth2.VerifierOption(codeVerifier))
		if err != nil {
			log.Printf("line token 兌換失敗：%v", err)
			http.Error(w, "登入失敗", http.StatusBadGateway)
			return
		}
		rawIDToken, ok := tok.Extra("id_token").(string)
		if !ok {
			http.Error(w, "回應缺少 id_token（scope 有帶 openid 嗎？）", http.StatusBadGateway)
			return
		}
		// ★ 網頁流程是 HS256，用第 5 節的專用函式驗（nonce 也在裡面比）
		claims, err := VerifyWebIDToken(rawIDToken, nonce)
		if err != nil {
			log.Printf("line id_token 驗證失敗：%v", err)
			http.Error(w, "登入失敗", http.StatusUnauthorized)
			return
		}
		// ★ 有帶 bot_prompt 時，q.Get("friendship_status_changed") == "true"
		//   代表這次登入順便加了好友（或解除封鎖）

		user, err := accounts.SignIn(ctx, db, lineProfile(claims), web.CurrentUserID(r))
		if err != nil {
			web.SignInErrorRedirect(w, r, err)
			return
		}
		if err := web.StartSession(w, r, user.ID); err != nil {
			log.Printf("無法建立 session：%v", err)
			http.Error(w, "登入失敗", http.StatusInternalServerError)
			return
		}
		http.Redirect(w, r, "/", http.StatusSeeOther)
	}
}

// LIFF 的登入端點也用這個（LIFF 篇第 6 節）
func lineProfile(c *LineClaims) accounts.ProfileFromProvider {
	return accounts.ProfileFromProvider{
		Provider:       "line",
		ProviderUserID: c.Subject, // ★ 使用者的唯一鍵，不要用 email
		Email:          c.Email,
		EmailVerified:  false, // ★ LINE 的 ID token 沒有 email_verified（見 2.1）
		DisplayName:    c.Name,
		AvatarURL:      c.Picture,
	}
}

class Auth::LineController < ApplicationController
  # liff 只收 JSON（見 LIFF 篇第 6 節）；callback 是 GET，Rails 的 CSRF 檢查本來就不管
  skip_before_action :verify_authenticity_token, only: :liff

  def start
    state         = SecureRandom.urlsafe_base64(32)
    nonce         = SecureRandom.urlsafe_base64(32)
    code_verifier = SecureRandom.urlsafe_base64(32)
    session[:line_tx] = { "state" => state, "nonce" => nonce,
                          "code_verifier" => code_verifier }

    query = {
      response_type: "code",
      client_id: LineOIDC::CHANNEL_ID,
      redirect_uri: LineOIDC::REDIRECT_URI,
      state: state,
      nonce: nonce,
      scope: "profile openid email",
      code_challenge: Base64.urlsafe_encode64(
        Digest::SHA256.digest(code_verifier), padding: false,
      ),
      code_challenge_method: "S256",
      # bot_prompt: "normal",   # 想順便邀請加官方帳號好友才加
    }
    redirect_to "#{LineOIDC::AUTH_URL}?#{query.to_query}", allow_other_host: true
  end

  def callback
    saved = session.delete(:line_tx) # 不論成敗都作廢，避免重放

    # ★ LINE 的錯誤碼是大寫：使用者按取消時是 ACCESS_DENIED
    if params[:error].present?
      Rails.logger.info("line 授權失敗：#{params[:error]} #{params[:error_description]}")
      return redirect_to(login_path, alert: "已取消登入")
    end

    unless saved && ActiveSupport::SecurityUtils.secure_compare(
      saved["state"], params[:state].to_s
    )
      return head :bad_request
    end

    tokens = exchange_code(params[:code].to_s, saved["code_verifier"])
    # ★ 網頁流程是 HS256，用第 5 節的專用函式驗（nonce 也在裡面比）
    claims = LineOIDC.verify_web_id_token(tokens["id_token"], saved["nonce"])
    # ★ 有帶 bot_prompt 時，params[:friendship_status_changed] == "true"
    #   代表這次登入順便加了好友（或解除封鎖）

    user = Identity.sign_in!(line_profile(claims), current_user: current_user)
    start_session(user)                    # 換發 session id，防 session fixation
    redirect_to root_path
  rescue Identity::SignInError => e
    redirect_sign_in_error(e)
  rescue LineOIDC::TokenExchangeError
    head :bad_gateway
  rescue JWT::DecodeError => e
    Rails.logger.warn("line id_token 驗證失敗：#{e.message}")
    head :unauthorized
  end

  private

  # LIFF 的登入端點也用這個（LIFF 篇第 6 節）
  def line_profile(claims)
    {
      provider: "line",
      provider_user_id: claims["sub"],   # ★ 唯一鍵，不要用 email
      email: claims["email"],
      email_verified: false,             # ★ LINE 的 ID token 沒有 email_verified（見 2.1）
      email_is_relay: false,
      display_name: claims["name"],
      avatar_url: claims["picture"],
    }
  end

  def exchange_code(code, code_verifier)
    res = Net::HTTP.post_form(URI(LineOIDC::TOKEN_URL), {
      "grant_type"    => "authorization_code",
      "code"          => code,
      "redirect_uri"  => LineOIDC::REDIRECT_URI, # 必須與第一步相同
      "client_id"     => LineOIDC::CHANNEL_ID,
      "client_secret" => LineOIDC::CHANNEL_SECRET,
      "code_verifier" => code_verifier,
    })
    unless res.is_a?(Net::HTTPSuccess)
      Rails.logger.error("line token 兌換失敗：#{res.body}")
      raise LineOIDC::TokenExchangeError
    end
    JSON.parse(res.body)
  end
end

        # "bot_prompt": "normal",   # 想順便邀請加官方帳號好友才加
    }

# ── 第二步：LINE 導回來 ──────────────────────────────────────
@router.get("/auth/line/callback")
async def callback(
    request: Request,
    code: str | None = None,
    state: str | None = None,
    error: str | None = None,
    error_description: str | None = None,
    friendship_status_changed: str | None = None,
    db: Session = Depends(get_db),
):
    saved = request.session.pop("line_tx", None)  # 不論成敗都作廢

    # ★ LINE 的錯誤碼是大寫：使用者按取消時是 ACCESS_DENIED
    if error:
        log.info("line 授權失敗：%s %s", error, error_description)
        return RedirectResponse("/login?error=cancelled", status_code=303)
    # compare_digest 收 str 時遇到非 ASCII 會丟 TypeError（變成 500），一律比 bytes
    if not saved or not secrets.compare_digest(
        saved["state"].encode(), (state or "").encode()
    ):
        raise HTTPException(400, "state 不符")
    if not code:
        raise HTTPException(400, "缺少 code")

    tokens = await exchange_code(code, saved["code_verifier"])
    try:
        # ★ 網頁流程是 HS256，用第 5 節的專用函式驗（nonce 也在裡面比）
        claims = verify_web_id_token(tokens["id_token"], saved["nonce"])
    except jwt.PyJWTError as exc:
        log.warning("line id_token 驗證失敗：%s", exc)
        raise HTTPException(401, "登入失敗") from exc
    # ★ 有帶 bot_prompt 時，friendship_status_changed == "true"
    #   代表這次登入順便加了好友（或解除封鎖）

    try:
        user = sign_in(db, line_profile(claims),
                       current_user=get_current_user(request, db))
    except SignInError as exc:
        return sign_in_error_redirect(exc)

    start_session(request, user)  # 換發 session，防 session fixation
    return RedirectResponse("/", status_code=303)


# LIFF 的登入端點也用這個（LIFF 篇第 6 節）
def line_profile(claims: dict) -> ProfileFromProvider:
    return ProfileFromProvider(
        provider="line",
        provider_user_id=claims["sub"],  # ★ 唯一鍵，不要用 email
        email=claims.get("email"),
        email_verified=False,  # ★ LINE 的 ID token 沒有 email_verified（見 2.1）
        display_name=claims.get("name"),
        avatar_url=claims.get("picture"),
    )


async def exchange_code(code: str, code_verifier: str) -> dict:
    async with httpx.AsyncClient(timeout=10) as client:
        res = await client.post(TOKEN_URL, data={
            "grant_type": "authorization_code",
            "code": code,
            "redirect_uri": REDIRECT_URI,  # 必須與第一步相同
            "client_id": CHANNEL_ID,
            "client_secret": CHANNEL_SECRET,
            "code_verifier": code_verifier,
        })
    if res.status_code != 200:
        log.error("line token 兌換失敗：%s", res.text)
        raise HTTPException(502, "登入失敗")
    return res.json()

5. ID token 有兩種簽章演算法​

這是 LINE 最容易卡住的地方：

ID token 來源演算法用什麼驗有沒有你給的 nonce
網頁登入（授權碼流程換來的）HS256Channel secret（對稱金鑰）有（你在授權請求帶的）
LIFF、原生 App／LINE SDKES256JWKS 上對應 kid 的公鑰沒有（授權請求是 SDK 自己發的）

所以如果你只照著一般 OIDC 的教學寫「去 JWKS 抓公鑰驗簽」，網頁登入會一直失敗， 而錯誤訊息通常只有「signature verification failed」或「unexpected algorithm」，完全不會提示你演算法不同。

反過來，每個入口其實都知道自己收的是哪一種：網頁 callback 只會收到 HS256， LIFF 的登入端點只會收到 ES256。所以下面寫成兩個函式，各自只接受一種演算法， 不去讀 token header 裡的 alg 來決定怎麼驗 —— 「讀 header 的 alg 再原封不動交給驗證函式」 正是 alg confusion 攻擊的入口（攻擊者把 alg 改成 none，或拿公開的 JWKS 公鑰當 HMAC 密鑰偽造簽章）， 細節見後端驗證第 2 節。

package authline

import (
	"context"
	"errors"
	"time"

	"github.com/MicahParks/keyfunc/v3"
	"github.com/golang-jwt/jwt/v5"

	"example.com/app/internal/web"

var lineJWKS keyfunc.Keyfunc

// initJWKS 由第 4 節的 Init 呼叫一次，jwksURL 來自 discovery。
// keyfunc 預設每小時在背景更新一次；遇到沒看過的 kid 會重抓，但五分鐘內最多一次
func initJWKS(ctx context.Context, jwksURL string) (err error) {
	lineJWKS, err = keyfunc.NewDefaultCtx(ctx, []string{jwksURL})
	return err
}

type LineClaims struct {
	jwt.RegisteredClaims
	Nonce   string   `json:"nonce"`
	AMR     []string `json:"amr"`
	Name    string   `json:"name"`
	Picture string   `json:"picture"`
	Email   string   `json:"email"`
}

// ★ 每個入口只允許一種演算法，白名單裡只放那一種
func parserOptions(alg string) []jwt.ParserOption {
	return []jwt.ParserOption{
		jwt.WithValidMethods([]string{alg}),
		jwt.WithIssuer(issuer),
		// LIFF app 掛在別的 LINE Login channel 的話，這裡要換成那個 channel 的 ID
		jwt.WithAudience(channelID),
		jwt.WithLeeway(60 * time.Second),
		jwt.WithExpirationRequired(),
		jwt.WithIssuedAt(),
	}
}

// VerifyWebIDToken 驗網頁登入（授權碼流程）拿到的 ID token：HS256，金鑰是 channel secret。
func VerifyWebIDToken(raw, expectedNonce string) (*LineClaims, error) {
	claims := &LineClaims{}
	_, err := jwt.ParseWithClaims(raw, claims,
		func(*jwt.Token) (any, error) { return []byte(channelSecret), nil },
		parserOptions(jwt.SigningMethodHS256.Alg())...,
	)
	if err != nil {
		return nil, err
	}
	if claims.Subject == "" {
		return nil, errors.New("缺少 sub")
	}
	if !web.SameToken(expectedNonce, claims.Nonce) {
		return nil, errors.New("nonce 不符")
	}
	return claims, nil
}

// VerifyLIFFIDToken 驗 liff.getIDToken() 拿到的 ID token：ES256，公鑰從 JWKS 來。
// 這種 token 沒有你能指定的 nonce，所以不比 nonce（見 LIFF 篇第 6 節）。
func VerifyLIFFIDToken(raw string) (*LineClaims, error) {
	claims := &LineClaims{}
	_, err := jwt.ParseWithClaims(raw, claims, lineJWKS.Keyfunc,
		parserOptions(jwt.SigningMethodES256.Alg())...,
	)
	if err != nil {
		return nil, err
	}
	if claims.Subject == "" {
		return nil, errors.New("缺少 sub")
	}
	return claims, nil
}

from jwt import PyJWKClient

# PyJWKClient 內建快取與「遇到新 kid 重抓」，建立一次重複用（見後端驗證第 3 節）
jwk_client = PyJWKClient("https://api.line.me/oauth2/v2.1/certs")

_COMMON = dict(
    # LIFF app 掛在別的 LINE Login channel 的話，這裡要換成那個 channel 的 ID
    audience=CHANNEL_ID,
    issuer=ISSUER,
    leeway=60,
    options={"require": ["exp", "iat", "sub", "aud", "iss"]},
)


def verify_web_id_token(id_token: str, expected_nonce: str) -> dict:
    """網頁登入（授權碼流程）：HS256，channel secret 當對稱金鑰。"""
    claims = jwt.decode(id_token, CHANNEL_SECRET, algorithms=["HS256"], **_COMMON)
    nonce = str(claims.get("nonce") or "")
    # compare_digest 收 str 時遇到非 ASCII 會丟 TypeError，一律比 bytes
    if not nonce or not secrets.compare_digest(nonce.encode(), expected_nonce.encode()):
        raise jwt.InvalidTokenError("nonce 不符")
    return claims


def verify_liff_id_token(id_token: str) -> dict:
    """liff.getIDToken() 拿到的：ES256，公鑰從 JWKS 來；沒有你能指定的 nonce（見 LIFF 篇第 6 節）。"""
    key = jwk_client.get_signing_key_from_jwt(id_token)
    return jwt.decode(id_token, key.key, algorithms=["ES256"], **_COMMON)

5.1 偷懶但安全的替代方案：用 LINE 的 verify 端點​

不想自己處理兩種演算法的話，LINE 提供一個伺服器端端點幫你驗，兩種來源都能用：

curl -X POST https://api.line.me/oauth2/v2.1/verify \
  --data-urlencode "id_token=eyJhbGciOi…" \
  --data-urlencode "client_id=你的 Channel ID" \
  --data-urlencode "nonce=你這次的 nonce"   # 網頁流程才帶；LIFF 的 token 不要帶

驗過會回 200 與 claims（iss、sub、aud、exp、iat、name、picture、email…）； 驗不過回 400，body 是 {"error": "invalid_request", "error_description": "…"}， error_description 會直接說原因：

error_description意思
Invalid IdToken.格式錯或簽章不對
Invalid IdToken Issuer.iss 不是 https://access.line.me
IdToken expired.過期了（LIFF 的 ID token 只有一小時，見 LIFF 篇第 6 節）
Invalid IdToken Audience.aud 跟你帶的 client_id 不同 —— LIFF 的話要帶LIFF app 所在的 LINE Login channel 的 ID
Invalid IdToken Nonce.nonce 不符

取捨：省事、不會寫錯，但每次登入多一次對外的 HTTP 往返， 而且 LINE 那端故障時你的登入就掛了。流量小的站用它沒問題；量大的話自己驗比較穩。 測試的時候也會多一個要 mock 的外部端點，見測試與 CI/CD。

6. LINE 特有的行為​

6.1 自動登入​

使用者的手機已經登入 LINE App 時，從下面兩種瀏覽器打開授權網址會自動登入 —— 不顯示登入畫面、也不顯示確認畫面（如果之前已經同意過）：

  • LINE 的內建瀏覽器（在聊天室裡點連結開的那個）
  • 之前用來做過 LINE Login 的外部瀏覽器

自動登入不能用的時候，如果這個瀏覽器之前登入過 LINE（access.line.me 上有 cookie）， 會顯示「以 ○○ 繼續」的 SSO 確認畫面；兩者都不行才是 email／QR code 登入。

幾個要知道的限制：

  • LINE 電腦版沒有自動登入；無痕模式下自動登入可能失敗
  • 想讓使用者看到登入畫面（例如要讓他換帳號）：帶 disable_auto_login=true（改走 SSO 或 email 登入）， 或帶 prompt=login（就算已登入也要重新驗證）
  • ID token 的 amr 會告訴你這次是怎麼登入的：lineautologin、linesso、lineqr、pwd、mfa

6.2 bot_prompt：順便加官方帳號好友​

先在 LINE Login channel 的 Basic settings 頁籤 → Linked LINE Official Account → Edit， 選要連結的官方帳號。條件是：

  • 官方帳號的 Messaging API channel 跟這個 LINE Login channel 在同一個 Provider 底下
  • 你同時是這個 LINE Login channel 與那個官方帳號的管理員
  • 一個 LINE Login channel 只能連結一個官方帳號

之後授權請求帶 bot_prompt=normal（同意畫面上多一個加好友的選項）或 bot_prompt=aggressive（同意之後另開一頁問），使用者就能在登入的同時加好友。 已經是好友的人不會看到選項；封鎖中的人看到的是「解除封鎖」。

登入完成後，callback 的 query string 會多一個 friendship_status_changed（true／false）， 告訴你這次登入有沒有改變好友狀態。想知道「現在是不是好友」，用 access token （需要 profile scope）打 GET https://api.line.me/friendship/v1/status，回應裡的 friendFlag 就是。

tip

這是 LINE Login 相對其他供應商最大的實務價值 —— 登入與加好友一次完成， 之後就能用 Messaging API 推播給這個人。前提是兩個 channel 在同一個 Provider 底下。

6.3 登出與解除授權​

你的「登出」只登出你的站。 呼叫撤銷端點（POST /oauth2/v2.1/revoke，帶 access_token、client_id， App types 只有 Web app 的 channel 還要帶 client_secret）只會讓那一把 access token 失效， 不會讓使用者登出 LINE 本身，下次點登入通常還是會自動登入。

這對「共用電腦」的情境有影響。需要強制重新確認身分的話，下次授權請求帶 prompt=login。 （prompt=consent 只會重新顯示同意畫面，不會要求重新驗證身分。）

使用者刪除帳號、或解除跟 LINE 的綁定時，LINE 的開發規範「要求」你呼叫 deauthorize：

curl -X POST https://api.line.me/user/v1/deauthorize \
  -H 'Authorization: Bearer {channel access token}' \
  -H 'Content-Type: application/json' \
  -d '{"userAccessToken": "{這個使用者的 access token}"}'

它會撤銷使用者當初在同意畫面上給的權限（LINE App 裡「設定 → 帳號 → 已授權的應用程式」那一項會消失）。 要注意兩件事：

  • 它需要這個使用者的 access token（30 天有效，可以用 refresh token 續）， 所以要做這件事，登入時就得把 token 存下來；只存 sub 的話到時候做不到
  • Authorization 用的是 channel access token（v2.1 或 stateless 那兩種），不是使用者的 token

規範也要求在服務條款或解除綁定的按鈕旁邊寫明「解除後會通知 LY Corporation、並終止與 LINE App 的連結」。

7. LIFF：在 LINE 裡開的網頁​

在 LINE 裡面開啟的網頁用 LIFF SDK 登入：liff.init() 完成登入，前端把 ID token 交給後端， 後端用第 5 節的 VerifyLIFFIDToken／verify_liff_id_token 驗。 它的前端載入流程（深層連結的整頁重載、SPA 的初始化順序、在 LINE 以外的瀏覽器打開） 與後端端點自成一套，另寫成一篇：LIFF：在 LINE 裡開的網頁。

8. 常見錯誤​

症狀原因
停在 LINE 的錯誤頁（400 Bad Request），沒有導回 callbackclient_id 錯，或 redirect_uri 沒登記在 LINE Login 頁籤。這兩種錯誤 LINE 不會導回你的網站，你的 log 裡看不到
callback 收到 error=INVALID_SCOPEscope 裡沒有 profile 也沒有 openid；帶了 email 卻沒帶 openid；或用逗號分隔（要用空白）
callback 收到 error=ACCESS_DENIED使用者在同意畫面按了取消。注意 LINE 的錯誤碼是大寫
別人登入看到類似「This channel is now developing status」的訊息，只有自己能登Channel 還在 Developing，對方不是 Admin／Tester（見 2.2）
ID token 裡沒有 email沒申請 email 權限／申請未過／scope 沒帶 email／使用者不同意提供／該帳號根本沒有 email
LIFF 相關（liff.getIDToken() 回 null、深層連結打開都是首頁、IdToken expired.…）見 LIFF 篇第 9 節
自己驗簽一直失敗網頁流程的 ID token 是 HS256 用 channel secret 簽的，拿 JWKS 的公鑰去驗當然過不了；通用 OIDC 函式庫讀 discovery 只會接受 ES256
換了 Provider 之後老用戶都變新用戶LINE user ID 依 Provider 發，換了就是另一組 ID，Channel 也不能搬 Provider。只能事先規劃，或讓使用者在新的 channel 重新綁定
推播回 400、訊息只有 Failed to send messages最常見的是那個 user ID 屬於另一個 Provider（例如從別的環境複製過來的帳號資料），見常見錯誤 6.3
invalid_grantcode 用過了或過期了（10 分鐘）；兌換時的 redirect_uri 與授權時不同；或 code_verifier 跟 code_challenge 對不起來
