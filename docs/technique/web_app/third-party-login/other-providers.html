其他供應商與託管方案的取捨

這一篇回答兩個問題：Google／LINE／Apple 以外的供應商各有什麼要注意的，以及要不要乾脆用現成的函式庫或託管方案。 先讀：Google 篇與後端驗證第 4 節（加一家的成本取決於你有沒有收斂成同一個介面）。

1. 加一家新供應商要改什麼​

如果你照著後端驗證的做法， 把三家收斂成同一個 ProfileFromProvider，那加第四家只需要三件事：

  1. 到那家的 console 申請 client，登記 redirect URI
  2. 寫一個新的 start + callback（複製既有的，換掉端點與 scope）
  3. 在 identities.provider 允許的值裡加上新的字串

SignIn、資料表、session 全都不用動；測試只需要為新的 callback 補一組。 如果你發現要動，那通常代表供應商的特殊邏輯漏進了共用層，值得回頭重整。

2. 常見供應商速查​

供應商是 OIDC 嗎拿得到 email 嗎特別注意
Google✅✅見專篇
LINE✅要申請見專篇
Apple✅可能是轉寄信箱見專篇
GitHub❌ 純 OAuth 2.0要 user:email scope 並另外呼叫 API沒有 id_token，見 3.1
Facebook部分（見 3.2）email 權限要提供「資料刪除」的說明網址或回呼，見 3.2
Microsoft Entra ID✅有，但不能拿來當身分依據多租戶時要自己驗 iss／tid，見 3.3
Discord❌ 純 OAuth 2.0email scope要看 verified 欄位，未驗證的 email 不能拿來比對帳號
X（Twitter）❌要 users.email scope（後來才加的，申請條件以官方文件為準）很多舊教學寫「拿不到 email」，已經過時；唯一鍵用數字 id，不要用 username
Slack✅（Sign in with Slack）✅sub 是使用者 ID，只在同一個工作區內唯一 —— 唯一鍵要用 team_id + sub

3. 三家值得單獨講的​

3.1 GitHub：沒有 ID token​

GitHub 是純 OAuth 2.0，不是 OIDC —— 換完 token 你只會拿到 access_token， 沒有可以驗簽的 id_token。身分要自己去 API 問：

# ① 換 token（注意要帶 Accept，否則回的是 form-urlencoded 不是 JSON）
curl -X POST https://github.com/login/oauth/access_token \
  -H "Accept: application/json" \
  -d "client_id=…&client_secret=…&code=…&redirect_uri=…&code_verifier=…"

# ② 拿使用者資料
curl https://api.github.com/user \
  -H "Authorization: Bearer <access_token>" \
  -H "Accept: application/vnd.github+json"
warning

/user 回的 email 欄位經常是 null —— 使用者只要在 GitHub 設定裡把信箱設為私密， 那個欄位就是空的。要拿到 email 必須：

  1. 授權時帶 scope=user:email（讀公開的個人資料不需要任何 scope；read:user 是要讀非公開資料才需要）
  2. 另外呼叫 GET /user/emails
  3. 從清單裡挑 primary: true 而且 verified: true 的那一個

只挑 primary 不看 verified 是個安全問題 —— 未驗證的 email 不能拿去比對既有帳號。

另外 GitHub 的使用者唯一鍵要用 id（數字）而不是 login（帳號名稱） —— login 是可以改的，而且改掉之後別人可以註冊走你原本的名字。 這跟 OIDC 的「用 sub 不要用 email」是同一個道理。

兩個比較新的變化：

  • GitHub 從 2025 年 7 月起支援 PKCE（只接受 S256），OAuth App 和 GitHub App 都可以用。 它不是必填，但既然支援了就帶上 —— 做法跟其他家一樣，授權時送 code_challenge， 換 token 時送 code_verifier。
  • GitHub 官方比較推薦用 GitHub App 而不是 OAuth App 來做「以 GitHub 身分登入」。 兩者的登入流程幾乎一樣，差在 GitHub App 的使用者 token 預設 8 小時就過期、會附 refresh token， 而且權限是細項的而不是 scope。只是拿身分的話兩種都可以。

3.2 Facebook：OIDC 只有一半，還要處理資料刪除​

  • 一般的 Facebook 登入不是 OIDC。 網頁上走的是 OAuth 2.0 授權碼流程， 拿到 access token 之後再呼叫 Graph API（/me?fields=id,name,email）問身分； 沒有可以驗簽的 id_token，情況跟 GitHub 一樣。唯一鍵用 Graph API 回的 id （這個 ID 是「每個 App 各自一組」的，換一個 App 就對不上）。
  • iOS 上的 Limited Login 才會發 OIDC 的 token。 它回的是一段帶 nonce 的 JWT （SDK 裡叫 AuthenticationToken），可以用 Facebook 的 discovery document 與 JWKS 驗簽， 行為比較接近 Sign in with Apple；代價是拿不到可以呼叫 Graph API 的 access token。
  • 權限與審查。 新建立的消費者型 App 預設就有 email 與 public_profile 的進階存取， 基本登入通常不需要送 App Review；要其他權限才需要送審，而送審通過前只有 在 App 裡有角色的人（管理員、開發者、測試人員）拿得到。審查規則改得很頻繁，以 App Dashboard 上顯示的為準。
  • 資料刪除。 你必須提供資料刪除說明的網址，或是一個資料刪除回呼 （Data Deletion Callback，使用者從 Facebook 那邊要求刪除資料時通知你的伺服器端點）， 兩者擇一。回呼可以自動化處理，但不是唯一的選項。

3.3 Microsoft Entra ID：多租戶的 iss／tid 陷阱​

Entra ID（舊稱 Azure AD）用的是 v2.0 端點，網址裡有一段 tenant：

https://login.microsoftonline.com/{tenant}/oauth2/v2.0/authorize
{tenant}誰能登入
你的 tenant ID（GUID）或網域名稱只有你組織的成員
organizations任何組織的成員（公司／學校帳號）
consumers個人的 Microsoft 帳號
common以上全部
danger

用 common 或 organizations 時，只驗 aud 是不夠的。 任何組織的帳號都能登入， 包括攻擊者自己開的免費租戶。如果你的服務是「只給某間公司內部用」， 就必須額外驗證 tid（tenant ID）claim 是你允許的組織， 或者一開始就把端點指向你自己的 tenant ID。

這是多租戶 SaaS 很常見的權限提升路徑：以為選了「公司登入」， 實際上全世界的 Microsoft 帳號都能進來。

iss 也因此不是固定字串。common／organizations 的 discovery document 裡， issuer 是一個樣板：https://login.microsoftonline.com/{tenantid}/v2.0。 Microsoft 文件建議的驗法是：

  1. 確認 token 裡的 tid 是一個 GUID
  2. 把樣板裡的 {tenantid} 換成這個 tid，再跟 iss 完全比對
  3. 允許哪些 tid 是你自己的授權規則，跟第 2 步分開做

另外兩件事：

  • 唯一鍵用 sub（或 oid）加上 tid，不要只用 sub，更不要用 email。 sub 是「每個 App 各自一組」的；oid 則在同一個租戶內跨 App 一致。
  • email claim 不能拿來當身分依據。 Microsoft 自己的說法是它不保證正確、而且會變， 不要拿來做授權或存使用者資料的鍵 —— 租戶管理員可以把帳號的 email 設成任何字串 （2023 年被稱為「nOAuth」的帳號接管手法就是利用這一點）。 要拿 email 去比對既有帳號之前， 至少要確認網域擁有者已驗證（可選 claim xms_edov），保守的做法是乾脆不自動合併。

4. 現成的 OAuth 函式庫​

不想每一家都手刻 start／callback 的話：

  • Go
  • Ruby on Rails
  • Python
套件說明
golang.org/x/oauth2Go 團隊維護的 OAuth 2.0 用戶端（在 golang.org/x 底下，不是標準函式庫），內建常見供應商的端點設定，也有 PKCE 的輔助函式。本系列範例用的就是它
go-oidc加上 OIDC 的 discovery 與 ID token 驗證，跟 x/oauth2 搭配使用
goth一次支援數十家供應商，但抽象層比較厚，要客製時反而麻煩；更新頻率也比前兩個慢

建議：x/oauth2 + go-oidc。 它們薄、維護好，而且你看得懂每一步在做什麼。

套件說明
omniauth + 各家 strategyRails 生態的標準做法，omniauth-google-oauth2、omniauth-apple 等
omniauth-rails_csrf_protection讓 OmniAuth 的 request phase 使用 Rails 的 CSRF token。也可以不裝，改用一行設定（見下方）
jwt自己驗 ID token 時用。本系列範例用的就是它
danger

OmniAuth 2.0 起，request phase 預設只接受 POST，而且 POST 要帶 CSRF token。 網路上很多舊教學還在寫 link_to "/auth/google_oauth2" 這種 GET 連結 —— 那在 OmniAuth 2.x 會失敗，而且當初改成 POST 正是為了修補一個 CSRF 漏洞（CVE-2015-9284）。 不要用 allowed_request_methods 把 GET 打開來「解決」這個問題。

登入按鈕要改用 button_to（會送 POST 並帶 CSRF token），並讓 OmniAuth 認得 Rails 的 token。 OmniAuth 官方 wiki 目前的建議是直接設定，不必再裝額外的 gem：

config/initializers/omniauth.rb
OmniAuth.config.request_validation_phase =
  OmniAuth::AuthenticityTokenProtection.new(key: :_csrf_token)

裝 omniauth-rails_csrf_protection 也能達到同樣效果，它仍有在維護。

各家 strategy 的品質差異很大，維護狀況也不一 —— 同一家常有好幾個名字相近的 gem，有的已經好幾年沒更新（LINE 就是一例，選之前先看最近一次釋出的日期， 以及它是否支援 LINE Login v2.1 的 ID token）。 Apple 的 strategy 尤其要挑（client_secret 輪替、form_post 的處理常有問題）， 自己實作那一家反而比較可控。

套件說明
authlib最完整，支援 Flask／Django／FastAPI（Starlette），內建 OIDC 與 discovery
PyJWT只做 JWT 驗證。本系列範例用的就是它
python-social-auth老牌，供應商多，但抽象層厚

Authlib 的最小用法：

from authlib.integrations.starlette_client import OAuth

oauth = OAuth()
oauth.register(
    name="google",
    server_metadata_url="https://accounts.google.com/.well-known/openid-configuration",
    client_id=CLIENT_ID,
    client_secret=CLIENT_SECRET,
    client_kwargs={
        "scope": "openid email profile",   # 有 openid 才會自動產生並檢查 nonce
        "code_challenge_method": "S256",   # PKCE 預設沒開，要自己加
    },
)

@router.get("/auth/google")
async def start(request: Request):
    return await oauth.google.authorize_redirect(request, REDIRECT_URI)

@router.get("/auth/google/callback")
async def callback(request: Request):
    token = await oauth.google.authorize_access_token(request)  # 含 state、nonce 與 ID token 驗證
    claims = token["userinfo"]
    # …之後與手刻版本相同

Authlib 會幫你處理 state、nonce 與 ID token 驗證，但 PKCE 預設是關的， 要像上面那樣在 client_kwargs 加 code_challenge_method。 nonce 也只有在 scope 含 openid 時才會產生與檢查。 它把這些暫存在 Starlette 的 session 裡，所以 App 要掛 SessionMiddleware。 用了函式庫仍然要自己寫負面測試確認真的有在擋。

5. 要不要用現成方案​

前面整個系列教的是「自己實作」。但這不一定是對的選擇，這一節講什麼時候不該自己做。

方案你不用做的事代價
自己實作（本系列）—每家供應商的申請與維護、client_secret 輪替、測試
Auth0 / Clerk / WorkOS供應商整合、MFA、密碼重設、後台按月付費，使用者資料在別人那裡，遷出成本高
Firebase Auth / Supabase Auth同上，且與各自的 BaaS 整合好綁定該平台；自訂流程受限（Firebase 要接 SAML／自訂 OIDC 得升級到 Identity Platform 方案）
Keycloak / Zitadel（自架）供應商整合、使用者管理後台你要維運一套 Java（Keycloak）或 Go（Zitadel）服務加它的資料庫；兩者也都有託管版本
note

託管方案的價格、免費額度、方案內含的功能變動得很頻繁，這裡刻意不寫數字。 評估時以各家當下的定價頁為準，並特別看「月活躍使用者」怎麼計算、超過額度之後的單價， 以及 SAML／企業連線是不是另外收費。

選擇的判準，依重要性排序：

① 你有幾個需要共用登入的系統？ 只有一個網站 → 自己實作最單純。 三個以上的服務要 SSO → 用集中式的方案（託管或自架 Keycloak）會省下很多重複。

② 你需要哪些「登入以外」的功能？ MFA、密碼重設信、SCIM、企業版 SAML、後台管理介面 —— 這些自己做每一個都要好幾週。 需要兩個以上，就值得評估託管方案。

③ 使用者資料放在外面可以嗎？ 這是最難回頭的一個決定。個資、資料落地要求、以及「未來想遷出時要怎麼把密碼／身分搬走」 都要先想清楚。問供應商「能不能匯出」之前，先問「匯出的格式能不能直接用」。

④ 你的團隊有沒有人真的懂這一套？ 自己實作最大的風險不是寫不出來，是寫出來之後沒人維護 —— Apple 的 secret 過期、供應商改版、金鑰輪替，都需要有人看得懂在做什麼。

tip

一個實務上的中間路線：自己實作，但把它隔離乾淨。 照後端驗證那樣 收斂成一個 ProfileFromProvider 介面，之後要換成 Auth0 或 Keycloak 時， 你需要改的只有「產生 ProfileFromProvider 的那一層」， 帳號、session、權限全部不用動。

這比一開始就決定「自己做 vs 用別人」更重要 —— 讓那個決定可以後悔。
