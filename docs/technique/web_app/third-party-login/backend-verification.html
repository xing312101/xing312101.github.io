後端驗證 ID token 與 session 設計

不管前面用哪一家、走哪一種流程，最後都會收斂到同一件事： 後端拿到一段 ID token，要確認它可信，然後換成自己的 session。 這一篇只講這一段，因為它是最容易寫錯、而且寫錯了不會有任何錯誤訊息的地方。

先讀：OAuth 2.0 與 OIDC 基礎（ID token 的結構與各個 claim）。 第 5 節的 CurrentUserID／StartSession 是 Google、LINE、Apple 三篇的 callback 共用的函式。

1. 為什麼一定要在後端驗​

JWT 的前兩段是明碼的 Base64URL，任何人都能解開、改掉、再組回去。 只有第三段簽章能證明內容沒被動過。

所以下面這幾種寫法都是沒有驗證、或只驗了一半，等於讓任何人用任何身分登入：

  • Go
  • Ruby on Rails
  • Python
// ❌ 只解碼不驗簽
parser := jwt.NewParser()
token, _, _ := parser.ParseUnverified(raw, jwt.MapClaims{})

// ❌ 沒有限制演算法：用哪個演算法驗，變成由 token 自己的 header 決定。
// golang-jwt 會擋 alg: none，也會因為金鑰型別不符擋掉大部分 HS／RS 混用，
// 但那是函式庫替你擋的，不是你的程式在擋 —— 換個函式庫或 keyFunc 寫得寬鬆一點就破了
jwt.Parse(raw, keyFunc) // 少了 jwt.WithValidMethods([]string{"RS256"})
# ❌ 第三個參數 false = 不驗簽
payload, header = JWT.decode(id_token, nil, false)

# ❌ 演算法照 token 自己的 header 走 —— 等於讓攻擊者選演算法
_, header = JWT.decode(id_token, nil, false)
JWT.decode(id_token, key, true, algorithms: [header["alg"]])

# ❌ 以為有驗 aud：ruby-jwt 只有在 verify_aud: true 時才檢查，只給 aud: 會被靜默忽略
JWT.decode(id_token, key, true, algorithms: ["RS256"], aud: CLIENT_ID)
# ❌ 明講不要驗
jwt.decode(id_token, options={"verify_signature": False})

# ❌ 演算法照 token 自己的 header 走 —— 等於讓攻擊者選演算法
alg = jwt.get_unverified_header(id_token)["alg"]
jwt.decode(id_token, key, algorithms=[alg], audience=CLIENT_ID)

# ❌ 以為有驗 exp：PyJWT 只在 token 裡「有」exp 時才檢查，沒有 exp 的 token 會直接通過
jwt.decode(id_token, key, algorithms=["RS256"], audience=CLIENT_ID, issuer=ISSUER)
# ↑ 少了 options={"require": ["exp", "iat", "iss", "aud", "sub"]}
danger

永遠不要相信前端傳來的「使用者是誰」。 前端可以傳 {"email": "admin@example.com"}， 那只是一個字串。後端要收的永遠是原始的 ID token，並且自己走完下面七步。

2. 七個驗證步驟​

#檢查不做會怎樣
1簽章正確，用供應商 JWKS 裡對應 kid 的公鑰（LINE 網頁流程則是 channel secret 的 HMAC）任何人都能偽造身分
2alg 在你寫死的白名單內，白名單照供應商與流程決定，不能從 token 的 header 讀alg confusion：none、或拿公鑰當 HMAC 密鑰簽出一段「驗得過」的 token
3iss 等於該供應商的固定值（完全相符）接受別家（或攻擊者自架）簽的 token
4aud 包含你的 client_id（可能是陣列）；有 azp 的話它也要是你認得的 client_id別人的 App 拿到的 token 可以拿來登入你的站
5exp 還沒過，iat 不在未來（兩者都允許 60 秒以內的時鐘誤差）舊 token 可以無限重放
6nonce 等於你這次存的值 —— 你有送 nonce，token 裡就必須有；沒有也算失敗token 重放；只寫成「有帶才比」的話，拿一段沒有 nonce 的 token 就繞過了
7sub 存在，並用 (供應商, sub) 當使用者的鍵用 email 當鍵會導致帳號被接管（見帳號串接）；另外 sub 的範圍各家不同，見帳號串接 2.1

這七步對應 OIDC Core §3.1.3.7 的驗證規則。 規格裡還有幾條視情況才需要的：

  • azp：OIDC Core 只要求「有這個 claim 時照相關規範驗」。實務上在 Google 會碰到 —— Android App 用 web client ID 要 ID token 時，aud 是 web client ID、azp 是 Android client ID。 aud 如果是陣列、而且裡面有你不信任的受眾，規格要求必須拒絕。
  • iat 太舊：規格允許你拒絕「簽發太久以前」的 token；後端只接受剛登入完送來的 token 時，可以設一個上限（例如 10 分鐘）。
  • auth_time：授權請求帶了 max_age 時要檢查。
  • 簽章能不能省：規格允許「後端直接從 token endpoint（走 TLS）拿到的 ID token」用 TLS 驗證取代驗簽。 但前端或 App 送來的 token 一定要驗簽，兩條路共用同一個驗證函式、一律驗簽最不容易出錯。
  • 跟身分有關的附加 claim：email_verified（Apple 可能給字串 "true"）、Google Workspace 的 hd。 這些不是「token 可不可信」的問題，而是「這個 email 能不能拿來比對帳號」的問題，見帳號串接第 5 節。

各家的值對照：

issaudalg公鑰（JWKS）
Googlehttps://accounts.google.com 或 accounts.google.com（兩種都可能出現）OAuth client IDRS256https://www.googleapis.com/oauth2/v3/certs
LINEhttps://access.line.meChannel IDHS256（網頁登入，金鑰是 channel secret）／ES256（原生 App、LINE SDK、LIFF）ES256 用 https://api.line.me/oauth2/v2.1/certs；HS256 不需要
Applehttps://appleid.apple.comServices ID 或 Bundle IDRS256https://appleid.apple.com/auth/keys

第 2 步最容易在 LINE 上破功：網頁登入是 HS256、其他都是非對稱簽章，最省事的寫法是 「header 說什麼就用什麼驗」—— 那正是第 2 步要擋的東西（攻擊者把 alg 改成 none， 或拿公開的 JWKS 公鑰當 HMAC 密鑰簽一段 token）。不要讓同一個驗證器同時接受 HS256 與 RS256／ES256， 依流程（網頁 callback 還是 App 送來的）決定白名單，而不是依 token —— LINE 篇第 5 節就是把兩種寫成兩個各只收一種演算法的函式。

warning

每一個函式庫預設驗的東西都不一樣，而且都不含 nonce：

函式庫預設會驗要你明講才驗不驗
go-oidc Verifier簽章、alg（照 discovery）、iss、aud、exp——nonce（文件明寫由呼叫端負責）、azp
ruby-jwt JWT.decode簽章、alg（不給 algorithms 會直接拒絕）、exp（有的話）iss、aud：要帶 verify_iss: true／verify_aud: true，只給 iss:／aud: 會被靜默忽略nonce
PyJWT jwt.decode簽章、alg（必須給 algorithms）、exp／iat（有的話）、aud（token 有 aud 就一定要給 audience）iss：要給 issuer=；「exp 一定要存在」要 options={"require": [...]}nonce

所以 nonce 一定要自己比對，iss／aud 也要確認真的有開。三篇供應商文件的範例裡都有那幾行，別刪掉它。

3. JWKS 的快取與輪替​

供應商的簽章公鑰會定期輪替。JWKS 端點會同時列出好幾把金鑰， ID token 的 header 裡有 kid 指出用的是哪一把。

正確的行為是：

  1. 快取整份 JWKS，不要每次登入都去抓（量大時會被限流）。
  2. 快取多久：有 Cache-Control: max-age 就照它（Google 給的是幾小時）； 沒有的話自己定一個固定時間。Apple 與 LINE 的 JWKS 回的是 no-store（撰稿當下實測）， 照字面遵守就等於每次都重抓 —— 這時靠第 3 步兜底即可。
  3. 遇到快取裡沒有的 kid 時，重抓一次再判定失敗。
  4. 重抓要有節流（例如同一個 key set 最多 30 秒～5 分鐘重抓一次）， 否則收到一堆亂填 kid 的 token 就會變成你自己打自己的 DDoS。

這些邏輯函式庫多半做了一部分，但你必須把 client 建立在模組／類別層級，只建一次，而且要知道它少做了哪一塊：

  • Go
  • Ruby on Rails
  • Python
// ✅ 啟動時建一次（Google 篇的 Init 就是這樣）。go-oidc 的 RemoteKeySet 會把金鑰留在記憶體，
// 碰到驗不過的 kid 才重抓，同時進來的重抓會合併成一次；但它沒有「幾秒內最多一次」的節流
var verifier *oidc.IDTokenVerifier

func Init(ctx context.Context, issuer string) error {
	provider, err := oidc.NewProvider(ctx, issuer)
	if err != nil {
		return err
	}
	verifier = provider.Verifier(&oidc.Config{ClientID: clientID})
	return nil
}

// ❌ 每個請求都 NewProvider：等於每次登入都去抓 discovery + JWKS
# ✅ initializer 裡的 lambda，快取在 @cached_jwks。Google、LINE、Apple 三篇的 JWKS_LOADER 都是這一段
JWKS_LOADER = lambda do |options|
  # ruby-jwt 在 kid 找不到時會帶著 kid_not_found: true 再呼叫一次。
  # 不加時間限制的話，每一段亂填 kid 的 token 都會觸發一次重抓，所以最多 5 分鐘清一次
  if options[:kid_not_found] && @jwks_fetched_at.to_i < Time.now.to_i - 300
    @cached_jwks = nil
  end
  @cached_jwks ||= begin
    @jwks_fetched_at = Time.now.to_i
    JSON.parse(Net::HTTP.get(URI(JWKS_URL)), symbolize_names: true)
  end
end
# 使用：JWT.decode(id_token, nil, true, algorithms: ["RS256"], jwks: JWKS_LOADER, ...)

4. 把三家收斂成同一個介面​

三家的差異應該只存在於「驗證」這一層。驗完之後，交給 帳號串接的東西要長得一模一樣：

Google callback ─┐
LINE   callback ─┼─► ProfileFromProvider ─► SignIn() ─► session
Apple  callback ─┘     {provider, sub, email,
                        email_verified, email_is_relay,
                        display_name, avatar_url}

這樣做的好處很具體：

  • 加第四家供應商時，SignIn 完全不用動，只要多寫一個 callback。
  • 測試可以只針對 SignIn 寫，不用每一家都重測一次帳號邏輯 （見測試與 CI/CD）。
  • 「哪些欄位可以信」的判斷（email_verified、email_is_relay）集中在一個地方。

5. 驗完之後：發你自己的 session​

ID token 驗過了，接下來要把它換成你自己的登入狀態。兩種主流做法：

伺服器端 session（cookie 存 session id）自簽 JWT 存在 cookie
撤銷立即生效（刪掉伺服器端那筆）做不到，除非再加一個黑名單表
水平擴展需要共用的 session store（Redis 等）不需要
cookie 大小小較大，且會塞進每個請求
適合大多數網站無狀態 API、多服務共用

如果你在猶豫，選左邊。 「能立刻把某個使用者踢下線」這件事， 在出事的時候價值遠高於省下一個 Redis。

note

框架「預設」的 session 多半是右邊那種：Rails 的 :cookie_store 與 Starlette 的 SessionMiddleware 都是把整份 session 資料簽章後放在 cookie 裡，伺服器端沒有任何紀錄 —— 登出時清 cookie， 但一份先前被偷走的 cookie 在過期前照樣能用。要左邊的行為，Rails 改用 :cache_store（搭配 Redis 之類的共用快取）或 activerecord-session_store；Starlette 可以只在 cookie 裡放一個 session ID，每個請求去資料庫／Redis 查那一筆。

cookie 設定的最低標準：

屬性值為什麼
HttpOnly開JS 讀不到，XSS 偷不走 cookie 本身
Secure開只走 https
SameSiteLax擋掉跨站的 POST、<img>、fetch 帶 cookie。不要用 Strict：從 Google／LINE 導回你的 callback 是一次跨站導覽，Strict 的 cookie 不會被帶上，存在 session 裡的 state 就讀不到
名稱前綴__Host-瀏覽器只接受「有 Secure、Path=/、沒有 Domain」的 __Host- cookie，所以別的子網域（或被接管的子網域）沒辦法替你的網域塞一個 session cookie 進來 —— 這正是 session fixation 常見的手法

Apple 的 form_post 是跨站的 POST，連 Lax 的 cookie 都不會帶，要另外處理，見 Apple 篇第 4 節。

本系列各篇的 callback 共用下面兩個函式：目前是誰登入（沒登入時是 0／nil／None， callback 靠它分辨「這是登入還是綁定」），以及登入成功時開始 session（換發 session ID，理由見 5.1）。

  • Go
  • Ruby on Rails
  • Python
internal/web/session.go
package web

import (
	"context"
	"net/http"
	"time"
)

const sessionCookie = "__Host-sid" // __Host-：必須 Secure、Path=/、不設 Domain

// SessionStore 是伺服器端的 session 儲存（Redis、資料庫…）。刪掉一筆，那個人就立刻登出
type SessionStore interface {
	Create(ctx context.Context, userID int64, ttl time.Duration) (id string, err error) // id 要是高熵隨機值
	Lookup(ctx context.Context, id string) (userID int64, ok bool)
	Delete(ctx context.Context, id string) error
}

// Sessions 在程式啟動時設定一次
var Sessions SessionStore

// CurrentUserID 回傳目前登入者的 ID；沒登入回 0
func CurrentUserID(r *http.Request) int64 {
	c, err := r.Cookie(sessionCookie)
	if err != nil {
		return 0
	}
	uid, ok := Sessions.Lookup(r.Context(), c.Value)
	if !ok {
		return 0
	}
	return uid
}

// StartSession 在登入成功時呼叫：舊的 session 作廢、發一個新的 ID（防 session fixation）
func StartSession(w http.ResponseWriter, r *http.Request, userID int64) error {
	if c, err := r.Cookie(sessionCookie); err == nil {
		_ = Sessions.Delete(r.Context(), c.Value)
	}
	const ttl = 14 * 24 * time.Hour
	id, err := Sessions.Create(r.Context(), userID, ttl)
	if err != nil {
		return err
	}
	http.SetCookie(w, &http.Cookie{
		Name:     sessionCookie,
		Value:    id, // 伺服器端 session 的 ID，本身不帶任何資料
		Path:     "/",
		HttpOnly: true,                 // JS 讀不到，降低 XSS 的傷害
		Secure:   true,                 // 只走 https
		SameSite: http.SameSiteLaxMode, // 不能用 Strict：從供應商導回 callback 時不會帶
		MaxAge:   int(ttl.Seconds()),
	})
	return nil
}

app/controllers/application_controller.rb
class ApplicationController < ActionController::Base
  helper_method :current_user

  private

  # 目前登入者；沒登入是 nil
  def current_user
    return @current_user if defined?(@current_user)

    @current_user = session[:user_id] && User.find_by(id: session[:user_id])
  end

  # 登入成功時呼叫：reset_session 換發 session ID（防 session fixation）再寫入
  def start_session(user)
    reset_session
    session[:user_id] = user.id
    @current_user = user
  end
end

app/web.py
from fastapi import Request
from sqlalchemy.orm import Session

from .db import SessionLocal  # sessionmaker(bind=engine)
from .models import User


def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()


def get_current_user(request: Request, db: Session) -> User | None:
    """目前登入者；沒登入回 None。"""
    user_id = request.session.get("user_id")
    return db.get(User, user_id) if user_id else None


def start_session(request: Request, user: User) -> None:
    """登入成功時呼叫：先清空再寫入（防 session fixation）。
    OAuth 流程暫存在 session 裡的 state／nonce 要在這之前讀出來用完。"""
    request.session.clear()
    request.session["user_id"] = user.id
warning

不要把登入狀態放在 localStorage。 只要頁面上有任何一個 XSS （包括你引入的第三方腳本、廣告、分析工具被攻擊），token 就會被讀走。 httpOnly cookie 至少讓攻擊者偷不到憑證本身。

5.1 三件容易漏掉的事​

  • 登入成功時要換發新的 session ID（上面三個 StartSession／start_session 做的就是這件事：Go 刪掉舊的那筆、重新產生 ID；Rails 的 reset_session； Starlette 的 request.session.clear() 後再寫入）。session fixation 是這樣發生的： 攻擊者先設法讓受害者的瀏覽器帶著一個攻擊者知道的 session ID（例如從他控制的子網域塞 cookie 進來）， 受害者登入後，如果伺服器沿用那個 ID，攻擊者手上那個 ID 就變成已登入的。 換發 ID 讓攻擊者手上的舊 ID 作廢；上面的 __Host- 前綴則讓「從子網域塞 cookie」這一步本身做不到。 OAuth 流程裡存在 session 的 state／nonce／code_verifier 要在換發之前讀出來用完。
  • 登出要真的把伺服器端那筆刪掉，不是只清 cookie（簽章 cookie 型的 session 做不到這一點，見上面的說明）。
  • 登出只會登出你的站。 使用者仍然登入在 Google／LINE／Apple； 他下次按登入會直接通過。在共用電腦的情境要提醒使用者，或在授權請求加參數要求供應商再確認一次。 OIDC 標準的做法是 prompt=login（或 max_age=0），但各家支援不同： LINE 支援 prompt=login 與 max_age；Google 文件列出的 prompt 只有 none、consent、select_account， 能用的是 select_account（至少讓使用者再選一次帳號）。prompt=consent 只是重新顯示同意畫面，不是重新驗證身分。

5.2 原本的登入關卡要一起走一遍​

第三方登入通常是加在一個已經有密碼登入的系統上。密碼登入那條路上， 這些年可能已經長出好幾道關卡：帳號停用、必須先改初始密碼、密碼過期、 email 未驗證、MFA。新的登入方式如果沒有經過同一組關卡，只會有兩種結果，而且兩種都沒有錯誤訊息：

發生什麼事例子
繞過關卡應該擋，卻被第三方登入跳過了已停用的帳號用 Google 還登得進來；有 MFA 的帳號用 LINE 登入就不用 MFA
鎖死關卡還在，但只有密碼那條路知道怎麼過管理員代設密碼的人帶著「必須先改密碼」的旗標，改用 Google 登入：登入成功，但每一支 API 都 403。前端拿到的登入回應是第三方那條路組的、沒帶那個旗標，所以改密碼的畫面也不會跳出來 —— 使用者看到的是一個什麼都打不開、也不告訴他原因的網站

做法：

  • 登入成功之後的判斷寫成一個函式，兩條路都呼叫它，而不是在密碼登入的 handler 裡各寫各的
  • 每一道關卡都逐一決定對第三方登入要不要成立：停用一定要擋；「必須改初始密碼」通常可以在綁定成功時清掉 （他已經用另一種方式證明身分了，但密碼本身不要動）；MFA 要看你信不信供應商那一端的驗證
  • 測試時拿第三方登入發出來的憑證，真的去打一支需要登入的 API。只斷言「登入回 200」測不到上面那個鎖死 —— 登入那一步本來就是成功的

5.3 前端和後端不同網域時​

前端是一個 SPA（app.example.com）、API 在另一個子網域（api.example.com）， 或者本機開發時前端 dev server 在 :3000、後端在 :8000 —— 這種架構會多出兩個問題。

一、交易 cookie 要設在 redirect URI 的那個網域上。

/auth/start 會把 state、nonce、PKCE 的 verifier 存進一個短命的 cookie， 供應商之後導回 redirect URI 時，瀏覽器要把這個 cookie 帶回來。所以開始流程的那個網域， 必須就是 redirect URI 的網域。

最常見的錯法是登入按鈕寫成相對路徑 /api/auth/start，經過前端的代理轉到後端： 後端設的 cookie 落在前端的網域上，而供應商導回的是後端的網址 —— cookie 不在那裡，每一次都是「state 不符」或「登入逾時」。tsc、build、單元測試都擋不住這種錯。

按鈕要連後端的絕對網址。這個網址最好由後端提供（例如一支免登入的 GET /auth/config 回傳 { enabled, start_url }），順便讓沒設定供應商的環境不要顯示按鈕 —— 按了才發現 503，比沒有按鈕更糟。

二、callback 在後端，登入狀態要怎麼交給前端？

callback 驗完 ID token 之後要把使用者導回前端，這時候有兩條路：

情況做法
前後端同一個可註冊網域（app. 與 api. 都在 example.com 底下）首選：照舊用 httpOnly cookie。 後端在 callback 設 session cookie，前端 fetch 帶 credentials: "include"，後端的 CORS 要 Access-Control-Allow-Credentials: true 並列出確切的 origin（不能是 *）。兩個子網域是 same-site，SameSite=Lax 照樣會送
前端已經是用 bearer token（Authorization header）打 API，改不動用一次性交換碼，見下
danger

不要把 access token 或 session token 直接放在導回前端的網址上（?token=… 或 #token=…）。 網址會留在瀏覽器歷史、被 Referer 帶給頁面上的第三方資源、被分析工具收走、 寫進每一層代理的存取紀錄。token 的壽命有多長，這個洞就開多久。

一次性交換碼的流程：callback 產一組隨機碼、在伺服器端記下「這組碼 → 這個使用者」， 60 秒過期、只能用一次，把碼放在網址上導回前端；前端再把碼 POST 給後端換真正的 token。 網址上就算外洩，那組碼也早就用掉或過期了。

  • Ruby on Rails
  • Python

// POST /auth/exchange  {"code": "…"}
func exchange(w http.ResponseWriter, r *http.Request) {
	var body struct {
		Code string `json:"code"`
	}
	if err := json.NewDecoder(r.Body).Decode(&body); err != nil || body.Code == "" {
		http.Error(w, "缺少交換碼", http.StatusBadRequest)
		return
	}
	// GETDEL：讀出來的同時刪掉。同一組碼被送兩次，只有一次拿得到
	uid, err := rdb.GetDel(r.Context(), "login_code:"+body.Code).Result()
	if errors.Is(err, redis.Nil) {
		http.Error(w, "交換碼無效或已使用，請重新登入", http.StatusUnauthorized)
		return
	} else if err != nil {
		http.Error(w, "internal error", http.StatusInternalServerError)
		return
	}
	token, err := issueAccessToken(r.Context(), uid)
	if err != nil {
		http.Error(w, "internal error", http.StatusInternalServerError)
		return
	}
	json.NewEncoder(w).Encode(map[string]string{"access_token": token})
}

class ExchangeIn(BaseModel):
    code: str


@router.post("/auth/exchange")
async def exchange(body: ExchangeIn):
    # GETDEL：讀出來的同時刪掉。同一組碼被送兩次，只有一次拿得到
    user_id = await redis.getdel(f"login_code:{body.code}")
    if user_id is None:
        raise HTTPException(401, "交換碼無效或已使用，請重新登入")

三個版本都用 Redis 的 GETDEL（6.2 以上）：「讀」和「刪」如果分成兩步， 兩個同時進來的請求會都讀到、都換到 token。沒有 Redis 的話，用資料庫的 DELETE … RETURNING（PostgreSQL；MySQL 不支援 RETURNING）或 「UPDATE … SET used_at = now() WHERE code = ? AND used_at IS NULL AND expires_at > now()，看影響列數是不是 1」 一樣能做到 —— 後者 MySQL 與 PostgreSQL 都能用。

tip

前端的落點頁要防自己送兩次。 React 的 StrictMode 在開發模式下會把 effect 跑兩次， 第二次拿同一組碼去換，一定是 401 —— 於是開發時每次都「登入失敗」，正式 build 卻正常， 很容易被誤判成後端的問題。用一個 ref 記住「已經送過了」：

const sent = useRef(false);
useEffect(() => {
  if (sent.current) return;
  sent.current = true;
  const code = new URLSearchParams(location.search).get("c");
  if (code) exchange(code).then(saveToken).catch(showError);
}, []);

另外，換完之後用 history.replaceState 把網址上的碼拿掉，不要讓它留在歷史紀錄裡。

這條路的前端仍然是自己保管 token，上面「不要放 localStorage」那段的風險還在 —— 交換碼只是讓 token 不經過網址。能改成 cookie 的話，還是走第一條。

6. 供應商的 token 要不要存​

Token純登入要呼叫供應商 API
id_token驗完就丟驗完就丟
access_token不用存存，但要加密
refresh_token不用存 —— Apple 例外（刪帳號要用）存，加密，並處理撤銷

要存的話：

  • 加密後再存（用你的應用程式金鑰，不是明碼欄位）。
  • 不要寫進日誌。順手寫的「把整個 token 回應印出來」會把 refresh token 送進你的日誌系統， 而日誌通常保留很久、權限也比資料庫寬鬆。
  • 準備好「refresh 失敗」的處理路徑：使用者可能已經在供應商那邊撤銷授權， 這時要引導他重新登入，不是丟 500。

7. 怎麼確認這些驗證真的有在擋​

登入這段程式碼的特性是平常一直走成功路徑，錯誤路徑可能上線一年都沒被執行過。 所以要針對「應該失敗」的情況寫測試 —— 完整做法（含自己當 IdP 簽測試 token、 在 CI 上怎麼跑）見 測試與 CI/CD。
