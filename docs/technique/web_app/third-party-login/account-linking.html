帳號串接與資料表設計

登入功能真正需要設計的地方只有這裡。程式碼本身不難，難的是把「一個人、多個登入方式」 這件事的邊界條件想清楚 —— 而這些邊界條件出錯時，輕則使用者多了一個孤兒帳號， 重則有人能登入別人的帳號。

Google、LINE、Apple 三篇的 callback 驗完 ID token 之後，最後都呼叫這一篇第 4 節的 SignIn， 遇到錯誤時用第 6 節的函式回應。資料表與這兩個函式先看懂，各家的程式碼就只剩驗證那一段不同。

1. 為什麼要兩張表​

新手最常見的做法是在 users 上直接加欄位：

-- ❌ 不要這樣
CREATE TABLE users (
  id            BIGINT PRIMARY KEY,
  email         VARCHAR(255),
  google_sub    VARCHAR(255),
  line_user_id  VARCHAR(255),
  apple_sub     VARCHAR(255)
);

問題會在第四家供應商出現時爆發：每加一家就要改表、改所有查詢、改所有 NULL 判斷； 而且「這個人綁了幾種登入方式」「哪一種是最近用的」這種問題都很難回答。

正確的做法是把「身分」拆成獨立的一張表：

users                      identities
┌────────────────┐         ┌──────────────────────────────┐
│ id             │◄───┐    │ id                           │
│ email          │    └────│ user_id        (FK)          │
│ display_name   │  1    n │ provider          ─┐ 一起     │
│ avatar_url     │         │ provider_user_id  ─┘ UNIQUE   │
│ created_at     │         │ email                        │
└────────────────┘         │ email_is_relay               │
                           │ last_login_at                │
                           │ refresh_token_encrypted  ─┐   │
                           │ refresh_token_client_id  ─┘   │
                           │   （只有 Apple 需要）          │
                           └──────────────────────────────┘

兩條規則：

  1. 一個 user 可以有多個 identity —— 同一個人綁了 Google、LINE、Apple， 三種方式登進來都是同一個帳號、同一份資料。
  2. 一個 identity 只能屬於一個 user —— 由 UNIQUE (provider, provider_user_id) 保證。
tip

第 2 點一定要用資料庫的唯一約束，不要只在程式裡 if 一下。 兩個請求同時進來時，程式裡的「先查有沒有、沒有就新增」中間有空檔， 會造成同一個 Google 帳號長出兩筆 identity、對應到兩個不同的 user。 唯一索引是唯一能在並行下保證這件事的東西。

2. 建表​

MySQL 8
CREATE TABLE users (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  -- email 允許 NULL：LINE 使用者可能根本沒有 email
  email         VARCHAR(255)     NULL,
  display_name  VARCHAR(100)     NULL,
  avatar_url    VARCHAR(512)     NULL,
  created_at    DATETIME(6)      NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  updated_at    DATETIME(6)      NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
                                 ON UPDATE CURRENT_TIMESTAMP(6),
  UNIQUE KEY uq_users_email (email)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE identities (
  id               BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  user_id          BIGINT UNSIGNED NOT NULL,
  -- 'google' / 'line' / 'apple'
  provider         VARCHAR(32)     NOT NULL,
  -- ID token 裡的 sub。長度抓寬一點，各家格式差很多；
  -- 識別碼區分大小寫，不能用預設那個不分大小寫的定序（見下方警告）
  provider_user_id VARCHAR(255) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
  -- 這個身分回報的 email，跟 users.email 分開存（見第 5 節）
  email            VARCHAR(255)    NULL,
  -- Apple 的私密轉寄信箱要標記出來，它不能拿來比對身分
  email_is_relay   BOOLEAN         NOT NULL DEFAULT FALSE,
  last_login_at    DATETIME(6)     NULL,
  -- 只有 Apple 需要：刪帳號時呼叫 revoke 用的 refresh token（加密後的密文），
  -- 以及它是發給哪個 client_id 的（Services ID 或 Bundle ID，revoke 時要用同一個）
  refresh_token_encrypted VARBINARY(2048) NULL,
  refresh_token_client_id VARCHAR(255)    NULL,
  created_at       DATETIME(6)     NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  updated_at       DATETIME(6)     NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
                                   ON UPDATE CURRENT_TIMESTAMP(6),

  -- ★ 核心約束：同一個第三方身分只能綁在一個 user 上
  UNIQUE KEY uq_identities_provider_subject (provider, provider_user_id),
  -- 同一個 user 在同一家只能綁一組帳號（見下方說明，不要的話可以拿掉）
  UNIQUE KEY uq_identities_user_provider (user_id, provider),

  CONSTRAINT fk_identities_user FOREIGN KEY (user_id)
    REFERENCES users (id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

PostgreSQL 的寫法（只列 identities，users 同理）：

PostgreSQL
CREATE TABLE identities (
  id               BIGSERIAL PRIMARY KEY,
  user_id          BIGINT      NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  provider         TEXT        NOT NULL,
  provider_user_id TEXT        NOT NULL,
  email            TEXT,
  email_is_relay   BOOLEAN     NOT NULL DEFAULT FALSE,
  last_login_at    TIMESTAMPTZ,
  refresh_token_encrypted BYTEA,
  refresh_token_client_id TEXT,
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (provider, provider_user_id),
  UNIQUE (user_id, provider)
);

PostgreSQL 版要注意兩件 MySQL 版自動幫你做掉的事：

  • 沒有 ON UPDATE CURRENT_TIMESTAMP。updated_at 要靠 ORM 更新，或自己加 trigger。
  • TEXT 的唯一索引區分大小寫。users.email 如果要「Alice@example.com 與 alice@example.com 算同一個」， 改用 UNIQUE (lower(email)) 的表達式索引或 citext 型別，查詢時也要用同樣的正規化。

幾個設計決定：

決定理由
users.email 允許 NULLLINE 帳號可能沒有 email；Apple 使用者可能只給轉寄信箱
users.email 上仍然有 UNIQUE避免兩個帳號用同一個 email。注意 MySQL／PostgreSQL 的唯一索引都允許多個 NULL，所以「很多個沒 email 的使用者」不會互撞
identities.email 與 users.email 分開同一個人的 Google 信箱和 Apple 轉寄信箱不一樣，兩個都要留著；users.email 是「這個帳號對外的主要信箱」
UNIQUE (user_id, provider)表示「一個人只能綁一個 Google 帳號」。如果你希望使用者能同時綁公司和私人的兩個 Google 帳號，就把這個索引拿掉
ON DELETE CASCADE刪 user 時自動清掉 identity。注意它不會幫你呼叫 Apple 的 revoke —— 刪之前要先把 refresh_token_encrypted 讀出來撤銷，見第 8 節
refresh_token_encrypted／refresh_token_client_id只有 Apple 需要：刪帳號時要拿 refresh token 呼叫 revoke，而 revoke 的 client_id 必須跟當初發 token 的一致（網頁是 Services ID、App 是 Bundle ID）。存的是加密後的密文，見後端驗證第 6 節。純登入的 Google／LINE 留 NULL
warning

provider_user_id 不要用整數欄位。 Google 的 sub 目前是一長串數字（會超過 64 bit 整數的範圍， 而且官方只保證是「最長 255 個、區分大小寫的 ASCII 字元」）、LINE 是 U 加 32 個十六進位字元、 Apple 是帶點的字串。一律當字串存。

比對也要區分大小寫。 MySQL 8 的 utf8mb4 預設定序（utf8mb4_0900_ai_ci）不分大小寫、也不分重音， 這對 email 剛好合適，但對「區分大小寫的識別碼」是錯的：兩個只差大小寫的 sub 會被唯一索引當成同一個。 所以上面的 provider_user_id 指定了 COLLATE ascii_bin（識別碼都是 ASCII，也讓索引短一點）。 PostgreSQL 的 TEXT 預設就是區分大小寫的，不用改。

2.1 sub 的範圍各家不同​

規格只保證 sub 在同一個簽發者（iss）底下唯一、不會重新分配。至於「同一個人在你的不同 client 拿到的是不是同一個值」，各家的答案不一樣：

供應商sub 跟著什麼走同一個人在… 拿到同一個 sub拿到不同的 sub
GoogleGoogle 帳號本身任何 client、任何專案——
LINEProvider同一個 Provider 底下的所有 channel（LINE Login、Messaging API、LIFF）不同 Provider 底下的 channel
Apple開發者 Team同一個 Team 底下的所有 App 與 Services ID不同 Team（不同的 Apple Developer 帳號）

依據：Google 文件寫 sub 在所有 Google 帳號之間唯一、不會重用； LINE 文件寫 user ID「即使是同一個使用者，每個 Provider 發的值也不同」； Apple 文件稱它為 team-scoped identifier：sub 與私密轉寄信箱都是同一個開發者團隊共用， App 轉移到別的團隊時兩者都會變。 discovery document 的 subject_types_supported 也看得出來：Google 是 public，LINE 與 Apple 是 pairwise。

這在平常不會有感覺，出事是在搬資料的時候：

warning

把帳號資料從一個環境複製到另一個環境時，identities 不要跟著複製。

測試站和正式站常常用不同的 LINE Provider、不同的 Apple Team。 這時從正式站把 users 連同 identities 複製到測試站，LINE／Apple 那幾列的 provider_user_id 在測試站那個 Provider／Team 底下根本不存在（Google 那幾列碰巧對得上，但不要依賴這一點）。 而且沒有任何地方會報錯：

  • 登入時查不到 (provider, sub)，使用者被當成新人 —— 開放註冊的系統會多長一個帳號， 不開放註冊的系統則是「對不到人」
  • 拿那個 LINE user ID 去推播會失敗，而且錯誤訊息完全不會提到 Provider（見常見錯誤 6.3）
  • 一起複製過去的 Apple refresh_token_encrypted 是發給另一個環境的 client 的，刪帳號時拿去 revoke 也不會成功

正確的做法：複製 users，不複製 identities，讓每個人在該環境重新綁一次 （開放註冊的系統靠 email 撞號流程、不開放的系統靠綁定碼）。 同樣的理由，LINE 的 Provider 與 Apple 的 Team 一旦上線就不要換 —— 換了就是全體使用者重新綁定。 Apple 在 App 轉移給另一個團隊時有官方的使用者遷移流程（transfer identifier，60 天的轉移期，見 TN3159 與 Apple 篇）；LINE 換 Provider 則沒有對應的機制。

4. 登入時的決策流程​

拿到 ProfileFromProvider 之後，只有四種情況：

① (provider, sub) 已經存在？
      └─ 是 → 目前沒登入，或登入的就是它的主人 → 登入它的 user   【回訪】
              目前登入的是別人 → 明確報錯「已綁在別的帳號上」
              （不能直接切成那個帳號：使用者按的是「綁定」，不是「換帳號」）

② 目前瀏覽器已經登入中？
      └─ 是 → 這個 user 已經綁過同一家的另一個帳號 → 明確報錯
              否則把這個新身分綁到目前的 user 上          【綁定第二種登入方式】

③ email 已驗證，而且 users 裡有同樣的 email？
      └─ 是 → 依你的政策：自動合併，或要求先用原方式登入 【撞號，見第 5 節】

④ 以上皆非
      └─ 建立新的 user + identity                     【新註冊】
note

④ 不一定是「建帳號」。 內部系統、後台、只給員工或客戶用的系統， 誰能進來是管理員決定的 —— 這時④應該是拒絕，而③的「對不到」也很常見 （員工用私人信箱登入）。這種系統的做法見第 5.1 節。 下面的範例是開放註冊的版本。

internal/accounts/signin.go
package accounts

import (
	"context"
	"database/sql"
	"errors"
	"fmt"
)

// SignInError 是「使用者要知道、而且要做點什麼」的登入失敗。
// Code 給網址與程式判斷用，Message 給人看。呼叫端要把它翻成對的下一步（第 6 節），不要吞掉
type SignInError struct {
	Code    string
	Message string
}

func (e *SignInError) Error() string { return e.Message }

var (
	// 這個第三方帳號已經綁在別人身上
	ErrIdentityTaken = &SignInError{"identity_taken", "這個第三方帳號已經綁定在另一個使用者上"}
	// 目前的使用者已經綁過同一家的另一個帳號
	ErrProviderAlreadyLinked = &SignInError{"provider_already_linked", "你已經綁定過這一家的另一個帳號，請先解除綁定"}
	// email 撞到既有帳號，需要使用者先用原本的方式登入
	ErrEmailTaken = &SignInError{"email_taken", "這個 email 已經有帳號了，請先用原本的方式登入再綁定"}

	// errRaced 表示寫入時撞到唯一約束：並行的另一個請求剛寫進了同一筆。只在這個套件裡用
	errRaced = errors.New("並行登入衝突")
)

// SignIn 處理「第三方登入回來之後」的所有情況，回傳最終要登入的 user。
// currentUserID 傳 0 表示目前沒有登入中的使用者（呼叫端用 web.CurrentUserID(r) 取得，見後端驗證第 5 節）。
func SignIn(ctx context.Context, db *sql.DB, p ProfileFromProvider, currentUserID int64) (*User, error) {
	u, err := signInTx(ctx, db, p, currentUserID)
	if errors.Is(err, errRaced) {
		// 同一個人連按兩次、或兩個分頁同時登入：另一個請求剛寫進了同一個身分（或同一個 email 的 user）。
		// 上一個交易已經整個回滾（連同可能建到一半的 user），開一個新交易重走一次，這次 ① 或 ③ 就會查到它。
		// 不能在原本的交易裡重查：MySQL 預設的 REPEATABLE READ 看不到別的交易剛提交的列，
		// PostgreSQL 的交易在出錯之後整個作廢，後面的查詢都會失敗。
		u, err = signInTx(ctx, db, p, currentUserID)
	}
	if errors.Is(err, errRaced) {
		return nil, fmt.Errorf("登入時資料衝突，請再試一次：%w", err)
	}
	return u, err
}

func signInTx(ctx context.Context, db *sql.DB, p ProfileFromProvider, currentUserID int64) (*User, error) {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return nil, err
	}
	defer tx.Rollback() // 已 Commit 的話這裡是 no-op

	// ① 這個第三方身分已經存在？
	var userID int64
	err = tx.QueryRowContext(ctx,
		`SELECT user_id FROM identities WHERE provider = ? AND provider_user_id = ?`,
		p.Provider, p.ProviderUserID,
	).Scan(&userID)

	switch {
	case err == nil:
		// 已登入的人想「綁定」一個屬於別人的身分：報錯，不能順勢切換成那個帳號
		if currentUserID != 0 && userID != currentUserID {
			return nil, ErrIdentityTaken
		}
		// 回訪。順手更新這個身分回報的資料
		if _, err := tx.ExecContext(ctx,
			`UPDATE identities SET email = ?, email_is_relay = ?, last_login_at = NOW(6)
			 WHERE provider = ? AND provider_user_id = ?`,
			nullString(p.Email), p.EmailIsRelay, p.Provider, p.ProviderUserID,
		); err != nil {
			return nil, err
		}

	case errors.Is(err, sql.ErrNoRows):
		if currentUserID != 0 {
			// ② 目前已登入 → 綁到現有帳號。先確認他沒綁過同一家的另一個帳號，
			// 讓使用者拿到一句對的話，而不是一個籠統的「重複」
			var n int
			if err := tx.QueryRowContext(ctx,
				`SELECT COUNT(*) FROM identities WHERE user_id = ? AND provider = ?`,
				currentUserID, p.Provider,
			).Scan(&n); err != nil {
				return nil, err
			}
			if n > 0 {
				return nil, ErrProviderAlreadyLinked
			}
			userID = currentUserID
		} else {
			// ③ email 撞號
			existing, err := findUserIDByVerifiedEmail(ctx, tx, p)
			if err != nil {
				return nil, err
			}
			if existing != 0 {
				// 政策一（保守）：要求先用原方式登入。
				// 想改成自動合併（userID = existing），users 那邊的 email 也必須是驗證過的，見第 5 節
				return nil, ErrEmailTaken
			}
			// ④ 全新使用者
			userID, err = createUser(ctx, tx, p)
			if isDuplicateKey(err) {
				return nil, errRaced // 並行的請求剛用同一個 email 建好 user
			}
			if err != nil {
				return nil, err
			}
		}

		// 建立 identity。唯一約束是這裡真正的守門員
		if _, err := tx.ExecContext(ctx,
			`INSERT INTO identities
			   (user_id, provider, provider_user_id, email, email_is_relay, last_login_at)
			 VALUES (?, ?, ?, ?, ?, NOW(6))`,
			userID, p.Provider, p.ProviderUserID, nullString(p.Email), p.EmailIsRelay,
		); err != nil {
			if isDuplicateKey(err) {
				// 上面兩種情況都查過了還撞到，只可能是並行的請求剛寫進同一筆
				return nil, errRaced
			}
			return nil, fmt.Errorf("建立 identity 失敗：%w", err)
		}

	default:
		return nil, err
	}

	u, err := loadUser(ctx, tx, userID)
	if err != nil {
		return nil, err
	}
	if err := tx.Commit(); err != nil {
		return nil, err
	}
	return u, nil
}

// 只有「供應商已驗證過、而且不是轉寄信箱」的 email 才能拿來比對既有帳號
func findUserIDByVerifiedEmail(ctx context.Context, tx *sql.Tx, p ProfileFromProvider) (int64, error) {
	if p.Email == "" || !p.EmailVerified || p.EmailIsRelay {
		return 0, nil
	}
	var id int64
	err := tx.QueryRowContext(ctx, `SELECT id FROM users WHERE email = ?`, p.Email).Scan(&id)
	if errors.Is(err, sql.ErrNoRows) {
		return 0, nil
	}
	return id, err
}

class Identity < ApplicationRecord
  PROVIDERS = %w[google line apple].freeze

  belongs_to :user

  validates :provider, inclusion: { in: PROVIDERS }
  validates :provider_user_id, presence: true,
                               uniqueness: { scope: :provider }

  # 使用者要知道、而且要做點什麼的登入失敗。呼叫端用 rescue SignInError 一次接住三種（第 6 節）
  SignInError           = Class.new(StandardError)
  IdentityTaken         = Class.new(SignInError)  # 這個第三方帳號已經綁在別人身上
  ProviderAlreadyLinked = Class.new(SignInError)  # 目前的使用者已經綁過同一家的另一個帳號
  EmailTaken            = Class.new(SignInError)  # email 撞到既有帳號，要先用原本的方式登入

  # 處理「第三方登入回來之後」的所有情況，回傳最終要登入的 user。
  # current_user 傳 nil 表示目前沒有登入中的使用者。
  def self.sign_in!(profile, current_user: nil)
    attempts = 0
    begin
      attempts += 1
      transaction { sign_in_once!(profile, current_user) }
    rescue ActiveRecord::RecordNotUnique
      # 並行的另一個請求剛寫進同一個身分（或同一個 email 的 user）。
      # transaction 已經整個回滾，開新交易重走一次，這次 ① 或 ③ 就會查到它。
      # 不能在同一個交易裡重查：MySQL 的 REPEATABLE READ 看不到剛提交的列，
      # PostgreSQL 的交易在出錯之後整個作廢
      retry if attempts < 2
      raise
    end
  end

  def self.sign_in_once!(profile, current_user)
    # 不要加 lock：查無此列時，MySQL 的 SELECT … FOR UPDATE 會鎖住一段間隙，
    # 兩個並行的新使用者會各自拿到間隙鎖、再互相等對方而死結
    identity = find_by(
      provider: profile[:provider],
      provider_user_id: profile[:provider_user_id],
    )

    # ① 回訪
    if identity
      # 已登入的人想綁定一個屬於別人的身分：報錯，不能順勢切換成那個帳號
      raise IdentityTaken if current_user && identity.user_id != current_user.id

      identity.update!(
        email: profile[:email],
        email_is_relay: profile[:email_is_relay],
        last_login_at: Time.current,
      )
      return identity.user
    end

    user =
      if current_user
        # ② 已登入 → 綁到現有帳號，但同一家只能綁一組
        if current_user.identities.exists?(provider: profile[:provider])
          raise ProviderAlreadyLinked
        end

        current_user
      else
        # ③ email 撞號（撞到會 raise EmailTaken）／④ 全新使用者
        find_user_by_verified_email(profile) ||
          User.create!(
            email: usable_email(profile),
            display_name: profile[:display_name],
            avatar_url: profile[:avatar_url],
          )
      end

    create!(
      user:, provider: profile[:provider],
      provider_user_id: profile[:provider_user_id],
      email: profile[:email], email_is_relay: profile[:email_is_relay],
      last_login_at: Time.current,
    )
    user
  end

  # 只有「供應商已驗證過、而且不是轉寄信箱」的 email 才能拿來比對既有帳號
  def self.find_user_by_verified_email(profile)
    return nil unless usable_email(profile)

    existing = User.find_by(email: profile[:email])
    return nil unless existing

    # 政策一（保守）：要求先用原方式登入。
    # 想自動合併就 return existing —— 但 users 那邊的 email 也必須是驗證過的，見第 5 節
    raise EmailTaken
  end

  def self.usable_email(profile)
    return nil unless profile[:email].present?
    return nil unless profile[:email_verified]
    return nil if profile[:email_is_relay]

    profile[:email]
  end
end
app/accounts.py
from datetime import datetime, timezone

from sqlalchemy import select
from sqlalchemy.exc import IntegrityError
from sqlalchemy.orm import Session

from .models import Identity, User
from .schemas import ProfileFromProvider


class SignInError(Exception):
    """使用者要知道、而且要做點什麼的登入失敗。code 給網址與程式判斷用（第 6 節）。"""
    code = "sign_in_error"


class IdentityTaken(SignInError):
    """這個第三方帳號已經綁在別人身上。"""
    code = "identity_taken"


class ProviderAlreadyLinked(SignInError):
    """目前的使用者已經綁過同一家的另一個帳號。"""
    code = "provider_already_linked"


class EmailTaken(SignInError):
    """email 撞到既有帳號，要求使用者先用原本的方式登入。"""
    code = "email_taken"


def usable_email(p: ProfileFromProvider) -> str | None:
    """只有供應商已驗證過、而且不是轉寄信箱的 email 才能拿來比對身分。"""
    if not p.email or not p.email_verified or p.email_is_relay:
        return None
    return p.email


def sign_in(db: Session, p: ProfileFromProvider,
            current_user: User | None = None) -> User:
    """處理「第三方登入回來之後」的所有情況，回傳最終要登入的 user。"""
    try:
        return _sign_in_once(db, p, current_user)
    except IntegrityError:
        # 並行的另一個請求剛寫進同一個身分（或同一個 email 的 user）。
        # _sign_in_once 已經 rollback，開新交易重走一次，這次 ① 或 ③ 就會查到它。
        # 不能在同一個交易裡重查：MySQL 的 REPEATABLE READ 看不到剛提交的列，
        # PostgreSQL 的交易在出錯之後整個作廢。第二次還撞到就讓它往上丟
        return _sign_in_once(db, p, current_user)


def _sign_in_once(db: Session, p: ProfileFromProvider,
                  current_user: User | None) -> User:
    now = datetime.now(timezone.utc)
    try:
        # ① 這個第三方身分已經存在 → 回訪
        identity = db.scalar(
            select(Identity).where(
                Identity.provider == p.provider,
                Identity.provider_user_id == p.provider_user_id,
            )
        )
        if identity:
            # 已登入的人想綁定一個屬於別人的身分：報錯，不能順勢切換成那個帳號
            if current_user is not None and identity.user_id != current_user.id:
                raise IdentityTaken
            identity.email = p.email
            identity.email_is_relay = p.email_is_relay
            identity.last_login_at = now
            db.commit()
            return identity.user

        if current_user is not None:
            # ② 已登入 → 綁到現有帳號，但同一家只能綁一組
            already = db.scalar(
                select(Identity.id).where(
                    Identity.user_id == current_user.id,
                    Identity.provider == p.provider,
                )
            )
            if already is not None:
                raise ProviderAlreadyLinked
            user = current_user
        else:
            # ③ email 撞號
            email = usable_email(p)
            if email and db.scalar(select(User.id).where(User.email == email)):
                # 政策一（保守）：要求先用原方式登入。想自動合併就改用那個既有的 User ——
                # 但 users 那邊的 email 也必須是驗證過的，見第 5 節
                raise EmailTaken
            # ④ 全新使用者
            user = User(
                email=email,
                display_name=p.display_name,
                avatar_url=p.avatar_url,
            )
            db.add(user)
            db.flush()  # 取得 user.id；email 撞到並行建立的 user 時會在這裡丟 IntegrityError

        db.add(Identity(
            user_id=user.id,
            provider=p.provider,
            provider_user_id=p.provider_user_id,
            email=p.email,
            email_is_relay=p.email_is_relay,
            last_login_at=now,
        ))
        db.commit()
        return user
    except Exception:
        db.rollback()  # 不管哪一種失敗，都不留下建到一半的 user
        raise
tip

三個版本都把「撞到」分成三種情況，而不是統一翻成「資料重複」：

情況什麼時候知道回什麼
這個第三方帳號已經綁在別人身上① 查詢時「這個帳號已經綁定在其他使用者上」
自己已經綁過同一家的另一個帳號② 寫入前先查「你已經綁定過這一家的另一個帳號」
上面都查過了，寫入時還是撞到唯一約束INSERT 失敗時不是使用者的錯，是並行的請求剛寫了同一筆 → 回滾、開新交易重走一次

這張表上有兩個唯一索引、還有一個外鍵，如果全部翻成同一句話，使用者會拿到一個完全指錯方向的訊息。 而前兩種情況在寫入前先查，比事後解析錯誤訊息裡的索引名稱可靠 —— 索引名稱的格式各資料庫、各版本都不一樣。

5. email 撞號怎麼處理​

情境：使用者先用 Google 註冊了 alice@example.com， 半年後他改用 Apple 登入，而 Apple 回報的 email 也是 alice@example.com。 這是同一個人嗎？

很可能是，但你不能直接假設。 先看這個攻擊：

danger

預先註冊式的帳號接管（pre-account takeover）

  1. 攻擊者知道受害者的公司信箱 victim@example.com，用你網站的密碼註冊功能 建一個帳號，email 填 victim@example.com（他當然收不到驗證信，所以帳號是未驗證狀態）。
  2. 受害者之後用 Google 登入你的網站。你的程式看到「email 相同」， 就把這個 Google 身分綁到那個既有帳號上。
  3. 攻擊者用他當初設的密碼登入 —— 他進到的是受害者的帳號。

防法：只有「雙方都已驗證」的 email 才能自動合併。 供應商回報的 email_verified 要是 true，你這邊那個既有帳號的 email 也必須是已驗證的。 兩者有一邊沒驗證，就走下面的保守政策。

三種政策，依風險由高到低：

政策行為適合
自動合併email 已驗證就直接綁到既有帳號內部系統、低風險的服務
要求先登入（範例採用）回一個明確的訊息：「這個 email 已經有帳號了，請先用原本的方式登入，再到設定頁綁定」大部分情況的建議做法
完全分開永遠建新帳號，email 重複就報錯幾乎不適用，使用者會很困惑

Apple 的轉寄信箱永遠不要拿來比對。 abc123@privaterelay.appleid.com 是「這個人對你的開發者 Team」專屬的位址（跟 sub 一樣是 team-scoped，同一個 Team 底下的 App 拿到的相同）， 跟他在別處用的 email 一定不同，拿它去跟其他供應商給的 email 撞號永遠撞不到。 這本身不會造成安全問題，但要記得別把它寫進 users.email 當主要信箱 之後拿去寄行銷信 —— 使用者隨時可以關掉轉寄；而且只有從你向 Apple 登記過的寄件網域寄出的信才轉得過去。

範例裡的 usable_email() 就是在做這個把關。

5.1 不開放自己註冊的系統​

內部系統、後台、只給簽約客戶用的平台：帳號是管理員建的，第三方登入只是換一種方式進來， 不是一個註冊入口。決策流程要改成這樣：

① (provider, sub) 已經綁過？
      └─ 是 → 直接登入

② email 已驗證，而且對得到一個既有帳號？
      └─ 是 → 綁上去，然後登入

③ 對不到
      └─ 不建帳號。請他輸入管理員發給他的「綁定碼」
            └─ 碼對 → 綁上去、把碼作廢，然後登入

③ 在這種系統裡很常發生：員工用私人 Gmail 登入、系統裡那筆帳號根本沒填 email、 或是兩邊的大小寫與別名對不起來。沒有③的話，這些人只能打電話找工程師手動改資料庫。

綁定碼的設計

  • 由管理員替某個帳號產生，再用別的管道（當面、公司通訊軟體）交給本人。 使用者此刻還登不進系統，沒辦法自己產碼
  • 隨機、夠長（8 碼以上），字元集拿掉容易看錯的 0／O、1／I／l； 使用者多半是貼上來的，比對前先去掉前後空白
  • 用過就作廢，重發時舊的一起作廢；最好也有期限
  • 輸入端點要限制嘗試次數。8 碼不算長，不擋的話是可以被猜的
  • 管理介面要能看到「這個人綁了哪些登入方式」，也要能解除綁定（離職、手機換人、綁錯人）
danger

③ 那一刻的「是誰」要留在伺服器端。 使用者從供應商回來、對不到人、被帶去輸入綁定碼 —— 這時候已經驗證過的 (provider, sub, email) 要存在伺服器端的短命狀態裡 （跟 state 一樣大約 10 分鐘），或放進一張你自己簽、很快過期的憑證。 輸入綁定碼的那支端點只收「綁定碼」加上那個狀態的參照。

如果它收的是前端送來的 sub，任何人拿到一組綁定碼，就能把他自己的 Google 帳號 綁到別人的帳號上 —— 而且這甚至不需要綁定碼外洩，只要他能改那個欄位。

warning

② 在這種系統裡信任的是「管理員打的字」。 既有帳號的 email 是管理員建帳號時填的， 本人從來沒有驗證過。管理員打錯一個字、而那個錯的位址剛好是別人的真實信箱， 那個人用 Google 一登就進來了。風險高的系統可以：

  • 公司有 Google Workspace 的話，限定網域（授權請求帶 hd，後端再驗 ID token 裡的 hd claim）
  • 或乾脆拿掉②，第一次綁定一律要綁定碼

6. 綁定第二種登入方式​

使用者已經登入，在「帳號設定」頁按「綁定 LINE」。流程跟登入完全一樣， 差別只在呼叫 SignIn／sign_in!／sign_in 時帶入目前登入中的使用者 （web.CurrentUserID(r)／current_user／get_current_user(request, db)，定義見後端驗證第 5 節）。 各家的 callback 都已經這樣寫了，綁定不需要另一支端點。

internal/web/signin_error.go
package web

import (
	"errors"
	"log"
	"net/http"

	"example.com/app/internal/accounts"
)

// SignInErrorRedirect 把 accounts.SignIn 的錯誤翻成使用者看得懂的下一步，各家 callback 共用。
// 三種情況分開導，不要併成一句「資料重複」
func SignInErrorRedirect(w http.ResponseWriter, r *http.Request, err error) {
	var se *accounts.SignInError
	if !errors.As(err, &se) {
		log.Printf("登入失敗：%v", err)
		http.Error(w, "登入失敗", http.StatusInternalServerError)
		return
	}
	// email 撞號：要先用原本的方式登入；另外兩種發生在設定頁的綁定
	page := "/settings"
	if errors.Is(err, accounts.ErrEmailTaken) {
		page = "/login"
	}
	http.Redirect(w, r, page+"?error="+se.Code, http.StatusSeeOther)
}

  private

  # Identity.sign_in! 的三種錯誤各給一句對的話，各家 callback 共用。
  # 不要併成一句「資料重複」
  def redirect_sign_in_error(error)
    case error
    when Identity::EmailTaken
      # email 撞號：要先用原本的方式登入；另外兩種發生在設定頁的綁定
      redirect_to login_path, alert: "這個 email 已經有帳號，請先用原本的方式登入再綁定"
    when Identity::ProviderAlreadyLinked
      redirect_to settings_path, alert: "你已經綁定過這一家的另一個帳號，請先解除綁定"
    else # Identity::IdentityTaken
      redirect_to settings_path, alert: "這個帳號已經綁定在其他使用者上了"
    end
  end
end

7. 解除綁定​

只有一條規則值得寫下來：不能讓使用者解除掉他最後一個登入方式，否則他會被鎖在門外， 而且你的資料庫裡會出現一個永遠登不進去、也刪不掉的孤兒帳號。

  • Go
  • Ruby on Rails
  • Python
func Unlink(ctx context.Context, db *sql.DB, userID int64, provider string) error {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer tx.Rollback()

	// 先鎖住這個 user 那一列：兩個「解除綁定」同時進來時，第二個會等第一個提交後才往下算，
	// 不會兩個都看到「還有 2 個」而各刪一個。
	// 不寫成 SELECT COUNT(*) … FOR UPDATE：PostgreSQL 不允許 FOR UPDATE 搭配聚合函式
	var id int64
	if err := tx.QueryRowContext(ctx,
		`SELECT id FROM users WHERE id = ? FOR UPDATE`, userID,
	).Scan(&id); err != nil {
		return err
	}

	var count int
	if err := tx.QueryRowContext(ctx,
		`SELECT COUNT(*) FROM identities WHERE user_id = ?`, userID,
	).Scan(&count); err != nil {
		return err
	}
	// 如果你也有密碼登入，這裡要一起算進去
	if count <= 1 {
		return errors.New("這是你最後一個登入方式，不能解除綁定")
	}

	res, err := tx.ExecContext(ctx,
		`DELETE FROM identities WHERE user_id = ? AND provider = ?`, userID, provider,
	)
	if err != nil {
		return err
	}
	if n, err := res.RowsAffected(); err != nil {
		return err
	} else if n == 0 {
		return errors.New("你沒有綁定這個登入方式")
	}
	return tx.Commit()
}
class Identity < ApplicationRecord
  LastIdentity = Class.new(StandardError)

  def unlink!
    self.class.transaction do
      # 先鎖住 user 那一列，避免兩個請求同時解除最後兩個身分。
      # 不寫成 user.identities.lock.count：那會變成 COUNT(*) … FOR UPDATE，PostgreSQL 不接受
      user.lock!
      siblings = user.identities.count
      # 如果你也有密碼登入，這裡要一起算進去
      raise LastIdentity, "這是你最後一個登入方式，不能解除綁定" if siblings <= 1

      destroy!
    end
  end
end
class LastIdentity(Exception):
    """不能解除最後一個登入方式。"""


def unlink(db: Session, user: User, provider: str) -> None:
    # 先鎖住 user 那一列，避免兩個請求同時解除最後兩個身分
    db.execute(select(User.id).where(User.id == user.id).with_for_update())
    rows = db.scalars(select(Identity).where(Identity.user_id == user.id)).all()
    targets = [row for row in rows if row.provider == provider]
    # 如果你也有密碼登入，這裡要一起算進去
    if len(rows) <= 1 or not targets:
        db.rollback()  # 放掉鎖
        if not targets:
            raise LookupError("你沒有綁定這個登入方式")
        raise LastIdentity("這是你最後一個登入方式，不能解除綁定")

    for row in targets:
        db.delete(row)
    db.commit()

8. 刪除帳號​

ON DELETE CASCADE 會處理掉 identities，但還有兩件事要做：

  1. 有 Sign in with Apple 的話，要呼叫它的撤銷（revoke）API，見 Apple 篇。 分清楚哪一條是硬性規定：App 內必須能發起刪除帳號，是 App Store 審核指南 5.1.1(v) 的要求； 刪除時用 REST API 撤銷 token，Apple 的說明頁 寫的是應該（should）。實務上照做，而這代表你當初就得把 Apple 的 refresh token 存下來 （上面的 refresh_token_encrypted／refresh_token_client_id）。 順序是先撤銷、再刪 user —— ON DELETE CASCADE 會把存著 token 的那一列一起刪掉。
  2. 想清楚是硬刪還是軟刪。 軟刪（標記 deleted_at）的話， identities 上的唯一索引仍然佔著那個 (provider, sub) —— 同一個人之後想重新註冊會被擋下來。做法是刪除時把 identity 真的刪掉， 或在 provider_user_id 後面加上時間戳讓它失效。

9. 常見錯誤​

症狀原因
同一個人變成兩個帳號少了 UNIQUE (provider, provider_user_id)，或用 email 當鍵而使用者換了 email
同一個 Google 帳號能登入兩個不同的使用者同上，唯一約束沒建
偶發的「重複」錯誤並行請求（連按兩次、兩個分頁同時登入）。唯一索引有擋住（正確），但程式把它當成錯誤回給使用者，而不是回滾後重走一次（見第 4 節的範例）
已登入的人按「綁定 Google」，結果被切換成另一個帳號① 查到身分就直接登入，沒有檢查「目前登入的是不是它的主人」
從正式站複製資料到測試站後，一批人登入變成新帳號、LINE 推播失敗或沒送到兩個環境的 LINE Provider／Apple Team 不同，複製過去的 identities 在那邊對不到任何人。見第 2.1 節
新舊版 App（或網站與 App）的 LINE 使用者對不起來兩個 channel 放在不同的 Provider 底下。見第 2.1 節
使用者綁了 LINE 之後，原本的 Google 登不進去了綁定時把 identities 更新成新的 provider 而不是新增一列
有一批帳號永遠登不進去解除綁定沒有擋「最後一個」
「名稱重複」這句話出現在一個跟名稱無關的操作上把所有唯一約束／外鍵違反都翻成同一句話。要分開判斷是哪一個約束
陌生人用自己的 Google 帳號就進了內部系統照開放註冊的流程寫，④ 對不到人就自動建帳號。不開放註冊的系統見第 5.1 節
用第三方登入進來之後，每一支 API 都 403原本密碼登入上的關卡（例如「必須先改初始密碼」）沒有跟著處理。見後端驗證第 5.2 節
