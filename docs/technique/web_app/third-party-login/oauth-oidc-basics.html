OAuth 2.0 與 OpenID Connect 基礎

OAuth 2.0 的規格很大，但做登入只會用到其中一小塊。這一篇把那一小塊講清楚， 後面三篇（Google／LINE／Apple）就只剩下各家的設定差異。這是整個系列的第一篇，不需要先讀別的。

1. OAuth 2.0 與 OIDC 的關係​

一句話：OAuth 2.0 管的是「授權」，OpenID Connect 管的是「身分」。

OAuth 2.0OpenID Connect
回答的問題「這個 App 可不可以代表使用者去讀他的通訊錄？」「現在登入的人是誰？」
產出access_token（一串給 API 用的憑證）id_token（一段有簽章、描述「這個人是誰」的 JWT）
適合做登入嗎不適合適合

OIDC 是蓋在 OAuth 2.0 上面的一層：流程完全一樣，只是在 scope 裡加上 openid， 供應商就會在回傳裡多給你一個 id_token。

danger

不要拿 access_token 當身分證明。 access_token 對供應商來說只是「持有者可以呼叫某些 API」的憑證， 它沒有指定受眾。攻擊者可以拿一個他自己的 App 取得的 access token 丟給你的後端， 如果你只是拿它去打 userinfo API 換使用者資料，你就會把攻擊者換成那個受害者登入 （這叫 token substitution／confused deputy）。

登入要用的是 id_token，因為它裡面有 aud（受眾），你可以確認「這張憑證是簽給我的」。

2. 授權碼流程一步一步​

以「使用者按下網站上的登入按鈕」為例：

① 產生三個隨機值，存進 session

state          = 隨機字串   → 確認 callback 是這個瀏覽器發起的（防 CSRF）
nonce          = 隨機字串   → 確認 ID token 是為這一次登入簽的（防重放）
code_verifier  = 隨機字串   → PKCE：確認拿 code 來換 token 的就是發起的那一方
code_challenge = BASE64URL(SHA256(code_verifier))

三個值各管一段，第 4～6 節分開講。

② 把瀏覽器導去供應商的授權端點

https://供應商/authorize
  ?response_type=code
  &client_id=你的 client id
  &redirect_uri=https%3A%2F%2Fapp.example.com%2Fauth%2Fcallback
  &scope=openid%20email%20profile
  &state=…
  &nonce=…
  &code_challenge=…
  &code_challenge_method=S256

③ 使用者在供應商的頁面登入、按同意。 這一段完全不經過你的伺服器 —— 使用者的密碼永遠不會出現在你這裡，這是第三方登入最主要的好處。

④ 供應商把瀏覽器導回你登記的 redirect_uri

https://app.example.com/auth/callback?code=4%2F0Ab…&state=…

⑤ 後端比對 state，不對就直接拒絕，什麼都不要做。

⑥ 後端用 code 去換 token（伺服器對伺服器，client_secret 只出現在這裡）

POST /token HTTP/1.1
Host: 供應商
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=4/0Ab…
&redirect_uri=https://app.example.com/auth/callback
&client_id=…
&client_secret=…
&code_verifier=…

⑦ 拿到 token，驗證 id_token（簽章與演算法、iss、aud、exp、nonce， 完整步驟見後端驗證）， 取出 sub，查或建你自己的使用者，發你自己的 session。

tip

第 ⑥ 步的 redirect_uri 不是用來導向的，而是給供應商做一致性檢查的 —— 它必須跟第 ② 步送出去的那個字串一模一樣。少一個斜線就會拿到 invalid_grant。

2.1 授權碼只能用一次​

code 的壽命很短（RFC 6749 建議最長 10 分鐘，實務上常見的是幾十秒到幾分鐘），而且只能兌換一次。 規格還建議供應商在發現同一個 code 被兌換第二次時，把第一次發出去的 token 也一起撤銷 （RFC 6749 §4.1.2）—— 所以重複兌換不只是第二次失敗，第一次拿到的 token 也可能跟著失效。這造成兩個常見的假 bug：

  • 使用者按了重新整理，瀏覽器重送 callback，第二次兌換就 invalid_grant。 → callback 處理完應該立刻 302 導到別的網址，不要停在 callback URL 上。
  • 開發時前端在 useEffect 裡打了兩次（React 18 起，StrictMode 在開發模式會刻意把 effect 跑兩次）。 → 第二次必定失敗，而且錯誤訊息完全不會提示你原因。

3. 四種 token 分別是什麼​

名稱長什麼樣壽命用途可以給前端嗎
code（授權碼）短字串數十秒～數分鐘，用一次就失效換 token它本來就會經過瀏覽器，但別存下來
id_tokenJWT，可以解開看內容各家不同，常見是 1 小時左右（看 exp）證明使用者是誰驗完就該丟掉，不要當 session
access_token不透明字串（各家格式不一）數十分鐘～數十天呼叫供應商的 API不要
refresh_token不透明字串數十天～不過期換新的 access token絕對不要

id_token 不是你的 session token。 它是「供應商在某個時間點證明了這個人的身分」的一次性證據， 驗完就該換成你自己的 session（cookie 或你自己簽的 JWT，見後端驗證第 5 節）。 直接把 Google 的 id_token 存進 localStorage 當登入狀態用，會遇到：一小時後過期、 無法主動撤銷、被 XSS 偷走後你完全不知道。

3.1 ID token 的結構​

id_token 是一段用 . 分成三段的 JWT：

eyJhbGciOiJSUzI1NiIsImtpZCI6IjEyMyJ9 . eyJpc3MiOiJodHRwczovL2V4YW1wbGUiLCJzdWIiOiIxMSJ9 . MEUCIQ…
└──────────── header ───────────────┘ └───────────── payload ─────────────────────────┘ └ signature ┘

前兩段只是 Base64URL，任何人都能解開看、也能改。真正讓它可信的是第三段簽章。 常見的 claim：

Claim意義注意
iss簽發者必須等於該供應商的固定值
sub使用者的唯一識別碼你該存進資料庫的東西。規格只保證它在同一個 iss 底下唯一、不會重新分配；不保證同一個人在你的每個 client 拿到同一個值（LINE 依 Provider 而不同、Apple 是同一個開發者團隊共用，見帳號串接 2.1）
aud受眾必須包含你的 client_id（可能是字串，也可能是陣列），這是防止 token 被挪用的關鍵
azp授權方（authorized party）只有「要 token 的 client」跟 aud 不同時才會出現（例如 Android App 替 web client 要 token）。有的話要是你認得的 client_id
exp / iat到期／簽發時間（Unix 秒）驗證時允許幾十秒的時鐘誤差；iat 在未來或太久以前都該拒絕
nonce你送出去的隨機值要跟 session 裡存的比對；你有送，token 裡卻沒有，也要拒絕
email / email_verified信箱與是否已驗證不一定有；沒驗證過的 email 不可信
name / picture顯示名稱、頭像隨時可能變，只當快取用

4. state 防的是 CSRF​

沒有 state 時的攻擊：攻擊者先在自己的瀏覽器走到第 ④ 步，拿到一個屬於他自己帳號的 code （拿到之後就停下來，不讓它被兌換），然後誘導受害者的瀏覽器開啟 https://app.example.com/auth/callback?code=攻擊者的code —— 例如一個自動跳轉的網頁或一個連結。 受害者的瀏覽器會帶著自己的 session 去兌換，結果有兩種：

  • 受害者原本沒登入：他被登入成攻擊者的帳號，之後在這個帳號裡填的資料、上傳的東西，攻擊者都看得到。
  • 受害者原本已登入，而你的 callback 會「已登入就綁定」（見帳號串接第 6 節）： 受害者的帳號被綁上了攻擊者的 Google 帳號 —— 之後攻擊者用自己的 Google 帳號就能登入受害者的帳號。
note

這個攻擊需要的是頂層導覽（連結、跳轉），不是 <img>：session cookie 設成 SameSite=Lax 時， 跨站的圖片請求不會帶 cookie，但跨站的頂層 GET 導覽會帶 —— 而 OAuth 的 callback 本來就是這樣進來的， 所以 SameSite=Lax 擋不住它。

所以 state 的規則是：

  1. 每次登入都重新產生一個高熵隨機值（照 RFC 6749 §10.10 對產生的憑證的標準：猜中機率不高於 2⁻¹²⁸；範例用 32 bytes = 256 bits）
  2. 存在只有這個瀏覽器讀得到的地方（server session，或 httpOnly cookie）
  3. callback 時用時間恆定比較比對
  4. 比對完就刪掉，不管成功失敗
note

RFC 9700 的說法是：用戶端必須防 CSRF， 而確定供應商支援 PKCE 時可以靠 PKCE、OIDC 流程裡可以靠 nonce，都沒有的話才一定要靠 state。 但 state 成本幾乎是零，而且有些供應商（例如 LINE）把它列為必填 —— 三個都帶就對了。

  • Ruby on Rails
  • Python

後面各篇的 Go 範例都用這兩個函式，放在共用的 web 套件裡：

internal/web/token.go
package web

import (
	"crypto/rand"
	"crypto/subtle"
	"encoding/base64"
)

// RandomToken 產生 32 bytes（256 bits）的隨機值，編成 43 個字元的 Base64URL。state、nonce 都用它
func RandomToken() string {
	b := make([]byte, 32)
	if _, err := rand.Read(b); err != nil {
		panic(err) // crypto/rand 失敗代表系統有嚴重問題，不該靜默忽略
	}
	return base64.RawURLEncoding.EncodeToString(b)
}

// SameToken 以時間恆定的方式比對。saved 是自己存的那一份，它是空字串時一律不相等 ——
// 「session 裡沒有」不能被當成「兩邊都是空的所以相同」。
// ConstantTimeCompare 在長度不同時直接回 0，長度相同時才逐位元組比；
// 長度本身不是秘密（一律是 43 個字元），所以這樣就夠了
func SameToken(saved, got string) bool {
	return saved != "" && subtle.ConstantTimeCompare([]byte(saved), []byte(got)) == 1
}

// 產生：state := web.RandomToken()，存進 session
// 比對：saved := 從 session 取出並立刻刪掉；if !web.SameToken(saved, r.URL.Query().Get("state")) { 400 }
# 產生
state = SecureRandom.urlsafe_base64(32)
session[:oauth_state] = state

# 比對
saved = session.delete(:oauth_state) # 先刪，避免重放
unless saved && ActiveSupport::SecurityUtils.secure_compare(saved, params[:state].to_s)
  return render plain: "state 不符", status: :bad_request
end
import secrets

# 產生
state = secrets.token_urlsafe(32)
request.session["oauth_state"] = state

# 比對
saved = request.session.pop("oauth_state", None)  # 先刪，避免重放
if not saved or not secrets.compare_digest(saved, state_from_query or ""):
    raise HTTPException(400, "state 不符")
tip

state 也很適合順便夾帶「登入完要回哪一頁」。但不要把回跳網址直接塞進 state 字串裡 —— 那等於讓使用者控制它。做法是：state 仍然是純隨機值，回跳網址存在 session 裡跟它放在一起。 而且回跳網址一定要驗證是站內路徑（以 / 開頭，但不是 // 也不是 /\ —— 瀏覽器會把這兩種當成 「換一個網域」），否則就是開放重導漏洞。

5. nonce 防的是 token 重放​

state 保護的是「這個 callback 是不是我發起的」；nonce 保護的是 「這個 id_token 是不是為了這一次登入而簽的」。

OIDC Core 對它的定義是「把用戶端的 session 跟 ID token 綁在一起，並減輕重放攻擊」。

做法一樣：登入前產生隨機值 → 放進授權請求的 nonce 參數 → 驗 id_token 時比對 id_token.nonce 是否等於 session 裡那個 → 比完刪掉。

warning

有送 nonce，token 裡就必須有 nonce 而且相等。 只寫成「token 裡有 nonce 才比對」， 攻擊者拿一段根本沒有 nonce 的 token 就繞過去了 （OIDC Core §3.1.3.7 第 11 步）。

在授權碼流程裡，nonce 還順便擋一件事：攻擊者把別的登入流程拿到的 code 塞進受害者的 callback （授權碼注入），換回來的 ID token 裡的 nonce 會是攻擊者那一次的，比對不會過。 RFC 9700 承認這是機密用戶端（有 client_secret 的網站後端）防授權碼注入的替代做法， 但它比 PKCE 弱：要靠你自己的程式確實比對、而且對公開用戶端（原生 App、SPA）沒有保護作用。 所以 nonce 不能取代下一節的 PKCE，兩個都要做。

在（B）架構（前端拿 ID token 交給後端）裡 nonce 特別重要，因為那裡沒有 code 可以換， nonce 是唯一能綁定「這次請求」的東西。這時 nonce 要由後端產生、存在後端， 前端只是拿去放進請求 —— 前端自己產、自己送給後端比對，等於沒比。

6. PKCE​

PKCE（Proof Key for Code Exchange，唸作 "pixy"，RFC 7636） 讓 code 只有發起這次授權的那一方換得到 token。它擋兩種攻擊：

  • 授權碼被攔截（RFC 7636 最初要解決的）：原生 App 用 custom scheme 當 redirect（myapp://callback）時， 同一支手機上的惡意 App 可能註冊同樣的 scheme 搶到那個 code。搶到的人沒有 code_verifier，換不到 token。
  • 授權碼注入（RFC 9700 的重點）： 攻擊者把他偷來或自己拿到的 code 塞進受害者的 callback，讓你的後端替他兌換。 這時兌換時送出去的是受害者 session 裡的 code_verifier，跟那個 code 當初的 code_challenge 對不上，供應商就會拒絕。

原理：

  1. 用戶端產生一個隨機的 code_verifier（43–128 個字元，只能用 A-Z a-z 0-9 - . _ ~）
  2. 授權請求送出 code_challenge = BASE64URL(SHA256(code_verifier))，只送雜湊
  3. 兌換 token 時才送出原始的 code_verifier
  4. 供應商比對雜湊是否相符

下面三種寫法產生的 verifier 都是 32 bytes 隨機值編成的 43 個字元，剛好落在範圍內。

  • Go
  • Ruby on Rails
  • Python
import (
	"crypto/sha256"
	"encoding/base64"

	"golang.org/x/oauth2"
)

// 方式一：用 x/oauth2 內建的（v0.13.0 起）
verifier := oauth2.GenerateVerifier() // 32 bytes 隨機值 → 43 個字元
authURL := conf.AuthCodeURL(state, oauth2.S256ChallengeOption(verifier))
// 兌換時：conf.Exchange(ctx, code, oauth2.VerifierOption(verifier))

// 方式二：自己算，看清楚在做什麼（等同 oauth2.S256ChallengeFromVerifier(verifier)）
sum := sha256.Sum256([]byte(verifier))
// RawURLEncoding = URL-safe 且「不補等號」，正好符合 Base64URL 的要求
challenge := base64.RawURLEncoding.EncodeToString(sum[:])
require "securerandom"
require "digest"
require "base64"

code_verifier = SecureRandom.urlsafe_base64(32)
code_challenge = Base64.urlsafe_encode64(
  Digest::SHA256.digest(code_verifier),
  padding: false,          # 不能留補位的等號
)
import base64, hashlib, secrets

code_verifier = secrets.token_urlsafe(32)
code_challenge = (
    base64.urlsafe_b64encode(hashlib.sha256(code_verifier.encode()).digest())
    .rstrip(b"=")            # urlsafe_b64encode 會補等號，一定要去掉
    .decode()
)

code_challenge_method 一定要用 S256，不要用 plain（那等於直接把 verifier 送出去）。

三種語言在補位等號上的行為不同：Go 的 RawURLEncoding 預設就不補， Ruby 要寫 padding: false，Python 要自己 rstrip(b"=")。 忘了去掉的症狀通常是兌換時被拒絕，而錯誤訊息只會說 invalid_grant —— 完全不會提示你原因。

tip

寫完先拿 RFC 7636 附錄 B 的測試向量驗一次： code_verifier 是 dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk 時， 算出來的 code_challenge 必須是 E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM（43 個字元、結尾沒有 =）。 上面三個版本都算得出這個值。

RFC 9700 的要求分兩級：

用戶端要求
公開用戶端（原生 App、SPA，沒有 client_secret）必須（MUST） 用 PKCE
機密用戶端（有 client_secret 的網站後端）建議（RECOMMENDED） 用 PKCE；OIDC 用戶端可以改用 nonce 當替代，但有額外前提（見第 5 節）

不要以為網站後端有 client_secret 就不需要 PKCE：client_secret 證明的是「來兌換的是你的後端」， 而授權碼注入攻擊裡，來兌換的本來就是你的後端 —— 只是它被騙去兌換一個不屬於這個使用者的 code。 這件事只有 PKCE（或確實比對的 nonce）擋得住，成本只是多幾行程式碼。

7. redirect URI 要當成白名單在管​

供應商只會把 code 導去你事先登記過的網址，這是整套安全性的地基。 RFC 9700 要求供應商用完全字串相符 （不是前綴、不是萬用字元；唯一的例外是原生 App 的 loopback 網址可以換埠號）。 Google 與 Apple 都是這樣比的；LINE 比較寬鬆：官方文件寫明可以在登記的 Callback URL 後面加任意 query 參數。

實作時一律照登記的字串原樣送，不要賭供應商會幫你正規化：

情況會不會被當成同一個
https://app.example.com/cb vs https://app.example.com/cb/不同（尾斜線）
https://app.example.com/cb vs https://App.Example.com/cb依字串比對就是不同。網域大小寫理論上不影響，但別測試供應商的寬容度，一律用小寫
https://app.example.com/cb vs https://app.example.com/cb?x=1Google／Apple：不同。LINE：可以（登記 …/cb 就能送 …/cb?x=1）
http://localhost:3000/cb vs http://127.0.0.1:3000/cb不同（要各自登記）

管理上的建議：

  • 只登記你真的會用到的那幾個。登記了一個你已經不用的子網域，等於留了一個洞 —— 只要那個子網域哪天被別人接手（子網域接管），他就能收到你的授權碼。
  • 正式站與測試站用不同的 client，不要圖方便在同一個 client 上登記十個 redirect URI。
  • redirect 的處理端點不要順便做別的事，尤其不要吃使用者給的網址做轉址。

8. discovery document：不要把端點寫死​

符合 OIDC 的供應商都會提供一份 JSON，列出它所有端點與支援的演算法：

https://accounts.google.com/.well-known/openid-configuration
https://appleid.apple.com/.well-known/openid-configuration
https://access.line.me/.well-known/openid-configuration
{
  "issuer": "https://accounts.google.com",
  "authorization_endpoint": "https://accounts.google.com/o/oauth2/v2/auth",
  "token_endpoint": "https://oauth2.googleapis.com/token",
  "jwks_uri": "https://www.googleapis.com/oauth2/v3/certs",
  "id_token_signing_alg_values_supported": ["RS256"]
}

用現成的 OIDC 函式庫時它會自己去讀這份文件（Go 的 go-oidc 就是這樣運作的）； 自己寫的話，至少 jwks_uri 要從這裡讀（金鑰網址是有可能搬家的）， 端點網址則可以寫死但要留意公告。

tip

這份文件也是排查問題的好工具。不確定某家支不支援 PKCE？ 看 code_challenge_methods_supported 有沒有 S256。 不確定 ID token 用什麼演算法簽？看 id_token_signing_alg_values_supported。 想知道 sub 是不是每個 client 都一樣？看 subject_types_supported：public 是同一個值， pairwise 表示會依 client（或它所屬的群組）給不同的值。

discovery 不一定列得完整。 撰稿當下實際抓到的：

id_token_signing_alg_values_supportedcode_challenge_methods_supportedsubject_types_supported
GoogleRS256plain、S256public
LINE只列 ES256 —— 但網頁登入拿到的 ID token 是 HS256（用 channel secret 簽）S256pairwise
AppleRS256沒有這個欄位pairwise

所以演算法白名單要照各家的文件設，不能只照 discovery 自動產生，否則 LINE 網頁登入會全部驗不過 （LINE 的兩種演算法各自怎麼驗，見 LINE 篇第 5 節）。

9. 不要用 implicit flow​

你可能會在舊文章看到 response_type=token 或 response_type=id_token， 讓供應商直接把 token 放在 URL 的 fragment 裡回傳。RFC 9700 明確表示不應該（SHOULD NOT）再用 response_type=token，應該改用 response_type=code。 原因是 access token 會出現在網址、瀏覽器歷史與各種紀錄裡，容易外洩也容易被注入，而且沒有辦法用 PKCE 保護。

現在正確的做法一律是 authorization code + PKCE。 唯一的例外是各家自己的 JS SDK 用的那種「直接回一段 ID token 給前端」的模式 （Google 的「使用 Google 帳戶登入」按鈕就是），那是（B）架構， 它靠的是 nonce + 後端驗簽，不是 implicit flow。

10. 本機開發怎麼測​

供應商http://localhost 可以嗎建議做法
Google可以，localhost 是明確的例外直接登記 http://localhost:3000/auth/google/callback
LINE通常可以（官方文件沒有寫明，以 console 實際接受與否為準）先直接登記 http://localhost:…；console 不收就改用下面的隧道做法
Apple不行，必須公開 https 網域用隧道服務（如 Cloudflare Tunnel、ngrok）取得一個固定的 https 網址，或用一個 dev.example.com 之類的子網域

用隧道服務時要注意：免費方案的網址每次重啟都會變，而你必須在 console 重新登記， 所以開發 Apple 登入時值得花錢買固定網址，或乾脆準備一個開發專用子網域。

tip

本機測試的第一步不是寫程式，是先用瀏覽器直接貼授權網址。把第 ② 步那串 URL 組好貼進網址列， 如果設定有錯（client_id 不對、redirect_uri 沒登記、scope 沒開），你會在那一頁就看到錯誤訊息， 不用先把整套 callback 寫完。這能省掉非常多來回。
