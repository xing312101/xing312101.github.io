SPA 白畫面排查手冊

前端部署上去，開起來是一片白。主控台可能有一行紅字，也可能什麼都沒有。

這份文件整理三個最常見的成因、各自的辨識特徵、修法，以及可以重現驗證的腳本。 重點在最後一項 —— 白畫面最大的成本不是修，是猜。

0. 先問一個問題，可以砍掉一半的可能性​

新訪客正常，開過的人白 —— 還是所有人都白？

觀察排除掉什麼剩下什麼
所有人都白瀏覽器端狀態建置產物壞掉、路徑錯、伺服器設定錯
新訪客正常、開過的白建置產物、伺服器設定localStorage / 快取 / service worker
同一台，無痕正常、一般視窗白同上，且更確定同上

第二、三種情況幾乎一定是「瀏覽器裡留下來的東西」。這三個東西是： localStorage、HTTP 快取的 index.html、service worker。以下一節一個。

tip

先做這個判斷，不要急著重新部署。「檔案沒上去」很少是真正的原因，而重新部署會浪費 一輪，還會讓你誤以為問題跟部署有關。

1. 成因 A：localStorage 配額爆掉​

症狀​

主控台有一行：

Uncaught QuotaExceededError: Failed to execute 'setItem' on 'Storage':
Setting the value of 'some_key' exceeded the quota.

畫面全白，而且每次重新載入都白 —— 因為超量的資料還在 localStorage 裡。

為什麼一行 setItem 會讓整個畫面消失​

關鍵是 React 的錯誤傳播規則，不是 localStorage 本身：

useEffect(() => {
  localStorage.setItem('items', JSON.stringify(items));   // ← 這裡 throw
}, [items]);

在 useEffect（或 render 等生命週期）裡未捕捉的例外，會往上冒到最近的 error boundary。如果整棵樹上沒有任何 error boundary，React 的預設行為是 卸載整棵樹 —— 不是「這個元件壞掉」，是整個 app 從 DOM 上消失。root 容器 變成空的，畫面就是純白。

這也是為什麼白畫面通常只留下一行錯誤：真正的資訊在那行，但畫面上什麼都不剩。

為什麼「照片存 localStorage」一定會爆​

  • localStorage 每個網域上限約 5 MB（各家瀏覽器略有差異，量級相同）。
  • base64 編碼會讓資料膨脹約 33%。一張 300 KB 的 JPEG 變成約 400 KB 的字串。
  • 十幾張照片就滿了。

而且爆掉的不一定是最大的那個鍵。配額是整個網域共用的，所以常見情況是 A 鍵慢慢長大，最後在寫 B 鍵的時候爆 —— 錯誤訊息指著 B，元凶是 A。

不要只看錯誤訊息裡的鍵名

把所有鍵的大小列出來再判斷：

Object.keys(localStorage).map(k => [k, (localStorage[k].length / 1024).toFixed(1) + ' KB'])

修法：包一層，讓寫入失敗是可接受的​

utils/safeStorage.ts
let quotaExceeded = false;

export const isStorageQuotaExceeded = () => quotaExceeded;

export function safeSetItem(key: string, value: string): boolean {
  try {
    localStorage.setItem(key, value);
    return true;
  } catch (err) {
    quotaExceeded = true;
    console.warn(
      `[safeStorage] 寫入 "${key}" 失敗（${(value.length / 1048576).toFixed(2)} MB）`, err
    );
    return false;
  }
}

然後把全部裸的 localStorage.setItem 換掉：

grep -rn "localStorage.setItem" src/          # 先看有幾個、在哪
perl -pi -e 's/\blocalStorage\.setItem\(/safeSetItem(/g' src/**/*.ts src/**/*.tsx
grep -rn "localStorage.setItem" src/          # 改完再確認一次
漏一個就等於沒修

只要還有一個裸的 setItem 留在 effect 裡，白畫面就還會發生。改完務必再 grep 一次。

這個修法解決什麼、不解決什麼​

✅ 解決畫面不再整個消失；使用者能繼續操作
⚠️ 不解決超量的資料不會被存下來。如果 localStorage 是唯一的儲存，那就是靜默的資料遺失

所以這是止血，不是根治。真正的修法是不要把大型二進位資料放 localStorage：

  • 用 IndexedDB（配額大得多，而且可以直接存 Blob，不必 base64）
  • 或上傳到後端／物件儲存，本機只留 URL
  • 若一定要留在本機，至少壓縮並限制張數，且在接近上限時明確告訴使用者

如果寫入失敗會造成使用者以為存好了、其實沒存，必須在畫面上說出來，不能只 console.warn。靜默失敗比白畫面更危險。

2. 成因 B：快取住的 index.html 配上內容雜湊檔名​

機制​

現代打包工具（Vite、webpack…）產出的檔名帶內容雜湊：

dist/
  index.html                       ← 唯一指出「要載哪一支」的檔案
  assets/index-a3f9c1d2.js
  assets/index-7b4e0a85.css

index.html 裡寫死了那個雜湊。換版之後雜湊會變，舊檔案通常會被刪掉。於是：

瀏覽器快取住舊的 index.html
        │
        ├─ 要 /assets/index-<舊雜湊>.js
        │
        └─ 伺服器上已經沒有這支了
                │
                ├─ 有設 SPA 退回 → 回 200 ＋ index.html 的 HTML 內容
                │                   module script 因 MIME 不符拒絕執行
                │                   → 白畫面，主控台只有一行 MIME 錯誤
                │
                └─ 沒設 SPA 退回 → 乾脆的 404 → 白畫面，但至少錯誤清楚

「新訪客正常、開過的人白」的典型長相就是這個。

最容易犯的錯：完全不設 Cache-Control​

app.example.com {
    root * /var/www/app.example.com
    file_server
    try_files {path} {path}/ /index.html
}

沒有 Cache-Control 不等於不快取。HTTP 允許瀏覽器做啟發式快取 （heuristic caching）—— 在只有 Last-Modified 的情況下，通常會自己算一個約 「距上次修改時間的 10%」的新鮮期，期間完全不回伺服器驗證。

也就是說：你以為沒開快取，其實開了，而且行為隨檔案年齡浮動、很難重現。

正確設法​

兩類檔案的快取策略完全相反，必須分開處理：

# bash
app.example.com {
    root * /var/www/app.example.com

    handle /assets/* {
        # 檔名帶內容雜湊，內容永不改變 → 放心永久快取
        header Cache-Control "public, max-age=31536000, immutable"
        file_server
    }

    handle {
        # index.html 是唯一指出「現在該載哪一支」的檔案。
        # 被存住就等於換版沒生效 —— 用 no-store，不要用 no-cache。
        header Cache-Control "no-store"
        try_files {path} {path}/ /index.html
        file_server
    }
}

三個要點：

  1. 資產和 index.html 一定要分開 handle。 混用裸指令時，多數伺服器的指令 排序會讓 try_files 先跑，把 /assets/* 也吃進 SPA 退回 —— 於是缺檔變成 「200 ＋ HTML」，症狀從清楚的 404 惡化成難查的 MIME 錯誤。

  2. no-store，不是 no-cache。 no-cache 仍然允許瀏覽器存下副本， 只是要求每次使用前驗證。no-store 才是「不准留」。index.html 通常只有幾百 bytes，不值得為它省。

  3. 資產的 immutable 是安全的 —— 前提是檔名真的帶內容雜湊。手寫的 /js/app.js 加 immutable 會讓你永遠更新不了。

進階：讓已經卡住的瀏覽器自己救回來​

上面的設定能防止「未來」發生，但救不了已經把舊 index.html 存起來的人 —— 伺服器改設定，改不到別人硬碟裡的快取。

作法是：/assets/* 找不到檔案時，不要回 404，回一段自我修復的 JS。

# bash
handle /assets/* {
    @exists file

    handle @exists {
        header Cache-Control "public, max-age=31536000, immutable"
        file_server
    }

    # 檔案不存在 ＝ 對方拿著舊版 index.html 在要一支已被換掉的 bundle
    handle {
        header Content-Type "text/javascript; charset=utf-8"
        header Cache-Control "no-store"
        respond `if(!location.search.includes("_cb")){location.replace(location.pathname+"?_cb="+Date.now())}` 200
    }
}

為什麼有效：查詢字串是 HTTP 快取鍵的一部分。帶了 ?_cb=… 之後就跟原本的 路徑是兩筆不同的快取項目，所以那次請求一定會回到伺服器，拿到新的 index.html。

_cb 那個判斷是防迴圈的煞車，不能省

沒有它的話，如果新的 index.html 因為任何原因還是壞的，就會變成無限重整。

Nginx 的對應寫法是 location /assets/ { try_files $uri @stale; } 搭一個 @stale 區塊 return 200 同一段 JS，並設好 default_type。

3. 成因 C：service worker​

排查時一定要排除，因為它會讓你在伺服器端做的所有修改都失效 —— service worker 攔截所有請求，可以無限期地餵舊版檔案，硬重新整理也不一定繞得過。

// 主控台貼這段
navigator.serviceWorker.getRegistrations().then(rs => console.log(rs));

有東西就先解除再測：

navigator.serviceWorker.getRegistrations()
  .then(rs => Promise.all(rs.map(r => r.unregister())))
  .then(() => caches.keys())
  .then(ks => Promise.all(ks.map(k => caches.delete(k))))
  .then(() => location.reload());
note

專案原始碼裡沒有 serviceWorker.register 不代表沒有 —— 可能是前一版留下來的， 或某個 PWA 外掛自動加的。以瀏覽器實際回報的為準。

4. 通用工具：白畫面診斷罩​

白畫面最難處理的一點是回報者看不到任何資訊。加一段行內腳本，把白畫面變成 一份可以直接截圖回報的診斷資料：

index.html
<script>
(function () {
  var errs = [];
  var note = function (s) { errs.push(String(s).slice(0, 500)); };

  window.addEventListener('error', function (e) {
    if (e.target && (e.target.tagName === 'SCRIPT' || e.target.tagName === 'LINK'))
      note('資源載入失敗: ' + (e.target.src || e.target.href));
    else
      note('JS 錯誤: ' + (e.message || e.error) + ' @ ' + (e.filename || '') + ':' + (e.lineno || ''));
  }, true);   // ← 第三個參數 true 是必要的，見下方說明

  window.addEventListener('unhandledrejection', function (e) {
    note('未處理的 Promise: ' + ((e.reason && e.reason.message) || e.reason));
  });

  setTimeout(function () {
    var root = document.getElementById('root');
    if (root && root.children.length > 0) return;      // 有畫面就不打擾

    var ls = [];
    try {
      for (var i = 0; i < localStorage.length; i++) {
        var k = localStorage.key(i);
        ls.push(k + ' = ' + ((localStorage.getItem(k) || '').length / 1024).toFixed(1) + ' KB');
      }
    } catch (e) { ls.push('讀不到 localStorage: ' + e); }

    document.body.insertAdjacentHTML('beforeend',
      '<div style="font:13px/1.6 monospace;padding:16px">' +
      '<h2>畫面載入失敗 —— 請把這整頁截圖回報</h2>' +
      '<pre>' + (errs.join('\n\n') || '(沒有攔到 JS 錯誤 —— 表示 bundle 沒執行，或 render 出空)') + '</pre>' +
      '<pre>' + [].map.call(document.querySelectorAll('script[src],link[rel=stylesheet]'),
                            function (n) { return n.src || n.href; }).join('\n') + '</pre>' +
      '<pre>' + (ls.join('\n') || '(localStorage 空的)') + '</pre>' +
      '<pre>' + location.href + '\n' + navigator.userAgent + '</pre>' +
      '</div>');
  }, 8000);
})();
</script>

幾個設計上的考量：

  • 放在行內、在 bundle 之前 —— bundle 本身載不到的時候它還是要能跑。
  • 第三個參數 true（捕獲階段） —— 資源載入失敗的事件不會冒泡， 不給 true 就抓不到「js 檔 404」這個最常見的情況。
  • 只在容器是空的時候才顯示，不要誤報。
  • 「沒有攔到任何錯誤」本身就是有用的資訊 —— 它把問題從「執行期爆炸」 導向「根本沒載到／render 出空」。

長期而言，真正該做的是加 error boundary。診斷罩是給「連 error boundary 都 沒來得及掛上」的情況用的補網。

5. 重現與驗證：不要靠猜​

白畫面很容易一路猜下去，每猜一輪就重新部署一次。改成用無頭瀏覽器建立 可重複執行的檢查：

// npm i puppeteer-core   （用系統既有的 Chrome，不另外下載一份）
import puppeteer from 'puppeteer-core';

const ORIGIN = 'https://app.example.com';
const browser = await puppeteer.launch({
  executablePath: '/Applications/Google Chrome.app/Contents/MacOS/Google Chrome',
  headless: 'new',
});

const ctx  = await browser.createBrowserContext();   // 每個情境一份乾淨的 origin storage
const page = await ctx.newPage();

const errors = [];
page.on('pageerror', e => errors.push(e.message.split('\n')[0]));
page.on('console',  m => { if (m.type() === 'error') errors.push(m.text()); });

await page.goto(ORIGIN, { waitUntil: 'networkidle2' });
await new Promise(r => setTimeout(r, 8000));         // 等非同步初始化跑完

const len = await page.evaluate(() => document.getElementById('root').innerHTML.length);
console.log(len > 1000 ? '✅ 有畫面' : '❌ 白畫面', errors);

await browser.close();

在這個骨架上可以做幾件手動測不了的事。

把 localStorage 灌到配額爆掉（重現成因 A）：

await page.evaluate(() => {
  const chunk = 'B'.repeat(512 * 1024);
  try { for (let i = 0; i < 40; i++) localStorage.setItem('ballast_' + i, chunk); }
  catch (e) { /* 撐到爆為止，就是我們要的狀態 */ }
});
await page.reload({ waitUntil: 'networkidle2' });

偽造一份「快取住的舊 index.html」（重現成因 B）：

await page.setRequestInterception(true);
let served = false;
page.on('request', req => {
  const u = new URL(req.url());
  if (u.pathname === '/' && !u.search.includes('_cb') && !served) {
    served = true;
    return req.respond({
      status: 200,
      contentType: 'text/html',
      body: '<div id="root"></div><script type="module" src="/assets/index-OLDHASH.js"></script>',
    });
  }
  req.continue();
});

這樣就能證明自癒機制真的有作用，而不是「這次剛好沒事」。

兩個方向都要測

壞的情況要修好，好的情況不能被弄壞（例如診斷罩不該在正常載入時誤報）。 只測一邊很容易做出「永遠顯示錯誤訊息」這種修法。

6. 檢查清單​

排查：

  • 無痕視窗開得起來嗎？（開得起來 → 瀏覽器端狀態問題）
  • 主控台第一行紅字是什麼？（QuotaExceededError ／ MIME ／ 404 各指向不同成因）
  • Network 分頁裡，bundle 的狀態碼是 200 嗎？Content-Type 對嗎？
  • navigator.serviceWorker.getRegistrations() 是空的嗎？
  • 各個 localStorage 鍵多大？加起來接近 5 MB 嗎？

部署設定：

  • 資產和 index.html 分開 handle，資產不吃 SPA 退回
  • index.html：Cache-Control: no-store
  • 帶內容雜湊的資產：max-age=31536000, immutable
  • 缺檔的資產回自癒 JS 而非 404（含 _cb 防迴圈煞車）
  • 換版用 rsync --delete 時，先確認目錄底下沒有別的東西在用

程式碼：

  • 有 error boundary
  • 所有 localStorage.setItem 都在 try/catch 裡（grep 確認沒有漏網的）
  • 大型二進位資料放 IndexedDB 或後端，不放 localStorage
  • 儲存失敗時，使用者看得到，不是只有 console.warn

附錄：三個成因的快速對照​

成因 A：配額成因 B：陳舊 index.html成因 C：service worker
無痕視窗✅ 正常✅ 正常✅ 正常
主控台QuotaExceededErrorMIME 錯誤或 404通常無錯誤，但版本是舊的
Network一切 200bundle 404 或回 HTML大量 (from ServiceWorker)
硬重新整理❌ 沒用✅ 通常有效❌ 不一定有效
清網站資料✅ 有效✅ 有效✅ 有效
伺服器端可修❌ 要改程式✅ 可（自癒 shim）❌ 要靠 SW 自己更新

「硬重新整理有沒有用」這一列最好用 —— 它幾乎可以一步把 A 和 B 分開。
