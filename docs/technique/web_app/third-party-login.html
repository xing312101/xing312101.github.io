第三方登入總覽

「用 Google 帳號登入」這種功能，實作起來的難點不在寫程式 —— 授權碼換 token 的程式碼 大概三十行就寫完了。難的是：每一家的申請流程、審查規則、以及各自的例外行為都不一樣， 而且踩到的時候錯誤訊息通常沒有指向真正的原因。

這一系列文件把「申請」「設定」「程式碼」「常見錯誤」四件事分開講， 並且在每一篇標出那一家特有的坑。

1. 各篇導覽​

第一次接觸的話，照這個順序讀：基礎 → Google（完整的基準實作）→ 後端驗證 → 帳號串接 → 你要接的其他家（LINE、LIFF、Apple 都只寫跟 Google 不一樣的地方）→ 測試。 已經上線、正在排查問題的話，直接從常見錯誤訊息對照開始。

note

範例程式碼一律提供 Go、Ruby on Rails、Python 三個版本，用分頁切換， 選過一次之後整份文件都會記住你的選擇。三個版本做的事完全一樣， 所以也可以拿來對照著看某個概念在不同生態系怎麼表達。 各家 callback 共用的函式（SignIn、目前登入者、開始 session、錯誤轉回應）各定義在哪一篇， 對照表在 Google 篇第 3 節開頭；環境變數的完整清單在測試篇 8.1。

各家的 console 介面改版很頻繁（Google 近年就把原本的「OAuth 同意畫面」整個改版成 「Google Auth Platform」，拆成 Branding、Audience、Data Access、Clients 幾頁）。這裡寫的是撰稿當下的路徑與選項名稱，畫面對不上時請以官方文件為準， 但底下的概念（要設哪些東西、為什麼要設）不太會變。

有 iOS App 的話先看這一條： App 讓使用者用第三方帳號（Google、LINE……）建立或登入主要帳號時， App Store 審核規則 4.8 要求同時提供另一個「等價」的登入選項 —— 只收集姓名與 email、讓使用者可以隱藏 email、 未經同意不拿 App 內的互動做廣告用途。Sign in with Apple 符合這三個條件，所以是最省事的做法， 但規則沒有指定一定要用它；Google 與 LINE 登入都沒有「隱藏 email」的選項，只做這兩家的話不算數。 純網站不受這條規範。 這件事會直接影響你要不要花那 US$99，最好在做 App 之前就決定； 例外情況與條文的演變見 Apple 篇第 1 節，細節以最新條文為準。

3. 你該選哪一種流程​

這是第二個要先決定的事，選錯會整套重寫。

3.1 兩種架構​

（A）後端主導的授權碼流程 —— 瀏覽器被導去供應商 → 供應商把 code 導回你的後端 → 後端用 code 換 token → 後端建立自己的 session。

瀏覽器 ──► 你的後端 /auth/google        (產生 state、nonce、PKCE，存進 session)
        ◄── 302 到 accounts.google.com
瀏覽器 ──► 供應商登入頁                 (使用者輸入帳密／按同意)
        ◄── 302 回 你的後端 /auth/google/callback?code=…&state=…
你的後端 ──► 供應商 token endpoint      (code + client_secret 換 token，走伺服器對伺服器)
        ◄── id_token / access_token
你的後端 ──► 設 session cookie，導回首頁

（B）前端拿到 ID token，交給後端驗 —— 用供應商的 JS SDK（Google 的「使用 Google 帳戶登入」按鈕、 LINE 的 LIFF）在前端直接拿到一段 ID token，前端 POST 給後端，後端驗簽後發自己的 session。

3.2 怎麼選​

情境建議
一般網站、有自己的後端（A）
要呼叫供應商的 API（讀日曆、發訊息）（A），因為只有它拿得到 access token／refresh token
三家都要接（A），流程一致，換供應商只是換設定
純前端 SPA + 現成的 BaaS（B）
在 LINE 內建瀏覽器裡跑的頁面（B）用 LIFF 比較順。LINE 官方已建議新的 LIFF app 直接建成 LINE MINI App（同樣用 LIFF SDK，後端驗證方式不變）
只想要一顆「一鍵登入」按鈕，不需要任何供應商 API（B）可以，但仍必須在後端驗簽

本系列的範例都是（A），因為它最通用，而且（B）只是把（A）的前半段換掉， 後半段（驗 ID token、建帳號、發 session）完全一樣。

（B）的前提是後端一定要自己驗那段 ID token。 前端傳來的 { userId: "..." }、 { email: "..." } 一律不可信 —— 那是使用者可以任意偽造的字串。 後端要收的是原始的 id_token 字串，自己驗簽、自己解出 sub （理由與驗法見後端驗證第 1、2 節）。

4. 資料模型：兩張表​

所有範例都建立在同一個資料模型上，先講清楚，後面看程式碼才不會卡住：

users                      identities
┌────────────────┐         ┌──────────────────────────────┐
│ id             │◄───┐    │ id                           │
│ email          │    └────│ user_id                      │
│ display_name   │  1    n │ provider          ─┐ 一起     │
│ avatar_url     │         │ provider_user_id  ─┘ UNIQUE   │
└────────────────┘         │ email                        │
                           └──────────────────────────────┘

規則只有兩條：

  1. 一個使用者可以有多個第三方身分 —— 同一個人可以同時綁 Google、LINE、Apple， 三種方式登進來都是同一個帳號。
  2. 一個第三方身分只能綁在一個使用者身上 —— 靠 UNIQUE (provider, provider_user_id) 這個資料庫約束保證，不是靠程式檢查。

不要用 email 當使用者的主鍵。 三家都可能給你一個會變、或根本沒有的 email： Apple 給的可能是 @privaterelay.appleid.com 這類轉寄信箱、LINE 要另外申請才有 email、 Google Workspace 的使用者改帳號名稱時 email 也會變。sub 不會變，email 會 （但 sub 的範圍各家不同，見帳號串接 2.1）。

完整的建表語句、索引、以及「登入時該怎麼查／建／綁」的三語言實作， 在帳號串接與資料表設計。

5. 最小可動的心智模型​

不管哪一家，你最後真正需要的只有兩樣東西：

  1. 一個穩定、供應商保證唯一的使用者識別碼 —— ID token 裡的 sub。 這是你 identities.provider_user_id 該存的東西。
  2. 確認那段 ID token 真的是那家供應商簽的、而且是簽給你的 —— 驗簽 + 檢查 iss／aud／exp／nonce。

其餘的（頭像、顯示名稱、email）都只是附加資料，而且隨時可能沒有或改變。

6. 上線前檢查清單​

每一項都在後面的文件裡有對應章節：

  • 授權請求有帶 state，callback 有比對而且比對後就作廢（基礎）
  • 授權請求有帶 nonce，並且跟 ID token 裡的 nonce 比對過；有送 nonce 的流程，token 裡沒有 nonce 也要拒絕，不是「有帶才比」（LIFF 這種你沒送 nonce 的流程另外處理，見 LIFF 第 6 節）（基礎）
  • 有用 PKCE（原生 App 必須，網站也建議；Apple 的文件沒有列出 PKCE，見 Apple 第 7 節）（基礎）
  • 後端有完整驗 ID token：簽章（演算法白名單寫在程式裡，不從 token 的 header 讀）、iss、aud、exp、iat（後端驗證）
  • JWKS 有快取、也有在 kid 找不到時重抓（後端驗證）
  • identities 上有 UNIQUE (provider, provider_user_id)（帳號串接）
  • 已驗證的 email 才拿來自動合併帳號（帳號串接）
  • client_secret、.p8 金鑰不在前端、不在版控裡
  • Apple 的 client_secret 是每次使用時即時簽發、效期很短的，不是簽一個六個月的放著等過期（Apple）
  • 正式站的 redirect URI 都登記了，而且沒有登記到不該登記的（基礎）
  • 每個環境各用自己的 OAuth client，client ID 與 secret 取自同一個 client（Google）
  • 帳號資料跨環境複製時沒有帶 identities（帳號串接）
  • LINE 的 channel 已經切到 Published，並用一個不是 Admin／Tester 的帳號登入過（常見錯誤）
  • 登入成功後有換發新的 session ID（防 session fixation）
  • 原本密碼登入上的關卡（停用、強制改密碼、MFA）第三方登入也逐一處理過，不會被繞過、也不會把人鎖死（後端驗證）
  • 前後端不同網域時：登入按鈕連的是後端的絕對網址；登入狀態不經過網址交給前端（後端驗證）
  • 不開放註冊的系統：對不到人時是拒絕，不是自動建帳號（帳號串接）
  • 原生 App 沒有用 WebView 跑登入（原生 App）
  • 有實作登出，而且知道登出只登出你的站，不會登出 Google／LINE
  • 有帳號刪除流程；有 Sign in with Apple 的話要呼叫 revoke（Apple）
  • 有 LINE 登入的話，使用者退出服務或解除 LINE 綁定時要呼叫 deauthorize（LINE）
  • 測試全綠之後，在正式網域、真的手機、LINE app 裡實際走過一次（測試）
