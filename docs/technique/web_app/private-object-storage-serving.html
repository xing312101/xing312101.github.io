私有雲端儲存的檔案下載

把使用者上傳的圖片與文件從本機磁碟搬到雲端物件儲存（GCS、S3、R2 之類）之後， 馬上會遇到一個問題：bucket 是私有的，瀏覽器要怎麼看到圖？

這份文件講三種做法的取捨、一個很多人猜錯的延遲問題、以及後端與 web server 實際要設定什麼。程式碼以 Python／FastAPI 為例，但概念在任何語言都一樣。

0. 先講結論​

適合不適合
公開 bucket靜態網站資產、商品圖任何有權限概念的檔案
簽名網址大檔（影片、大 PDF）、伺服器與 bucket 距離遠權限要即時收回、檔案小而多
後端串流絕大多數情況，尤其伺服器跟 bucket 同區單檔很大又流量很高

預設選後端串流。 它最簡單、權限最完整，而且在「伺服器跟 bucket 同一個 region」 的常見架構下，實測還比簽名網址快（見 §3）。

別把本機磁碟那條路砍掉

搬上雲之後很容易順手把「存本機」的程式碼刪掉。留著。 有些環境（內網、離線、 不想依賴外部服務、客戶要求資料不出機房）本來就只能落地，而且測試要靠它才不用連網路。 把它跟雲端實作放在同一個介面後面，維護成本幾乎是零 —— 見 §4。

1. bucket 一定要私有​

不管選哪種給檔方式，bucket 本身永遠不對外。

要開的設定​

設定值為什麼
統一存取控制
(Uniform bucket-level access)		啟用關掉物件層 ACL。權限只有一個地方，不會出現「bucket 是私有的但某個物件被設成公開」
防止公開存取
(Public access prevention)		強制擋掉 allUsers / allAuthenticatedUsers，連手殘點到都加不進去
服務帳戶角色物件層級的讀寫角色
（GCS：Storage Object Admin）		不要給 bucket 管理權限。金鑰外流時，對方改不了 bucket 設定、開不了公開存取
角色綁定位置綁在 bucket 上，不是專案上綁專案等於這把金鑰能碰專案裡所有 bucket
不要用「網址猜不到」當保護

物件名稱再長再亂都不是安全機制。只要 bucket 允許匿名讀取，網址一旦被貼到聊天室、 寫進前端原始碼、或出現在 Referer 標頭裡，檔案就等於公開了。

驗證真的擋住了​

放一個誘餌檔，然後用沒有任何憑證的 HTTP 去打它的每一種公開網址形式：

BUCKET=your-bucket
OBJ=__leaktest__/canary.txt
# 先用有憑證的工具放上去，內容寫一段容易 grep 的字串

for URL in \
  "https://storage.googleapis.com/$BUCKET/$OBJ" \
  "https://$BUCKET.storage.googleapis.com/$OBJ" \
  "https://storage.googleapis.com/$BUCKET" ; do
  echo "$(curl -s -o /dev/null -w '%{http_code}' -m 20 "$URL")  $URL"
done

全部應該回 403（S3 是 403 或 404）。三件事要一起確認：

  1. 單一物件抓不到
  2. 列不出 bucket 內容 —— 不然攻擊者至少知道裡面有什麼
  3. 從不同網路再測一次 —— 從你自己的機器測可能有殘留憑證或 IP 白名單

還有一個容易漏掉的：storage.cloud.google.com/BUCKET/OBJ 這種「瀏覽器網址」會回 302。不要看到 302 就以為漏了，要跟到底：

curl -sL "https://storage.cloud.google.com/$BUCKET/$OBJ" -o /tmp/probe.html
grep -c "誘餌字串" /tmp/probe.html   # 應該是 0，內容會是 Google 登入頁

2. 三種給檔方式​

2.1 後端串流（預設選這個）​

瀏覽器 ──帶 token──▶ 後端 ──服務帳戶──▶ 物件儲存
   ▲                  │
   └─────位元組────────┘

後端檢查完權限，自己去 bucket 把物件讀出來，再把位元組吐給瀏覽器。 對外從頭到尾沒有任何 bucket 網址存在。

優點：

  • 權限檢查完整 —— 每一次請求都經過你的授權邏輯，收回權限立刻生效
  • 前端不用改 —— 本來打 API 拿檔案，現在還是打 API
  • 沒有網址外洩問題

代價：位元組經過你的伺服器。但如果伺服器跟 bucket 同 region，那一段通常 免費而且只有幾毫秒（見 §3）。

2.2 簽名網址（Signed URL）​

後端檢查完權限，簽一張只對這一個物件、只在幾分鐘內有效的網址回給前端， 瀏覽器自己去 bucket 抓。

適合：單檔很大（影片）、或伺服器與 bucket 距離遠。

三個一定要知道的坑

① 不要做成 302 轉址。 如果 API 回 302 轉去簽名網址，XMLHttpRequest／fetch 跟著轉址時會把 Authorization 標頭一起送到儲存服務的網域。GCS／S3 看到「簽名 + Authorization 兩套驗證」會直接回 400。正確做法是回 JSON 帶網址，讓前端自己發第二個請求。

② 簽出去就收不回來。 在有效期內，那張網址轉給誰都能用，繞過你所有的權限檢查。所以效期要短 （5–15 分鐘），而且絕對不要寫進 log。

③ bucket 要設 CORS。 瀏覽器直連儲存服務屬於跨來源請求，沒設 CORS 會被擋掉。

CORS 設定範例（GCS）：

[
  {
    "origin": ["https://app.example.com"],
    "method": ["GET", "HEAD"],
    "responseHeader": ["Content-Type", "Content-Disposition"],
    "maxAgeSeconds": 3600
  }
]

2.3 公開 bucket​

只有在「這些檔案本來就該給全世界看」時才用，例如商品圖、部落格附圖。 只要檔案有一點權限概念就不要走這條，因為之後想加權限等於整套重做。

3. 延遲：一個很多人猜錯的地方​

直覺會說「讓瀏覽器直接打 bucket 一定比較快，少一跳」。實測常常相反。

某次實際量測（使用者在亞洲、伺服器與 bucket 都在美西同一個 region）：

路徑首位元組370 KB 總計
簽名網址直連 bucket0.96 s1.62 s
經過後端串流0.45 s1.33 s

原因是私有物件在 CDN 邊緣不會被快取：

直連 bucket：  使用者 ──▶ 邊緣節點(近) ──▶ 原始 region 取物件 ──▶ 回使用者   兩段
經過後端：     使用者 ─────────────▶ 伺服器(原始 region 隔壁，約 10ms) ──▶ 回  一段

握手確實是直連 bucket 快（邊緣節點離使用者近），但資料還是得從原始 region 拉， 反而多繞一趟。伺服器就在 bucket 隔壁的話，那一段幾乎不算時間。

判斷準則：

  • 伺服器與 bucket 同 region → 後端串流通常較快
  • 伺服器與 bucket 跨區／跨洲 → 簽名網址較有優勢
  • 檔案很大（數 MB 以上）→ 簽名網址的頻寬優勢會顯現出來（實測 5 MB 檔直連 可跑到 2.6 MB/s，經過後端只有 0.64 MB/s）
  • 檔案小而多（縮圖、照片）→ 首位元組時間決定一切，頻寬不是重點
自己量，不要照抄

上面的數字只在那個地理配置成立。用 curl -w 量你自己的兩條路徑：

curl -s -o /dev/null -m 60 \
  -w "連線 %{time_connect}s  TLS %{time_appconnect}s  首位元組 %{time_starttransfer}s  總計 %{time_total}s  %{speed_download} B/s\n" \
  "$URL"

4. 後端：抽一層再說​

不要把物件儲存的 SDK 直接散在各個上傳／下載端點裡。理由很實際：

os.makedirs()、open()、os.path.exists()、回傳檔案路徑 —— 這些全是 磁碟才有的概念。物件儲存沒有目錄、exists 是一次網路往返、也不能拿路徑 餵給檔案回應。散在 N 個地方的話，換儲存體等於那 N 個地方全部重寫，而且測試 會被迫連網路。

4.1 儲存層介面​

storage.py
import os
import shutil
from typing import BinaryIO, Optional

CHUNK = 1024 * 1024


class TooLarge(Exception):
    """上傳超過上限。邊寫邊算，不是寫完才量。"""


def normalize_prefix(prefix: Optional[str]) -> str:
    """`demo` / `/demo` / `demo/` / `/demo/` 一律變成 `demo`。

    抽成模組層函式而不是寫在 `__init__` 裡：`__init__` 會建真的 Client，
    測試繞不過去，寫在裡面等於這段正規化沒有測試守著。
    """
    return (prefix or "").strip("/")


def with_prefix(prefix: str, key: str) -> str:
    """環境隔離的第一層。兩份實作共用同一支 —— 各寫各的話，
    改對一邊漏掉另一邊，而且漏的那邊會**安靜地**穿過隔離牆。"""
    return f"{prefix}/{key}" if prefix else key


class LocalDisk:
    """落在檔案系統上。**這是正式選項，不是只給開發用** —— 有些環境
    （內網、離線、不想依賴外部服務）本來就只能落地。所以兩份實作的行為
    要對齊，尤其是「找不到回 None」。"""

    def __init__(self, root: str, prefix: str = ""):
        self.root = root
        self.prefix = normalize_prefix(prefix)

    def _full(self, key: str) -> str:
        """組出磁碟上的完整路徑，**並且擋住逃出根目錄的 key**。

        這道檢查只有本機這份需要 —— 物件儲存沒有「上一層」的語意，`a/../b`
        就是一個叫 `a/../b` 的物件。但在檔案系統上它是真的會往上跳：

        - `../../etc/passwd` 直接寫到 root 外面
        - `/etc/passwd`（絕對路徑）更狠，`os.path.join` 會**丟掉前面所有片段**，
          root 等於不存在

        而 key 常常有一部分來自別人給的檔名（見 §4.5），所以不能假設它乾淨。

        **檢查 key 本身，不能只檢查算出來的路徑。** 有前綴的時候
        `/etc/passwd` 會被接成 `prod//etc/passwd` —— 它沒有逃出根目錄，
        但也不是你要的名字，而且不會有任何錯誤。靜靜地存到別的地方
        比直接失敗難查得多。
        """
        if key.startswith("/") or ".." in key.split("/"):
            raise ValueError(f"key 不可以是絕對路徑或含有 '..'：{key!r}")
        full = os.path.normpath(os.path.join(self.root, with_prefix(self.prefix, key)))
        root = os.path.normpath(self.root)
        if full != root and not full.startswith(root + os.sep):
            raise ValueError(f"key 逃出儲存根目錄：{key!r}")
        return full

    def exists(self, key: str) -> bool:
        return os.path.exists(self._full(key))

    def save(self, key: str, src: BinaryIO, limit: Optional[int] = None) -> int:
        full = self._full(key)
        os.makedirs(os.path.dirname(full), exist_ok=True)
        written = 0
        try:
            with open(full, "wb") as out:
                while chunk := src.read(CHUNK):
                    written += len(chunk)
                    if limit is not None and written > limit:
                        raise TooLarge()
                    out.write(chunk)
        except BaseException:
            if os.path.exists(full):     # 半截檔不留下來
                os.remove(full)
            raise
        return written

    def open(self, key: str) -> Optional[BinaryIO]:
        full = self._full(key)
        return open(full, "rb") if os.path.exists(full) else None

    def size(self, key: str) -> Optional[int]:
        full = self._full(key)
        return os.path.getsize(full) if os.path.exists(full) else None

    def delete(self, key: str) -> None:
        full = self._full(key)
        if os.path.exists(full):
            os.remove(full)

    def delete_prefix(self, prefix: str) -> None:
        # 本機是真的目錄，砍整棵就好。目錄名天生分得開，所以不會有
        # 「`attachments/1` 誤刪 `attachments/10`」那個問題 —— 那是雲端版
        # 才會犯的錯（見下面 GCS 的同名方法）。
        shutil.rmtree(self._full(prefix), ignore_errors=True)


class GCS:
    """SDK 延遲匯入 —— 跑本機或測試時不必安裝這個套件。"""

    def __init__(self, bucket_name: str, prefix: str = ""):
        from google.cloud import storage as gcs
        self._bucket = gcs.Client().bucket(bucket_name)
        self.prefix = normalize_prefix(prefix)

    def _key(self, key: str) -> str:
        return with_prefix(self.prefix, key)

    def save(self, key: str, src: BinaryIO, limit: Optional[int] = None) -> int:
        blob = self._bucket.blob(self._key(key))
        written = 0
        try:
            with blob.open("wb") as out:
                while chunk := src.read(CHUNK):
                    written += len(chunk)
                    if limit is not None and written > limit:
                        raise TooLarge()
                    out.write(chunk)
        except BaseException:
            try:
                blob.delete()            # 多半沒 commit，delete 會 404
            except Exception:
                pass
            raise
        return written

    def open(self, key: str) -> Optional[BinaryIO]:
        blob = self._bucket.blob(self._key(key))
        return blob.open("rb") if blob.exists() else None

    def size(self, key: str) -> Optional[int]:
        blob = self._bucket.get_blob(self._key(key))
        return blob.size if blob else None

    def exists(self, key: str) -> bool:
        return self._bucket.blob(self._key(key)).exists()

    def delete(self, key: str) -> None:
        blob = self._bucket.blob(self._key(key))
        if blob.exists():
            blob.delete()

    def delete_prefix(self, prefix: str) -> None:
        # 物件儲存沒有目錄，「刪掉一整組」就是刪掉同前綴的所有物件。
        # 前綴後面補斜線，不然 users/1 會連 users/10 一起帶走。
        p = self._key(prefix)
        p = p if p.endswith("/") else p + "/"
        for blob in self._bucket.list_blobs(prefix=p):
            blob.delete()


def _build():
    prefix = normalize_prefix(os.getenv("STORAGE_PREFIX"))
    if (os.getenv("STORAGE") or "local").lower() == "gcs":
        bucket = os.getenv("GCS_BUCKET")
        if not bucket:
            raise RuntimeError("STORAGE=gcs 但沒有設 GCS_BUCKET")
        if not prefix:
            # 不給預設值 —— 見 §4.5
            raise RuntimeError("STORAGE=gcs 一定要設 STORAGE_PREFIX（例如 demo / prod）")
        return GCS(bucket, prefix)
    # 本機的隔離通常已經由「每個環境各自的 UPLOAD_DIR」做掉了，所以前綴選填
    return LocalDisk(os.getenv("UPLOAD_DIR", "./uploads"), prefix)


backend = _build()
四個容易踩到的細節
  1. delete_prefix 的斜線 —— 少一個斜線，users/1 會把 users/10、users/19 一起刪掉。本機版用 rmtree 刪目錄天生不會犯這個錯，所以這條只有雲端那份會出事，測試要分開寫。
  2. 大小上限邊寫邊擋 —— 「寫完再量、超過就刪」會先把磁碟塞爆（在雲端是先把傳輸費付完）才退掉。
  3. 找不到就回 None —— 兩份實作行為要一致，不然換儲存體時錯誤處理會不一樣。
  4. key 的路徑檢查只有本機那份需要 —— 物件儲存沒有「上一層」的語意，但檔案系統有。這是兩份實作行為必須不同的少數地方之一，所以那條測試不要寫進共用的契約測試裡（見 §7）。
兩份實作的方法要一樣齊

exists()、delete_prefix() 這種「只有其中一份用得到」的方法最容易漏 —— 少一支，換儲存體的那天才會炸，而且是在正式環境炸。契約測試會逼你補齊 （見 §7）：測試同時跑過兩份實作，少一支就是 AttributeError。

4.2 下載端點​

物件儲存回的是串流不是路徑，所以 Content-Type 與 Content-Disposition 要自己補。

routes.py
import mimetypes
from urllib.parse import quote

from fastapi import APIRouter, Depends, HTTPException
from fastapi.responses import StreamingResponse

import storage

router = APIRouter()


def attachment_response(stream, filename: str | None, key: str = ""):
    """最小版；`Content-Disposition` 的正確做法見 §4.4，這裡先看主幹。"""
    media = mimetypes.guess_type(filename or key or "")[0] or "application/octet-stream"
    headers = {
        # 物件 key 帶隨機字串、內容不會變 → 可以放心設一年。
        # private：只有使用者自己的瀏覽器能快取，中間的代理不行。
        "Cache-Control": "private, max-age=31536000, immutable",
        "X-Content-Type-Options": "nosniff",
    }
    if filename:
        # RFC 5987。非 ASCII 檔名一定要用這個格式，不然中日韓檔名會變亂碼
        # safe="" —— quote() 預設不會編碼 `/`，檔名裡帶斜線就會生出壞掉的標頭
        headers["Content-Disposition"] = f"attachment; filename*=UTF-8''{quote(filename, safe='')}"
    return StreamingResponse(stream, media_type=media, headers=headers)


@router.get("/attachments/{attachment_id}/download")
def download(attachment_id: int, user=Depends(current_user), db=Depends(get_db)):
    att = db.get(Attachment, attachment_id)
    if not att:
        raise HTTPException(404, "not found")

    # ★ 兩層檢查缺一不可
    require_capability(user, "attachment.view")   # 這一類東西看不看得到
    assert_owns(user, att)                        # 這一筆屬不屬於他

    stream = storage.backend.open(att.key)
    if stream is None:
        raise HTTPException(404, "資料庫有紀錄但物件不存在")
    return attachment_response(stream, att.filename, att.key)
兩層檢查是不同的東西

「能力檢查」只管這一類資源看不看得到，管不到這一筆屬於誰。 只做前者的話，把 id 從 1 數到 N 就能把別人的檔案抓完。

反過來，如果你的資料表有 ON DELETE CASCADE 外鍵，父物件刪掉子物件就跟著沒了， 那「父物件還在嗎」這個檢查是多餘的 —— 由資料庫保證，不要在 router 再查一次。

4.3 上傳端點​

MAX_MB = 20


@router.post("/attachments")
def upload(file: UploadFile = File(...), user=Depends(current_user)):
    key = f"attachments/{user.id}/{uuid.uuid4().hex[:8]}_{safe_name(file.filename)}"
    try:
        size = storage.backend.save(key, file.file, MAX_MB * 1024 * 1024)
    except storage.TooLarge:
        raise HTTPException(413, f"檔案超過 {MAX_MB} MB 上限")
    finally:
        file.file.close()
    # ... 寫資料庫，key 存起來

一次傳多個檔的話要能整批回滾 —— 資料庫是一次寫入，檔案這邊也要一起成功 或一起沒有，不然儲存區會留下沒有任何資料列指向的垃圾：

written = []
try:
    for f in files:
        key = make_key(f)
        storage.backend.save(key, f.file, limit)
        written.append(key)
        rows.append(Attachment(key=key, ...))
except Exception:
    for k in written:              # 已經寫進去的收回來
        storage.backend.delete(k)
    raise
db.add_all(rows)
db.commit()

4.4 給檔的時候：inline 還是 attachment​

同一條上傳路徑進來的東西，出去的時候要分開對待。圖片跟 PDF 是拿來看的， 一律強制下載很難用；但內嵌顯示是有代價的。

內嵌別人上傳的檔案 = 在你的來源上執行別人的程式碼

大多數上傳端只會清理檔名裡的危險字元，不會擋副檔名 —— 所以 .html、.svg 傳得進來。這兩種如果讓瀏覽器內嵌顯示：

  • .html 直接就是網頁
  • .svg 是 XML，可以內嵌 <script>

而且它們是從你的 API 網域送出去的，所以那段腳本拿得到同源的 cookie、 localStorage、以及使用者的登入狀態。這是標準的儲存型 XSS。

正確做法是允許清單，不是黑名單：

#: 可以讓瀏覽器內嵌顯示的型別。**清單裡永遠不要加** svg / html / xml。
INLINE_OK = frozenset({
    "image/jpeg", "image/png", "image/gif", "image/webp", "image/bmp",
    "application/pdf",
})


def attachment_response(stream, filename: str | None, key: str = ""):
    media = mimetypes.guess_type(filename or key or "")[0] or "application/octet-stream"
    headers = {
        "Cache-Control": "private, max-age=31536000, immutable",
        # 不准瀏覽器自己猜型別。少了這個，一個叫 .txt 但內容是 HTML 的檔案
        # 會被嗅探成網頁執行 —— 上面那份允許清單就白做了。
        "X-Content-Type-Options": "nosniff",
    }
    disposition = "inline" if media in INLINE_OK else "attachment"
    if filename:
        headers["Content-Disposition"] = (
            f"{disposition}; filename*=UTF-8''{quote(filename, safe='')}"
        )
    else:
        headers["Content-Disposition"] = disposition
    return StreamingResponse(stream, media_type=media, headers=headers)

三件必須一起做的事：

做什麼少了會怎樣
①Content-Disposition 一定要送，不能省略沒送的話瀏覽器自己決定，等於預設內嵌
②inline 走允許清單黑名單永遠列不完（.xhtml、.svgz、.mhtml…）
③X-Content-Type-Options: nosniff瀏覽器會忽略你標的型別，照內容猜
更強的隔離：換一個網域

如果要放寬到「使用者上傳什麼都能預覽」，正規做法是把使用者內容放在另一個網域 （例如 usercontent.example.com），跟 API 與前端不同源。這樣就算跑了腳本也拿不到 主站的 cookie。做不到的話，就守住允許清單。

寫成測試的話，重點是守住「危險型別不准進清單」—— 有人想順手加 svg 進去時會變紅：

def test_dangerous_types_never_inline():
    for t in ("image/svg+xml", "text/html", "application/xhtml+xml",
              "application/xml", "text/xml", "text/javascript"):
        assert t not in INLINE_OK, f"{t} 跑進允許清單了"

    for name in ("evil.svg", "evil.html", "evil.xhtml"):
        r = attachment_response(io.BytesIO(b"<script>alert(1)</script>"), name)
        assert r.headers["content-disposition"].startswith("attachment")


def test_nosniff_always_present():
    for name in ("photo.jpg", "evil.html", "no-extension"):
        r = attachment_response(io.BytesIO(b"x"), name)
        assert r.headers["x-content-type-options"] == "nosniff"

4.5 檔案不是從瀏覽器來的：從第三方 API 匯入​

不是每個檔案都走 multipart 上傳。常見的另一種是後端自己去別的服務把檔案抓回來：

  • 通訊軟體的 webhook（LINE、Slack、WhatsApp）給你一個 message id， 要拿它去 content API 換檔案內容
  • 從外部系統同步附件
  • 使用者貼一個網址，要求存成附件

形狀不一樣，四個地方要特別小心。

① 邊抓邊寫，不要整包進記憶體​

最容易寫錯的一行：

# ❌ 整個檔案進記憶體。10 個人同時傳 20 MB 的影片就是 200 MB，
#    而且是在你的 worker 行程裡
content = requests.get(url).content
storage.backend.save(key, io.BytesIO(content))
# ✅ 串流轉存。記憶體用量固定在一個 chunk
with requests.get(url, stream=True, timeout=30) as r:
    r.raise_for_status()
    storage.backend.save(key, r.raw, limit=MAX_BYTES)

r.raw 有 .read(n)，跟儲存層要的介面一樣，所以直接接得上 —— 這就是抽那一層的 回報之一。（requests 要記得 stream=True，否則 r.raw 會是空的。）

② 對方給的檔名與型別都不能信​

第三方 API 回的 Content-Type 與 filename 是別人送的字串，不是事實。

# ❌ 直接拿來當 key 的一部分
key = f"imports/{resp.headers['x-filename']}"      # ../../etc/passwd

# ✅ 自己產 key，對方的檔名只當顯示用，而且要清乾淨
key = f"imports/{msg_id}/{uuid4().hex[:8]}_{safe_name(claimed_name)}"

safe_name() 至少要做：取 basename（去掉路徑）、白名單字元、限制長度。 ../ 這種東西進到 key 裡，在本機磁碟那份實作上就是任意路徑寫入。

顯示用的型別也一樣 —— 決定 inline / attachment 時，用你自己從副檔名推的 型別（見 §4.4），不要用對方宣稱的 Content-Type。

③ 大小上限要在下載的時候擋​

對方可能回一個沒有 Content-Length 的串流，或宣稱 1 KB 卻送 1 GB。 儲存層的「邊寫邊算」在這裡剛好派上用場 —— 超過就丟例外，連線斷掉， 已經寫進去的半截也不會留下。

順便設 timeout：沒設的話一個掛住的連線會佔住 worker 直到天荒地老。

④ Webhook 要能重試，所以要冪等​

通訊軟體的 webhook 幾乎都是「至少送一次」，同一則訊息可能送兩三次。 key 用隨機 uuid 的話，重試會存出重複的物件。

# 用來源的識別當 key 的一部分 —— 同一則訊息重送幾次都是同一個物件
key = f"imports/{channel_id}/{message_id}"
if storage.backend.exists(key):
    return                                   # 已經處理過

資料庫那邊也要對應的唯一鍵，兩邊一起才擋得住。

webhook 不要在請求裡做這件事

大部分平台要求 webhook 在幾秒內回應，超時就重送。抓檔案是網路 I/O，會超時。 收到就先回 200，把抓檔丟進背景工作（佇列、背景任務都行）， 不然你會拿到一堆重試，然後每一個重試又各自去抓一次檔案。

4.6 環境隔離：第一層前綴​

demo、staging、正式如果共用同一個 bucket，第一層一定要分開。

bucket/
├── demo/attachments/42/a1b2c3_contract.pdf
├── staging/attachments/42/...
└── prod/attachments/42/...

前綴放在儲存層裡，不進資料庫 —— 各環境的資料列可以長得一模一樣， 把正式的資料庫複製到 demo 也不用轉換任何欄位。

不要給前綴預設值

猜一個 prod 或空字串當預設，猜錯的後果是 demo 把檔案寫進正式的物件堆裡， 而且不會有任何錯誤訊息 —— 要等到有人發現檔案對不上才知道。 沒設就讓程式起不來，是這裡唯一安全的行為。

def _build():
    prefix = normalize_prefix(os.getenv("STORAGE_PREFIX"))
    if backend == "gcs":
        if not prefix:
            raise RuntimeError("STORAGE=gcs 一定要設 STORAGE_PREFIX（例如 demo / prod）")

更強的隔離是「各環境各一個 bucket」 —— 連 IAM 都分開，程式有 bug 也跨不過去。 前綴的好處是只要一個 bucket、一套設定；兩者可以並存（不同 bucket + 不同前綴）， 上面的程式碼兩種都支援。

三個容易漏掉的地方：

  1. 每一支方法都要冠前綴。 少冠一支就是那一支穿過隔離牆，而且是安靜地穿過去。
  2. 「刪一整組」要被前綴框住。 那是唯一一支會一次刪很多物件的，沒框住的話 demo 刪一組會把正式環境同名的那組一起帶走。
  3. 前綴的斜線要正規化。 /demo 沒處理會變成 //demo/... —— 在物件儲存上 那是合法但不同的名字，等於又多開了一個環境。

4.7 資料庫存什麼​

存物件 key（相對路徑），不要存完整網址。

✅  attachments/42/a1b2c3d4_contract.pdf
❌  https://storage.googleapis.com/my-bucket/attachments/42/...

存 key 的好處：換 bucket、換供應商、從本機磁碟搬上雲，資料庫一個字都不用改 —— 本機版是相對路徑、雲端版是 object name，同一個字串。

5. Web server 與反向代理​

後端串流時，前面那層代理有幾個預設值會扯後腿。

Nginx​

location /api/ {
    proxy_pass http://127.0.0.1:8000;

    # ① 關掉回應緩衝。開著的話 Nginx 會等整個檔案收完才開始送給瀏覽器，
    #    大檔的首位元組時間會等於整個下載時間，而且吃記憶體或落地成暫存檔。
    proxy_buffering off;

    # ② 上傳大小上限。預設 1MB，超過直接 413，而且錯誤訊息不會提到是 Nginx 擋的。
    client_max_body_size 25m;

    # ③ 別讓大檔下載被逾時砍斷
    proxy_read_timeout 300s;
    proxy_send_timeout 300s;

    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

Caddy​

Caddy 預設就是串流（不緩衝），大多數情況不用特別設定：

app.example.com {
    handle /api/* {
        reverse_proxy localhost:8000
    }

    handle {
        root * /var/www/app
        file_server
        try_files {path} {path}/ /index.html
    }
}
Caddy 的 handle 不能跟裸指令混用

同一個站台區塊裡，如果一部分用 handle {} 包起來、另一部分寫成裸指令 （直接寫 root、file_server、try_files），Caddy 的指令排序會讓 try_files 先跑，把 /api/* 也吃進 SPA 的 fallback，API 就會回傳 index.html。 要包就全部包。

應用伺服器​

項目設定
Worker 逾時拉長到足以送完最大的檔（gunicorn --timeout）
Worker 型別串流大檔時用 async worker，不然一個下載佔住一個 worker
上傳暫存確認暫存目錄有空間，且大檔不會整個進記憶體

6. 快取：CP 值最高的一項​

如果物件 key 帶了隨機字串（uuid4().hex[:8]_原始檔名），同一個 key 的內容 永遠不會變。這叫不可變資產，可以放心給最長的快取：

Cache-Control: private, max-age=31536000, immutable
  • private —— 只有使用者自己的瀏覽器能存，中間的共用代理不行（有權限的檔案一定要加這個）
  • immutable —— 連「重新整理時發 If-None-Match 問一下」都省掉
  • 更新檔案時產生新的 key，不要覆蓋舊的

效果：第二次看同一張圖，網路請求歸零。跨區存取時這一項省下的時間比任何優化都多。

縮圖​

如果畫面上是縮圖牆，注意下載完整原圖只為了畫一個 150×110 的方格有多浪費 —— 平均照片 370 KB、縮圖實際需要約 15 KB，96% 的位元組是白送的。

做法是加一個縮圖端點，第一次請求時縮好存回 bucket 的另一個前綴：

@router.get("/attachments/{attachment_id}/thumb")
def thumb(attachment_id: int, ...):
    att = ...            # 權限檢查照舊
    thumb_key = f"thumbs/{att.key}"

    stream = storage.backend.open(thumb_key)
    if stream is None:                        # 還沒縮過
        src = storage.backend.open(att.key)
        if src is None:
            raise HTTPException(404)
        buf = make_thumbnail(src, width=300)  # Pillow 之類
        storage.backend.save(thumb_key, buf)
        buf.seek(0)
        stream = buf

    return attachment_response(stream, None, thumb_key)

前端再配 loading="lazy"，捲不到的就不抓。

7. 測試：兩份實作跑同一組契約測試​

儲存層抽出來最大的好處就是這個。不要各測各的 —— 兩份是不同的程式碼， 只測本機那份的話，雲端那份的上限檢查可以整條拿掉都沒人發現。

正確做法是寫一組契約測試，用參數化 fixture 跑過每一份實作：

test_storage.py
@pytest.fixture(params=["local", "gcs"])
def make_storage(request, tmp_path):
    """回一個 make_storage(prefix="") 工廠。

    同一次測試裡拿到的都指向同一個底層儲存（本機是同一個 tmp_path、
    雲端是同一個假桶）—— 隔離的測試要能同時用「帶前綴」與「不帶前綴」
    兩個視角看同一批物件，才驗得出東西到底落在哪一層。
    """
    if request.param == "local":
        return lambda prefix="": storage.LocalDisk(str(tmp_path), prefix)

    bucket = FakeBucket()

    def make(prefix=""):
        g = storage.GCS.__new__(storage.GCS)   # 跳過 __init__，不建真的 Client
        g._bucket = bucket
        g.prefix = storage.normalize_prefix(prefix)
        return g

    return make

    s = make_storage()
    assert s.open("nope") is None
    assert s.size("nope") is None
    s.delete("nope")                    # 刪不存在的不該爆

雲端那份不必連網路 —— 它只透過 bucket 物件一個介面做事，塞一個假的進去就驗得完：

class FakeWriter:
    """模仿 blob.open("wb")：寫的先收著，離開 with 才 commit。
    真的物件儲存也是這個行為 —— 中途丟例外就不會產生物件。"""

    def __init__(self, blob):
        self.blob, self.buf = blob, bytearray()

    def write(self, chunk):
        self.buf += chunk

    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc, tb):
        if exc_type is None:
            self.blob.bucket.objects[self.blob.name] = bytes(self.buf)
        return False


class FakeBlob:
    def __init__(self, bucket, name):
        self.bucket, self.name = bucket, name

    def exists(self):
        return self.name in self.bucket.objects

    @property
    def size(self):
        return len(self.bucket.objects[self.name])

    def delete(self):
        self.bucket.objects.pop(self.name, None)

    def open(self, mode):
        if mode == "wb":
            return FakeWriter(self)
        return io.BytesIO(self.bucket.objects[self.name])


class FakeBucket:
    def __init__(self, **objects):
        self.objects = dict(objects)

    def blob(self, name):
        # 真的 SDK：不管物件在不在，都給你一個 handle
        return FakeBlob(self, name)

    def get_blob(self, name):
        # 真的 SDK：物件不存在時回 None。**跟 blob() 是兩件事** ——
        # 假物件少了這一支的話，`size()` 那條測試會是 AttributeError，
        # 而不是你以為在驗的「找不到要回 None」。
        b = FakeBlob(self, name)
        return b if b.exists() else None

    def list_blobs(self, prefix=""):
        return [FakeBlob(self, n) for n in sorted(self.objects) if n.startswith(prefix)]
用突變測試檢查測試本身

把某一行改壞（if limit is not None and written > limit: 改成 if False:）， 重跑測試，應該要變紅。沒變紅表示那一行沒有任何測試守著。

這招在儲存層特別值得做，因為有些錯誤平常跑起來完全正常，出事才發現： 前綴沒冠上、半截檔沒清掉、delete_prefix 少一個斜線。

8. 常見錯誤清單​

症狀原因
上傳大檔回 413，但後端沒有印任何 log反向代理的 client_max_body_size 擋掉了，請求根本沒到後端
大檔下載要等很久才開始傳proxy_buffering 沒關，代理在等整個檔案收完
簽名網址回 400做成 302 轉址，Authorization 被一起送到儲存服務
瀏覽器直連 bucket 被擋沒設 CORS
中日韓檔名變亂碼Content-Disposition 沒用 filename*=UTF-8''
刪掉一組物件，隔壁那組也不見了delete_prefix 的前綴沒補斜線
圖片明明存在卻顯示不出來Content-Type 沒設，瀏覽器當成 application/octet-stream
PDF 點下去變成下載，不能預覽Content-Disposition 一律寫死 attachment，沒做允許清單
使用者上傳的 SVG 竟然能執行腳本讓非允許清單的型別內嵌，或漏了 nosniff
從第三方 API 匯檔時記憶體爆掉沒用串流（requests 少了 stream=True），整包進記憶體
Webhook 進來的檔案重複好幾份key 用隨機值，webhook 重送就存出多份；要用來源識別當 key
換權限之後舊使用者還看得到用了簽名網址，效期內收不回來
測試在 CI 上很慢或不穩測試連到真的 bucket，沒有走本機實作
demo 的檔案出現在正式環境環境前綴沒設，或某一支方法忘了冠前綴
前綴寫成 /demo 之後檔案找不到沒正規化，變成 //demo/... 這個不同的名字
磁碟被上傳塞爆大小上限是「寫完才量」，不是邊寫邊擋
檔案出現在儲存根目錄外面本機實作沒擋 key 裡的 .. 或絕對路徑（雲端那份沒這個問題）
檔案存進去了但位置不對，也沒報錯key 是絕對路徑，被前綴接成 prefix//etc/... 這種名字
換儲存體之後某個端點噴 AttributeError兩份實作的方法沒對齊，而契約測試只跑了其中一份

9. 上線前檢查​

  • bucket 統一存取控制已啟用、防止公開存取已強制
  • 服務帳戶只有物件層級角色，且綁在 bucket 上不是專案上
  • 匿名 HTTP 打各種公開網址形式都回 403（含列出 bucket 內容）
  • 從不同網路再驗一次
  • 金鑰檔權限 600，不在版控、不在部署會同步的目錄裡
  • 下載端點有能力檢查與逐筆歸屬檢查
  • Content-Disposition 一定會送，inline 走允許清單（沒有 svg / html / xml）
  • 每個下載回應都有 X-Content-Type-Options: nosniff
  • 從第三方匯入的檔案：串流轉存、自己產 key、不信對方給的檔名與型別、可重試冪等
  • 反向代理的上傳上限與逾時已調整、回應緩衝已關閉
  • 回應有 Cache-Control: private, ..., immutable
  • 資料庫存的是 key 不是完整網址
  • 各環境的第一層前綴（或各自的 bucket）已分開，且沒設就起不來
  • 本機磁碟那條路還在，行為跟雲端實作一致（方法要一樣齊）
  • 本機實作擋掉 key 裡的 .. 與絕對路徑
  • 測試不連網路，且兩份實作跑同一組契約測試
  • 用 curl -w 量過你自己的實際延遲，不是照抄別人的數字
