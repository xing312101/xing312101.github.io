PWA 設定手冊

PWA（Progressive Web App）是「用網頁做出可以裝到手機主畫面、開起來沒有網址列」的一組瀏覽器標準。 不用上架、不用審核、不用維護兩份原生程式碼。

這份文件講怎麼設定、不同框架差在哪、以及為什麼裝不起來。

0. 先確認你真的需要 PWA​

PWA 值得做的情況只有兩種：

情況為什麼
使用者每天要開好幾次省掉「開瀏覽器 → 找書籤 → 等網址列縮起來」
現場作業要用相機或離線全螢幕、沒有網址列擋住、可以快取

如果使用者一週開一次，加書籤就夠了 —— PWA 的維護成本（圖示、快取失效、iOS 的各種例外）不划算。

1. 四個必要條件​

四個都要有，缺一個就裝不起來。瀏覽器不會告訴你缺哪一個，這是最花時間的地方。

1.1 manifest.json​

放在對外可以直接取得的路徑（通常是 public/manifest.json → 部署後是 /manifest.json）。

{
  "name": "完整名稱（安裝畫面顯示）",
  "short_name": "短名稱（主畫面圖示下方，超過 12 字會被截斷）",
  "start_url": "/app/",
  "scope": "/app/",
  "display": "standalone",
  "background_color": "#ffffff",
  "theme_color": "#4f46e5",
  "orientation": "portrait-primary",
  "icons": [
    { "src": "/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icon-512.png", "sizes": "512x512", "type": "image/png" },
    { "src": "/icon-512-maskable.png", "sizes": "512x512", "type": "image/png", "purpose": "maskable" }
  ]
}

幾個容易錯的：

  • start_url 是「點主畫面圖示會落在哪一頁」，不是網站首頁。如果 app 的入口是某個子路徑，就該指那裡，指 / 的話使用者每次都要再點兩下。

  • scope 決定「哪些網址算在 app 裡面」，而且不寫的話那個預設值會咬人。 沒寫 scope 時，它是 start_url 去掉最後一段路徑：

    start_url沒寫 scope 時的實際範圍
    /app/（有尾斜線）/app/ —— 只有 app 底下算
    /app（沒有尾斜線）/ —— 整個網站都算

    一個斜線的差別。範圍太寬，使用者點到官網、登出頁都留在沒有網址列的視窗裡；範圍太窄，站內正常的連結會跳出 standalone、開回瀏覽器分頁，症狀是「用一用網址列突然自己跑出來」。想清楚要哪一種，然後明寫，不要靠預設。

    start_url 一定要落在 scope 裡面

    這是最容易寫出來的無效組合：start_url: "/app" 配 scope: "/app/" —— 少一個尾斜線， /app 就不在 /app/ 的範圍內，Chrome 會判定 manifest 無效、整個裝不起來。 DevTools → Application → Manifest 會明講這件事，但你得先想到去看。

  • display: "standalone" 才會沒有網址列。"browser" 等於沒裝。

  • 圖示一定要放自己的檔案，不要指外部網址（CDN、圖庫）。安裝時抓不到就整個裝不起來，而且那張圖隨時可能失效或被換掉。

  • purpose: "maskable" 那張要另外做。Android 會把圖示裁成圓形／方角，沒有 maskable 版本就會把你的 logo 邊緣切掉。安全區是中心 80% 的圓。

不要用 "purpose": "any maskable" 一次兼兩用

把同一張圖同時宣告成 any 和 maskable 是很常見的寫法，看起來省事，實際上是把 「沒有留安全區的圖」交給系統去裁 —— Android 照樣會切掉邊緣，而你因為宣告了 maskable，連 Chrome 的檢查都不會提醒你。

要嘛真的另外做一張四周留白的（logo 縮到中心 80% 的圓內），要嘛就只宣告 any， 讓系統用它自己的白底外框去包。兩張圖各自單一用途，不要混。

在 HTML 的 <head> 引用：

<link rel="manifest" href="/manifest.json" />
<meta name="theme-color" content="#4f46e5" />
<meta name="viewport" content="width=device-width, initial-scale=1.0, viewport-fit=cover" />

1.2 service worker​

即使你不需要離線，也一定要有一個 —— 沒有註冊 service worker，Chrome 不會出現「安裝應用程式」。

最小可用的版本：

// public/sw.js
self.addEventListener('install', () => self.skipWaiting());
self.addEventListener('activate', (e) => e.waitUntil(self.clients.claim()));

// 這個 fetch handler 什麼都不做，是刻意的：它不呼叫 respondWith，
// 所以每個請求照樣走網路 —— 沒有任何東西被快取。
// 留著它是為了滿足「service worker 要有 fetch handler」這個舊版安裝條件。
self.addEventListener('fetch', () => {});
那一行 fetch handler 未必還是必要的

Chrome 的安裝條件這幾年放寬過幾次，較新的版本不一定還要求 fetch handler。 留著它成本是零、也不會快取任何東西，所以本文保留；但如果你看到有人的 service worker 沒有 fetch handler 卻裝得起來，那不是他運氣好。 要確認你的目標瀏覽器版本，以 DevTools → Application → Manifest 的實測為準。

註冊（進入點，例如 src/main.tsx）：

if ('serviceWorker' in navigator) {
  window.addEventListener('load', () => {
    navigator.serviceWorker.register('/sw.js').catch(() => {
      // 註冊失敗不該擋住網站本身
    });
  });
}

⚠️ service worker 是最容易造成「改了程式但使用者看到舊版」的東西。 如果你要做快取，務必先讀 spa-white-screen-debugging.md 那一份 —— 快取策略寫錯會讓 使用者永遠停在某一版，而且清快取也救不回來。不確定就不要快取。

1.3 HTTPS​

這是最常見的絆腳石。 下列全部需要安全來源（secure context）：

  • Service worker 註冊
  • 「加入主畫面」／「安裝應用程式」
  • 相機（<input capture>、getUserMedia）
  • 定位、推播

唯一的例外是 http://localhost（含 127.0.0.1）。

所以拿手機連內網 IP（http://192.168.1.50:5173）會發現裝不了 app、相機也叫不出來。 這不是程式的 bug，是瀏覽器的安全規則。內網要測的解法：

方法適用
ngrok http 5173 之類的隧道臨時測試最快
內網自簽憑證 + 手機安裝根憑證長期內網部署
正式網域 + Let's Encrypt上線
Chrome 的 chrome://flags/#unsafely-treat-insecure-origin-as-secure只能自己測，不要教使用者做

1.4 圖示檔案真的存在​

用 curl 確認，不要用眼睛看：

for f in manifest.json sw.js icon-192.png icon-512.png; do
  echo -n "  $f → "; curl -s -o /dev/null -w "%{http_code} %{content_type}\n" "https://你的網域/$f"
done

SPA 最陰險的地方：很多設定會把「找不到的路徑」一律回 index.html（給前端路由用）。 所以圖示不存在時你拿到的是 200 + text/html，不是 404 —— 看起來檔案在，實際上是一頁 HTML。 上面那段 curl 會印出 content_type，就是為了抓這個。

2. 各家框架的差異​

四個必要條件是瀏覽器標準，跟框架無關。 差別只在「靜態檔案放哪」與「有沒有現成的外掛」。

Vite（React / Vue / Svelte 都一樣）​

靜態檔案放 public/，建置時原樣複製到 dist/ 根目錄。

public/manifest.json  →  /manifest.json
public/sw.js          →  /sw.js
public/icon-192.png   →  /icon-192.png

index.html 在專案根目錄（不是 public/），直接編輯它加 <link rel="manifest">。

要自動化的話有 vite-plugin-pwa（用 Workbox 產生 service worker）：

// vite.config.ts
import { VitePWA } from 'vite-plugin-pwa';
export default defineConfig({
  plugins: [VitePWA({ registerType: 'autoUpdate', manifest: { /* 同上 */ } })],
});

手寫 sw.js 與 vite-plugin-pwa 二選一。兩個都有的話會互相覆蓋註冊， 症狀是「有時候更新得到、有時候更新不到」，非常難查。

Next.js​

public/ 的規則跟 Vite 一樣。但沒有 index.html —— meta 標籤要寫在程式裡：

// app/layout.tsx（App Router）
export const metadata = {
  manifest: '/manifest.json',
  appleWebApp: { capable: true, title: 'My App', statusBarStyle: 'default' },
};
export const viewport = { themeColor: '#4f46e5' };

Pages Router 則是在 pages/_document.tsx 的 <Head> 裡放 <link rel="manifest">。

App Router 也可以用 app/manifest.ts 直接產生 manifest（回傳一個物件）， 這樣它能讀環境變數 —— 多環境部署時很有用。

Service worker 一樣放 public/sw.js，註冊要放在 client component（'use client'）。

Next.js 的 SSR 會讓你以為 service worker 也在伺服器跑 —— 不會。它永遠是瀏覽器端的。

Nuxt​

public/（Nuxt 3）或 static/（Nuxt 2）。官方模組是 @vite-pwa/nuxt，設定寫在 nuxt.config.ts。

Angular​

ng add @angular/pwa 一行搞定 —— 它會產生 manifest、圖示、並啟用 @angular/service-worker （快取策略寫在 ngsw-config.json，不是手寫 sw.js）。

純靜態 HTML​

什麼都不用裝，四個檔案放對位置就好。PWA 本來就不需要框架。

差異總表​

靜態檔案meta 標籤寫在哪官方 PWA 工具
Vitepublic/根目錄的 index.htmlvite-plugin-pwa（社群）
Next.jspublic/app/layout.tsx 的 metadata無官方，用 next-pwa（社群）
Nuxt 3public/nuxt.config.ts 的 app.head@vite-pwa/nuxt
Angularsrc/assets/src/index.html@angular/pwa（官方）
純 HTML隨你HTML 裡無

3. 裝不起來的五個原因（照發生頻率排）​

① 不是 HTTPS​

看 §1.3。用內網 IP 測就會踩到。這一項佔一半以上。

② 圖示抓不到​

外部網址（CDN、圖庫）失效，或者 SPA 的 fallback 把 404 變成 200+HTML。用 §1.4 的 curl 確認。

③ manifest 的 JSON 壞了​

多一個逗號、註解（JSON 不能有註解）、或者被 SPA fallback 回 HTML。 Chrome DevTools → Application → Manifest 會直接告訴你解析結果。

④ service worker 沒註冊成功​

DevTools → Application → Service Workers。狀態要是 activated。 常見原因：sw.js 路徑錯（要在根目錄，不然作用範圍會被限縮）、或註冊那段程式碼從來沒執行到。

⑤ iOS 的例外​

Safari 對 PWA 的支援一直落後，而且規則會變。目前（2026）：

  • 只能用 Safari 安裝（Chrome for iOS 底層也是 WebKit，但沒有「加入主畫面」）

  • 使用者要手動點分享 → 加入主畫面。iOS 沒有自動的安裝提示，所以介面上要自己寫一段說明

  • apple-mobile-web-app-capable 這個 meta 還是要有，但兩個都放：

    <meta name="mobile-web-app-capable" content="yes" />
    <meta name="apple-mobile-web-app-capable" content="yes" />

    標準名稱是沒有 apple- 前綴的那個，Chrome DevTools 現在會提示帶前綴的版本已棄用； 但舊版 iOS 只認帶前綴的。兩行都寫最省事。

  • Web Push 在 iOS 16.4 之後才支援，而且只有已經加入主畫面的才收得到

除錯的起手式​

Chrome DevTools → Lighthouse → 勾 "Progressive Web App" → 跑一次。 它會直接列出缺哪一項，比一項一項猜快得多。
