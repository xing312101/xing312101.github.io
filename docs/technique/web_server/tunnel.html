本機服務開對外網址（webhook 測試）

LINE Bot、金流這類 webhook 只會打公開的 HTTPS 網址，打不到你的 localhost。 開發時用「通道（tunnel）」把本機的某個 port 接到一個公開網址上；連線是本機往外撥，不用開對外的 port。

這一系列分成四篇：

  • 本篇：怎麼選、通道接哪個 port、怎麼驗有沒有通、接 LINE webhook、共同的坑
  • ngrok：註冊就有一個固定網址；只有一個服務要對外時最省事
  • Cloudflare Tunnel（cloudflared）：不用帳號就能開臨時網址，可以同時開好幾條；網域放到 Cloudflare 就能固定
  • 自架中繼（SSH 反向通道）：自己開一台小機器（GCP 免費額度）放 nginx 和憑證，本機用 ssh -R 接上去；自己的網域、DNS 不用搬、好幾個服務各一個固定網址

最後更新：2026-11，依官方文件整理；cloudflared 的臨時通道、自架中繼、LINE 的 webhook API 實測過。後台的選單名稱常改，對不上時以官方文件為準。

結論

  • 只有一個服務、想要網址固定（webhook 後台只填一次）：ngrok，註冊就有固定的 dev domain。
  • 同時要給兩個以上的服務各一個網址：cloudflared 的臨時通道，一個服務開一條。
  • 要長期固定網址又不想付費：網域的 DNS 放到 Cloudflare，用 cloudflared 建固定通道。
  • 有自己的網域、DNS 不想搬到 Cloudflare，又要好幾個服務各一個固定網址：自架中繼。代價是要自己顧一台機器。

webhook 只要「POST 打得到」就好；但如果還要在手機上開網頁（LINE 的 LIFF、OAuth 登入回呼），ngrok 免費的警告頁和照路徑分流都會出問題： 網頁裡的檔案多半用根目錄起算的路徑（/assets/...），掛在 /app1/ 底下就找不到。

2. 通道要接哪個 port​

如果前端的開發伺服器會把 /api 轉給後端（Vite 的 server.proxy、或自己寫的 Node 伺服器），接前端那個 port 就好： 網頁和 webhook（/api/...）走同一個網址。前端沒有轉 /api 的話，webhook 要接後端的 port。

接前端時，網頁打開可能是 403：開發伺服器擋掉了通道的網域，見 §5。

只要 webhook、不用開網頁的服務，通道直接接後端就好：前端的開發伺服器就不會跟著對外（開發伺服器有過對外才會被利用的漏洞，見自架中繼 §10）。

3. 先用 curl 驗有沒有通​

URL=https://<通道網址>/<你的 webhook 路徑>
curl -s -o /dev/null -w '%{http_code}\n' "$URL"                       # GET
curl -s -o /dev/null -w '%{http_code}\n' -X POST \
     -H 'Content-Type: application/json' -d '{"events":[]}' "$URL"    # 沒帶簽章的 POST
看到什麼代表
GET 回 405（只收 POST 的端點）、POST 回 400／401（有驗簽的話）有通到你的程式，而且有在驗簽，正常
502，或 ngrok 的錯誤頁 ERR_NGROK_8012通道有開，但本機那個 port 沒有程式在聽（或通道指錯 port）；自架中繼的話，也可能是通道根本沒開
530（cloudflared）通道本身沒連上：cloudflared 沒在跑，或剛開還沒好
ngrok 的錯誤頁 ERR_NGROK_3200這個網址現在沒有 endpoint 在線上：ngrok 沒在跑
404路徑打錯，或通道接到了沒有這個路徑的服務（前端／後端接反了）；cloudflared 還可能是設定檔蓋掉了 --url
403，內容是 Blocked request開發伺服器擋掉了通道的網域，見 §5

4. 接 LINE webhook​

  1. 用測試用的 channel：在 LINE Developers 另外建一個 Messaging API channel 給本機用。 不要把正式 channel 的 Webhook URL 改成本機網址：一改，正式的機器人就收不到訊息；本機關掉之後更是誰都收不到。
  2. 本機的設定（.env 之類）放測試 channel 的 Channel secret（驗簽用）與 Channel access token（發訊用）。
  3. LINE Developers → 該 channel → Messaging API → Webhook URL 填 https://<通道網址>/<你的 webhook 路徑>，並打開 Use webhook。
    • ngrok：dev domain 不會變，填一次就好。
    • cloudflared 臨時通道：每次重開網址都變，要回來重填；常常重開的話就建固定通道。
    • 自架中繼：網址固定，填一次就好。
  4. 先用 §3 的 curl 確認有通。
  5. 再按 LINE 後台的 Verify：會送一個帶簽章的測試事件，回 200 才算成功。 失敗多半是本機放的 Channel secret 不是這個 channel 的。
  6. 要看 LINE 實際送來什麼：ngrok 開 4040；cloudflared 加 --loglevel debug。

也可以不開後台，用 Messaging API 設定、驗證（實測過；TOKEN 是那個 channel 的 Channel access token）：

read -rs TOKEN     # 貼上 token 後按 Enter：不會顯示，也不會進 shell 的歷史紀錄
H="Authorization: Bearer $TOKEN"

# 設 Webhook URL：成功回 {}
curl -s -X PUT https://api.line.me/v2/bot/channel/webhook/endpoint -H "$H" \
     -H 'Content-Type: application/json' -d '{"endpoint":"https://<通道網址>/<你的 webhook 路徑>"}'

# 看現在的設定：{"endpoint":"…","active":true}，active 就是 Use webhook 有沒有開
curl -s https://api.line.me/v2/bot/channel/webhook/endpoint -H "$H"

# 請 LINE 送一個測試事件到 Webhook URL（等於後台的 Verify）
curl -s -X POST https://api.line.me/v2/bot/channel/webhook/test -H "$H" \
     -H 'Content-Type: application/json' -d '{}'
# 通：{"success":true,…,"statusCode":200,"reason":"OK",…}
# 不通：{"success":false,…,"statusCode":400,"reason":"ERROR_STATUS_CODE",…}
  • 用 API 設好網址之後，active 還是 false：Use webhook 要到 LINE Developers 該 channel 的 Messaging API 分頁打開。
  • 還沒設過網址時，查詢會回 404 {"message":"Webhook endpoint not found"}。
  • 測試回 400：多半是本機放的 Channel secret 不是這個 channel 的，或程式還沒重開、沒讀到新的設定。

驗簽：LINE 用 Channel secret 對 request body 做 HMAC-SHA256，放在 X-Line-Signature。 程式要拿原始 body 算，先把 JSON 解析再轉回字串會算不對。

5. 共同的坑​

  • 網頁打開是 403「Blocked request. This host (...) is not allowed」：Vite 開發伺服器擋掉不認得的網域（防 DNS rebinding）。在 vite.config 加上通道的網域： 
    server: { allowedHosts: ['.trycloudflare.com', '.ngrok-free.dev', '.ngrok-free.app'] }   // 點開頭＝這個網域底下全部
    webpack-dev-server 顯示 Invalid Host header 是同一回事，設定也叫 allowedHosts。不要圖方便設成 true（全部放行）。 自架中繼的話，也可以在 nginx 把 Host 改成 localhost，就不用動 allowedHosts（自架中繼 §6）。
  • authtoken、Channel secret、通道的 token 不要貼在公開的地方（issue、聊天室、截圖、筆記、git）。不小心貼了，就到後台重設一組。
  • 通道＝把本機的服務放上網路：webhook 端點一定要驗簽；開發中的管理頁面、沒有登入保護的 API，也會一起被看到。用完就關。 開發伺服器要保持最新版：Vite 有過好幾個對外時才會被利用的讀檔漏洞（見自架中繼 §10）。
  • 正式環境不要靠通道撐：換成有固定網域、憑證的主機（見 nginx、SSL、DDNS）。
