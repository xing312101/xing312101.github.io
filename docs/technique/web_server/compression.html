Web server 回應壓縮總覽（gzip / Brotli / zstd）

把 HTML、CSS、JavaScript、JSON 這類文字內容壓縮後再送出，通常能讓傳輸量減少六到九成， 是 Web 效能最便宜的一項優化。但它也有一些不設定就會踩到的坑：串流回應卡住、 快取送錯版本、CPU 被高壓縮等級吃光、甚至是 BREACH 這類資安問題。

note

文中的實測數據與行為，是在 nginx 1.30.4（Alpine 套件，含 ngx_brotli 與 zstd 第三方模組）、 Apache httpd 2.4.68、Caddy 2.11.4、Node.js 22 + Express 5.2 + compression 1.8.2 上跑出來的。 不同版本、不同編譯選項的行為可能不同，請以你實際使用的版本與官方文件為準， 並用驗證一篇的方法自己確認一次。

1. 壓縮是怎麼協商的​

HTTP 回應壓縮是「用戶端說它看得懂什麼，伺服器挑一種」：

GET /assets/app.js HTTP/1.1
Host: example.com
Accept-Encoding: gzip, deflate, br, zstd
HTTP/1.1 200 OK
Content-Type: text/javascript
Content-Encoding: br
Vary: Accept-Encoding
標頭方向意義
Accept-Encoding請求用戶端能解的編碼清單，可以帶 q 值表達偏好，例如 br;q=1.0, gzip;q=0.8
Content-Encoding回應這個回應本體實際用了哪種編碼。沒有這個標頭就代表沒壓縮（identity）
Vary: Accept-Encoding回應告訴快取：「同一個網址會因 Accept-Encoding 不同而有不同版本」，快取必須分開存

幾個容易混淆的地方：

  • Content-Encoding 不是 Transfer-Encoding。 前者是「這份內容被編碼過」， 是端到端的；後者（例如 chunked）是逐段傳輸的方式，每一跳都可能不同。 平常講的回應壓縮都是 Content-Encoding。
  • 動態壓縮的回應通常沒有 Content-Length，而是改用 Transfer-Encoding: chunked（HTTP/1.1） 或以 DATA frame 的結束旗標標示結尾（HTTP/2）。因為伺服器邊壓邊送，事先不知道壓完多大。
  • 主流瀏覽器只在 HTTPS 上宣告 br 與 zstd。 用 http:// 測試時請求裡通常只有 gzip, deflate，看不到 Brotli 是正常的，不是設定錯了。

1.1 伺服器怎麼挑​

規格上，伺服器應該參考 q 值；實際上各家實作差很多。實測結果：

伺服器看不看 q 值同時支援多種時選哪個
nginx 1.30（gzip + ngx_brotli + zstd 模組）不看由模組實作與載入順序決定，沒有設定可以調；實測以動態模組載入時，內建的 gzip 排在第三方模組之後
Apache 2.4（BROTLI_COMPRESS;DEFLATE）不看照 filter 串的順序，寫在前面的先搶
Caddy 2.11看q 值相同時，照 encode 後面列出的順序（預設 zstd 優先，再來 gzip）
Express compression 1.8看q 值相同時 br 優先，再來 gzip

所以「我想要 br 優先」這種需求，在 nginx 上最穩的做法是只開你要的那幾種， 然後用 curl 實際確認送出的是哪一種。

2. 三種演算法​

項目gzipBrotli（br）Zstandard（zstd）
規格RFC 1952RFC 7932RFC 8878；HTTP 上的視窗限制見 RFC 9659
瀏覽器支援全部所有現代瀏覽器（僅 HTTPS）Chrome／Edge 123 起、Firefox 126 起；Safari 要到很新的版本才支援，請查 caniuse（僅 HTTPS）
等級範圍1–90–111–19（加 --ultra 可到 22）
特性最通用，壓縮與解壓都快文字壓縮率最好，但高等級（10、11）非常慢相同壓縮率下速度快，適合動態壓縮
nginx內建第三方 ngx_brotli第三方模組（官方說明為實驗性）
Apache httpdmod_deflatemod_brotli（2.4.26 起）沒有動態壓縮模組，但可以送預先壓縮的 .zst
Caddy內建標準版不支援動態壓縮；預先壓縮檔可以送內建
Express compression有有（1.8.0 起）沒有（1.8.2）

拿一個真實、已經 minify 過的前端函式庫檔案（131,835 bytes）實測，各種方式壓出來的大小：

方式大小相對原檔
不壓縮131,835 bytes100%
gzip 等級 5（nginx 動態）43,387 bytes32.9%
zstd 等級 3（nginx 動態）44,708 bytes33.9%
Brotli 等級 5（nginx 動態）41,037 bytes31.1%
gzip -9（預先壓縮）42,895 bytes32.5%
zstd -19（預先壓縮）39,566 bytes30.0%
Brotli -q 11（預先壓縮）37,180 bytes28.2%

光是 gzip 就把傳輸量降到三分之一；Brotli 最高等級再多省約 14%，但那個等級慢到只適合預先壓縮 （時間成本見常見陷阱）。

tip

數字會隨內容變化很大 —— 同一批測試裡，有一份結構重複的 JSON，zstd -19 反而比 Brotli -q 11 小將近一半。 拿你自己的檔案量一次，不要只看別人的 benchmark。

3. 該壓什麼、不該壓什麼​

壓縮只對「還有重複可以消除」的內容有效。已經壓縮過的格式再壓一次， 大小幾乎不變甚至變大，只是白白吃 CPU。

應該壓縮的 MIME 型別：

類別MIME 型別
網頁text/html、text/css、text/javascript、application/javascript
資料application/json、application/ld+json、application/manifest+json、application/xml、text/xml、application/rss+xml、application/atom+xml、text/plain、text/csv
圖形image/svg+xml（SVG 是文字）、image/x-icon（.ico 內部通常是未壓縮的點陣圖）
其他application/wasm、font/ttf、font/otf、application/vnd.ms-fontobject

不應該壓縮的：

類別例子原因
圖片JPEG、PNG、GIF、WebP、AVIF格式本身就已壓縮
影音video/*、audio/*（MP4、WebM、MP3、AAC、Opus）同上；而且動態壓縮會拿掉 Accept-Ranges，影片會無法拖曳進度
字型font/woff、font/woff2WOFF 內部用 zlib、WOFF2 內部用 Brotli，已經壓過
封存檔ZIP、gzip、7z、RAR、xz、zstd已壓縮
文件PDF、.docx／.xlsx／.pptx（本質是 ZIP）、EPUB內部多半已壓縮，收益很小
未知二進位application/octet-stream不知道內容，壓了多半沒用
串流text/event-stream 等不是壓不小，而是會被壓縮器的緩衝卡住，詳見常見陷阱
warning

不要用萬用字元開啟所有型別（例如 nginx 的 gzip_types *;）。它會把圖片、影片、 text/event-stream 全部吃進來。用白名單列出要壓的型別。

4. 快速決策​

  1. 靜態資源（build 產物：JS、CSS、SVG、WASM） —— build 時就產生 .br 與 .gz， 伺服器直接送（預先壓縮）。可以用最高等級，只花一次 CPU。
  2. 動態回應（HTML、API 的 JSON） —— 在反向代理（nginx、Apache、Caddy）做動態壓縮， 用中等等級：gzip 5 左右、Brotli 4–5、zstd 3。
  3. 串流回應（SSE、串流 API） —— 這些路徑排除壓縮，同時關掉代理的緩衝。
  4. HTTPS 回應裡同時有機密（CSRF token、個資）和使用者輸入的反射 —— 評估 BREACH，必要時對那些路徑關壓縮或遮罩 token。
  5. 前面還有 CDN 或另一層代理 —— 先決定由哪一層壓， 確認 Vary: Accept-Encoding 一路都在。
  6. 改完一定要驗證 —— 照驗證一篇檢查 Content-Encoding、大小與串流。

4.1 三十秒版本​

只想先開起來的話（細節與建議設定見各篇）：

nginx：放在 http 區塊內
gzip on;
gzip_vary on;
gzip_types text/plain text/css text/javascript application/javascript application/json application/xml image/svg+xml;
Apache httpd：需要 mod_deflate 與 mod_filter
AddOutputFilterByType DEFLATE text/html text/plain text/css text/javascript application/javascript application/json application/xml image/svg+xml
Caddy：Caddyfile 的站台區塊內
example.com {
	encode
	file_server
}
