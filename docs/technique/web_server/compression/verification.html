驗證回應壓縮是否生效

設定檔寫對、nginx -t 通過，不代表壓縮真的生效 —— 型別沒列到、前面的代理改了標頭、 後端自己先壓了，都會讓結果跟你想的不一樣。改完一定要實際量一次。

1. 用 curl 看回應標頭​

curl -s -o /dev/null -D - -H 'Accept-Encoding: gzip, br, zstd' https://example.com/
參數用途
-s不顯示進度條
-o /dev/null把回應本體丟掉（壓縮過的二進位內容印在終端機上只會是亂碼）
-D -把回應標頭印到標準輸出
-H 'Accept-Encoding: ...'宣告用戶端接受哪些編碼。curl 預設不送這個標頭，不加的話伺服器本來就不會壓

輸出裡要看的是：

HTTP/2 200
content-type: text/html; charset=utf-8
content-encoding: br
vary: Accept-Encoding

（HTTP/2 的標頭名稱一律小寫。）

  • 有 content-encoding: br（或 gzip、zstd）就是壓了；沒有這一行就是沒壓。
  • 要有 vary: Accept-Encoding，快取才不會送錯版本。
  • 動態壓縮通常沒有 content-length；預先壓縮檔則會有。

1.1 curl -I 的陷阱​

curl -I 送的是 HEAD 請求。它看起來比較省事，但伺服器對 HEAD 的處理不一定跟 GET 相同。實測：

伺服器curl -I -H 'Accept-Encoding: gzip' 的結果
nginx 1.30有 Content-Encoding，與 GET 一致
Apache httpd 2.4有 Content-Encoding 與壓縮後的 Content-Length
Caddy 2.11（動態壓縮）有 Content-Encoding，但 Content-Length 是一個跟內容無關的小數字
Express compression 1.8沒有 Content-Encoding（HEAD 請求一律不壓）

所以 curl -I 可以快速看一眼，結論請以 GET（-o /dev/null -D -）為準。

2. 比較傳輸大小​

url=https://example.com/assets/app.js
for enc in identity gzip br zstd; do
  curl -s -o /dev/null -H "Accept-Encoding: $enc" \
    -w "$enc\t%{size_download} bytes\t%header{content-encoding}\n" "$url"
done

輸出範例（一個 minify 過的 JavaScript 檔，經 nginx 動態壓縮）：

identity	131835 bytes
gzip	43387 bytes	gzip
br	41037 bytes	br
zstd	44708 bytes	zstd
寫法意義
%{size_download}收到的回應本體位元組數，也就是實際傳輸的（壓縮後）大小，不含標頭
%header{content-encoding}回應中某個標頭的值。需要 curl 7.84.0 以上；舊版可改用 -D - 再 grep
identity明確要求不壓縮，拿來當基準

哪一列的大小跟 identity 一樣、而且沒有編碼名稱，就代表那種編碼沒有生效。

tip

用 http:// 測試時，瀏覽器不會宣告 br 與 zstd，但 curl 會照你寫的送。 所以「curl 拿得到 br、瀏覽器拿不到」多半是因為瀏覽器那邊走的是 HTTP，不是伺服器設定問題。

3. --compressed​

curl -s --compressed https://example.com/ | head

--compressed 會讓 curl 自動送出它支援的所有編碼，並把回應解壓後再輸出，方便直接看內容。 要注意：

  • 它送出的編碼清單取決於 curl 編譯時帶了哪些函式庫。用 curl -V 看 Features 那一行有沒有 brotli、zstd。例如 macOS 內建的 curl 只帶 zlib，--compressed 只會送 deflate, gzip。
  • 實測 curl 8.x 加了 --compressed 時，%{size_download} 仍然是傳輸的（壓縮後）位元組數。 不過要比較各編碼的大小，還是用上一節手動指定 Accept-Encoding 最清楚。

4. 確認解壓後的內容正確​

預先壓縮最怕的是「送出去的 .br 是舊版本」。把回應解壓，跟原檔逐位元組比對：

curl -s -H 'Accept-Encoding: br'   https://example.com/assets/app.js | brotli -d | cmp - dist/assets/app.js && echo same
curl -s -H 'Accept-Encoding: gzip' https://example.com/assets/app.js | gzip -d   | cmp - dist/assets/app.js && echo same
curl -s -H 'Accept-Encoding: zstd' https://example.com/assets/app.js | zstd -dq  | cmp - dist/assets/app.js && echo same

印出 same 才算通過；cmp 報差異就是壓縮檔過期了。

5. 確認串流回應沒被卡住​

SSE 等串流回應被壓縮或緩衝時，事件會卡住、最後一次湧出。用時間戳看得最清楚：

curl -sN --compressed -H 'Accept: text/event-stream' https://example.com/events \
  | while IFS= read -r line; do
      if [ -n "$line" ]; then printf '%s  %s\n' "$(date +%T)" "$line"; fi
    done
參數用途
-N關掉 curl 自己的輸出緩衝，收到就印
--compressed萬一回應被壓縮了，讓 curl 解開，才看得懂內容
while read ...每一行前面加上收到的時間（略過事件之間的空行）

正常的樣子（每秒一個事件）：

16:09:01  data: {"n":0}
16:09:02  data: {"n":1}
16:09:03  data: {"n":2}

被卡住的樣子（全部同一秒到）：

16:09:05  data: {"n":0}
16:09:05  data: {"n":1}
16:09:05  data: {"n":2}

也順便看一下串流回應的標頭（--max-time 讓它幾秒後自己結束）：

curl -sN -o /dev/null -D - --max-time 5 \
  -H 'Accept: text/event-stream' -H 'Accept-Encoding: gzip, br, zstd' \
  https://example.com/events

串流回應不應該有 content-encoding。修正方式見常見陷阱。

6. 瀏覽器 DevTools​

6.1 Chrome／Edge​

  1. 開啟 DevTools（F12），切到 Network 面板，勾選 Disable cache，重新整理頁面。
  2. Size 欄顯示的是傳輸大小（標頭加上壓縮後的本體）。在 Network 面板的設定（齒輪圖示）打開 Big request rows，Size 欄會變成兩行：上面是傳輸大小，下面是解壓後的資源大小。 兩者差很多，就代表有壓縮。
  3. 面板最下方的狀態列會顯示整頁的「transferred」（傳輸量）與「resources」（資源解壓後的總量）。
  4. 想直接看每個請求的編碼：在請求列表的欄位標題上按右鍵 → Response Headers → Manage Header Columns → Add custom header，加入 Content-Encoding。
  5. 點單一請求 → Headers 分頁，在 Response Headers 裡確認 content-encoding 與 vary。
  6. 同樣在欄位選單可以打開 Protocol 欄，看是 http/1.1、h2 還是 h3。
  7. SSE 請求點進去有 EventStream 分頁，可以看到每個事件到達的時間。

Size 欄顯示 (memory cache) 或 (disk cache) 的請求是從快取拿的，沒有經過網路，不能拿來判斷壓縮。

6.2 Firefox​

  1. 開啟開發者工具（F12），切到 Network（網路）面板，勾選停用快取，重新整理。
  2. Transferred 欄是實際傳輸的位元組數，Size 欄是資源大小； 有壓縮時 Transferred 會明顯小於 Size。從快取拿的會顯示 cached 之類的字樣。
  3. 點單一請求，在 Headers 面板查看 content-encoding。
warning

用 http://localhost 開發時，瀏覽器不會宣告 br 與 zstd，只會看到 gzip 或完全沒壓。 要驗證 Brotli／zstd，請用 HTTPS 的環境，或用 curl 手動指定。

7. 伺服器端記錄​

在日誌裡記下每個回應的編碼與大小，可以長期觀察，也能抓到「某些路徑其實沒壓」。

nginx：http 區塊內
log_format compression '$time_iso8601 "$request" $status $body_bytes_sent '
                       '"$sent_http_content_encoding" ratio=$gzip_ratio';
access_log /var/log/nginx/compression.log compression;

實測輸出（時間欄省略）：

... "GET /assets/app.js HTTP/1.1" 200 43408 "gzip" ratio=3.04
... "GET /assets/app.js HTTP/1.1" 200 41050 "br" ratio=-
... "GET /assets/app.js HTTP/1.1" 200 131835 "-" ratio=-

$gzip_ratio 只有 gzip 模組會填，Brotli 回應顯示 -；$sent_http_content_encoding 則對各種編碼都有效。

Apache httpd 用 DeflateFilterNote／BrotliFilterNote 把壓縮前後的位元組數寫進日誌，範例見 mod_deflate 與 mod_brotli 的官方文件； 回應標頭可以用 LogFormat 的 %{Content-Encoding}o 記錄。

Caddy 用 log 指令開啟的存取日誌是 JSON，每筆都有 size（送出的位元組數）與 resp_headers（含 Content-Encoding）。

8. 檢查清單​

項目怎麼確認
HTML、CSS、JS、JSON、SVG 都有壓第 2 節的迴圈，每種型別挑一個網址
圖片、影片、字型（WOFF2）、ZIP 沒有壓同上，應該沒有 content-encoding
小於門檻的回應沒有壓找一個很小的 API 回應測試
每個壓縮回應都有 Vary: Accept-Encoding第 1 節
預先壓縮檔內容與原檔一致第 4 節
串流回應沒有壓縮、沒有被卡住第 5 節
經過 CDN 與直連原站的結果一致分別對兩個位址跑第 2 節
瀏覽器實際拿到的編碼第 6 節（要用 HTTPS）
