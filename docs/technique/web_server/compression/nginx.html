nginx 的回應壓縮設定

nginx 內建 gzip，Brotli 與 zstd 要靠第三方模組。這篇依序講：需要哪些模組、 最小設定、建議設定、Brotli、zstd、反向代理時的行為、串流回應怎麼排除、預先壓縮。

note

本文設定以 nginx 1.30（stable）驗證過。指令語法請以 nginx 官方文件為準；第三方模組請以各自的 README 為準。

1. 需要的模組​

功能模組是否內建
動態 gzipngx_http_gzip_module內建
送預先壓縮的 .gzngx_http_gzip_static_module需要 --with-http_gzip_static_module 編譯選項；nginx.org 官方套件有編入
替不支援 gzip 的用戶端解壓ngx_http_gunzip_module需要 --with-http_gunzip_module
Brotli（動態與預先壓縮）ngx_brotli（兩個模組：filter 與 static）第三方
zstd（動態與預先壓縮）例如 zstd-nginx-module第三方，README 自述為實驗性

確認你手上的 nginx 有什麼：

# 列出編譯選項，看有沒有 gzip_static／gunzip
nginx -V 2>&1 | tr ' ' '\n' | grep -E 'gzip_static|gunzip'

# 看動態模組目錄（路徑依發行版不同，常見的是這兩個）
ls /usr/lib/nginx/modules/ /etc/nginx/modules/ 2>/dev/null

1.1 安裝 ngx_brotli​

環境做法
Debian／Ubuntu（套件庫有提供的版本）sudo apt install libnginx-mod-http-brotli-filter libnginx-mod-http-brotli-static；套件會自動在 /etc/nginx/modules-enabled/ 放好 load_module，不用自己寫
Alpineapk add nginx-mod-http-brotli；載入設定放在 /etc/nginx/modules/
使用 nginx.org 官方套件，或自行編譯的 nginx下載同版本的 nginx 原始碼，依 ngx_brotli README 用 ./configure --with-compat --add-dynamic-module=/path/to/ngx_brotli 與 make modules 編出 .so，再用 load_module 載入
warning

動態模組必須跟正在執行的 nginx 版本與編譯參數相容。升級 nginx 後忘了重編模組， nginx -t 會回報模組版本不符或 is not binary compatible，而 nginx 會拒絕啟動。 用發行版套件的好處是模組會跟著 nginx 一起升級。

2. 最小設定（只開 gzip）​

/etc/nginx/conf.d/compression.conf
gzip on;
gzip_vary on;
gzip_types text/plain text/css text/javascript application/javascript
           application/json application/xml image/svg+xml;
指令用途
gzip on;開啟動態 gzip 壓縮
gzip_vary on;在壓縮相關的回應加上 Vary: Accept-Encoding，讓快取分開存壓縮與未壓縮版本
gzip_types ...;除了 text/html（永遠會壓）以外，還要壓哪些 MIME 型別。預設只有 text/html，不列的話 CSS、JS、JSON 都不會壓

/etc/nginx/conf.d/*.conf 在官方套件與 Debian 系的預設 nginx.conf 裡，都是在 http 區塊內被 include 的，所以這個檔案直接寫指令即可，不用再包一層 http { }。

danger

Debian／Ubuntu 的預設 /etc/nginx/nginx.conf 已經有一行 gzip on;。 你在 conf.d/ 再寫一次，nginx -t 會回報：

[emerg] "gzip" directive is duplicate in /etc/nginx/conf.d/compression.conf:1

解法是把 nginx.conf 那一行註解掉，或你的檔案不要再寫 gzip on;。 其他 gzip_* 指令在 Debian 的預設檔裡是註解狀態，不會衝突。

3. 建議設定​

/etc/nginx/conf.d/compression.conf
# ---- gzip（內建）----
gzip on;
gzip_comp_level 5;
gzip_min_length 256;
gzip_vary on;
gzip_proxied any;
gzip_types
    text/plain text/css text/xml text/javascript text/csv
    application/javascript application/json application/xml
    application/ld+json application/manifest+json
    application/rss+xml application/atom+xml
    application/wasm
    image/svg+xml image/x-icon
    font/ttf font/otf application/vnd.ms-fontobject;
# text/html 不用列，永遠會壓
# 不要列 text/event-stream，也不要寫 gzip_types *;
指令預設值建議值與說明
gzip_comp_level1範圍 1–9。5 左右是 CPU 與壓縮率的平衡點；6 以上多花的 CPU 換到的空間很少
gzip_min_length20小於這個位元組數就不壓。建議 256 以上。注意：只看回應的 Content-Length 標頭，後端用 chunked 送、沒有 Content-Length 的回應，不管多小都會壓
gzip_varyoff設 on。這個指令同時控制 ngx_brotli 與 zstd 模組的 Vary（實測關掉它，br／zstd 回應也不會帶 Vary）
gzip_proxiedoff設 any。見下方說明
gzip_typestext/html用白名單列出要壓的型別
gzip_http_version1.1保持預設。請求是 HTTP/1.0 的（少數舊代理、ab 壓測工具）不會被壓，測試時要注意
gzip_buffers32 4k 或 16 8k保持預設

3.1 gzip_proxied 跟 proxy_pass 無關​

這是最常被誤解的指令。它不是「要不要壓縮 proxy_pass 回來的回應」 （那些預設就會壓），而是：

當請求帶有 Via 標頭（代表這個請求是經過某個代理或 CDN 轉來的）時，要不要壓縮。

預設 off 的意思是：只要請求有 Via，gzip 就不壓。很多 CDN 回源時會帶 Via， 結果就是「直連有壓、經過 CDN 就沒壓」。實測：

請求gzip_proxied offgzip_proxied any
一般請求gzipgzip
帶 Via: 1.1 edge不壓gzip

另外，實測 ngx_brotli 與 zstd 模組不看 gzip_proxied，帶 Via 的請求照樣壓。

gzip_proxied 還有 expired、no-cache、no-store、private、no_last_modified、no_etag、auth 等選項，可以依回應標頭細分；除非你清楚前面那層快取的行為，否則用 any 並確保 Vary 正確即可。

3.2 nginx 動態壓縮的其他行為​

以下是實測或讀原始碼得知的行為，官方文件沒有全部寫出來：

  • 只壓縮狀態碼 200、403、404 的回應；206（Range）、5xx 等不壓。
  • 壓縮後會移除 Content-Length 與 Accept-Ranges，改用 chunked 傳送。 所以動態壓縮的回應無法續傳、影片無法拖曳 —— 這也是影片不該列進 gzip_types 的原因之一。
  • 強 ETag 會被改成弱 ETag（前面加 W/）。
  • 後端回應已經帶 Content-Encoding，nginx 不會再壓一次。

4. Brotli（ngx_brotli）​

先載入模組（用 Debian／Alpine 套件的話，套件已經幫你載入，跳過這步）：

/etc/nginx/nginx.conf（最上層，在 events 與 http 區塊之外）
load_module modules/ngx_http_brotli_filter_module.so;
load_module modules/ngx_http_brotli_static_module.so;

再加上設定：

/etc/nginx/conf.d/compression.conf（接在 gzip 設定後面）
# ---- Brotli（ngx_brotli）----
brotli on;
brotli_comp_level 5;
brotli_min_length 256;
brotli_types
    text/plain text/css text/xml text/javascript text/csv
    application/javascript application/json application/xml
    application/ld+json application/manifest+json
    application/rss+xml application/atom+xml
    application/wasm
    image/svg+xml image/x-icon
    font/ttf font/otf application/vnd.ms-fontobject;
指令預設值說明
brotlioff開啟動態 Brotli 壓縮
brotli_comp_level6範圍 0–11。動態壓縮建議 4–6；10、11 非常慢，只適合預先壓縮
brotli_min_length20最小長度門檻，同樣只看 Content-Length
brotli_typestext/html不會繼承 gzip_types，要自己再列一次
brotli_window512k滑動視窗大小，保持預設
brotli_staticoff預先壓縮，見第 9 節
brotli_buffers—已棄用、會被忽略
warning

只開 Brotli、沒寫 gzip_vary on; 的話，br 回應不會帶 Vary: Accept-Encoding。 不管你開了哪幾種壓縮，都要寫 gzip_vary on;。

瀏覽器只在 HTTPS 上宣告 br，所以用 http:// 測不到 Brotli 是正常的； 用 curl -H 'Accept-Encoding: br' 手動送就可以驗證（見驗證）。

5. zstd（第三方模組）​

nginx 官方沒有 zstd 模組。社群有幾個實作，例如 zstd-nginx-module， 其 README 自述為實驗性。Alpine 有 nginx-mod-http-zstd 套件；其他環境多半要自行編譯。

/etc/nginx/nginx.conf（最上層）
load_module modules/ngx_http_zstd_filter_module.so;
load_module modules/ngx_http_zstd_static_module.so;
http 區塊內
zstd on;
zstd_comp_level 3;     # 預設 1
zstd_min_length 256;   # 預設 20
zstd_types
    text/plain text/css text/javascript
    application/javascript application/json application/xml
    image/svg+xml;
tip

目前支援 zstd 的瀏覽器也都支援 Brotli。對大多數網站來說，gzip + Brotli 就足夠， zstd 可以等到有官方模組或你確定需要時再加。

6. 同時開多種編碼時，nginx 選哪一個​

nginx 不看 Accept-Encoding 的 q 值，也沒有「偏好順序」的指令。 請求同時接受多種時，哪個模組先處理就用哪個，取決於模組實作與載入順序。實測：

設定（動態模組）Accept-Encoding: gzip, deflate, br, zstdbr;q=0.5, gzip;q=1
gzip + Brotlibrbr（q 值被忽略）
gzip + Brotli + zstdzstdbr

建議：只開你真的需要的編碼，並用 curl 確認實際送出的是哪一種。

7. 反向代理時的行為​

nginx 會用同一套規則壓縮 proxy_pass 回來的回應（型別、最小長度等）。要注意三件事：

  1. nginx 預設會把用戶端的 Accept-Encoding 原封不動轉給後端。 後端如果自己會壓（例如 Express 開了 compression），回來就已經是壓縮過的， nginx 看到 Content-Encoding 就直接轉送，你在 nginx 設的等級、型別都不會生效。

  2. 想統一由 nginx 壓縮，就不要讓後端看到 Accept-Encoding：

    location /api/ {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Accept-Encoding "";   # 後端一律回未壓縮，由 nginx 壓
    }

    用 sub_filter 改寫後端回應內容時，也必須這樣做 —— sub_filter 無法處理壓縮過的內容。

  3. 後端一律回 gzip、而你要服務不支援 gzip 的用戶端時，可以用 gunzip on; （需要 ngx_http_gunzip_module）讓 nginx 替這些用戶端解壓。

8. 串流回應（SSE、串流 API）要排除​

壓縮器為了壓得小，會先把資料累積在緩衝區裡，湊夠了才輸出。 對 Server-Sent Events（text/event-stream）這種「一次送一小段、要馬上到」的回應， 結果就是事件卡在緩衝區，用戶端遲遲收不到。

text/event-stream 不在 gzip_types 預設值裡，所以只要你沒把它加進去、也沒寫 gzip_types *;， 預設就不會被壓。問題通常出在有人為了「全部都壓」而把它加進去。

實測（後端每秒送一個事件，共 5 個）：

設定結果
text/event-stream 被列進 gzip_types／brotli_types，proxy_buffering 維持預設 on5 個事件連同回應標頭，全部在第 5 秒一起到，中間什麼都沒有
同上，但 proxy_buffering off，或後端送 X-Accel-Buffering: no每秒到一個（每個事件都被 flush），但每個事件都付出壓縮的額外開銷
不壓縮，並 proxy_buffering off每秒到一個，回應標頭立即送出

建議寫法：

SSE 端點
location /events {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Connection "";

    proxy_buffering off;       # 收到多少就送多少
    proxy_cache off;           # 串流回應不要進快取
    proxy_read_timeout 1h;     # 預設 60s，事件間隔超過就會被斷線

    gzip off;
    brotli off;                # 有裝 ngx_brotli 才寫這行，否則會是 unknown directive
}
指令用途
proxy_http_version 1.1; 與 proxy_set_header Connection "";讓 nginx 用 HTTP/1.1 長連線連後端（預設是 HTTP/1.0）
proxy_buffering off;關閉代理緩衝。也可以改由後端在回應送 X-Accel-Buffering: no，只對那個回應生效
proxy_read_timeout兩次讀取之間的最長等待。SSE 通常搭配後端定期送註解行（: ping）當心跳
gzip off;／brotli off;保險起見明確關掉；即使上層有人改了 *_types 也不會影響這裡

其他串流情境：

  • FastCGI／uWSGI 後端：對應的是 fastcgi_buffering off;、uwsgi_buffering off;。
  • 長輪詢（long polling）：每次回應是一整包送出，壓縮不會讓它卡住； 要注意的是 proxy_read_timeout 必須大於伺服器端最長的等待時間。
  • 串流下載（邊產生邊送的匯出檔）：用 proxy_buffering off; 讓位元組持續流出； 若內容本身是 ZIP 等已壓縮格式，確保型別不在 gzip_types 裡。

9. 預先壓縮：gzip_static 與 brotli_static​

build 時先產生 app.js.gz、app.js.br（做法見預先壓縮）， nginx 看到用戶端支援、檔案也存在，就直接送壓縮檔，不必每次重壓。

server 區塊內
root /var/www/example;

location /assets/ {
    gzip_static on;
    brotli_static on;   # 需要 ngx_brotli 的 static 模組
    # zstd_static on;   # 需要 zstd 模組
}
指令說明
gzip_static on;請求 /assets/app.js 時，若用戶端接受 gzip 且 app.js.gz 存在，就送 .gz 並加上 Content-Encoding: gzip。會參考 gzip_http_version、gzip_proxied、gzip_disable、gzip_vary
gzip_static always;不檢查用戶端是否支援，一律送 .gz。用在磁碟上只有 .gz、沒有原檔的情況，通常要搭配 gunzip on; 替不支援 gzip 的用戶端解壓
brotli_static on;同上，對應 .br

實測行為：

  • 送出的是真正的檔案，所以有 Content-Length、支援 Range，ETag 是依壓縮檔本身算出的強 ETag。
  • 找不到 .gz／.br 時，會回到一般流程送原檔；若 gzip on; 也開著，就會改成動態壓縮。
  • 同時有 .br 與 .gz、用戶端兩種都接受時，實測送 .br。
warning

nginx 官方文件建議原檔與壓縮檔的修改時間要一致。更重要的是： nginx 只檢查壓縮檔「存不存在」，不會比對它是不是跟原檔同一版。 原檔更新了、舊的 .br 還留著，使用者就會拿到舊內容。每次 build 要清空輸出目錄再重新產生。

10. 驗證​

# 看回應標頭（用 GET，只把本體丟掉）
curl -s -o /dev/null -D - -H 'Accept-Encoding: br' https://example.com/assets/app.js

# 只印出編碼與傳輸大小（curl 7.84 以上）
curl -s -o /dev/null -H 'Accept-Encoding: gzip' \
  -w 'enc=%header{content-encoding} vary=%header{vary} bytes=%{size_download}\n' \
  https://example.com/assets/app.js

nginx 內建變數 $gzip_ratio（壓縮比）可以寫進存取日誌觀察效果。完整的驗證方法見驗證。
