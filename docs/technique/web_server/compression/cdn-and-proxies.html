前面還有 CDN 或另一層代理時

單一台伺服器的壓縮設定很直觀；一旦前面多了 CDN、負載平衡器或另一層反向代理， 每一層都可能壓縮、解壓、緩衝、快取，問題就從「有沒有壓」變成「是哪一層壓的、中間有沒有被動過」。

瀏覽器 ──HTTPS──▶ CDN 邊緣節點 ──▶ 負載平衡器 ──▶ 反向代理（nginx／Apache／Caddy） ──▶ 應用程式

本文不針對特定 CDN 供應商；各家的預設行為差異很大，實際行為請以你使用的服務的官方文件為準， 並用驗證一篇的方法分別從邊緣與原站量測。

1. 由哪一層壓​

位置優點缺點
CDN 邊緣離使用者最近；原站省 CPU；有些 CDN 會替你做 Brotli 或 zstd原站到 CDN 的回源流量沒壓；壓哪些型別、用什麼等級由供應商決定
原站反向代理行為完全可控；可以送預先壓縮檔（最高壓縮率）；回源流量也省下來動態內容要花原站 CPU
應用程式可以逐回應決定見應用程式層壓縮

原則：

  1. 每個回應只壓一次。 已經壓縮過的回應，中間層不要解開再壓（除非它必須改寫內容，見第 5 節）。
  2. 靜態資源在原站預先壓縮，CDN 只負責依 Vary 快取各個版本並轉送。
  3. 原站做不到時才讓 CDN 壓，並確認 CDN 會壓你需要的型別（例如 application/json）。

2. 原站要注意的設定​

2.1 nginx 的 gzip_proxied​

CDN 或代理轉來的請求常會帶 Via 標頭，而 nginx 的 gzip_proxied 預設 off， 意思是「帶 Via 的請求不壓」。實測：

請求gzip_proxied off（預設）gzip_proxied any
一般請求gzipgzip
帶 Via: 1.1 edge不壓gzip

所以常見的症狀是「直連原站有壓，經過 CDN 就沒壓」。原站用 nginx 時，設定 gzip_proxied any; 並確保 gzip_vary on;。（實測 ngx_brotli 不看這個設定。）詳見 nginx 第 3.1 節。

2.2 回源時的 Accept-Encoding 可能跟瀏覽器不同​

有些 CDN 回源時會改寫 Accept-Encoding（例如只送 gzip），再由邊緣自己決定給瀏覽器什麼。 要模擬 CDN 回源，直接對原站送一樣的標頭：

curl -s -o /dev/null -D - \
  -H 'Host: example.com' \
  -H 'Accept-Encoding: gzip' \
  -H 'Via: 1.1 edge' \
  https://origin.example.com/assets/app.js

（origin.example.com 換成你的原站位址；原站憑證只對正式網域有效時，改用 curl --resolve。）

3. Vary 與快取鍵​

同一個網址會因 Accept-Encoding 不同而有不同的回應內容，快取必須知道這件事：

情況後果
壓縮回應沒有 Vary: Accept-Encoding快取只存一份。第一個請求是 br，之後不支援 br 的用戶端也拿到 br —— 畫面變成亂碼或空白
有 Vary: Accept-Encoding快取依 Accept-Encoding 分開存 —— 這是正確行為
Vary: *許多快取乾脆不存
Vary: User-Agent幾乎每個瀏覽器版本一份，快取命中率大跌

Accept-Encoding 的原始值五花八門（gzip, deflate, br、gzip, deflate, br, zstd、順序不同……）， 如果快取直接拿原始字串當鍵，同一個檔案會被存成很多份。多數 CDN 會把它正規化成少數幾類 （例如「支援 br」「只支援 gzip」「都不支援」），請查你的 CDN 怎麼做。

自己架的快取層也一樣：nginx 的 proxy_cache 從 1.7.7 起會依後端回應的 Vary 分開存， 前提是後端（或 nginx 自己的壓縮）有送出正確的 Vary。

danger

「偶爾有使用者看到亂碼或白畫面，清快取就好」，十之八九是某一層的壓縮回應少了 Vary。 逐層用 curl -D - 檢查回應裡有沒有 Vary: Accept-Encoding。

4. 不要讓中間層改內容：Cache-Control: no-transform​

依 RFC 9111，回應帶 Cache-Control: no-transform 時， 中間層不得轉換內容（包含改變編碼）。實測與原始碼：

元件看到回應的 no-transform
Caddy encode不壓縮
Express compression不壓縮
nginx gzip不看，照壓
Apache mod_deflate／mod_brotli不看，照壓
CDN依供應商而定，請查文件

所以不能只靠 no-transform 讓 nginx 或 Apache 不壓，還是要在它們的設定裡排除。

適合加 no-transform 的情境：SSE 等串流回應、需要逐位元組一致的下載檔。 一般網頁與 API 不需要，否則 CDN 就不會替你壓縮了。

5. 中間層需要改寫內容時​

有些代理功能要讀或改回應本體，例如 nginx 的 sub_filter（替換字串）、注入分析碼、 Apache 的 mod_substitute。它們無法處理壓縮過的內容，所以要讓後端回未壓縮的版本， 由最外層再壓：

伺服器做法
nginxproxy_set_header Accept-Encoding "";，後端就會回未壓縮內容；nginx 改寫完再依自己的設定壓縮
Caddyreverse_proxy 區塊內 header_up -Accept-Encoding（實測有效）
Apache httpd不要用 RequestHeader unset Accept-Encoding（實測會連 Apache 自己的壓縮一起關掉）。後端只回 gzip 時，可以用 mod_deflate 提供的 INFLATE 輸出 filter 先解壓，見 mod_deflate 文件；最單純的做法是關掉後端的壓縮

6. 串流回應經過 CDN 與負載平衡器​

SSE 或其他串流回應，在應用程式與原站反向代理都處理好之後，仍可能在外層卡住：

問題說明對策
外層緩衝部分 CDN 或負載平衡器預設會緩衝回應，或對可壓縮型別做壓縮查供應商對 SSE／串流的說明；回應加 Cache-Control: no-cache, no-transform；讓串流路徑不經快取
閒置逾時負載平衡器與 CDN 通常有閒置逾時，一段時間沒有資料就斷線伺服器定期送 SSE 註解行（例如每 15–30 秒送 : ping）當心跳；逾時值請查供應商文件
快取了串流串流回應被當成一般回應快取Cache-Control: no-cache 或 no-store，並在 CDN 設定排除該路徑
連線數瀏覽器到邊緣若只走 HTTP/1.1，SSE 會佔掉每個網域 6 條連線之一確認邊緣有開 HTTP/2（見延伸閱讀）

7. TLS 在 CDN 終止也一樣要注意 BREACH​

BREACH 攻擊的條件是「HTTPS + HTTP 壓縮 + 回應裡同時有機密與使用者輸入的反射」， 跟壓縮發生在哪一層無關。CDN 在邊緣替你壓縮，一樣符合條件。見常見陷阱：BREACH。

8. 檢查清單​

  • 決定好由哪一層壓縮，其他層不重複壓
  • 原站用 nginx 時，gzip_proxied any;、gzip_vary on;
  • 每一層的壓縮回應都帶 Vary: Accept-Encoding
  • 分別從邊緣與原站量過 Content-Encoding 與大小
  • 需要改寫內容的代理，後端回的是未壓縮內容
  • 串流路徑：不壓縮、不快取、不緩衝、有心跳，且逾時設定足夠
  • 改了壓縮設定後，清除（purge）CDN 上已快取的舊版本
