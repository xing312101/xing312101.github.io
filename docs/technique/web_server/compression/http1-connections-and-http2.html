延伸閱讀：HTTP/1.1 連線數限制與 HTTP/2 多工

這一篇不是在講壓縮本身，而是跟串流回應一起出現的另一個問題： 長連線會佔掉瀏覽器的連線數。 排查「SSE 卡住」時常常兩個問題混在一起，所以放在這裡一起說明。

1. HTTP/1.1：一條連線同一時間只能跑一個請求​

HTTP/1.1 的一條 TCP 連線，同一時間只能處理一個請求與回應。要同時載入多個資源，瀏覽器就開多條連線， 但主流瀏覽器對同一個來源最多只開 6 條。

Chrome DevTools 的官方說明就把這寫在請求時序的 Queueing 階段：已經有 6 條 TCP 連線開著， 這是上限（只適用於 HTTP/1.0 與 HTTP/1.1）。

2. 長連線佔掉連線數​

SSE、串流 API、長輪詢的共同點是：一個請求會佔住一條連線很久。在 HTTP/1.1 下：

狀況結果
頁面開了 1 條 SSE剩 5 條給其他請求，通常還好
使用者開了 6 個分頁，每頁 1 條 SSE6 條全被佔滿，第 7 個請求（包含一般的 API、圖片）開始排隊，頁面看起來卡死
頁面同時有 SSE、長輪詢、大檔下載同上，只是更快發生

依 MDN 的 EventSource 說明， 這個限制是以瀏覽器加網域計算，所有分頁共用；Chrome 與 Firefox 都已將相關議題標記為不修正。

在 DevTools 裡的樣子：請求的 Timing 分頁中 Queueing 或 Stalled 時間很長， 而且關掉其他分頁就恢復。這跟「串流被壓縮器卡住」（事件延遲後一次湧出）的症狀不同，可以用這點區分。

3. HTTP/2：一條連線上多工​

HTTP/2 在一條 TCP 連線上同時跑多個「串流」（stream），每個請求／回應是一個串流，彼此交錯傳送。 長連線只佔掉一個串流，不會卡住其他請求。

同時可以開幾個串流，由伺服器在連線建立時宣告：

伺服器設定預設值
nginxhttp2_max_concurrent_streams128
Apache httpd（mod_http2）H2MaxSessionStreams100

MDN 的說明中也提到，HTTP/2 下同時的串流數由伺服器與用戶端協商，預設為 100。

HTTP/2 仍有一個限制：底層還是一條 TCP 連線，封包遺失時所有串流一起等重傳（TCP 層的 head-of-line blocking）。 HTTP/3 改用 QUIC（跑在 UDP 上），每個串流獨立處理遺失，才解決這一點。

4. 跟回應壓縮的關係​

項目說明
本體壓縮HTTP/2 不改變回應本體的壓縮方式，Content-Encoding、Vary 的規則完全一樣
標頭壓縮HTTP/2 用 HPACK、HTTP/3 用 QPACK 壓縮標頭，這是協定內建的，不需要（也不能）設定 gzip
HTTPS瀏覽器只在 HTTPS 上使用 HTTP/2，也只在 HTTPS 上宣告 br、zstd。開 HTTPS 同時解決兩件事
串流回應HTTP/2 解決了「佔連線數」，但解決不了「被壓縮器或代理緩衝卡住」，後者還是要照常見陷阱排除
反向代理到後端瀏覽器到反向代理走 HTTP/2，不代表反向代理到後端也是。後端那一段通常是 HTTP/1.1，長連線會佔用後端的連線，要注意代理的連線池與後端的並行上限

5. 各伺服器啟用 HTTP/2​

伺服器做法
nginx1.25.1 起在 server 區塊寫 http2 on;；較舊版本是在 listen 443 ssl http2; 加參數（新版本已標記為棄用）。見 ngx_http_v2_module
Apache httpd載入 mod_http2，設定 Protocols h2 http/1.1。MPM 的選擇會影響效果，見 HTTP/2 指南
CaddyHTTPS 站台預設就開 HTTP/2 與 HTTP/3，不需要設定
nginx 1.25.1 以上
server {
    listen 443 ssl;
    http2 on;
    server_name example.com;

    ssl_certificate     /etc/ssl/example.com/fullchain.pem;
    ssl_certificate_key /etc/ssl/example.com/privkey.pem;
}
Apache httpd
Protocols h2 http/1.1

確認實際用的協定：

curl -s -o /dev/null -w '%{http_version}\n' https://example.com/
# 2 表示 HTTP/2；1.1 表示 HTTP/1.1

或在 DevTools 的 Network 面板打開 Protocol 欄（h2、h3、http/1.1）。

6. 延伸：過去的最佳化手法在 HTTP/2 下可能變成反效果​

  • 網域分割（domain sharding）：把資源分散到多個子網域以突破 6 條連線限制。 在 HTTP/2 下反而多了 DNS 查詢與 TLS 交握，也無法共用同一條連線。
  • 把所有 JS／CSS 合併成一個大檔：在 HTTP/1.1 下減少請求數很重要； 在 HTTP/2 下適度拆分反而對快取更友善（改一個模組不必讓整包失效）。但檔案太碎仍有成本，要實測。
