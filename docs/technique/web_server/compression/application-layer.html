應用程式層壓縮

多數 Web 框架都有壓縮的 middleware，一行就能開。問題是：前面已經有 nginx、Apache 或 Caddy 時， 兩邊都開不會壓兩次，但只有一邊的設定會生效，而且常常不是你以為的那一邊。

1. 誰來壓​

情境建議
前面有反向代理（nginx、Apache、Caddy）交給反向代理。Express 官方的效能建議也是這麼寫：高流量的正式環境，最好在反向代理層壓縮，這時就不需要 compression middleware
應用程式直接對外，前面沒有任何代理，平台也不幫你壓在應用程式層壓
需要「依每個回應」細緻決定（例如依使用者、依回應內容）應用程式層比較彈性；但只是依路徑排除的話，反向代理也做得到
前面有 CDN見 CDN 與多層代理，先決定壓縮發生在哪一層

交給反向代理的理由：

  • 壓縮實作是 C 或 Go，效能較好，也不佔用應用程式行程的 CPU；
  • 設定集中在一個地方，靜態檔、API、各個後端服務都套同一套規則；
  • 反向代理本來就要處理 TLS、HTTP/2，壓縮放在同一層最自然。

2. Express：compression​

npm install compression

2.1 最小設定​

app.js
import express from 'express';
import compression from 'compression';

const app = express();
app.use(compression());   // 要放在所有路由與 express.static 之前

// ... 你的路由

app.use(compression()) 會包住它之後註冊的所有路由；放在路由後面就不會生效。

2.2 建議設定​

app.js
import zlib from 'node:zlib';
import express from 'express';
import compression from 'compression';

const app = express();

app.use(compression({
  threshold: 1024,   // 小於 1 KB 不壓（預設值）
  level: 6,          // gzip／deflate 等級，0–9；預設 -1 等同 6
  brotli: {
    params: {
      [zlib.constants.BROTLI_PARAM_QUALITY]: 4,   // Brotli 品質 0–11；套件預設 4
    },
  },
  filter(req, res) {
    // 串流端點不壓（見第 3 節）
    if (req.path.startsWith('/events')) return false;
    // 其他交給預設判斷：依 Content-Type 決定是否值得壓
    return compression.filter(req, res);
  },
}));
選項預設值說明
threshold1kb小於這個大小不壓。回應大小事先不知道時（沒有 Content-Length），一律當作超過
level-1（等同 6）gzip／deflate 的等級
brotli品質 4傳給 Node.js zlib 的 Brotli 選項；params 會蓋過預設值
filtercompression.filter回傳 false 就不壓。預設依 Content-Type 判斷是否為可壓縮型別
enforceEncodingidentity請求完全沒有 Accept-Encoding 時用哪種編碼，保持預設

以 compression 1.8.2 實測的行為：

  • 支援 br（1.8.0 起）、gzip、deflate；不支援 zstd。
  • 會看 q 值；q 值相同時 br 優先。
  • 回應帶 Cache-Control: no-transform 時不壓。
  • HEAD 請求不壓。所以用 curl -I 檢查會看不到 Content-Encoding，誤以為沒生效 —— 請用 GET（見驗證）。
  • 會加上 Vary: Accept-Encoding。

3. SSE 與其他串流回應​

compression 為了壓得好，會把輸出累積在緩衝區裡。SSE 這種一次寫一小段的回應， 事件就會卡住。官方 README 的解法是每次寫完呼叫它提供的 res.flush()。實測 （每秒送一個事件，共 5 個）：

寫法結果
經過 compression，沒有呼叫 res.flush()5 個事件連同回應標頭，全部在第 5 秒一起到
每次 res.write() 後呼叫 res.flush()每秒到一個（被壓縮，每個事件都有額外開銷）
回應設 Cache-Control: no-cache, no-transform不壓縮，每秒到一個
用 filter 排除這個路徑不壓縮，每秒到一個

建議直接排除，最單純：

排除串流端點
app.use(compression({
  filter(req, res) {
    if (req.path.startsWith('/events')) return false;
    return compression.filter(req, res);
  },
}));

app.get('/events', (req, res) => {
  res.setHeader('Content-Type', 'text/event-stream');
  res.setHeader('Cache-Control', 'no-cache, no-transform');
  res.flushHeaders();   // 先把回應標頭送出去，用戶端馬上知道連線成功

  const timer = setInterval(() => {
    res.write(`data: ${JSON.stringify({ now: Date.now() })}\n\n`);
  }, 1000);

  req.on('close', () => clearInterval(timer));
});

真的要壓縮串流，就在每次寫完後呼叫 res.flush()：

壓縮但每次都 flush
res.write(`data: ${payload}\n\n`);
res.flush();   // compression 加上的方法，把已壓縮的部分立刻送出

同樣的問題也會出現在任何「邊產生邊送」的回應，例如逐行輸出 JSON 的串流 API。

warning

即使應用程式正確 flush 了，前面的反向代理或 CDN 也可能把它緩衝住。 串流端點要從應用程式一路檢查到最外層：nginx、 Apache、Caddy、 CDN。

4. 放在反向代理後面​

兩邊都開壓縮時，實際發生的事：

  1. 反向代理把用戶端的 Accept-Encoding 轉給應用程式；
  2. 應用程式依自己的設定壓好，回應帶 Content-Encoding；
  3. 反向代理看到已經壓過，原樣轉送。

結果是反向代理的壓縮設定對這些回應完全不生效。實測 nginx 與 Caddy 在 Express（開了 compression）前面，用戶端要 br，拿到的就是 Express 以它的預設品質壓的 br。

選一邊就好：

做法設定
由應用程式壓反向代理什麼都不用改（已壓縮的回應它不會再動）
由反向代理壓（建議）最直接：把應用程式的 compression middleware 拿掉
由反向代理壓，但暫時不能改應用程式nginx：proxy_set_header Accept-Encoding "";
Caddy：reverse_proxy 區塊內 header_up -Accept-Encoding
warning

Apache 不要用 RequestHeader unset Accept-Encoding 來做這件事。 實測它會把請求上的 Accept-Encoding 整個拿掉，連 Apache 自己的 mod_deflate／mod_brotli 也看不到， 結果變成兩邊都不壓。在 Apache 後面，請直接關掉應用程式的壓縮。

另外，應用程式與反向代理之間通常是本機或同一個內網，這一段壓縮只是讓兩邊都多花 CPU， 沒有節省到真正貴的頻寬。

5. 其他框架​

各框架都有對應元件，選項與預設值差很多，請以官方文件為準：

框架元件文件
Fastify@fastify/compressGitHub
Koakoa-compressGitHub
Starlette／FastAPIGZipMiddlewareStarlette、FastAPI
DjangoGZipMiddlewareDjango middleware（文件中也有 BREACH 相關說明）
ASP.NET CoreResponse Compression Middleware官方文件
Go（net/http）標準函式庫沒有現成 middleware，常見的是第三方套件，例如 gzhttpklauspost/compress/gzhttp

不管用哪個框架，都要確認三件事：

  1. 串流回應怎麼處理（排除，或每次 flush）；
  2. 有沒有最小長度門檻；
  3. 前面的反向代理是不是也在壓，兩邊的設定哪一邊實際生效。

6. 無伺服器與 PaaS 平台​

很多託管平台或其前端的負載平衡器會自動壓縮回應，也可能完全不壓。 部署前後各用 curl 看一次 Content-Encoding，再決定應用程式層要不要開， 不要假設。
