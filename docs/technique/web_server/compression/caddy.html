Caddy 的回應壓縮設定

Caddy 的壓縮由 encode 指令負責，標準版內建 gzip 與 zstd； Brotli 不能動態壓縮，但 file_server 可以送預先壓縮好的 .br 檔。 Caddy 的站台預設就走 HTTPS（並開 HTTP/2 與 HTTP/3）；瀏覽器只在 HTTPS 上宣告 br、zstd， 所以用 Caddy 預設設定時，這兩種編碼都能協商得到。

note

本文設定以 Caddy 2.11.4 驗證過。指令語法請以 Caddy 官方文件為準。

1. 支援的編碼​

編碼動態壓縮（encode）預先壓縮（file_server precompressed）
gzip標準版內建支援（.gz）
zstd標準版內建支援（.zst）
Brotli標準版不支援支援（.br）

確認你的 Caddy 有哪些壓縮模組：

caddy list-modules | grep http.encoders
# http.encoders.gzip
# http.encoders.zstd

在標準版寫 encode br，caddy validate 會回報 module not registered: http.encoders.br。社群有 Brotli 的第三方外掛， 需要用 xcaddy 自行編譯，請自行評估維護狀況； 多數情況下，動態用 zstd／gzip、靜態資源用預先壓縮的 .br 就夠了。

2. 最小設定​

Caddyfile
example.com {
	root * /var/www/example
	encode
	file_server
}

encode 不帶參數時，等於 encode zstd gzip：兩種都開、用戶端沒有明確偏好時 zstd 優先。 Caddyfile 的指令會依內建順序自動排好，encode 一定會包在 file_server、reverse_proxy 外層，不用擔心寫的先後。

3. 建議設定​

Caddyfile
example.com {
	root * /var/www/example

	encode {
		zstd
		gzip 5
		minimum_length 512
	}

	file_server
}
設定預設值說明
zstd [<level>]default（約等於 zstd 等級 3）可選 default、fastest、better、best
gzip [<level>]5範圍 1–9
區塊內的順序—用戶端沒有明確偏好（q 值相同）時，先列的優先
minimum_length512小於這個位元組數就不壓。Content-Length 或第一次寫出的資料量，任一個超過門檻就壓
match一組文字型別用回應的 Content-Type 決定要不要壓，見 3.1

實測行為：

  • 會看 q 值。 Accept-Encoding: zstd;q=0.1, gzip;q=1 拿到 gzip。
  • 壓縮時會移除 Content-Length 與 Accept-Ranges、加上 Vary: Accept-Encoding， 並在強 ETag 後面加上 -gzip／-zstd。Caddy 會在收到 If-None-Match 時自動把後綴去掉再比對，實測可以正常回 304。
  • 回應狀態是 206（Range）時不會壓縮。
  • 回應已經帶 Content-Encoding（例如後端自己壓過）時不會再壓。

3.1 預設會壓哪些型別​

match 的預設清單（摘要，完整清單見官方文件） 包含 text/*、application/json*、application/javascript*、application/xml*、 application/wasm*、image/svg+xml* 以及 TTF／OTF 等字型型別。圖片、影片、ZIP 不在清單內。

注意兩點：

  • text/* 包含 text/event-stream（SSE）。見第 5 節。
  • 官方文件頁列出的是 font/*，但 2.11.4 原始碼裡實際只有 font/ttf* 與 font/otf*， 實測 font/woff2 不會被壓（這是對的，WOFF2 內部已經用 Brotli 壓過）。文件與實作不一致時，以實測為準。

要自訂清單時，寫 match 區塊，同一個欄位的多行是「任一符合」：

Caddyfile：只壓這些型別
encode {
	zstd
	gzip 5
	match {
		header Content-Type text/html*
		header Content-Type text/css*
		header Content-Type text/plain*
		header Content-Type text/javascript*
		header Content-Type application/javascript*
		header Content-Type application/json*
		header Content-Type application/xml*
		header Content-Type image/svg+xml*
	}
}

寫了 match 就會整個取代預設清單，不是追加。

4. 搭配 reverse_proxy​

encode 一樣會壓縮 reverse_proxy 回來的回應。要注意：

  1. Caddy 會把用戶端的 Accept-Encoding 轉給後端。 後端自己會壓的話， 回來就帶著 Content-Encoding，Caddy 原樣轉送，你在 encode 設的等級與型別不會生效。 實測後端（Express + compression）回 br，Caddy 就送 br。

  2. 想統一由 Caddy 壓縮，就別讓後端看到用戶端的 Accept-Encoding：

    Caddyfile
    example.com {
    	encode
    	reverse_proxy 127.0.0.1:3000 {
    		header_up -Accept-Encoding
    	}
    }

    實測這樣設定後，用戶端要 zstd 就拿到由 Caddy 壓的 zstd。 （拿掉之後，Caddy 的 HTTP transport 會自己向後端要 gzip，收到後在內部解開，再依 encode 的設定壓給用戶端；見下一點。）

  3. 依官方文件，用戶端請求沒有 Accept-Encoding 時，Caddy 的 HTTP transport 會自己對後端送 Accept-Encoding: gzip，讓後端可以回壓縮的內容；要關掉這個行為，在 transport http 區塊寫 compression off。

5. 串流回應（SSE）要排除​

reverse_proxy 遇到 Content-Type: text/event-stream 會自動立即 flush，不需要另外設定 flush_interval。問題出在 encode：它的預設清單包含 text/*，所以 SSE 也會進到 encode。

實測 Caddy 2.11.4（後端先送出回應標頭，再每秒送一個事件）：

情況結果
SSE 經過 encode，每個事件都小於 minimum_length（512）不壓縮，事件照常到；但回應標頭要等到第一個事件才送出
SSE 經過 encode，第一個事件大於 512 bytes整條串流被壓縮，每個事件仍會 flush；標頭一樣延到第一個事件
後端回應帶 Cache-Control: no-transform不壓縮
SSE 放在沒有 encode 的 handle 裡不壓縮，標頭立即送出

回應標頭延遲的影響：瀏覽器 EventSource 的 open 事件要等到第一個事件才觸發； 如果你的串流是「有資料才送」，前面還有其他代理或負載平衡器時，可能會被當成沒有回應而逾時。 這是已知問題（caddy#6293）， 修正（caddy#7905）已在 2026 年 7 月合併， 但 2.11.4 還沒有包含，之後的版本行為可能不同，請以你使用版本的 release notes 為準。

建議寫法一：串流路徑放在沒有 encode 的 handle

Caddyfile
example.com {
	root * /var/www/example

	handle /events* {
		reverse_proxy 127.0.0.1:3000
	}

	handle {
		encode
		file_server
	}
}

handle 區塊彼此互斥，請求只會進入第一個符合的區塊，所以 /events 開頭的請求完全不會經過 encode。

建議寫法二：用請求比對器排除

Caddyfile
example.com {
	root * /var/www/example

	@compressible not path /events*
	encode @compressible

	reverse_proxy /events* 127.0.0.1:3000
	file_server
}

補充：後端送 Cache-Control: no-transform

Caddy 2.11.4 的原始碼中，請求或回應帶有 Cache-Control: no-transform 時，encode 不會壓縮 （實測成立，但官方文件頁沒有寫出這個行為）。SSE 回應本來就常加 Cache-Control: no-cache， 改成 no-cache, no-transform 可以當作額外保險，也能順便讓其他遵守規格的中間層不去改動內容。

其他串流型別（例如逐行送 JSON 的串流 API）：Content-Length 未知的回應 Caddy 也會立即 flush； 需要時可在 reverse_proxy 區塊設 flush_interval -1 強制低延遲模式。同樣建議排除在 encode 之外。

6. 預先壓縮：file_server precompressed​

build 時先產生 .br／.zst／.gz（做法見預先壓縮），Caddy 直接送：

Caddyfile
example.com {
	root * /var/www/example

	encode
	file_server {
		precompressed br zstd gzip
	}
}
設定說明
precompressed br zstd gzip依序找 .br、.zst、.gz 旁檔（sidecar）；不寫格式時預設就是 br zstd gzip
搭配 encode某個檔案沒有預先壓縮檔時，由 encode 動態壓縮；兩者可以同時開

實測行為：

  • 會看 q 值：br;q=0.5, gzip 拿到 .gz。
  • 送出的是檔案本身：有 Content-Length，每種編碼有各自的 ETag，並帶 Vary: Accept-Encoding。
  • Caddy 會先確認原檔存在，才去找壓縮檔；只放壓縮檔、不放原檔是找不到的。
warning

Caddy 只檢查壓縮檔「存不存在」，不比對它跟原檔是不是同一版。 原檔更新後舊的 .br 還留著，使用者就會拿到舊內容。build 時要清空輸出目錄再重新產生。

7. 驗證​

curl -s -o /dev/null -D - -H 'Accept-Encoding: zstd' https://example.com/
curl -s -o /dev/null -D - -H 'Accept-Encoding: br' https://example.com/assets/app.js   # 預先壓縮
tip

不要用 curl -I（HEAD）驗證 Caddy 的動態壓縮：實測 HEAD 回應會帶 Content-Encoding， 但 Content-Length 是一個跟實際內容無關的小數字。用 GET 並把本體丟掉（-o /dev/null）才準。

完整的驗證方法見驗證。

8. 常見錯誤​

症狀原因解法
module not registered: http.encoders.br標準版沒有 Brotli 動態壓縮改用 encode zstd gzip；靜態資源用 precompressed 送 .br
http:// 測不到 zstd瀏覽器只在 HTTPS 宣告 zstd／br用 HTTPS，或用 curl -H 'Accept-Encoding: zstd' 測
SSE 連上後很久才觸發 openencode 延到第一個事件才送標頭見第 5 節
設了 encode 等級，API 回應卻是別的編碼後端自己壓了見第 4 節
自訂型別的回應（例如 application/x-ndjson）沒被壓不在預設 match 清單自訂 match 清單（注意會取代預設清單）
更新網站後使用者看到舊內容殘留舊的預先壓縮檔build 時清空輸出目錄
