回應壓縮的常見陷阱

這些問題的共同點是：設定檔語法正確、伺服器正常啟動、大部分頁面也正常， 只有特定情況才出錯，而且錯的方式很難聯想到壓縮。

1. 串流回應被壓縮器卡住​

1.1 為什麼會卡​

壓縮演算法要「看過一段資料」才能找出重複的部分，所以壓縮器會把輸入累積在緩衝區， 湊夠一個區塊才輸出。對一般回應這沒問題 —— 回應結束時緩衝區會被清空。 但對不會結束、一次送一小段、而且要馬上到的回應，資料就一直卡在緩衝區裡， 直到湊滿或連線結束。反向代理本身的回應緩衝也會造成同樣的現象。

受影響的回應：

類型例子影響
Server-Sent EventsContent-Type: text/event-stream事件延遲或最後一次湧出，EventSource 看起來像斷線
串流 API逐行輸出 JSON（NDJSON）、逐字輸出生成結果、分段送出的進度同上
HTTP 串流式的長連線用一條不結束的回應持續推送資料同上
串流下載邊產生邊送的匯出檔第一個位元組變慢；動態壓縮拿掉 Content-Length，下載沒有進度條
一般的長輪詢伺服器等到有資料才回一整包不受壓縮影響（回應是一次送完的）；要注意的是代理的讀取逾時

1.2 各元件的實測結果​

後端每秒送一個小事件、共 5 個，text/event-stream 被列入壓縮型別時：

元件結果
nginx 1.30，proxy_buffering on（預設）全部在最後一起到，連回應標頭都延到最後
nginx 1.30，proxy_buffering off 或後端送 X-Accel-Buffering: no每秒到一個，但每個事件都被壓縮
Apache httpd 2.4 + mod_proxy_http每秒到一個，但每個事件都被壓縮
Caddy 2.11.4 encode事件照常到；回應標頭延到第一個事件才送出；第一個事件超過 512 bytes 時整條串流會被壓縮
Express compression，沒有呼叫 res.flush()全部在最後一起到
Express compression，每次寫完呼叫 res.flush()每秒到一個

同一個設定在不同元件上的表現差很多，而且你的請求可能經過好幾層。 最穩的做法是：串流路徑一律不壓縮、不緩衝。

1.3 各伺服器的排除方式​

元件做法詳細
nginx串流的 location 裡 gzip off;（有裝才寫 brotli off;）、proxy_buffering off;，且不要把 text/event-stream 放進 gzip_typesnginx 第 8 節
Apache httpd串流的 Location 裡 SetEnv no-gzip 1、SetEnv no-brotli 1Apache 第 6 節
Caddy串流路徑放在沒有 encode 的 handle，或用請求比對器排除Caddy 第 5 節
Expressfilter 回傳 false，或每次寫完 res.flush()應用程式層第 3 節
CDN／負載平衡器查供應商的串流說明、排除快取、注意閒置逾時CDN 第 6 節

另外，應用程式送出串流回應時加上 Cache-Control: no-cache, no-transform： 實測 Caddy 的 encode 與 Express 的 compression 看到 no-transform 就不壓， 遵守規格的中間層也不會改動內容。但 nginx 與 Apache 的壓縮模組不看這個標頭， 所以它只能當作額外保險，伺服器端的排除設定還是要做。

串流連線通常還需要：

  • 心跳：每 15–30 秒送一行 SSE 註解（: ping 加上空行），避免被代理或負載平衡器的閒置逾時切斷；
  • 足夠的逾時：nginx 的 proxy_read_timeout、Apache ProxyPass 的 timeout=；
  • HTTP/2：HTTP/1.1 下每條 SSE 佔掉瀏覽器對該網域 6 條連線中的一條，見延伸閱讀。

2. 已經壓縮過的格式不要再壓​

JPEG、PNG、WebP、AVIF、MP4、WOFF2、ZIP 這些格式內部已經壓縮過，再壓一次幾乎沒有收益。實測：

檔案原始大小gzip 5Brotli 5
照片（JPEG）244,755 bytes242,960（-0.73%）242,789（-0.80%）
照片（PNG）636,301 bytes635,817（-0.08%）636,306（+0.00%）
隨機資料（等同已壓縮內容）200,000 bytes200,083（變大）200,005（變大）

省不到 1%，卻要付出：

  • 每個請求的 CPU；
  • 失去 Content-Length 與 Range 支援：動態壓縮會拿掉 Accept-Ranges，影片無法拖曳進度、大檔下載無法續傳；
  • 失去下載進度條：沒有 Content-Length，瀏覽器不知道總大小。

避免方式：

  • 用白名單列出要壓的型別（gzip_types、AddOutputFilterByType、Caddy 的 match），不要用萬用字元；
  • 確認伺服器回傳正確的 Content-Type。未知副檔名常被當成 application/octet-stream，不在白名單就不會被壓，但如果你的型別清單寫得太寬就會；
  • .svgz 是已經 gzip 過的 SVG，要用 Content-Type: image/svg+xml 加 Content-Encoding: gzip 送出，不要再動態壓縮。

完整的「該壓／不該壓」清單見總覽第 3 節。

3. 最小長度門檻​

壓縮格式本身有固定開銷（gzip 的標頭與結尾就佔 18 bytes），太小的回應壓完反而變大。實測：

原始大小gzip 5Brotli 5zstd 3
3 bytes23716
11 bytes（{"ok":true}）311524
52 bytes645665
216 bytes937495
851 bytes170121177
2,141 bytes298181201

一兩百 bytes 以下幾乎沒賺，甚至虧；而且一個 TCP 封包本來就能裝下約 1.4 KB， 把 800 bytes 壓成 200 bytes 並不會少一次來回。門檻設在 256 bytes 到 1 KB 之間都合理。

各元件的預設值：

元件設定預設值注意
nginx gzipgzip_min_length20 bytes只看 Content-Length；沒有 Content-Length 的回應（chunked）一律會壓
ngx_brotlibrotli_min_length20 bytes同上
Apache mod_deflate／mod_brotli無此設定—實測 mod_brotli 連 3 bytes 都壓
Caddyminimum_length512 bytes沒有 Content-Length 時看第一次寫出的資料量
Express compressionthreshold1 KB大小未知時一律當作超過

4. Vary: Accept-Encoding 與快取​

同一個網址會因為 Accept-Encoding 不同而回傳不同的內容， Vary: Accept-Encoding 就是告訴所有快取（瀏覽器、代理、CDN）：「請依這個請求標頭分開存」。

少了 Vary 的後果：中間的快取只存第一份。第一個請求是 br，之後不支援 br 的用戶端也會拿到 br， 看到的就是亂碼或白畫面，而且只在某些人、某些時候發生，非常難查。

元件預設會不會加 Vary
nginx不會，要 gzip_vary on;（這個指令也控制 ngx_brotli 與 zstd 模組的 Vary）
Apache httpd會
Caddy會
Express compression會
Apache 用 mod_rewrite 送預先壓縮檔不會，要自己用 Header merge Vary Accept-Encoding

4.1 ETag 也會被影響​

同一個網址的壓縮版與未壓縮版內容不同，各伺服器處理 ETag 的方式不同，會影響 304 回應：

元件動態壓縮時的 ETag能不能正常回 304
nginx改成弱 ETag（W/"..."）能
Apache httpd（預設 AddSuffix）加上 -gzip／-br 後綴不能：瀏覽器帶回後綴過的 ETag，Apache 比對不上，每次都回完整 200
Caddy加上 -gzip／-zstd 後綴能（Caddy 會自己把後綴去掉再比對）
預先壓縮檔（各伺服器）依壓縮檔本身算出的強 ETag能

Apache 的處理方式見 Apache 第 4 節。

5. BREACH 攻擊​

5.1 原理​

BREACH（2013 年公開）利用的是「壓縮後的長度會洩漏內容」： 如果回應裡同時有一段機密（例如 CSRF token）和一段攻擊者能控制的文字， 當攻擊者猜的字串跟機密有越多相同的部分，壓縮後的回應就越小。 攻擊者只要能看到加密後封包的長度（例如跟受害者在同一個公共 Wi-Fi）， 並誘使受害者的瀏覽器發出大量帶有猜測字串的請求（例如讓受害者開一個惡意網頁）， 就能逐字元推出機密。TLS 加密擋不住，因為長度沒有被隱藏。

5.2 哪些回應要小心​

三個條件同時成立才有風險：

  1. 經 HTTPS 送出，且有 HTTP 層壓縮（gzip、Brotli、zstd 都算）；
  2. 回應本體反射了使用者輸入（網址參數、表單內容，例如「您搜尋的是：xxx」）；
  3. 回應本體含有機密（CSRF token、API 金鑰、個資、工作階段相關的值）。
回應風險
靜態資源（JS、CSS、圖片）沒有機密，無風險
公開頁面、不反射輸入的 API缺條件，風險低
登入後的頁面，含 CSRF token，又把搜尋字串或網址參數顯示在頁面上高
回應裡同時有 token 與使用者送來的內容（例如回顯請求）的 API高

Cookie 放在標頭裡，不在 HTTP 回應本體，不是 BREACH 的目標。 另外，BREACH 與 CRIME 不同：CRIME 攻擊的是 TLS 層壓縮，現代 TLS 早已不用；BREACH 攻擊的是 HTTP 層壓縮，至今仍然適用。

5.3 緩解方式​

BREACH 官方網站依有效程度列出的緩解方式，以及實務上的做法：

緩解方式實務做法
對有風險的回應關閉壓縮只針對上一節的「高」風險路徑關，不需要整站關
把機密與使用者輸入分開不要在同一個回應裡同時放 token 與反射內容；例如 token 改由另一支 API 取得
每次請求都隨機化機密每次輸出 CSRF token 都用新的隨機值遮罩（例如與隨機值 XOR）。許多框架的 CSRF 機制已經這樣做，請確認你用的框架
對有風險的頁面加上 CSRF 防護讓攻擊者無法任意觸發帶有受害者身分的請求。Cookie 設 SameSite 也能降低跨站請求帶上身分的機會
隱藏長度在回應中加入隨機長度的填充。例如 Django 的 GZipMiddleware 實作了 Heal-The-Breach，在壓縮回應中加入最多 100 bytes 的隨機資料（見 Django 文件）
限制請求頻率攻擊需要大量請求，限流可以提高成本

針對特定路徑關壓縮的寫法：

nginx
location /account/ {
    gzip off;
    brotli off;   # 有裝 ngx_brotli 才寫
    # ... 其他設定
}
Apache httpd
<Location "/account/">
    SetEnv no-gzip 1
    SetEnv no-brotli 1
</Location>
Caddy
@compressible not path /account/*
encode @compressible

6. 壓縮等級與 CPU：動態 vs 預先壓縮​

壓縮等級越高，壓縮率越好，但 CPU 時間增加得遠比壓縮率快。 以一個約 1 MB、未 minify 的真實 JavaScript 檔案實測（單執行緒命令列工具、含行程啟動時間，只看相對比例）：

演算法與等級壓縮後大小（相對原檔）耗時
gzip 127.7%6 ms
gzip 522.2%12 ms
gzip 621.7%17 ms
gzip 921.5%51 ms
Brotli 125.0%5 ms
Brotli 420.9%8 ms
Brotli 519.5%12 ms
Brotli 619.1%13 ms
Brotli 918.5%24 ms
Brotli 1116.8%854 ms
zstd 124.3%4 ms
zstd 322.3%5 ms
zstd 919.4%12 ms
zstd 1917.3%149 ms

觀察：

  • gzip 從 6 到 9，多花三倍時間，只多省 0.2%。
  • Brotli 從 5 到 11，多花七十倍時間，多省約 14%。
  • zstd 在低等級速度最快，高等級則介於兩者之間。
  • 解壓縮的成本在用戶端，三種演算法解壓都很快，而且幾乎不受壓縮等級影響。

建議等級：

用途gzipBrotlizstd
動態壓縮（每個請求都壓）4–64–53
預先壓縮（build 時壓一次）91119

判斷原則：

  • 會重複送很多次、內容不變的 → 預先壓縮，用最高等級。見預先壓縮。
  • 每次都不一樣的（HTML、API） → 動態壓縮，用中等等級。
  • 前面有 CDN 快取時，動態壓縮的回應在快取有效期間只會被壓一次，可以考慮稍微調高等級； 沒有快取時，每個請求都要付這筆 CPU。
  • 調整等級前，先確認 CPU 真的是瓶頸。多數網站的動態壓縮用中等等級，CPU 佔比很低。
