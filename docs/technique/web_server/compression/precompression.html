預先壓縮：build 時產生 .gz／.br／.zst

動態壓縮是「每個請求壓一次」；預先壓縮是「build 時壓一次，之後每個請求直接送檔案」。 對內容不會變的靜態資源（JS、CSS、SVG、WASM、TTF／OTF 字型），預先壓縮幾乎只有好處。 （WOFF／WOFF2 字型本身已經壓縮過，不需要。）

1. 動態壓縮 vs 預先壓縮​

項目動態壓縮預先壓縮
CPU 成本每個請求都要花只在 build 時花一次
可用的壓縮等級中等（gzip 5、Brotli 4–5），太高會拖慢回應最高（gzip -9、Brotli -q 11、zstd -19）
Content-Length通常沒有（chunked）有
Range 請求（續傳、影片拖曳）通常不支援支援
ETag被改寫（弱化或加後綴）每種編碼各自有強 ETag
適用內容動態產生的 HTML、API 回應build 產物、不會變的靜態檔

一個約 1 MB、未 minify 的真實 JavaScript 檔案，實測（單執行緒、含行程啟動時間，只看相對比例）：

方式大小耗時
Brotli -q 5（動態壓縮常用等級）210,671 bytes約 12 ms
Brotli -q 11（預先壓縮）180,984 bytes約 854 ms

多省 14%，但慢了七十倍。這種等級拿來做動態壓縮，每個請求都要等將近一秒； 拿來做預先壓縮，只是 build 多跑一秒。

2. 產生壓縮檔​

需要的工具：gzip（系統內建）、brotli、zstd。

環境安裝
Debian／Ubuntusudo apt install brotli zstd
Alpineapk add brotli zstd
macOS（Homebrew）brew install brotli zstd

2.1 單一檔案​

gzip   -9 -n -k app.js    # 產生 app.js.gz，保留原檔
brotli -q 11   app.js     # 產生 app.js.br（預設就會保留原檔）
zstd   -19 -q  app.js     # 產生 app.js.zst（預設就會保留原檔）
參數用途
gzip -9最高等級
gzip -n不把原檔名與時間寫進 gzip 標頭，同樣的輸入每次產生完全相同的輸出（可重現建置）
gzip -k保留原檔（沒有 -k 會把原檔刪掉）
brotli -q 11最高品質（-q 範圍 0–11，不寫時預設就是 11）
zstd -19不加 --ultra 時的最高等級
zstd -q不顯示進度
warning

zstd 不要加 --long 或 --ultra。 RFC 9659 規定 HTTP 上的 zstd 內容編碼，編碼端不得產生需要超過 8 MB 視窗的資料， 瀏覽器也只保證支援到 8 MB。--long 預設會用 128 MB 的視窗，--ultra 的高等級也會超過， 產生出來的檔案瀏覽器可能解不開。一般大小的前端檔案用 -19 不會有問題。

2.2 整個目錄​

下面這支腳本會替目錄裡的文字資源產生三種壓縮檔，並且：

  • 跳過 1 KB 以下的小檔（壓了省不到什麼，還多一次檔案查找）；
  • 壓完沒有變小的就刪掉；
  • 把壓縮檔的修改時間設成跟原檔一樣。
scripts/precompress.sh
#!/bin/sh
# 用法：precompress.sh <目錄>
# 替文字資源產生 .gz、.br、.zst；壓完沒有比較小的就刪掉
set -eu

dir="${1:?用法：$0 <目錄>}"
min_size=1024   # 不處理小於等於這個大小（bytes）的檔案

find "$dir" -type f \
  \( -name '*.html' -o -name '*.css' -o -name '*.js' -o -name '*.mjs' \
     -o -name '*.json' -o -name '*.svg' -o -name '*.xml' -o -name '*.txt' \
     -o -name '*.wasm' \) \
  -size +"${min_size}c" |
while IFS= read -r f; do
  orig=$(($(wc -c < "$f")))

  gzip   -9 -n -k -f -- "$f"
  brotli -q 11 -f    -- "$f"
  zstd   -19 -q -f   -- "$f"

  for ext in gz br zst; do
    out="$f.$ext"
    if [ $(($(wc -c < "$out"))) -ge "$orig" ]; then
      rm -f -- "$out"          # 沒有變小，留著只會浪費空間
    else
      touch -r "$f" -- "$out"  # 修改時間與原檔一致
    fi
  done
done

這支腳本在 macOS 的 /bin/sh 與 Alpine（BusyBox）的 sh 上都測過。檔名含換行字元的情況不處理。

部分用途
find ... -name ...只挑文字型別；圖片、影片、字型（WOFF／WOFF2）不在清單內
-size +"${min_size}c"大於 1024 bytes 的檔案（c 代表 bytes）
-f已有舊的壓縮檔時直接覆蓋
$(($(wc -c < "$f")))取得位元組數；外層的算術展開順便去掉 wc 輸出的前導空白
touch -r "$f" -- "$out"讓壓縮檔的修改時間跟原檔一樣（nginx 官方文件建議這麼做）

要不要產生 .zst？ 目前支援 zstd 的瀏覽器也都支援 Brotli，而伺服器通常會優先送 .br。 .zst 可有可無；如果你的伺服器設定是 zstd 優先（例如 Caddy 動態壓縮的預設）， 預先放好 .zst 可以避免這些請求落到動態壓縮。

2.3 整合到建置流程​

最簡單的做法是在 build 之後跑一次腳本：

package.json
{
  "scripts": {
    "build": "vite build && sh scripts/precompress.sh dist"
  }
}

（vite build 換成你的建置指令。）

也可以用建置工具的外掛，例如 webpack 的 compression-webpack-plugin； 其他建置工具也有社群外掛，請自行評估維護狀況。外掛的好處是跟建置整合， 壞處是多一個相依、參數要另外學。用獨立腳本，換建置工具時不用改。

用容器部署時，壓縮可以放在建置階段（multi-stage build 的前段），最終映像檔只需要放產物與壓縮檔。

3. 伺服器怎麼送​

伺服器設定格式多種都有時選哪個詳細說明
nginxgzip_static on;、brotli_static on;（ngx_brotli）、zstd_static on;（第三方）.gz、.br、.zst不看 q 值，由模組決定（實測 .br 優先於 .gz）nginx 第 9 節
Apache httpdmod_rewrite 改寫 + mod_headers 補標頭任意（自己寫規則）依規則順序Apache 第 8 節
Caddyfile_server { precompressed br zstd gzip }.br、.zst、.gz看 q 值，相同時依列出的順序Caddy 第 6 節

三者的共同點：

  • 用戶端不接受、或壓縮檔不存在時，退回原檔；若同時開了動態壓縮，會改成動態壓。
  • 都會送 Content-Length，也都支援 Range。
  • 都只檢查壓縮檔「存不存在」，不會比對它是不是跟原檔同一版。

4. 只放壓縮檔、不放原檔？​

為了省空間，有人會只部署 .gz。不建議：

  • nginx 要用 gzip_static always;，再搭配 gunzip on; 替不支援 gzip 的用戶端解壓； ngx_brotli 沒有對應的「解壓 Brotli」功能，只放 .br 就沒有退路。
  • Caddy 會先確認原檔存在才找壓縮檔，只放壓縮檔會 404。
  • Apache 的改寫規則同樣以原檔為準。

磁碟空間通常不是問題，原檔一定要留著。

5. 陷阱​

5.1 過期的壓縮檔​

最常見也最難查的問題：原檔更新了，舊的 .br 還在，伺服器照送不誤， 使用者拿到舊版內容，而你打開原檔怎麼看都是新的。

  • 每次 build 前清空輸出目錄，不要在舊產物上疊加。
  • 部署時用會刪除多餘檔案的方式同步（例如 rsync --delete），或每次部署到新目錄再切換。
  • 檔名帶內容 hash（app.3f2a1c.js）能大幅降低這個風險，因為新版本是新檔名。

5.2 修改時間不一致​

nginx 送 .gz 時，Last-Modified 與 ETag 取自壓縮檔本身。原檔與壓縮檔時間不同， 同一個網址不同編碼的驗證資訊就不一致。上面的腳本用 touch -r 處理； gzip、brotli、zstd 命令列工具實測也都會保留原檔的修改時間，但建置外掛不一定。

5.3 型別錯誤​

Apache 用改寫規則時，app.js.gz 預設會被當成 application/x-gzip， 要用 [T=text/javascript] 修正，否則瀏覽器會把它當成下載檔。nginx 與 Caddy 會依原檔的副檔名決定型別，沒有這個問題。

5.4 物件儲存與 CDN 的靜態託管​

把檔案放在物件儲存再經 CDN 送出時，通常沒有「依 Accept-Encoding 挑 .br 旁檔」的機制。 常見做法有兩種，各有取捨：

  • 上傳時就上傳壓縮後的內容，並設定該物件的 Content-Encoding 中繼資料 —— 但這樣就不能依用戶端協商，不支援該編碼的用戶端會拿到看不懂的內容。
  • 上傳原檔，由 CDN 在邊緣動態壓縮 —— 見 CDN 與多層代理。

請以你使用的服務的官方文件為準。

6. 驗證​

# 1. 確認送的是壓縮檔，而且有 Content-Length
curl -s -o /dev/null -D - -H 'Accept-Encoding: br' https://example.com/assets/app.js

# 2. 確認解壓後的內容跟原檔一模一樣（最能抓到「過期壓縮檔」）
curl -s -H 'Accept-Encoding: br'   https://example.com/assets/app.js | brotli -d | cmp - dist/assets/app.js && echo same
curl -s -H 'Accept-Encoding: gzip' https://example.com/assets/app.js | gzip -d   | cmp - dist/assets/app.js && echo same
curl -s -H 'Accept-Encoding: zstd' https://example.com/assets/app.js | zstd -dq  | cmp - dist/assets/app.js && echo same

更多方法見驗證壓縮是否生效。
