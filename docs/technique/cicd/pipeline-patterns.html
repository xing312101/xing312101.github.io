Pipeline 樣式與 .gitlab-ci.yml 骨架

把觀念組合成可重用的 pipeline 結構。本篇提供與語言無關的骨架與樣式；把 script 換成你語言的 lint/測試/build/發佈指令即可。

通用骨架​

stages:
  - check      # 快檢：lint / 測試（雲端、進 merge gate）
  - build      # 產出 artifact（tag 觸發）
  - release    # 發佈（手動關卡）

# ---------- 1) 雲端快檢：進 merge gate ----------
fast_check:
  stage: check
  image: <你語言的 CI image>
  interruptible: true                       # 同一 MR 新 push 時取消舊 pipeline
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
  cache:
    key:
      files: [ <你的鎖定檔，如 lockfile> ]
    paths: [ <依賴快取目錄> ]
  script:
    - <安裝依賴>
    - <lint（記得用會回非 0 的檢查模式）>
    - <測試>

# ---------- 2) 產出 artifact：tag 觸發 ----------
build:
  stage: build
  image: <你語言的 CI image>
  rules:
    - if: $CI_COMMIT_TAG =~ /^v/            # 只在推 v* tag 時出現
  script:
    - <build>
  artifacts:
    paths: [ <產物路徑> ]
    expire_in: 1 week

# ---------- 3) 發佈：手動關卡 ----------
release:
  stage: release
  needs: [ build ]
  # tags: [ <自架 runner 標籤> ]           # 需要特定環境時指名自架
  rules:
    - if: $CI_COMMIT_TAG =~ /^v/
      when: manual                          # 手動按才發佈
      allow_failure: true                   # ← 必要！寫在 rules 裡時預設是 false（阻塞）
  script:
    - <發佈指令>
別把上面那行 allow_failure: true 刪掉

when: manual 寫在 rules: 裡面時，allow_failure 的預設是 false（只有直接寫在 job 層級才 預設 true）。少了這行，這個 release job 會變成阻塞式，pipeline 卡在 blocked 等人按。 完整的三段式預設值見基本觀念 §4。

快檢設計要點​

  • 只在 MR 與 merge 進主分支時跑：用 rules 限定 merge_request_event，避免每個 feature 分支的每次 push 都燒分鐘。
  • 進 merge gate 的只有快檢：build/release 用 tag + manual，排除在「Pipelines must succeed」之外，才不會被自架機器有沒有開機拖累。
  • 重測試分開：整合 / e2e / 端對端等慢又重的測試，改成 merge 後或 schedule（nightly） 跑，讓 MR 回饋維持在幾分鐘內。

省 compute minutes 三招​

  1. 只在 MR（和 merge 進主分支）跑 —— rules 限定觸發來源。
  2. interruptible: true —— 同一 MR 連續 push 時自動取消舊 pipeline（搭配 Settings → CI/CD → 開 "Auto-cancel redundant pipelines"）。
  3. 快取依賴 —— 用 lockfile 當 cache key，依賴沒變就重用。

Push options：不用 API token 就能在 push 時開 MR​

不必裝 CLI、也不必準備 access token，git push 帶 -o 就能順手建立 MR：

git push -o merge_request.create \
         -o merge_request.target=main \
         -o merge_request.title="<標題>" \
         -o merge_request.remove_source_branch

其他常用的：merge_request.description、merge_request.label=<標籤>、merge_request.draft、 ci.skip（本次 push 不觸發 pipeline），以及 merge_request.merge_when_pipeline_succeeds：MR 的 pipeline 一過就自動 merge （搭配 Pipelines must succeed、fast-forward、刪來源分支，一行 push 就走完「開 MR → 測 → 進主分支 → 觸發部署」）。

push option 只在「有 ref 更新」時才會被處理

如果分支已經是最新（Everything up-to-date），這些 -o 完全不會生效——不會報錯，也不會建 MR。 它們是在 GitLab 端的 receive 階段處理的，沒有 ref 變動就沒有那個階段。

所以「先 push、想起來要開 MR、再 push 一次帶 -o」是行不通的。要嘛第一次 push 就帶上，要嘛改用網頁。 （--force-with-lease 改寫歷史也算 ref 更新，會觸發。）

另外：該分支已有開著的 MR 時，merge_request.create 不會重複建立；但如果先前的 MR 已被關閉， 它會建一個新的——force-push 整理過 commit 之後容易不小心留下兩張單，記得回去看一眼。

只檢查「這次改了什麼」：比對基準要選對​

有些檢查只該看這次的改動（新加的 migration、新加的 CSS class、改到的檔案）。最容易寫錯的是拿來比的基準：

寫法問題
跟主分支比（git diff origin/main...HEAD）直接 push 主分支的團隊，在主分支上永遠沒有差異，這個檢查等於沒做
$CI_COMMIT_BEFORE_SHA（這次 push 之前的 tip）✅ 對；但新分支第一次 push 時它是一串 0、force push 之後那個 commit 可能已經不在歷史裡；MR 的 pipeline 裡也是一串 0
$CI_MERGE_REQUEST_DIFF_BASE_SHA（MR 分岔出去的那一點）✅ MR 的 pipeline 用這個：就是 MR 畫面上那份 diff 的基準

穩的做法：MR 裡先用 $CI_MERGE_REQUEST_DIFF_BASE_SHA，其餘用 $CI_COMMIT_BEFORE_SHA；是全 0 或 git cat-file -e <sha> 找不到，就退回跟主分支的分岔點（git merge-base HEAD origin/main，要先 git fetch origin main）。

另外 GitLab 預設只淺複製最近 20 個 commit（GIT_DEPTH），基準常常不在裡面 —— 這種 job 要設：

variables:
  GIT_DEPTH: "0"     # 完整歷史

從新增的行裡挑東西檢查時（例如「新加的 CSS class 有沒有生成」），先拿掉註解：註解裡用反引號包的字（「放在 text」） 會被當成字串字面值、再被當成 class，一句註解就讓檢查紅。整行註解整行不看；行尾的 // … 要前面是空白才算（網址裡的 https:// 不算）。 改完用一個「註解裡有可疑字、程式碼裡有真的打錯字」的 commit 驗：要抓到打錯的、不抓註解的。

用 services: 起資料庫​

測試要真的資料庫時，用 services: 起一個，以服務名稱連線：

pytest:
  services:
    - name: mysql:<正式環境那一版>
      command: ["--character-set-server=utf8mb4", "--collation-server=<正式環境的定序>"]
  variables:
    MYSQL_ROOT_PASSWORD: ci-only
    MYSQL_DATABASE: app_test
  script:
    - <等資料庫起來的迴圈>      # 剛啟動的頭幾秒連不上
    - <建表 / migration>
    - <測試>
  • 一定要有「等它起來」那一步：job 開始時 service 不保證已經能連（迴圈試連 30～60 秒）
  • 連線的主機名就是 image 名推出來的別名（mysql）。再寫一個相同的 alias: 會在 log 出現 alias is already in use，不影響執行，可以不寫
  • 版本與定序照正式環境釘死（見下一節）：不同定序的表跨表比字串會 Illegal mix of collations，只在某個環境出現

push 之前，在本機用同一個 image 模擬 CI​

CI 一次要等好幾分鐘、而且吃額度。改 .gitlab-ci.yml 之前，先在本機用同一個 image照著跑一次：

docker network create ci-sim
docker run -d --rm --name ci-db --network ci-sim --network-alias mysql -e MYSQL_ROOT_PASSWORD=ci-only <資料庫 image>
docker run --rm --network ci-sim -v "$PWD":/repo -w /repo <CI 用的 image> bash -c '<把 script 那幾行照抄進來>'
docker stop ci-db && docker network rm ci-sim
模擬抓得到模擬抓不到
時區不同（容器預設 UTC）、少環境變數、版本差異、image 缺工具（slim 沒有 git）機器剛開機這類狀態（容器沒有自己的開機時間，算的是宿主 kernel／Docker Desktop 那台 VM 的）、runner 的網路與權限、GitLab 端的設定

模擬全過不等於 CI 會過 —— 真的跑一次才算數（見本機綠、CI 紅）。

  • job 裡每次都 apk add／apt-get install 的，本機模擬先做一個裝好套件的 image：本機連套件的 CDN 常常一裝就好幾分鐘（runner 上通常很快）， 每跑一次等一次。基底與套件跟 job 寫的一樣，只是先裝好：

    FROM <job 用的 image>
    RUN apk add --no-cache <job 裡 apk add 的那一串>

  • 模擬用的臨時腳本放在 repo 外面：放在 repo 裡，下一次 git add -A 就一起 commit、push 上去了

套件漏洞檢查放進 CI​

audit-python:
  stage: test
  before_script: []                 # 不用先裝整套相依：照鎖定檔查就好
  script:
    - pip install -q pip-audit==<版本>
    - pip-audit -r requirements.lock --no-deps --progress-spinner off --desc $(for id in ${PIP_AUDIT_IGNORE:-}; do printf -- '--ignore-vuln %s ' "$id"; done)

audit-node:
  stage: test
  script:
    - npm audit || true                                   # 全部印出來
    - if [ -n "${NPM_AUDIT_SKIP:-}" ]; then echo "這次跳過：$NPM_AUDIT_SKIP"; exit 0; fi
    - npm audit --audit-level=high                        # 高風險以上才擋
  • 查的是線上的漏洞資料庫：同一個 commit 今天綠、明天可能紅 —— 那是新公布的漏洞，不是程式壞了。所以要留緊急出口： 新漏洞跟這次要上的修正無關、又急著上時，用 CI 變數暫時忽略（Python 那邊可以指定漏洞編號；npm 不行，只能整個跳過），上完立刻升級、把變數刪掉
  • 不要用 allow_failure: true：黃燈沒有人會看，等於沒有這個 job
  • 前端的套件幾乎都只在建置、測試、本機伺服器用（正式站多半是靜態檔），中度的擋部署多半是雜訊，門檻放在 high；後端照鎖定檔、有就擋
  • 升級時只升有漏洞的那幾個：照舊鎖定檔裝一套跟線上一樣的，再 pip install -U <那幾個>、pip check、pip freeze。整份重產的話， 無關的間接相依也全部換版本，出問題時分不出是誰
  • 升級後沒人用的相依一起拿掉（pip show <套件> 的 Required-by 是空的、程式裡 grep 不到）；換掉某個函式庫時，它帶進來的相依常常也變成沒人用
  • 修補一直不完整、又沒有修正版的函式庫（例如 JWT 函式庫的演算法混淆修了又修），與其等，不如換成維護比較積極的；驗 token 的地方一律寫死演算法

SDK 版本一致性（通用原則）​

CI 與本機必須用同一個 SDK 版本，否則會出現「本機過、CI 掛」或反之。做法：

  • 用你語言的版本管理工具鎖版本（寫進專案的版本檔）。
  • 單一真相來源：把版本寫死在 .gitlab-ci.yml 的 variables，image tag 與 job 都引用它，並確保等於專案版本檔。
  • 以正式環境為準，不是以開發機為準：CI 要證明的是「上線會不會壞」。語言版本到 patch、資料庫 service 的版本 （寫 mysql:8.4.10，不寫 mysql:8.4）、資料庫的預設定序，都照正式環境實際跑的那一版。
  • 相依套件照正式環境實際裝的鎖死：鎖定檔從正式環境的套件清單產生（例如在主機上 pip freeze）， CI 嚴格照它裝（Python：pip install --no-deps -r <鎖定檔> 再 pip check，漏了誰會被抓到，不會被自動補上最新版）。 每隔一陣子拿正式環境的清單跟鎖定檔比一次：多台主機很容易各自漂掉一兩個套件。
  • 在 CI 裡斷言版本：例如讀專案的版本檔、跟 image 的版本比，不一致就讓 job 失敗。
真實案例

兩台開發機一個用新版 SDK、一個用舊版，跑起來行為不同、測試結果分岔。鎖死版本並讓 CI 也吃同一版即可根治。

⚠️ 自架 GitLab（self-managed）沒有免費 shared runner​

若你的 GitLab 是 gitlab.com（SaaS），Linux hosted runner 現成可用、含免費額度。 若是公司自架（self-managed），預設不會有任何 shared runner——連 Linux 快檢都得自己準備一台 runner（見 self-hosted-runner）。判斷方式：到 Settings → CI/CD → Runners 看有沒有可用的 instance/shared runner。
