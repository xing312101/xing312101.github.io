Merge gate 與 MR：紅的進不了主分支

要開哪些設定，紅的 MR 才進不了主分支；設好之後主分支上的 pipeline 怎麼寫；為什麼只讓雲端快檢當閘門；以及用 push options 在 git push 時順手開 MR、綠了自動 merge。 第一次幫專案接 CI 時，讀完基本觀念就讀這篇。

1. 不綠就不准 merge​

pipeline 綠不綠是一回事，「不綠就不准 merge」要另外開：

  1. Settings → Merge requests → 勾「Pipelines must succeed」 → MR 的 merge 按鈕在 pipeline 沒綠之前是鎖住的。
  2. Settings → Repository → Protected branches → 保護主分支，禁止直接 push，強迫所有變更走 MR + 過 CI。

完整的一組（主分支一有 push 就自動部署測試環境、上正式又只能從主分支打 tag 時，主分支必須永遠是綠的 —— 直接 push 的話，CI 紅了之後壞的 commit 已經在主分支上）：

在哪裡設定
Protected branches → 主分支Allowed to merge：Maintainers；Allowed to push and merge：No one；force push 關
Merge requests → Merge methodFast-forward merge：歷史一直線、沒有 merge commit；而且進主分支的就是 MR 上測過的那個內容（要求分支先跟上主分支）
Merge requests → Squash commits when mergingRequire：一個 MR 進主分支就是一個 commit
Merge requests → Merge checksPipelines must succeed
這一頁每個區塊有自己的 Save changes

Merge requests 設定頁分成好幾個區塊，各自要按該區塊的存檔。漏按的那一塊不會生效、也不會提示 —— 實際發生過：以為設好了，第一個 MR 進去卻多了一個 merge commit、原本的 commit 也沒被 squash。設完開一個小 MR 試，看主分支的歷史長怎樣。

2. 主分支上不重跑測試​

fast-forward 之下，進主分支的 commit 內容就是 MR 上測過的那一個，主分支的 pipeline 只要做部署：

workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS   # 分支已有開著的 MR：不另跑分支 pipeline（同一個 commit 不跑兩次）
      when: never
    - if: $CI_COMMIT_BRANCH
    - if: $CI_COMMIT_TAG

.check_rules: &check_rules                                # 測試、lint、漏洞檢查共用
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH && $CI_COMMIT_BRANCH != $CI_DEFAULT_BRANCH
    - if: $CI_COMMIT_TAG =~ /^release/                    # 上正式的 tag 照樣再跑一次

deploy-staging:
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH && $CI_PIPELINE_SOURCE != "schedule"   # 主分支：只部署（排程那條不部署）
  • 順序：先在 GitLab 設好保護與合併方式，再把這份 rules 送進去（用 MR 送）。反過來的話，中間有人直接 push 主分支，就會不經測試直接部署
  • squash 之後主分支上的 commit 是新的 SHA（跟 MR 上測過的那個不同，內容一樣），訊息預設只有 MR 的標題、描述不會帶進去 —— 要寫細的就寫在標題，或改 squash commit 的訊息範本
  • MR pipeline 在 feature 分支的情境跑，拿不到 Protected 變數：測試 job 要不需要機密才行（見機密管理）
  • 主分支不跑檢查的代價：漏洞檢查只在 MR 那天和打 tag 時跑，中間新公布的漏洞要到上正式才發現 —— 每天在主分支上排程跑一次（見套件漏洞檢查）， 部署的 rule 要排除排程（上面 deploy-staging 那行的 != "schedule"，見 Pipeline 樣式 → 排程）

3. 只讓 always-on 的雲端快檢進 merge gate​

不要讓跑在自架機器上的 build 成為 MR 的必過 job —— 否則機器沒開機時 MR 會卡死。發佈類 job 一律用 tag + manual，排除在 merge 判斷之外。

例外是額度不夠、把快檢也搬到自架：那就是刻意讓 merge gate 綁在那台機器上，一定要留一行就能切回雲端的開關（見同一台 Mac 的兩種 runner → 代價）。

4. Push options：不用 API token 就能在 push 時開 MR​

不必裝 CLI、也不必準備 access token，git push 帶 -o 就能順手建立 MR：

git push -o merge_request.create \
         -o merge_request.target=main \
         -o merge_request.title="<標題>" \
         -o merge_request.remove_source_branch

其他常用的：merge_request.description、merge_request.label=<標籤>、merge_request.draft、 ci.skip（本次 push 不觸發 pipeline），以及 merge_request.merge_when_pipeline_succeeds：MR 的 pipeline 一過就自動 merge （搭配 Pipelines must succeed、fast-forward、刪來源分支，一行 push 就走完「開 MR → 測 → 進主分支 → 觸發部署」）。

ci.variable="<名稱>=<值>" 讓這次 push 觸發的那一條 pipeline 多帶一個變數。MR 的 pipeline 吃不到；推 tag 的那一條吃得到 （原始碼裡 tag 跟分支走同一段建 pipeline 的程式）。適合緊急時只改一條，例如 tag pipeline 臨時換一台 runner：

git push origin <tag> -o ci.variable="RUNNER_TAG=<另一個 tag>"

平常的切換還是寫在 CI 檔、走 MR（理由見同一台 Mac 的兩種 runner）。

push option 只在「有 ref 更新」時才會被處理

如果分支已經是最新（Everything up-to-date），這些 -o 完全不會生效——不會報錯，也不會建 MR。 它們是在 GitLab 端的 receive 階段處理的，沒有 ref 變動就沒有那個階段。

所以「先 push、想起來要開 MR、再 push 一次帶 -o」是行不通的。要嘛第一次 push 就帶上，要嘛改用網頁。 （--force-with-lease 改寫歷史也算 ref 更新，會觸發。）

另外：該分支已有開著的 MR 時，merge_request.create 不會重複建立；但如果先前的 MR 已被關閉， 它會建一個新的——force-push 整理過 commit 之後容易不小心留下兩張單，記得回去看一眼。

設了自動 merge 之後再推一次，自動 merge 就不算了（amend 之後 force push、推空 commit 重跑都一樣）：pipeline 綠了也停在那裡等人按。 GitLab 的原始碼裡，來源分支一更新就取消自動 merge（「the source branch was updated」）。重推時再帶一次 merge_request.merge_when_pipeline_succeeds 也救不回來（實測：重推了三次都停住，其中一次有再帶這個選項）。要改的在開 MR 之前改完；重推過的那一張，到網頁上按 merge（或重新設 auto-merge）。
