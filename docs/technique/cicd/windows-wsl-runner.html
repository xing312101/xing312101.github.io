用 Windows 的 WSL2 當 runner

手邊有一台大多閒著的 Windows（例如辦公室某個人的桌機），可以在它的 WSL2 裡跑 Linux 的 runner： Docker executor 跑 Web 專案的 CI（跟雲端同一個 image），需要的話再加一條 Linux 的 shell 道（例如 Android 的 build）。

常見的起因是同一台 Mac 的 Docker 道把 Mac 的記憶體吃滿了：Docker Desktop 那台 VM 先佔走一大塊， 再加上原生的 iOS build —— 實測 16 GB 的 Mac 上 Docker Desktop 佔了 8 GB，swap 幾乎用滿。

本篇只講 Windows／WSL 這一端要注意的。註冊 runner、config.toml、並發這些通用的部分在原本的篇章； 要讓它跟原本那台互為備援（平常跑這台、這台不在才跑那台），見兩台 runner 互為備援。

1. 另外建一個只給 CI 用的 WSL 系統​

做法問題
裝在那台電腦現有的 Ubuntu（WSL）那是別人的開發環境：CI 會跟它搶資源、互相改到套件
用那台電腦的 Docker Desktop跟那個人的容器、設定混在一起；那個人一關掉 Docker Desktop，CI 就停
另外匯入一個專用的 WSL 系統，在裡面裝 Docker Engine 和 gitlab-runner ✅多一個系統要維護；記憶體要跟別人分（第 6 節）
# 官方的 Ubuntu WSL 映像（rootfs 壓縮檔）下載下來，先跟官方公布的 SHA256 比對
Get-FileHash .\<映像檔> -Algorithm SHA256

# 匯入成一個新的 WSL 系統：放在 SSD、非系統槽（不要放傳統硬碟，build 會很慢）
wsl --import <名稱> D:\wsl\<名稱> .\<映像檔> --version 2

2. /etc/wsl.conf：跟 Windows 隔開​

[boot]
systemd=true

[automount]
enabled=false
mountFsTab=false

[interop]
enabled=false
appendWindowsPath=false

[network]
hostname=<名稱>
設定為什麼
systemd=truedocker、gitlab-runner 用 systemd 管，開機自己起來
automount 關掉不掛 Windows 的磁碟：job 碰不到那台電腦上的檔案
interop 關掉job 不能執行 Windows 的程式，PATH 裡也不會混進 Windows 的路徑
  • 改完要重啟那個 WSL 系統才生效：wsl --terminate <名稱>（會中斷正在跑的 job，先確認沒有 job 在跑）。 重啟之前，舊的設定照樣有效 —— 實測：[network] 加了 generateResolvConf=false，WSL 每開一個新的 session 還是把 /etc/resolv.conf 換回它產生的那一份（檔案時間就是那個 session 開始的時間）。 如果有東西每分鐘 wsl -d … 進來一次（例如健康檢查），自己改的 DNS 設定撐不到一分鐘，而且不會有任何錯誤訊息
  • 這個檔只寫 ASCII：用 PowerShell 5.1 的腳本寫這個檔時，腳本裡有中文（例如註解），整段會被當成系統的 ANSI 編碼讀而亂掉 —— 實際發生過 [boot] 那一行被吃掉、systemd 沒有起來。說明寫在別的地方，或用英文

3. 裝 Docker Engine 和 gitlab-runner​

照兩邊官方文件的 apt 來源裝（是 Docker Engine，不是 Docker Desktop），兩個服務都 systemctl enable。 註冊見自架 Runner；Docker 道的 config.toml 照 Mac 的 Docker 道（pull_policy、shm_size、volumes），差別只有這台是 linux/amd64。

  • runner 的帳號不要加進 docker 群組：apt 裝的 gitlab-runner 會建一個 gitlab-runner 帳號，shell 道的 job 就是用它跑。 它不在 docker 群組裡，shell 道的 job 就碰不到 Docker 道的容器（部署 job 的私鑰在那些容器裡）。用 id gitlab-runner 確認。 Mac 上做不到這件事：Docker Desktop 就是你那個使用者在用（見同一台 Mac 的兩種 runner的「拿私鑰的 job 也想跑在這台時」）
  • 同一台的 Docker 道和 shell 道共用一個 concurrent，照並發與跨專案共用算（例如 Docker 4 格＋Android 1 格＝5）

4. 讓這個 WSL 系統一直開著​

WSL 沒有人在用時會自己停掉，裡面的 docker、gitlab-runner 跟著停。做法是用 Windows 的「工作排程器」開一個不會結束的程序：

wsl.exe -d <名稱> -u root -- sleep infinity
設定值為什麼
觸發開機時＋每 5 分鐘「快速啟動」開著時，按「關機」再開機其實是從休眠恢復，不一定會觸發「開機時」；每 5 分鐘那個是保險
已經在跑時不要啟動新的執行個體（IgnoreNew）每 5 分鐘那次只在它不在時才補起來。「上次執行結果」常常是 0x800710E0：被略過了，不是錯誤
執行身分不論使用者登入與否均執行、不儲存密碼（S4U）開機後不用有人登入
執行時間上限不限制預設 3 天，時間到會被停掉
失敗時每 1 分鐘重新啟動
電源使用電池時也執行筆電才需要

實測：wsl --terminate <名稱> 之後約 90 秒自己回來；真的關機再冷開機，沒有人登入，約 2 分鐘後 docker、gitlab-runner 都起來了，gitlab-runner verify 正常。

5. 從別台機器操作​

  • 連線用 mDNS 名稱：路由器不是自己管、IP 會變的話，連 <電腦名稱>.local。~/.ssh/config 加 HostKeyAlias， 名稱或 IP 換了，known_hosts 裡記的那一把照樣對得上（第一次連之前，先跟那台電腦上的主機金鑰指紋比對）

  • 指令寫成腳本，從 stdin 送進 WSL：

    ssh <win> 'wsl -d <名稱> -u root -- bash -s' < script.sh

    中間隔著 Windows 的 cmd：一行裡直接寫 |、引號，會先被 cmd 解讀（實測錯誤訊息是「不是內部或外部命令」）； bash -c "cat > 檔案" 也收不到 stdin（實測）。要放上去的檔案，內容用 base64 塞進 bash -s 的那支腳本裡

  • PowerShell：先 scp 一個 .ps1 上去，再 powershell -File 執行；檔案只寫 ASCII（理由同第 2 節）

  • 有些事 SSH 做不到：帳號在 Administrators 群組，SSH 進去照樣沒有系統管理員權限（實測）。 要系統管理員才能做的（例如 w32tm /resync 對時、把 WSL 的目錄加進防毒的排除清單），要有人在那台電腦上做

6. 踩過的三個坑​

時鐘被往回撥：ninja「still dirty」​

症狀：CMake、NDK 的原生建置（例如 Flutter 外掛的 C++ 部分）偶發失敗：

ninja: error: manifest 'build.ninja' still dirty after 100 tries

原因：WSL 裡的 systemd-timesyncd 跟 WSL 自己的「跟 Windows 對時」互搶。那台 Windows 沒有在對網路時間（時間來源是主機板的時鐘，快了一秒多）， WSL 一直把時鐘對回 Windows、timesyncd 又照網路時間撥回去，每 32 秒往回撥一次。撥回的那一刻剛好在 CMake 寫檔中間，build.ninja 就比它依賴的檔還舊。

  • 看有沒有在撥：journalctl -b | grep -c 'Clock change detected'（時鐘每跳一次，systemd-resolved 就記一行），正常要是 0

  • 改法：只讓 WSL 跟 Windows 對時，不要再另外裝 chrony、ntp

    systemctl disable --now systemd-timesyncd
    systemctl mask systemd-timesyncd

  • 想讓時間本身準：在 Windows 用系統管理員身分 w32tm /resync（SSH 做不到，見第 5 節）

  • 實測：mask 之後就沒有再出現 Clock change detected

DNS：一次查很多網址就失敗​

症狀：Gradle 一開始就同時查很多網址，偶發 Temporary failure in name resolution；一般的 job 很少遇到。

原因：WSL 預設產生的 /etc/resolv.conf 直接指向 Windows 的 NAT DNS 代查，沒有快取、也不會換伺服器。 實測在 WSL 裡同時送很多查詢，每一台 DNS 伺服器都會掉 6～17%（那台只有 Wi-Fi）—— 不是某一台 DNS 壞了。

改法：在 WSL 裡用 systemd-resolved 當本機的快取、上游多給幾台，WSL 本身和 Docker 道的容器都改用它：

# /etc/systemd/resolved.conf.d/ci-dns.conf
# DNSStubListenerExtra：也在 docker0 上聽，容器才連得到（容器裡的 127.0.0.53 是容器自己）
[Resolve]
DNS=<區網的 DNS> 1.1.1.1 8.8.8.8
FallbackDNS=8.8.4.4
Cache=yes
DNSStubListener=yes
DNSStubListenerExtra=172.17.0.1
# /etc/gitlab-runner/config.toml：Docker 道的 job 容器都用它（runner 會自己重讀，不用重啟）
[[runners]]
  [runners.docker]
    dns = ["172.17.0.1"]          # Docker 預設網段的 docker0
# WSL 本身：/etc/resolv.conf 換成一般檔案再鎖住，WSL 開新 session 時就蓋不掉
cp -P /etc/resolv.conf /etc/resolv.conf.bak     # 原本是 WSL 產生的連結，留著還原用
rm /etc/resolv.conf
echo 'nameserver 127.0.0.53' > /etc/resolv.conf
chattr +i /etc/resolv.conf                      # 還原：chattr -i，再把連結放回去
  • 為什麼要鎖住：WSL 每開一個新的 session 就會重寫 /etc/resolv.conf；wsl.conf 的 generateResolvConf=false 要重啟 WSL 系統才生效（第 2 節）。鎖住就不用等重啟；generateResolvConf=false 也照樣加，給之後重啟用
  • 實測：容器裡同時查 180 次，失敗 0 次；WSL 開新 session 之後沒被改回，連查 30 次失敗 0 次
  • 還沒實測：WSL 重啟之後 resolved 綁不綁得到 172.17.0.1（它可能比 docker0 先起來）—— 重啟後用 ss -lun | grep 172.17.0.1:53 看一次
  • 寫這篇時，Gradle 那邊還沒累積到足夠的 build 次數，有沒有完全解決還不知道

記憶體：WSL 預設只拿一半​

WSL2 預設最多用 Windows 記憶體的一半（32 GB 的機器就是 16 GB 左右），Docker 道、shell 道一起分：

  • Android（Gradle）一支 build 就可能吃到 10 GB：gradle.properties 的 -Xmx8G 只是 Gradle 那一個 JVM，另外還有 Kotlin daemon、原生編譯。 實測兩支同時跑，其中一支被系統砍掉
  • 所以 Android 那一道 limit = 1。要同時跑兩支，先在 Windows 的 %UserProfile%\.wslconfig 調高 [wsl2] 的 memory= （改完要 wsl --shutdown，這台電腦上所有的 WSL 系統都會停），而且要留 Docker 道的份
  • 看用量：WSL 裡 free -g

7. 這台是別人每天在用的電腦​

  • 晚上會被關機：沒有備援的話，這段時間的 job 會排隊，排太久 GitLab 會直接判失敗、不會等到隔天（規則見兩台 runner 互為備援）
  • Windows Update 會在「使用時段」以外自己重開機：每週清理、長時間的 job 避開那段時間
  • 不要借用那台電腦上的開發工具：Windows 版的 SDK、Flutter 在 WSL 的 Linux build 用不了，而且這個 WSL 系統刻意不掛磁碟、不能執行 Windows 程式； 共用的話，CI 跟那個人的開發環境會互相影響。CI 要的工具裝在 WSL 裡 runner 帳號的家目錄（Android 的清單見 Flutter：跑在哪台機器 → 自架 Linux 的 shell 道）

8. 每週清理​

Docker 道的 cache volume 會一直留著重用：數量大約是「專案數 × 並發格數 × 2（受保護分支另一份）」，裡面的 pip、npm 快取越長越大。用 systemd timer 每週清一次：

# /etc/systemd/system/runner-cleanup.service
[Unit]
After=docker.service
Requires=docker.service

[Service]
Type=oneshot
ExecStart=/usr/share/gitlab-runner/clear-docker-cache prune-volumes
ExecStart=/usr/bin/docker image prune -f
# /etc/systemd/system/runner-cleanup.timer
# Persistent=true：那個時間電腦沒開的話，下次開機補跑
[Timer]
OnCalendar=Sun *-*-* 12:30:00
Persistent=true
RandomizedDelaySec=10min

[Install]
WantedBy=timers.target

systemctl enable --now runner-cleanup.timer，systemctl list-timers 看下一次的時間。

  • clear-docker-cache（gitlab-runner 套件附的）只清帶 runner 標籤、沒在用的容器、volume、image；docker image prune -f 只清沒有標籤的 image —— 釘了版本的 CI image（python、node、mysql…）會留著，下一個 job 不用重抓
  • systemd 的設定檔不能在值的後面寫註解（Persistent=true # … 整串會被當成值），註解要自己一行
  • 時間避開 Windows Update 可能重開機的時段
  • 代價：清完之後的第一個 job 沒有快取，會慢一點
  • 實測：第一次手動跑清掉約 700 MB 的 cache volume，CI 的 image 都還在

9. 驗收清單​

  • gitlab-runner verify 每一個都 valid，GitLab 上顯示 online
  • wsl --terminate <名稱> 之後幾分鐘內自己回來；真的關機再開機，沒有人登入也回來
  • id gitlab-runner 裡沒有 docker
  • journalctl -b | grep -c 'Clock change detected' 是 0
  • 開兩個新的 session，/etc/resolv.conf 都還是 nameserver 127.0.0.53、檔案時間沒變，lsattr /etc/resolv.conf 有 i
  • 推一個只改 CI 檔的測試分支，job 頁面開頭印的 runner 名稱是這台
