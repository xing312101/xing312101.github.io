兩台 runner 互為備援：平常跑 A，A 不在才跑 B

兩台自架機器都能跑同一類 job（例如 Windows 的 WSL2 和原本那台 Mac，都有 Docker 道）， 想要「平常跑 A，A 關機或出問題時 B 自動接手，A 回來再交回去」。本篇講怎麼做、切過去的順序，以及 runner 跑到一半不見時 GitLab 怎麼判、retry 要列哪些。

1. GitLab 沒有「優先」這回事​

同一個 tag 掛在兩個 runner 上，job 給先來問的那一個 —— 沒有權重、沒有順序。所以「A 優先」只能這樣做：A 正常的時候，B 的 runner 根本不要開。

做法要什麼代價
用 API 把 B 暫停、恢復一把有 API 權限的 tokentoken 要放在跑切換程式的那台機器上
B 的那一道拆成獨立的 gitlab-runner run 程序，切換程式直接開關它 ✅什麼都不用B 那台多一個程序要管

2. 兩台掛同一個 tag​

variables:
  # 跑在哪，切換就改這一行（走 MR）：
  #   linux-docker            兩台都可以：平常 A，A 不在時 B 接手
  #   win-docker / mac-docker 只要某一台（除錯、量時間）
  #   saas-linux-small-amd64  GitLab.com 的共享 runner（吃額度）
  RUNNER_TAG: linux-docker
  • A 的 runner 加上 linux-docker，B 的 runner 也加；各自原本的 tag 留著，要指定機器時用。tag 在 GitLab 網頁上改（tag 存在伺服器端）
  • 每個要用的 repo 都要把 A 的 runner 開放進來（忘了的症狀是 job 永遠 pending，見並發與跨專案共用）
  • 寫法跟同一台 Mac 的兩種 runner的寫法 B 一樣，只是多一個「兩台都可以」的值

3. 把 B 的那一道拆成獨立的程序​

~/.gitlab-runner/config.toml          原本的：只留 B 的其他道（例如 iOS 的 shell 道），一直開著
~/.gitlab-runner-docker/config.toml   新的：只有要備援的那一道，由切換程式開關
  • 沒有 job 在跑的時候，把那一個 [[runners]] 區塊（含 token）搬到新的 config.toml、加上它自己的 concurrent；原本那份拿掉它、concurrent 跟著減
  • 同一個 token ＝ GitLab 上還是同一個 runner；.runner_system_id 也一樣（照機器算出來的），不會多出一個 runner manager
  • 新程序的 service（macOS 的 launchd、Linux 的 systemd）不要開機自動啟動、不要掛了自動重啟：開關交給切換程式
  • 拆開之後 concurrent 是每個程序各算各的，整台的總量是相加（見並發與跨專案共用）

4. 切換程式​

每分鐘跑一次（launchd、systemd timer、cron 都可以）：

  1. 檢查 A：SSH 過去看 docker、gitlab-runner 是不是 active，再跑一次 docker info（要設逾時，例如 45 秒：Docker 卡住時 docker info 會一直不回來）
  2. 連續 5 次正常 → 交回 A：對 B 的程序送 SIGQUIT（同一個 pid 只送一次）
  3. 連續 3 次不正常 → B 接手：B 需要的東西先開好（例如 Docker Desktop 沒開就先開、等 docker info 通了），再啟動 B 的程序
  4. 狀態寫進一個檔（現在的目標、連續次數、送過 SIGQUIT 的 pid），每次切換記一行 log、跳通知
  • 兩邊的次數不一樣是刻意的：A 掛了要快一點接手；A 回來要確定穩了才交回去，不然 A 時好時壞時，B 會一直開開關關
  • SIGQUIT，不要 SIGTERM：SIGQUIT 是「不接新的 job、手上的跑完才結束」；SIGTERM、SIGINT 會中斷正在跑的 job（官方文件的 signals 一節）。 Linux 上 systemctl stop gitlab-runner 預設送的是 SIGTERM，官方文件建議 unit 設 KillSignal=SIGQUIT
  • 先用「觀察模式」跑一陣子：只記判斷、不真的開關，B 一律開著。log 裡的判斷跟實際情況對得上，才改成正式模式
  • 留一個開關能假裝 A 正常、不正常（例如環境變數），測「第 5 次才停、不會重複送」「第 3 次才開」
  • B 那台上別的東西不要動：例如 Docker Desktop 裡還有開發用的資料庫，切換程式只負責開它、不關它
  • 用 bash 寫的話，注意變數後面緊接中文（例如 $pid））會出錯，寫成 ${pid}
  • 要有一行指令能把整套切換停掉（停掉切換程式本身的排程），之後手動開關 B

5. 切過去的順序：不讓 job 卡住​

  1. A 的 runner 註冊好、每個 repo 都開放、試跑過（推一個只改 CI 檔的測試分支，RUNNER_TAG 指到 A 專用的 tag）
  2. B 的 runner 加上共用的 tag
  3. B 的那一道拆成獨立程序，切換程式用觀察模式跑起來
  4. 開 MR，把每個 repo 的 RUNNER_TAG 改成共用的 tag
  5. 看一陣子：兩台都接到 job、都是綠的
  6. 才把切換程式改成正式模式

第 6 步不能提前：還有 job 只帶 B 專用的 tag 時，B 一停，那些 job 就沒有 runner 接。實測觀察期間兩台各接了十幾個 job，全部成功，才改成正式模式。

6. runner 跑到一半不見：GitLab 怎麼判、retry 要列哪些​

GitLab 與 gitlab-runner 目前的原始碼裡是這樣判的：

狀況什麼時候判失敗failure reason
跑到一半，runner 整台不見（斷電、斷網、被直接關掉）30 分鐘沒收到回報no_updates_running
跑到一半，runner 被叫停、而且來得及回報（作業系統關機、服務被停掉）當下runner_interrupted
在排隊，能接它的 runner 都超過 2 小時沒連上 GitLab排隊超過 1 小時stuck_pending_no_matching_runners
在排隊（不管 runner 在不在）排隊超過 1 天stuck_pending_with_matching_runners

所以帶 $RUNNER_TAG 的 job 這樣寫：

.runner: &runner
  tags: [ $RUNNER_TAG ]
  retry:
    max: 1
    when:
      - runner_system_failure   # runner 自己出錯（例如 Docker 起不來）
      - runner_interrupted      # runner 被叫停：機器關機、服務被停掉
      - no_updates_running      # runner 整台不見：30 分鐘沒回報才判
  • 舊的寫法 stuck_or_timeout_failure 現在是別名：GitLab 把它拆成上表的 no_updates_running 和兩個 stuck_pending_*，舊名字照樣對得上這幾個，但會出現 deprecated 的警告。 它對不上 runner_interrupted —— 只列了舊名字和 runner_system_failure 的話，機器正常關機時中斷的 job 不會自動重跑
  • 自架的 GitLab 版本比較舊時，可能還沒有這幾個新的值，CI 檔會驗證失敗 —— 那時候用 stuck_or_timeout_failure
  • stuck_pending_* 不建議列：沒有 runner 在線時重排一次，只是再等一個小時、再失敗一次
  • 只有「做到一半、從頭再做一次也沒關係」的 job 才能自動重跑。部署要先設計成可以重跑，見用 deploy repo 部署 → 切換在主機上自己跑
  • 實際發生過：傍晚那台 Windows 被關機時，一條部署的 pipeline 正在跑端對端測試。runner 的 log 停在關機那一刻，沒有任何「收到停止訊號」的紀錄 —— 也就是沒有機會回報，只能等 30 分鐘後判 no_updates_running；備援的 Mac 那晚在睡，到隔天早上都沒有接到任何 job，重跑的那一個也沒有人接
晚上兩台都不在：job 不會乖乖排到隔天

能接的 runner 都超過 2 小時沒連上 GitLab 之後，排隊超過 1 小時的 job 會被判失敗（pipeline 變紅）；列了 stuck_or_timeout_failure 的話會再排一次，再過一小時又失敗。 隔天開機也不會自己接著跑，要手動 Retry。傍晚的 merge、打 tag 要記得這件事。

7. 沒有 API token，怎麼看現在跑在哪​

  • job 頁面開頭印的 runner 名稱：這是正本
  • Docker 道：job 的容器帶著 label，docker inspect -f '{{index .Config.Labels "com.gitlab.gitlab-runner.job.url"}}' <容器> 就是那個 job 的網址（另外還有 ….job.ref、….job.sha）
  • shell 道：看 runner 帳號底下的程序，工作目錄 builds/<token 前段>/<槽位>/<namespace>/<專案> 看得出是哪一道、哪個專案。 只算 runner 程序底下的子孫：job 結束後留下來的孤兒程序（例如 Xcode 的背景程序）不算
  • 切換程式的狀態檔、log：現在的目標是哪一台、最近幾次切換
  • 排隊中的 job 看不到：那要 API

8. 代價​

  • 兩台都要維護：runner 版本、image、每週清理
  • merge gate 綁在「兩台至少一台開著」；兩台都不在的時段（例如晚上）跟只有一台時一樣，見上面的 warning
  • 切換程式本身也會壞：它停了，B 就維持當下的狀態 —— 所以第 4 節最後那一行停用指令要寫在文件裡
  • 部署的 job 也跑在這兩台的話，私鑰兩台都會經手（拿私鑰的 job 也想跑在這台時）
