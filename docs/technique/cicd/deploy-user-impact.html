部署時使用者看到什麼：重啟不報錯、維護模式、舊分頁

部署自動化之後，部署變得很頻繁 —— 每一次都會有使用者剛好在用。這篇處理「部署的那幾秒到幾分鐘，使用者看到什麼」。 反向代理附 Caddy 與 nginx 兩種寫法，每一段都實測過（量法在最後一節）。

先量，再決定要做哪幾項

每個專案停機的長度不一樣。先照最後一節的方法量一次「現在重啟會連不上幾秒」，再看要做到哪一步。

0. 部署的每個階段​

階段典型長度沒處理時使用者看到的處理方式
前端換版rsync 那幾秒剛好打開的人拿到「新的 index.html、它要的 JS 還沒到」前端每版一個目錄、切連結（用 deploy repo 部署）
後端重啟（沒有 migration）5～10 秒（實測：等長連線關閉＋程式載入）這幾秒所有 API 都是 502第 1 節：代理先等，或後端不關監聽的 socket
後端停機（有 migration）幾十秒到幾分鐘全部 502；從聊天 App 打開網頁、要先登入的人卡在「登入失敗」第 2 節：維護模式
部署之後還開著的舊分頁直到使用者自己重新整理舊版前端打新版 API，改過的地方出錯第 3 節：提示有新版
前後端分開部署的中間兩條 pipeline 之間幾分鐘新後端配舊前端（或反過來）第 4 節：相容的順序

1. 後端重啟時不要回 502​

Caddy：連不上就先等​

api.example.com {
    reverse_proxy localhost:9000 {
        lb_try_duration 20s     # 連不上時最多等 20 秒
        lb_try_interval 250ms   # 每 250ms 試一次
    }
}

實測（重啟期間每 0.2 秒打 GET 與 POST）：改之前約 10 秒全部 502，改之後 0 個錯誤，最慢的請求等 8～9 秒。

  • 只有「連不上」才重試：請求還沒送到後端，POST 不會重複（實測：後端收到的 POST 數＝送出的數，3 MB 的 body 也照樣送到）
  • 擋不到的：重啟那一刻正在處理中的請求（例如正在上傳的檔案）還是會斷；停機超過 20 秒的，等滿照樣 502（那是第 2 節的事）
  • 代價：後端真的掛掉時，使用者要等 20 秒才看到錯誤

nginx：沒有「先等」，要換做法​

nginx 免費版沒有「連不上就等一下再試」：連線被拒時立刻 502，proxy_next_upstream 只會換另一台後端。所以只有一個後端時， 要從後端那邊下手 —— 讓監聽的 socket 在重啟期間一直開著，或開兩個後端輪流重啟。

做法 A：後端用 gunicorn，部署用 kill -HUP 熱重載（Python；FastAPI 用 -k uvicorn.workers.UvicornWorker）

gunicorn --chdir /srv/app/current -b 127.0.0.1:9000 -w 2 -p /run/app.pid app:app
# 部署：切好 current 連結之後
kill -HUP "$(cat /run/app.pid)"      # 監聽的 socket 不關，新 worker 起來、舊的做完手上的再退

實測：0 個錯誤，最慢等 4 秒（新 worker 載入程式的時間）；POST 沒有重複。

每版一個目錄（current 連結）時，--chdir 一定要寫連結的路徑

實測：以 systemd 啟動、沒寫 --chdir 時，切了 current、再 HUP，跑的還是舊版，而且沒有任何錯誤。 原因：gunicorn 重載時回到「啟動時的工作目錄」，它先看環境變數 PWD（保留連結的路徑），沒有才用解析過的真實路徑 （releases/<舊版>）。在終端機裡手動啟動有 PWD，所以手動測都正常；systemd 不設 PWD，上線才出事。 寫了 --chdir /srv/app/current 就兩種情況都正確。驗收時要確認回應的確是新版（例如 health 帶版本號），不能只看 200。

做法 B：兩個後端，輪流重啟

upstream app {
    server 127.0.0.1:9001 max_fails=0;
    server 127.0.0.1:9002 max_fails=0;
}
server {
    location /api/ {
        proxy_pass http://app;
        proxy_next_upstream error timeout;   # 連不上這台就換另一台
        proxy_connect_timeout 2s;
    }
}

部署：重啟 9001 → 等它能回應 → 重啟 9002 → 等它能回應。實測 0 個錯誤、POST 沒有重複（請求沒送出去才換台）。

max_fails 的預設會讓第二次重啟漏掉幾個

預設 max_fails=1 fail_timeout=10s：9001 重啟時被記成「掛了」，之後的 fail_timeout 內 nginx 都不會再試它 —— 就算它已經起來了。這時馬上重啟 9002，nginx 認為兩台都掛了，直接 502。 實測 max_fails=1 fail_timeout=2s、兩次重啟緊接著：GET、POST 各 2 個 502。改成 max_fails=0（每次都試），或兩次重啟中間 等超過 fail_timeout，都是 0 個錯誤。

兩個後端要注意：定時任務只能在其中一個跑、兩個版本會短暫同時在線（第 4 節的相容規則要成立）。只有一個後端又不想換 gunicorn 時， 另一條路是 systemd 的 socket activation（由 systemd 持有監聽的 socket，重啟期間新連線在系統排隊）—— 本篇沒有實測，用之前自己量。

2. 停機比較久時：維護模式​

有 migration 要停服務幾分鐘時，光「等」不夠（等滿照樣 502），而且 502 的訊息是「暫時無法連線」—— 使用者會以為是自己的網路， 或以為系統壞了。

做法：部署腳本在停服務前建一個旗標檔，反向代理看到它就不轉給後端，一律回固定的 503 JSON；後端起來、health 正常之後刪掉。

停服務前：touch <旗標檔> → 等幾秒讓進行中的請求做完 → 停服務 → 備份、migration → 啟動 → health 200 → rm <旗標檔>
  • 旗標檔放在反向代理的帳號讀得到、又不會被當成網頁送出去的地方（例如前端目錄最上層，而網站的 root 指 current）
  • 部署中途失敗時旗標留著（服務本來就是停的，說「更新中」是對的）；部署腳本開始時看到旗標還在就停下，等人來看 —— 回滾例外：事故處理是「開維護 → 停服務 → downgrade → 回滾」，回滾要能在維護模式開著時做，切換完、後端起來了自己關掉（見用 deploy repo 部署的回滾）
  • 後端自己的 health（127.0.0.1:<埠>）不經過代理，部署腳本照樣用它判斷起來了沒
代理自己回的錯誤，沒有後端加的 CORS header

前後端不同網域時，CORS header 平常是後端加的。維護模式的回應是代理給的 —— 不自己帶，瀏覽器會把它擋掉， 前端只看到 Failed to fetch，維護畫面根本出不來（實測：同一個維護回應拿掉 CORS 那幾行，瀏覽器就讀不到）。 帶 Authorization 的請求，瀏覽器還會先送預檢（OPTIONS），預檢也要代理自己回、而且要 2xx。

Caddy​

api.example.com {
    @maintenance file {
        root /var/www/web.example.com
        try_files /MAINTENANCE
    }
    handle @maintenance {
        header Cache-Control "no-store"
        header Vary "Origin"
        @from_web header Origin https://web.example.com
        header @from_web Access-Control-Allow-Origin "https://web.example.com"
        header @from_web Access-Control-Allow-Credentials "true"
        @preflight method OPTIONS
        handle @preflight {
            header Access-Control-Allow-Methods "GET, POST, PUT, PATCH, DELETE, OPTIONS"
            header Access-Control-Allow-Headers "{http.request.header.Access-Control-Request-Headers}"
            respond 204
        }
        handle {
            header Content-Type "application/json; charset=utf-8"
            header Retry-After "30"
            respond `{"maintenance":true,"detail":"系統更新中，約幾分鐘後恢復"}` 503
        }
    }
    handle {
        reverse_proxy localhost:9000 {
            lb_try_duration 20s
            lb_try_interval 250ms
        }
    }
}

nginx​

map $http_origin $cors_origin      { default ""; "https://web.example.com" $http_origin; }
map $http_origin $cors_credentials { default ""; "https://web.example.com" "true"; }

server {
    server_name api.example.com;

    location /api/ {
        if (-f /var/www/web.example.com/MAINTENANCE) { return 503; }
        proxy_pass http://127.0.0.1:9000;
    }

    # 「=」：用 @maintenance 給的狀態碼 —— 預檢要回 204，不能沿用 503
    error_page 503 = @maintenance;
    location @maintenance {
        # always：非 2xx 的回應也要帶。值是空字串的 header nginx 不會送（別的網域就拿不到 CORS）
        add_header Access-Control-Allow-Origin $cors_origin always;
        add_header Access-Control-Allow-Credentials $cors_credentials always;
        add_header Access-Control-Allow-Methods "GET, POST, PUT, PATCH, DELETE, OPTIONS" always;
        add_header Access-Control-Allow-Headers $http_access_control_request_headers always;
        add_header Vary Origin always;
        add_header Cache-Control no-store always;
        add_header Retry-After 30 always;
        if ($request_method = OPTIONS) { return 204; }
        default_type application/json;
        return 503 '{"maintenance":true,"detail":"系統更新中，約幾分鐘後恢復"}';
    }
}
  • error_page 503 只接這裡 return 503 的：後端自己回的 503 照原樣轉出去（沒開 proxy_intercept_errors 的話），不會被說成維護中
  • 兩種都實測過：前端網域來的帶 CORS、預檢 204、別的網域沒有 CORS、沒有 Origin 的呼叫方（例如第三方 webhook）拿到 503 JSON

前端：等到恢復，原樣重送​

維護回應是代理給的，那個請求保證沒有到過後端 —— 所以連寫入也可以放心在恢復後原樣重送，不會重複。 前端所有 API 請求走同一個函式的話，只要改一個地方：

async function sendThroughMaintenance(send: () => Promise<Response>) {
  const started = Date.now();
  for (;;) {
    const res = await send();                       // 每次重新送（fetch 重新建；FormData 可以重複用）
    if (res.status !== 503) return res;
    const body = await res.clone().text();
    if (!isMaintenance(body)) return res;           // 沒有 maintenance 標記 → 不是維護，照舊報錯
    showMaintenanceOverlay();                       // 蓋上「系統更新中」
    if (Date.now() - started > 20 * 60_000) throw new Error('系統更新比預期久，請稍後重新整理再試一次');
    await sleep(5_000 * (0.8 + Math.random() * 0.4)); // 加亂數：恢復那一刻所有分頁不要同時湧回來
  }
}
  • 只認 maintenance: true：後端真的掛掉時的 502 沒有這個標記，要照舊顯示「暫時無法連線」。把當機說成「更新中」，使用者會一直等、沒有人去通報
  • 維護畫面不能讓人關掉（底下那個請求還在等，能點就會再按一次、送出第二份），也不要重新整理頁面（表單打到一半的字會不見）
  • 對元件來說只是那個請求比較慢：恢復後拿到正常結果，使用者不用重按
  • 不用另外開一個維護站：前端網頁是靜態檔，維護期間照樣打得開，只有 API 停 —— 維護畫面做成前端的一個元件就好；轉去別的網址反而丟掉原本的頁面與表單
  • 有自己另外寫 fetch 的地方（公開頁、登入流程）也要走同一個函式。第三方 webhook 在維護期間拿到 503，對方預設多半不會重送，要不要開對方的重送設定要決定

3. 舊分頁：提示有新版​

辦公室那種開了一整天沒關的分頁，跑的是早上載入的前端；部署了新版它不會自己換。

  • build 時把版本（commit）寫進程式，同時產生 version.json；兩個放在同一版的目錄、一起切換，所以「不一樣」就是真的換版了
  • 分頁切回前景、拿到焦點、每隔一段時間（例如 10 分鐘）抓一次 /version.json（cache: 'no-store'），跟自己的版本不同就在頂端提示「有新版本，重新整理」
  • 只提示、不強制重新整理：表單打到一半不能因為換版就不見
  • 拿不到 version.json（離線、舊版沒有這個檔）一律當「沒有新版」，不要亂提示；本機開發 build 不帶版本就不檢查
  • 單頁應用的 web server 對找不到的路徑會回 index.html（SPA fallback）：舊版沒有 version.json 時拿到的是 200 加一頁 HTML， 不是 404 —— 所以判斷要以「解析得出版本字串」為準，不能只看狀態碼
  • 舊分頁的檢查有節流（例如 60 秒內不重複）：自動測試時要等過節流時間再觸發，不然會以為沒有提示
  • 維護模式結束時也看一次：前後端常常一起換

Vite 產生 version.json：

// vite.config.ts
function versionFile(): Plugin {
  return {
    name: 'version-file',
    apply: 'build',
    generateBundle() {
      const version = process.env.VITE_APP_VERSION;   // 部署 build 時帶 commit
      if (version) this.emitFile({ type: 'asset', fileName: 'version.json', source: JSON.stringify({ version }) });
    },
  };
}

部署驗收時順便比對：網站送出的 /version.json 要等於這次部署的版本。

4. 前後端分開部署：誰先上​

前端、後端各有 pipeline，就會有幾分鐘是「新後端＋舊前端」—— 加上第 3 節的舊分頁，這個時間其實更長。規則：

  • 後端先上，而且要相容舊前端一版：新增的欄位、API 可以先有；要拿掉或改名的，分兩次 —— 這一版先停用（舊前端還能用）， 下一版才真的刪（expand → contract）
  • 資料庫也一樣：要刪的欄位先「不再寫入、不再讀」上線一版，確認沒有人在用，再寫 migration 刪掉

5. 一次完整演練的樣子​

用一個不 push 的 commit（加一支什麼都不做的 migration）在測試環境走一遍，旁邊開瀏覽器觀察使用者那一側：

時間發生什麼
0 秒開維護模式、停服務
約 2 秒後瀏覽器蓋上維護畫面（這時剛好有請求在等）
約 1 分鐘後端起來、關維護模式
之後 1 秒內維護畫面自己收起來，頁面正常，沒有錯誤

每次部署都應該是這個樣子；哪一步不是，就是那一段的設定或腳本有問題。

6. 怎麼量​

改之前、改之後各量一次，數字寫進文件。重啟期間每 0.2 秒同時打 GET 與 POST（POST 帶大一點的 body），統計回應碼：

import time, threading, subprocess, urllib.request, urllib.error, collections
URL = "https://api.example.com/api/health"; res = collections.defaultdict(list); stop = time.time() + 30
def loop(method):
    while time.time() < stop:
        try:
            req = urllib.request.Request(URL, method=method, data=b"{}" if method == "POST" else None)
            code = urllib.request.urlopen(req, timeout=40).status
        except urllib.error.HTTPError as e: code = e.code
        except Exception as e: code = type(e).__name__
        res[method].append(code); time.sleep(0.2)
ts = [threading.Thread(target=loop, args=(m,)) for m in ("GET", "GET", "POST", "POST")]; [t.start() for t in ts]
time.sleep(3); subprocess.run(["ssh", "<主機>", "sudo systemctl restart <服務>"]); [t.join() for t in ts]
for m, codes in res.items(): print(m, collections.Counter(codes))
  • POST 要打一支會讀 body 的端點：回 405 的端點不讀 body，大的 body 送到一半連線就被關掉，看起來像失敗、其實跟重啟無關
  • 查 POST 有沒有重複：數後端 log 裡那支端點的筆數，跟送出的數比
  • 維護模式要用真的瀏覽器、跨網域測一次（curl 不管 CORS，curl 過了不代表瀏覽器讀得到）
  • 在本機用容器起代理＋一個會重啟的小後端，就能把各種寫法都量一遍，不必拿正式環境試
