  • 用 tag 上正式

用 tag 上正式：測試 → 配對端對端測試 → 閘門 → 部署 → 補號碼

接在用 deploy repo 部署之後：主分支 push 自動上測試環境，正式環境要人打一個 tag 才上。 前端、後端各一個 repo，deploy repo 一份。本篇每一段都在測試環境上當正式實際跑過（包括故意弄壞的那一次）。

1. 號碼與 tag​

  • 名稱含 release 就觸發；慣例 release-YYYYMMDD-N，全系統一起數（不是每個 repo 各數各的）
  • 只上一邊就只在那一邊打；沒打的那一邊維持線上的版本
  • 兩邊都上：兩邊打同一個號碼，而且在短時間內都推上去（見第 6 節）
  • 把 release* 設成 protected tag（只有 Maintainer 能建）：打 tag 等於同意上正式
protected tag 用 git 刪不掉

git push origin :refs/tags/<tag> 會被擋（「You can only delete protected tags using the web interface」）。打錯的 tag 只能從網頁刪。 演練、測試時用的 tag 名稱要明顯（release-test-…），事後記得去網頁刪。

2. 打 tag 的那條 pipeline：要不要重跑測試？​

直覺是「這個 commit 在主分支上已經測過了，不用再跑」。但部署是在 deploy repo 做的，它要確認「這個 commit 的 CI 是綠的」—— CI_JOB_TOKEN 讀不到別的專案的 pipeline 結果，在 deploy repo 那一側判斷不了。

最直接的做法：打 tag 的那條 pipeline 自己再跑一次測試，觸發 deploy repo 的 job 排在測試之後。代價是每次上正式多用幾分鐘的 CI 分鐘數。

test:
  rules:
    - if: $CI_COMMIT_BRANCH
    - if: '$CI_COMMIT_TAG =~ /release/ && $CI_COMMIT_TAG_MESSAGE !~ /^\[mirror\]/'

deploy-release:
  stage: deploy                         # 測試全綠才到這裡
  rules:
    - if: '$CI_COMMIT_TAG =~ /release/ && $CI_COMMIT_TAG_MESSAGE !~ /^\[mirror\]/'
  trigger:
    project: <group>/<deploy-repo>
    branch: main
    strategy: depend
  variables:
    TARGET: production
    FROM_REPO: backend
    UPSTREAM_SHA: $CI_COMMIT_SHA
    RELEASE_TAG: $CI_COMMIT_TAG

[mirror] 那個條件是給第 6 節「補號碼」用的：系統補上去的 tag 不能再觸發測試與部署（不然會繞圈）。

3. 部署前的檢查（deploy repo）​

檢查不過時
tag 指的就是觸發帶來的這個 commit停
這個 commit 在主分支上（git merge-base --is-ancestor <sha> origin/main）停：不在主分支上的東西不能上正式
這個號碼在這一站、這一邊沒有被別的 commit 用過停：換號碼
正式環境已經比它新停（紅）——日常 push 到測試環境時這種情況是「跳過」，上正式打到舊版本是打錯了，要讓人看到
號碼檢查要分得出「這一次換的是哪一邊」

部署紀錄一行裡通常兩邊的版本都有，但沒換的那一邊只是線上原本的版本。實測：前後端同號，後端先上，那一行的 frontend= 是線上原本的前端 —— 前端那條拿它比對，判成「這個號碼的前端是別的版本」，紅了。紀錄要多記一欄 side=（這次換的是哪一邊），檢查只比對同一邊的。

4. 配對端對端測試​

主分支 push 時，前後端各自的 CI 只守自己：後端測自己的 API、前端的型別檢查只看前端自己定義的型別。 改了 API 的回傳形狀，兩邊都綠、放在一起畫面卻壞。上正式前補一關：把「這次要上的那一對」放在一起跑瀏覽器流程。

  • 這一對＝打 tag 的那一邊＋另一邊同號的 tag（等最多 2 分鐘讓它推上來）；沒有就配正式環境線上的那個版本
  • 全部在 runner 上、跑完就丟：資料庫用 job 的 services:（先斷言庫名），金鑰（JWT 之類）這次亂數產生，檔案存本機，不給第三方服務的金鑰 —— 碰不到任何一站
  • 登入：無頭瀏覽器走不完第三方登入，用後端提供的一次性登入連結（跟真的出事時用的同一個機制）
  • 環境：語言版本照正式環境的 image，前端的 Node 照那個 commit 的版本檔現裝、瀏覽器現裝。實測 runner 上整段約 2.5 分鐘，不必另做 image
  • 部署 job 用 needs: 接在它後面：它沒過，部署就不會開始
pair-e2e:
  stage: build
  image: <正式環境的語言 image>
  rules:
    - if: $TARGET && $RELEASE_TAG
  services:
    - name: mysql:<正式環境的版本>
  script: [ "<起這一對前後端、跑 e2e 的腳本>" ]
  artifacts:
    when: always                    # 沒過的時候最需要 log
    paths: [ <後端、前端、e2e 的 log 目錄> ]

deploy:
  needs:
    - job: pair-e2e
      optional: true                # 日常 push 沒有這個 job
驗它真的擋得住：做一對「只在 e2e 才壞」的版本

「沒過就不部署」靠的是 needs:，要實際讓它紅一次才算數。在測試分支放一個只在 e2e 的 build 裡才出錯的改動（例如 build 參數是 e2e 時一載入就丟錯）， 單元測試與各站的 build 照樣綠、tag 那條會一路走到配對測試；打一個測試用的 release tag。 確認：配對測試紅、部署 job 沒有跑（主機上沒有部署的登入、部署紀錄沒變）。就算部署被誤放行，第 3 節「不在主分支上」也會擋下來 —— 演練不會真的上線。

  • 安裝瀏覽器的系統套件時 apt 會印一堆 debconf: unable to initialize frontend —— 設 DEBIAN_FRONTEND=noninteractive； 輸出寫進 log 檔、失敗時才印最後幾行，不要整個丟到 /dev/null（裝不起來時就看不到原因）
  • 觸發帶來的 CI_COMMIT_SHA 是 40 碼，紀錄與訊息統一截成 7 碼

5. 閘門：沒人在用才上​

正式環境有人在操作時不要停服務。讀反向代理的存取紀錄：最近 10 分鐘沒有寫入才放行；有人在用就每分鐘看一次，最多等 60 分鐘，超過就停、由人決定。

  • 只算成功的寫入（狀態 < 400）：量測、掃描打錯的 POST 都是 4xx，算進去閘門會一直等
  • 排除「開著網頁就會有」的請求（例如通知串流換票）
  • 只印時間、方法、路徑 —— 不印查詢字串（網址裡可能有簽名、token）
  • 等待放在緊貼著切換的地方：等的這段時間可能有人在建資料
  • 用一份假的存取紀錄驗邏輯（10 分鐘內成功的寫入算、換票不算、失敗的不算、讀取不算、壞掉的行跳過）

6. 補號碼：讓兩個 repo 都看得到那一對​

只上後端時，前端 repo 裡沒有這個號碼 —— 之後要查「這個號碼上正式時前端是哪一版」只能翻部署紀錄。 部署、驗收都成功後，在沒打號碼的那一邊、它線上的那個 commit，補一個 annotated tag，訊息以 [mirror] 開頭（第 2 節的 rule 靠它不再觸發）。

  • 推到別的 repo 要寫入權限：CI_JOB_TOKEN 只能讀別的專案。用 deploy key：前後端各一把、各只能寫自己那個 repo， 公鑰加進那個 repo 的 Deploy keys（勾寫入）並加進 protected tag 的 Allowed to create，私鑰放 deploy repo 的 File 變數
  • 實測 gitlab.com 免費方案可以：deploy key 建得出 protected tag
  • 推 tag 用 SSH，gitlab.com 的主機指紋固定在 repo 裡的 known_hosts 檔（跟官方公布的核對過），不要 StrictHostKeyChecking=no
  • 沒設金鑰時只提醒、不失敗：上正式本身照常
兩邊都要上時，tag 要在等待時間內都推上去

系統等另一邊的同號 tag 只等一段時間（例如 2 分鐘）。超過了，它會把那個號碼補在另一邊線上原本的版本上 —— 之後才推的真正 tag 就推不上去了（同名 tag 已存在，而且是 protected）。

7. 實測順序（把測試環境當正式）​

  1. 先讓測試環境落後一版（用回滾），模擬「正式還沒上」
  2. 只打一邊 → 看：測試 → 配對（配線上的另一邊）→ 閘門 → 部署 → 紀錄有號碼 → 另一邊被補上號碼、而且沒觸發任何 job
  3. 兩邊同號、故意先推前端 → 看前端等後端先上
  4. 反向：tag 不在主分支上、正式已經比 tag 新 → 都要在動到任何東西之前停下
  5. 做一對壞的（第 4 節的 tip）→ 配對測試紅、部署沒跑
  6. 最後才把 TARGET 換成真的正式環境 —— 而且正式環境那邊（目錄結構、部署帳號的權限、反向代理的設定）要先準備好，不然下一次打 tag 就紅
