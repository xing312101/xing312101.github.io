本機綠、CI 紅：測試依賴「跑的那台機器」

同一份程式、同一份測試，在你的電腦上全綠，上了 CI 就紅（或反過來）。原因幾乎都是測試偷偷依賴了跑的那台機器的狀態。 CI 每次都是一台剛開的乾淨機器，正好把這些依賴全部翻出來 —— 這是好事，代表正式環境哪天換機器也會撞到。

1. 時區​

你的電腦在台灣時區，CI 的容器預設是 UTC。凡是「本地時間」的邏輯都會差 8 小時：

期待：「2026-10-01 07:05」（台灣早上 7 點）
CI： 「2026-09-30 23:05」（UTC 的前一天晚上）

修法：把測試的時區固定下來，不要靠跑的那台：

// vitest.config.ts（要在 worker 啟動前設，Date 才會照它算）
process.env.TZ = 'Asia/Taipei';
# 後端：「今天」一律用指定時區算，不要用 date.today()（那是主機的日期）
datetime.now(ZoneInfo("Asia/Taipei")).date()

驗證：在本機故意用 UTC 跑（TZ=UTC npm test）要照樣過。

2. 機器「剛開機」​

time.monotonic()（以及各語言的 monotonic clock）是開機到現在的秒數，不是絕對時間。拿它做節流時，初始值設成 0 就出事：

_last_check = 0.0                      # ✗
def maybe_check():
    now = time.monotonic()
    if now - _last_check < 600:        # 機器開機不到 10 分鐘 → now < 600 → 第一次就被擋掉
        return

你的電腦開了好幾天，now 很大，永遠過；CI 的機器是剛開的，now 只有幾十秒，第一次檢查永遠被跳過。 正式環境也一樣：主機重開機後那 10 分鐘內的第一次會漏掉。

修法：初始值用「從來沒查過」：_last_check = float("-inf")（或 None 另外判斷）。 補一條測試：把 monotonic patch 成很小的值（例如 5 秒），斷言第一次會執行。

note

這類問題在本機用 docker 模擬 CI 也抓不到：容器沒有自己的開機時間，monotonic 算的是宿主 kernel（Mac 上是 Docker Desktop 那台 VM）開了多久，通常早就超過門檻。只有真的上 CI 才會撞到。

3. 「前提不成立就 skip」把問題藏起來​

def test_default_settings_apply():
    if not default_settings_exist():
        pytest.skip("前置條件：要有預設設定")     # ✗

在你那份累積很久的測試庫裡，前提一直成立，測試一直在跑；CI 是全新建的環境，前提不成立 → skip → pipeline 照樣綠。 真正的問題（「新建的環境少了預設設定」）就這樣一直沒人發現。

修法：前提不成立本身就是問題，讓它失敗，並在訊息裡講清楚前提是誰負責建的：

assert default_settings_exist(), "沒有預設設定：舊環境靠 migration 補、新環境靠 seed"

順手看一眼 CI 報告裡的 skipped 數量：本機 0 個、CI 有幾個，那幾個就是線索。

4. 全新建的環境 vs 一路升級上來的環境​

正式環境是一路 migration 升級上來的；CI 是從空庫用「建新環境」的腳本建的。兩條路建出來的資料不一定一樣：

  • migration 幫「已經設定過的資料」補一列（只補設定過的），但新環境跑 migration 時還什麼都沒設定 → 什麼都沒補
  • 接著建環境的 seed 寫入它自己那份（舊的）清單 → 新加的東西就這樣漏了，沒有任何錯誤

修法：

  • seed 的清單補齊；再加一條結構性的測試：「凡是 migration 補過的項目，seed 裡也要有」（掃 migration 檔裡的那類寫入）
  • CI 就用「建新環境」的那支腳本建測試庫 —— 它就是在測「明天開一個新站會不會少東西」

5. 升級框架之後「安靜地全綠」的測試​

有些測試會翻框架的內部結構，例如「逐支檢查每個 API 都有權限規則」：掃 app.routes，對每一支檢查。 Web 框架升級後，app.routes 不再把 include 進來的子路由攤平（變成一層包裝），這條測試找不到任何路由 —— 迴圈一次都沒跑，所以全綠。 同一個檔案裡有一條寫了「至少檢查到 80 支」的斷言，紅了才被發現；另一條沒寫，就安靜地綠著。

  • 會迴圈的守門測試，一定要斷言「真的檢查到了幾個」（例如 assert checked > 80）。不然「範圍變成空的」跟「全部合格」看起來一模一樣
  • 把「列出所有路由」收成一個共用的小工具，數量的斷言寫在工具裡：結構再變時紅在一個地方
  • 升級框架時特別看這類測試：它們不是因為功能壞了才紅，而是可能不紅

6. 對照表​

症狀先懷疑
日期／時間差一天、差 8 小時時區
「每 N 分鐘一次」的功能第一次沒跑monotonic 初始值、機器剛開機
本機 0 skipped、CI 有 skipped前提靠本機資料才成立
只在全新環境缺東西seed 跟 migration 不一致
送到主機上跑的腳本語法錯誤，本機跑得好好的主機的語言版本比較舊（例：f-string 的大括號裡再用同一種引號，Python 3.12 才可以；主機是 3.11）——用主機的版本跑一次
本機手動跑腳本才炸、CI 綠本機 bash 3.2 vs CI bash 5（見基本觀念 §3.1）
依賴的套件版本不同鎖定檔沒照正式環境、CI 沒嚴格照鎖定檔裝（見 pipeline-patterns）
