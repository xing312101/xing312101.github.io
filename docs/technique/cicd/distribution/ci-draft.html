CI：打包、照使用者的步驟裝一次、建草稿

接在總覽之後。推 v* 的 tag 時跑；最後只建一個草稿，簽章和發佈在自己的電腦上。

1. 工作怎麼分​

工作跑在做什麼跑不跑第三方程式
testLinux全部的測試、弱點和授權檢查；tag 要等於版本號、commit 要在 main 上會（npm ci）
buildLinux打包每個平台、確認內容一致、算 SHA-256、Linux 版照使用者的步驟裝一次會
verify-macosmacOSmacOS 版照使用者的步驟裝一次（用最低支援的執行環境版本）只跑打包好的檔
verify-windowsWindowsWindows 版照使用者的步驟裝一次只跑打包好的檔
draftLinux核對 SHA-256、同步使用者文件、建草稿不跑：沒有 npm ci，不執行任何套件的程式

拿得到 releases repo 寫入 token 的只有 draft，而它不執行任何依賴套件。依賴被下毒時，能動手腳的最多到 build 為止，碰不到那把 token； 它換掉的壓縮檔，也會在 draft 跟 job output 的 SHA-256 核對時對不上。

on:
  push:
    tags: ['v*']
permissions:
  contents: read          # 預設只讀；寫 releases repo 用另外的 token
concurrency:
  group: release-${{ github.ref }}
  cancel-in-progress: false

2. test：tag 要對得上​

- name: tag 要跟版本號一樣，而且要在 main 上
  env:
    TAG: ${{ github.ref_name }}
  run: |
    version=$(node -p "require('./package.json').version")
    [ "$TAG" = "v$version" ] || { echo "tag $TAG 跟版本號 $version 不一樣"; exit 1; }
    git merge-base --is-ancestor "$GITHUB_SHA" origin/main || { echo '這個 commit 不在 main 上'; exit 1; }

checkout 要 fetch-depth: 0，不然比不出祖先關係。不發佈沒有經過 main 的版本：在別的分支上打的 tag、沒推上 main 的 commit，都不會出去。

3. build：一台打包所有平台，確認內容一樣​

  • 在一台 Linux 上打包所有平台（macOS、Linux x64／arm64、Windows 的 zip）。程式本體如果是同一份（例如打包成單一 JS 檔），確認每個壓縮檔裡的那一份一模一樣： 這樣在 macOS、Windows、Linux x64 上驗過，x64 的 runner 跑不了的 linux-arm64 也等於驗過了。

  • 比對時要小心「全部都讀不到」：讀不到的檔雜湊是空字串的雜湊（e3b0c442…b855），四個都讀不到時「種類只有一種」，看起來全部一致。

    [ "$(ls dist/*.tar.gz dist/*.zip | wc -l)" = 4 ] || { echo '壓縮檔不是 4 個'; exit 1; }
    sums=$({
      for f in dist/*.tar.gz; do tar -xOzf "$f" "$(basename "$f" .tar.gz)/mytool.mjs" | sha256sum; done
      for f in dist/*.zip;    do unzip -p   "$f" "$(basename "$f" .zip)/mytool.mjs"    | sha256sum; done
    })
    printf '%s\n' "$sums" | grep -q '^e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855' && { echo '有壓縮檔讀不到'; exit 1; }
    [ "$(printf '%s\n' "$sums" | sort -u | wc -l)" = 1 ] || { echo '各平台的內容不一樣'; exit 1; }

  • 打包一完成就算 SHA-256，走 job output，不跟壓縮檔放在同一個 artifact：整個 artifact 被換掉的話，裡面的 .sha256 也跟著換，核對不出來。

    - id: sums
      run: |
        cd dist
        { echo 'sums<<SUMS_END'; sha256sum -- *.tar.gz *.zip; echo 'SUMS_END'; } >> "$GITHUB_OUTPUT"
    - uses: actions/upload-artifact@<SHA> # v5.0.0
      id: upload
      with: { name: release, path: "dist/*", if-no-files-found: error, retention-days: 7 }

  • 這一版的更新說明要寫好：在 build 就檢查 CHANGELOG 裡有這一版的段落，不要等到最後一步才失敗。

4. 每個平台照使用者的步驟裝一次​

打包壞了要在簽章之前發現。每個平台各一個工作，照使用者文件的步驟裝：解壓、放進 PATH、跑 --version、跑自我檢查的指令（例如 mytool doctor）， 需要沙盒之類的功能就確認它真的起得來。

  • 用使用者端最低支援的版本（例如 Node 的現役 LTS）：開發用最新版，使用者端的最低版本靠這一步守著。

  • 照 id 下載 artifact，不照名字：拿到的一定是 build 傳的那一份，不是之後有人同名上傳的。

    - uses: actions/download-artifact@<SHA> # v6.0.0
      with:
        artifact-ids: ${{ needs.build.outputs.artifact-id }}
        merge-multiple: true
        path: dist

  • 這些工作不跑 npm ci，只執行打包好的檔案 —— 也就是使用者會拿到的那一份。

macOS 的 runner 在私有 repo 的分鐘數是 Linux 的 10 倍。另外做一個手動觸發的 workflow 跑同一支 macOS 檢查，推 tag 之前先在那裡跑一次：紅了不用重推 tag。

5. draft：核對、同步文件、建草稿​

draft 拿得到 releases repo 的寫入 token，所以它只複製、不執行：

  1. 原始碼 checkout 到另一個資料夾（path: source），artifact 下載到另一個。使用者文件、更新說明、使用條款從這個 tag 的原始碼產生，不用 artifact 裡的東西。

  2. 跟 build 的 job output 核對 SHA-256（不是跟 artifact 裡的比）。檔名不認得、是 symlink、artifact 裡多出來的檔，一律停：

    printf '%s\n' "$SUMS" | grep . > expected.sha256 || { echo 'build 沒有傳 SHA-256 過來'; exit 1; }
    mkdir out
    while read -r sum name; do
      case $name in */* | *..* | '') echo "不認得的檔名：$name"; exit 1 ;; mytool-*.tar.gz | mytool-*-windows.zip) ;; *) exit 1 ;; esac
      { [ -f "artifact/$name" ] && [ ! -L "artifact/$name" ]; } || { echo "artifact 裡沒有 $name"; exit 1; }
      cp "artifact/$name" "out/$name"
      printf '%s  %s\n' "$sum" "$name" > "out/$name.sha256"   # 給使用者的 .sha256 從核對過的值產生
    done < expected.sha256
    [ "$(find artifact -mindepth 1 | wc -l)" = "$(wc -l < expected.sha256)" ] || { echo 'artifact 裡多了東西'; exit 1; }
    (cd out && for f in *.sha256; do sha256sum -c "$f"; done)

  3. 同步文件：只複製一般的檔案（symlink 會把它指到的內容推到公開的 repo）。公鑰、tap 的名字這類佔位字串在這裡填，填完檢查沒有剩下佔位字串、公鑰的格式對： 手動維護 README 上的公鑰一定會忘，而忘了就等於使用者驗不了章。

  4. 先同步文件、再建 release：第一次發佈時 releases repo 是空的，空的 repo 建不了 release（tag 要指到一個 commit），clone 下來也沒有分支，一律推到 HEAD:main。 token 用 gh auth setup-git，不寫進 clone 的網址（會留在 .git/config，也會出現在 ps）。

  5. 建草稿：gh release create "$TAG" out/* --repo "$RELEASES_REPO" --notes-file notes.md --target main --draft。

重跑時：已經發佈的檔案不能被默默換掉​

上一次在建草稿之後失敗、重跑時 release 已經在了。這時已經在上面的壓縮檔要跟這次打包的一模一樣，才補傳： tag 被移到別的 commit、或打包不可重現時，不能換掉使用者可能已經下載、驗過的檔案。

names=$(gh release view "$TAG" --repo "$RELEASES_REPO" --json assets --jq '.assets[].name')   # 先單獨取得清單
while IFS= read -r name; do
  case $name in *.tar.gz | *.zip) ;; *) continue ;; esac
  gh release download "$TAG" --repo "$RELEASES_REPO" --pattern "$name" --dir published
  cmp -s "published/$name" "out/$name" || { echo "已發佈的 $name 跟這次的不一樣：不覆蓋"; exit 1; }
done <<< "$names"

清單要先單獨取得：寫成 for name in $(gh …) 的話，gh 失敗（例如 502）也不會停，迴圈跑零次，接著就直接覆蓋了。

6. 已經發佈的版本不能改寫​

發佈之後，tag 指到的 commit 就是使用者驗過的那一版。之後 amend、rebase、force push 把它換掉的話，那個版本就從 main 的歷史裡消失了： 比不出版本之間差了什麼，使用者回報問題時也找不到他那一版的原始碼。

  • 規矩：修改一律加新的 commit、一般的 git push。commit 之前先看 git tag --contains HEAD，有輸出就代表 HEAD 已經發佈過，不能 amend。

  • CI 抓得到：私有 repo 在 Free 方案用不了「禁止 force push」的分支保護，所以每次推 main 都檢查每個 v* tag 都還在歷史裡：

    #!/bin/sh
    # 用法：sh scripts/check-release-tags.sh [要檢查的 commit，預設 HEAD]
    set -eu
    head=${1:-HEAD}
    bad=0
    for t in $(git tag --list 'v*'); do
      if ! git merge-base --is-ancestor "$t^{commit}" "$head"; then
        printf '✗ %s 不在 %s 的歷史裡：已經發佈的版本被改寫了\n' "$t" "$head" >&2
        bad=1
      fi
    done
    exit "$bad"
    released-history:
      if: github.ref == 'refs/heads/main'   # 只看 main：別的分支本來就可能比 tag 舊
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@<SHA> # v7.0.1
          with: { persist-credentials: false, fetch-depth: 0 }   # 淺的 clone 比不出 tag 在不在歷史裡
        - run: sh scripts/check-release-tags.sh

7. 釘住第三方 action​

uses: actions/checkout@v7 的 v7 是一個可以被移動的 tag：action 的 repo 被入侵時，下一次跑的就是別的程式，而且拿得到你的 token。 一律釘在 commit SHA，註解寫版本：

- uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1

註解是給人看的，改了註解沒改 SHA（或反過來）看不出來。升版本時、以及偶爾手動，用 GitHub API 核對註解的版本真的指到那個 SHA：

grep -rhoP 'uses: \K[^ ]+@[0-9a-f]{40} # \S+' .github/workflows/*.yml | sort -u | while read -r ref _ ver; do
  repo=${ref%@*}; sha=${ref#*@}
  real=$(curl -sS "https://api.github.com/repos/$repo/git/ref/tags/$ver" | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>console.log(JSON.parse(s).object?.sha??'?'))")
  [ "$sha" = "$real" ] && echo "✓ $repo $ver" || echo "✗ $repo $ver：釘 ${sha:0:12}…，實際 ${real:0:12}…"
done

（annotated tag 的 object.sha 是 tag 物件、不是 commit，對不上時再查一次 git/tags/<sha>。）

8. 要先設好的​

Settings → Secrets and variables → Actions（repo 層級）：

名稱種類內容
RELEASES_REPOvariable<帳號>/mytool-releases（不寫進 git）
MINISIGN_PUBLIC_KEYvariableminisign 公鑰那一串（.pub 檔的第二行，RW 開頭），會填進使用者的 README
RELEASES_TOKENsecretfine-grained token，只開 releases repo 的 Contents 寫入

私鑰不在這張表上：它只在你的電腦上。
