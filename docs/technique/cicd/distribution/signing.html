在自己的電腦上簽章

接在 CI：打包、驗證、建草稿之後。CI 建好草稿（使用者看不到），你在自己的電腦上簽、發佈。

1. 為什麼不在 CI 上簽​

最直覺的做法是把私鑰放進 GitHub Actions 的 secret，tag 一推就簽好發佈。問題在於簽之前沒有人看一眼，而且：

  • 私有 repo 用不了「必要的審核者」（environment 的 required reviewers）：GitHub 的 Free、Pro、Team 方案只給公開的 repo。
  • Free 方案連 environment 的 secret 都沒有，只能放 repo 層級的 secret：任何分支的 workflow 都拿得到。有人（或一個被下毒的依賴）能推一個 workflow 到任一分支，就能簽出驗得過的檔案。

所以改成：CI 只建草稿；私鑰只放在你的電腦上，簽的時候密碼是你自己在終端機前輸入的。代價是每一版要你在電腦前跑一支腳本、按一次 y —— 這一下就是「簽之前的人工確認」。

2. minisign​

  • 小、只做簽章這件事、金鑰是一行字（Ed25519），使用者用一行指令驗。不用 GPG 的信任網，也不用買憑證。
  • trusted comment：簽章裡一段也被簽到的文字。簽的時候寫進版本和檔名，使用者驗章時看得到，改了就驗不過（第 4 節）。

產生金鑰（只做一次）。檔名帶工具的名字，跟你別的金鑰分得開；設密碼：

mkdir -p ~/.minisign
minisign -G -p ~/.minisign/mytool.pub -s ~/.minisign/mytool.key

.pub 的第二行（RW 開頭）就是公鑰，設成 repository variable MINISIGN_PUBLIC_KEY，CI 建草稿時填進 releases repo 的 README。

3. 簽章腳本：有一步不對就停，不會發佈​

sh scripts/sign-release.sh <tag> [releases repo]
  1. 那個 release 要是草稿：已經發佈的不重簽
  2. 下載壓縮檔和 .sha256 到新的暫存資料夾，逐一核對（不解開、不執行裡面的任何東西）
  3. 列出要簽的檔案和 SHA-256，你按 y 才繼續
  4. 用你的私鑰簽；再用 releases repo 的 README 上的公鑰（使用者驗章用的那一把）驗一次
  5. 上傳 .minisig，把草稿改成正式發佈；叫 Homebrew tap 的 workflow 更新

重點片段：

set -eu
key=${MINISIGN_KEY:-$HOME/.minisign/mytool.key}

# 1. 草稿才簽
draft=$(gh release view "$tag" --repo "$repo" --json isDraft --jq .isDraft) || die "讀不到 ${repo} 的 ${tag}"
[ "$draft" = true ] || die "${tag} 已經發佈了，不是草稿：不重簽"

work=$(mktemp -d)
trap 'rm -rf "$work"' EXIT INT TERM
gh release download "$tag" --repo "$repo" --dir "$work" --pattern '*.tar.gz' --pattern '*.zip' --pattern '*.sha256'

# 2. 核對 SHA-256：草稿裡的 .sha256 是 CI 照 build 的 job output 產生的
for f in "$work"/mytool-*; do
  case $f in *.sha256) continue ;; esac
  expected=$(cut -d ' ' -f 1 <"$f.sha256")
  [ "$(awk '{print $2}' <"$f.sha256")" = "$(basename "$f")" ] || die "$(basename "$f").sha256 寫的是別的檔案"
  [ "$expected" = "$(sha256 "$f")" ] || die "$(basename "$f") 的 SHA-256 對不上"
done

# 3. 你按 y 才簽
printf '簽這些檔、發佈 %s？[y/N] ' "$tag"
read -r answer || answer=
[ "$answer" = y ] || die "沒有簽，草稿留著"

# 4. 簽；用 README 上的公鑰驗（使用者照文件驗章用的就是那一把）
pub=$(gh api "repos/$repo/contents/README.md" --jq '.content | @base64d' | grep -oE 'RW[A-Za-z0-9+/]{40,}={0,2}' | head -n 1)
for f in "$work"/mytool-*; do
  case $f in *.sha256) continue ;; esac
  minisign -S -s "$key" -m "$f" -t "mytool $tag $(basename "$f")"
  minisign -V -P "$pub" -m "$f" >/dev/null || die "用 README 上的公鑰驗不過：私鑰跟公開的公鑰不是同一對"
done

# 5. 發佈
gh release upload "$tag" "$work"/*.minisig --repo "$repo" --clobber
gh release edit "$tag" --repo "$repo" --draft=false --latest
gh workflow run update.yml --repo "${repo%%/*}/homebrew-mytool" || echo '沒叫到 tap 的 workflow：它每天會自己看一次'
  • 第 4 步用 README 上的公鑰驗，不是用你電腦上的 .pub：README 上那一把才是使用者會用的。變數設錯、換過金鑰忘了改，這裡就擋下來，不會發出一版所有人都驗不過的檔。
  • 私鑰的預設位置只是方便：MINISIGN_KEY 可以指到別的位置（例如外接的加密磁碟）。
  • macOS 內建的 bash 是 3.2（/bin/sh 預設也是它）：中文訊息裡 $var 後面直接接中文字會被當成變數名稱的一部分（set -u 下直接報錯），一律寫 ${var}。

4. 附註為什麼要綁住版本和檔名​

簽章驗得過，只代表「這是發佈者簽過的某個檔案」。沒有附註的話：

  • 有人可以把 v1.0.0（有已知漏洞）的壓縮檔連同它真的簽章，換到 v1.2.0 的位置 —— 簽章完全正確。
  • 也可以把別的平台的檔案連同它的簽章，改名放到這個平台的位置：簽章照樣驗得過，裝到的是別的東西。

附註寫成 mytool v1.2.0 mytool-1.2.0-darwin.tar.gz，使用者（和 Homebrew tap 的更新腳本）就能檢查版本和檔名都是自己要的那一個。

5. 使用者怎麼驗​

使用者文件要寫的：

minisign -Vm mytool-<版本>-<平台>.tar.gz -P <公鑰>
# Signature and comment signature verified
# Trusted comment: mytool v1.2.0 mytool-1.2.0-darwin.tar.gz
  • 公鑰第一次拿到之後自己留一份，之後每次更新都用自己留的那一份驗。公鑰跟程式放在同一個 repo，只從那裡拿的話，repo 被動手腳時公鑰會跟著被換掉。
  • 看 trusted comment 的版本要跟自己要裝的一樣；不要裝比現在用的更舊的版本（第 4 節的降版）。
  • Windows 也有 minisign（GitHub releases 或 scoop install minisign），指令一樣。

6. 金鑰遺失、外洩、換新​

minisign 沒有撤銷機制，也沒有「舊的那把替新的背書」以外的交接方式。換得掉，但要講清楚：

情況做法
遺失（私鑰不見、忘了密碼）產生新的一對、改 MINISIGN_PUBLIC_KEY，下一版起用新的。README 留著舊的公鑰、寫明哪幾版用哪一把，更新說明講為什麼換。不講的話，自己留了公鑰的使用者會發現新版驗不過 —— 跟有人換掉 releases 的檔案看起來一模一樣
外洩（別人可能拿到）拿到的人簽得出驗得過的檔案：馬上換，公告舊的那一把不能再信，從哪一版開始用新的
還在手上、只是想換用舊的私鑰簽新的公鑰，一起發佈：使用者用自己留的舊公鑰驗得到這次交接

預防：私鑰設密碼；加密備份一份放在別的地方，密碼另外放。

7. 這支腳本怎麼測​

不用真的 GitHub、也不用真的金鑰：在 PATH 前面放假的 gh、minisign（幾行的 shell 腳本，照參數回固定的內容、記錄被呼叫的方式）， 再驗每一個「應該停下來」的情況：已經發佈的不重簽、SHA-256 對不上、.sha256 寫的是別的檔、沒按 y、README 上的公鑰跟私鑰不是同一對 —— 每一種都要沒有呼叫到 gh release edit --draft=false。
