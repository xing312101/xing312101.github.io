同一台 Mac 跑兩種 runner：shell 道與 Docker 道

一台自架 Mac 常常同時服務兩類專案，設定方法完全不一樣，不要把其中一邊的寫法照抄到另一邊：

  • App 專案（Flutter／iOS）：要原生 Xcode、模擬器、鑰匙圈 → shell executor。 自架 Runner 與並發與跨專案共用講的主要是這種。
  • Web 專案（後端、前端、deploy repo）：CI 本來就是 Linux 容器＋資料庫 services:＋瀏覽器測試 → 在同一台 Mac 另外註冊一個 docker executor 的 runner（靠 Docker Desktop）。雲端怎麼跑，這裡就怎麼跑，只是不吃額度。

本篇是兩者的對照、「什麼時候跑 Mac、什麼時候跑雲端」的兩種切換寫法、merge gate 的代價，以及 Docker 道在 macOS 上要注意的。 註冊 runner、config.toml、跨專案觸發這些通用的部分各在原本的篇章，這裡只連過去。

對照表​

shell 道（App 專案）Docker 道（Web 專案）
executorshelldocker（Docker Desktop 那台 Linux VM；Apple silicon 上是 linux/arm64）
image:被忽略；工具鏈要裝在機器上（Homebrew、fvm、Xcode）照用，跟雲端 runner 同一個 image
services:（資料庫等）不支援支援，主機名就是服務別名
工作目錄~/builds/… 重用，跟你自己的檔案是同一個使用者每個 job 一個新容器；/builds、/cache 放在 Docker volume 裡留給下一個 job（git fetch、快取才快）
全域狀態互相破壞（鑰匙圈、/tmp 固定檔名、simctl）有，要分出 limit = 1 的專用道容器裡沒有；共用的只剩 Docker VM 的 CPU、記憶體
macOS 的雷（Spotlight 鎖檔、鑰匙圈密碼框、PATH）有（見自架 Runner）沒有：檔案在 VM 的 volume 裡
架構原生 arm64 macOSimage 要有 linux/arm64 版
放拿私鑰的 job不適合：跟裝第三方套件的 job 同一個使用者、同一個家目錄比 shell 好；仍建議留在雲端「用完就丟」的 runner（見下文）
跟雲端切換的寫法兩支 job＋旗標互斥（兩邊環境不一樣）一支 job＋變數 tag（兩邊同一個 image）

怎麼選：job 需要 Xcode、模擬器、鑰匙圈 → shell；其他（lint、單元測試、要資料庫的測試、Playwright）→ Docker 道。

不要為了 Web 專案改用 shell 道

看起來「同一台機器、少註冊一個 runner」比較省事，實際上 image: 與 services: 全部失效：Python／Node 的版本變成跟著這台 Mac 走、 要自己在 Mac 上裝資料庫、Alpine 的 apk、Debian 的 apt 這類寫法都要改；而且 npm ci、pip install 裝進來的第三方程式 跟你的家目錄同一個使用者，之後同一台機器上拿私鑰的 job 也在用這個環境。

切換跑在哪：兩種寫法​

兩種寫法有一個共同原則：切換寫在 .gitlab-ci.yml 裡、走 MR，不要用 GitLab 網頁上的 CI 變數切。網頁上的變數別人看不到、不進版本； 不會只有一個人在開發，大家要看得到現在跑在哪裡、是誰什麼時候改的。

寫法 A：兩支 job＋旗標互斥（App 專案）​

shell 道會忽略 image:，PATH、工具鏈、快取路徑都跟雲端不一樣，before_script 寫不成一份 —— 所以同一件事寫兩支 job，用旗標讓它們互斥：

variables:
  VERIFY_ON: "mac"            # 切換就改這一行："mac" | "cloud"

.setup_mac: &setup_mac        # shell 道：工具鏈在機器上
  tags: [ mac-shell ]
  before_script:
    - export PATH="/opt/homebrew/bin:$PATH"
    - <用機器上的版本管理工具裝／切到專案指定的版本>

.setup_cloud: &setup_cloud    # 雲端：容器每次全新
  image: <你語言的 CI image>
  before_script:
    - <在容器裡裝工具鏈>

.analyze_job:
  stage: verify
  script: [ "<analyze>" ]

analyze_mac:
  extends: .analyze_job
  <<: *setup_mac
  rules:
    - if: '$VERIFY_ON != "mac"'
      when: never
    - when: always

analyze_cloud:
  extends: .analyze_job
  <<: *setup_cloud
  rules:
    - if: '$VERIFY_ON == "mac"'
      when: never
    - when: always

Flutter 的完整版（fvm、快取）見 Flutter 快檢 → 額度不夠：快檢改跑自架 Mac。

寫法 B：一支 job＋變數 tag（Web 專案）​

Docker 道跟雲端跑的是同一個 image，差別只在「誰執行」，所以一支 job 就夠，把 tag 寫成變數：

variables:
  # 切換就改這一行：
  #   mac-docker              自架 Mac 的 Docker 道（不吃額度）
  #   saas-linux-small-amd64  GitLab.com 的共享 Linux runner（吃額度）
  RUNNER_TAG: mac-docker

.runner: &runner
  tags: [ $RUNNER_TAG ]

pytest:
  stage: test
  image: python:<正式環境那一版>
  services:
    - name: mysql:<正式環境那一版>
  <<: [ *check_rules, *runner ]          # 要合併好幾個錨點就寫成清單
  script: [ "<測試>" ]

deploy:                                  # 拿私鑰的 job：刻意不帶 tag
  environment: { name: hosts/$TARGET }
  script: [ "<部署>" ]
  • tags: 裡可以用變數（實測：帶 $RUNNER_TAG 的 job 都被自架那台接走）
  • saas-linux-small-amd64 是 GitLab.com 共享 Linux runner 的 tag（官方文件；沒帶 tag 的 job 預設也是它接）
  • 拿私鑰的 job 刻意不帶 tag：沒有 tag ＝只有共享 runner 會接（自架那台要關掉「Run untagged jobs」，見下面「註冊這一道」）， 私鑰只出現在雲端用完就丟的機器上，用 environment 收窄私鑰的前提不變。 實測：部署 pipeline 裡拿私鑰的那兩個 job 沒有出現在 Mac 上、部署照常完成；跑在 Docker 道的 build job 開頭印出「拿不到私鑰變數」
  • trigger job 不佔 runner，不用帶 tag
  • 有 deploy repo 這種跨專案觸發的，觸發端要加 inherit: variables: false：不然程式 repo 的 RUNNER_TAG 會被帶進下游、而且蓋過下游自己那一行（理由見 deploy repo → 觸發端）

共通：切回雲端的那張 MR 不會被卡住​

MR 的 pipeline 用的是來源分支的 .gitlab-ci.yml。Mac 關機時開一張「把那一行改成雲端」的 MR，這張 MR 自己就跑在雲端，過了就能 merge。 已經在排隊的其他 pipeline 不會自己換過去，要 rebase 或重跑。

代價：merge gate 綁在這台 Mac 上​

基本觀念的原則是「只讓 always-on 的雲端快檢進 merge gate」。額度不夠、把快檢搬上 Mac，就是刻意放棄這條：

  • Mac 關機、睡眠：MR 的 job 一直 pending —— 不會失敗、不會通知，只是不能 merge
  • 用 tag 上正式時，打 tag 那條會再跑一次測試，一樣要等這台
  • Docker 道多一種狀況：Docker Desktop 沒開時 runner 還在線上、照樣會接 job，但開不了容器，job 在準備階段就失敗

Mac 開著的時候一切照常：MR 的 pipeline 全部跑在 Mac 上，過了照樣自動 merge、觸發部署（實測）。

對策：上面那一行切換、這台設成接電源不睡眠（見自架 Runner）、Docker Desktop 設成登入時啟動。 並且寫進團隊文件：卡住時誰去改哪個檔的哪一行。

Docker 道在 macOS 上要注意的​

  1. Docker Desktop 要一直開著。它跟 brew 的 LaunchAgent 一樣是登入之後才起；沒開時的症狀見上面「代價」。

  2. image 要有 linux/arm64 版。用到的每個 image（含 services: 的）先查一次：

    docker manifest inspect <image>:<tag> | python3 -c \
      "import json,sys; print(sorted({m['platform']['architecture'] for m in json.load(sys.stdin).get('manifests', [])}))"

    常見的官方 image（python、node、mysql、alpine）都有；後端測試（含 MySQL service）、前端的 lint／測試／vite build 在 arm64 上都正常（實測）。腳本裡自己下載工具的（例如照版本檔現裝 Node），用 uname -m 判斷架構 （aarch64 → arm64），不要寫死 x64。

  3. 瀏覽器測試要加大 /dev/shm：Docker 預設只有 64MB，Chromium 容易因此當掉（Playwright 官方建議加大或用 --ipc=host）。 playwright install --with-deps chromium 在 arm64 的 Debian 系 image 上裝得起來、開得了頁面（實測）。

  4. pull_policy = ["if-not-present"]：本機有就不重抓，省頻寬，也避開 Docker Hub 的匿名拉取上限。代價是可變的 tag 不會更新， 所以 image 一律釘到 patch（python:3.11.15，不要寫 python:3）—— 這本來就是版本一致性的要求。

  5. 記憶體看 Docker VM 的上限（Docker Desktop → Settings → Resources），不是看這台 Mac 的總記憶體：資料庫 service＋測試＋瀏覽器同時跑要算得下。

  6. 看有沒有接到 job：docker ps 會出現 runner-<token 前段>-project-<專案 id>-concurrent-<槽位>-… 的容器， 後綴 -predefined（取原始碼）、-build（你的 script）、-<服務>-0（service）。job 跑完容器就刪；要在本機留輸出就趁它在跑時 docker logs -f <容器> > 檔案。正本是 GitLab 的 job 頁面。

  7. 會留下來的東西：/builds、/cache 的具名 volume（runner-…-cache-…，受保護分支另一份 -protected）會一直留著重用； service 的資料 volume 隨容器刪掉（volume_keep = false，實測沒有累積）。清 volume 之前先看清楚：同一份清單裡也有這台機器上別的東西（本機開發用的資料庫 volume）。

config.toml 裡這一道大概長這樣（[[runners]] 的其他欄位照 register 產生的）：

[[runners]]
  name = "mac-docker"
  limit = 1                         # 加了這一道要重算 concurrent（見並發與跨專案共用）
  executor = "docker"
  [runners.docker]
    image = "alpine:<版本>"          # job 沒寫 image 時的預設
    privileged = false
    volumes = ["/cache"]
    pull_policy = ["if-not-present"]
    shm_size = 536870912            # 512MB，給 Chromium

註冊這一道​

一般步驟見自架 Runner → 在 GitLab 建立 runner，這一道要注意的只有：

  • Tags 用寫法 B 那一行的值（例如 mac-docker），Run untagged jobs 不勾：拿私鑰的 job 不帶 tag，才會留在雲端
  • 建在其中一個 repo（project runner），再到其他 repo 的 Settings → CI/CD → Runners 按 Enable for this project；每個 repo 的 Instance runners 保持開著
  • 這台已經有一份寫了說明的 config.toml（例如 App 專案的 shell 道）：照並發與跨專案共用 → 已經寫了說明，又要加一個 runner，不要直接貼網頁給的那行 register
  • 加了這一道要重算 concurrent（同一篇）

驗證：推一個只改 .gitlab-ci.yml 的測試分支（不會觸發部署的那種），看 job 頁面寫的 runner 名稱、docker ps 有沒有出現上面那種容器。
