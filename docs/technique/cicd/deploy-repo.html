用獨立的 deploy repo 部署到自己的主機（multi-project pipeline）

前端、後端各是一個 repo，部署到自己管的 Linux 主機（不是雲端平台）。做法是另開一個 deploy repo，所有部署邏輯只放這一份； 程式 repo 的主分支 CI 綠了，就用 trigger: 叫它部署。

為什麼不把部署腳本放在後端 repo：改一行部署腳本就變成一個後端 commit，會觸發一輪後端測試與部署，而且前端也要部署，兩邊會各寫一份。 另一個好處：前端、後端的部署最後都落在同一個專案的 pipeline，resource_group 才擋得住兩邊同時部署（它只在單一專案內有效）。

push 主分支就自動部署，只適合測試／demo 環境

總覽的原則 3（正式釋出要有人按一下）照樣成立：正式環境改用 release tag 觸發，或在觸發 job 加 when: manual。 下面的範例是 staging。

1. 觸發端（程式 repo）​

stages: [test, deploy]

deploy-staging:
  stage: deploy                      # test 全綠才會跑到這裡
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
  trigger:
    project: <group>/<deploy-repo>
    branch: main
    strategy: depend                 # 部署失敗，這條 pipeline 也紅
  variables:
    TARGET: staging
    FROM_REPO: backend               # 只換這一邊，另一邊維持線上那版
    UPSTREAM_SHA: $CI_COMMIT_SHA

2. 被觸發端（deploy repo）​

workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "push"                  # push 這個 repo：只檢查腳本
    - if: $TARGET && $FROM_REPO =~ /^(backend|frontend)$/ && $UPSTREAM_SHA
    - when: never

stages: [check, build, deploy]

check:                               # 腳本的語法檢查、lint；push 這個 repo 時跑
  stage: check
  rules:
    - if: $CI_PIPELINE_SOURCE == "push"
  script: [ "<shellcheck / bash -n / 自己的檢查>" ]

build-frontend:
  stage: build
  rules:
    - if: $TARGET && $FROM_REPO == "frontend"
  script: [ "bash bin/build-frontend.sh $TARGET $UPSTREAM_SHA" ]
  artifacts: { paths: [dist/], expire_in: 1 day }

deploy:
  stage: deploy
  rules:
    - if: $TARGET
  resource_group: $TARGET            # 同一個環境一次只部署一條
  needs:
    - job: build-frontend
      optional: true                 # 後端部署時沒有這個 job
  script: [ "bash bin/deploy.sh $TARGET $FROM_REPO $UPSTREAM_SHA $CI_PIPELINE_URL" ]
  • dotenv 產出的變數不能拿來寫 rules（rules 在 pipeline 建立時就決定了），要用觸發時就知道的變數（FROM_REPO）
  • resource_group 讓同一個環境排隊；但後到的不一定比較新（連續 push 時舊的那條可能後跑）→ 部署腳本自己要檢查 「線上已經是這版、或線上比較新 → 跳過」（git merge-base --is-ancestor <這次> <線上那版>）

3. 一定要在 GitLab 網頁上設的（漏了就是莫名其妙的錯）​

在哪個 repo設定漏了的症狀
deploy repoSettings → CI/CD → Variables →「Minimum role to use pipeline variables」至少開到會觸發部署的人的角色（push 程式 repo 主分支、打 tag 的人；只有 Maintainer 以上能 push 的話設 Maintainer，不要開到 Developer —— 見機密管理）觸發端的 job 失敗：Downstream pipeline can not be created。新版 GitLab 對新建的專案預設「沒有人可以傳 pipeline variables」，trigger: 帶的 variables: 就算
程式 repo（被 clone 的那邊）Settings → CI/CD → Job token permissions → 允許清單加 deploy repodeploy repo 用 CI_JOB_TOKEN clone 程式 repo 時 403／找不到
deploy repomain 是 protected branchProtected 變數（SSH 私鑰）在 pipeline 裡是空的
deploy repoSSH 私鑰、主機指紋的 File 變數見機密管理 → SSH 私鑰

4. 主機上的部署帳號：最小權限​

不要用你自己登入的那個帳號（多半是免密碼 sudo）給 CI：私鑰放進 GitLab 等於交出整台。開一個專用帳號：

sudo useradd --create-home --shell /bin/bash deploy && sudo passwd -l deploy     # 不能用密碼登入
# authorized_keys 那一行前面加 restrict：只能執行指令，不能轉發、不能開互動終端
echo "restrict ssh-ed25519 AAAA… ci-deploy" | sudo tee /home/deploy/.ssh/authorized_keys

檔案權限用 ACL，不要把它加進原帳號的群組（群組會連帶給它一堆不相干的寫入權）：

sudo setfacl -m u:deploy:--x /home/<原帳號>                         # 只能穿過，不能列出
sudo setfacl -m u:deploy:rwx /srv/<app>                             # 程式目錄本身：建 current 連結、寫部署紀錄
sudo setfacl -R -m u:deploy:rwX /srv/<app>/releases                 # 已經有的檔
sudo setfacl -R -d -m u:deploy:rwX /srv/<app>/releases              # 預設 ACL：之後新建的檔也套用
sudo setfacl -m u:deploy:r /srv/<app>/.env                          # 設定檔唯讀（跑 migration 要資料庫密碼）
sudo setfacl -m u:deploy:rwx /srv/backups/<app>                     # 只給這個專案的備份目錄，不是整個 backups/
  • 少了 -d（預設 ACL）：原帳號手動部署時新建的檔，部署帳號下一次就寫不進去
  • .env 唯讀也是機密：私鑰外流等於資料庫密碼外流，外流時兩個要一起換（見機密管理）

sudo 只開完整、寫死的指令：

deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart <app>.service, \
                            /usr/bin/journalctl --no-pager -u <app>.service --since -1h
sudoers 不要用 * 當參數

/usr/bin/journalctl --no-pager -u <app>.service --since * 看起來只放寬了時間，但 * 吃得下空格： sudo journalctl --no-pager -u <app>.service --since x -u 別的服務 也符合規則 —— 整台主機的 log 都看得到。 參數寫死（--since -1h），寫完用幾種繞過寫法實測會被擋。

別讓部署帳號順帶碰到不相干的機密：程式一被 import 就會初始化雲端儲存（讀雲端金鑰檔）的話，部署帳號跑 「import 檢查」就需要那把金鑰 —— 那把金鑰往往能存取所有環境的檔案。不要開權限給它，改成部署帳號跑檢查時 用環境變數把儲存切到本機暫存目錄；真的服務仍以原帳號跑、照樣用雲端，切換後的 health check 會驗到。

部署帳號讀得到的設定檔，要看裡面的帳號權限有多大：部署帳號通常要讀 .env（跑 migration 要資料庫密碼）， 所以「部署金鑰外流」＝「.env 外流」。實際檢查過一次：.env 裡的資料庫帳號是整台資料庫伺服器的 root，看得到同一台上別的站、別的系統的庫 —— 金鑰外流的範圍遠大於以為的「這一站」。每站一個只看得到自己的庫（加上部署演練用的那個庫）的帳號；檢查方法：用 .env 的帳號連上去跑 SELECT CURRENT_USER()、SHOW DATABASES。

備份目錄：只給它自己那一格，上一層連看都不能看。部署前的資料庫備份要寫在某個目錄，常見的寫法是給部署帳號 「那個專案的備份子目錄」的權限 —— 但如果上一層是 775、裡面的 dump 是 644（mysqldump > 檔 照 umask 產生的預設就是這樣）， 部署帳號照樣讀得到上一層所有的備份：別的站、別的系統、手動做的正式站整庫 dump。實際查過一次，部署帳號讀得到全部 65 份。 這種是離線、帶走就收不回的整庫副本，比讀得到密碼更難善後。

B=/srv/backups
sudo chmod 750 $B && sudo setfacl -m u:deploy:--x $B             # 只能穿過去自己那一格，列不出、讀不到上一層
sudo setfacl -d -m u::rwx,g::r-x,o::--- $B                       # 之後新建的檔其他人一律沒有權限（不靠 umask）
sudo find $B -mindepth 1 -path $B/<app> -prune -o -exec chmod o-rwx {} +   # 已經有的檔
sudo chmod 770 $B/<app> && sudo setfacl -m u:deploy:rwx,d:u:deploy:rwx,d:o::--- $B/<app>

驗：部署帳號 ls $B 要被擋、讀別份 dump 要被擋、自己那一格照常寫讀刪（部署前的備份與「驗備份完整」都要它）。 從別處 mv 進來的檔會保留原本的權限，要自己 chmod o-rwx。

這些設定不在任何程式裡，換主機時不會自己跟過去，漏了也不會有錯誤訊息（部署照樣成功，只是部署帳號看得到不該看的）。 把整套（帳號、ACL、備份目錄、sudoers、反向代理的標頭）寫成一份「換主機照做」的文件放在 deploy repo，最後一節列「該做得到／該被擋」的檢查。

反向代理加上安全標頭（以 Caddy 為例，snippet 寫一次、每個站台區塊 import）：

(security_headers) {
    header {
        Strict-Transport-Security "max-age=31536000"      # 只走 HTTPS；同網域底下還有別的系統時不要加 includeSubDomains
        X-Content-Type-Options "nosniff"
        Referrer-Policy "strict-origin-when-cross-origin"
        Content-Security-Policy "frame-ancestors 'none'"  # 不准被嵌進別人的網頁（點擊劫持）
        X-Frame-Options "DENY"
    }
}
(csp_report_only) {                                       # 完整 CSP 先只回報不擋，{args[0]} 是那一站的 API 網域
    header Content-Security-Policy-Report-Only "default-src 'self'; connect-src 'self' https://{args[0]}; img-src 'self' data: blob: https:; style-src 'self' 'unsafe-inline'; object-src 'none'; base-uri 'self'"
}
app.example.com {
    import security_headers
    import csp_report_only api.example.com
    …
}
  • snippet 要定義在第一個用到它的站台區塊之前，不然 caddy validate 會說「File to import not found」
  • frame-ancestors 'none' 之前先確認自己沒有用 iframe 嵌自己的頁面；在 App 內建瀏覽器（例如通訊軟體裡開網頁）是整頁打開，不是嵌入，不受影響 —— 但要實際開一次確認
  • 先在測試環境 validate → reload，用瀏覽器把主要頁面走一遍、看 console 有沒有 CSP 的訊息，再上正式

上 CD 之前，掃一次主機上留下的舊設定檔：例如當初建站時放的 .env.<站名> 範本，權限常是 644（任何帳號讀得到），裡面也有密碼與金鑰。 程式只讀 .env 的話，這些檔沒有用處，刪掉或改成 600。

寫完一定要實測兩邊：該做得到的（寫程式目錄、重啟這個服務）要做得到；不該做得到的（讀別的服務的設定、重啟別的服務、 停 web server、sudo -u 原帳號、讀 /etc/shadow）要被擋。

5. 部署腳本的寫法​

主機上不放部署腳本：腳本放 deploy repo，用 ssh 送過去執行，部署邏輯只有一份：

remote() {   # remote <動作> 參數…
  local action=$1; shift
  cat remote/lib.sh "remote/$action.sh" | ssh … deploy@<主機> bash -s -- "$(printf '%q ' "$@")"
}
在遠端放背景程式：整組的輸入輸出都要導開

ssh host "cd dir && server ... > log 2>&1 &" 會一直卡著不回來：& 放到背景的是整串 cd … && …，重新導向只套在最後那個指令上， 背景那層 shell 還開著 ssh 的輸出，ssh 就一直等它。整組包起來導開：(cd dir && exec server …) < /dev/null > log 2>&1 &， 或乾脆寫成腳本用 ssh host bash -s < script.sh 送過去。另外 pkill -f '<字串>' 會連「命令列裡剛好有這個字串」的自己那個 shell 一起砍掉 —— 用記下來的 pid。

ssh 會重新切參數

ssh 把參數用空格接成一行送到遠端、再由遠端的 shell 重新切 —— 帶空格的參數（例如部署說明「後端 abc → def」）會被拆散， 只有第一段到得了。先 printf '%q ' 逐一加引號再送。

  • 開頭 set -euo pipefail，而且注意 pipefail 的反向陷阱（grep -v 濾到空 → 中斷）

  • 每版一個目錄、切連結：releases/<sha>/ 解好、建好相依、import 驗過，再 ln -sfn releases/<sha> current.tmp && mv -T current.tmp current， 比原地 rsync 覆蓋安全（不會新舊檔混在一起、回滾只要切回去）

  • 前端也要每版一個目錄，不要以為檔名有 hash 就夠：rsync 會先傳最上層的 index.html、後傳 assets/（實測 rsync 3.4）， 上傳那幾秒打開的人拿到「新的 index.html、它要的 JS 還沒到」；而且沒辦法切回上一版、不知道哪個 hash 檔屬於哪一版所以永遠清不掉。做法：

    web/releases/<sha>/     每版完整一份（index.html、圖、assets/）
    web/pool/assets/        每一版上線過的 hash 檔（給還開著舊頁面的人）
    web/current → releases/<sha>

    web server 的 root 指 current，/assets/* 在 current 找不到再找 pool。上傳順序：先放 pool → 再放 release → 確認 index.html 引用的每個檔兩邊都在 → 才換連結。清理：release 留最近幾版；pool 只刪「沒有留著的版本在用、又放了超過 N 天」的檔。 驗收時比對網站送出的 index.html 就是 current 那一份（web server 沒指 current 會被抓到）

  • 目錄的擁有者要一致（全部是部署帳號的）：人手動部署也以部署帳號寫（rsync --rsync-path="sudo -u deploy rsync"）， 不然之後 CD 清舊版時刪不掉別人的檔。手動建完目錄看一眼權限位元：有些主機在帶預設 ACL 的目錄裡 mkdir 會多出 sticky（t）， sticky 的目錄裡只有擁有者刪得掉東西

  • 有資料庫 migration：先拿正式資料的當下備份在主機上還原到拋棄式的庫，跑 upgrade → downgrade → upgrade； 過了才停服務、備份、升級、切換。dump 是客戶資料，不送到 runner

  • 驗收：每一支 API 都要歸類（直接打／展開參數／排除並寫理由），沒歸類到的新端點讓驗收失敗；再看 log 有沒有新的錯誤

  • 寫部署紀錄（固定格式，機器讀得懂）：下一次部署靠它判斷線上是哪一版

失敗了要能收拾​

停在線上的狀態怎麼辦
準備新版／演練沒動修好重試
切換前的檢查（服務已停）服務是停的、資料庫沒動直接啟動舊版
migration 做到一半服務是停的、資料庫半套downgrade 或用剛做的備份還原，先找人一起看
驗收已經是新版、在跑重試：腳本看到「已經切過去了」就只補驗收與紀錄
驗收過了才發現有問題新版在跑回滾：前後端都只要把 current 切回上一版（有 migration 的要先 downgrade）；上一版被清掉了才重 build
  • 讓腳本可以從失敗的地方重跑：切過去之後才失敗的，重跑不要再切一次，只補後面的步驟
  • 加一個暫停開關（例如 deploy repo 的 CI 變數 CD_PAUSED，有值就第一步停下、讓 pipeline 紅）：有人在手動處理時，CD 不會跟他搶
  • 留一份手動流程：CD 掛了時，在本機用 runner 同一個 image 的容器跑 deploy repo 的同一套腳本（備份、演練、驗收都一樣）

回滾：同一套腳本，多一個開關​

不要另寫一支回滾腳本：在 deploy repo 按 Run pipeline（新版介面叫 New pipeline），帶跟觸發時一樣的變數，加一個 ROLLBACK=1、版本寫要退回的 commit 或 previous。 走同一條路（備份、切換、驗收、寫紀錄），差別只有「允許往回」。

  • 只准退回「那一站上線過的版本」：回滾帶的 commit 要出現在那一站的部署紀錄裡。不檢查的話，ROLLBACK=1 加上任何 commit 都上得去 —— 還沒合併的分支、沒過測試的 commit；而回滾通常又跳過上正式前的那幾道檢查（端對端測試、閘門）。上線過＝當時那幾道都過了，退回去才確定跑得起來。 同理，不是 release、不是回滾的一般部署，也要檢查 commit 在 main 上（git merge-base --is-ancestor <sha> origin/main），手動 Run pipeline 才帶不進別的分支。 驗這兩條：在一份暫時的 clone 上做一個不在 main 上的 commit，拿它去試，要停在檢查、主機上什麼都沒動。 看停下來的那一句是不是你要測的那一條：實測時第一輪 ROLLBACK=1 沒帶進容器（zsh 不會把 $VAR 拆成多個參數，-e ROLLBACK=1 整串變成一個參數）， 測「回滾」卻停在「不在 main 上」那一條 —— 一樣是「擋住了」，看起來像過了。驗守衛時把預期的訊息寫下來比對，不要只看有沒有停
  • previous 是「紀錄裡上一個不一樣的版本」，不是倒數第二行：前後端各自部署時，上一次部署的常常是另一邊，倒數第二行這一邊的版本跟現在一樣
  • 後端中間有 migration（資料庫比要退回的版本新）就停下來，不要硬切：舊程式對著新的表結構跑會出事，而且舊版的 migration 目錄裡沒有新的那幾支， 它自己 downgrade 不了。訊息要講清楚「資料庫是 X、要退回的版本只到 Y、先用線上這一版 downgrade 到 Y」
  • 資料庫現在的版本，要用「線上那一版」的程式讀：在要退回的舊版目錄裡跑 alembic current，它不認得比它新的版本、直接失敗 —— 實測第一次的訊息是「資料庫是 FAILED:」，把錯誤訊息當成了版本號
  • 事故處理的順序：開維護模式 → 停服務與排程 → 用線上這一版 downgrade → 回滾。所以「維護模式開著就不部署」這條要對回滾開例外； 回滾切換完、後端起來之後，自己關掉維護模式、恢復排程
  • build 的檢查要考慮「舊版還沒有這個功能」：例如檢查 build 有沒有產生某個檔，回滾到加這個功能之前的 commit 就一定沒有 —— 先看那個 commit 的設定有沒有產生它的程式，有才要求
  • 正式環境用 tag 上：見用 tag 上正式
  • 演練一次：用一個不 push 的 commit（加一支什麼都不做的 migration）部署到測試環境，再照事故順序回滾；旁邊開瀏覽器看使用者那一側

一次性：從「直接覆蓋」搬成「每版一個目錄」​

已經在跑的正式環境要搬，順序照這樣（實際搬過一次：整個過程只重啟一次，而且反向代理先等，不會直接回 502）：

1. 唯讀檢查：先證明線上是哪一版

  • 後端：git archive <紀錄上的 commit> 解出來，跟線上 rsync -rcn --itemize-changes --delete（排除 .env*、venv、上傳目錄、紀錄檔）—— 只比對、不寫入。 直接覆蓋的老做法常留下「從來沒更新過的測試檔」之類的東西，確認差異只在那裡
  • 套件：線上 venv 的 pip freeze 跟鎖定檔比
  • 前端：用那一站的 build 參數重 build 紀錄上的 commit，比對 index.html 與每個檔。線上可能不等於任何一個 commit 的 build（例如後來單獨換過一張圖）—— 那就照原樣複製，不重 build
  • .env 裡的路徑要是絕對路徑：程式改從 releases/<sha>/ 跑之後，相對路徑會指到每一版自己的目錄（上傳的檔跟著版本跑掉）。.env 本身原位不動，每版放一個連結
  • 順便看部署帳號接下來讀得到什麼：.env 裡的資料庫帳號權限、目錄裡留下的舊範本檔

2. 不影響使用者的準備

  • 部署帳號的權限（ACL、sudo）照測試站那一套，實測「該做得到／不該做得到」兩邊 —— 正式環境不要為了測試真的重啟，用 sudo -l 確認列得出來
  • 用部署帳號把線上那一版做成 releases/<sha>/（建 venv、放 .env 連結、import 驗過）
  • 在另一個埠試跑那個目錄、打一輪唯讀的 API。先確認程式啟動時沒有背景工作（排程、發通知），多開一份才不會有副作用； 部署帳號拿不到的外部儲存（雲端金鑰）切到本機暫存，那幾支讀檔的 API 失敗是預期的
  • 前端：線上的檔照原樣複製進 releases/<sha>/、舊的 hash 檔全部放進 pool/，逐檔比對
  • 反向代理先加好「後端重啟時先等」（部署時使用者看到什麼）：切換時那次重啟就不會有人看到錯誤

3. 切換：等沒人在用，一支腳本跑完

  • 腳本開頭再看一次有沒有人在用（從決定開始到真的跑，中間可能有人進來）
  • 所有可能「比對不上」的東西先產生、先驗過，才開始動：例如反向代理的新設定。原本寫在中間才產生，比對不上就會停在半套（後端切了、前端沒切）
  • 備份資料庫 → systemd 的 WorkingDirectory、ExecStart 改指 current（先備份 unit 檔）→ 建 current 連結 → daemon-reload → 重啟 → 確認服務真的跑在新目錄（readlink -f /proc/<MainPID>/cwd 是 releases/<sha>，不只是 health 200）
  • 前端：反向代理的 root 改指 current、/assets/* 找不到再找 pool → reload → 確認網站送出的 index.html 就是那一份（比對失敗要停：cmp && echo 失敗不會停，要寫成 if）
  • 部署紀錄轉成新格式；舊的最上層檔搬到備份，不要刪；最後用部署帳號跑一次正式的驗收

4. 最後才把上正式的 tag 指到這一站（用 tag 上正式），第一次上的時候在旁邊看。

6. 上線前先在本機跑一次​

GitLab 設定還沒好之前，就能用 runner 同一個 image 在本機跑完整個部署腳本（掛上私鑰、主機指紋、本機的程式 repo）， 每條路線都走一次：正常部署、同一版再部署（要跳過）、舊版（不往回部署）、有 migration 的演練、切換。 本機跑過的，上 GitLab 通常只剩「GitLab 端的設定」會出問題（見第 3 節的表）。
