前後端一起上正式：等另一邊，也要知道另一邊失敗了

接在用 tag 上正式之後。前後端打同一個號碼時，前端那條要等後端先上線再換（誰先上）。 如果只靠「看線上的後端是不是這一版」來等，它答得出「上線了沒」，卻答不出另一邊是還在跑、已經失敗、還是根本沒出發。實際發生過：

  • 後端在自己 repo 的檢查就紅了（漏洞檢查碰上當天新公布的漏洞），觸發 deploy repo 的那支 job 根本沒跑。 前端在 deploy repo 裡乾等到逾時，deploy repo 裡也完全看不到後端那一條 —— 最後是靠 runner 那台機器上的容器結束碼，才知道是後端先死了

同一類的還有兩個（設計上本來就有、還沒撞到就先改了）：

  • 後端的閘門最多等 60 分鐘，前端卻只等 30 分鐘：白天有人在用時，前端先放棄、後端照樣上 —— 正式環境只上了一半，沒有人知道
  • 前端在部署 job 裡等，而部署 job 掛著 resource_group：後端的部署 job 要同一個 group，進不來（第 1 節）

為什麼不直接問 GitLab「另一條怎麼了」：deploy repo 的 CI_JOB_TOKEN 讀不到別的專案的 pipeline（用 tag 上正式 §2）。 另開一個 access token 放進 CI 變數，就多一把要保管、要輪替、權限又比部署還大的鑰匙。兩條 pipeline 本來就都 SSH 得到主機 —— 進度就寫在主機上。

1. 在哪裡等：不要在 resource_group 裡面等​

resource_group 讓同一個環境一次只部署一條（用 deploy repo 部署），在裡面等的 job 會一直佔著它。 前端的部署 job 掛著 resource_group: production 等後端上線，後端的部署 job 也要 production —— 前端先拿到的話，後端排在它後面進不來，兩邊互等到前端逾時。

規則：「等別人」放在不掛 resource_group 的 job。部署前本來就有一支問主機的小 job（plan：算上一版、配哪一版），等待放在它裡面，等到了才進部署的排隊：

plan:                         # 不掛 resource_group：在這裡等
  stage: plan
  timeout: 3 hours            # 要比等待的總上限長（第 4 節），不然先被 GitLab 砍掉，訊息只剩「逾時」
  environment:
    name: hosts/$TARGET
    action: prepare
  script: [ "bash bin/plan.sh ..." ]

deploy:
  stage: deploy
  resource_group: $TARGET     # 排隊只排「真的要動主機」的這一段
  needs: [plan]
等待中的 job 也佔 runner 的一格

GitLab 的共享 runner 每個 job 一台機器，沒有這個問題。在自架 runner 上，等待的 job 幾乎不吃 CPU，卻佔著一格： 這一道 limit = 1 的話，前端的 plan 佔著唯一的一格在等，後端要跑的 job 全排在它後面 —— 一樣是互等，而且這段時間共用這一道的 CI 全停。 最壞的情況是「前端在 plan 等後端」＋「後端的部署在閘門等」兩格都掛著，再留一格給測試：limit 至少 3，concurrent 跟著讓出這幾格（並發與跨專案共用）。

2. 進度寫在主機上​

每個號碼、每一邊一個小檔：<部署目錄>/RELEASE_STATUS/<號碼>-<backend|frontend>，四行：

state=running
at=1792400000
pipeline=https://gitlab.com/<group>/<deploy-repo>/-/pipelines/123
detail=閘門：有人在用，已等 12 分
state意思
running還在跑；detail 是走到哪一步，at 是最後一次更新的時間
deployed已經上線（部署紀錄寫完了）
failed失敗了；pipeline 是紅的那一條

誰寫：

誰什麼時候state
plan開始、開始等另一邊、做完running
部署 job開始、migration 演練、閘門每分鐘、切換、驗收running
部署 job寫完部署紀錄（或線上已經是這一版）deployed
deploy repo 的 report-failure這一條有 job 紅了（when: on_failure，第 3 節）failed
deploy repo 的 release-failed程式 repo 的檢查沒過，觸發過來報（第 3 節）failed

讀寫都用同一支小腳本，用 ssh 送到主機上跑（主機上不放腳本，見部署腳本的寫法）：

# release_status.sh <部署目錄> <號碼> <backend|frontend> [<state> <pipeline 網址> <說明>]
# 只給三個參數＝讀：印出那四行，再加一行 age（距離上次寫入幾秒）；這個號碼沒寫過就什麼都不印
site_dir=$1; release=$2; side=$3; state=${4:-}
d="$site_dir/RELEASE_STATUS"; f="$d/${release}-${side}"
if [ -z "$state" ]; then
  [ -f "$f" ] || exit 0
  cat "$f"
  echo "age=$(( $(date +%s) - $(sed -n 's/^at=//p' "$f") ))"     # 用主機的時鐘算，不拿 runner 的時間比
  exit 0
fi
pipeline=$5; detail=$6
if [ "$state" = failed ] && [ -f "$f" ]; then
  case "$(sed -n 's/^state=//p' "$f")" in
    running)  detail="${detail}；停在：$(sed -n 's/^detail=//p' "$f")" ;;
    deployed) state=deployed; detail="$(sed -n 's/^detail=//p' "$f")；之後的步驟紅了：${detail}" ;;
  esac
fi
mkdir -p "$d"
printf 'state=%s\nat=%s\npipeline=%s\ndetail=%s\n' "$state" "$(date +%s)" "$pipeline" "$detail" > "$f.tmp"
mv "$f.tmp" "$f"                          # 另一邊每 20 秒讀一次：先寫暫存檔再換名，不會讀到寫一半的
find "$d" -type f -mtime +180 -delete     # 一個號碼兩個小檔，留半年

幾個寫法上的決定：

  • failed 接上最後一句 running：寫 failed 的是 when: on_failure 的那支 job，它不知道前面哪一支紅了；最後一次寫進來的 running（「閘門：有人在用」「migration 演練」）就是答案。 等的那一邊印出「失敗了：部署那條有 job 紅了；停在：migration 演練」，看的人就知道去哪裡查
  • 已經 deployed 的不改成 failed：上線之後的步驟（例如補號碼）才紅，版本確實已經在線上。改成 failed 的話，等著的另一邊會停下來不上 —— 變成「後端上了、前端沒上」
  • 只有上正式（帶號碼）才寫：日常部署、回滾不寫
  • 寫不進去只提醒、不擋部署：進度是寫給另一邊看的，不能因為它讓自己的部署失敗。例外是專門回報失敗的那支（第 3 節）：它的用處就是寫進去，寫不進去要紅
set_release_status() {   # set_release_status <state> <說明>
  [ -n "${RELEASE_TAG:-}" ] || return 0
  remote release_status "$SITE_DIR" "$RELEASE_TAG" "$SIDE" "$1" "$CI_PIPELINE_URL" "$2" \
    || echo "[注意] 進度寫不進主機（${1}：${2}），部署照常"
}

3. 失敗的那一邊要說出來：when: on_failure​

上正式會在兩個地方紅，各補一支只在失敗時跑的 job：

在哪裡紅原本的狀況補的 job
程式 repo 的 tag pipeline（測試、漏洞檢查）觸發 deploy repo 的 job 排在測試後面，根本沒跑 —— deploy repo 不知道有這一條程式 repo 的 report-release-failure：失敗時另外觸發 deploy repo，多帶 REPORT_FAILED
deploy repo 那一條（plan、e2e、build、部署）那一條紅了，主機上的進度卻停在最後一句 runningdeploy repo 的 report-failure：放在最後一個 stage，失敗時寫 failed

程式 repo（跟觸發部署的 deploy-release 放同一個 stage）：

report-release-failure:
  stage: deploy
  rules:
    - if: '$CI_COMMIT_TAG =~ /release/ && $CI_COMMIT_TAG_MESSAGE !~ /^\[mirror\]/'
      when: on_failure                # 前面的 stage（測試、漏洞檢查）有 job 紅了才跑
  trigger:
    project: <group>/<deploy-repo>
    branch: main                      # 不寫 strategy: depend：這一條已經紅了，不用等下游
  inherit:
    variables: false
  variables:
    TARGET: production
    FROM_REPO: backend
    UPSTREAM_SHA: $CI_COMMIT_SHA
    RELEASE_TAG: $CI_COMMIT_TAG
    REPORT_FAILED: $CI_PIPELINE_URL   # 紅的是哪一條

deploy repo：

stages: [check, plan, build, deploy, report]

.report: &report
  image: alpine:<版本>
  environment:
    name: hosts/$TARGET
    action: access                    # 要 SSH（私鑰限定 environment 範圍），但不記成一次部署
  before_script:
    - apk add --no-cache -q bash openssh-client

# 程式 repo 的檢查沒過：記下來、不部署。記完照樣紅 —— 這一條就是「這個號碼的這一邊沒上」的紀錄
release-failed:
  stage: plan
  <<: *report
  rules:
    - if: $REPORT_FAILED && $TARGET && $RELEASE_TAG
  script:
    - bash bin/release-failed.sh "$TARGET" "$FROM_REPO" "$RELEASE_TAG" "$REPORT_FAILED" "tag pipeline 的檢查沒過，沒有觸發部署"
    - exit 1

# 這一條有 job 紅了
report-failure:
  stage: report
  <<: *report
  rules:
    - if: $REPORT_FAILED
      when: never
    - if: $TARGET && $RELEASE_TAG
      when: on_failure
  script:
    - bash bin/release-failed.sh "$TARGET" "$FROM_REPO" "$RELEASE_TAG" "$CI_PIPELINE_URL" "部署那條有 job 紅了"

# 原本的每一支（plan、build、e2e、deploy）rules 最前面都加這兩行：回報失敗的那一條不能部署
plan:
  rules:
    - if: $REPORT_FAILED
      when: never
    - if: $TARGET

release-failed.sh 就是用 ssh 在主機上跑上一節那支 release_status.sh … failed …，再把讀回來的內容印出來；寫不進去就讓 job 紅。

  • on_failure 的定義是「前面的 stage 有 job 失敗」（官方文件）：
    • 同一個 stage 的 deploy-release 因為下游部署失敗而紅（strategy: depend），不會觸發 report-release-failure —— 那種失敗由 deploy repo 自己的 report-failure 記，不會記兩次
    • allow_failure: true 的 job 紅了算成功，不會觸發（漏洞檢查不要用 allow_failure 的另一個理由，見 pipeline-patterns）
  • trigger job 能用的 when 只有 on_success、on_failure、always、manual（官方文件的 trigger 一節）
  • 觸發過來的那一條帶的變數跟正常上正式一樣、只多一個 REPORT_FAILED，deploy repo 的 workflow: rules 不用改
  • action: prepare、verify、access 都不會建立部署紀錄；environment 範圍的變數只看 environment 的名稱、不看 action —— prepare 拿得到是官方文件寫的、也實際用過；access 是看 GitLab 的原始碼確認的
合併順序：deploy repo 先

程式 repo 先合併的話，失敗的 tag 會帶著 REPORT_FAILED 觸發還不認得這個變數的舊 deploy repo。舊版只看 TARGET、RELEASE_TAG， 會把這個檢查沒過的版本照常部署上正式。 通則：新增一個「讓下游換一種做法」的觸發變數時，下游先學會認它，上游才開始送。

被取消不算失敗

on_failure 只在「失敗」時跑；job 或整條 pipeline 被取消時，on_failure 的 job 不會跑，也就沒有人寫 failed。 所以等的那一邊一定要有自己的「多久沒動靜就停」（第 4 節），不能只靠失敗通知。

4. 等的那一邊：每 20 秒看一次，照這個順序判斷​

先等另一邊的同號 tag 推上來（最多 2 分鐘；沒有就當成「這次只上這一邊」，見用 tag 上正式 §4）。有的話，每 20 秒讀一次進度與線上版本：

順序看到動作
1另一邊 failed立刻停，印出那一條的網址與「停在哪一步」
2線上的另一邊就是同號的那一版（或更新）放行
3另一邊 deployed，線上卻不是它停：之後被回滾了
4running，但 45 分鐘沒更新停：被取消或卡住了（取消不會觸發 on_failure）
5一直沒有任何進度，已經等了 45 分鐘停：還在自己 repo 跑測試、卡在排隊，或被取消
6總共等滿 150 分鐘停
—其他繼續等；進度有變才印一行
  • 1 要排在 2 前面：另一邊失敗之後，有人改打下一個號碼上線了 —— 線上雖然比較新，卻不是這個號碼一起配對測試過的那一對
  • 停下來的訊息要講另一邊的事（哪一條 pipeline、停在哪一步），不要只說「逾時」：看的人要去的是另一個 repo
# 前端的 plan 裡呼叫；die＝印出訊息、exit 1。STEP=20、SILENT_MAX=2700、TOTAL_MAX=9000（秒，測試時用環境變數縮短）
wait_for_backend() {
  local release=$1 bsha st state age detail url online start waited last=""
  # （這之前：fetch 後端 repo 的 tag，最多等 2 分鐘讓同號的 tag 推上來）
  bsha=$(git -C backend rev-parse --short=7 "refs/tags/${release}^{commit}" 2>/dev/null || true)
  if [ -z "$bsha" ]; then echo "後端沒有 ${release}：這次只上前端"; return 0; fi
  start=$(date +%s)
  while :; do
    st=$(remote release_status "$SITE_DIR" "$release" backend)
    state=$(echo "$st" | sed -n 's/^state=//p'); age=$(echo "$st" | sed -n 's/^age=//p')
    detail=$(echo "$st" | sed -n 's/^detail=//p'); url=$(echo "$st" | sed -n 's/^pipeline=//p')
    [ "$state" != failed ] || die "後端 ${release} 失敗了：${detail}。那一條：${url}"
    online=$(remote online_version backend)                       # 主機上部署紀錄裡的後端版本
    if [ "$online" = "$bsha" ] || git -C backend merge-base --is-ancestor "$bsha" "$online" 2>/dev/null; then
      echo "後端已經是 ${online}，換前端"; return 0
    fi
    waited=$(( $(date +%s) - start ))
    case "$state" in
      deployed) die "後端 ${release} 上過了，線上卻是 ${online}：之後被回滾了？" ;;
      running)  [ "$age" -lt "$SILENT_MAX" ] || die "後端的進度 $((age / 60)) 分鐘沒更新（最後：${detail}）：被取消或卡住了？${url}" ;;
      *)        [ "$waited" -lt "$SILENT_MAX" ] || die "後端 $((SILENT_MAX / 60)) 分鐘都沒走到部署：還在測試、在排隊，或被取消" ;;
    esac
    [ "$waited" -lt "$TOTAL_MAX" ] || die "等了 $((TOTAL_MAX / 60)) 分鐘，後端還沒上到 ${release}（最後：${detail:-沒有進度}）"
    if [ "$detail" != "$last" ]; then echo "等後端 ${release}：${detail:-還在後端自己的 repo 跑檢查}"; last=$detail; fi
    sleep "$STEP"
  done
}

數字怎麼選：

  • 總上限要比另一邊「最慢的正常情況」長：閘門最多 60 分鐘，加上測試、配對測試、migration 演練 → 150 分鐘。原本只等 30 分鐘，比另一邊的閘門還短 —— 「只上了一半」就是從這裡來的
  • 多久沒動靜算卡住，要比另一邊兩次寫入之間最長的空檔長：閘門裡每分鐘寫一次（不然「閘門在等」跟「卡住了」看起來一樣），最長的空檔是另一邊還在跑測試、配對測試的時候 → 45 分鐘
  • 等的那支 job 的 timeout 要比總上限長（第 1 節的 3 小時）

被等的那一邊上完也看一眼：同號的另一邊已經是 failed 的話，在 log 印一行「正式環境現在是新後端＋線上原本的前端」。 這個組合能用，靠的是後端相容舊前端一版。

5. 測試：主機換成暫存目錄，等待縮成幾秒​

這段邏輯只有真的上正式才會走到，錯了的代價是「該停的沒停」或「不該停的停了」。寫成腳本測，放在 deploy repo 的 check job（約 20 秒）：

  • 主機換成本機的暫存目錄：把「ssh 到主機跑那支腳本」的函式換成「在本機跑同一支腳本」，部署目錄指到 mktemp -d
  • 另一邊的 repo 換成本機建的假 repo：三個空 commit old ← tagged ← newer，在 tagged 打同號的 tag；線上寫成 newer 就是「比同號的更新」
  • 等待的秒數用環境變數縮短：每 1 秒看一次、4 秒沒動靜算卡住、總上限 8 秒
  • 「幾秒後上線」「一直有進度」用背景程序模擬（( sleep 2; 寫入線上版本 ) &）；「很久沒更新」直接改檔裡的 at=
  • 每一種情況各一條，名稱寫成實際會發生的事（「後端在自己 repo 的檢查就紅了：立刻停，講出是哪一條」）； 斷言結束碼＋輸出裡的關鍵字 —— 只看有沒有停，分不出停在哪一條規則
  • macOS 內建的 bash 3.2 與 CI 的 alpine 都要跑過（本機的 bash 跟 CI 的不一樣）

寫完把守衛一個一個拿掉：「failed 就停」「沒動靜就停」「deployed 不被 failed 蓋掉」各拿掉一次，對應的那一條要紅 —— 不會紅的測試等於沒有。

bash 的變數是動態作用域：測試的變數不要跟被測的函式撞名

測試裡放了一個全域變數 site=<暫存目錄> 給替身函式用；被測的函式自己有 local site=$1（值是站名）。替身是在被測函式裡面被呼叫的， 它讀到的 $site 是呼叫者的那個 local —— 於是去讀「站名/部署紀錄」，錯誤是 sed: production/DEPLOYED_COMMIT: No such file or directory，看起來像腳本的路徑寫錯了。 bash 的 local 對它呼叫的函式也看得到（動態作用域，不是多數語言那種詞法作用域）。給替身用的變數取一個被測程式不會用的名字（例如 host_dir）。

6. 還沒擋的、還沒真的走過的​

  • 另一邊的 tag 晚超過 2 分鐘才推：等的那一邊會當成「這次只上這一邊」先上（新前端＋舊後端，不保證相容）。 分不出「本來就只上一邊」和「另一邊晚一點才推」，所以照舊：兩邊都要上時同時推（用 tag 上正式 §6 的警告是同一件事）
  • 寫這篇時：進度檔與等待的判斷有上面的測試，deploy repo 那一側已經上線； 「程式 repo 的檢查沒過 → 觸發 deploy repo 記下」還沒在一次真的失敗上走過，是照官方文件的行為寫的。第一次遇到時確認三件事： deploy repo 出現了 release-failed 那一條、主機上有那個檔、等的那一邊立刻停
  • 想先演練：在測試環境用測試用的號碼（release-test-…），讓後端那個 commit 的測試故意紅一次，再兩邊一起推

7. 讓這種失敗早一點發生：漏洞檢查每天跑一次​

主分支不重跑測試的話，漏洞檢查只在 MR 那天和打 tag 那一刻跑 —— 中間新公布的漏洞，要到上正式那一刻才擋下來，那時另一邊已經出發了。 每天在主分支上排程跑一次，前一天就會知道：見 pipeline-patterns → 每天在主分支上排程跑一次。
