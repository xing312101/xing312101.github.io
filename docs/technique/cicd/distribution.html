發佈給使用者安裝的程式

通用核心講的是部署到自己的主機；這一系列講另一種：做好的程式（例如一個命令列工具）發給別人下載、裝在他們的電腦上。 用的是 GitHub Actions 和 GitHub Releases，簽章用 minisign，另外提供 Homebrew。

部署到自己的主機出錯，自己修好就好；發出去的檔案會在使用者的電腦上執行，所以要多回答兩個問題：

  1. 使用者怎麼知道下載到的，是你發佈的那一份？（SHA-256 只證明下載沒壞；檔案和 SHA-256 可以一起被換掉）
  2. 發佈流程本身被動手腳時會怎樣？（CI 上的 token、第三方 action、artifact、releases 頁面，哪一個被換掉都要擋得下來）

範例裡的工具叫 mytool，帳號寫 <帳號>。

1. 三個 repo​

repo公開放什麼誰寫
<帳號>/mytool私有（公開也一樣）原始碼、測試、發佈的 workflow你
<帳號>/mytool-releases公開只放給使用者的文件（README、安裝說明、使用條款、更新說明）和 GitHub Releases 的下載檔原始碼 repo 的發佈 workflow（只開這一個 repo 的寫入權限）
<帳號>/homebrew-mytool公開只有 Formula/mytool.rbtap repo 自己的 workflow（用它自己的 GITHUB_TOKEN）
  • 下載檔放在 GitHub Releases，不 commit 進 git：不然每一版都永遠留在歷史裡。
  • formula 不從原始碼 repo 推：那樣原始碼 repo 要再拿一個 repo 的寫入權限，formula 也會有兩份（模板和實體），修法容易只進一邊。 改成 tap 自己從公開的 release 讀版本、驗簽章、改自己的檔（Homebrew tap）。
  • Homebrew 的 tap repo 要叫 homebrew-<名字>，使用者打 brew tap <帳號>/<名字>。兩個對外的 repo 都要公開，私有的 tap 使用者得自己設 token。

2. 整條流程​

篇內容
CI：打包、照使用者的步驟裝一次、建草稿tag 的檢查、每個平台的檔案一致、SHA-256 不跟檔案放一起、建草稿的工作不跑任何第三方程式、重跑時不覆蓋已發佈的檔、已經發佈的版本不能改寫、釘住 action
在自己的電腦上簽章為什麼不在 CI 簽、minisign、簽章腳本的每一步、附註綁住版本和檔名、使用者怎麼驗、金鑰遺失或外洩怎麼換
Homebrew tapformula 的寫法、tap 自己的 workflow 驗過簽章才更新、使用者端要 brew trust、怎麼測這些腳本

3. 鐵則​

  1. 打包在 CI，不在自己的電腦上：每一版都從 tag 的原始碼、乾淨的環境打包。
  2. 簽章在自己的電腦上，私鑰從來不放上 GitHub：CI 只建草稿（使用者看不到），簽之前有人看一眼（原因）。
  3. SHA-256 只證明下載沒壞，簽章才證明是你。使用者文件要教驗簽章，而且要使用者自己留一份公鑰。
  4. 已經發佈的版本不能改寫：tag 不移動，tag 指到的 commit 不 amend、不 rebase、不 force push；要修就發新版（CI 檢查）。
  5. 第三方 action 釘在 commit SHA，註解寫版本，定期核對兩者對得上。
  6. 給 CI 的 token 只開一個 repo 的一種權限（releases repo 的 Contents 寫入）。
  7. 文件和程式永遠是同一個版本：使用者文件寫在原始碼 repo，發佈時從 tag 的原始碼同步到 releases repo。
  8. 不想讓帳號、repo 名稱出現在原始碼裡（例如之後可能公開）：放在 repository variable，文件裡用佔位字串，發佈時由 CI 填。
