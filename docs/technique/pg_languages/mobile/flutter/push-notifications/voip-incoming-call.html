VoIP 來電（喚醒 + 原生來電 UI + 接聽 / 拒接 / 導頁）

讓 App 在來電時被喚醒、跳出原生來電畫面，並處理接聽 / 拒接 / 導頁。這層與通話協定無關——它只負責「叫醒 + 顯示 + 把使用者的接聽 / 掛斷轉給通話引擎」。通話本體（SIP）是可抽換的實作。

共用前置（Firebase、APNs .p8、token 表、背景分派器）見 推播基礎設定。

套件：

dependencies:
  flutter_callkit_incoming: ^x.y.z   # CallKit / Android 來電 UI + iOS VoIP token
  permission_handler: ^x.y.z         # 麥克風等執行期權限

為什麼 iOS 要用 PushKit 而不是 FCM？​

  • VoIP push 能在 App 被殺掉時喚醒它、priority 最高、不需使用者點通知。
  • iOS 13 起，VoIP push 收到後必須立刻 report 給 CallKit，否則 App 被殺且未來收不到 VoIP push。
  • FCM 不能送 VoIP 類型推播 → iOS 來電推播要由你的後端 / Push Gateway 直接打 APNs（見 後端觸發）。

通話引擎接口（CallEngine）​

VoIP 層只透過一個協定無關的接口跟「通話本體」打交道。SIP 只是它的一種實作（見 SIP 通話引擎）：

import 'package:flutter/foundation.dart';   // ValueListenable

enum CallStatus { connecting, ringing, active, ended, failed }

abstract class CallEngine {
  Future<void> connectAndAnswer(String callId); // 被殺/背景：從零連線並接聽
  Future<void> answer();                          // 前景：直接接聽
  Future<void> hangup();                          // 掛斷活躍通話
  Future<void> setMuted(bool muted);              // 靜音 / 取消靜音
  Future<void> setSpeaker(bool on);               // 擴音 開 / 關
  ValueListenable<CallStatus> get status;         // 目前狀態 + 變更通知（CallPage 監聽）
}
接口三條規範（不論用哪種引擎都成立）
  • 拒接在 App 被殺時沒有已連上的 session，不要呼叫 hangup()；改用輕量 REST 通知後端（見 被殺 / 背景導頁）。
  • 音訊只在 CallKit didActivate 由系統啟用後交給引擎，不要自己 setActive(true)，否則接通沒聲音。
  • 對應：push payload 帶 callId，要與引擎的通話識別一致，App 才知道接的是哪一通。

iOS VoIP（PushKit + CallKit）​

Apple 端設定​

  1. Xcode → Signing & Capabilities → Background Modes → 勾 Voice over IP。確認 Push Notifications capability 也在（見前置）。
  2. ios/Runner/Info.plist — 麥克風用途說明（通話錄音，沒寫會被審核擋）+ 背景模式加 voip：
<key>NSMicrophoneUsageDescription</key>
<string>通話時需要使用麥克風</string>

<key>UIBackgroundModes</key>
<array>
    <string>remote-notification</string>
    <string>voip</string>
</array>
  1. VoIP push 的 topic 是 <bundleId>.voip（例：com.example.myapp.voip），apns-push-type: voip，沿用前置那把 .p8。

PushKit token​

強烈建議用 flutter_callkit_incoming（見 Flutter 整合），它在 iOS 會自動註冊 PKPushRegistry、自動 report CallKit。若要自己寫原生：

import PushKit
import CallKit

extension AppDelegate: PKPushRegistryDelegate {
  func registerVoIP() {
    let registry = PKPushRegistry(queue: .main)
    registry.delegate = self
    registry.desiredPushTypes = [.voIP]
  }
  // 取得 VoIP token → 丟回 Flutter → 上傳後端（與 FCM token「分開」存）
  func pushRegistry(_ r: PKPushRegistry, didUpdate c: PKPushCredentials, for type: PKPushType) {
    let voipToken = c.token.map { String(format: "%02x", $0) }.joined()
    // 經 MethodChannel 傳給 Dart，再 POST 給後端
  }
  // 收到來電 push → 「必須」立刻 report 給 CallKit（同步，否則被系統懲罰）
  func pushRegistry(_ r: PKPushRegistry, didReceiveIncomingPushWith payload: PKPushPayload,
                    for type: PKPushType, completion: @escaping () -> Void) {
    let info = payload.dictionaryPayload
    reportIncomingCall(uuid: UUID(),
                       handle: info["caller"] as? String ?? "來電",
                       completion: completion)
  }
}

CallKit 來電畫面 + 音訊路由（無聲的關鍵）​

import CallKit
import AVFoundation

let provider = CXProvider(configuration: {
  let c = CXProviderConfiguration()
  c.supportsVideo = false
  c.supportedHandleTypes = [.generic]
  return c
}())

func reportIncomingCall(uuid: UUID, handle: String, completion: @escaping () -> Void) {
  let update = CXCallUpdate()
  update.remoteHandle = CXHandle(type: .generic, value: handle)
  provider.reportNewIncomingCall(with: uuid, update: update) { _ in completion() }
}

extension AppDelegate: CXProviderDelegate {
  func provider(_ p: CXProvider, perform action: CXAnswerCallAction) {
    // 通知通話引擎接受來電（answer），完成後：
    action.fulfill()
  }
  func provider(_ p: CXProvider, perform action: CXEndCallAction) {
    // 通知通話引擎掛斷（hangup），完成後：
    action.fulfill()
  }

  // ★ 關鍵：音訊路由「必須」在這裡由 CallKit 啟用，
  //   你「不要」自己對 AVAudioSession setActive(true)，
  //   否則媒體引擎拿不到正確的音訊 session → 接通卻沒聲音。
  func provider(_ p: CXProvider, didActivate audioSession: AVAudioSession) {
    // 把 audioSession 交給媒體引擎（用套件時 flutter_webrtc / sip_ua 內部會處理）
  }
  func provider(_ p: CXProvider, didDeactivate audioSession: AVAudioSession) {}
  func providerDidReset(_ p: CXProvider) {}
}
warning

上面這些 flutter_callkit_incoming 都幫你做好了，強烈建議用套件，自己寫原生只在套件不夠用時才需要。但「不要自己 activate 音訊 session」這條規則，用套件時一樣成立。

Android 喚醒（FCM data → 全螢幕來電）​

Android 沒有 PushKit，流程是：FCM 高優先級 data message → 喚醒 App → 全螢幕來電 UI。FCM data 由前置的背景分派器接到 type == 'incoming_call' 後導來這裡顯示。

被殺（killed）狀態的可靠度

從 Dart 背景 isolate 冷啟顯示來電，在「被殺」狀態下可能有延遲或不穩（isolate 冷啟需時、各廠商省電會殺）。要最穩，讓 flutter_callkit_incoming 的原生服務（或自寫原生 FirebaseMessagingService）直接接 FCM data 並顯示來電，而非只靠 Dart onBackgroundMessage。

Android 沒有「系統提供的來電畫面」，別期待它像 CallKit

這是兩個平台最本質的差異，也最容易誤判。

套件會把通話註冊進 Android 的 Telecom 框架（TelecomManager.addNewIncomingCall，需要 MANAGE_OWN_CALLS），系統 log 也看得到 ConnectionServiceWrapper 在管你的通話 —— 但那是 self-managed ConnectionService，Telecom 只負責音訊焦點、與電信通話的互通、以及在該顯示 UI 時呼叫 onShowIncomingUI 通知你。

Android 官方對 self-managed 的定位是「App 能夠、而且必須自己提供通話 UI」——包含通話中的介面與來電通知介面；Telecom 在自管模式下不會替你播鈴聲、也不會替你貼通知。

也就是說畫面一律要 App 自己畫（套件的全螢幕 Activity / 自訂版面通知就是在做這件事）。iOS 的 CallKit 則是系統把整個來電畫面畫好，App 連背景色都改不了。

實務影響：

  • 想「讓 Android 也用系統原生來電畫面」是做不到的。把套件的自繪關掉不會讓系統接手，只會變成某些情境下完全沒有來電 UI。
  • 兩個平台要「統一」，只能讓 Android 的自繪去模仿 CallKit（深色底、圓形接聽/拒接鍵），或接受兩邊本來就長得不一樣。
  • Telecom 註冊本身要保留 —— 它負責音訊焦點與互通，關掉會影響通話音訊。

Android 14（API 34）全螢幕來電的額外授權​

從 Android 14 起，USE_FULL_SCREEN_INTENT 不再自動授予一般 App。要在執行期檢查，沒有就導去設定頁，否則鎖屏不跳全螢幕來電：

val nm = getSystemService(Context.NOTIFICATION_SERVICE) as NotificationManager
if (Build.VERSION.SDK_INT >= 34 && !nm.canUseFullScreenIntent()) {
    startActivity(Intent(
        Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT,
        Uri.parse("package:$packageName")
    ))
}
廠商省電限制

小米 / OPPO / 三星… 有省電 / 自啟限制，背景被殺時要引導使用者開「自啟動 / 電池不優化」。flutter_callkit_incoming 會建前景服務 + 全螢幕通知，但權限與廠商引導仍要你做。全螢幕來電通知 category 要設 CATEGORY_CALL（套件已處理）。

裝置休眠（Doze）/ 鎖屏喚醒​

Doze 下怎麼還叫得醒？ 裝置深度休眠（Doze）時一般 FCM 會被延後，只有高優先級 data 能即時穿透 Doze，並給 App 一小段 wakelock 處理來電——這就是後端送 priority: HIGH 的原因。兩個現實限制要知道：

  • App 太久沒用、落入 restricted / rare standby bucket，或被 force-stop → 高優先也可能被限流甚至不送達。
  • 各廠商（小米 / OPPO / 三星…）自家省電更激進（見上方廠商省電提醒）。

① 請求電池最佳化白名單（權限已在上方清單加 REQUEST_IGNORE_BATTERY_OPTIMIZATIONS；用 permission_handler 觸發系統對話框）：

import 'package:permission_handler/permission_handler.dart';

Future<void> ensureBatteryExemption() async {
  if (await Permission.ignoreBatteryOptimizations.isGranted) return;
  await Permission.ignoreBatteryOptimizations.request();   // 跳系統白名單對話框
}
caution

REQUEST_IGNORE_BATTERY_OPTIMIZATIONS 是 Google Play 受限權限，通話 / VoIP 屬被允許用途，上架時要在 Play Console 說明。

② 鎖屏點亮螢幕並蓋過鎖屏（導向你自己的 Flutter 通話頁時需要；只用套件的全螢幕通知可不寫）。android/app/src/main/kotlin/.../MainActivity.kt：

import android.app.KeyguardManager
import android.content.Context
import android.os.Build
import android.os.Bundle

import io.flutter.embedding.android.FlutterActivity

            setShowWhenLocked(true)

        } else {

Flutter 整合（flutter_callkit_incoming）​

一個套件同時搞定：iOS PushKit token + CallKit、Android 全螢幕來電 UI，並用統一事件流給 Dart。

import 'package:flutter_callkit_incoming/flutter_callkit_incoming.dart';
import 'package:flutter_callkit_incoming/entities/entities.dart';

Future<void> showIncoming(String callId, String caller) async {
  await FlutterCallkitIncoming.showCallkitIncoming(CallKitParams(
    id: callId,                       // 與通話引擎的 call id 對應
    nameCaller: caller,
    handle: caller,
    type: 0,                          // 0 = audio
    ios: const IOSParams(handleType: 'generic', supportsVideo: false),
    android: const AndroidParams(
      isCustomNotification: true, isShowFullLockedScreen: true),
  ));
}

// 你的引擎（SIP 實作見 sip-call-engine.md）
final CallEngine callEngine = /* callEngineProvider 提供 */;

// 監聽接聽/掛斷 → 轉給引擎（App「存活時」的 happy path；被殺/背景見下方導頁章）
FlutterCallkitIncoming.onEvent.listen((event) async {
  switch (event!.event) {
    case Event.actionCallAccept:  await callEngine.answer();   break;
    case Event.actionCallDecline:
    case Event.actionCallEnded:   await callEngine.hangup();   break;
    default: break;
  }
});

// iOS：取得 VoIP push token（回傳後端，與 FCM token 分開）
final voipToken = await FlutterCallkitIncoming.getDevicePushTokenVoIP();

兩平台喚醒路徑不同（重要觀念）：

  • iOS：VoIP push 由套件的原生 PushKit 直接收（即使 App 被殺），套件自動先 report CallKit（滿足 iOS 13+ 規定）。Dart 端只在 actionCallAccept 時接引擎。
  • Android：FCM data message 由前置的 Dart 背景分派器收，在那裡呼叫 showIncoming(...)：
// 前置的背景分派器中，type == 'incoming_call' 分支：
await showIncoming(m.data['callId']!, m.data['caller'] ?? '來電');

早 / 延遲 / 常駐連線（接通速度的關鍵）​

「什麼時候連通話引擎」直接決定接通速度與可靠度。下面是引擎無關的取捨（SIP 的 REGISTER 細節見 SIP 註冊策略）：

策略何時連引擎優點缺點適用
延遲（接聽後）按接聽才 connectAndAnswer()最省電接通慢（push→連線→接受需 1–3s）；易「按了接聽卻沒通話可接」競態對接通延遲不敏感
早連線（推薦）收到 push、顯示來電的同時就背景連線接通快；按接聽時多半已就緒每通都要連線；要處理 push→連線生命週期大多數行動來電場景
常駐App 啟動就長連線前景接通最快、甚至不需 pushiOS 背景 / 被殺後長連線必斷、耗電不會被殺的固定裝置（壁掛機 / 桌面）
行動端為何不選常駐

iOS 被系統殺掉後長連線無法存活，所以行動端實務是「push 喚醒 + 早連線」。常駐只適合常開不被殺的裝置。

端到端流程（通用 · 早連線版）​

PBX 要「等」：push 發出到 App 連線上線需 1–3 秒，要讓來電維持 ringing（或重送），等 App 上線才送達，否則使用者按了接聽卻沒通話可接。

App 被殺 / 背景：拒接與接聽導頁​

來電顯示做完了，真正難的是使用者按下去之後。導頁以 go_router + Riverpod 示範。

三種 App 狀態 × 接 / 拒 行為​

App 狀態來電顯示由誰處理按「拒接」按「接聽」
前景Dart 在跑，onEvent 直接收callEngine.hangup()直接 callEngine.answer()
背景（未被殺）iOS：原生 PushKit→CallKit；Android：Dart 背景 isolate事件進 onEvent，App 不前景；通知後端App 轉前景 → 接引擎 + 導頁
被殺（killed）iOS：系統喚醒背景行程 + 原生 report CallKit；Android：FCM data → 背景 isolate 顯示不前景；REST 通知後端（沒有 session，別用 hangup()）冷啟到前景；activeCalls() 補抓 → 從零連引擎 → pending-route 導頁
iOS「不開啟 App」的精確說法

VoIP push 一定會把 App 行程在背景喚醒（PushKit 機制），但不會把畫面帶到前景。拒接時使用者看不到 App 開起來；只有「接聽」才會把 App 帶到前景。

拒接：不開啟 App​

被殺狀態下沒有已連上的 session，所以 hangup() 在這裡無效。改用輕量 REST 通知後端「這通被拒」：

// 純 HTTP，不依賴引擎連線；可在背景 isolate / onEvent 內呼叫
Future<void> declineCall(String callId) async {
  await Dio().post('https://api.example.com/calls/$callId/decline');
}

// onEvent 內：
case Event.actionCallDecline:
case Event.actionCallEnded:
  final callId = _callIdOf(e);
  if (callId != null) await declineCall(callId);   // 不前景、不碰引擎
  break;
終止狀態收不收得到事件，依套件版本

被殺狀態能不能收到拒接事件，依 flutter_callkit_incoming 版本而定（Android 走背景 isolate / 原生 receiver、iOS 走原生 CallKit delegate）。把「通知後端」動作放原生層或背景 isolate 最穩；收不到時，退而求其次讓 PBX ring 逾時當未接。

接聽：冷啟動導到指定頁（go_router + Riverpod）​

被殺時按接聽，OS 會冷啟動 App。難點：accept 事件可能比 listener 還早發生，所以不能在回呼裡直接 push。正解是「狀態先存住，router 看著狀態導頁」。

① Riverpod 存待處理來電，go_router 監聽它

final pendingCallProvider = StateProvider<String?>((ref) => null);  // 待導頁的 callId

class _CallRefresh extends ChangeNotifier {
  _CallRefresh(Ref ref) {
    ref.listen(pendingCallProvider, (_, __) => notifyListeners());
  }
}

final routerProvider = Provider<GoRouter>((ref) {
  return GoRouter(
    refreshListenable: _CallRefresh(ref),
    redirect: (ctx, state) {
      final pending = ref.read(pendingCallProvider);
      if (pending != null && state.matchedLocation != '/call/$pending') {
        return '/call/$pending';                    // 有待處理來電 → 導到通話頁
      }
      return null;
    },
    routes: [
      GoRoute(path: '/', builder: (_, __) => const HomePage()),
      GoRoute(path: '/call/:id',

② main()：盡早註冊事件 + 冷啟補抓 activeCalls()（在前置骨架上疊加，不是另寫一份）

Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  await Firebase.initializeApp(options: DefaultFirebaseOptions.currentPlatform);
  FirebaseMessaging.onBackgroundMessage(firebaseBackgroundHandler);   // 前置骨架

  final container = ProviderContainer();
  final CallEngine engine = container.read(callEngineProvider);       // SIP 實作見 sip-call-engine.md

  String? handledCallId;                            // idempotent guard
  Future<void> acceptCall(String callId) async {
    if (handledCallId == callId) return;            // onEvent 與 activeCalls() 可能都接到
    handledCallId = callId;
    container.read(pendingCallProvider.notifier).state = callId;  // 觸發導頁
    await engine.connectAndAnswer(callId);          // 被殺時「從零」連引擎再接
  }

  FlutterCallkitIncoming.onEvent.listen((e) async {
    if (e == null) return;
    final callId = _callIdOf(e);
    switch (e.event) {
      case Event.actionCallAccept:
        if (callId != null) await acceptCall(callId);
        break;
      case Event.actionCallDecline:
      case Event.actionCallEnded:
        if (callId != null) await declineCall(callId);
        break;
      default: break;
    }
  });

  // 冷啟補抓：accept 可能在 listener 掛上「之前」就發生（等同來電版的 getInitialMessage()）
  final active = await FlutterCallkitIncoming.activeCalls();
  if (active is List && active.isNotEmpty) {
    final callId = active.first['id'] as String?;
    if (callId != null) await acceptCall(callId);   // 與 onEvent 共用 guard
  }

  runApp(UncontrolledProviderScope(container: container, child: const MyApp()));
}

String? _callIdOf(CallEvent e) =>
    (e.body is Map) ? e.body['id'] as String? : null;   // body 結構依套件版本

③ 進通話頁後清掉 pending：避免 router 迴圈導頁。這併進下方通話頁面 CallPage 的 initState（連同訂閱通話狀態一起做）。

三個必備防護
  • activeCalls() 補抓：冷啟時 plugin 可能在 listener 掛上前就處理了 accept，事件收不到，靠它撈回「啟動當下已存在的通話」（角色等同通知的 getInitialMessage()）。
  • 引擎從零連：被殺時沒有既有連線，接聽後 connectAndAnswer()，通話頁先顯示「接通中…」，連上再轉「通話中」。
  • 避免重複：onEvent 與 activeCalls() 可能都接到同一通，用 handledCallId 擋一層。

漏接 / 逾時 / 其他​

  • 只註冊一個 onEvent listener：上面 Flutter 整合 的 onEvent 只是「App 存活時」的 happy-path 示意；正式就用本章 main() 這一個 listener——它同一套事件涵蓋前景 / 背景 / 被殺，差別只在「拒接改用 REST、接聽要先 connectAndAnswer 再導頁」。兩個都註冊會讓同一通被處理兩次。
  • 漏接 / 逾時 / 對方掛斷：Event.actionCallTimeout / actionCallEnded → 寫一筆未接來電（本地通知或回報後端）。
  • Android Activity launchMode：來電頁建議 singleTop（或 singleTask），接聽 deep-link 用 intent extras 帶 callId，避免重複堆疊同一頁。

取消來電（主叫方在接聽前掛斷）​

被叫端還在響鈴、主叫端就掛了——這在對講機 / 客服類 App 是家常便飯，卻是整個 VoIP 流程裡最容易做錯的一段：做錯不會噴錯誤，只會讓鈴聲一路響到逾時，或讓後端的通話紀錄靜默寫錯。

兩個平台的流程差很多，不要想用同一套邏輯處理。

iOS 為什麼不能用 FCM 或一般推播取消​

響鈴當下這三條路全是死的：

管道為什麼不行
FCM 前景 onMessageCallKit 是全螢幕系統 UI，它蓋上來時 App 就不是 active，事件不會觸發
FCM 背景 handler來電本來就是 PushKit 把 App 從背景喚起才顯示的，背景 isolate 不保證跑得到
一般 APNs content-availableApple 規定背景推播必須用低優先權（apns-priority: 5），系統可自行節流、延後；App 被使用者滑掉時更是完全喚不醒

只有 VoIP push 能保證即時送達、而且叫得醒被殺掉的 App。 取消要走的就是跟來電同一條管道，payload 換個 type 而已。

陷阱一：不要用 endAllCalls() 收掉未接聽的來電​

這是最貴的一個坑，因為它不會出錯，只會讓資料錯。

endAllCalls() 底層走的是 CXEndCallAction，而套件對「未接聽的通話收到 CXEndCallAction」一律送出 DECLINE 事件——它無法分辨這是使用者按了拒接，還是你的程式自己收掉的。iOS 與 Android 的實作都是如此。

於是 Dart 端收到 DECLINE、把它翻譯成「使用者拒接」回報後端，「主叫方取消」就被記成「被叫方拒接」，通話紀錄靜默寫錯，要等到有人去對帳才會發現。

// ❌ 會讓後端收到「使用者拒接」
plugin.endAllCalls()

// ✅ 語意正確：這通是遠端結束的，而且不會送出任何 Dart 事件
provider.reportCall(with: uuid, endedAt: Date(), reason: .remoteEnded)
判斷原則

CXEndCallAction 的語意是「使用者掛斷」，reportCall(with:endedAt:) 的語意是「這通已經結束了，通知系統」。程式主動收掉通話一律用後者。

同樣的原則適用於任何「程式自己收掉來電」的場合：殘留來電清理、逾時、被其他裝置接走。分不出來源時就不要回報狀態，讓後端依訊令自行判定，比猜錯好。

陷阱二：收之前一定要守門​

CXCallObserver.calls 是整台裝置的通話清單，不是只有你的 App。沒有守門的話，使用者正在講的那通會被一起掛掉——情境是「通話中另一通被取消」或「後端重送取消」。

for call in callObserver.calls
where !call.hasEnded && !call.hasConnected && !call.isOutgoing {
    // 只收「還在響、沒接通、非外撥」的
    provider.reportCall(with: call.uuid, endedAt: Date(), reason: .remoteEnded)
}

Android 對應的守門是 isAccepted——要注意接聽後通話不會從 active 清單移除，只是把旗標設為 true：

// ❌ 連使用者正在講的那通一起收掉
getDataActiveCalls(this).forEach { sendBroadcast(getIntentEnded(this, it.toBundle())) }

// ✅ 只收還沒接聽的
getDataActiveCalls(this)
    .filterNot { it.isAccepted }
    .forEach { sendBroadcast(getIntentEnded(this, it.toBundle())) }

已接通的通話本來就該由通話協定自己收尾（SIP 的 BYE），不需要靠推播。

陷阱三：佔位來電會被顯示約 2 秒，無法消除​

iOS 13 規定每顆 VoIP push 都必須在 handler 回傳前同步呼叫 reportNewIncomingCall，取消 push 也不例外。Apple 明確允許「報一通其實不存在的來電，再非同步收掉」來滿足這條規則（Twilio 處理 CancelledCallInvite 也是同一招）。

但實測會發現：不管你多快把佔位收掉，CallKit 都會把它顯示滿約 2 秒。 三種收掉的時機都試過：

時機結果
同步、緊接在 report 之後太早，系統還沒註冊完，那筆 end 被丟掉
DispatchQueue.main.async 下一個 tick太晚，handler 一回傳、當下又沒有其他活躍通話時 App 立刻被系統暫停，那段程式碼根本不會執行
reportNewIncomingCall 的 completion 裡正確時機，但畫面照樣呈現約 2 秒

系統 log 顯示得很清楚：結束指令已經送達，之後才開始顯示來電。這是 CallKit 的最短呈現時間，程式端無解。

maximumCallGroups = 1 擋不住，別白費力氣

直覺會想從 CXProviderConfiguration 下手 —— 把 maximumCallGroups 設成 1，宣告「這支 App 同時只支援一組通話」，期待 CallKit 直接拒絕第二通。實測無效：設成 1 之後，通話進行中報進去的佔位來電照樣以插撥樣式呈現約 2 秒。

對照 CallKit 的拒絕原因列舉也說得通 —— callUUIDAlreadyExists / filteredByDoNotDisturb / filteredByBlockList 之外，沒有「超過通話組數上限」這一項。這個參數描述的是分組與會議能力，不是 reportNewIncomingCall 的准入閘門。

同一輪實測中 supportsHolding: false 是有效的（插撥畫面的「Hold & Accept」確實消失），可見參數本身有正確傳達到系統 —— 是 maximumCallGroups 的語意就不是准入控制。

report placeholder          T+0ms
reportNewIncomingCall       T+5ms      ← 送達系統
end placeholder             T+39ms     ← completion 裡收掉
reportCallWithUUID(endedAt) T+39ms     ← 結束指令送達
Call state → Ringing        T+61ms     ← ⚠️ 結束指令「之後」才開始顯示
Call state → Disconnected   T+2184ms   ← 約 2 秒後才消失

實作上寫成一支共用函式，取消來電與「已有通話時收到重複來電」兩處都用它：

/// 報一通佔位來電並立刻收掉，用來滿足 iOS 13 的規則而不干擾使用者。
/// UUID 必須全新——用過的 UUID 會被系統靜默拒絕，等於沒報。
private func reportAndEndPlaceholder(payload: [AnyHashable: Any]) {
    let uuid = UUID()
    let update = CXCallUpdate()
    update.localizedCallerName = payload["caller"] as? String ?? "來電"
    // 在 completion 裡收掉：此時系統已註冊完成，且 App 因為剛報了一通來電必然還活著
    provider.reportNewIncomingCall(with: uuid, update: update) { _ in
        self.provider.reportCall(with: uuid, endedAt: Date(), reason: .remoteEnded)
    }
}
想完全避免那 2 秒？別用取消 push

根本原因是「取消走 PushKit 進來」，才產生報佔位的義務。若在響鈴期間就維持一條訊令連線（例如來電當下就完成 SIP 註冊，或保持自家長連線），主叫方的 CANCEL 可以直接經那條連線進來收掉 CallKit——不經過 PushKit 就沒有這條規則，畫面完全乾淨。

代價是接通速度與耗電的取捨（見早連線），以及要處理註冊失敗與逾時。這也是部分商用通訊 App 看不到這個畫面的原因。

已有通話時，不要再顯示新來電​

後端常會在響鈴期間重送來電 push，有些實作連使用者接聽之後都照送。iOS 端沒有任何內建去重，來一顆就顯示一通，於是通話中跳出第二通來電、兩個通話 UI 疊在一起。

但不能直接 return——那顆 push 一樣要滿足 iOS 13 的規則：

if callObserver.calls.contains(where: { !$0.hasEnded }) {
    // 已有通話在進行 → 不顯示新來電，但仍要報一通佔位再收掉
    reportAndEndPlaceholder(payload: payload)
    completion()
    return
}

Android 的等價守門要分辨三種情況，不能一律略過：

val activeCalls = getDataActiveCalls(this)
when {
    // ① 同一通重送 → 靜靜略過
    activeCalls.any { it.id == callId } -> return
    // ② 真的在通話中 → 不打斷，改留一則未接來電通知
    activeCalls.any { it.isAccepted } -> { showMissedCallNotification(); return }
    // ③ 只有未接聽的殘留 → 照常顯示這通新來電
}

只寫 isNotEmpty() 就 return 的話，只要清單裡有任何清不掉的殘留，之後每一通來電都會被擋掉、畫面不跳出來——實測症狀是「打三次才成功一次」，而且因為有未接通知，使用者只會說「來電沒跳出來，只有通知頁面有」。殘留本身是另一個要修的問題，但守門不該因為有殘留就讓來電功能整個停擺。

通話中的插撥畫面有誤點風險，而且 App 端無解

通話進行中報進去的佔位來電，iOS 會用插撥樣式呈現，按鈕是 End & Accept / Decline / Hold & Accept。supportsHolding: false 可以拿掉第三顆，但 End & Accept 沒有對應旗標——使用者手滑點下去，正在講的通話就被掛斷了。

唯一的根治方法在後端：被叫方已經接聽之後，這通與後續的來電、取消 push 都不要再送。那個階段 App 已經連上通話協定的訊令通道（例如 SIP 已註冊），訊令走那條即可，不需要 push；沒有 push 就沒有報來電的義務，畫面自然不存在。

後端通常分得出來——App 接聽時會回報通話狀態，訊令層也有 200 OK。

順帶一提，iOS 每通來電必須用全新的 UUID，不可以像 Android 那樣用「通話 ID 決定性產生」來去重：CallKit 對用過的 UUID 會靜默拒絕 reportNewIncomingCall，症狀是「同一個來源打第二通完全沒有來電畫面」，push 有到、log 也顯示有呼叫，極難查。Android 反而要用決定性 ID 才能讓重送的來電覆蓋前一個通知。

通話頁面（CallPage）​

通話畫面「瞬間出現」會接到上一個畫面的觸控

接聽的手勢發生在別的畫面上——Android 是套件的來電 Activity、iOS 是 CallKit。那個畫面消失、你的通話頁補上來的位置，往往正是使用者手指剛按下去的地方。而通話頁在「等待接通」狀態下，那個位置通常就是掛斷鍵。

實測命中：使用者按下接聽，一秒後 hangup() 被觸發，剛註冊好的 SIP 帳號被註銷，那一通就此消失。症狀看起來像「接聽沒反應／第一通固定失敗」，完全不會聯想到是誤觸。

用 route 推頁時，轉場動畫與導航延遲天然避開了這件事；一旦改成沒有動畫的呈現方式（例如把通話畫面做成覆蓋層、或 pushReplacement 無動畫），就必須自己補上防護：

// 畫面出現後短時間內吃掉觸控
AbsorbPointer(
  absorbing: _justAppeared,   // 由 Timer 在 ~600ms 後設回 false
  child: callScreen,
)

順帶一提，通話畫面做成覆蓋層（掛在 MaterialApp.builder 之上而非進 navigator）本身是好主意：不會被 Navigator 的 pushAndRemoveUntil 之類洗掉、不需要 pop（也就沒有「pop 掉最後一個 route 造成黑畫面」的問題）、回到前景時只要把旗標設回 true 就能還原。但要記得配上 PopScope(canPop: false)，否則 Android 的返回鍵會 pop 掉底下那頁——使用者看到通話畫面沒動、背後卻被退了一層。

接聽後導到的通話頁。它監聽 CallEngine.status 切「接通中 → 通話中 → 結束」，並提供靜音 / 擴音 / 掛斷與通話秒數。status 用 ValueListenable（不是一次性 Stream），所以晚一點才在 initState 訂閱也能先讀到目前值，不會漏掉早於訂閱發生的事件（被殺冷啟時很關鍵）。callEngineProvider 見 SIP 引擎、pendingCallProvider 見 上方 Part K。

import 'dart:async';
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';

class CallPage extends ConsumerStatefulWidget {
  const CallPage({super.key, required this.callId});
  final String callId;
  @override
  ConsumerState<CallPage> createState() => _CallPageState();
}

class _CallPageState extends ConsumerState<CallPage> {
  late CallStatus _status;
  bool _muted = false, _speaker = false;
  Duration _elapsed = Duration.zero;
  Timer? _timer;

  CallEngine get _engine => ref.read(callEngineProvider);

  @override
  void initState() {
    super.initState();
    // 消費掉 pending，避免 router 迴圈導頁（取代 Part K 的 ③）
    WidgetsBinding.instance.addPostFrameCallback((_) {
      ref.read(pendingCallProvider.notifier).state = null;
    });
    _status = _engine.status.value;          // 先讀目前值（避免錯過早於訂閱的事件）
    _applyStatus(_status);
    _engine.status.addListener(_onStatus);
  }

  void _onStatus() {
    final s = _engine.status.value;
    setState(() => _status = s);
    _applyStatus(s);
  }

  void _applyStatus(CallStatus s) {
    if (s == CallStatus.active && _timer == null) {
      _timer = Timer.periodic(const Duration(seconds: 1),
          (_) => setState(() => _elapsed += const Duration(seconds: 1)));
    } else if (s == CallStatus.ended || s == CallStatus.failed) {
      _timer?.cancel();
      _timer = null;
      Future.delayed(const Duration(milliseconds: 800), () {
        if (mounted) Navigator.of(context).maybePop();   // 顯示「已結束」一下再退出
      });
    }
  }

  @override
  void dispose() {
    _engine.status.removeListener(_onStatus);
    _timer?.cancel();
    super.dispose();
  }

  String get _statusText => switch (_status) {
        CallStatus.connecting => '接通中…',
        CallStatus.ringing    => '響鈴中…',
        CallStatus.active     => _fmt(_elapsed),
        CallStatus.ended      => '已結束',
        CallStatus.failed     => '連線失敗',
      };

  String _fmt(Duration d) =>
      '${d.inMinutes.toString().padLeft(2, '0')}:'
      '${(d.inSeconds % 60).toString().padLeft(2, '0')}';

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      backgroundColor: Colors.black87,
      body: SafeArea(
        child: Column(
          children: [
            const Spacer(),
            const CircleAvatar(radius: 48, child: Icon(Icons.person, size: 48)),
            const SizedBox(height: 16),
            Text(widget.callId,
                style: const TextStyle(color: Colors.white, fontSize: 22)),
            const SizedBox(height: 8),
            Text(_statusText, style: const TextStyle(color: Colors.white70)),
            const Spacer(),
            Row(
              mainAxisAlignment: MainAxisAlignment.spaceEvenly,
              children: [
                _CircleToggle(
                  icon: _muted ? Icons.mic_off : Icons.mic,
                  label: '靜音',
                  on: _muted,
                  onTap: () async {
                    await _engine.setMuted(!_muted);
                    setState(() => _muted = !_muted);
                  },
                ),
                _CircleToggle(
                  icon: Icons.volume_up,
                  label: '擴音',
                  on: _speaker,
                  onTap: () async {
                    await _engine.setSpeaker(!_speaker);
                    setState(() => _speaker = !_speaker);
                  },
                ),
              ],
            ),
            const SizedBox(height: 32),
            FloatingActionButton(
              backgroundColor: Colors.red,
              onPressed: () => _engine.hangup(),   // 狀態轉 ended 後會自動退頁
              child: const Icon(Icons.call_end),
            ),
            const SizedBox(height: 40),
          ],
        ),
      ),
    );
  }
}

class _CircleToggle extends StatelessWidget {
  const _CircleToggle({
    required this.icon, required this.label, required this.on, required this.onTap,
  });
  final IconData icon;
  final String label;
  final bool on;
  final VoidCallback onTap;

  @override
  Widget build(BuildContext context) {
    return Column(
      mainAxisSize: MainAxisSize.min,
      children: [
        IconButton.filled(isSelected: on, onPressed: onTap, icon: Icon(icon)),
        const SizedBox(height: 4),
        Text(label, style: const TextStyle(color: Colors.white70, fontSize: 12)),
      ],
    );
  }
}

路由（/call/:id）已在 Part K 的 go_router 定義。callId 這裡直接當顯示名稱，實務上可改成查通訊錄 / 後端的來電者名稱。

後端 / Push Gateway（觸發來電推播）​

PBX 偵測被叫裝置在背景 / 離線，就由這層發推播喚醒 App。iOS 直連 APNs(VoIP)、Android 走 FCM v1 data。裝置 token 表見前置。

iOS：直連 APNs 發 VoIP push（Node.js）​

用 .p8 產生 ES256 JWT，走 HTTP/2 打 APNs：

const http2 = require('http2');
const jwt = require('jsonwebtoken');
const fs = require('fs');

const TEAM_ID = 'YOUR_TEAM_ID';
const KEY_ID  = 'YOUR_KEY_ID';
const BUNDLE  = 'com.example.myapp';
const p8 = fs.readFileSync('./AuthKey_YOURKEY.p8');

// APNs 對「太頻繁換 provider token」會回 429 TooManyProviderTokenUpdates，
// 所以 JWT 要快取重用、不要每通都重簽。
let _jwt = null, _jwtAt = 0;

function apnsJwt() {                       // JWT 最長 1 小時，建議快取約 50 分鐘再換
  const now = Date.now();
  if (_jwt && now - _jwtAt < 50 * 60 * 1000) return _jwt;   // 重用約 50 分鐘，不要每通重簽
  _jwt = jwt.sign({}, p8, { algorithm: 'ES256', issuer: TEAM_ID, keyid: KEY_ID });
  _jwtAt = now;
  return _jwt;
}

function sendVoip(voipToken, payload, { production = false } = {}) {
  const host = production
    ? 'https://api.push.apple.com'           // 正式
    : 'https://api.sandbox.push.apple.com';  // 開發
  const client = http2.connect(host);        // 範例每通新建連線；正式應重用持久連線
  const req = client.request({
    ':method': 'POST',
    ':path': `/3/device/${voipToken}`,
    'apns-topic': `${BUNDLE}.voip`,          // ← 注意 .voip 後綴
    'apns-push-type': 'voip',
    'apns-priority': '10',
    'authorization': `bearer ${apnsJwt()}`,
  });
  let data = '';
  req.setEncoding('utf8');
  req.on('data', (c) => (data += c));
  req.on('end', () => { console.log('APNs', data); client.close(); });
  req.end(JSON.stringify(payload));
}

// 來電時：
sendVoip('<device-voip-token>', {
  callId: 'abc-123', caller: '管理室', handle: 'sip:1001@sip.example.com',
});
環境一致性（常見翻車）

開發 / 測試 build 的 aps-environment 是 development → 打 api.sandbox.push.apple.com；上架 / TestFlight 是 production → 打 api.push.apple.com。token 來源、entitlement、端點三者必須一致，否則回 BadDeviceToken。

上面 sendVoip() 的 production 預設是 false（sandbox），正式環境記得傳 true。

⚠️ 如果 build 是 CI 產的，aps-environment 有可能跟你以為的不一樣——Manual 簽章下 Xcode 不會 幫你改寫這個值。那是一種「後端顯示送出成功、裝置永遠收不到」的無聲失敗，排查方式見 推播基礎設定 → 疑難排解。

Android：FCM HTTP v1 發 data-only（Node.js）​

Legacy server key 已停用，必須用 HTTP v1 + OAuth：

const { GoogleAuth } = require('google-auth-library');
const PROJECT_ID = 'your-firebase-project-id';

const auth = new GoogleAuth({
  keyFile: './service-account.json',  // ← Firebase Console 下載的服務帳號金鑰
  scopes: ['https://www.googleapis.com/auth/firebase.messaging'],
});

async function sendFcmData(fcmToken, data) {
  const client = await auth.getClient();
  const res = await client.request({
    url: `https://fcm.googleapis.com/v1/projects/${PROJECT_ID}/messages:send`,
    method: 'POST',
    data: {
      message: {
        token: fcmToken,
        // data-only：不要放 notification 欄位；value「必須都是字串」
        data: Object.fromEntries(
          Object.entries(data).map(([k, v]) => [k, String(v)])),
        android: { priority: 'HIGH' },   // 高優先級才能在背景/被殺喚醒
      },
    },
  });
  console.log('FCM', res.status);
}

// 來電時：
sendFcmData('<device-fcm-token>', {
  type: 'incoming_call', callId: 'abc-123', caller: '管理室',
  handle: 'sip:1001@sip.example.com',
});

PBX 偵測離線 → 觸發​

  • PBX 撥號規則發現被叫不在線（無註冊）時，呼叫上面的 Gateway：iOS 查 voip_token 打 APNs、Android 查 fcm_token 送 FCM。
  • 維持 ringing：發 push 後讓這通維持 ringing 數秒，等 App 上線再送通話請求（搭配早連線，窗口很短）。

測試​

  1. iOS VoIP（真機，模擬器不支援）。取 VoIP token（getDevicePushTokenVoIP()），直接打 APNs 驗證：
# 開發 build 用 sandbox；正式 build 改 api.push.apple.com
curl -v -H "apns-push-type: voip" \
     -H "apns-topic: com.example.myapp.voip" \
     -H "authorization: bearer <JWT>" \
     --data '{"callId":"abc123","caller":"管理室"}' \
     --http2 https://api.sandbox.push.apple.com/3/device/<voip-token>

App 被殺時也應跳 CallKit。回 BadDeviceToken → 多半環境不符。

  1. Android VoIP：後端送 priority:HIGH 的 data-only FCM → 確認鎖屏 / 背景 / 殺掉都跳全螢幕來電。測 Android 14 全螢幕權限與各廠牌省電限制。

  2. 取消來電：三種 App 狀態各測一次（前景 / 背景 / 從多工滑掉），確認鈴聲立刻停、且後端收到的狀態不是「使用者拒接」。

三個會浪費你半天的測試陷阱
  • 每次重裝 App，VoIP token 都會換新，後端手上那顆立刻失效，APNs 回 410 Unregistered，裝置端毫無動靜——看起來跟「後端沒送」一模一樣。所以每輪測試前都要先開 App 走到會上傳 token 的流程（通常是登入後的首頁）。
  • iOS 14+ 的 Flutter debug build 不能從主畫面獨立啟動（Cannot create a FlutterEngine instance in debug mode without Flutter tooling or Xcode），一離開 flutter run 就起不來。要測背景 / 被殺情境必須用 profile 或 release build。
  • iOS 17 的 apsd 系統 log 把 topic 遮成 <private>，無法從系統 log 判斷 push 落在哪個 topic。要在自己的 PushKit handler 第一行加 NSLog 印出 payload 的 type，才分得出「push 根本沒到」與「push 到了但處理有問題」——這兩者的症狀完全相同。

設定檢查清單​

iOS VoIP

  • Background Modes → Voice over IP；Info.plist UIBackgroundModes 含 voip
  • NSMicrophoneUsageDescription 已寫
  • PushKit 註冊、取得 VoIP token 上傳後端（與 FCM token 分開）
  • 收到 VoIP push 同步 report CallKit（用套件即自動）
  • 音訊只在 didActivate 啟用，不自己 setActive
  • 取消來電：報佔位 + reportCall(endedAt:)，不用 endAllCalls()
  • 收掉來電前過濾 hasConnected / isOutgoing
  • 每通來電使用全新 UUID（用過的會被 CallKit 靜默拒絕）

Android VoIP

  • USE_FULL_SCREEN_INTENT / FOREGROUND_SERVICE(_PHONE_CALL) / WAKE_LOCK / RECORD_AUDIO
  • Android 14：runtime 檢查 canUseFullScreenIntent()，否則導設定頁
  • 後端送 data-only、priority HIGH
  • 全螢幕來電 UI（套件）+ 廠商省電引導

後端 / Push Gateway

  • PBX 偵測被叫離線 → 觸發 push
  • iOS 直連 APNs（VoIP topic、.p8 JWT、環境正確）
  • Android 走 FCM HTTP v1 + OAuth（非 legacy server key）
  • 主叫方取消時也送一顆 push：iOS 必須走 VoIP（同 topic、同 token），Android 走同一條 FCM
  • 使用者接聽後停止重送來電 push，否則通話中會跳出第二通來電

常見坑​

  1. iOS 用 FCM 想做 VoIP → 不行，必須 PushKit + 直連 APNs。
  2. 收到 VoIP push 沒立刻 report CallKit → App 被殺、之後收不到 VoIP push（iOS 13+ 懲罰）。用套件可避免。
  3. iOS 真機才有推播 → 模擬器拿不到 APNs / VoIP token。
  4. Android 送了 notification 欄位 → 背景由系統托盤接管，data 邏輯不執行、來電 UI 不跳。要送 data-only。
  5. 接通沒聲音（iOS 音訊 session） → 自己對 AVAudioSession setActive(true) 搶在 CallKit 前；改成只在 didActivate 啟用。
  6. 按了接聽卻沒通話 → push 與引擎連線的時序沒接好；採早連線 + PBX 等 App 上線。
  7. VoIP token 與 FCM token 混用 → 兩者不同、要分開存與分開發送。
  8. Android 廠商省電 → 背景被殺收不到，要引導開自啟動 / 關電池優化。
  9. Android 14 全螢幕來電沒跳 → USE_FULL_SCREEN_INTENT 未在執行期取得。
  10. 後端用 legacy FCM server key → 已停用，改 HTTP v1 + OAuth。
  11. FCM data 的 value 不是字串 → HTTP v1 要求 data 全為字串，數字 / 布林要先轉字串。
  12. APNs 打錯環境 → BadDeviceToken；token / entitlement / 端點三者要一致。
  13. 用 endAllCalls() 收掉被取消的來電 → 套件送出 DECLINE，你的 App 把「主叫方取消」回報成「使用者拒接」，通話紀錄靜默寫錯。改用 reportCall(with:endedAt:reason:.remoteEnded)（見取消來電）。
  14. 取消 push 沒報 CallKit → 跟來電 push 一樣受 iOS 13 規則約束，不報一樣被砍、一樣會被撤銷 VoIP token。
  15. 收掉來電時沒過濾已接通的通話 → CXCallObserver.calls 是整台裝置的清單，會把使用者正在講的那通一起掛掉。
  16. 以為 maximumCallGroups = 1 能擋掉第二通 → 它描述的是分組能力，不是 reportNewIncomingCall 的准入閘門，實測擋不住（見取消來電）。
  17. 以為 Android 有系統來電畫面 → self-managed ConnectionService 只管音訊焦點與互通，畫面一律要 App 自己畫（見 Android 喚醒）。
  18. 通話畫面沒有轉場動畫 → 會接到上一個畫面的觸控，使用者按接聽卻打在掛斷鍵上（見通話頁面）。
  19. 只用「有沒有活躍通話」當來電守門 → 一筆清不掉的殘留就會讓之後每一通來電都被擋掉。
