iOS 打包與上架

iOS 是整條 pipeline 最麻煩的一段，痛點全在程式碼簽章（code signing）。全部跑在自架 macOS runner 上。

runner 本身的安裝/註冊/防火牆見通用自架 runner；機密通則見機密管理。本篇補 iOS/Flutter 專屬部分。

0. macOS runner 的 Flutter/iOS 前置​

除了通用的 gitlab-runner（executor 用 shell，因 iOS build 需原生 Xcode 無法容器化），這台 Mac 還要裝：

# Xcode（App Store 安裝）＋命令列工具
sudo xcodebuild -license accept
xcode-select --install

brew install fvm          # Flutter 版本管理（與團隊 .fvmrc 一致）
brew install cocoapods    # iOS 依賴
brew install fastlane     # 簽章與上架

註冊 runner 時給 tag macos，job 才能用 tags: [macos] 指名它。

GitHub 用戶：這台 Mac 可以省下來

上面整套是 GitLab.com（無免費 macOS） 的前置——你得自備並維護一台 Mac。GitHub Actions 有官方 hosted macOS runner（macos-14），Xcode/工具鏈預裝好，iOS job 直接 runs-on: macos-14 就能跑、不必自架（代價：macOS 分鐘較貴，約 Linux 10×）。因為簽章上傳邏輯都在 fastlane，GitHub 就是在 macos-14 上跑同一組 lane——見下方 GitHub Actions 節。

1. 簽章體系速覽​

名詞是什麼
Apple Developer 帳號付費會員（US$99/年），一切前提
App ID / Bundle IDapp 的唯一識別，如 com.yourcompany.app
Certificate（憑證）證明「是誰簽的」（Distribution 憑證用於上架）
Provisioning Profile（描述檔）綁定 App ID + 憑證 + 裝置，允許 build 被安裝/上傳
App Store Connect API Key讓 CI 免帳密自動上傳 TestFlight / App Store

手動上架時 Xcode 自動管理簽章即可；進 CI 建議用 fastlane match 集中管理，才能跨機器重現同一份簽章。

2. 用 fastlane match 管理簽章​

match 把憑證與描述檔加密後存進一個私有 git repo，任何機器（含 CI）都能同步同一份，避免「每台機器各自一套憑證」的地獄。

cd ios
fastlane match init          # 設定存放憑證的私有 repo（獨立於程式碼 repo）
fastlane match appstore      # 產生/同步 App Store 用的憑證與描述檔

CI 上取用走唯讀：

fastlane match appstore --readonly
warning

存憑證的那個 git repo 要私有，並用 MATCH_PASSWORD 加密。

3. App Store Connect API Key（給 CI 用）​

App Store Connect → Users and Access → Integrations → API Keys 建立，取得 Key ID、Issuer ID、.p8 私鑰檔，放進 CI/CD Variables 讓 fastlane 免帳密上傳。

4. 打包 IPA​

flutter build ipa --release --export-options-plist=ios/ExportOptions.plist
# 或交給 fastlane gym（更可控，常搭配 match）
cd ios && bundle exec fastlane gym

產物：build/ios/ipa/*.ipa

5. 上傳 TestFlight（內測）​

ios/fastlane/Fastfile：

platform :ios do
  lane :beta do
    # 用三個變數組出 API key 物件（見 §7）
    api_key = app_store_connect_api_key(
      key_id:       ENV['ASC_KEY_ID'],
      issuer_id:    ENV['ASC_ISSUER_ID'],
      key_filepath: ENV['ASC_API_KEY_P8'],      # File 型變數展開後就是檔案路徑
      in_house:     false
    )
    setup_ci                                    # CI 上建立臨時 keychain
    match(type: "appstore", readonly: true)
    build_app(scheme: "Runner")                 # = gym
    upload_to_testflight(                        # = pilot
      api_key: api_key,
      skip_waiting_for_build_processing: true
    )
  end
end
api_key 和 api_key_path 不是同一個東西
  • api_key: 收的是 app_store_connect_api_key 產生的物件（上面的寫法）。
  • api_key_path: 收的是一個 JSON 金鑰描述檔的路徑——不是 Apple 給你的 .p8。把 .p8 餵給 api_key_path 會失敗。

只有 .p8 + Key ID + Issuer ID 時（§7 就是這個組合），用 app_store_connect_api_key 這條路。

cd ios && bundle exec fastlane beta

6. 送 App Store 上架（正式）——務必手動關卡​

platform :ios do
  lane :release do
    api_key = app_store_connect_api_key(
      key_id:       ENV['ASC_KEY_ID'],
      issuer_id:    ENV['ASC_ISSUER_ID'],
      key_filepath: ENV['ASC_API_KEY_P8']
    )
    deliver(
      api_key: api_key,
      submit_for_review: true,       # 送審
      automatic_release: false,      # 審核過後不自動釋出，你手動按
      force: true
    )
  end
end

這一步在 .gitlab-ci.yml 一定要是 when: manual：push 只做到「build + 上 TestFlight」，真正送審 / 釋出正式版要人到 GitLab 按一下。

7. 需要的 CI/CD Variables​

變數用途
MATCH_PASSWORDmatch 憑證庫的加密密碼
MATCH_GIT_URL存憑證的私有 repo 位址
ASC_KEY_IDApp Store Connect API Key ID
ASC_ISSUER_IDApp Store Connect Issuer ID
ASC_API_KEY_P8.p8 內容（File 型變數）

GitHub Actions：hosted macOS 跑同一份 fastlane​

GitHub 的好處是有 hosted macOS（macos-14），iOS 不必自架 Mac。因為簽章/上傳邏輯都在 fastlane（§2–§6），GitHub 就是在 macos-14 上跑同一組 lane：

# .github/workflows/ios.yml
jobs:
  ios_beta:
    runs-on: macos-14
    if: startsWith(github.ref, 'refs/tags/v')
    steps:
      - uses: actions/checkout@v4
      - uses: subosito/flutter-action@v2
        with: { flutter-version: '<FLUTTER_VERSION>' }
      - run: flutter pub get
      - run: cd ios && bundle exec fastlane beta       # 同一份 Fastfile：match + gym + pilot
        env:
          MATCH_PASSWORD: ${{ secrets.MATCH_PASSWORD }}
          MATCH_GIT_URL:  ${{ secrets.MATCH_GIT_URL }}
          ASC_KEY_ID:     ${{ secrets.ASC_KEY_ID }}
          ASC_ISSUER_ID:  ${{ secrets.ASC_ISSUER_ID }}
          ASC_API_KEY_P8: ${{ secrets.ASC_API_KEY_P8 }}

正式送審（fastlane release）綁 Environment（required reviewers）當手動關卡，對應 GitLab 的 when: manual。

fastlane 是兩邊通用的關鍵

match / gym / pilot / deliver 在 GitLab 自架 Mac 與 GitHub hosted macOS 上跑的是同一份 Fastfile——CI 平台只負責「提供一台 Mac + 餵祕密」，簽章上傳邏輯零重複。這就是為什麼上面 §2–§6 不分平台。GitHub 也有官方 apple-actions/*（import-codesign-certs / download-provisioning-profiles / upload-app-store）能不靠 match，但那把簽章綁死在 GitHub，跨平台就得各寫一套。

深入：不用 match 的手刻簽章（三個真實地雷）​

fastlane match 把簽章包起來很省事，但若你想看清楚它在做什麼、或不想多開一個憑證 repo，可以在自架 Mac 上手刻 keychain + xcodebuild。這條路能跑，但有三個把整條 pipeline 卡死的地雷（Flutter + SPM + 自架 Mac）：

三個地雷

1. flutter build ipa --export-options-plist 不夠——ExportOptions 只管「export」，不管「archive」。 archive 那步仍走 Xcode 專案的簽章設定；Flutter 專案預設 Automatic，headless 下會去找 Development 憑證而 archive failed。解法：flutter build ios --release --config-only 先產設定，再自己 xcodebuild archive。

2. 強制 Manual 簽章「只能套 App target」，不能全域。 命令列 xcodebuild ... PROVISIONING_PROFILE_SPECIFIER=... archive 是全域 build setting，會套到每個 target——包含 SPM 套件（如 Promises），而它們不支援 provisioning profile → does not support provisioning profiles、archive 失敗。正解：把簽章寫進 ios/Flutter/Release.xcconfig（只有 Runner/App target 以它為 base），SPM 套件用別的 xcconfig 不受影響。

3. 臨時 keychain 別設成「預設」再刪掉。 若 security default-keychain -s build.keychain 再於 after_script 刪除，預設鑰匙圈就變成「已刪除的東西」，runner 的 git（macOS 預設開 osxkeychain credential helper）存 CI token 時會 failed to store: -60006、跳鑰匙圈密碼框，卡住整條 pipeline。正解：只加進搜尋清單、不改預設，並在 runner 停用 git credential helper（見 自架 Runner 備註）。

完整手工流程（GitLab 自架 Mac，避開上述三雷）：

ios_release_manual:
  stage: release
  tags: [macos]
  variables:
    IOS_TEAM_ID: "<你的 Team ID>"
    IOS_BUNDLE_ID: "<你的 bundle id>"
  script:
    # (1) 臨時 keychain + 匯入發佈憑證（只加進搜尋清單、不改預設——避開地雷 3）
    - |
      security create-keychain -p "$IOS_KEYCHAIN_PASSWORD" build.keychain
      security set-keychain-settings -lut 3600 build.keychain
      security unlock-keychain -p "$IOS_KEYCHAIN_PASSWORD" build.keychain
      security list-keychains -d user -s build.keychain "$HOME/Library/Keychains/login.keychain-db"
      echo "$IOS_DIST_CERT_P12_BASE64" | base64 --decode > /tmp/dist.p12
      security import /tmp/dist.p12 -k build.keychain -P "$IOS_DIST_CERT_PASSWORD" \
        -T /usr/bin/codesign -T /usr/bin/security
      security set-key-partition-list -S apple-tool:,apple: -s -k "$IOS_KEYCHAIN_PASSWORD" build.keychain
    # (2) 安裝 provisioning profile
    - |
      mkdir -p "$HOME/Library/MobileDevice/Provisioning Profiles"
      echo "$IOS_PROVISION_PROFILE_BASE64" | base64 --decode \
        > "$HOME/Library/MobileDevice/Provisioning Profiles/dist.mobileprovision"
    # (3) ExportOptions.plist（給 (7) 的 exportArchive 用）
    - |
      cat > /tmp/ExportOptions.plist <<PLIST
      <?xml version="1.0" encoding="UTF-8"?>
      <!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
      <plist version="1.0"><dict>
        <key>method</key><string>app-store</string>
        <key>teamID</key><string>${IOS_TEAM_ID}</string>
        <key>signingStyle</key><string>manual</string>
        <key>provisioningProfiles</key><dict>
          <key>${IOS_BUNDLE_ID}</key><string>${IOS_PROVISION_PROFILE_NAME}</string>
        </dict>
        <key>uploadSymbols</key><true/>
      </dict></plist>
      PLIST
    # (4) 只產生 iOS 設定 + 裝 Pods，先不 build（避開地雷 1）
    - fvm flutter build ios --release --config-only
    # (5) Manual 簽章「只套 App(Runner) target」——寫進 xcconfig（避開地雷 2）
    - |
      {
        echo "CODE_SIGN_STYLE = Manual"
        echo "DEVELOPMENT_TEAM = $IOS_TEAM_ID"
        echo "PROVISIONING_PROFILE_SPECIFIER = $IOS_PROVISION_PROFILE_NAME"
        echo "CODE_SIGN_IDENTITY = Apple Distribution"
      } >> ios/Flutter/Release.xcconfig
    # (6) archive（簽章來自 xcconfig，命令列不傳任何 signing 設定）
    - |
      xcodebuild -workspace ios/Runner.xcworkspace -scheme Runner \
        -configuration Release -sdk iphoneos -destination 'generic/platform=iOS' \
        -archivePath "$PWD/build/Runner.xcarchive" archive
    # (7) 匯出簽章 .ipa
    - |
      xcodebuild -exportArchive -archivePath "$PWD/build/Runner.xcarchive" \
        -exportPath "$PWD/build/ios/ipa" -exportOptionsPlist /tmp/ExportOptions.plist
    # (8) 上傳 App Store Connect（API key）
    - |
      mkdir -p "$HOME/.appstoreconnect/private_keys"
      echo "$ASC_API_KEY_P8_BASE64" | base64 --decode \
        > "$HOME/.appstoreconnect/private_keys/AuthKey_${ASC_KEY_ID}.p8"
      xcrun altool --upload-app -t ios -f "$(ls build/ios/ipa/*.ipa | head -1)" \
        --apiKey "$ASC_KEY_ID" --apiIssuer "$ASC_ISSUER_ID"
  after_script:
    # 還原搜尋清單 → 刪臨時 keychain → 清掉落在機器上的憑證與私鑰
    - security list-keychains -d user -s "$HOME/Library/Keychains/login.keychain-db" 2>/dev/null || true
    - security delete-keychain build.keychain 2>/dev/null || true
    - rm -f /tmp/dist.p12 2>/dev/null || true
    - rm -f "$HOME/.appstoreconnect/private_keys/AuthKey_${ASC_KEY_ID}.p8" 2>/dev/null || true
    # SPM checkouts 是一堆巢狀 git repo：趁現在沒程序鎖著清掉，別留給下一次 git clean
    - rm -rf build/ios/SourcePackages 2>/dev/null || true
  rules:
    - if: $CI_COMMIT_TAG =~ /^v/

after_script 那幾行不是可選的收尾：

  • /tmp/dist.p12 與 AuthKey_*.p8 是解密後的憑證與私鑰，留在自架機器上等於長期落地。
  • build/ios/SourcePackages 若不清，會留到下一條 pipeline 的 git clean，在 macOS 上很容易撞 Spotlight 索引而以「Directory not empty」失敗——那個雷的細節見自架 Runner。
為什麼 SPM checkouts 會落在 workspace 裡（而你改不掉）

build/ios/SourcePackages 不是 Xcode 的預設位置——Xcode 預設會把它放進 DerivedData。是 Flutter 自己在解析套件時傳了 -clonedSourcePackagesDirPath <workspace>/build/ios/SourcePackages：

xcodebuild -clonedSourcePackagesDirPath <專案>/build/ios/SourcePackages -resolvePackageDependencies

所以在你自己的 xcodebuild archive 加這個旗標並不能把它們移出 workspace —— Flutter 那一步早就 建好了。這也是為什麼「一堆巢狀 git repo 出現在 workspace 內」對 Flutter 專案來說是常態，而不是設定 錯誤：只能靠 after_script 清掉，加上把 builds 目錄排除在 Spotlight 之外。

別用 workspace 的 build/ 大小判斷 archive 有沒有進度

上面的 xcodebuild archive 沒有傳 -derivedDataPath，所以編譯產物是寫到 ~/Library/Developer/Xcode/DerivedData/，workspace 的 build/ 要到最後才會出現 .xcarchive。

「build/ 好幾分鐘都沒長大」因此不是卡住的證據。要判斷 archive 是否真的在跑，看：

top -l 2 -o cpu -n 10 -stats pid,cpu,command | ...   # 注意 top 第一次取樣的 %CPU 一定是 0
pgrep -fl "swift-frontend|clang|ibtoold"              # 真正在算的子程序

（ps 的 %cpu 是行程生命週期的平均值，不是瞬時值，用它判斷「現在忙不忙」會被誤導。）

這段腳本裡的固定名稱，在並發環境會跨 job 互相破壞

build.keychain、dist.mobileprovision、/tmp/dist.p12、/tmp/ExportOptions.plist 全是寫死的名稱，而 security list-keychains -d user -s 改的是使用者全域清單。一次一個 job 沒問題，但一旦同一台機器同時跑兩個簽章 job（尤其是把這份模板複製到第二個專案之後），症狀包括：

  • 一邊的 after_script 把另一邊還在用的 build.keychain 刪掉
  • 兩邊互相覆寫全域搜尋清單，其中一邊默默地找不到憑證
  • ExportOptions.plist 被覆蓋 → 用別的 App 的 team ID／描述檔去 export

處理方式（把名稱唯一化，或分出一條 limit = 1 的專用 runner）見並發與跨專案共用。

GitHub 手刻版可用官方 apple-actions/import-codesign-certs + download-provisioning-profiles 把 (1)(2) 包起來，其餘 build/export/upload 同理。

Manual 簽章下的 entitlements：Release 要有自己一份​

改用 Manual 簽章之後，多出一個只在 CI 上才會出錯的類別：entitlements 的值不再會被自動修正。

最典型的是推播的 aps-environment：

值連到哪個 APNs
developmentsandbox
production正式

Xcode 在 Automatic 簽章下會默默把這個值改寫成跟描述檔一致，所以本機開發永遠是對的，你不會注意到它。但 CI 走 Manual（上面 §「深入」把 CODE_SIGN_STYLE = Manual 寫進 Release.xcconfig），就沒有那層改寫了——值寫錯就原封不動簽進二進位。

因此 Debug/Profile 與 Release 要用兩份不同的 entitlements 檔，在 Xcode 專案裡讓 Release configuration 指向 Release 那份：

<!-- Runner.entitlements（Debug / Profile） -->
<key>aps-environment</key><string>development</string>

<!-- RunnerRelease.entitlements（Release，CI 用這份） -->
<key>aps-environment</key><string>production</string>
這個錯誤不會有任何錯誤訊息

兩種可能的症狀，都很難從 CI log 看出來：

  1. 上傳就被擋：App Store Connect 回報 entitlements 不是描述檔的子集（這種還算幸運，至少有紅字）。
  2. 上架後才發現（更糟）：二進位帶著 development，於是推播 SDK 拿到的是 sandbox token，後端往正式 APNs 推永遠推不到，而且兩邊都不會報錯——後端看起來推送成功，裝置就是收不到。

驗收方式：從 CI 產出的 .ipa 反查實際簽進去的值，別只看原始碼。

unzip -p build/ios/ipa/<App>.ipa "Payload/*.app/embedded.mobileprovision" \
  | security cms -D | plutil -p - | grep -i aps-environment

其他同類的 entitlement（App Groups、Keychain Sharing、NFC…）也一樣：Manual 簽章下，entitlements 必須是描述檔所授權範圍的子集，多寫、寫錯都會在 archive 或上傳時失敗。

推播那一側的完整排查（APNs token 環境、.p8 為何讓錯誤變無聲），見 推播基礎設定。

常見雷區​

  • 憑證只在某台機器 → 改用 match 集中管理。
  • 描述檔過期 / 裝置沒註冊 → match 重新產生；上架用 App Store 描述檔不綁裝置。
  • CI keychain 權限 → fastlane setup_ci 建立臨時 keychain 避免卡住（手刻版見上方地雷 3）。
  • No profiles for '...' were found → ExportOptions.plist 的 bundle id → profile 名稱沒對上（要用 Apple Developer 顯示的字串，不是檔名）。
  • 上傳成功但 TestFlight 看不到 → Apple 端要跑處理（數分鐘～數十分鐘）；缺 export compliance 會卡「遺失合規」，補一次或設 ITSAppUsesNonExemptEncryption。
  • build number 重複 → 每次上傳必須遞增（$CI_PIPELINE_IID / github.run_number），見 release-runbook。

備素材時最常卡的三件事（設定前先確認）​

  • 「我沒有 .p12 / 找不到 Distribution 憑證」：多半是你以前用 Xcode 自動（或雲端）簽章上架，那張發佈憑證是 Xcode 託管的、不在你可匯出的鑰匙圈。CI 走 Manual/match 需要「私鑰在你手上」的憑證：鑰匙圈輔助程式產 CSR → Apple Developer 建 Apple Distribution 憑證 → 裝進 login 鑰匙圈 → 才匯得出 .p12。
  • 「Integrations 看不到 App Store Connect API / 建不了 key」：API 存取要先由 Account Holder 按一次 Request Access 開通（只有帳號持有人能開），且只有 Admin/Account Holder 看得到 Integrations。不是付費項目——已含在開發者年費裡。
  • 團隊（Team ID）對不上：開發機的 Development 憑證團隊，可能跟 App 上架的團隊不是同一個（個人團隊 vs 公司團隊）。建憑證/profile/API key 時，右上角切到 App 真正的團隊。
