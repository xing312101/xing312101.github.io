裝置測試（整合 / e2e / screenshot）

單元與 widget 測試在快檢就跑掉了；整合測試（integration_test/）、e2e、screenshot/golden 測試需要真的把 app 跑在裝置上，又慢又重。這篇講怎麼在 CI 裡妥善安排。

原則：不要塞進每個 MR​

測試觸發
單元 / widget每個 MR（快檢）
整合 / e2emerge 進 main 後，或 nightly schedule
screenshot / goldennightly，或手動 / 出版本前

在 GitLab 設 nightly：Settings → CI/CD → Schedules → New schedule（cron），job 用 rules: - if: $CI_PIPELINE_SOURCE == "schedule" 命中。

方案 A：Firebase Test Lab（雲端真機，推薦）​

把 app 與測試打包上傳，跑在 Google 的真機/模擬器上，不吃 GitLab compute minutes（另計 Google 那邊的額度，有免費配額）。

Android​

pushd android
./gradlew app:assembleDebug app:assembleAndroidTest \
  -Ptarget=integration_test/app_test.dart
popd

gcloud firebase test android run \
  --type instrumentation \
  --app build/app/outputs/apk/debug/app-debug.apk \
  --test build/app/outputs/apk/androidTest/debug/app-debug-androidTest.apk \
  --device model=<DEVICE_MODEL>,version=<API_LEVEL>,locale=zh_TW,orientation=portrait \
  --timeout 10m

iOS（在自架 macOS runner 上打包）​

flutter build ios integration_test/app_test.dart --release

xcodebuild build-for-testing \
  -workspace ios/Runner.xcworkspace \
  -scheme Runner \
  -derivedDataPath build/ios_integ \
  -sdk iphoneos

pushd build/ios_integ/Build/Products
zip -r ios_tests.zip *.xctestrun *-iphoneos
popd

gcloud firebase test ios run \
  --test build/ios_integ/Build/Products/ios_tests.zip \
  --device model=<IOS_DEVICE>,version=<IOS_VERSION>,locale=zh_TW,orientation=portrait \
  --timeout 10m
前置

建立 Google Cloud 專案、開通 Test Lab、用 service account 讓 CI 免互動登入（把 JSON 放 CI/CD Variable，gcloud auth activate-service-account，見機密管理）。

CI job 範例​

integration_testlab:
  stage: check
  image: ghcr.io/cirruslabs/flutter:$FLUTTER_VERSION   # Android 部分
  rules:
    - if: $CI_PIPELINE_SOURCE == "schedule"            # nightly
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH       # merge 進 main 後
  script:
    - echo "$GCLOUD_SA_JSON" > /tmp/sa.json
    - gcloud auth activate-service-account --key-file=/tmp/sa.json
    - ./scripts/run_android_integration_on_testlab.sh

（iOS 整合測試 job 記得加 tags: [macos]，跑在自架 Mac 上打包。）

方案 B：自架裝置 / 模擬器​

在自架 runner 接實體 Android 手機/平板或起模擬器跑：

flutter test integration_test/ -d <DEVICE_ID>
  • Android：自架 runner 接 USB 實機，或 flutter emulators --launch <id> 起模擬器。多台裝置可平行分擔不同尺寸（如手機 / 平板版面）。
  • iOS：只能在 macOS runner 上用 iOS 模擬器或接實體 iPhone（實機需事先在描述檔註冊 UDID）。

取捨：自架省雲端費用、能用手上的實機測特定尺寸；代價是機器要在線、環境自己維護、多尺寸覆蓋不如雲端裝置庫齊全。

GitHub Actions：hosted 模擬器 / emulator​

GitHub 的 hosted runner 內建模擬器，小專案不必自架也不必上 Firebase：

iOS simulator（macos-14 內建）：

jobs:
  e2e_ios:
    runs-on: macos-14
    steps:
      - uses: actions/checkout@v4
      - uses: subosito/flutter-action@v2
        with: { flutter-version: '<FLUTTER_VERSION>' }
      - run: flutter pub get
      - run: |
          xcrun simctl boot "iPhone 15" || true
          flutter test integration_test
用機型名稱直接 boot 是模擬器 e2e 最常見的 flake 來源

兩個問題：boot 是非同步的（它回來不代表開機完成，測試會撞上還沒 ready 的模擬器），而且用名稱指定容易撞到同名的多個裝置。穩一點的寫法是先查 UDID、開機、等開完：

UDID=$(xcrun simctl list devices available \
  | grep -m1 "$IOS_SIM (" \
  | grep -oiE '[0-9A-F]{8}(-[0-9A-F]{4}){3}-[0-9A-F]{12}')
if [ -z "$UDID" ]; then echo "找不到 simulator：$IOS_SIM"; exit 1; fi   # 失敗要響
xcrun simctl boot "$UDID" 2>/dev/null || true
xcrun simctl bootstatus "$UDID" -b        # ← 等到真的開完才往下
flutter test integration_test -d "$UDID"

收尾要注意：after_script 是新的 shell，讀不到 script 裡的 $UDID。所以清理常被寫成 xcrun simctl shutdown all——那是全機器範圍的，同一台機器上還有別的 job 在跑模擬器時會一起關掉。要嘛把 UDID 寫進檔案讓收尾階段讀，要嘛把這類 job 集中到一條 limit = 1 的 runner（見並發與跨專案共用）。

Android emulator（hosted Linux 有 KVM，社群 action 一步到位）：

jobs:
  e2e_android:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: subosito/flutter-action@v2
        with: { flutter-version: '<FLUTTER_VERSION>' }
      - run: flutter pub get
      - uses: reactivecircus/android-emulator-runner@v2
        with:
          api-level: 34
          arch: x86_64
          script: flutter test integration_test

GitLab 對照：iOS 在自架 Mac 上 xcrun simctl boot 開模擬器；Android emulator 要自架 Linux 且機器有 /dev/kvm（雲端 shared runner 通常沒 KVM、開不了 emulator，這也是 Android e2e 在 GitLab 常改自架的原因）。

序列化：別讓多條 pipeline 互踩沙箱​

若 e2e 會改到共用的後端測試資料（建立/刪除），多條 pipeline 同時跑會互踩 → 隨機紅：

  • GitLab：resource_group: <名稱> → 同一個專案內，同時間只跑一條該群組的 job。
  • GitHub：concurrency: { group: e2e, cancel-in-progress: false }。
resource_group 只在單一專案內互斥

它的作用域是專案。兩個專案各自寫 resource_group: 同一個名字，那是兩個獨立的群組，照樣會同時跑。

所以兩種衝突要用不同工具擋：

衝突來源用什麼擋
共用的後端沙箱資料（同一個專案的多條 pipeline）resource_group
同一台機器上的全域狀態（模擬器、鑰匙圈、固定檔名）自架 runner 的 limit（機器範圍）

多個專案共用一台 Mac 時，xcrun simctl shutdown all 這類全機器範圍的指令會關掉別的專案正在用的模擬器——那要靠把這些 job 集中到一條 limit = 1 的 runner，見並發與跨專案共用。

搭配「建立 → 驗證 → finally 清除」契約 + 鎖一個可拋棄的沙箱帳號（帳密寫死在測試 harness，洩漏也無所謂 → 不必進 CI 祕密）。

推薦組合：合併後跑 + 非阻塞 + 看得到

最順的一種設法：只在合併進主分支後自動跑一次，且非阻塞（GitLab allow_failure: true／GitHub 該 job 不列入 required checks）。

  • MR / feature 分支不跑 → MR pipeline 乾淨、不擋合併。
  • 每次 merge 才跑一次（不是每個 push）→ 大幅減少打真後端。
  • 紅了不擋 main，但仍顯示在 pipeline 上（看得到、易發現，又不拖紅整條）。
  • 別設成「阻塞式 manual」（when: manual + allow_failure: false）：那會卡在 blocked、MR 併不了。

Screenshot / Golden 測試​

  • Golden 測試（matchesGoldenFile）對字型、DPI、渲染引擎敏感，不同平台產出的 golden 可能不一致。對策：固定在單一環境產生與驗證（例如都在雲端 Linux image），別混平台；更新用 flutter test --update-goldens 並把更新後的檔一起 commit、review。
  • screenshot 測試（跑真 app 截圖）較重，排 nightly 或出版本前跑。
