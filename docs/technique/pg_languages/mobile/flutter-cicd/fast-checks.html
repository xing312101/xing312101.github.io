Flutter 快檢

把通用快檢骨架填上 Flutter 指令：每個 MR 在 GitLab 免費 Linux runner 上跑格式、靜態分析、單元/widget 測試，不需要裝置。

用現成的 Flutter Docker image​

不用自己在 CI 裡裝 SDK，直接用含 Flutter 的官方社群 image，並把版本對齊你 .fvmrc 鎖定的版本：

image: ghcr.io/cirruslabs/flutter:<FLUTTER_VERSION>   # 換成你 .fvmrc 的版本

快檢 job​

stages: [check]

fast_check:
  stage: check
  image: ghcr.io/cirruslabs/flutter:<FLUTTER_VERSION>
  interruptible: true
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
  variables:
    PUB_CACHE: "$CI_PROJECT_DIR/.pub-cache"
  cache:
    key:
      files: [ pubspec.lock ]
    paths: [ .pub-cache/ ]
  before_script:
    - flutter --version
    - flutter pub get
  script:
    - dart format --set-exit-if-changed .    # ← 注意旗標！沒加就不會擋
    - flutter analyze --fatal-infos --fatal-warnings
    - flutter test
warning

dart format 預設只重排、不回非 0。一定要加 --set-exit-if-changed，否則格式沒過也放行（見通用觀念：exit code）。

flutter analyze 也有「看起來有擋、其實沒擋」的層級

flutter analyze 只有 error 級別會回非 0；info / warning 預設是回 0 的。專案剛開始零問題時，加上 --fatal-infos --fatal-warnings 可以避免這些提示慢慢累積成幾百條沒人看的雜訊。

已經累積很多的舊專案不要直接開（會瞬間全紅）。折衷做法是先在 analysis_options.yaml 把要治的規則 調成 error、其餘暫時降級，逐步收斂。

同一份快檢：GitHub Actions 版​

觀念完全一樣（雲端 Linux、進 merge gate），只是換語法。subosito/flutter-action 幫你裝 SDK、cache: true 內建快取：

# .github/workflows/checks.yml
name: checks
on:
  pull_request:
  push:
    branches: [ main ]

jobs:
  fast_check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: subosito/flutter-action@v2
        with:
          flutter-version: <FLUTTER_VERSION>    # 對齊 .fvmrc
          cache: true                            # 內建快取 pub-cache / SDK
      - run: flutter pub get
      - run: dart format --set-exit-if-changed .   # ← 同樣別忘旗標
      - run: flutter analyze
      - run: flutter test

要當「必過」條件：GitHub 走 Settings → Branches → Branch protection rules，把 fast_check 加進 required status checks（對應 GitLab 的 "Pipelines must succeed"）。

Flutter 版本一致性（與 fvm）​

CI 有兩處在指定 Flutter 版本，必須都對齊 .fvmrc：

  • 雲端快檢：image tag ghcr.io/cirruslabs/flutter:<版本>。
  • 自架 runner：機器上用 fvm，讀專案的 .fvmrc。

避免漂移（擇一）：

  1. 單一真相來源：版本寫死在 .gitlab-ci.yml 的 variables.FLUTTER_VERSION，image tag 用它，並確保等於 .fvmrc。
  2. 一律走 fvm：連雲端 job 也 fvm install && fvm flutter ...（讀 .fvmrc），版本只由 .fvmrc 決定，最不會漂。

選 2 的話，image 只當底座（裡面附的 SDK 版本就不必對齊 .fvmrc 了，反正不會用到），但要記得把 fvm 裝的 SDK 也快取起來，否則每次 job 都重新下載一整套 SDK：

variables:
  FVM_CACHE_PATH: "$CI_PROJECT_DIR/.fvm-cache"   # 移進 workspace 才快取得到
cache:
  key:
    files: [ pubspec.lock, .fvmrc ]              # ← 版本換了要換 key
  paths:
    - .pub-cache/
    - .fvm-cache/                                # fvm 裝的 SDK
before_script:
  - dart pub global activate fvm
  - export PATH="$PATH:$CI_PROJECT_DIR/.pub-cache/bin"
  - fvm install --setup
  - fvm flutter --version

cache.key 一定要把 .fvmrc 也列進去——只用 pubspec.lock 當 key 的話，升版 Flutter 後會沿用舊 key 裡的舊 SDK。

自架 runner 就簡單得多：fvm 是全域安裝，SDK 也在機器上常駐，fvm install --setup 多數時候是 no-op。 （多個專案共用一台機器時注意：fvm 的 SDK 目錄是全域的，兩個 job 同時安裝不同版本是併發寫入——偶發的 fvm 錯誤可以先往這裡查。）

讓覆蓋率顯示在 MR 上​

flutter test --coverage 會產生 coverage/lcov.info。GitLab 靠掃 job log 的 regex 抓覆蓋率數字（不是讀 lcov 檔），所以要自己印一行給它看：

test:
  script:
    - flutter test --coverage --reporter expanded
    # 由 lcov.info 重算總覆蓋率，並列出「未覆蓋行數」最多的檔案
    - |
      awk '
        /^SF:/ { f = substr($0, 4) }
        /^LF:/ { lf[f] = substr($0, 4) + 0; tot_lf += substr($0, 4) + 0 }
        /^LH:/ { lh[f] = substr($0, 4) + 0; tot_lh += substr($0, 4) + 0 }
        END {
          pct = (tot_lf > 0) ? tot_lh * 100.0 / tot_lf : 0
          printf "TOTAL_COVERAGE: %.1f%%  (%d/%d lines)\n", pct, tot_lh, tot_lf
          for (k in lf)
            printf "%6d %6.1f%% %s\n",
                   lf[k] - lh[k], (lf[k] > 0 ? lh[k] * 100.0 / lf[k] : 0), k \
                   > (ENVIRON["CI_PROJECT_DIR"] "/percov.txt")
        }
      ' coverage/lcov.info
    - echo "--- 未覆蓋行數最多的 10 個檔案 ---"
    - sort -rn "$CI_PROJECT_DIR/percov.txt" | head -10
  coverage: '/TOTAL_COVERAGE: (\d+\.\d+)%/'   # ← 對上上面那行的格式
  artifacts:
    when: always
    paths: [ coverage/lcov.info ]

兩個容易踩到的點：

  • coverage: 的 regex 必須剛好對上你印的格式，而且那行要走 stdout。改格式就要同步改 regex，否則覆蓋率會安靜地變成空白。
  • 暫存檔不要放 /tmp 的固定路徑。/tmp/percov.txt 這種寫法在「一次一個 job」時沒事，但只要自架 runner 的並發大於 1，兩個 job 就會互相覆蓋同一個檔案。放 $CI_PROJECT_DIR 底下才會跟著 workspace 隔離（見並發與跨專案共用）。

排序用「未覆蓋行數」而不是百分比，比較能指出「補哪個檔最划算」——一個 1000 行、80% 的檔案比一個 20 行、10% 的檔案值得先補。

重測試不要塞進快檢​

整合 / e2e / screenshot 測試又慢又重，不要放每個 MR。交給 device-testing 的 Firebase Test Lab，觸發改成 merge 後或 nightly schedule，讓 MR 回饋維持在幾分鐘內。
