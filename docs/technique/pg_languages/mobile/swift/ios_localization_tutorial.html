iOS App 語系宣告完整教學

為什麼 App Store 產品頁的「語言」顯示錯誤?從 CFBundleLocalizations、.lproj 到 developmentRegion 的完整解法。 本文為通用教學,不涉及任何特定專案。

1. 問題現象​

你在 App Store Connect 把商店文案(名稱、描述、截圖)都做了繁體中文版,產品頁的文字也確實顯示中文,但是往下捲到「資訊 / Information」區塊時,「語言 / Languages」那一欄卻只寫著 英文。

或是相反:你的 App 明明只支援中文,產品頁卻列出一堆你根本沒做的語言。

這兩個症狀的根源是同一個:「語言」欄位跟你在 App Store Connect 填的東西完全無關。

2. 先分清楚三種「語言」​

這是整件事最容易混淆的地方。iOS 生態裡有三個獨立的「語言」概念,彼此不互通:

概念設定位置影響什麼
商店文案語系App Store Connect → App 資訊 / 版本資訊產品頁的文字內容(名稱、描述、關鍵字、截圖)
App 二進位語系Xcode 專案 / Info.plist / .lproj 資料夾產品頁的**「語言」欄位**、系統認定 App 支援哪些語系
執行期語系程式碼內的 i18n 框架使用者實際看到的 UI 文字

關鍵:產品頁那一欄「語言」讀的是第二項,也就是你上傳的 build 本身。你在 App Store Connect 加再多語系文案,都不會改變它。

同理,第三項也不算數。如果你用某個框架在應用層自己做多語系(常見於跨平台框架),而沒有告訴 iOS bundle「我支援這些語言」,Apple 就看不到。

3. Apple 如何決定產品頁的語言欄位​

上傳 build 到 App Store Connect 時,Apple 會解析 .ipa 裡的 .app bundle,依序收集:

  1. CFBundleDevelopmentRegion — App 的主要 / 原生語言,會被列在第一個。
  2. .app 根目錄下的 .lproj 資料夾 — 每一個資料夾名稱就是一個語系。這是最權威的來源。
  3. Info.plist 裡的 CFBundleLocalizations 陣列 — 給「不用 .lproj 做在地化」的 App 用的補充宣告。

實務上第 2 項最可靠。第 3 項在文件上是有效的,但實際被 App Store 採信的程度不穩定 — 這正是最常見的踩坑點。

注意:Base.lproj 不算一個語系。它是 Base Internationalization 的產物(存放未在地化的 storyboard / xib),Apple 不會把它當成一種語言列出來。所以一個「只有 Base.lproj」的 App,在 Apple 眼中就只有 CFBundleDevelopmentRegion 那一種語言。

4. 三個關鍵設定​

CFBundleDevelopmentRegion​

App 的原生語言。在 Xcode 專案裡由 developmentRegion 決定,Info.plist 通常寫成變數形式:

<key>CFBundleDevelopmentRegion</key>
<string>$(DEVELOPMENT_LANGUAGE)</string>

這個變數會被 build settings 展開成專案的 development region。預設值是 en,而且大多數人從來沒改過 — 這就是為什麼一堆非英文 App 的產品頁第一個語言是英文。

CFBundleLocalizations​

一個字串陣列,宣告「這個 App 支援哪些語系」,不需要對應的 .lproj 資料夾:

<key>CFBundleLocalizations</key>
<array>
    <string>zh-Hant</string>
    <string>en</string>
</array>

.lproj 資料夾​

實際存在於 bundle 內的在地化資源目錄,例如 zh-Hant.lproj/InfoPlist.strings。這是 Apple 最認的形式。

5. 為什麼跨平台框架特別容易踩到​

原生 iOS 專案在 Xcode 加一個語系時,Xcode 會自動幫你:

  • 在 knownRegions 加上該語系
  • 建立 xx.lproj/ 資料夾
  • 把檔案掛進 Copy Bundle Resources

所以 build 出來的 .app 自然就有 .lproj。

但跨平台框架(Flutter、React Native 等)的多語系是在應用層做的 — 翻譯字串放在 Dart / JS 那一側,完全不經過 iOS 的 .lproj 機制。結果就是:

  • App 跑起來確實是中文 ✅
  • .app bundle 裡只有 Base.lproj ❌
  • Apple 看到的語言只有 development region 的 en ❌

而且這類專案的 iOS 殼是框架的樣板產生的,developmentRegion 幾乎必然停在 en。

6. 解法 A:CFBundleLocalizations​

最省事的做法,只改 Info.plist:

<key>CFBundleLocalizations</key>
<array>
    <string>zh-Hant</string>
    <string>en</string>
</array>

優點:一行設定,不用動 Xcode 專案檔。 缺點:不保證生效。實務上有不少案例是加了這個、重新上架後,產品頁語言欄位依然沒變。

建議把它當成「加了沒壞處」的補充,而不是唯一手段。如果你送了新 build 上去、審核通過後語言欄位仍然不對,就直接跳到解法 B。

7. 解法 B:建立真正的 .lproj​

這是可靠的做法:讓 bundle 裡真的出現 zh-Hant.lproj/。

步驟 1:建立 InfoPlist.strings​

在 iOS 專案的主要 target 資料夾底下建立:

Runner/                       ← 你的 target 資料夾名稱
├── en.lproj/
│   └── InfoPlist.strings
└── zh-Hant.lproj/
    └── InfoPlist.strings

內容可以只放 App 顯示名稱:

"CFBundleDisplayName" = "你的 App 名稱";
"CFBundleName" = "你的 App 名稱";

提醒:InfoPlist.strings 會覆寫 Info.plist 裡對應的鍵。如果你不想改變任何語系下的顯示名稱,就把兩個檔案都填成跟 Info.plist 一樣的值 — 行為完全不變,但 bundle 裡多了實體的 .lproj,目的就達成了。

步驟 2:用 Xcode GUI 掛進專案(推薦)​

  1. 在 Xcode 的 Project Navigator 對 target 資料夾按右鍵 → Add Files to...,把 en.lproj/InfoPlist.strings 加進來。
  2. 選中該檔案 → 右側 File Inspector → Localization 區塊 → 點 Localize...。
  3. 勾選要支援的語系(例如 Chinese, Traditional)。

Xcode 會自動處理 knownRegions、variant group 和 build phase。

步驟 3:手動改 project.pbxproj(CI / 無 GUI 時)​

如果你需要在沒有 Xcode GUI 的環境完成,要改四個地方。

(a) PBXFileReference — 每個語系一筆:

E11700082F000008009E16D5 /* en */ = {isa = PBXFileReference; fileEncoding = 4; lastKnownFileType = text.plist.strings; name = en; path = en.lproj/InfoPlist.strings; sourceTree = "<group>"; };
E11700092F000009009E16D5 /* zh-Hant */ = {isa = PBXFileReference; fileEncoding = 4; lastKnownFileType = text.plist.strings; name = "zh-Hant"; path = "zh-Hant.lproj/InfoPlist.strings"; sourceTree = "<group>"; };

(b) PBXVariantGroup — 把多個語系檔包成一個邏輯檔案:

E11700072F000007009E16D5 /* InfoPlist.strings */ = {
    isa = PBXVariantGroup;
    children = (
        E11700082F000008009E16D5 /* en */,
        E11700092F000009009E16D5 /* zh-Hant */,
    );
    name = InfoPlist.strings;
    sourceTree = "<group>";
};

(c) PBXBuildFile + Resources build phase — 讓它真的被複製進 bundle:

E117000A2F00000A009E16D5 /* InfoPlist.strings in Resources */ = {isa = PBXBuildFile; fileRef = E11700072F000007009E16D5 /* InfoPlist.strings */; };

然後把這個 ID 加進 target 的 PBXResourcesBuildPhase 的 files 清單,以及把 variant group 加進 target 的 PBXGroup children。

(d) knownRegions:

knownRegions = (
    en,
    Base,
    "zh-Hant",
);

ID 規則:pbxproj 的物件 ID 是 24 位大寫十六進位字串,只要在同一個檔案內唯一即可,不需要特定格式。手改前先備份,改完務必驗證(見下一節)。

8. 設定主要語言 developmentRegion​

決定產品頁語言欄位第一個顯示什麼,也影響系統在找不到對應語系時的 fallback。

在 project.pbxproj 的 PBXProject 區塊:

developmentRegion = "zh-Hant";

改完之後 $(DEVELOPMENT_LANGUAGE) 就會展開成 zh-Hant,CFBundleDevelopmentRegion 也跟著變。

要不要改? 如果你的 App 主要市場是中文區,建議改。如果 App 是真正的多語系產品、英文是原始開發語言,那維持 en 才是正確的語意。

改動時記得 knownRegions 必須包含新的 development region,否則 Xcode 會警告。

9. 驗證方法​

不要等到上架才發現沒生效。 每次改完都在本機驗證。

檢查 .app bundle​

# 列出所有頂層語系資料夾
find path/to/Runner.app -maxdepth 1 -name "*.lproj"

# 應該看到 en.lproj、zh-Hant.lproj,而不是只有 Base.lproj

檢查主要語言​

/usr/libexec/PlistBuddy -c "Print :CFBundleDevelopmentRegion" path/to/Runner.app/Info.plist

檢查 CFBundleLocalizations​

/usr/libexec/PlistBuddy -c "Print :CFBundleLocalizations" path/to/Runner.app/Info.plist

檢查 .strings 內容有沒有被正確編譯​

build 之後 .strings 會從純文字被編譯成 binary plist,用 plutil 讀:

plutil -p path/to/Runner.app/zh-Hant.lproj/InfoPlist.strings

直接檢查 .ipa​

unzip -l YourApp.ipa | grep '\.lproj'

⚠️ 增量建置的陷阱​

移除語系時特別要注意:Xcode 的增量建置不會刪掉 .app 裡已經不需要的資源。你把 en.lproj 從專案移除、重新 build,bundle 裡那個 en.lproj 還是會在,因為它只是上一輪的殘留孤兒。

判斷方式是看時間戳:

ls -la path/to/Runner.app/en.lproj/

如果檔案時間比 .app 本身舊,就是殘留。驗證「移除」類的改動一定要跑乾淨建置,否則你會誤以為沒生效而白改一輪(或更糟 — 誤以為生效了,結果上傳的還是舊的)。

新增語系時反而不受影響,增量建置就看得到。

驗證 pbxproj 沒有改壞​

手改 project.pbxproj 之後一定要跑:

plutil -convert xml1 -o /dev/null YourApp.xcodeproj/project.pbxproj && echo "OK"
xcodebuild -list -project YourApp.xcodeproj

第一個指令檢查語法,第二個檢查 Xcode 能不能正常載入專案。

10. 上架後多久會更新​

產品頁的語言欄位是在 build 被 Apple 處理時算出來的,而且只跟「目前可供銷售的那個 build」綁定。

這代表:

  • 你在專案裡改的設定,對已經上架的舊 build 完全沒有影響。
  • 必須送一個新的 build 上去,而且通過審核、實際上架之後,欄位才會更新。
  • 只是上傳到 TestFlight 不會改變產品頁。
  • 產品頁有 CDN 快取,上架後可能還要等幾小時才看得到變化。

所以完整流程是:改設定 → 本機驗證 bundle → bump build number → 上傳 → 送審 → 上架 → 等快取。

11. 常見問題​

Q:我在 App Store Connect 加了繁體中文文案,為什麼語言欄位沒變?​

那是商店文案語系,跟語言欄位是兩回事。見第 2 節。

Q:只加 CFBundleLocalizations 就好了嗎?​

不一定。文件上有效,實務上不穩定。加了沒壞處,但如果新 build 上架後還是不對,就改用 .lproj。

Q:我的 App 列出了一堆我沒做的語言,怎麼移除?​

通常是第三方 SDK 帶進來的。有些 SDK 會在自己的 .bundle 裡塞幾十個 .lproj。檢查一下:

find path/to/Runner.app -name "*.lproj" | sort

如果是巢狀在 SomeSDK.bundle/xx.lproj,Apple 一般不會把它算進 App 的語言;但有些情況會。真的要清掉的話,得在 build phase 加腳本刪除不需要的 .lproj,或改用 CFBundleLocalizations 明確限定清單。

Q:我的 App 只支援單一語言,要怎麼設?​

不要留任何多餘的語系宣告 — 商店列出你其實沒做的語言是誤導使用者,也可能在審核時被質疑。三處都要清乾淨:

  1. CFBundleLocalizations 只留該語系(或整個拿掉)
  2. 只保留該語系的 .lproj,刪掉其他的(含 pbxproj 裡的 file reference、variant group children、knownRegions)
  3. developmentRegion 設成該語系

Base.lproj 要留著 — 它存放 storyboard,刪掉會壞。

很多跨平台專案會在程式碼裡直接鎖死語系(而不是跟隨裝置語言),這種情況更應該只宣告一種語言,才跟實際行為一致。

Q:Base.lproj 為什麼不算?​

它是 Base Internationalization 的容器,不代表任何特定語言。

Q:應該用 zh-Hant 還是 zh-TW?​

優先用 zh-Hant。它是以「書寫系統」為準的現代寫法,涵蓋台港澳。zh-TW 也能用,但語意上更窄。避免混用兩者。

Q:改了 development region 會不會影響 App 行為?​

會影響系統的語系 fallback 順序 — 當使用者的語系在你的支援清單裡都找不到時,會落到 development region。如果你的 App 有真正的多語系資源,改之前先想清楚 fallback 該落在哪一種語言。
