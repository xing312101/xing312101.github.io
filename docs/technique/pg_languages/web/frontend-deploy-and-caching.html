前端靜態部署與快取完整教學

公開教學。為什麼「明明部署了,使用者看到的還是舊版」?從內容雜湊、index.html 的快取、部署原子性到 Service Worker 的完整解法。 適用對象:任何要把 SPA / 靜態站台放上伺服器的人(Vite / webpack / Next 靜態輸出 / CRA 皆適用)。

0. 先搞懂:快取會出兩種相反的問題​

動手之前先分清楚,因為兩者的解法方向完全相反:

問題症狀使用者感受
快取太黏部署完了,瀏覽器還是拿舊檔「你根本沒改吧?」
快取太弱每次進站都重新下載全部資源「這網站好慢」

大多數人只處理了後者(設個 max-age 就收工),結果撞上前者;或是被前者咬過一次之後,乾脆全站 no-store,又掉進後者。

⚠️ 正確答案不是二選一,是「分檔案類型給不同策略」。 靜態資源(JS / CSS / 圖)要永久快取,入口 HTML 要每次確認。 這一份教學基本上就是在講「為什麼可以這樣分」以及「怎麼設」。

1. 內容雜湊(content hash)為什麼有效​

現代打包工具產出的檔名長這樣:

dist/
├── index.html
└── assets/
    ├── index-4f8a1c2b.js
    ├── index-9d3e7a05.css
    └── logo-2b7c9e41.svg

中間那串亂碼是檔案內容的雜湊。它帶來一個很強的性質:

內容不變 → 檔名不變 → 瀏覽器手上那份永遠是對的。 內容一變 → 檔名一定變 → 瀏覽器沒看過這個檔名,一定會去抓。

所以這些檔案可以放心設成「快取一年、而且不用回來問」。舊版本的檔案還留在伺服器上也無所謂 —— 沒有人會再指向它。

1-1. 打包工具怎麼設​

Vite 預設就會做,不用設定。要調整輸出檔名時:

// vite.config.js
export default {
  build: {
    rollupOptions: {
      output: {
        entryFileNames: 'assets/[name]-[hash].js',
        chunkFileNames: 'assets/[name]-[hash].js',
        assetFileNames: 'assets/[name]-[hash][extname]',
      },
    },
  },
}

webpack:

// webpack.config.js
module.exports = {
  output: {
    filename: '[name].[contenthash].js',
    chunkFilename: '[name].[contenthash].chunk.js',
    assetModuleFilename: '[name].[contenthash][ext]',
  },
}

注意是 [contenthash] 不是 [hash]。 webpack 的 [hash] 是整個 build 的雜湊 —— 只改一個檔案,所有檔名都會變,等於每次部署都讓使用者重下載全部資源。[contenthash] 才是逐檔計算的。

1-2. 用 immutable 告訴瀏覽器「真的不用問」​

Cache-Control: public, max-age=31536000, immutable
  • max-age=31536000 = 一年
  • immutable 是額外的保證:即使使用者按了重新整理,也不要送條件請求來問

沒有 immutable 的話,使用者按 F5 時瀏覽器仍會對每個資源發一次 If-None-Match,拿一堆 304 回來。檔案是沒重下載,但那些往返還是要時間 —— 資源一多就很有感。

2. index.html 是那個例外​

這裡就是「部署了卻看到舊版」的病根。

index.html 是指路的檔案,內容長這樣:

<script type="module" src="/assets/index-4f8a1c2b.js"></script>
<link rel="stylesheet" href="/assets/index-9d3e7a05.css">

它必須用固定的名字(使用者輸入的網址就是它),所以不可能帶 hash。而只要它被快取住:

瀏覽器手上的 index.html  →  指向 index-舊hash.js  →  那個檔還在伺服器上  →  200 OK

每一步都成功,使用者看到的卻是舊版,而且沒有任何錯誤訊息。 這是最容易誤判成「部署失敗」或「程式沒改到」的情況。

2-1. 為什麼「檔名有 hash」救不了這一步​

很多人以為「我有做 content hash 所以快取沒問題」。錯 —— hash 解決的是資源檔的快取,前提是有人告訴瀏覽器新的檔名。而那個「有人」就是 index.html。指路的人手上拿的是舊地圖,再精確的門牌也沒用。

2-2. 判斷是不是踩到這個坑​

# 1. 伺服器上的 index.html 指向哪個 hash
curl -s https://example.com/ | grep -o 'index-[A-Za-z0-9_-]*\.js'

# 2. 你剛剛 build 出來的是哪個
ls dist/assets/

兩邊一致 → 伺服器是新的,問題在瀏覽器快取。 兩邊不一致 → 檔案根本沒上去,是部署的問題。

先分清楚這兩件事,再往下查。

3. Cache-Control 該怎麼設​

3-1. 三個最常被搞混的值​

指令實際行為什麼時候用
no-store完全不存。每次都完整重新下載含個資的頁面、一次性 token
no-cache存,但每次都要回來問。沒變的話伺服器回 304,不重傳內容入口 HTML
max-age=0存,立刻過期,下次要用時回來問效果接近 no-cache,但語意較弱

⚠️ no-cache 不是「不要快取」。 這是整份文件最容易記錯的一個字。 它的意思是「先別直接用,回來確認一下」。真正的「不要存」是 no-store。 入口 HTML 用 no-cache 就對了 —— 內容沒變時只會回一個幾百 bytes 的 304,不會重傳整份 HTML。

3-2. 條件請求與 304 怎麼運作​

no-cache 之所以便宜,是因為它走條件請求:

第一次:
  GET /index.html
  ← 200 OK
    ETag: "a1b2c3"
    Cache-Control: no-cache
    <整份 HTML>

之後每一次:
  GET /index.html
  If-None-Match: "a1b2c3"
  ← 304 Not Modified          ← 沒有 body,幾百 bytes

只有內容真的變了才會回 200 帶新的 HTML。所以「每次都問」的成本遠低於直覺 —— 一次 RTT,不是一次下載。

ETag 由伺服器產生(通常是內容雜湊或 inode+mtime),大部分靜態伺服器預設就會帶。另一個等價機制是 Last-Modified + If-Modified-Since,精度到秒。

3-3. 建議策略​

路徑Cache-Control
/index.html、/(以及任何無 hash 的 HTML)no-cache
/assets/*(帶 hash 的 JS / CSS / 圖)public, max-age=31536000, immutable
/favicon.ico、/manifest.json、robots.txtpublic, max-age=3600(短一點,它們沒有 hash)
API 回應由 API 自己決定,通常 no-store 或短 max-age

3-4. 各家伺服器的寫法​

Caddy

example.com {
    root * /var/www/app
    file_server
    try_files {path} /index.html

    # 帶 hash 的資源:永久快取
    @assets path /assets/*
    header @assets Cache-Control "public, max-age=31536000, immutable"

    # 入口 HTML:每次確認
    @html path / /index.html
    header @html Cache-Control "no-cache"
}

Nginx

server {
    root /var/www/app;

    location /assets/ {
        add_header Cache-Control "public, max-age=31536000, immutable";
    }

    location = /index.html {
        add_header Cache-Control "no-cache";
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}

⚠️ Nginx 的 add_header 在同一個 location 裡只要出現一次,父層的 add_header 就全部失效。 如果外層設了別的標頭(例如安全標頭),內層又加了 add_header Cache-Control,外層那些會整組消失。要嘛每層都重寫一遍,要嘛改用 always 搭配 map。這是 Nginx 最惡名昭彰的陷阱之一。

Apache

<Directory /var/www/app/assets>
    Header set Cache-Control "public, max-age=31536000, immutable"
</Directory>

<Files "index.html">
    Header set Cache-Control "no-cache"
</Files>

# SPA fallback
FallbackResource /index.html

S3 + CloudFront

上傳時就把標頭寫進物件的 metadata:

# 資源:永久
aws s3 sync dist/assets/ s3://my-bucket/assets/ \
  --cache-control "public, max-age=31536000, immutable"

# 入口:每次確認(最後傳,見第 4 章)
aws s3 cp dist/index.html s3://my-bucket/index.html \
  --cache-control "no-cache"

CloudFront 還有自己的邊緣快取。改了 index.html 之後要讓邊緣節點失效:

aws cloudfront create-invalidation --distribution-id ABC123 --paths "/index.html" "/"

只失效 /index.html 就好,不要用 /* —— 帶 hash 的資源本來就不需要失效,而 invalidation 是按路徑計費的。

4. 部署的原子性​

4-1. 順序錯了會有一段「壞掉的視窗」​

假設你用 rsync 或 s3 sync 一次把 dist/ 整包丟上去,而檔案是逐一傳的。若 index.html 剛好先傳完:

t0  index.html 已更新 → 指向 index-新hash.js
t1  index-新hash.js 還在上傳中
    ↑ 這段時間進站的使用者:HTML 拿到新的,JS 404,整頁白畫面

規則:先傳資源,最後才傳入口 HTML。

# 1. 先傳所有帶 hash 的資源(新舊並存,互不干擾)
rsync -a dist/assets/ user@host:/var/www/app/assets/

# 2. 確認都上去了,最後才換指路的那一份
rsync -a dist/index.html user@host:/var/www/app/index.html

S3 同理:先 sync assets/,再 cp index.html。

4-2. 不要急著刪舊資源​

已經開著頁面的使用者,手上那份 index.html 還指向舊 hash。你若在部署時用 --delete 把舊資源清掉:

  • 他們已經載入的程式碼不受影響(在記憶體裡)
  • 但延遲載入的 chunk(路由切換、動態 import)會 404 → 點某個頁面就爆掉
# 危險:舊分頁的 lazy chunk 會立刻 404
rsync -a --delete dist/ user@host:/var/www/app/

比較安全的作法:

  • 保留 N 個版本的資源不刪,定期(例如一週後)再清
  • 或用版本化目錄 + symlink 切換(見下)

4-3. symlink 切換法(真正的原子部署)​

# 每次部署放進獨立目錄
releases/
├── 20240801-a1b2c3/
├── 20240805-d4e5f6/
└── 20240807-g7h8i9/     ← 剛上傳的

# 全部傳完之後,一個指令切換(rename 是原子操作)
ln -sfn /var/www/releases/20240807-g7h8i9 /var/www/current.new
mv -Tf /var/www/current.new /var/www/current

mv -T 對 symlink 的替換在同一檔案系統上是原子的 —— 不存在「切到一半」的狀態。回滾也只是把 symlink 指回上一個目錄。

伺服器的 root 要指向 /var/www/current。注意 Nginx 預設會快取 symlink 解析結果,切換後可能要 nginx -s reload;Caddy 沒有這個問題。

4-4. 前端 build 不要把後端網址寫死​

// 不好:網域寫死在 bundle 裡,換環境就要重 build
const API = 'https://api.example.com'

// 較好:走相對路徑,由反向代理決定後端在哪
const API = '/api'

走相對路徑的好處是同源:不需要 CORS、不需要為每個環境產生不同的 build、同一份 dist/ 可以部署到任何環境。反向代理只要多一段:

example.com {
    handle /api/* {
        reverse_proxy localhost:8080
    }
    root * /var/www/app
    file_server
    try_files {path} /index.html
}

如果非得在 build 時決定(例如前後端在不同網域),記得每個環境都要各自 build,而且部署腳本要驗證 bundle 裡的網址是對的:

grep -o 'https://[a-z.]*\.example\.com' dist/assets/*.js | sort -u

5. SPA 的 fallback​

5-1. 為什麼需要​

SPA 的路由是前端做的。使用者直接輸入 https://example.com/settings/profile 時,伺服器上並沒有 settings/profile 這個檔案 → 404。

所以要設「找不到檔案就回 index.html」,讓前端路由接手:

try_files $uri $uri/ /index.html;
try_files {path} /index.html

5-2. 最常見的錯誤:fallback 把 API 也吞掉​

# 錯誤示範
example.com {
    root * /var/www/app
    try_files {path} /index.html      # ← 這條在前面
    handle /api/* {
        reverse_proxy localhost:8080
    }
}

打 /api/xxx 時若後端回 404,fallback 會把它變成回傳 index.html 而且狀態碼 200。前端拿到一坨 HTML 去 JSON.parse,錯誤訊息會是:

SyntaxError: Unexpected token '<', "<!doctype "... is not valid JSON

看到這個訊息,九成是 SPA fallback 把 API 路徑吃掉了,不是後端壞了。把 API 的 handle 放在 fallback 之前就解決。

5-3. fallback 也不要吞掉真正的靜態 404​

圖片、字型打錯路徑時,你會希望它是 404 而不是一份 HTML。可以只對「看起來像路由」的路徑做 fallback:

location / {
    try_files $uri $uri/ @spa;
}

location @spa {
    # 有副檔名的當作靜態檔,不 fallback
    if ($uri ~* \.\w+$) { return 404; }
    rewrite ^ /index.html last;
}

6. Service Worker:更黏的一層​

如果專案裝了 PWA 外掛(vite-plugin-pwa、workbox),那還有第三層快取,而且它比 HTTP 快取黏得多 —— 它會在使用者離線時也回傳舊內容,這正是它的功能。

6-1. 更新流程​

1. 使用者進站,舊 SW 立刻接管(回傳快取內容)
2. 瀏覽器在背景抓新的 sw.js
3. 發現有變 → 安裝新 SW → 進入 waiting 狀態
4. 舊分頁全部關掉之後,新 SW 才 activate

第 4 步是關鍵:只重新整理是不夠的,因為分頁沒有真的關閉。這就是「我重整很多次還是舊版」的另一個成因。

6-2. 要不要 skipWaiting​

// 立刻接管,不等舊分頁關閉
self.addEventListener('install', () => self.skipWaiting())
self.addEventListener('activate', (e) => e.waitUntil(clients.claim()))

代價是:使用者正在操作的頁面,底下的資源版本會中途被換掉。已載入的 JS 不受影響,但之後動態載入的 chunk 會來自新版本 —— 兩個版本的程式碼混在同一個分頁裡跑。

比較穩的作法是偵測到新版就提示使用者,由他決定何時重載:

import { registerSW } from 'virtual:pwa-register'

const updateSW = registerSW({
  onNeedRefresh() {
    // 顯示「有新版本,要重新載入嗎?」的提示
    if (confirm('有新版本,要重新載入嗎?')) updateSW(true)
  },
})

6-3. sw.js 本身千萬不要長快取​

Cache-Control: no-cache

sw.js 被快取住的話,新的 Service Worker 永遠不會被發現,上面整套更新流程都不會啟動。這是 PWA 最致命的設定錯誤 —— 而且症狀是「怎麼部署都沒用」,非常難查。

7. 驗證清單​

部署完之後,照順序確認。每一步都是在區分「是誰的問題」:

# 1. 伺服器上的 index.html 指向哪個 hash?
curl -s https://example.com/ | grep -o 'index-[A-Za-z0-9_-]*\.js'
#    → 跟本機 dist/assets/ 比對。不一致 = 檔案沒上去

# 2. 那個資源檔真的存在嗎?
curl -sI https://example.com/assets/index-4f8a1c2b.js | head -1
#    → 404 = 部署順序錯了(HTML 先上、資源沒上)

# 3. 標頭對不對?
curl -sI https://example.com/ | grep -i cache-control
#    → 應該是 no-cache
curl -sI https://example.com/assets/index-4f8a1c2b.js | grep -i cache-control
#    → 應該是 max-age=31536000, immutable

# 4. 新的內容真的在 bundle 裡嗎?
curl -s https://example.com/assets/index-4f8a1c2b.js | grep -c '你這次加的某個字串'

瀏覽器端:

  • 硬重新整理(Cmd/Ctrl + Shift + R)—— 略過快取重抓
  • 無痕視窗 —— 排除所有既有快取與 Service Worker
  • DevTools → Network → 勾 Disable cache
  • DevTools → Application → Service Workers → Unregister

8. 症狀對照表​

症狀最可能的原因往哪裡查
部署了但看到舊版,硬重整就好了index.html 被快取第 2、3 章
硬重整也沒用,關掉分頁重開才好Service Worker 還沒 activate第 6 章
怎樣都是舊版,連無痕也是檔案根本沒上去 / CDN 邊緣沒失效第 7 章第 1 步、第 3-4 章
部署當下有幾秒白畫面先傳了 HTML、資源還沒傳完第 4-1 章
舊分頁點某個頁面就爆 chunk 404部署時 --delete 清掉了舊資源第 4-2 章
Unexpected token '<' ... is not valid JSONSPA fallback 把 API 路徑吞了第 5-2 章
每次部署使用者都要重下載全部資源用了 [hash] 不是 [contenthash]第 1-1 章
設了 Cache-Control 但沒生效(Nginx)add_header 覆蓋了父層第 3-4 章

9. 一頁總結​

帶 hash 的資源   →  Cache-Control: public, max-age=31536000, immutable
index.html      →  Cache-Control: no-cache
sw.js           →  Cache-Control: no-cache
部署順序         →  先傳資源,最後換 index.html
清舊資源         →  延後幾天,別在部署當下 --delete
SPA fallback    →  放在 API 路由之後
驗證             →  比對線上 index.html 指向的 hash 與本機 build 的 hash

把這幾條做對,「部署了卻看到舊版」這個問題就不會再出現;真的出現時,第 8 章的對照表也能在一兩分鐘內定位到是哪一層。
