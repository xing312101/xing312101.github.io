定時排程：從 cron 到 AI agent

「每天半夜把過期的資料收起來」「每月 1 號開這個月的工作單」「每週一早上寄報表」—— 這類事情看起來都要排程，但其實分成兩種：

  • 只是狀態會隨時間改變：例如「完成超過兩個月就算封存」。這種不一定需要排程，查詢時照日期算就好。
  • 時間到了要真的做一件事：建資料、寄信、呼叫外部 API。這種才真的需要有東西在那個時間去執行。

本文先講怎麼判斷，再講三種傳統做法（cron、systemd timer、應用程式內排程）與寫排程工作的原則， 最後說明用 LLM 與 AI agent 排程是怎麼一回事、什麼時候適合。

1. 先問：真的需要排程嗎？​

需求做法理由
「超過 N 天的算過期／封存」查詢時照日期算（WHERE created_at < :cutoff）不用排程、不會漏跑；時間一到自己就成立
「每月 1 號開這個月的單」排程要在資料庫建出東西，總要有東西在那個時間去做
「每天寄前一天的報表」排程對外的動作，時間到了才做
「某件事做完，接著開下一件」事件觸發（在「做完」的程式裡直接處理）比排程即時；排程只當補漏
tip

能照時間算的就不要排程。排程多一個「沒跑到」的失敗模式，而照時間算的邏輯在每次查詢時都會成立。 真的要排程時，也盡量讓排程只負責「時間到了觸發」，規則本身寫在應用程式裡，才測得到。

照時間算的例子（PostgreSQL／MySQL 都適用）：

-- 「完成、而且是上個月以前的」就算封存，不需要任何排程去改狀態
SELECT * FROM jobs
WHERE NOT (completed_at IS NOT NULL AND period_month < :first_day_of_last_month);

2. 三種傳統做法對照​

cronsystemd timer應用程式內排程（APScheduler、node-cron、Celery beat⋯）
設定一行兩個檔（.service ＋ .timer）寫在程式裡
主機那時候沒開錯過就沒了Persistent=true 開機後補跑程式沒在跑就沒了
執行紀錄預設沒有，要自己導到檔案自動進 journal跟應用程式的 log 一起
上次／下次執行時間要自己翻systemctl list-timers看實作
同時跑兩次會疊，要自己加鎖上一次沒跑完不會再起一個多個 worker 時每個都會跑
時區主機時區（部分實作支援 CRON_TZ）OnCalendar 可以直接寫時區看實作
適合簡單、單機、不在意漏跑Linux 主機上的正式工作開發方便、單一行程的服務

雲端與容器環境也有對應的東西：Kubernetes 的 CronJob、各家雲的排程服務（例如 Cloud Scheduler、EventBridge Scheduler）、 CI 的排程（例如 GitHub Actions 的 schedule）。原理相同，下面的原則一樣適用。

warning

GitHub Actions 的 schedule 一律照 UTC、尖峰時段可能延遲很久才跑， 公開 repo 長時間沒有活動時排程還會被停用。拿來跑「一定要準時」的工作要特別小心。

3. cron​

3.1 基本寫法​

# 分 時 日 月 星期  指令
10 16 * * * cd /srv/app && ./venv/bin/python scripts/daily_job.py >> /var/log/app/daily_job.log 2>&1
欄位範圍例子
分0–5910
時0–2316（主機是 UTC 時，等於 UTC+8 的 00:10）
日1–311＝每月 1 號
月1–12*＝每月
星期0–7（0 和 7 都是星期日）1＝星期一

3.2 常見的坑​

坑症狀解法
環境變數很少手動跑得動，cron 跑不動（找不到指令、找不到套件）指令、虛擬環境都寫完整路徑；需要的環境變數在腳本裡讀設定檔
沒有 log失敗了沒人知道>> 檔案 2>&1 導出去，並且設定 log 輪替
時區時間差了 8 小時先 date 確認主機時區；Debian／Ubuntu 預設的 cron 不一定支援 CRON_TZ，最保險是自己換算
上一次還沒跑完兩個一起跑、重複處理用 flock -n /tmp/daily_job.lock <指令> 包起來
主機那時候關機那天漏跑cron 不補；需要補跑就改用 systemd timer 或 anacron

4. systemd timer​

在用 systemd 的 Linux 上，timer 是比較好維護的選擇：紀錄、補跑、手動觸發都內建。

4.1 設定檔​

/etc/systemd/system/daily-job.service：

[Unit]
Description=Daily job

[Service]
Type=oneshot
User=app
WorkingDirectory=/srv/app
ExecStart=/srv/app/venv/bin/python scripts/daily_job.py

/etc/systemd/system/daily-job.timer：

[Unit]
Description=Run daily job at 00:10 (UTC+8)

[Timer]
OnCalendar=*-*-* 00:10:00 Asia/Taipei
# 主機在那個時間沒開的話，開機後補跑一次
Persistent=true
# 多台主機同時跑時錯開，避免同一秒打爆資料庫
RandomizedDelaySec=60

[Install]
WantedBy=timers.target
note

OnCalendar 後面直接寫時區需要較新的 systemd。先用下面的指令確認你寫的時間被解讀成什麼：

systemd-analyze calendar '*-*-* 00:10:00 Asia/Taipei'

不支援的話，改寫成主機時區的時間（例如主機是 UTC 就寫 *-*-* 16:10:00）。

4.2 啟用與日常操作​

sudo systemctl daemon-reload
sudo systemctl enable --now daily-job.timer   # 啟用排程（不是 .service）

systemctl list-timers daily-job.timer         # 上次、下次什麼時候跑
sudo systemctl start daily-job.service        # 手動跑一次，環境跟排程跑的完全一樣
journalctl -u daily-job.service -n 100        # 看最近的輸出
journalctl -u daily-job.service --since today # 看今天跑了什麼
tip

Type=oneshot 的服務還在執行時，timer 不會再起一個，所以不用自己加鎖。

5. 應用程式內排程​

在 Web 應用程式裡直接用排程套件（Python 的 APScheduler、Node.js 的 node-cron 等）最方便，但要注意：

問題說明解法
多個 worker 會各跑一次用 gunicorn／uvicorn 開多個 worker、或開多台機器時，每個行程都有自己的排程器只在一個行程啟動排程；或用資料庫鎖、Redis 鎖決定誰執行
重啟時剛好錯過部署重啟那幾秒剛好是排程時間搭配「啟動時檢查有沒有漏跑」，或改用外部排程
跟請求搶資源排程工作佔住 CPU、資料庫連線，影響使用者重的工作丟到 worker 佇列

規模一大，通常會改成「外部排程觸發 ＋ 應用程式裡的函式做事」：排程只負責時間到了叫一支 API 或腳本。

6. 寫排程工作的原則​

不管用哪一種排程，工作本身都要做到這幾件事：

原則為什麼做法
冪等（重跑不會重複做）補跑、手動重跑、兩個排程器同時跑都會發生資料庫加唯一索引（例如「同一個對象、同一期、同一次」只能一筆），撞到就當作已經做過
能試跑上線前、改規則前，要先看「會做什麼」提供 --dry-run：照真的規則算，最後 rollback 不寫入
能補漏排程跑的那一刻可能剛好失敗每次執行都檢查「該做而還沒做的」，而不是只做「今天這一筆」
時區明確主機多半是 UTC，業務日期是當地時間系統時間存 UTC；「今天」「這個月」用業務時區算
失敗要有人知道排程失敗通常是靜悄悄的失敗、部分失敗都要發通知；講清楚是哪一筆、為什麼（見第 7 節）
沒跑也要有人知道排程整個沒啟動時，不會有任何錯誤監控「最後一次成功的時間」，太久沒更新就告警（dead man's switch，見 7.4）
規則放在應用程式裡規則寫在 shell 腳本裡就測不到腳本只是入口，呼叫應用程式裡的函式；規則寫單元測試

一個排程腳本的骨架（Python）：

"""每天跑一次。重跑不會重複做。

    python scripts/daily_job.py            # 真的做
    python scripts/daily_job.py --dry-run  # 只印會做什麼
"""
import argparse

from app.db import SessionLocal
from app.jobs import run_daily  # 規則寫在應用程式裡，才測得到


def main() -> int:
    ap = argparse.ArgumentParser()
    ap.add_argument("--dry-run", action="store_true")
    args = ap.parse_args()
    with SessionLocal() as db:
        report = run_daily(db)  # 回報：做了哪些、哪些失敗、為什麼
        lines = report.summary_lines()  # rollback 之前先整理好要印的
        if args.dry_run:
            db.rollback()
        else:
            db.commit()
            report.notify_if_any_failed()
    print("\n".join(lines))
    return 1 if report.failed else 0  # 失敗回非 0，systemd／cron 的紀錄看得出來


if __name__ == "__main__":
    raise SystemExit(main())

7. 排程出問題時：怎麼發現、怎麼通知、怎麼處理​

排程最麻煩的地方是壞了通常不會出聲。沒有人在看的時候它沒跑、跑到一半當掉、或跑完了但做錯， 結果都一樣：要等到有人說「這個月的單怎麼沒開」才發現。這一節講怎麼讓它出聲。

7.1 失敗有哪幾種​

種類常見原因症狀為什麼不會自己報錯怎麼發現
根本沒觸發timer 沒裝或沒 enable、主機關機、cron 服務沒跑、時區算錯、部署時被覆蓋掉該有的資料沒出現程式從頭到尾沒被執行，沒有任何東西可以丟例外「最後一次成功的時間」太久沒更新（7.4）
觸發了但當掉未處理的例外、資料庫連不上、檔案權限、套件版本不合只做了一部分，或完全沒做錯誤只留在主機的紀錄裡，沒人會去看exit code 非 0、OnFailure=、腳本自己包 try/except 發通知（7.3）
跑完了但部分失敗某幾筆資料不完整、外部服務逾時、某個對象設定錯大部分做了，少數幾筆沒做整體看起來是成功的回報「哪幾筆、為什麼」，失敗清單當通知送出
跑完了但結果不對規則寫錯、時區錯一天、拿不到指定的設定就靜靜改用預設資料出現了，但內容是錯的從程式的角度看一切正常測試、--dry-run 先看會做什麼、抽查；寧可報錯也不要靜靜走錯
跑太久、重疊資料量變大、等外部服務、鎖等待下一輪開始時上一輪還沒結束，重複處理或互相卡住每一輪單獨看都沒錯記開始與結束時間；cron 用 flock，systemd 的 oneshot 本來就不會重疊
warning

「沒觸發」是最危險的一種：其他幾種至少還有程式在跑、有機會報錯；沒觸發就是一片安靜。 監控一定要能抓到「什麼事都沒發生」，只監控錯誤訊息是抓不到的。

7.2 怎麼判斷排程失效​

先看排程器本身（systemd timer）：

systemctl list-timers daily-job.timer      # LAST 是上次觸發、NEXT 是下次；LAST 是 n/a 代表從來沒跑過
systemctl status daily-job.timer           # timer 有沒有 enable、是不是 active (waiting)
systemctl status daily-job.service         # 上一次跑的結果：status=0/SUCCESS 或 status=1/FAILURE
journalctl -u daily-job.service --since "2 days ago"   # 最近兩天的輸出與錯誤

cron：

grep CRON /var/log/syslog | tail -20       # Debian／Ubuntu；有些發行版要用 journalctl
journalctl -u cron --since today           # 服務名稱可能是 cron 或 crond

光看主機的紀錄有兩個問題：要有人登入主機去看，而且只知道「有沒有觸發」，不知道「做的事有沒有成功」。 所以應用程式自己也要記，一個排程一列：

欄位用途
last_started_at最後一次開始。開始了卻沒有對應的成功 → 跑到一半掛了
last_success_at最後一次成功跑完。監控看這一欄
last_error_at／last_error最後一次失敗的時間與錯誤訊息（最後一行就好）

再開一支健康檢查的 API（例如 GET /health/jobs），回傳每個排程「多久沒成功」，外部監控或後台頁面都可以用：

daily-job: last_success 2026-01-15 00:10 (+08:00), 9 小時前, ok
weekly-report: last_success 2026-01-05 07:00 (+08:00), 10 天前, STALE

7.3 失敗時要通知​

情況做法
腳本自己當掉主程式包 try/except：記錯誤、發通知、回非 0 的 exit code。發通知要用新的連線 —— 原本那條可能就是壞掉的原因
腳本連通知都發不出去（資料庫整個掛了）靠排程器：systemd 的 OnFailure=、cron 的 MAILTO
部分失敗通知裡講清楚哪一筆、為什麼、去哪裡改，不要只說「有 3 筆失敗」

systemd 的 OnFailure=：服務失敗時自動啟動另一個 unit 去發通知。

# /etc/systemd/system/daily-job.service
[Unit]
Description=Daily job
OnFailure=notify-failure@%n.service

[Service]
Type=oneshot
ExecStart=/srv/app/venv/bin/python scripts/daily_job.py
# /etc/systemd/system/notify-failure@.service
[Unit]
Description=Notify failure of %i

[Service]
Type=oneshot
# %i 是失敗的那個 unit 名稱；腳本裡打你的通知管道（信、聊天 webhook）
ExecStart=/usr/local/bin/notify-failure.sh %i

cron 則是在 crontab 最上面設 MAILTO=ops@example.com，指令有任何輸出就寄信（主機要能寄信）。

同一個原因只通知一次。 天天出現的同一則通知，幾天之後就沒人看了，真正的新問題會被淹掉：

  • 每一輪把失敗清單記下來（對象 → 原因）
  • 下一輪只通知「上一輪沒有、或原因變了」的那幾筆
  • 已經好了的從清單消失；之後又壞，會再通知一次

不該通知的： 本來就不該做的事不是失敗。例如合約已經到期的客戶不開工作單 —— 這個狀態在客戶清單上已經標著， 每天再通知「開不成」只是噪音。通知只留給「該做卻做不成」的事。

tip

通知的內容要讓收到的人不用登入主機也知道下一步：哪個排程、哪一筆、為什麼、去哪裡改。 「daily-job failed」這種訊息，收到的人只能再去找寫程式的人問。

7.4 「沒跑」要怎麼通知：dead man's switch​

排程死了就沒辦法自己報，所以要反過來：由別的東西定期確認「它最近有成功過」，太久沒有就告警。 這種做法叫 dead man's switch。

做法 A：外部心跳服務。 排程成功跑完時打一個網址，服務那邊超過約定時間沒收到就通知你。 Healthchecks.io、Cronitor、Better Stack 這類服務都有，也有可以自架的開源版本。

# 成功跑完才打；失敗時打 /fail，服務那邊會馬上告警
/srv/app/venv/bin/python scripts/daily_job.py \
  && curl -fsS -m 10 --retry 3 https://hc-ping.example.com/your-check-uuid \
  || curl -fsS -m 10 --retry 3 https://hc-ping.example.com/your-check-uuid/fail

做法 B：應用程式裡被動檢查。 不另外架服務，把檢查掛在使用者常打的 API 上（例如每個人一登入就會載入的通知清單）， 發現「週期＋寬限時間」內都沒成功過，就發一則通知。要注意三件事：

  1. 節流：不要每次請求都查，例如每個行程十分鐘查一次
  2. 同一段沒跑只講一次：記下「通知過了」的時間，排程恢復成功之後再停才再講
  3. 新環境不要誤報：剛設定好、還沒到第一次執行時間，「從來沒成功過」是正常的。記一個「開始監看的時間」，從那時候起算
from datetime import datetime, timedelta

PERIOD = timedelta(days=1)
GRACE = timedelta(hours=2)  # 主機晚一點跑不算沒跑


def check_stale(db, job_name: str, now: datetime | None = None) -> bool:
    """太久沒成功就通知一次。回有沒有發通知。"""
    now = now or datetime.utcnow()
    run = db.get_job_run(job_name)            # job_run 表的那一列，沒有就建一列
    if run.watched_since is None:             # 第一次看到：從現在起算，不要馬上喊沒跑
        run.watched_since = now
        db.commit()
    since = run.last_success_at or run.watched_since
    if now - since <= PERIOD + GRACE:
        return False
    if run.stale_notified_at and run.stale_notified_at > since:
        return False                          # 這一段沒跑已經講過了
    hours = int((now - since).total_seconds() // 3600)
    notify_admins(
        f"{job_name} 已經 {hours} 小時沒有成功跑完。"
        f"最近一次錯誤：{run.last_error or '（沒有紀錄，可能根本沒觸發）'}"
    )
    run.stale_notified_at = now
    db.commit()
    return True
外部心跳服務應用程式內被動檢查
主機整台掛了抓得到抓不到（應用程式也掛了）
要多架或多付費的東西要不用
通知送到哪服務支援的管道（信、聊天、簡訊）你自己的通知系統，跟其他業務通知在一起
沒人使用系統時照樣會告警沒人打 API 就沒人檢查

兩種可以並用：外部服務抓「整台掛了」，應用程式內的檢查抓「主機好好的但排程沒跑」。

7.5 監控本身也會失效​

監控也是一個會壞的系統，而且它壞的時候同樣不會出聲：

監控怎麼失效例子對策
通知管道壞了信箱滿了、聊天 webhook 的金鑰過期、收件人離職定期發測試通知；用兩條不同的管道
心跳服務自己掛了，或帳號過期免費方案到期、檢查被誤刪每週摘要（見下）；服務本身也開告警
被動檢查掛在沒人打的 API 上假日沒人登入、那支 API 改版不再被呼叫掛在最常用的地方；搭配外部服務
告警太多被靜音同一則每天出現、大家設成已讀去重（7.3）；只通知要處理的事
寬限時間設太長每天跑的排程設了七天寬限寬限跟著週期走：每天跑的抓一兩個小時就好
tip

每週送一份摘要：「本週 daily-job 跑了 7 次、成功 7 次、通知 2 則」。 摘要照常收到，代表排程、監控、通知管道都還活著；哪一週沒收到摘要，本身就是警訊。

danger

監控要演練才知道會不會響：故意停掉 timer（systemctl stop daily-job.timer）， 等過了寬限時間，確認真的收到通知，再恢復。沒演練過的監控，等於沒有監控。

7.6 出問題時的處理流程​

步驟做什麼指令或重點
1. 止血結果會繼續做錯的話，先暫停排程sudo systemctl stop daily-job.timer；要跨過重開機就再 disable
2. 找原因看紀錄與應用程式記的錯誤journalctl -u daily-job.service --since "3 days ago"、last_error
3. 修好之後先試跑照真的規則算一次，不寫入python scripts/daily_job.py --dry-run，確認「會做什麼」跟預期一樣
4. 手動跑一次用排程器跑，環境才跟平常一樣sudo systemctl start daily-job.service，再看 systemctl status 與紀錄
5. 補漏工作是冪等、會補漏的話，重跑是安全的漏掉的那段要不要補由人決定：一次補一大段可能會發出一大批通知、建出一大批資料，先 --dry-run 看量
6. 恢復排程把 timer 打開，確認下一次時間對sudo systemctl enable --now daily-job.timer、systemctl list-timers
7. 事後檢討為什麼壞、為什麼這麼久才發現「為什麼這麼久才發現」常常比「為什麼壞」更值得改
warning

補漏不要寫成全自動。排程停了一個月，恢復時自動補開一個月份的資料、推一個月份的通知， 收到的人只會覺得系統壞了。程式負責列出漏了什麼，要不要補、補哪些由人決定。

7.7 小結​

要抓的狀況用什麼
排程有沒有觸發systemctl list-timers、journalctl、cron 的 syslog
跑完有沒有成功應用程式記 last_success_at；健康檢查 API
當掉腳本 try/except 發通知、非 0 exit code、OnFailure=、MAILTO
部分失敗通知講清楚哪一筆、為什麼；同一個原因只講一次
根本沒跑dead man's switch：外部心跳服務，或應用程式內被動檢查
監控自己壞了每週摘要、兩條通知管道、定期演練
出事時止血 → 找原因 → 試跑 → 手動跑 → 人決定要不要補 → 恢復 → 檢討

8. 用 LLM／AI agent 排程​

8.1 跟傳統排程差在哪​

傳統排程AI 排程
時間到了做什麼跑一支寫死的程式叫一個 LLM／agent，給它一段指示和一組工具，讓它自己判斷要做什麼
結果同樣的輸入，同樣的結果每次可能不一樣
擅長規則明確的事：建資料、搬資料、算數字要「讀懂」的事：整理信件、摘要報表、判斷異常是否要緊
成本幾乎是零每次執行都是一次（或多次）模型呼叫
出錯時看 log、重跑要看它「為什麼這樣判斷」，而且重跑不一定一樣

要注意的是，AI 排程底下仍然是一個傳統排程器：時間到了由排程器觸發，差別只在觸發之後執行的是 agent，不是固定的程式。

8.2 三種常見做法​

做法怎麼運作適合
傳統排程 ＋ 呼叫 LLM APIcron／systemd timer 跑一支腳本，腳本裡呼叫 LLM API 做其中一步（摘要、分類）已經有排程、只想在某一步加上「讀懂」的能力
個人 AI agent 的排程（如 OpenClaw「小龍蝦」、Hermes Agent）agent 常駐在你的電腦或伺服器，內建排程，時間到了自己醒來做事、透過聊天軟體通知你個人助理型的工作：提醒、追蹤、整理資訊
雲端 agent 平台的排程在平台上定義好 agent 與排程（cron 表示式 ＋ 時區），平台定時開一個 session 執行不想自己維護主機、需要隔離的執行環境

8.3 傳統排程 ＋ 呼叫 LLM API​

最容易控制的做法：排程與資料的讀寫都是確定性的程式，只有「判讀」那一步交給模型。 例如每天早上把前一天的錯誤紀錄交給模型摘要，再寄給值班的人：

"""每天 08:00 跑：把昨天的錯誤紀錄摘要成給值班看的重點。

LLM 只做「讀懂、摘要」；撈資料、寄信都是確定性的程式。
"""
import anthropic

from app.logs import errors_of_yesterday
from app.notify import send_to_oncall

client = anthropic.Anthropic()  # 從環境變數讀 ANTHROPIC_API_KEY


def main() -> int:
    errors = errors_of_yesterday()
    if not errors:
        return 0  # 沒有錯誤就不用叫模型，省一次呼叫

    response = client.beta.messages.create(
        model="claude-opus-5-5",
        max_tokens=4000,
        output_config={"effort": "low"},  # 摘要不需要深度推理
        # 模型因安全規則拒答時，由 API 自動改用建議的備援模型重跑
        betas=["server-side-fallback-2026-07-01"],
        fallbacks="default",
        system="你是值班助理。把錯誤紀錄整理成 5 點以內的重點：哪些服務、影響範圍、是否需要立刻處理。",
        messages=[{"role": "user", "content": "\n".join(errors)}],
    )
    if response.stop_reason == "refusal":
        send_to_oncall("昨天的錯誤摘要沒有產生（模型拒答），請直接看原始紀錄。")
        return 1

    summary = "".join(b.text for b in response.content if b.type == "text")
    send_to_oncall(summary)
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
note

模型名稱、參數會隨版本變動，實際使用前請對照模型供應商的最新文件。

8.4 個人 AI agent 的排程：以 OpenClaw（小龍蝦）為例​

OpenClaw 是一個開源、自架的個人 AI agent（中文社群常叫它「小龍蝦」）。 它有兩種讓 agent 「自己動起來」的機制：

Heartbeat（心跳）Cron（排程工作）
時間大約每隔一段時間醒來一次（預設 30 分鐘）精確時間：一次性、固定間隔、或 cron 表示式
在哪裡跑主要的 session，看得到先前的對話脈絡預設開一個全新的隔離 session
做什麼照一份檢查清單看看有沒有事要處理；沒事就安靜回報「一切正常」，有事才通知你在指定時間做一件指定的事
適合「有變化再告訴我」：監看信箱、追蹤待辦、注意異常「九點整做這件事」：晨報、定時提醒、週報
其他可以限定活躍時段，時段外不打擾結果可以送到聊天頻道、webhook，或只留在內部

社群常見的搭配是：heartbeat 每 30–60 分鐘負責「監看、抓異常」，cron 每天兩三個固定時間點負責「一定要準時做的事」。

warning

heartbeat 每醒來一次就是一次模型呼叫，間隔設太短、清單寫太長，費用會累積得很快。 設定鍵名與指令在不同版本之間變動很快，請以 OpenClaw 官方文件 為準。

8.5 Hermes Agent 的排程​

Hermes Agent 是 Nous Research 做的開源（MIT）自架 agent， 定位跟 OpenClaw 很像：常駐在你的主機上，透過 Telegram、Discord、Slack 等聊天軟體跟你對話， 可以接不同供應商的模型。它的特色是會從做過的事情裡**自己整理出技能（skill）**下次重用， 也提供從 OpenClaw 匯入設定、記憶與技能的工具。

排程方面，Hermes 只有 cron 一套機制，沒有 OpenClaw 那種在主 session 裡的 heartbeat：

項目說明
怎麼觸發常駐的 gateway 每 60 秒檢查一次，有到期的工作就開一個全新的隔離 session 執行
時間寫法自然語言（every monday 9am）、cron 表示式（0 9 * * 1-5）、間隔（every 30m）、一次性（in 2h、ISO 時間）
怎麼建立直接跟它說「每天早上九點整理新聞傳給我」，或用指令
工作可以帶技能每個排程工作可以掛一到多個技能，執行前先載入
結果送到哪建立工作的那個對話、本機檔案、指定的聊天頻道，或同時送多個
不叫模型的模式--no-agent 只跑一支腳本，有輸出才通知、沒輸出就安靜、失敗就告警；完全不花 token
串接一個工作可以拿另一個工作的上一次輸出當脈絡（先「收集」、再「評分」）
漏跑gateway 停掉期間錯過的，重新啟動後補跑一次（可以關掉）
防失控排程執行中的 agent 預設不能再建排程，避免自己越排越多

指令的樣子（實際語法以官方文件為準）：

# 讓 agent 做：每兩小時檢查一次，結果送回原本的對話
hermes cron create "every 2h" "檢查 https://app.example.com 的狀態，異常才回報"

# 不叫模型：每 5 分鐘跑腳本，有輸出才推到 Telegram
hermes cron create "every 5m" --no-agent --script disk-watchdog.sh \
  --deliver telegram --name "disk-watchdog"

hermes cron list                 # 列出所有工作、下次執行時間、是否逾時沒跑
hermes cron run disk-watchdog    # 手動跑一次
hermes cron pause disk-watchdog  # 暫停

8.6 OpenClaw 與 Hermes Agent 的排程比較​

OpenClaw（小龍蝦）Hermes Agent
機制heartbeat ＋ cron 兩套只有 cron
「有事再告訴我」的監看heartbeat：在主 session 定期醒來，看得到先前的對話脈絡，照檢查清單判斷用間隔排程（例如 every 30m）做，但每次都是新的 session；需要延續要另外設定
精確時間的工作cron：隔離 sessioncron：隔離 session
不叫模型的排程沒有對應的模式，要另外用系統的 cron／systemd timer內建 --no-agent，腳本有輸出才通知
工作之間串接靠主 session 的脈絡或自己寫檔內建「拿另一個工作的輸出當脈絡」
費用的主要來源heartbeat 的頻率（每次醒來都是一次模型呼叫）排程的頻率；監看類的用 --no-agent 可以壓到零

簡單說：OpenClaw 的 heartbeat 比較像一個隨時在旁邊的助理，它記得你們聊過什麼，自己判斷要不要開口； Hermes 比較像一個排程器，每個工作都是獨立的一次執行，可預期、好追蹤， 而且把「判斷要不要叫模型」交給腳本，省錢的空間比較大。

tip

兩者的共同原則：能用腳本判斷的就不要叫模型。先用便宜的程式檢查「有沒有變化」，有變化才交給模型去讀懂與摘要。

8.7 雲端 agent 平台的排程​

部分 LLM 供應商的 agent 平台提供「排程部署」：先定義好 agent（模型、指示、工具、執行環境）， 再設一個 cron 表示式與時區，平台每次到點就開一個 session 執行，並留下每次執行的紀錄，可以暫停、恢復。 開發工具類的 agent（例如程式碼助理）也有類似的「定時在雲端跑一個 agent」功能。

好處是不用自己維護主機與排程器；代價是執行環境、權限、費用都在平台上，要另外管理。

9. 什麼時候該用 AI 排程​

工作建議理由
建立資料、扣款、對外承諾（開單、下訂、發票）傳統排程要確定、可測、可重跑；不能「這次判斷不一樣」
搬資料、清資料、產報表數字傳統排程規則明確，程式比模型便宜也可靠
摘要、分類、草稿（寫給人看的）傳統排程 ＋ LLM 那一步產出給人看，有一點不一致可以接受
監看非結構化資訊（信件、討論、新聞）並判斷要不要通知AI agent（OpenClaw 的 heartbeat，或 Hermes 的「腳本先篩、有變化才叫模型」）規則寫不完，需要「讀懂」
個人提醒、追蹤待辦AI agent 的 cron方便；錯了影響有限

最穩的組合是分工：確定性的排程負責「做事」，模型負責「判讀與寫給人看」， 模型的判斷如果會改到資料，先讓它產出建議，由程式驗證或由人核准後才執行。

9.1 AI 排程的安全與成本清單​

  • 權限最小化：agent 只拿得到這件工作需要的工具與資料；能唯讀就唯讀
  • 外部內容當資料，不當指令：信件、網頁、別人寫的文件裡可能藏著「指令」（prompt injection），不能讓它直接驅動有副作用的動作
  • 有副作用的動作要有閘門：寄信給客戶、改資料、付款前，要程式驗證或人核准
  • 費用上限：限制每次執行的長度、每天的執行次數；heartbeat 間隔別設太短
  • 留紀錄：每次執行的輸入、輸出、它呼叫了哪些工具都要能事後查
  • 冪等仍然要做：agent 一樣會被重跑，有副作用的動作照第 6 節做唯一鍵
  • 失敗與拒答要有出口：模型失敗、拒答、逾時，要有明確的通知，而不是靜悄悄沒產出

10. 小結​

情境選擇
狀態只是隨時間改變不排程，照時間算
某件事做完就要接著做事件觸發，排程只當補漏
Linux 主機上的正式工作systemd timer（Persistent=true）
簡單、單機、漏跑一次沒關係cron
容器、雲端Kubernetes CronJob、雲端排程服務
要「讀懂」非結構化資訊傳統排程 ＋ LLM 那一步，或 AI agent
有副作用、要可靠傳統排程；模型只產出建議
怕排程壞了沒人知道記最後一次成功時間＋dead man's switch＋失敗通知（第 7 節）
排程出事先停 timer，試跑確認，再手動跑、由人決定要不要補（7.6）
