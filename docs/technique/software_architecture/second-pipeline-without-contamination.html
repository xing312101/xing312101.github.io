同一個 repo 養兩個產品管線而不互相污染 — 架構決策與三層圍籬

情境：你有一個成熟的引擎產品（例：行為驗證驅動的「舊系統重寫」引擎）， 想開第二個近親產品（例：「舊系統重構」引擎）。兩者共用大量基建， 但核心語意有一條反轉的公理。本文回答三個依序出現的問題： 該不該延伸？延伸在哪個粒度？如何保證日後開發（尤其是 AI 輔助開發）不把兩邊攪渾？

適用對象：手上有一個成熟產品、想開近親的第二產品，而且日常會用 AI 助手（Claude Code 之類）改碼的人。 例子用 Rust 的 crate 講，換成 Go module、TypeScript workspace package 道理一樣。

1. 先分清楚：「底盤」與「上層建築」​

近親產品的複用判斷，第一步是把既有系統拆成兩類：

  • 底盤（chassis）：與產品語意無關的機器——行為捕捉、中間表示、重放與 diff 機構、決定性基建（content-addressed steps／快取／resume）、容器編排、 agent 迴圈的治理機制（judge≠writer、提案協定、防環護欄）。 特徵：換一個產品語意，這些一行都不用改。
  • 上層建築（superstructure）：實現某個產品公理的部分——規劃器、 生成骨架、判決規則、驗收標準。特徵：產品公理一變，這些整段重寫。

判斷延伸可行性的試金石：列出新產品需要的每個環節，逐一問「這是底盤還是上層建築」。 底盤佔比高（本例約七成）→ 延伸划算；佔比低 → 另起爐灶更誠實。

2. 為什麼「加一個模式旗標」是陷阱​

工程上最誘人的路是在既有管線加 mode: refactor——可行性看起來最高， 因為接縫都是現成的。但要警惕一種特殊情況：兩個產品的核心公理互為反轉。

本例中：重寫引擎的公理是「系統內部結構是設計自由，只驗外部行為」； 重構引擎的公理是「內部結構就是產品本身，必須保留」。同一條判決鏈若要 同時承載兩者，每一個判決點都要帶條件分支——這不是加幾個 if 的問題：

  1. 判決語意從「一套公理」變成「兩套公理共用一個法庭」，每個閘的正確性 都要對兩種模式分別論證；
  2. 安全關鍵路徑的測試矩陣直接 ×2，且未來每一件新機制都要永久多答一題 「另一個模式下適用嗎」；
  3. 規格文件被迫全篇織入條件句——若你的規格有「章節編號凍結」之類的 可稽核性紀律，模式化等於把它撕掉重寫。
判準一句話

底盤可以共用，公理不能共用。公理反轉的兩個產品 ＝ 兩條管線。

3. 正確的粒度：同 repo、第二條管線​

同一個 monorepo
├─ 共用 crates（底盤）：capture / IR / replay / diff / 決定性 / 容器 / 迴圈治理
│    └ 迴圈機制經 trait 注入複用（編譯閘、驗證器本就是注入的接縫）
├─ 管線 A（重寫）：自己的入口、自己的 step 鏈、自己的規格文件
└─ 管線 B（重構）：自己的入口（子命令）、自己的 step 鏈、自己的規格文件
     └ 跳過 A 特有的階段（重設計、資料遷移、生成骨架），換上自己的
       規劃器與更嚴格的驗收 oracle
口訣

repo 同、crates 共、入口分、spec 分、判決鏈永不共條件句。

兩條管線唯一的「法定交會點」設在資料層：同一份行為基準線 artifacts， 餵哪條管線都行——共享發生在產物層，永不發生在判決層。這同時是產品漏斗： 一次捕捉，兩個產品。

4. 三層圍籬：讓「不污染」不依賴任何人的紀律​

規則寫在文件裡會被忘記——人會忘，AI 開發助手在長 session 裡也會。 可靠的做法是把每條規則降級到「違反時機械性失敗」的層級，按強度分三層：

第一層：編譯期不可能（最強、零成本）​

利用語言的模組系統當圍籬。以 Rust 為例：沒在 Cargo.toml 宣告依賴， use 都寫不出來。規則只有一條方向律：

底盤 crates → 不依賴任何管線 crate
管線 crates → 互不宣告依賴

想「順手引用」對面管線的東西？編譯直接紅。這層免費，前提是開工第一天 就把 crate 邊界切對——圍籬先於房子。

第二層：測試紅燈（防手滑，一次寫永久生效）​

  1. 依賴圖斷言測試：讀建置系統的 metadata（如 cargo metadata）， 斷言方向律成立。誰改依賴宣告開了後門，CI 紅。約 30 行，永久站崗。
  2. 雙 oracle ＝ 兩個函式，不是一個函式帶旗標：兩種驗收標準各自獨立 入口，並互為反證測試——「A 的 oracle 必須忽略內部事件」與 「B 的 oracle 必須不忽略」各釘一測。誰想合併成 if mode，兩邊同時紅。
  3. 消費者契約測試：底盤的每個被依賴行為，兩條管線各自釘一份 自己的期望。底盤一改、哪條管線的語意被動搖，那條的測試立刻紅—— 污染從「靜默發生」變成「顯性失敗」。這是三層裡最值錢的一道。
  4. 毒詞絆線（便宜的縱深）：掃描底盤 crates 源碼，出現管線專屬的 概念詞即失敗——攔截依賴圖抓不到的「概念滲透」。
  5. 產物命名空間：管線 B 的步驟 ID 一律帶前綴——同一個產物目錄被 錯的管線接手時，結構上就對不起來。

第三層：session 語境（管開發助手的「認知」）​

  1. repo 級指引檔寫死邊界三律：依賴方向、「共用 crate 永不收模式參數」、 「哪份規格管哪些 crates」。所謂指引檔，就是每個 AI session 開場自動載入的那份—— Claude Code 的 CLAUDE.md、Cursor 的 rules、Copilot 的 copilot-instructions.md 之類；
  2. 規格頭部帶管轄清單（「本規格管 crates X/Y/Z」）——助手碰檔前 查規格，自然被引到對的法典；
  3. 跨界動作強制上浮：明文規定「一個變更看起來需要同時動兩條管線 ＝停下來問人」——因為那要嘛是底盤演化（該走共用 crate＋兩邊消費者 測試的正規路），要嘛是設計錯了。

5. 收束​

  • 該不該延伸？→ 該，從底盤延伸，不從上層建築延伸。
  • 同 repo 還是分開？→ 同 repo、第二條管線；分開的是公理和法庭， 共用的是地基和學費。
  • 怎麼保證不污染？→ 三層圍籬：編譯期讓「引用錯」寫不出來、測試層讓 「改壞了」立刻紅、語境層讓助手一開場就知道自己站在哪個法庭。 三層都不依賴任何人（或任何模型）記得規則——對機器紀律的正確態度， 是把它變成機器的問題。
