用 Firebase 做環境參數設定 & Cloud Functions 代理實作

公開教學。示範如何用 Firebase 管理「環境參數 / 開關 / 敏感設定」,以及如何用 Cloud Functions 把機敏帳密留在伺服器端不下發到 App。 適用對象:行動 App(Flutter / iOS / Android)或前端要跟後端拿設定、換 token 的情境。

0. 先搞懂一個觀念:什麼東西「可以」下發到 client​

在動手前,先分清楚兩種「參數」,做法完全不同:

類型例子可以下發到 App 嗎?建議做法
非機密設定功能開關、API base URL、版本公告、A/B 分組可以Remote Config / Firestore
機密憑證API 金鑰、Basic Auth 帳密、簽章私鑰不可以Cloud Functions(留伺服器端)

⚠️ 鐵律:任何會「下發到 App 端」的東西,都可能被反編譯或攔截流量挖出來。 Remote Config、Firestore 的值最終都會傳到裝置上,所以它們適合放「不怕被看到的設定」,不適合放真正的機密。 真機密請走 第 3 章 Cloud Functions。

1. Firebase Remote Config —— 環境參數 / 開關​

適合放:不怕被看到、但希望能不發版就改的設定。例如功能開關、公告文字、後端 URL、逾時秒數、A/B 測試分組。

好處:

  • 不寫死在原始碼(不進版控)
  • 不用重新送審 / 發版就能線上改值
  • 支援「條件式」下發(依 App 版本、地區、使用者群組給不同值)

1-1. 安裝套件(Flutter 範例）​

# pubspec.yaml
dependencies:
  firebase_core: ^3.6.0
  firebase_remote_config: ^5.1.3
flutter pub get

1-2. 初始化與讀取​

import 'package:firebase_core/firebase_core.dart';
import 'package:firebase_remote_config/firebase_remote_config.dart';

Future<FirebaseRemoteConfig> initRemoteConfig() async {
  final rc = FirebaseRemoteConfig.instance;

  await rc.setConfigSettings(RemoteConfigSettings(
    fetchTimeout: const Duration(seconds: 10),
    // 開發時可設短一點方便測；正式環境建議 1 小時以上避免超額
    minimumFetchInterval: const Duration(hours: 1),
  ));

  // 預設值:拿不到遠端值時的 fallback
  await rc.setDefaults(const {
    'api_base_url': 'https://api.example.com',
    'enable_new_ui': false,
    'request_timeout_seconds': 15,
  });

  await rc.fetchAndActivate();
  return rc;
}

讀值:

final rc = FirebaseRemoteConfig.instance;
final baseUrl = rc.getString('api_base_url');
final newUi   = rc.getBool('enable_new_ui');
final timeout = rc.getInt('request_timeout_seconds');

1-3. 在 Firebase Console 設定值​

  1. Firebase Console → Remote Config
  2. Add parameter,填 key(如 api_base_url)與 value
  3. (選)加 Conditions:例如 App version >= 2.0.0 才給新值,做灰度發布
  4. 按 Publish changes

1-4. 注意事項​

  • minimumFetchInterval 太短會被 Firebase 節流(throttle),正式版建議 ≥ 1 小時。
  • Remote Config 不是即時的:App 下次 fetch 才會拿到新值。
  • 一樣不要放機密。

2. Firestore 存 config —— 另一種環境參數做法​

如果專案已經在用 Cloud Firestore,可以直接開一份「設定文件」來存環境參數,不用另外裝 Remote Config。相較 Remote Config,好處是可以搭配 Security Rules 精細控制「誰能讀」。

適合放:跟 Remote Config 差不多的非機密設定,或需要更彈性讀寫規則的設定。

2-1. 資料結構範例​

config (collection)
  └─ app_settings (document)
       ├─ api_base_url: "https://api.example.com"
       ├─ enable_new_ui: false
       └─ maintenance_mode: false

2-2. 讀取(Flutter 範例)​

import 'package:cloud_firestore/cloud_firestore.dart';

Future<Map<String, dynamic>> loadAppConfig() async {
  final snap = await FirebaseFirestore.instance
      .collection('config')
      .doc('app_settings')
      .get();
  return snap.data() ?? {};
}

// 想即時同步就用 snapshots():
Stream<Map<String, dynamic>> watchAppConfig() {
  return FirebaseFirestore.instance
      .collection('config')
      .doc('app_settings')
      .snapshots()
      .map((s) => s.data() ?? {});
}

2-3. Security Rules —— 限制讀寫​

// firestore.rules
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // 設定檔:所有人可讀、禁止 client 寫(只能由後台/Console 改)
    match /config/{docId} {
      allow read: if true;
      allow write: if false;
    }

    // 若要「只有登入者能讀」,改成:
    // allow read: if request.auth != null;
  }
}

2-4. 重要提醒​

  • 就算加了 allow read: if request.auth != null,登入者(= App)還是拿得到值,所以 Firestore 一樣不適合放真機密。
  • Security Rules 只能擋「誰能透過 SDK 存取」,擋不了「已下發的值被看到」。

3. Cloud Functions —— 把機密留在伺服器端(推薦)​

這是唯一能真正保護機密的做法:機密(API 金鑰、Basic Auth 帳密…)只存在雲端,App 端永遠拿不到。

3-1. 概念圖​

❌ 危險(帳密在 App):
   App ──(帳密寫在 App 裡)──> 第三方服務

✅ 安全(帳密在雲端):
   App ──(用 Firebase 身分驗證)──> Cloud Function ──(帳密在雲端環境變數)──> 第三方服務

App 只知道「怎麼呼叫自己的 Cloud Function」,完全不知道機密長怎樣。

3-2. 前置準備​

Cloud Functions 是 Firebase 的服務(底層是 Google Cloud Functions)。第 2 代 Cloud Functions 需要 Blaze(按量計費)方案,但有免費額度(見第 4 章)。

npm install -g firebase-tools
firebase login
firebase init functions   # 選 JavaScript / TypeScript

3-3. 把機密存成環境變數(不要寫死在程式碼)​

推薦用 Secret Manager(第 2 代 Functions 內建支援):

# 設定一個名為 THIRD_PARTY_PASSWORD 的密鑰,執行後會提示輸入值
firebase functions:secrets:set THIRD_PARTY_PASSWORD
firebase functions:secrets:set THIRD_PARTY_USERNAME

3-4. 代理 Function 範例(Node.js / 2nd gen）​

以「代理去第三方服務換 token,並在伺服器端補上 Basic Auth」為例:

// functions/index.js
const { onCall, HttpsError } = require("firebase-functions/v2/https");

exports.getToken = onCall(
  {
    // 綁定要用到的密鑰,執行時才會注入到 process.env
    secrets: ["THIRD_PARTY_USERNAME", "THIRD_PARTY_PASSWORD"],
    region: "asia-east1",   // 選離使用者近的區域
    maxInstances: 10,       // 上限並發數,順便當成本護欄(見第 4 章)
  },
  async (request) => {
    // 1) 驗證呼叫者身分:未登入直接擋掉
    if (!request.auth) {
      throw new HttpsError("unauthenticated", "需要登入才能取得 token");
    }

    // 2) 機密只在伺服器端組出來,永不下發到 App
    const user = process.env.THIRD_PARTY_USERNAME;
    const pass = process.env.THIRD_PARTY_PASSWORD;
    const basic = Buffer.from(`${user}:${pass}`).toString("base64");

    // 3) 由伺服器端去打第三方服務
    const resp = await fetch("https://token-server.example.com/token/generate", {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        "Authorization": `Basic ${basic}`,
      },
      body: JSON.stringify({
        channel_name: request.data.channelName,
        uid: request.data.uid,
      }),
    });

    if (!resp.ok) {
      throw new HttpsError("internal", `上游服務失敗: ${resp.status}`);
    }

    const data = await resp.json();
    // 4) 只回傳 App 真正需要的東西
    return { token: data.data?.token };
  }
);

3-5. 部署​

firebase deploy --only functions

3-6. App 端呼叫(Flutter 範例)​

# pubspec.yaml
dependencies:
  cloud_functions: ^5.1.3
import 'package:cloud_functions/cloud_functions.dart';

Future<String> fetchToken(String channelName, int uid) async {
  final callable = FirebaseFunctions.instanceFor(region: 'asia-east1')
      .httpsCallable('getToken');

  final result = await callable.call({
    'channelName': channelName,
    'uid': uid,
  });

  final token = result.data['token'] as String?;
  if (token == null || token.isEmpty) {
    throw Exception('取得 token 失敗');
  }
  return token;
}

App 端從頭到尾沒碰到任何帳密 —— 這就是重點。

3-7. 進階:加上 App Check 防濫用​

即使有登入驗證,還是建議開 Firebase App Check,確保只有「你自己的正版 App」能呼叫 Function,擋掉別人拿你的 endpoint 亂打。

4. 費用與免費額度(＋自動暫停)​

4-1. 方案差別​

方案說明Cloud Functions 能用嗎
Spark(免費）不綁卡,免費額度用完就停止服務(不會扣錢)❌ 第 2 代 Functions 不能用
Blaze(按量計費）綁信用卡,含一層免費額度,超過才計費✅ 需要

4-2. Cloud Functions 免費額度(每月,約略值)​

項目免費額度
呼叫次數約 200 萬次 / 月
運算時間約 40 萬 GB-秒 / 月
對外網路流量約 5 GB / 月

小型代理(回傳一小段字串、每次幾百毫秒)通常遠遠用不完免費額度,實際帳單常常是 $0。

4-3. 重點問答:免費額度到了能「自動暫停」嗎?​

簡短答案:Google 沒有提供「用到免費額度就精準硬性停止」的官方開關。 但可以用下面的方法逼近「到達門檻就自動停」。

方法 A(最接近硬性停止):預算 + Pub/Sub + 自動停用帳單​

Google 官方文件有這個「cap (disable) billing」模式:

  1. Cloud Billing → Budgets & alerts 建立預算(例如設 $1,約等於超出免費額度就觸發)。
  2. 預算把通知送到一個 Pub/Sub topic。
  3. 寫一支訂閱該 topic 的 Cloud Function,當花費超過門檻時,呼叫 Cloud Billing API 把專案的帳單帳戶「停用 / 解除連結」 → 專案退回無帳單狀態,付費服務就停。
// 停用帳單的核心邏輯(概念示意)
const { CloudBillingClient } = require("@google-cloud/billing");
const billing = new CloudBillingClient();

exports.stopBilling = async (pubsubEvent) => {
  const data = JSON.parse(
    Buffer.from(pubsubEvent.data, "base64").toString()
  );
  // 花費超過預算才動作
  if (data.costAmount <= data.budgetAmount) return;

  const projectName = `projects/${process.env.GCP_PROJECT}`;
  await billing.updateProjectBillingInfo({
    name: projectName,
    projectBillingInfo: { billingAccountName: "" }, // 解除連結 = 停用帳單
  });
  console.log("已停用帳單,避免繼續產生費用");
};

⚠️ 注意:停用帳單是「大絕招」,會讓專案上所有付費服務停擺,某些資源甚至可能被清掉。而且預算資料有數小時延遲,不是即時、也不是精準卡在免費額度那一刻。適合當「保命防爆帳單」機制,不適合當日常流量控制。

方法 B(較溫和,推薦日常用):限制並發 + 預算警示​

  • maxInstances:在 Function 上限制最大同時執行數(如上面範例的 maxInstances: 10),避免流量暴衝把成本拉高。
  • 預算警示(Budget Alerts):只寄 email 通知(50% / 90% / 100%),不自動關服務 —— 讓你能人工判斷再處理,不會誤殺正式服務。

方法 C:App Engine 的每日花費上限(不適用 Functions)​

App Engine 有內建「daily spending limit」,但 Cloud Functions 沒有這個原生功能,所以才需要方法 A。

4-4. 建議組合​

情境建議
個人 / 學習專案,怕爆帳單方法 A(自動停用帳單當保險)+ 方法 B(預算 email 警示)
正式營運服務方法 B 為主(maxInstances + 預算警示),別用自動停用帳單(會誤殺正式服務)

5. 總結:怎麼選​

需求建議做法
功能開關 / 公告 / URL,可被看到Remote Config(第 1 章)
同上,但已在用 Firestore / 要精細讀寫規則Firestore config(第 2 章)
API 金鑰 / 帳密 / 簽章等真機密Cloud Functions(第 3 章)—— 唯一治本
怕爆帳單預算警示 + maxInstances;要硬性保險再加自動停用帳單(第 4 章)

一句話原則:會被下發到 App 的,就當它「所有人都看得到」;真機密只放伺服器端。
