教學：用「開發容器」當控制面，直接管理宿主 Docker（DooD）

目標讀者：想讓「跑在容器裡的開發環境」能自己對宿主 docker 下指令、 自動起停／重建應用服務，達成「本機只起一次，之後改動直接生效」的人。

全文使用通用範例，方法可套用到任何專案。

範例用到的占位符（請自行代換）：

  • ${PROJECT_DIR}：專案在宿主上的絕對路徑，例如 /Users/me/myproject
  • dev：開發容器（控制面）
  • myapp：被管理的應用疊（compose project 名）
  • db / cache / api / web：應用疊裡的範例服務
  • ${DOCKER_GID}：宿主 docker 群組的 gid（Linux 才需要，見 §4.3）
  • ${HOST_WORKSPACE_ROOT}：路徑陷阱解法 B 用的宿主路徑變數（見 §5.1）
  • APP_COMPOSE：指向應用疊 compose 檔（宿主對齊路徑）的環境變數（見 §6）

目錄：§0 總結｜§1 為什麼｜§2 DooD vs DinD｜§3 架構｜§4 三個關鍵設定｜ §5 三個雷（路徑/安全/多專案互見）｜§6 工作流｜§7 驗證清單｜§8 完整範例｜§9 一頁速查

🛡️ 安全那一半在另一篇：本篇 §5.2／§5.3 只講清楚洞在哪；怎麼把它補起來 （收窄共享目錄 ＋ 過濾式 socket 代理，含實作要點與驗證清單）見 〈DooD 的沙箱〉。若容器裡跑的是 AI agent，那篇請當必讀。

0. 一句話總結​

把開發容器升級成控制面（control plane）：裝 docker client、掛宿主 docker.sock、 給 group_add 權限——三件套——它就能像在宿主一樣下 docker compose up -d 去管理 「應用疊」那組容器；再配上路徑對齊避開 DooD 路徑陷阱，整套在 macOS 上零額外設定即可運作。

1. 為什麼要這樣做？先分清「兩種修改」​

開發時你的修改其實分兩類，待遇完全不同：

類型例子容器內會怎樣
原始碼程式碼、模板、設定檔、路由邏輯✅ 自動生效。靠 bind mount 共用檔案 + 熱重載工具（air / Vite / nodemon…），一存檔就重載，不必下任何指令。
基礎設施（infra）port 對映、環境變數、加服務、相依套件清單、Dockerfile❌ 一定要 recreate / rebuild 容器才生效。這是 Docker 的本質，掛 volume 救不了。

「本機只起一次、改動直接更新 docker」這個願望，卡點只在第二類。 要補它，唯一辦法是讓開發容器自己有能力對宿主 docker 下指令 —— 這就是 DooD。

2. DooD vs DinD：先選對工具​

方式做法特性
DinD（Docker-in-Docker）容器內跑一整顆 dockerd需要 --privileged、巢狀儲存層、較重，容易踩 overlay 問題。多半用在 CI 隔離。
DooD（Docker-outside-of-Docker）✅容器內只裝 docker client，掛宿主 docker.sock，client 連的是宿主的 daemon輕量。容器內「起」的容器其實是宿主上的兄弟容器（sibling），不是孫容器。

本教學用 DooD。心智模型很重要：

你的開發容器（控制面）
  └─ docker CLI ──(/var/run/docker.sock)──▶ 宿主 dockerd
                                              ├─ db    ┐
                                              ├─ cache │ 應用疊（兄弟容器，
                                              ├─ api   │ 不是被「包」在開發容器裡）
                                              └─ web   ┘

重點：因為連的是宿主 daemon，所有路徑、port、volume 都以宿主為基準來解析， 且同一台宿主上所有掛 socket 的容器連的是同一顆 daemon —— 第 5 節的三個雷全都源自這兩句話。

3. 架構全貌：控制面 + 應用疊​

把環境拆成「兩個各自獨立的 compose project」：

┌─ 控制面：dev container ─────────────────────┐
│  開發環境跑在這（裝 docker client、掛 socket）│
└─────────────────────────────────────────────┘
            │ DooD 下指令
            ▼
┌─ 應用疊：myapp ─────────────────────────────┐
│  name: myapp（釘死 project 名）              │
│  db / cache / api / web                      │
└─────────────────────────────────────────────┘
        ▲ 兩邊都 bind-mount 同一份宿主原始碼 ▲

為什麼應用疊 compose 要寫 name: myapp？ 這樣不管是「你在宿主起」還是「控制面用 DooD 起」，compose 都認得是同一個 project， 會去「對帳、只重建有變的容器」，不會起出第二份平行的疊。

4. 三個關鍵設定（逐一拆解）​

4.1 在開發容器裡裝 docker client（Dockerfile）​

只裝 client，不裝 daemon：

# Docker client（DooD：連宿主 daemon，不裝 dockerd）＋ compose v2 plugin
ARG DOCKER_CLI_VERSION=27.3.1
RUN curl -fsSL "https://download.docker.com/linux/static/stable/$(uname -m)/docker-${DOCKER_CLI_VERSION}.tgz" \
      | tar -xz -C /usr/local/bin --strip-components=1 docker/docker \
 && mkdir -p /usr/local/lib/docker/cli-plugins \
 && curl -fsSL "https://github.com/docker/compose/releases/latest/download/docker-compose-linux-$(uname -m)" \
      -o /usr/local/lib/docker/cli-plugins/docker-compose \
 && chmod +x /usr/local/lib/docker/cli-plugins/docker-compose
  • $(uname -m)：arm64 機器回 aarch64，x86 回 x86_64，剛好對得上官方靜態檔名 → 同一份 Dockerfile 跨架構可用。
  • compose v2 是 CLI plugin（docker compose，無連字號），放到 cli-plugins/ 才會被 docker 認得。

4.2 掛 socket（docker-compose.yml）​

    volumes:
      - /var/run/docker.sock:/var/run/docker.sock   # DooD 的命脈

掛了它，容器內的 docker client 才有對象可連。

⚠️ 這一行同時是整個架構唯一的安全問題，而且比看起來嚴重得多（≈ 交出宿主 root，見 §5.2）。 生產做法是不要直接掛：改掛一個過濾代理開出來的 socket，開發容器設 DOCKER_HOST 指向它。做法見〈DooD 的沙箱〉；那條路連下一節的 group_add 都不需要了。

4.3 權限：group_add（最常卡住的地方）​

很多人卡在「掛了 socket 還是 permission denied」。原因是 socket 是有權限的 unix 檔：

    group_add:
      - "${DOCKER_GID:-0}"

機制拆解（務必理解）：

  1. macOS Docker Desktop 跑在一個 linuxkit VM 裡，被掛進來的 /var/run/docker.sock 在 VM 內是 root:root、模式 0660。
  2. 0660 = owner rw / group rw / others 完全不能碰。容器內若以非 root 使用者（例如 uid 1000）執行， 預設不屬於任何能碰它的群組 → 直接用就 permission denied。
  3. 解法不是 chmod、也不是改用 root，而是讓該使用者加入 socket 的群組。 socket 群組是 root = gid 0，所以把補充群組 0 加給它，0660 的 group-rw 就生效了。
  4. group_add: ["0"] 做的就是這件事。

⚠️ 每一個掛 socket 的服務都要各自 group_add（compose 不會繼承）。以 root 跑的映像 （如 scratch 靜態 binary）「碰巧」不用加也能動——那是隱式依賴，哪天改成非 root user 就 permission denied。掛 socket 與 group_add 永遠成對寫，最省事。

為什麼預設值寫 ${DOCKER_GID:-0}？ 為了一份 compose 同時吃兩種 host：

Hostsocket 擁有者怎麼設
macOS Docker Desktoproot:root 0660（群組 = gid 0）預設 0 即可，零設定 docker compose up -d
Linuxroot:docker（gid 例如 999）帶入宿主 docker gid：DOCKER_GID=$(getent group docker | cut -d: -f3) docker compose up -d

5. 三個 DooD 一定要懂的「雷」​

5.1 路徑陷阱（最重要）​

回想第 2 節那句：daemon 在宿主上解析路徑。於是：

  • docker compose 的 volume bind 來源（../../api:/app）→ 由宿主 daemon 解析 → 必須是宿主路徑。
  • docker compose build 的 build context → 由容器內的 CLI 打包上傳 → 必須是容器內存在的路徑。

兩者方向相反，這就是雷。假設開發容器把專案掛在 /workspace，但宿主實際路徑是 /Users/me/myproject/：你在容器內跑 compose，相對路徑會解析成 /workspace/api， 丟給宿主 daemon → 宿主上根本沒有 /workspace/... → mount 壞掉。

解法 A：路徑對齊（推薦，最少改動） 把專案額外掛在「和宿主一模一樣的絕對路徑」，跑 compose 時就用那個路徑：

    volumes:
      - ${PROJECT_DIR}:/workspace          # 給人用的工作目錄
      - ${PROJECT_DIR}:${PROJECT_DIR}      # ★ 路徑對齊：容器內路徑 == 宿主路徑

之後一律用對齊路徑跑：docker compose -f ${PROJECT_DIR}/path/to/docker-compose.yml ... → build context 在容器內找得到、volume 來源宿主也找得到，兩邊一致。

解法 B：把 bind 來源參數化 在應用疊 compose 把來源寫成 ${HOST_WORKSPACE_ROOT:-.}/api:/app， 從容器內跑時帶 HOST_WORKSPACE_ROOT=<宿主絕對路徑>，在宿主直接跑則用預設 .。 （查宿主路徑：docker inspect <dev-container> 看該 mount 的 Source。）

兩解法都對。A 不必改應用疊 compose、但多掛一份；B 不用雙掛、但每次要帶 env。

5.2 安全邊界​

掛 docker.sock 不是「容器可以用 docker」，而是容器可以叫宿主的 daemon 做任何事。 在容器內三行就能拿到宿主：

docker run --rm -v /Users/you:/h:ro alpine cat /h/.ssh/id_rsa   # 你的私鑰
docker inspect other_project_container                          # 別人 env 裡的明文祕密
docker run --rm --privileged -v /:/host alpine chroot /host sh   # 整台機器

而且 cap_drop: ALL、no-new-privileges、read_only 在 socket 開著時形同虛設—— 你關掉的是 capability，卻開了一個比 capability 大得多的後門。

以前這算「本機開發、可接受的風險」。現在容器裡跑的可能是一個會自己下指令的 agent， 或某個相依套件的 postinstall 腳本——風險不再只來自你自己手滑，所以預設值該換了： 不掛真 socket，改連過濾代理（〈沙箱〉）。容器仍能起停應用疊， 但掛不走專案目錄以外的東西、也看不到別的專案。

真的要直接掛（過渡期），至少先做第一層：Docker Desktop 的共享目錄縮到只剩專案目錄， 讓 -v ~/.ssh 在建立容器時就被擋。

兩種都「對」的姿態，依容器定位選：

定位姿態
常駐控制面（管理應用疊是它的本業）socket 常開，誠實接受「它=準宿主 root」，靠外圍（誰能進這個 shell）把關；cap_drop 之類的硬化在 socket 開著時只是心理安慰
開發/建置沙箱（偶爾才需要 docker）預設硬化（cap_drop、資源上限），socket 寫成臨時開：要用時解註解 up -d、用完註解回去恢復硬化——把例外留在 diff 裡看得見

5.3 多專案互見（同一顆 daemon 沒有租戶概念）​

同一台宿主上若有兩個以上掛了 socket 的控制面（例如兩個專案各自照本教學設定）， 它們連的是同一顆 daemon——這代表：

  • 任一邊 docker ps 看得到宿主上所有容器（包含另一個專案的）；
  • 任一邊可以 docker exec 進對方的容器、docker stop/rm 對方的服務；
  • docker inspect 會全裸吐出對方容器的 environment——tunnel token、DB 密碼等 以 env 注入的祕密，對「拿得到 socket 的任何人」都是明文。

這不是設定沒調好，是 DooD 的本質：socket 沒有租戶概念，拿到＝拿到整顆 daemon。 能做到的隔離分四級，由輕到重：

  1. 不用時關掉：沙箱型容器把 socket 寫成臨時開（§5.2），互見問題直接單向化/消失。
  2. 衛生層（防誤傷、不防窺探）：各應用疊釘 name:、container_name 用專案前綴、各走 自己的 network——防「一邊 compose down 誤殺另一邊」這類意外，不是安全邊界。
  3. socket 過濾代理——這裡要分清兩種，差別很大：
    • method＋path 白名單（tecnativa/docker-socket-proxy、wollomatic/socket-proxy、 CetusGuard）：一旦放行 POST /containers/create，就擋不住 body 裡的 -v /Users； 而 list／inspect 天生全域 → 縮能力有效，給不了隱形。
    • 會檢查 body、也會過濾回應的代理：bind 來源白名單、禁特權旗標、新建物件蓋租戶標籤、 list 端點依標籤過濾 → 別的專案在容器眼中真的看不到。現成的沒有（唯一做過的 sockguard 已於 2021 封存），但自己寫不大（Go 標準庫、約 1200 行含測試）—— 規則表、怎麼設定範圍、實作要點與踩過的坑見〈DooD 的沙箱〉。
  4. 真隔離＝每專案一顆 daemon：Linux 用 rootless dockerd（每專案一個 socket）； macOS 用 Colima 開第二顆 VM（或 Docker Desktop＋Colima 並存），各專案 DOCKER_HOST 指自己的 daemon——互相完全不可見。代價：image cache 雙份＋兩顆 VM 的記憶體， 在單機資源緊的情況要先掂量。

經驗法則：先做「Desktop 共享目錄收窄 ＋ 會檢查 body 的代理」——兩層合起來已經擋掉 「讀走宿主家目錄」與「碰別的專案」這兩類實際會出事的情況，代價只有一個 sidecar 容器。 1 與 2 順手做（便宜）；兩專案必須同時跑又互不可信時才上 4。

6. 完成後的工作流​

人只在宿主做一次：

docker compose build dev    # 重建控制面：裝好 docker client + compose plugin
docker compose up -d        # 用新設定起控制面（套 socket / group_add / 路徑對齊）

⚠️ 重建控制面會重啟「開發環境所在的容器」＝當前 session 會斷，重進即可。

之後：

  • 改原始碼 → 熱重載工具自動生效，零指令。
  • 改 infra → 在控制面（容器內）直接： 
    # 建議在 compose 放一個指向「宿主對齊路徑」的環境變數，例如 APP_COMPOSE
    docker compose -f "$APP_COMPOSE" up -d        # 起/重建套用變更
    docker compose -f "$APP_COMPOSE" ps           # 看狀態
    docker compose -f "$APP_COMPOSE" logs -f api
    人完全不用動手。

7. 驗證清單（重建後跑一次）​

docker version                              # client 連得到宿主 daemon？(看到 Server 版本就通)
docker compose version                      # compose plugin 裝好了？
id                                          # 執行身分是否有 group 0（或宿主 docker gid）
docker compose -f "$APP_COMPOSE" config     # 應用疊 compose 能正確解析？(路徑對不對)
docker compose -f "$APP_COMPOSE" ps         # 看到既有應用疊，且沒起出第二份

全過 = DooD 控制面打通。

8. 完整最小範例​

Dockerfile（控制面）​

FROM <你的基底映像>

# 你的開發工具鏈... (略)

# Docker client + compose plugin（DooD）
ARG DOCKER_CLI_VERSION=27.3.1
RUN curl -fsSL "https://download.docker.com/linux/static/stable/$(uname -m)/docker-${DOCKER_CLI_VERSION}.tgz" \
      | tar -xz -C /usr/local/bin --strip-components=1 docker/docker \
 && mkdir -p /usr/local/lib/docker/cli-plugins \
 && curl -fsSL "https://github.com/docker/compose/releases/latest/download/docker-compose-linux-$(uname -m)" \
      -o /usr/local/lib/docker/cli-plugins/docker-compose \
 && chmod +x /usr/local/lib/docker/cli-plugins/docker-compose

USER node          # 以非 root 執行；靠下方 group_add 取得 socket 權限
WORKDIR /workspace

docker-compose.yml（控制面）​

services:
  dev:
    build: .
    stdin_open: true
    tty: true
    # 長駐控制面建議成對加（沙箱型容器可省）：
    #   restart —— 主機/daemon 重開後自己回來（手動 stop 過的不會）
    #   init    —— PID1 掛 tini，長駐時幫 tmux/工具的孤兒子行程收屍、正確轉發停止訊號
    restart: unless-stopped
    init: true
    working_dir: /workspace
    volumes:
      - ${PROJECT_DIR}:/workspace            # 工作目錄
      - ${PROJECT_DIR}:${PROJECT_DIR}        # ★ 路徑對齊（DooD 必備）
      - /var/run/docker.sock:/var/run/docker.sock   # ★ DooD socket
      # ⚠️ 這是最小可跑範例。實際用請改成過濾代理（見〈沙箱〉那篇）：
      #   volumes:     - dood-sock:/run/dood
      #   environment: DOCKER_HOST: unix:///run/dood/docker.sock
      #   換過去之後下面的 group_add 也不需要了（代理以正確的 gid 開 socket）。
    group_add:
      - "${DOCKER_GID:-0}"                   # ★ socket 權限（Mac=0；Linux 帶 docker gid）
    environment:
      # 指向「宿主對齊路徑」的應用疊 compose，方便引用
      APP_COMPOSE: ${PROJECT_DIR}/path/to/docker-compose.yml

docker-compose.yml（應用疊，被管理者）​

name: myapp        # ★ 釘死 project 名 → 宿主起 / DooD 起都是同一個 project
services:
  db:    { image: postgres:16-alpine, ports: ["5432:5432"] }
  cache: { image: redis:7-alpine }
  api:
    build: ../../api
    volumes: ["../../api:/app"]   # 熱重載；DooD 跑時靠路徑對齊解析成宿主路徑
    ports: ["8080:8080"]
  web:
    build: ../../web
    volumes: ["../../web:/app"]
    ports: ["5173:5173"]

9. 一頁速查​

DooD 控制面三件套：
  1) Dockerfile  : 裝 docker client + compose plugin（不裝 dockerd）
  2) compose     : 掛 /var/run/docker.sock
  3) compose     : group_add: ["${DOCKER_GID:-0}"]   ← Mac 用 0、Linux 帶 docker gid

三個雷：
  A) 路徑：daemon 在宿主解析 → 容器內路徑要對齊宿主（或用 ${HOST_WORKSPACE_ROOT}）
  B) 安全：掛 socket ≈ 宿主 root（cap_drop 之類同時形同虛設）
     → 正路＝不掛真 socket，改連過濾代理：見 sandbox_dood_proxy
  C) 多專案：同一顆 daemon 互相全可見可控（inspect 連 env 祕密都讀得到）
     → 防誤傷靠 name/前綴；會過濾回應的代理可以給隱形；要真隔離才需分 daemon

口訣：
  改 code → 自動熱重載（零指令）
  改 infra → 控制面內 docker compose -f "$APP_COMPOSE" up -d（人不用動手）
