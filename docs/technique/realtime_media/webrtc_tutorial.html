WebRTC 完整教學

從零開始理解 WebRTC:概念、架構、核心 API 與實戰範例。 本文為通用教學,不涉及任何特定專案。

1. 什麼是 WebRTC​

WebRTC(Web Real-Time Communication) 是一套開放標準與 API,讓瀏覽器與行動 App 不需安裝外掛,就能進行即時的音訊、視訊與任意資料的**點對點(peer-to-peer)**傳輸。

它由 Google 於 2011 年開源,現已成為 W3C(API 標準)與 IETF(傳輸協定)的正式標準。目前所有主流瀏覽器(Chrome、Firefox、Safari、Edge)以及 Android / iOS 原生都支援。

核心特色​

特色說明
免外掛瀏覽器原生支援,不需 Flash 或任何插件
低延遲專為即時通訊設計,延遲通常 < 200ms
點對點媒體資料可直接在兩端間傳輸,不一定經過伺服器
加密強制加密(SRTP / DTLS),無法關閉
自適應依網路狀況自動調整位元率、解析度

2. WebRTC 能做什麼​

  • 視訊 / 語音通話(一對一、多方會議)
  • 直播、螢幕分享
  • 檔案傳輸(透過 DataChannel)
  • 線上遊戲的即時資料同步
  • IoT 裝置串流(攝影機、感測器)
  • 遠端桌面控制

3. 核心架構與名詞​

WebRTC 常被誤解為「純點對點、不需伺服器」。實際上它需要信令伺服器(Signaling Server)來協助雙方交換連線資訊,只是媒體資料本身盡量走點對點。

   ┌─────────┐        信令(交換 SDP / ICE)       ┌─────────┐
   │ Peer A  │ <──────────────────────────────> │ Peer B  │
   │(瀏覽器)│         ↑ 透過 Signaling Server    │(瀏覽器)│
   └─────────┘                                   └─────────┘
        │                                             │
        └──────────── 媒體資料(P2P,SRTP)───────────┘
                     (必要時經 TURN 中繼)

關鍵名詞​

  • Signaling(信令):交換連線協商資訊的過程。WebRTC 不規定用什麼協定,你可以用 WebSocket、HTTP、甚至 QR code。
  • SDP(Session Description Protocol):描述「我支援哪些編碼、解析度、網路位址」的文字格式。
  • ICE(Interactive Connectivity Establishment):找出兩端之間「可以連通的路徑」的框架。
  • STUN:協助 peer 得知自己的公網 IP(打洞用)。
  • TURN:當無法直接 P2P 時,提供中繼伺服器轉發資料。
  • NAT:網路位址轉換,是 P2P 連線的主要障礙。

4. 連線建立流程​

WebRTC 建立連線的核心是 Offer / Answer 交換模型,搭配 ICE candidate 的收集與交換。

完整流程圖​

   Peer A                    Signaling Server                 Peer B
     │                            │                             │
     │ 1. createOffer()           │                             │
     │ 2. setLocalDescription     │                             │
     │─────── offer(SDP) ────────>│──────── offer(SDP) ────────>│
     │                            │           3. setRemoteDescription
     │                            │           4. createAnswer()  │
     │                            │           5. setLocalDescription
     │<────── answer(SDP) ────────│<─────── answer(SDP) ─────────│
     │ 6. setRemoteDescription    │                             │
     │                            │                             │
     │<───── ICE candidates(雙向持續交換)─────────────────────>│
     │                            │                             │
     │═══════════ 媒體 / 資料開始傳輸(P2P)══════════════════════│

步驟說明​

  1. A 建立 Offer:呼叫 createOffer() 產生描述自己能力的 SDP。
  2. A 設定本地描述:setLocalDescription(offer)。
  3. 透過信令傳給 B:用你自己的伺服器把 offer 傳過去。
  4. B 收到後設定遠端描述:setRemoteDescription(offer)。
  5. B 建立 Answer:createAnswer(),並 setLocalDescription。
  6. B 把 answer 傳回 A,A setRemoteDescription(answer)。
  7. 雙方交換 ICE candidate:一邊收集一邊透過信令傳給對方,直到找到可連通的路徑。
  8. 連線建立,媒體開始流動。

5. 三大核心 API​

5.1 RTCPeerConnection​

整個 WebRTC 的核心物件,管理連線、協商、媒體傳輸。

const pc = new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },
    // 需要 TURN 時:
    // { urls: 'turn:turn.example.com:3478', username: 'user', credential: 'pass' }
  ],
});

// 監聽 ICE candidate,透過信令傳給對方
pc.onicecandidate = (event) => {
  if (event.candidate) {
    signalingSend({ type: 'candidate', candidate: event.candidate });
  }
};

// 監聽對方送來的媒體軌
pc.ontrack = (event) => {
  remoteVideo.srcObject = event.streams[0];
};

// 監聽連線狀態
pc.onconnectionstatechange = () => {
  console.log('連線狀態:', pc.connectionState);
  // new → connecting → connected → disconnected → failed → closed
};

5.2 MediaStream / getUserMedia​

取得本地攝影機與麥克風。

const stream = await navigator.mediaDevices.getUserMedia({
  video: { width: 1280, height: 720 },
  audio: true,
});

localVideo.srcObject = stream;

// 把每一條軌加入 PeerConnection
stream.getTracks().forEach((track) => {
  pc.addTrack(track, stream);
});

5.3 RTCDataChannel​

傳輸任意資料(文字、二進位、檔案)。

const channel = pc.createDataChannel('chat');
channel.onopen = () => channel.send('Hello!');
channel.onmessage = (e) => console.log('收到:', e.data);

6. 實戰:一對一視訊通話​

以下是一個最小可運行的範例,使用 WebSocket 當信令伺服器。

6.1 前端(caller 與 callee 共用)​

// ---- 設定 ----
const pc = new RTCPeerConnection({
  iceServers: [{ urls: 'stun:stun.l.google.com:19302' }],
});
const ws = new WebSocket('wss://your-signaling-server.example.com');

// ---- 本地媒體 ----
const localStream = await navigator.mediaDevices.getUserMedia({ video: true, audio: true });
document.getElementById('localVideo').srcObject = localStream;
localStream.getTracks().forEach((t) => pc.addTrack(t, localStream));

// ---- 遠端媒體 ----
pc.ontrack = (e) => {
  document.getElementById('remoteVideo').srcObject = e.streams[0];
};

// ---- ICE 交換 ----
pc.onicecandidate = (e) => {
  if (e.candidate) ws.send(JSON.stringify({ type: 'candidate', candidate: e.candidate }));
};

// ---- 信令處理 ----
ws.onmessage = async (msg) => {
  const data = JSON.parse(msg.data);

  if (data.type === 'offer') {
    await pc.setRemoteDescription(data.offer);
    const answer = await pc.createAnswer();
    await pc.setLocalDescription(answer);
    ws.send(JSON.stringify({ type: 'answer', answer }));
  } else if (data.type === 'answer') {
    await pc.setRemoteDescription(data.answer);
  } else if (data.type === 'candidate') {
    await pc.addIceCandidate(data.candidate);
  }
};

// ---- 主叫方按下「撥號」時 ----
async function startCall() {
  const offer = await pc.createOffer();
  await pc.setLocalDescription(offer);
  ws.send(JSON.stringify({ type: 'offer', offer }));
}

6.2 信令伺服器(Node.js + ws,最簡版)​

const { WebSocketServer } = require('ws');
const wss = new WebSocketServer({ port: 8080 });

wss.on('connection', (socket) => {
  socket.on('message', (data) => {
    // 廣播給「其他」連線的 peer
    wss.clients.forEach((client) => {
      if (client !== socket && client.readyState === 1) {
        client.send(data.toString());
      }
    });
  });
});

⚠️ 這只是教學用途。正式環境需要房間(room)機制、身分驗證、以及只轉發給正確的對象。

6.3 HTML​

<video id="localVideo" autoplay muted playsinline></video>
<video id="remoteVideo" autoplay playsinline></video>
<button onclick="startCall()">撥號</button>

7. STUN / TURN 與 NAT 穿透​

大多數裝置位於 NAT / 防火牆後方,沒有公開 IP。WebRTC 用 ICE 框架解決:

STUN(Session Traversal Utilities for NAT)​

  • 功能:告訴 peer「你在公網上的 IP 和 port 是什麼」。
  • 成本:非常低,Google 提供免費公用伺服器。
  • 適用:約 80% 的網路環境可透過 STUN 完成 P2P 打洞。

TURN(Traversal Using Relays around NAT)​

  • 功能:當雙方無法直接連通(對稱型 NAT、嚴格防火牆)時,由伺服器中繼所有媒體資料。
  • 成本:高,消耗頻寬,需要自己架設(如 coturn)或付費服務。
  • 適用:剩下約 20% 難連的情況的保底方案。
   直接 P2P 成功       → 走 host / srflx candidate(最佳)
   P2P 失敗、需中繼    → 走 relay candidate(經 TURN)

自架 TURN(coturn)範例設定​

# /etc/turnserver.conf
listening-port=3478
fingerprint
lt-cred-mech
user=myuser:mypassword
realm=turn.example.com

8. 資料通道 DataChannel​

不只音視訊,WebRTC 也能傳任意資料,類似 WebSocket 但走 P2P。

// 建立方
const dc = pc.createDataChannel('file', {
  ordered: true,        // 是否保證順序
  maxRetransmits: 3,    // 最大重送次數(可做成不可靠傳輸)
});

// 接收方
pc.ondatachannel = (event) => {
  const channel = event.channel;
  channel.onmessage = (e) => console.log('收到資料:', e.data);
};

可靠 vs 不可靠模式​

模式設定用途
可靠有序預設檔案傳輸、聊天訊息
不可靠無序maxRetransmits: 0 或 ordered: false遊戲狀態、即時位置更新

9. 進階主題​

9.1 多方通訊架構​

一對一用純 P2P 沒問題,但人數變多時 P2P 全連接(mesh)會爆炸(N 人需 N×(N-1)/2 條連線)。常見解法:

  • Mesh(網狀):每人連每人。簡單但只適合 2~4 人。
  • SFU(Selective Forwarding Unit):每人只上傳一份到伺服器,由伺服器轉發。主流方案(如 mediasoup、Janus、LiveKit)。
  • MCU(Multipoint Control Unit):伺服器把所有畫面混流成一路。省客戶端頻寬但耗伺服器 CPU。
   Mesh              SFU                    MCU
  A───B          A ──┐                  A ──┐
  │ ╳ │              ├─> [SFU] ─> 轉發      ├─> [MCU 混流] ─> 單一串流
  C───D          B ──┘                  B ──┘

9.2 頻寬與品質控制​

const sender = pc.getSenders().find((s) => s.track.kind === 'video');
const params = sender.getParameters();
params.encodings[0].maxBitrate = 500_000; // 限制在 500 kbps
await sender.setParameters(params);

9.3 統計資訊(getStats)​

const stats = await pc.getStats();
stats.forEach((report) => {
  if (report.type === 'inbound-rtp' && report.kind === 'video') {
    console.log('封包遺失:', report.packetsLost);
    console.log('抖動:', report.jitter);
  }
});

9.4 螢幕分享​

const screenStream = await navigator.mediaDevices.getDisplayMedia({ video: true });
const screenTrack = screenStream.getVideoTracks()[0];

// 替換現有的視訊軌
const sender = pc.getSenders().find((s) => s.track.kind === 'video');
sender.replaceTrack(screenTrack);

10. 常見問題與除錯​

問題可能原因解法
看不到遠端畫面ICE 沒連通檢查 connectionState,加 TURN
getUserMedia 失敗非 HTTPS 環境必須用 https 或 localhost
連線在公司網路失敗嚴格 NAT / 防火牆部署 TURN 伺服器
音訊有回音未啟用回音消除getUserMedia 加 echoCancellation: true
手機瀏覽器影片黑畫面缺 playsinlinevideo 標籤加 playsinline 屬性

除錯利器​

  • chrome://webrtc-internals:Chrome 內建的 WebRTC 除錯頁,可看到所有連線狀態、ICE candidate、統計圖表。
  • about:webrtc:Firefox 對應功能。

總結​

WebRTC 的三個心智模型:

  1. 信令是你的責任:WebRTC 不管你怎麼交換 offer/answer,自己選 WebSocket 等方式實作。
  2. 媒體盡量走 P2P:用 STUN 打洞,失敗才用 TURN 中繼。
  3. 人多要用 SFU:純 P2P 只適合少數人,多方會議需要媒體伺服器。

掌握 RTCPeerConnection、getUserMedia、Offer/Answer 流程這三塊,就能建立絕大多數即時通訊應用。
