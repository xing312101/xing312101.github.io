自己做 coding agent：值得借鏡的設計

coding agent 的核心迴圈很短：送出對話 → 模型要用工具 → 執行 → 把結果送回去 → 再送，直到模型不再呼叫工具。 幾百行就寫得出來。難的是外面那一圈（業界叫它 harness）：模型要求的動作哪些能做、做的時候能碰到什麼、出錯時怎麼收拾、 換一家模型時哪些東西會壞，以及怎麼證明這些規則真的守得住。

這一系列整理自己做一個 coding agent 時，實際做過、驗過的設計。跟用哪一家模型無關，也不限定語言（範例是 TypeScript）。

篇內容
總覽（本篇）分層、唯一路徑：工具只收得到權限層核准過的呼叫
權限規則白名單的條件、危險清單、機密檔、信任的資料夾、要核准的東西必須看得到
OS 沙盒規則擋不完的交給沙盒：三個平台的做法、預設政策、延遲執行的繞道、沙盒擋不到的、啟動不了就拒絕
工具與跑指令改檔工具的設計、乾淨的環境、輸出截斷、不留下程序、復原、遮掉金鑰
轉接層、上下文與花費訊息格式不能是各家的最小公約數、重試只在一個地方做、快取友善的上下文、歷史只能往後加
怎麼證明守得住假模型、架構測試、「拿掉修法，測試要紅」的突變檢查、先關掉沙盒跑一次、評測與注入測試

1. 分層：模型只是可以替換的零件​

介面層    終端機；之後可以是通訊軟體、排程、網頁
          只認核心送出的事件；要權限時透過 Asker 問使用者
──────────────────────────────────────────────────────────
核心（不 import 任何一家的 SDK）
  agent 迴圈   送出 → 模型要用工具 → 權限層（必經）→ 執行 → 結果 → 再送
  權限層       權限規則 ＋ OS 沙盒 ＋ 信任的資料夾
  工具         read · list · search · edit · write · bash
  上下文       快取友善的排序、專案規則（AGENTS.md）、輸出截斷、摘要
  花費         用量 × 價格表；每輪、每天、每月的上限
  對話紀錄     JSONL，用來接續、除錯、評測
──────────────────────────────────────────────────────────
轉接層（換廠商只動這裡；保留各家的原生資料）
  anthropic · chat-completions（OpenAI、Ollama、llama.cpp、vLLM、自建）· gemini
  fake：照劇本回答，測試用

幾個關鍵的決定：

  • 核心不 import 任何一家的 SDK。 各家的格式只出現在自己的轉接層裡，轉接層之間也互不 import。換模型、加一家，核心不動。

  • 介面只認核心的事件（文字、工具呼叫、工具結果、被擋、提醒、這一輪結束）。要問使用者時，核心呼叫一個 Asker 介面：

    interface Asker {
      askTool(req: PermissionRequest): Promise<'yes' | 'no' | 'always'>;
      askDomain(host: string): Promise<'once' | 'session' | 'no'>;
    }

    之後要把 agent 接到通訊軟體上，只要換一個 Asker（詢問變成訊息裡的按鈕），核心不用改。

  • 假模型是正式的一家：跟真的轉接層實作同一個介面，照劇本吐出文字、工具呼叫、錯誤、切成小段的串流。自動化測試只用它（怎麼證明守得住）。

依賴方向寫成表，再用測試守住​

資料夾可以 import
main.ts全部（只有這裡把各層接起來）
interfaces/core/、config/
guard/（權限層）core/、tools/、config/
tools/core/、config/
adapters/<家>core/、config/、自己那一家的 SDK
core/只用自己裡面的，加上 config/

跨資料夾只能 import 對方的 index.ts。這張表不是寫給人記的：一個架構測試掃過每個檔案的 import，違反就紅（怎麼證明守得住 §2）。 其中最重要的一條是「只有權限層能 import 工具」，下一節的唯一路徑就靠它。

2. 唯一路徑：沒有任何一條路能不經過權限層就執行工具​

迴圈、介面、轉接層都拿不到工具本身。工具的 run() 只收一種型別，這個型別只有權限層建得出來：

// 只有 guard/ 建得出來；工具的 run() 只收這個型別
declare const approved: unique symbol;
type ApprovedCall = ToolCall & { readonly [approved]: true };

三層，各擋一種錯：

  1. 型別擋寫錯：忘了檢查就呼叫工具，編譯不過。
  2. 執行時再核對一次：權限層把自己核准過的物件放進一個 WeakSet，工具執行前確認在裡面。有人用 as ApprovedCall 繞過型別也過不了。
  3. 測試從外面驗：架構測試擋「權限層以外出現 as ApprovedCall」；另一個測試讓假模型丟出每一種工具呼叫，記錄每一次執行前有沒有經過檢查。

為什麼要這麼囉嗦：權限如果靠別人的程式路徑（例如用某個 agent SDK 的權限回呼），一旦它在某條路徑上沒有呼叫你，你不會知道。 實際發生過「寫檔沒問就執行了」，原因查不清楚 —— 自己做的理由之一就是權限放在自己的程式路徑上，而且有測試守著。

一輪裡的細節​

  • 同一輪有多個工具呼叫：權限一個一個問。只讀的可以同時跑，會改東西的照順序跑；bash 一律不跟其他工具同時跑（工具與跑指令 §1）。
  • 被拒絕時不中斷這一輪：回給模型「使用者拒絕了：原因」，讓它換別的方法。
  • 上限：每輪的工具呼叫次數、每輪的花費各有上限，碰到就停下來問。
  • Ctrl-C 只中斷這一輪：中斷一路傳到轉接層和正在跑的指令（整個行程群組）；被中斷的工具呼叫補一個「使用者中斷」的結果， 因為各家都要求工具呼叫後面接著結果，歷史才合法；對話可以接著繼續。
  • 工具的錯誤訊息是寫給模型看的：講清楚錯在哪、怎麼改。例如「old_string 在檔案裡出現 3 次，請多帶幾行，讓它只出現一次」。

3. 三個頭：權限規則、OS 沙盒、信任的資料夾​

頭做什麼擋什麼
權限規則每個工具呼叫：允許、問、拒絕模型想做、但使用者沒同意的事
OS 沙盒bash 跑出去的程序只能碰允許的檔案和網域規則沒料到的寫法（正規表示式永遠列不完）
信任的資料夾第一次在某個資料夾開啟時問信不信任別人的 repo 裡會被執行的東西：package.json 的 scripts、.git/config、hooks

白名單只是讓使用者少被問幾次，不是安全邊界。安全邊界是沙盒。 細節見權限規則和 OS 沙盒。
