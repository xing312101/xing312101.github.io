讓 AI agent 自己動手測試：工具總覽

lint、build、單元測試全過，不代表按鈕會動。agent 能做的不只是跑測試，它可以像人一樣打一次 API、開瀏覽器點一次、 在手機上走一次，再把截圖拿回來看。這一包文件整理怎麼把這些工具交給 agent。

1. 怎麼選​

要測的東西工具文件
後端 API 回什麼curl、專案的測試框架其他測試
函式、元件的邏輯專案的單元測試（pytest、vitest、jest⋯）其他測試
網頁畫面與流程（電腦版、手機尺寸、列印版面）Playwright網頁：Playwright
手機上的網頁或 App，不需要真的相機、第三方 AppiOS Simulator、Android Emulator手機模擬器
App 內建瀏覽器、相機、相簿、系統對話框、列印手機實機＋Appium手機實機：Appium（不用 Appium、直接用 adb／WebDriverAgent：另一個系列）
視覺跑版、無障礙、效能、桌面程式Playwright 外掛、Lighthouse、k6、computer use其他測試

由上往下越接近真實，也越慢、越難準備。先用便宜的找到問題，最後才上實機。

2. agent 的操作模式​

不論哪一種工具，agent 都是同一個循環：

動作（點擊／打字／開網址） → 等畫面穩定 → 截圖或讀畫面結構 → 判斷 → 下一個動作
給 agent 的方式適合缺點
寫成腳本（Playwright、curl）要重跑的檢查、一次驗很多項要先知道畫面長怎樣
MCP 工具（Playwright MCP）第一次探索一個頁面每一步都來回，比較耗 token
包成 shell 函式（Appium 的 tap、shot）手機，靠截圖找座標座標容易算錯，要寫清楚換算方式

3. 讓測試結果可信的原則​

  • 改了畫面就實際點一次。 型別檢查擋不住「沒把 callback 傳下去」、HTML 擋不住「表格少一格」
  • 做了畫面就打一次它用的 API。 一次就好，很多 500 是 UI 做完從沒打過
  • 寫完測試，把修法拿掉，確認它會紅。 永遠會過的測試比沒有測試更糟，它讓人以為有守著
  • 斷言之前，確認比對的是程式實際用的那個值，不是名字相像的另一個
  • 說「壞了」之前，先讓它壞給你看。 讀程式碼推出來的結論常常錯
  • 測試會改到共用的資料時，在 finally 放回原狀（不管過沒過）。驗「會紅」那一輪，修法拿掉時它真的會改壞資料
  • 用等待條件，不要用固定秒數（等回應、等元素出現）。實機截圖例外，動畫要等
  • 先在本機或測試環境，不拿正式站當第一個測試場
danger

截圖、畫面內容會送給模型。 一律用測試帳號、測試資料；不要讓 agent 輸入真正的密碼， 登入狀態檔（cookie、token）不要放進版控。
