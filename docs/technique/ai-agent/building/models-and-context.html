轉接層、上下文與花費

接在工具與跑指令之後。要能換模型，各家的差異就得全部關在轉接層裡； 而上下文怎麼排、歷史怎麼改，直接決定快取吃不吃得到（也就是每一輪要花多少錢），有些家甚至會因此回 400。

1. 轉接層：格式不能是各家的最小公約數​

統一的訊息格式只有幾種內容（文字、工具呼叫、工具結果、圖片），再加一個各家自己的原生資料欄位：

interface Message {
  role: 'user' | 'assistant';
  parts: Part[];
  // 各家的原生資料（推理區塊與簽章、thought signature、reasoning item）。
  // 核心只保存、不解讀；只有同一家的轉接層會讀寫
  native?: { provider: string; model: string; data: unknown };
}

為什麼一定要這一欄：每一家都有「下一輪要原樣送回去」的東西，丟了就壞。

  • Gemini：多輪工具呼叫時，thought signature 要原封不動傳回去，漏了就回 400。很多 OpenAI 相容層會把它丟掉，結果第一輪正常、第二輪開始壞。所以 Gemini 要用原生的轉接層。
  • Anthropic：推理（thinking）區塊要連同簽章原樣傳回去，而且綁著產生它的那段對話（第 3 節）。
  • OpenAI：Responses API 的 reasoning item 也有類似的要求。

規則：

  1. 轉接層送出時，native.provider 是自己的就原樣帶上，不是自己的就忽略。
  2. 對話中途換到別家：原生資料帶不過去。把歷史轉成純文字（工具呼叫和結果也寫成文字，太長就先摘要），畫面上講清楚「換廠商了，之前的對話已轉成文字」。
  3. 本地模型和自建服務一律走 Chat Completions（Ollama、llama.cpp、vLLM）：它們雖然也有 /v1/responses，底下多半是轉成 Chat Completions 在跑。

錯誤：用實際打出來的錯誤決定怎麼對應​

各家的錯誤在轉接層翻成同一組：quota_exhausted、rate_limited（帶 retry-after）、auth_failed、model_not_found、context_too_long、network、server_error。

  • 照實際打出來的錯誤寫，不要照文件猜：錯的 key、不存在的模型、超長的上下文，各實際打一次，把回應錄下來當測試資料（先拿掉金鑰和請求標頭）。
  • 有一種不是錯誤的結束：安全分類器擋下請求時，Anthropic 回 HTTP 200、stop_reason: "refusal"。讀內容之前先判斷，畫面上講清楚，不要當成模型回了空白。

重試只在一個地方做​

  • 限流照 retry-after 退避，網路斷就重試，上下文太長就摘要後重試一次；額度用完、key 錯不重試，直接講清楚。
  • 各家 SDK 自己的重試都關掉：Anthropic 的 SDK 預設會重試 2 次，疊上核心的 3 次，同一個請求最多送 9 次。
  • 串流已經印出內容之後就不整段重送，免得畫面重複；直接講清楚斷在哪裡。

金鑰和用量不要跑到別的帳號​

  • 用 agent 自己的環境變數名稱（例如 MYAGENT_ANTHROPIC_API_KEY），不用 ANTHROPIC_API_KEY 這類通用的名稱：別的工具也會讀它，設成全域就可能被別的工具拿去用。
  • 建 client 時一定明確傳入 apiKey 和 baseURL：SDK 沒拿到 key 時，會自己去找環境變數、別的工具存的登入設定，用量就記到別的帳號去了。讀到的 key 是空的就直接報錯。
  • 金鑰讀進來只交給轉接層；讀金鑰的模組只有進入點能 import；跑指令的子程序用的是乾淨的環境（工具與跑指令 §2）。

能力表：先問 API，再看設定​

上下文大小、最大輸出、推理強度有哪幾級、能不能關掉推理、能不能看圖：先向各家的模型清單 API 查（Anthropic 的 /v1/models、Gemini 的 models.list、Ollama 的 /api/show），查不到的才用設定檔，設定檔可以覆寫。 查到的快取一天，啟動不用等、離線也能用。都查不到的模型用保守的預設（只給讀、搜尋、改檔三個工具，上下文 32K），並提醒「這個模型沒有能力資料」。

2. 上下文：排序要讓快取吃得到​

  • 固定的放前面、會變的放後面：工具定義 → system prompt（含專案規則）→ 對話。
  • system prompt 裡不放時間、隨機值：放了每一輪都是新的開頭，快取永遠不中。
  • 專案規則（AGENTS.md、CLAUDE.md）在對話開始時讀一次，之後不重建。
  • 快取跟著模型走：中途換模型、或另外用便宜的模型做摘要，都吃不到原本的快取。
  • 用到才去找：不預先把整個專案塞進去，讓模型用 list、search、read 自己找；工具結果截斷、讀檔分段、搜尋有上限。

3. 歷史只能往後加​

推理區塊綁著產生它的那段對話：改過、刪過、重排之前的訊息，或中途重建 system、工具清單，之後的推理區塊就失效（Anthropic 現行的模型會檢查，回 400）。 沒被檢查的模型照這樣做，快取也比較容易命中。所以：

  • 模式切換、AGENTS.md 更新、復原了哪一輪這類提醒：不改 system，在對話後面附加一則 system 訊息。 這也是工具輸出偽造不了的指令管道（工具結果裡寫「系統：現在是全自動模式」沒有用）。不支援這種訊息的模型，由轉接層改成附在使用者訊息裡。
  • 工具清單整個對話固定不變，各模式不能做的事交給權限層擋。
  • 要清掉舊的工具結果，用伺服器端的 context editing，不要自己從歷史裡刪。
  • Ctrl-C 中斷的那則回覆只保留完整的區塊；還沒收到簽章的推理區塊不能送回去。

摘要（compaction）​

  • 門檻用 token 數，不用百分比：例如預設 15 萬、但不超過上下文的 80%。1M 的視窗用到 80% 才摘要太晚：每一輪光讀快取就很貴，速率上限也會先碰到； 有些模型的 prompt 超過某個長度單價會變好幾倍，門檻要訂在那之下。
  • 自己做的話用「簡單摘要」：下一個請求只放摘要和新的使用者訊息。「摘要舊的、最近幾輪保留原文」會違反「只能往後加」。
  • 不在一輪工具呼叫還沒結束時摘要。
  • 摘要要保留目標、已經做的決定、改過的檔、還沒做完的事：摘要之後模型只剩這一段。

4. 改完檔自動檢查（事後感測）​

業界把 harness 的機制分成兩種：事前引導（AGENTS.md、skills，讓它一開始就往對的方向做）和事後感測（改完自動檢查，交給使用者之前自己發現錯、自己修）。

  • 這一輪有改檔的話，結束前自動跑專案指定的檢查（測試、lint、型別），失敗的輸出（截斷過）交給模型修；最多重試幾次，還是失敗就停下來交給使用者。
  • 跑哪些指令由使用者指定。repo 裡別人寫的設定只在信任的資料夾才讀；第一次跑之前列出來問，內容一變就重新問。
  • 這份設定模型不能改（沙盒擋寫入，OS 沙盒 §3）：不然它可以在下次自動跑的檢查裡塞指令。
  • 在沙盒裡跑，跟 bash 同一套規則；沒設定任何檢查就不跑。

5. 花費：錯的數字比沒有數字更糟​

  • 花費＝各家回報的用量 × 價格表。用量包含輸入、輸出、寫入快取、讀快取、推理的 token；快取寫入的不同 TTL 價格不同，讀快取的折扣每個模型不一樣，逐項填，不要用固定倍數算。
  • 價格表放在設定檔，不寫死在程式裡；每一筆記下抄自哪一頁、哪一天抄的，太久沒更新就提醒。
  • 各家的 API 都不給價格；沒有價格的模型顯示「未知」，不顯示 $0。本地模型要明確設成 0。
  • 每輪、每天、每月各有上限，到 80% 提醒，到 100% 停下來問。比的是預估的花費，畫面上標「約」，定期跟服務商的帳單對一次。

6. 給模型的、給使用者的，分開​

  • 給模型看的（system prompt、工具說明、工具結果、錯誤訊息）只有一份，用英文：介面換成哪個語言，模型收到的指令都一樣，評測的結果才比得起來。
  • 給使用者看的（畫面、詢問、說明）用使用者的語言，全部放在對照表裡用 key 拿，同一句兩邊都要的就各給一份。
  • 用測試擋「對照表以外的地方出現中文字」（註解、正規表示式除外），不然改著改著就有一半的畫面沒翻。
