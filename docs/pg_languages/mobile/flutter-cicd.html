Flutter Mobile CI/CD

把 GitLab CI/CD 通用核心 套用到 Flutter（Android + iOS） 專案：快檢指令、Android/iOS 打包簽章與上架、裝置測試。

本章同時涵蓋 GitLab CI/CD 與 GitHub Actions：mobile 的難點（iOS 簽章、上傳商店）兩邊觀念一樣，差別在語法與「誰提供 macOS 機器」。build/簽章/上傳的邏輯統一走 fastlane（跨平台通用），每節再給兩種 CI 的對照片段。

note

先讀通用核心（觀念、pipeline 樣式、自架 runner、機密管理），本層只補 Flutter/mobile 專屬的部分。所有網址、Bundle ID、Team ID、版本號皆為佔位符。

Flutter 專案的混合架構對應​

一般 web/後端專案，一台 Linux runner 全包。Flutter mobile 不行，因為 iOS 只能在 macOS 上 build。先看每種工作各自需要什麼：

工作需要什麼跑得動的環境對應通用核心
dart format / flutter analyze / flutter test（widget/unit）純 Dart、headless，不需裝置也不需原生工具鏈任何 Linux（含雲端免費）快檢，進 merge gate
flutter build appbundle（Android）Android SDK + Gradle，不需裝置任何 Linux（含雲端免費）build / release
flutter build ios / ipaXcode → 只能 macOS只有 macOS「需要特定 OS」的自架案例
flutter test integration_test（e2e）模擬器 / 實體裝置iOS 需 macOS；Android emulator 需 KVM重測試排 nightly

歸納：只有 iOS build 和 iOS e2e 綁死 macOS；其餘（analyze、test、Android 全部）在 Linux 就能跑。所以真正的關鍵問題只有一個——誰提供那台 macOS？

「能跑」不等於「跑得動」：原生依賴很多的 App，Android build 有可能在免費雲端 runner 上因磁碟不足（No space left on device）而失敗，那時候也得移到自架機器。見 Android 上架。

誰提供 macOS？GitHub 有、GitLab.com 沒有​

同樣要一台 macOS，兩個平台待遇完全不同，這直接決定你要不要自己準備一台 Mac：

GitHub ActionsGitLab.com（SaaS）自架 GitLab（self-managed）
Linux runner（analyze/test/Android）✅ 免費額度內建✅ 免費額度內建❌ 預設無，要自架
macOS runner（iOS build）✅ 官方 hosted（macos-14 等，吃額度但免自架）❌ 無免費 macOS，必須自架一台 Mac❌ 必須自架
自架 runner✅ 支援✅ 支援✅ 支援

白話：

  • GitHub → iOS 直接跑在 hosted macOS runner，不必自己準備 Mac（但 macOS 分鐘比 Linux 貴，通常 10×）。
  • GitLab.com → 沒有免費 macOS，iOS 相關 job 一定要自架一台 Mac runner（executor 選 shell，因為 Xcode 無法容器化）。
  • 兩邊的 Android / analyze / test 都能上各自的 hosted Linux，不必自架。

一句話：同一個 Flutter 專案，在 GitLab 上比在 GitHub 上更需要一台常駐 Mac。

建議的 pipeline 形狀​

StageJob觸發要祕密?要裝置?
verifyanalyze、test每次 push/MR❌❌
buildios_build（--no-codesign）、android_buildMR / 主分支❌❌
e2eintegration_test（模擬器）手動 / nightly❌*✅
releaseios_release、android_releaserelease tag✅❌

* e2e 若走「登入真後端」，帳密建議鎖一個可拋棄的沙箱帳號、寫死在測試 harness，就不必進祕密。

關鍵：只有快檢是 always-on 的雲端，才適合當 MR 的必過條件。所有 build/release 都用 tag + 手動，不會因為你的 Mac 沒開機而卡住 MR。

三個 Flutter 專屬的地雷（先知道，各節細講）​

  1. iOS 在 CI 不能用 Automatic 簽章。Automatic 要 Xcode 互動登入 Apple ID；CI 是 headless，必須改成 Manual 簽章（或用 fastlane match 集中管理憑證/描述檔）。詳見 iOS 上架。
  2. flutter test 不等於「編得過」。widget/unit test 是 headless 的 Dart，不編譯原生層，CocoaPods 衝突、Swift 版本、Info.plist、Gradle 問題它一律抓不到。要另一個 job 真的 flutter build（iOS 用 --no-codesign）當「編譯保護網」。
  3. e2e 需要裝置、又慢、又常打真後端。別讓它進 merge gate（會被自架機器有沒有開機、模擬器狀態拖累）。用手動或 nightly schedule。詳見 裝置測試。

GitHub ↔ GitLab 名詞對照（速查）​

後面各節會並列兩種語法，先記這張對照表：

概念GitLab CI/CDGitHub Actions
設定檔.gitlab-ci.yml（單一檔）.github/workflows/*.yml（可多檔）
執行單位job（歸在 stage）job（歸在 workflow，可設 needs 排序）
觸發workflow: / rules:on:（push / pull_request / tags…）
只在某條件跑rules: - if: …on: + if:（job/step 層級）
hosted 機器image:（Linux）；無免費 macOSruns-on: ubuntu-latest / macos-14
自架機器tags: [...] 指名runs-on: [self-hosted, macOS]
機密Settings → CI/CD → Variables（Masked/Protected/File）Settings → Secrets and variables → Actions secrets
只給受保護 ref變數勾 Protected + Protected branches/tagsEnvironments + required reviewers
手動關卡job when: manual（+ allow_failure）Environments 的 required reviewers
產物artifacts:actions/upload-artifact
快取cache:actions/cache（或 setup 動作內建）
